## What Redis is

An in-memory data structure server: strings, hashes, lists, sets, sorted sets, streams, bitmaps, HyperLogLogs, geospatial indexes, plus pub/sub, Lua scripting, transactions (`MULTI`/`EXEC`), and optional persistence. Single-threaded command execution (I/O threads aside) means every command is atomic and ordering is total, which is why Redis is the natural home for counters, locks and rate limiters. Latency is sub-millisecond; throughput hundreds of thousands of operations per second per node. Valkey is the open-source fork (Linux Foundation) that AWS and others now ship alongside Redis OSS; the API is the same.

## Production configuration

- **Memory**: `maxmemory` set below the instance's RAM (leave headroom for replication buffers and fork overhead); `maxmemory-policy allkeys-lru` for pure caches, `volatile-lru`/`volatile-ttl` when some keys must never be evicted (sessions with TTL evicted before config without TTL), `noeviction` only for queues/locks where losing data is worse than errors. Monitor `used_memory`, `evicted_keys`, fragmentation ratio.
- **Persistence**: none for pure caches (fast restart, repopulate); **AOF** (`appendonly yes`, `everysec`) for sessions, queues and anything you would rather not lose; RDB snapshots for backups. On ElastiCache, enable backups where data matters.
- **Replication and HA**: primary plus replicas across AZs with automatic failover (Sentinel self-managed; ElastiCache Multi-AZ). Replication is asynchronous: a failover can lose the last writes; clients must reconnect (use a client with topology refresh or the ElastiCache primary endpoint).
- **Cluster mode**: shards data across nodes by key hash slot for datasets beyond one node or very high throughput; multi-key operations must target the same slot (`{hashtag}` in key names); clients must be cluster-aware. Start without cluster mode; move when memory or throughput requires.
- **Security**: never on a public IP (exposed Redis instances are compromised within minutes); TLS in transit; `requirepass`/ACL users (Redis 6+) with least-privilege command sets per application (`+@read +@write -@dangerous`); disable or rename `FLUSHALL`, `CONFIG`, `KEYS`, `DEBUG` for application users; private subnets and security groups (Part VII chapter 6).
- **Timeouts**: client connect/read timeouts of tens of milliseconds for cache paths; `timeout` for idle clients; `tcp-keepalive`.
- **Big keys and slow commands**: avoid `KEYS *` (blocks the server; use `SCAN`), huge values (hundreds of KB) and unbounded collections; `SLOWLOG GET`, `redis-cli --bigkeys`, `LATENCY DOCTOR`; `MEMORY USAGE key`.

## Cache invalidation

Phil Karlton's joke is true because invalidation requires knowing every place a changed fact was copied to. Strategies, roughly in order of preference:

1. **TTL only**: accept staleness up to the TTL; simplest; right for data whose staleness is harmless (catalogue listing, rates refreshed hourly).
2. **TTL + delete on write**: the writer deletes the entity's cache key after committing (Part III chapter 8); the TTL catches missed deletes. Works when keys map one-to-one to entities.
3. **Versioned keys**: include a version in the key (`user:42:v17:profile`); the writer increments the version stored in a small hot key; readers look up the version then the data; old versions expire by TTL. No deletes needed; two lookups per read (or embed the version in a frequently cached parent).
4. **Tag-based invalidation**: track dependencies in sets (`tag:product:9 → {key1, key2…}`); on change, delete all members. Powerful for derived views (a product change invalidates every listing containing it); the sets themselves need bounding and TTLs.
5. **Event-driven**: publish change events (outbox, Part IX chapter 6); cache maintainers subscribe and invalidate or update. Decoupled; eventually consistent; more moving parts.
6. **Write-through / refresh-ahead**: the cache is updated on write or proactively refreshed; coherence by construction for the paths that go through it, at the cost of making the cache part of the write path.

Rules that save you: keys scoped by tenant and user; never cache data whose staleness causes harm you cannot tolerate (authorization decisions beyond seconds, balances, inventory at checkout); jitter TTLs; single-flight hot keys; and measure hit rates per key family to see whether each cache earns its complexity.

## Distributed locks, honestly

`SET lock NX PX 30000` gives a lock on a single Redis node. It fails if the node fails over before replication (two holders), if the holder pauses (GC, network) longer than the TTL (expired lock, two holders), or if release is not token-checked (deleting someone else's lock). Use Redis locks for **efficiency** (avoid duplicate work) with idempotent operations, not for **correctness** of invariants; for correctness use the database (row locks, unique constraints, conditional updates) or a consensus store. Redlock over multiple independent nodes is debated; the database is usually the better answer.

```lua
-- release only if we hold it
if redis.call('GET', KEYS[1]) == ARGV[1] then return redis.call('DEL', KEYS[1]) else return 0 end
```

## Operating Redis

Metrics: `used_memory` vs `maxmemory`, `evicted_keys`, `keyspace_hits/misses` (hit ratio per workload, not globally), `connected_clients`, `instantaneous_ops_per_sec`, `rejected_connections`, replication lag (`master_repl_offset` vs replica), `latency` percentiles from the client side, CPU (single-threaded: 100% of one core is saturation). ElastiCache exposes these in CloudWatch (`EngineCPUUtilization`, `DatabaseMemoryUsagePercentage`, `Evictions`, `CurrConnections`, `ReplicationLag`). Alarm on memory > 80%, evictions when they should not happen, CPU > 80%, replication lag, and connection count near `maxclients`. Failover tests: force a failover in staging and verify clients recover.

## When not to use Redis

As the system of record (it is not durable enough by default and does not do constraints); for large objects (keep blobs in S3); for complex queries; as a message broker where durability and ordering across failures matter (SQS/Kafka); when a local in-process cache would do (feature flags, config).

## Common mistakes

- Redis exposed publicly or without AUTH/TLS.
- No `maxmemory`; the host OOMs instead of evicting.
- `noeviction` on a cache; writes fail when full.
- Caching without TTLs; stale forever.
- `KEYS *` in production code.
- Sessions on a single node without replication or persistence.
- Multi-key operations across slots in cluster mode.
- Redis locks for correctness; duplicate payments.
- Hit ratio measured globally; one noisy key family hides a useless cache.
