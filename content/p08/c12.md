# Performance Tuning and Database Scaling

:::objectives
- Diagnose database performance problems from symptoms to causes using metrics, wait events and query statistics.
- Fix the common application-side causes: N+1 queries, missing indexes, over-fetching, chatty transactions, connection churn.
- Tune the server sensibly: memory, autovacuum, checkpoints, and the handful of parameters that matter on managed services.
- Follow a scaling ladder from a single instance to replicas, caching, partitioning and beyond, with the cost and complexity of each rung.
:::

## Where the time goes

Database slowness has a small number of causes: the query reads too much (missing index, bad plan), too many queries (N+1, chatty code), waiting (locks, I/O, CPU saturation), too many connections, or the working set no longer fits in memory. The method: measure which, then fix that, then measure again. Guesswork (bigger instance first) is expensive and often wrong.

## Application-side causes (most of them)

**N+1 queries**: load 100 orders, then one query per order for its customer: 101 round trips. Symptom: thousands of fast identical queries per request in `pg_stat_statements`; trace shows a staircase of tiny spans. Fix: eager loading (`selectinload`/`joinedload` in SQLAlchemy, `select_related`/`prefetch_related` in Django, `include` in Prisma), or an explicit `WHERE id = ANY($1)` batch, or a join. Detect with query counters in tests (assert a request issues fewer than N queries).

**Over-fetching**: `SELECT *` on wide rows, loading entire tables to filter in Python, fetching 10,000 rows to show 20. Fix: select needed columns, filter and paginate in SQL (keyset), aggregate in the database.

**Chatty transactions**: many small statements in one transaction with network round trips between them; a transaction held across an external call (Part III chapter 13). Fix: fewer, set-based statements; shorter transactions.

**Connection churn**: opening a connection per request or per Lambda invocation (chapter 6).

**Lock contention**: hot rows updated by every request (a counters table), long transactions, lock-order deadlocks (chapter 5). Fix: shard counters, use Redis for high-frequency counts, shorten transactions.

**Missing indexes and bad plans**: chapter 4.

**Unbounded growth**: tables that only grow (events, logs) slowing every query and vacuum; retention and partitioning (chapters 8 and 10).

## Server-side tuning that matters

On managed services most parameters are set sensibly by instance class; the handful worth reviewing:

- **Memory**: `shared_buffers` (RDS default ~25% of RAM is reasonable), `work_mem` (per sort/hash per query: raise for reporting roles via `ALTER ROLE … SET work_mem`, not globally, to avoid memory blow-ups under concurrency), `effective_cache_size` (tells the planner how much cache exists; RDS sets it), `maintenance_work_mem` (faster index builds and vacuum).
- **Autovacuum**: more aggressive on hot tables (`autovacuum_vacuum_scale_factor = 0.02`, `autovacuum_vacuum_cost_limit` higher) so bloat and stale statistics do not accumulate; monitor `n_dead_tup` and last autovacuum times; watch for transaction ID wraparound warnings (a database that stops accepting writes is the end state of neglected vacuum).
- **Checkpoints**: `checkpoint_timeout` 15 min and `max_wal_size` large enough that checkpoints are time-based, not size-based (frequent checkpoints cause I/O spikes); `checkpoint_completion_target 0.9`.
- **Planner**: `random_page_cost` 1.1 on SSD (RDS sets it); statistics targets for skewed columns; `CREATE STATISTICS` for correlated columns.
- **Logging**: `log_min_duration_statement`, `log_lock_waits`, `pg_stat_statements` (chapters 1 and 4).
- **Connections**: `max_connections` is not a performance knob; poolers are (chapter 6).

MySQL equivalents: `innodb_buffer_pool_size` (~70% of RAM on a dedicated host), `innodb_log_file_size`, `innodb_flush_log_at_trx_commit` (1 for durability), the slow query log, `performance_schema`.

## Caching as a database tool

The cheapest read scaling is not reading: Part III chapter 8 and chapter 11. Cache hot entities and expensive aggregates with short TTLs and delete-on-write; keep the database for the source of truth and for writes. Measure the database QPS saved, not the hit ratio.

Most client systems live between rungs 0 and 3 for their whole life. The ladder is also a communication tool: show the client where the system is, what the next rung costs, and what metric would trigger it.

## Load testing the database

Before launch and before raising scaling limits: a load test (Part XI chapter 8) with production-shaped data (volumes and distributions matter: a 1,000-row dev database hides every plan problem) and realistic query mix; watch `pg_stat_statements`, wait events, connections and host metrics during the run; find the knee where latency climbs; set alarms below it. Tools: `pgbench` for raw capacity, application-level load tests (k6) for real queries.

## Common mistakes

- Bigger instance first; the N+1 stays and the bill doubles.
- Tuning server parameters while the top query does a sequential scan.
- Global `work_mem` raised; memory exhaustion under concurrency.
- Autovacuum left at defaults on a table updated a million times an hour; bloat and stale plans.
- Reports on the primary during business hours.
- Scaling decisions without `pg_stat_statements` or Performance Insights ever enabled.
- Load tests on tiny data.
- Sharding discussed before indexes are right.

## Exercises

1. Add a query counter to your test suite and fail tests when a request exceeds a threshold; find and fix one N+1.
2. Run a load test against a production-shaped copy while recording `pg_stat_statements`, wait events and host metrics; identify the knee and the top three queries; fix one and re-run.
3. Write your system's position on the scaling ladder with the metric and threshold that would trigger the next rung, and the cost of that rung.
