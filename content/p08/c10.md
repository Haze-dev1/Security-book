# Database Security and Data Retention

:::objectives
- Harden a database: network isolation, authentication, least-privilege roles, encryption, auditing and patching.
- Protect sensitive columns with field-level encryption, masking and access separation.
- Implement data retention and deletion as database mechanisms, not intentions.
- Audit a database's security posture quickly.
:::

:::prereq
Part IV chapters 11, 16, 17, 22, 23; Part III chapter 15; chapters 1 and 5 of this part.
:::

## The database is the target

Everything else exists to protect what is in the database. Application vulnerabilities become data breaches here; a leaked database credential is the breach itself. Database security is layers: nobody can reach it (network), only the right identities can connect (authentication), each identity can do only its job (authorisation), data is unreadable where it rests and travels (encryption), everything is recorded (audit), and the software is current (patching). Plus the part teams skip: data that no longer needs to exist is deleted.

## Network

Private subnets with no Internet route (Part VII chapter 5); security group allowing the port only from application and worker security groups and from a controlled administrative path (SSM port forward, bastion, VPN); no public endpoint, ever (`publicly_accessible = false`); `rds.force_ssl` / `ssl = on` with `verify-full` on clients; VPC Flow Logs capturing connection attempts.

## Authentication

No shared superuser used by applications. Options in order of preference: **IAM database authentication** (short-lived tokens, no passwords, per-role audit); **managed, rotated secrets** (Secrets Manager rotation for RDS; apps re-read on failure); long-lived passwords only where unavoidable, strong and rotated. PostgreSQL `pg_hba.conf` (self-managed) restricts which users may connect from which networks with which methods (`scram-sha-256`, never `md5` or `trust`). The master user is for administration and emergencies, stored in a secrets manager, used rarely and audited.

## Authorisation: roles that match jobs

```sql
-- Roles per function; no login role owns tables except the migrator
CREATE ROLE app_owner NOLOGIN;                                   -- owns schema objects
CREATE ROLE app_migrator LOGIN IN ROLE app_owner;                 -- runs migrations (DDL)
CREATE ROLE app_rw LOGIN;                                         -- the application: DML only
CREATE ROLE app_ro LOGIN;                                         -- reporting, analysts, replicas' readers
CREATE ROLE app_support LOGIN;                                    -- support tooling with limited, audited access

GRANT USAGE ON SCHEMA app TO app_rw, app_ro, app_support;
GRANT SELECT, INSERT, UPDATE, DELETE ON ALL TABLES IN SCHEMA app TO app_rw;
GRANT SELECT ON ALL TABLES IN SCHEMA app TO app_ro;
GRANT SELECT (id, tenant_id, email, created_at) ON app.customers TO app_support;   -- column-level: no address, no notes
ALTER DEFAULT PRIVILEGES FOR ROLE app_owner IN SCHEMA app GRANT SELECT, INSERT, UPDATE, DELETE ON TABLES TO app_rw;   -- future tables
ALTER DEFAULT PRIVILEGES FOR ROLE app_owner IN SCHEMA app GRANT SELECT ON TABLES TO app_ro;
REVOKE ALL ON SCHEMA public FROM PUBLIC;                          -- nobody creates in public by default
ALTER ROLE app_rw SET statement_timeout = '30s';
ALTER ROLE app_rw SET idle_in_transaction_session_timeout = '60s';
ALTER ROLE app_ro SET statement_timeout = '5min';
-- Row-level security for tenant isolation (Part III chapter 15); app_rw is not the owner, so RLS applies
```

The application role cannot `DROP`, `TRUNCATE`, `ALTER`, create extensions, read other schemas, or escalate; a SQL injection in the application (Part IV chapter 11) is bounded accordingly. Audit grants periodically (`\dp`, `information_schema.role_table_grants`); remove roles for departed people and dead integrations.

## Encryption

**At rest**: storage encryption with a customer managed KMS key (RDS at creation; cannot be added later without snapshot-restore); covers data files, backups, snapshots, replicas, logs. Protects against media and snapshot exposure, not against anyone with credentials.

**In transit**: TLS enforced and verified (chapter: Part VII chapter 16).

**Field-level**: for the most sensitive columns (government IDs, bank details, health data, third-party tokens) encrypt in the application with envelope encryption (Part IV chapter 16) so that database credentials alone cannot read them; store ciphertext; search via blind indexes (HMAC of the value) when equality lookups are required. `pgcrypto` can encrypt in the database, but then the database (and anyone with its credentials and the key) can decrypt; application-level encryption with keys in KMS keeps the key away from the database.

**Masking and views**: give support and analytics roles views that mask or omit sensitive columns (`SELECT id, left(email, 2) || '***' AS email …`); dynamic data masking features exist in some engines; column-level grants (above) are the simplest tool.

## Auditing

What happened in the database and who did it: **pgAudit** (session and object audit logging of DDL, role changes, reads/writes on sensitive tables) on self-managed and RDS PostgreSQL; `log_connections`/`log_disconnections`; MySQL audit plugins; RDS activity streams (Aurora, near-real-time to Kinesis, tamper-proof) for regulated workloads; CloudTrail for control-plane actions (snapshots, parameter changes, deletions). Ship logs off-box with retention (Part IV chapter 22). Alert on: new roles or grants, failed logins spike, DDL outside deploy windows, access to sensitive tables by unexpected roles, snapshot sharing or export (`ModifyDBSnapshotAttribute`, a known exfiltration path).

## Patching

Minor versions automatically in the maintenance window (RDS `auto_minor_version_upgrade`); majors as planned projects with Blue/Green deployments or logical replication (chapter 8); extensions kept current; self-managed hosts per Part V chapter 12. Database engines publish CVEs; a database two years behind is exposed to known authentication and privilege bugs.

## Retention and deletion

Data retention is a security control (what you do not hold cannot leak) and a legal obligation (Part IV chapter 23). Make it mechanical:

- **Define** retention per table or data class in the schema documentation (`events: 90 days; audit: 7 years; sessions: 30 days; deleted customers: hard-delete 30 days after soft delete`).
- **Implement** with partitions dropped on schedule (chapter 8), scheduled batched deletes (`pg_cron` or an application job), TTLs where the store supports them (DynamoDB, Redis), and S3 lifecycle for exports and backups.
- **Propagate** deletion to replicas (automatic), caches, search indexes, analytics copies, backups (expire on rotation; document the window), and processors (Part IV chapter 23).
- **Verify** with a periodic query that nothing older than the policy exists, and record the proof.
- **Anonymise** where records must persist for integrity (orders of a deleted customer: replace PII with tokens, keep the financial facts).

```sql
-- pg_cron (available on RDS): nightly retention job in batches
SELECT cron.schedule('retention-events', '15 3 * * *', $$
  DELETE FROM app.events WHERE id IN (SELECT id FROM app.events WHERE occurred_at < now() - interval '90 days' LIMIT 20000)
$$);
SELECT cron.schedule('hard-delete-customers', '45 3 * * *', $$
  SELECT app.hard_delete_customers(now() - interval '30 days')     -- function anonymises orders, deletes PII rows, logs counts
$$);
```

## Backups and exports as data

Backups contain everything; a leaked backup is a full breach. Encrypted, access-restricted, in a separate account (chapter 9). Exports for analysts, migrations and support tickets are the most common uncontrolled copies: provide masked exports by default, require approval and logging for raw exports, and expire them (presigned URLs, short-lived buckets).

## The database security audit

```checklist
# Database security review
- No public endpoint; private subnets; SG only from app/worker/admin paths; flow logs on.
- TLS enforced and verified; IAM auth or rotated secrets; master credential in a secrets manager and unused by applications.
- Roles per function; application role DML-only on its schema; no superuser or owner privileges for runtime roles; RLS where multi-tenant; column grants for support.
- statement_timeout and idle_in_transaction_session_timeout on application roles.
- Encryption at rest with a customer managed key; field-level encryption for the most sensitive columns; masked views for analysts.
- pgAudit/activity streams on for DDL, role changes and sensitive tables; logs shipped and retained; alerts on grants, DDL off-window, snapshot sharing.
- Minor versions current; major version in support; extensions current.
- Retention defined per table and implemented mechanically; verification query passes; deletion propagated to caches/indexes/exports.
- Backups encrypted, cross-account, immutable, restore-tested; exports masked by default and expiring.
- Access review done this quarter: roles, grants, people, integrations.
```

## Common mistakes

- Application connecting as the master user; injection becomes total compromise.
- Public endpoint "for the dashboard tool".
- Unencrypted at creation; discovered at audit time.
- Retention "policy" in a document with no job behind it; a decade of PII.
- Snapshots shared publicly or to the wrong account (a real exfiltration vector; AWS Config rule `rds-snapshots-public-prohibited`).
- Raw production dumps given to analysts and contractors.
- No audit logging; "who read this record" unanswerable.
- Roles and grants never reviewed; former contractors' logins still valid.

2. Enable pgAudit for DDL and for reads on a sensitive table; perform actions and locate them in the shipped logs.
