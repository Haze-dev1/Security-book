## Why relational

Business data is relationships: customers have orders, orders have items, items reference products, payments reference orders. The relational model stores each kind of thing once, in a table with a declared schema, and expresses relationships with keys; constraints make invalid states unrepresentable (an order cannot reference a customer that does not exist; a quantity cannot be negative); transactions make multi-table changes atomic; SQL answers questions nobody anticipated when the schema was designed. Fifty years on, it is still the best default for the system of record. NoSQL stores (chapter 2) trade some of these properties for specific gains; choose them deliberately, not by default.

## The model

- **Table** (relation): a set of rows with declared columns and types.
- **Primary key**: uniquely identifies a row. Prefer generated identifiers: `bigint GENERATED ALWAYS AS IDENTITY` or UUIDv7 (time-ordered, avoids index fragmentation of random UUIDv4). Natural keys (email, national ID) change; use them as unique constraints, not as the primary key.
- **Foreign key**: a column referencing another table's primary key, with declared behaviour on delete/update (`RESTRICT`, `CASCADE`, `SET NULL`). Enforced by the database, every time, regardless of which application writes.
- **Constraints**: `NOT NULL`, `UNIQUE`, `CHECK (qty > 0)`, exclusion constraints; the cheapest, most reliable validation you will ever write because it cannot be bypassed.
- **Indexes**: separate structures for fast lookup (chapter 4).
- **Views**: saved queries; **materialised views**: precomputed and refreshed.
- **Schemas** (PostgreSQL namespaces): group tables (`app`, `audit`, `analytics`) for organisation and permissions.

```sql
CREATE TABLE customers (
  id          bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  tenant_id   uuid NOT NULL REFERENCES tenants(id),
  email       citext NOT NULL,
  name        text NOT NULL,
  created_at  timestamptz NOT NULL DEFAULT now(),
  UNIQUE (tenant_id, email)
);
CREATE TABLE orders (
  id           uuid PRIMARY KEY DEFAULT uuidv7(),          -- PostgreSQL 18 has uuidv7(); earlier: use an extension or app-generated
  tenant_id    uuid NOT NULL REFERENCES tenants(id),
  customer_id  bigint NOT NULL REFERENCES customers(id) ON DELETE RESTRICT,
  status       text NOT NULL CHECK (status IN ('pending','paid','shipped','cancelled')),
  total_cents  bigint NOT NULL CHECK (total_cents >= 0),
  currency     char(3) NOT NULL,
  created_at   timestamptz NOT NULL DEFAULT now(),
  updated_at   timestamptz NOT NULL DEFAULT now()
);
CREATE INDEX orders_tenant_created_idx ON orders (tenant_id, created_at DESC);
```

Choices visible there: `timestamptz` (never `timestamp` without time zone), money as integer minor units (never float), `citext` for case-insensitive emails, tenant scoping on every table (Part III chapter 15), a composite index matching the dominant query.

For new client systems, PostgreSQL is the default recommendation unless the client's team, tooling or existing systems favour MySQL. Both are excellent; the operational discipline in the following chapters matters more than the choice.

## SQL you will actually use

```sql
-- Upsert (idempotent writes, Part III chapter 3)
INSERT INTO settings (tenant_id, key, value) VALUES ($1, $2, $3)
ON CONFLICT (tenant_id, key) DO UPDATE SET value = EXCLUDED.value, updated_at = now();

-- Returning generated values
INSERT INTO orders (...) VALUES (...) RETURNING id, created_at;

-- Keyset pagination (Part III chapter 2)
SELECT * FROM orders WHERE tenant_id = $1 AND (created_at, id) < ($2, $3) ORDER BY created_at DESC, id DESC LIMIT 50;

-- Conditional update as an atomic check (Part III chapter 13)
UPDATE inventory SET reserved = reserved + $2 WHERE sku = $1 AND on_hand - reserved >= $2 RETURNING on_hand - reserved;

-- Window functions: running totals, ranks, deduplication
SELECT id, customer_id, total_cents, SUM(total_cents) OVER (PARTITION BY customer_id ORDER BY created_at) AS running_total FROM orders;
SELECT DISTINCT ON (customer_id) customer_id, id, created_at FROM orders ORDER BY customer_id, created_at DESC;  -- latest order per customer

-- CTEs for readability; JSONB queries
WITH recent AS (SELECT * FROM orders WHERE created_at > now() - interval '7 days')
SELECT status, count(*) FROM recent GROUP BY status;
SELECT id FROM events WHERE payload @> '{"type": "refund"}' ;           -- GIN index on payload makes this fast

-- Locking a row for a workflow step
SELECT * FROM jobs WHERE status = 'queued' ORDER BY created_at FOR UPDATE SKIP LOCKED LIMIT 1;

-- Safe bulk delete in batches
DELETE FROM events WHERE id IN (SELECT id FROM events WHERE created_at < now() - interval '90 days' LIMIT 5000);
```

## Working with the database in production

```sql
-- what is running
SELECT pid, now() - query_start AS duration, state, wait_event_type, left(query, 100) FROM pg_stat_activity WHERE state <> 'idle' ORDER BY duration DESC;
-- connections by application and state
SELECT application_name, state, count(*) FROM pg_stat_activity GROUP BY 1, 2;
-- biggest tables and indexes
SELECT relname, pg_size_pretty(pg_total_relation_size(oid)) FROM pg_class WHERE relkind = 'r' ORDER BY pg_total_relation_size(oid) DESC LIMIT 10;
-- top queries by total time (pg_stat_statements)
SELECT calls, round(total_exec_time) AS total_ms, round(mean_exec_time, 2) AS mean_ms, left(query, 100) FROM pg_stat_statements ORDER BY total_exec_time DESC LIMIT 10;
-- terminate a runaway
SELECT pg_cancel_backend(pid); SELECT pg_terminate_backend(pid);
```

Set `statement_timeout` and `idle_in_transaction_session_timeout` per application role; name connections with `application_name`; keep `pg_stat_statements` on; treat the database's logs (slow queries, errors, connections) as first-class (Part V chapter 9).

## Common mistakes

- `timestamp` without time zone; floats for money; `varchar(255)` everywhere by habit.
- Random UUIDv4 primary keys on huge tables (index bloat); or exposing sequential IDs publicly (Part III chapter 2).
- No foreign keys "for performance"; orphaned rows forever.
- Validation only in the application; constraints missing; bad data from the second writer.
- ORMs hiding N+1 queries (chapter 12) and transaction scope (Part III chapter 13).
- Choosing MySQL or PostgreSQL by familiarity alone without checking the client's constraints.
- Running `DELETE`/`UPDATE` without `WHERE` or without a transaction in a production shell.

## Exercises

1. Design and create the schema for a small order system with tenant scoping, proper types, constraints and foreign keys; try to insert invalid data and watch each constraint reject it.
2. Run `EXPLAIN ANALYZE` on a query before and after `ANALYZE` on a table whose statistics you deliberately let go stale (insert a million rows with autovacuum disabled). Compare plans.
3. Enable `pg_stat_statements` on a development database, run an application workload, and list the top ten queries by total time.
