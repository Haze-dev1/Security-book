# Schema Design and Relationships

:::objectives
- Design normalised schemas that model the business correctly, and denormalise deliberately for read paths.
- Model one-to-many and many-to-many relationships, hierarchies, history and soft deletes.
- Choose types for identifiers, time, money, text, enums and flexible attributes.
- Evolve schemas safely over years without rewrites.
:::

:::prereq
Chapter 1; Part III chapter 2.

## The problem

Schema mistakes outlive code. A column that should have been a table, a missing tenant key, a float for money, a `status` string with twelve spellings, a soft-delete flag nobody filters on: each becomes a migration project once data exists. Good schema design is boring: a few principles applied consistently, documented, and reviewed before the first row is written.

## Normalisation, pragmatically

Normalisation removes duplication so a fact lives in one place. In practice: each table represents one kind of thing; each column depends on the whole key; repeating groups become child tables; attributes of other things live in those things' tables. Third normal form is the working target for transactional schemas. The payoff is integrity (one update changes the fact everywhere) and flexibility (new queries do not require new copies).

Denormalise **deliberately** for specific reads: a `customers.order_count` maintained by trigger or application for a dashboard; a snapshot of product name and price copied into `order_items` because an order must show what was sold *then*; a materialised view for reporting. Each denormalisation is a documented decision with a maintenance mechanism and a reconciliation check.

## Relationships

- **One-to-many**: foreign key on the many side (`orders.customer_id`). Index the foreign key (PostgreSQL does not do this automatically; MySQL does).
- **Many-to-many**: a junction table with a composite primary key and both foreign keys (`order_tags(order_id, tag_id)`), plus any attributes of the relationship (`added_at`). Index both directions as needed.
- **One-to-one**: usually the same table; a separate table for optional or sensitive data (`customer_payment_profiles`) or very wide rarely-used columns.
- **Hierarchies** (categories, org charts): adjacency list (`parent_id`) with recursive CTEs for most cases; closure tables or `ltree` for heavy traversal.
- **Polymorphic associations** (a comment on an order or a product): avoid `(target_type, target_id)` without foreign keys; prefer separate junction tables per target or a supertype table.

```sql
CREATE TABLE order_items (
  order_id    uuid NOT NULL REFERENCES orders(id) ON DELETE CASCADE,
  line_no     smallint NOT NULL,
  product_id  bigint NOT NULL REFERENCES products(id),
  sku         text NOT NULL,               -- snapshot: what was sold
  name        text NOT NULL,               -- snapshot
  qty         integer NOT NULL CHECK (qty > 0),
  unit_cents  bigint NOT NULL CHECK (unit_cents >= 0),
  PRIMARY KEY (order_id, line_no)
);
CREATE INDEX order_items_product_idx ON order_items (product_id);

CREATE TABLE order_tags (
  order_id uuid REFERENCES orders(id) ON DELETE CASCADE,
  tag_id   bigint REFERENCES tags(id) ON DELETE CASCADE,
  added_at timestamptz NOT NULL DEFAULT now(),
  PRIMARY KEY (order_id, tag_id)
);
CREATE INDEX order_tags_tag_idx ON order_tags (tag_id);
```

## Types

| Concern | Use | Avoid |
|---|---|---|
| Primary keys | `bigint identity`, or UUIDv7 when IDs are generated by clients or must be unguessable | UUIDv4 on hot tables (random inserts fragment indexes); natural keys |
| Public identifiers | Prefixed random IDs (`ord_01HZX…`) or UUIDs; map to internal keys if needed | Sequential integers exposed in URLs |
| Time | `timestamptz` (stored UTC); `date` for dates; `interval` for durations | `timestamp` without zone; strings; epoch ints unless required |
| Money | `bigint` minor units with a `currency char(3)`, or `numeric(19,4)` | `float`, `double` |
| Text | `text` with `CHECK (length(x) <= n)` where limits matter; `citext` for case-insensitive | `varchar(255)` by reflex; `char(n)` padding |
| Enumerations | `text` with a `CHECK` constraint, or a lookup table (when values carry attributes or change often); PostgreSQL `enum` only if the set is truly static | Magic integers; free text |
| Booleans | `boolean NOT NULL DEFAULT false` | Nullable booleans (three states) |
| Flexible attributes | `jsonb` with a GIN index, validated by application schema | Entity-attribute-value tables; one column per possible attribute |
| Large blobs | S3 with a key column | `bytea` in hot tables |
| Arrays | PostgreSQL arrays for small, owned lists | Arrays as a substitute for junction tables |

## Multi-tenancy

Every tenant-scoped table carries `tenant_id NOT NULL` with it first in composite indexes and unique constraints (`UNIQUE (tenant_id, email)`), foreign keys include it where child and parent must share a tenant (composite foreign keys), and row-level security enforces it (Part III chapter 15).

## Soft deletes, history and audit

**Soft delete** (`deleted_at timestamptz`): keeps data for recovery and references; every query must filter it (views or RLS help; forgotten filters are the classic bug); unique constraints need partial indexes (`UNIQUE (tenant_id, email) WHERE deleted_at IS NULL`); hard-delete on a schedule for privacy (Part IV chapter 23). Use when undo or referential integrity matters; otherwise hard delete.

**History**: for "what did this look like on March 3rd?", either an audit/history table written by trigger or application on every change (row snapshots with `valid_from`/`valid_to`), or event sourcing for domains that need it. **Audit** of who changed what belongs in a separate append-only table (Part IV chapter 22). Temporal tables (system-versioned) exist in MariaDB and via extensions in PostgreSQL.

`created_at` and `updated_at` on every table, maintained by defaults and a trigger (or the application), are cheap and endlessly useful.

## Constraints as documentation

A schema with `NOT NULL`, `CHECK`, `UNIQUE` and foreign keys documents the business rules in the one place every writer must pass. Add `COMMENT ON TABLE/COLUMN` for meaning and ownership; generate schema docs from the catalogue. Name constraints explicitly (`orders_status_check`) so error messages and migrations are readable.

## Designing for evolution

Schemas change for years. Habits that keep changes cheap: additive changes first (new nullable column, new table) and removal later (expand/contract, Part X chapter 8); no `SELECT *` in application code; views for stable interfaces over changing tables when external consumers read the database (better: no external consumers of the database at all; use the API); avoid wide "god tables" (split by access pattern); keep lookup data in tables so adding a value is data, not a deploy; version JSONB document shapes with a `schema_version` key.

## Review checklist

```checklist
# Schema review
- Every table: primary key, tenant_id (if multi-tenant), created_at/updated_at, meaningful constraint names, comments.
- Types per the table above: timestamptz, integer money, text with checks, booleans NOT NULL.
- Foreign keys on every relationship with explicit ON DELETE behaviour; indexes on foreign keys.
- Unique constraints express business uniqueness (scoped by tenant); partial where soft deletes exist.
- Indexes match the known queries (tenant first; chapter 4), no speculative indexes.
- Denormalisations documented with their maintenance mechanism.
- No polymorphic (type, id) pairs without integrity; no EAV tables.
- Soft-delete filtering strategy decided (view/RLS) and privacy hard-delete scheduled.
- Public identifiers unguessable; internal keys stable.
- Migration plan is additive; rollback considered.
```

## Common mistakes

- Missing foreign keys and indexes on them.
- Enum-like strings with inconsistent casing and no check.
- `timestamp` without time zone; servers in different zones; off-by-hours bugs.
- Money in floats; totals that do not add up.
- Soft-delete flag without a filtering mechanism; deleted users still receive emails.
- One giant `users` table with sixty columns from every feature.
- EAV or JSONB for everything; no constraints; every query a parsing exercise.
- Schema designed around the first UI screen rather than the domain.
