## Why replicate

Three reasons: **availability** (a standby to fail over to), **durability** (a copy on another machine or AZ), and **read scaling** (serve reads from replicas). A single database node is a single point of failure and a ceiling on read throughput; replication addresses both at the cost of consistency subtleties and operational complexity.

## Physical (streaming) replication

The primary ships its WAL to replicas, which replay it, producing byte-identical copies (same major version, whole cluster). **Asynchronous**: the primary commits without waiting; replicas lag by milliseconds to seconds (or minutes under heavy write load or long replica queries). **Synchronous**: the primary waits for at least one replica to confirm receipt (or apply) before acknowledging commit: zero data loss on failover at the cost of latency and a dependency on the replica's availability (configure a quorum or a fallback). RDS Multi-AZ is synchronous replication to a standby that does not serve reads; RDS read replicas are asynchronous and do.

**Failover**: promote a replica to primary; repoint applications (DNS endpoint change, or a proxy that follows the primary). With async replication, transactions not yet shipped are lost (RPO > 0); clients must handle the connection break (Part VIII chapter 6). Automated failover needs a fencing mechanism so the old primary cannot accept writes after promotion (split brain); managed services handle this; self-managed setups use Patroni, repmgr or Stolon.

## Logical replication

Replicates row changes (not WAL bytes) for selected tables via publications and subscriptions; works across major versions and to different schemas; the subscriber is writable. Uses: zero-downtime major version upgrades (replicate to a new version, switch over), selective replication to reporting systems, change data capture (Debezium → Kafka) for event-driven integration, migrating between providers. Costs: DDL is not replicated (coordinate schema changes), sequences are not replicated, conflicts possible if the subscriber is also written, and initial sync of large tables takes time.

## Read replicas in applications

Routing reads to replicas offloads the primary, but asynchronous lag introduces the classic bug: a user updates their profile (write to primary), the next request reads the profile from a replica that has not caught up, and the change "vanishes". Strategies:

- **Read your own writes**: after a write, pin the session to the primary for a short window (a cookie or a timestamp in the session), or route reads that follow writes to the primary.
- **Replica for non-critical, lag-tolerant reads only**: reports, analytics, dashboards, search indexing, background jobs; keep the request path on the primary unless load demands otherwise.
- **Lag-aware routing**: check `pg_last_wal_replay_lsn()`/lag metric and fall back to the primary when lag exceeds a threshold; some proxies (pgpool, ProxySQL for MySQL) do this.
- **Monitor lag** (`ReplicaLag` in CloudWatch; `pg_stat_replication` on the primary) and alert; long replica queries can delay replay (`max_standby_streaming_delay`), and cancelled replica queries (`hot_standby_feedback`) are the trade-off.

```python
# Simple routing: explicit choice per query; default to primary
class DB:
    def __init__(self, primary, replica): self.primary, self.replica = primary, replica
    def reader(self, *, tolerate_lag: bool):
        return self.replica if tolerate_lag and self.replica_healthy() else self.primary
# usage: db.reader(tolerate_lag=True).fetch("SELECT ... FROM reports ...")   # report
#        db.primary.fetch("SELECT ... FROM accounts WHERE id = $1")          # balance check: never stale
```

Aurora's reader endpoint load-balances across replicas with low lag (typically tens of milliseconds) which makes replica reads more practical, but the consistency rule still applies.

## Partitioning

Partitioning splits one logical table into physical pieces by a key (range on `created_at`, list on `tenant_id` or region, hash on an ID) within a single database. Queries that include the partition key touch only relevant partitions (partition pruning); old partitions can be dropped instantly instead of deleted row by row (retention for events, logs, audit); indexes and vacuum work per partition; very large tables become manageable.

```sql
CREATE TABLE events (
  id uuid NOT NULL, tenant_id uuid NOT NULL, occurred_at timestamptz NOT NULL, type text NOT NULL, payload jsonb,
  PRIMARY KEY (occurred_at, id)                       -- partition key must be part of unique constraints
) PARTITION BY RANGE (occurred_at);
CREATE TABLE events_2026_03 PARTITION OF events FOR VALUES FROM ('2026-03-01') TO ('2026-04-01');
CREATE TABLE events_2026_04 PARTITION OF events FOR VALUES FROM ('2026-04-01') TO ('2026-05-01');
CREATE INDEX ON events (tenant_id, occurred_at DESC);   -- created on each partition
-- retention: DROP TABLE events_2025_03;  (instant, no bloat)
```

Operational notes: create future partitions ahead of time (pg_partman automates it); queries without the partition key scan all partitions; too many partitions (thousands) slow planning; foreign keys referencing partitioned tables have constraints; unique constraints must include the partition key. Partition when a table is tens of millions of rows with time- or tenant-based access and retention needs, not before.

## Sharding

Sharding splits data across **multiple databases** by a shard key (tenant ID, user ID range, hash). It is the only way to scale writes beyond one primary, and it costs: every query must know its shard (no cross-shard joins or transactions without application-level coordination), rebalancing when shards fill is complex, schema changes multiply, backups and monitoring multiply, and uniqueness and reporting become distributed problems. Before sharding: vertical scaling (bigger instance; modern instances are enormous), read replicas, caching, partitioning, archiving cold data, and moving high-volume non-relational data (events, logs) to purpose-built stores. If sharding is still needed, shard by tenant where possible (tenant-per-database or groups of tenants per shard, Part III chapter 15), use a routing layer (Citus distributes PostgreSQL tables transparently; Vitess for MySQL; application-level directories), and plan for rebalancing from day one. Most client systems never need it; saying so, with the evidence, is part of the job.

## Replication and backups are different

Replicas protect against hardware and AZ failure; they faithfully replicate a `DROP TABLE` within milliseconds. Backups and PITR (chapter 9) protect against mistakes and corruption. You need both.

## Common mistakes

- Reading from replicas in the request path without a read-your-writes strategy.
- Treating replicas as backups.
- Synchronous replication with a single replica and no fallback; replica outage halts writes.
- Failover without fencing; two primaries accepting writes.
- Partitioning tiny tables; or partitioning without the partition key in queries.
- Sharding early, before vertical scaling, replicas, caching and partitioning were exhausted.
- Logical replication without coordinating DDL; subscriber breaks on the first schema change.
- Ignoring replica lag alerts until a report shows yesterday's data.
