# Connection Pooling

:::objectives
- Explain why database connections are expensive and why unbounded connections take databases down.
- Size application pools correctly across many instances and workers, and configure them for failover and idle timeouts.
- Deploy an external pooler (PgBouncer or RDS Proxy) and understand transaction versus session pooling.
- Diagnose and resolve connection exhaustion incidents.
:::

Chapters 1 and 5; Part II chapter 6; Part VII chapter 11.

## The problem

A PostgreSQL connection is a server process with its own memory (several MB), authenticated and configured at startup (tens of milliseconds, more with TLS). Opening one per request is slow and wasteful; keeping thousands open consumes memory and CPU on the database and degrades every query (PostgreSQL's performance falls as active backends exceed a few times the core count). `max_connections` exists to protect the server, and when it is hit the error is immediate and total: `FATAL: too many connections`, for every new client. Connection exhaustion is one of the top three database incidents, and it is almost always caused by arithmetic nobody did.

## Pools inside the application

A connection pool keeps a bounded set of open connections per process and lends them to requests:

```python
# SQLAlchemy / asyncpg pool settings worth setting explicitly
engine = create_async_engine(
    url,
    pool_size=5,              # steady connections per process
    max_overflow=5,           # temporary extra under burst (total 10 per process)
    pool_timeout=5,           # wait at most 5 s for a connection, then fail (503) rather than queue forever
    pool_recycle=600,         # recycle connections every 10 min (below any idle timeout on the path: NAT 350 s, proxies, DB idle timeouts)
    pool_pre_ping=True,       # validate before use: detect connections killed by failover or timeouts
    connect_args={"server_settings": {"application_name": "api", "statement_timeout": "30000"}},
)
```

The arithmetic: **total connections = processes × (pool_size + max_overflow) × instances**, plus workers, plus migrations, plus admin sessions, plus replicas' own needs. Example: 4 Gunicorn workers × 10 × 6 ECS tasks = 240 connections from the API alone, before workers. A `db.t4g.medium` RDS instance defaults to roughly 400 `max_connections` (RDS derives it from memory). Scale the API to 12 tasks and the database rejects connections. Rule: compute the total for max autoscaling, keep it under ~70% of `max_connections`, and remember that PostgreSQL performs best with far fewer *active* connections than that (often 2–4× cores); more connections than that means queueing inside the database rather than in your pool.

Pool size per process should be small: an API worker handling I/O-bound requests rarely needs more than 5–10 connections; async applications with one process per task can use a pool of 10–20 shared across all coroutines. `pool_timeout` must be short so that pool exhaustion produces a fast, visible 503 (and a metric) instead of a hung request.

## External poolers

When many processes (dozens of tasks, hundreds of Lambda invocations) each need a pool, the total still exceeds what the database should hold. An external pooler multiplexes: thousands of client connections map onto a few dozen server connections.


**PgBouncer**: lightweight, single-threaded (run several or use `so_reuseport`), configure `pool_mode = transaction`, `default_pool_size` per database/user (20–50 is typical), `max_client_conn` high (thousands), `server_idle_timeout`, `query_wait_timeout`; run it as a sidecar per host/task, or as a central service in the data tier with its own HA (two instances behind an NLB). Authenticate clients to PgBouncer (`auth_type = scram-sha-256`, `auth_query`) and PgBouncer to PostgreSQL with TLS.

**RDS Proxy**: managed, Multi-AZ, with IAM authentication, Secrets Manager integration, connection multiplexing (transaction-level pinning rules), and faster failover (it keeps client connections open while the database fails over, reconnecting server side). Cost per vCPU of the database instance per hour (meaningful for small instances; check pricing). The usual answer for Lambda-to-RDS and for ECS fleets that scale wide.

Application settings behind a transaction-mode pooler: avoid session-level `SET` (use `SET LOCAL` inside transactions), avoid session advisory locks (use transaction-level `pg_advisory_xact_lock`), set the application's own pool to a small size (the pooler does the multiplexing), and keep `pool_pre_ping`.

## Failover and idle timeouts

Multi-AZ failover changes the endpoint's address; existing connections die. Clients need: short DNS caching, `pool_pre_ping` or retry-on-connection-error with backoff, and a connect timeout so a dead address fails fast. Idle connections through NAT or firewalls die silently (Part II chapter 4); `pool_recycle` below the shortest idle timeout plus TCP keepalives (`keepalives_idle=60` in libpq) keep pools healthy. The database's own `idle_in_transaction_session_timeout` kills leaked transactions (chapter 5).

## Connections and Lambda

Each concurrent Lambda execution environment is a process with its own pool; 500 concurrent invocations means 500+ connections. Options: RDS Proxy (the standard fix), reserved concurrency to cap invocations, Data API for Aurora (HTTP, no connections), or DynamoDB for Lambda-heavy designs. Never let Lambda connect directly to a small RDS instance without a cap.

## Diagnosing exhaustion

```sql
SHOW max_connections;
SELECT count(*), state, application_name, usename, client_addr FROM pg_stat_activity GROUP BY 2,3,4,5 ORDER BY 1 DESC;
SELECT count(*) FILTER (WHERE state = 'idle in transaction') AS idle_in_txn, count(*) FILTER (WHERE state = 'idle') AS idle, count(*) FILTER (WHERE state = 'active') AS active FROM pg_stat_activity;
SELECT pid, now()-xact_start AS txn_age, application_name, left(query,80) FROM pg_stat_activity WHERE state = 'idle in transaction' ORDER BY txn_age DESC LIMIT 10;
```

Interpretation: many `idle` connections from one application: pools oversized relative to need (lower pool sizes or add a pooler); many `idle in transaction`: application bug (transaction opened, I/O performed, never committed) or interactive sessions (set the timeout, fix the code); many `active` with long durations: slow queries or locks (chapter 4, 5), not a pooling problem per se; connections from unknown `client_addr`: something else (a BI tool, a developer laptop) is consuming slots. Immediate relief: `pg_terminate_backend` the idle-in-transaction offenders; raise `max_connections` only as a stopgap (it needs a restart on RDS via parameter group and costs memory). Structural fix: pool arithmetic, pooler, timeouts.

## Common mistakes

- Pools sized without multiplying by processes and instances.
- No `pool_timeout`; requests hang when the pool is empty.
- No `pool_pre_ping`/recycle; the first requests after failover or idle fail.
- Lambda directly to RDS at scale.
- Session-level `SET` behind a transaction-mode pooler; mysterious state leakage.
- Raising `max_connections` to 2,000 as the fix; the database slows for everyone.
- Developers' and BI tools' connections uncounted.
- No alarm on connection count.
