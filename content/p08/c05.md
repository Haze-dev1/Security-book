## ACID

- **Atomicity**: all statements in a transaction commit or none do; implemented by WAL and rollback of uncommitted changes on failure.
- **Consistency**: a transaction moves the database from one valid state to another; constraints are checked (immediately or at commit for deferred constraints). Note: this is "constraints hold", not the distributed-systems meaning (Part IX chapter 5).
- **Isolation**: concurrent transactions do not see each other's intermediate states, to a degree chosen by the isolation level.
- **Durability**: once committed, changes survive crashes; WAL fsync before commit acknowledgement (`synchronous_commit`, and synchronous replication for durability across nodes, chapter 8).

## Concurrency: MVCC

Both PostgreSQL and InnoDB implement **multi-version concurrency control**: readers see a snapshot of committed data as of their statement or transaction start, without blocking writers, and writers do not block readers. Updates create new row versions; old versions remain for transactions that might still need them (PostgreSQL in the heap, cleaned by VACUUM; InnoDB in undo logs, purged). Writers block writers on the *same row* (row-level locks) until the first transaction ends.

## Anomalies and isolation levels

| Anomaly | What happens | Read Committed | Repeatable Read | Serializable |
|---|---|---|---|---|
| Dirty read | See uncommitted data from another transaction | prevented | prevented | prevented |
| Non-repeatable read | Same row read twice gives different values within one transaction | **possible** | prevented | prevented |
| Phantom read | Same query returns different *sets* of rows within one transaction | **possible** | prevented (PostgreSQL); possible by SQL standard | prevented |
| Lost update | Two transactions read, compute, write; one overwrites the other | **possible** (without explicit locking or atomic updates) | prevented for the same row (PostgreSQL errors) | prevented |
| Write skew | Two transactions each check a condition over rows and write different rows so that the combined result violates an invariant (two doctors both go off-call because each saw the other on-call) | possible | **possible** | prevented |

Defaults: PostgreSQL **Read Committed**; MySQL InnoDB **Repeatable Read** (with gap/next-key locks that reduce phantoms at the cost of surprising lock waits).

Guidance: Read Committed is right for most OLTP work *when writes are made atomic* (`UPDATE … SET x = x + 1`, conditional updates with `WHERE` checks, `INSERT … ON CONFLICT`). Repeatable Read for reports and multi-statement reads that need one consistent snapshot. **Serializable** for invariants spanning several rows (booking, inventory across variants, balance across accounts) where write skew would be a real bug; PostgreSQL's SSI implementation is cheap enough for targeted use, and the application must **retry** transactions that fail with serialisation errors (`40001`).

```python
# Retry loop for serialisation failures and deadlocks (psycopg)
import psycopg, time, random
def run_serializable(conn, fn, attempts=5):
    for i in range(attempts):
        try:
            with conn.transaction():
                conn.execute("SET TRANSACTION ISOLATION LEVEL SERIALIZABLE")
                return fn(conn)
        except psycopg.errors.SerializationFailure:
            time.sleep(min(0.5, 0.02 * 2**i) + random.random() * 0.02)
        except psycopg.errors.DeadlockDetected:
            time.sleep(0.05 + random.random() * 0.05)
    raise RuntimeError("transaction failed after retries")
```

## Locks

Row locks are taken by `UPDATE`/`DELETE` and by `SELECT … FOR UPDATE` (exclusive) / `FOR SHARE` / `FOR NO KEY UPDATE` / `FOR KEY SHARE`; they last until commit. Table-level locks protect against conflicting DDL (`ALTER TABLE` needs `ACCESS EXCLUSIVE` for many operations: everything waits behind it, and *it* waits behind any running query, which is how a "quick" migration freezes production; chapter 7). Advisory locks (`pg_advisory_xact_lock(key)`) implement application-level mutual exclusion (one job runner per key) without a lock table.

Patterns:

- **Atomic update instead of read-modify-write**: `UPDATE accounts SET balance = balance - 100 WHERE id = $1 AND balance >= 100 RETURNING balance` (Part III chapter 13).
- **Pessimistic lock for a workflow**: `SELECT … FOR UPDATE` on the parent row, do work, commit; keep it short.
- **Queue consumption**: `FOR UPDATE SKIP LOCKED` lets many workers take different rows without blocking.
- **Optimistic concurrency**: a `version` column; `UPDATE … WHERE id = $1 AND version = $2`; zero rows means someone else changed it; the API returns 409 (Part III chapter 2).
- **Consistent lock ordering**: when a transaction must lock several rows, lock them in a fixed order (sorted IDs) to avoid deadlocks.

## Deadlocks

Transaction A holds row 1 and wants row 2; B holds 2 and wants 1. The database detects the cycle after `deadlock_timeout` (1 s) and aborts one with error `40P01`. Causes: inconsistent lock ordering, long transactions touching many rows, foreign key checks acquiring locks on parent rows, batch updates in different orders. Fixes: order locks consistently; shorten transactions; batch by sorted key; retry on deadlock (the aborted transaction is the victim, not a corruption). Diagnose from the PostgreSQL log (`log_lock_waits = on` shows waits over a second with both queries) and `pg_locks` joined to `pg_stat_activity`:

```sql
SELECT blocked.pid AS blocked_pid, blocked.query AS blocked_query, blocking.pid AS blocking_pid, blocking.query AS blocking_query, now() - blocked.query_start AS waiting
FROM pg_stat_activity blocked
JOIN pg_stat_activity blocking ON blocking.pid = ANY(pg_blocking_pids(blocked.pid))
WHERE cardinality(pg_blocking_pids(blocked.pid)) > 0;
```

## Timeouts that protect the database

`statement_timeout` (per role or session; e.g. 30 s for the API, longer for reports), `lock_timeout` (fail fast instead of queueing behind a lock; essential in migrations), `idle_in_transaction_session_timeout` (kill connections that opened a transaction and went idle: the top cause of bloat and lock pile-ups, usually a bug or an interactive session left open). Set them on the application role, not globally, so administrative sessions can override.

## Durability knobs

`synchronous_commit = on` (default) waits for WAL fsync; `off` risks losing the last few hundred milliseconds of commits on a crash in exchange for throughput, acceptable for some logging workloads, never for money. With replicas, `synchronous_standby_names` makes commits wait for a replica to confirm (zero data loss on failover at a latency cost; RDS Multi-AZ does this for you). `fsync = off` is never acceptable in production.

## Common mistakes

- Read-modify-write in application code under Read Committed; lost updates under concurrency.
- Serializable without retry logic; users see random failures.
- Transactions held open across network calls or user think time (Part III chapter 13).
- Long reports on the primary under Repeatable Read blocking vacuum for hours; run them on a replica.
- DDL without `lock_timeout` queueing behind a long query and freezing the application.
- No `idle_in_transaction_session_timeout`; a forgotten `BEGIN` in a psql session holds locks all weekend.
- Deadlocks treated as mysterious; no lock ordering discipline; no retry.
- MySQL's default Repeatable Read and gap locks surprising developers from PostgreSQL (and vice versa).
