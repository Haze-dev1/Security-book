# Backups and Point-in-Time Recovery

:::objectives
- Distinguish logical and physical backups and choose the right combination for a database.
- Implement point-in-time recovery with WAL archiving (self-managed) or managed PITR (RDS/Aurora).
- Run and automate restore drills that prove recoverability and measure RTO.
- Protect backups from the failures that destroy them: same-account storage, missing keys, silent job failure.
:::

:::prereq
Chapter 8; Part V chapter 11.
:::

## Two kinds of backup

**Logical backups** (`pg_dump`, `mysqldump`) export schema and data as SQL or a custom archive. Portable across major versions and architectures; selective (one table, one schema); human-readable; slow to restore at scale (hours for hundreds of GB, because it replays inserts and rebuilds indexes); a snapshot as of the dump's start (consistent within a single transaction). Essential for migrations between providers or versions and as an independent copy; insufficient alone for low RPO.

**Physical backups** copy the data files plus the WAL needed to make them consistent: `pg_basebackup`, filesystem/volume snapshots, RDS automated snapshots. Fast to restore (copy files, replay WAL); same version and architecture only; whole cluster. Combined with **continuous WAL archiving**, physical backups give **point-in-time recovery**: restore the base backup and replay WAL up to any chosen moment before the mistake.

The standard production combination: **managed PITR (or WAL archiving) for low RPO and fast RTO, plus a periodic logical dump stored independently for portability and defence against engine-level corruption**, with copies in another Region and account (Part V chapter 11).

## Self-managed PostgreSQL PITR

```bash
# pgBackRest: full backup weekly, differential daily, WAL archived continuously to S3 (encrypted)
# postgresql.conf
#   archive_mode = on
#   archive_command = 'pgbackrest --stanza=prod archive-push %p'
#   wal_level = replica
# /etc/pgbackrest.conf
#   [global] repo1-type=s3 repo1-s3-bucket=client-a-db-backups repo1-s3-region=eu-west-1 repo1-cipher-type=aes-256-cbc repo1-retention-full=4 process-max=4
#   [prod] pg1-path=/var/lib/postgresql/16/main
pgbackrest --stanza=prod --type=full backup
pgbackrest --stanza=prod --type=diff backup
pgbackrest --stanza=prod info                                    # last backups, WAL archive range
# Restore to a point in time on a fresh server
pgbackrest --stanza=prod --delta --type=time --target="2026-03-14 10:15:00+00" --target-action=promote restore
systemctl start postgresql    # recovers to the target, promotes
```

Monitor: WAL archive failures (`pg_stat_archiver.failed_count`, and the archive command's exit status: a failing archive command fills the disk with unshipped WAL and eventually stops the database), backup job success and age, and repository size. Test restores monthly on a separate instance and time them.

## RDS and Aurora

RDS: enable automated backups (retention 7–35 days), which combines daily snapshots with continuous transaction log upload for PITR to any second within the window; copy snapshots (automated via AWS Backup) to another Region and account for DR; manual snapshots for pre-migration safety points (kept until deleted); `restore-db-instance-to-point-in-time` creates a **new** instance (plan the endpoint switch, security groups, parameter group, which are not all carried over). Aurora adds continuous backup to its storage layer and **fast database cloning** (copy-on-write clones in minutes for testing restores, migrations and analytics on production data without touching production). Encryption follows the source; a snapshot encrypted with a customer managed key needs that key accessible in the destination account/Region (multi-Region keys or re-encryption on copy).

## Restore drills

A restore you have not performed is a hypothesis. The drill (automated monthly, Part V chapter 11):

1. Restore the latest backup/PITR to a fresh instance in an isolated network.
2. Run verification: row counts for key tables versus production at the restore point, checksums of recent rows, application smoke tests against the restored copy, `pg_dump` of the restored copy to confirm it is readable end to end.
3. Record elapsed time (provisioning + recovery + verification) against the RTO; record the RPO achieved (time between the restore point and the newest data available).
4. Destroy the instance; file the results where the client can see them.

Also drill the **operator-error scenario**: "a migration at 14:02 dropped a column; recover the data." Steps: identify the exact time; PITR to 14:01 on a new instance; extract the lost data; reconcile into production (or fail over to the restored instance if the whole database must revert, accepting loss of post-14:02 writes). Knowing the procedure cold is what turns a disaster into a bad afternoon.

## Protecting the backups

- **Different account and Region**, immutable (Object Lock / Vault Lock), so production credentials or ransomware cannot destroy them (Part V chapter 11).
- **Keys**: backups encrypted under a key that will exist when you need it; multi-Region keys; key deletion alarmed.
- **Job monitoring**: alert on *absence* of a successful backup within the expected window, not only on failures (a cron job that never runs produces no failure).
- **Retention** matching the slowest discovery of problems (corruption found after three weeks needs a four-week-old copy) and legal requirements; logical dumps retained longer in cold storage.
- **Access**: a backup role for the jobs; humans via break-glass; restore permissions separate from delete permissions.
- **Consistency**: database-aware methods (PITR, dumps) rather than raw volume snapshots of a live database unless frozen (Part V chapter 6).

## MySQL notes

`mysqldump --single-transaction` (InnoDB) for consistent logical dumps; Percona XtraBackup for hot physical backups; binary log archiving for PITR (`mysqlbinlog` replay to a point); RDS MySQL has the same automated backup and PITR model.

## Common mistakes

- Only nightly dumps; a day of data lost on any failure.
- WAL archiving failing silently; disk fills; database stops.
- Snapshots in the same account; deleted along with production by a compromised key or a cleanup script.
- Restore never tested; the first restore reveals the backup is of the wrong database, unreadable, or takes 19 hours.
- Retention of 7 days when corruption is discovered after 10.
- Encryption key gone; backups unreadable.
- PITR target chosen as "just before the incident" without identifying the exact time from logs.
- Treating replicas as backups (chapter 8).

## Exercises

1. Set up pgBackRest (or WAL-G) with S3 for a test PostgreSQL; take backups; drop a table; perform a PITR to just before the drop; verify.
2. On RDS, restore to a point in time, run verification queries, time the whole procedure, and destroy the instance; record RTO and RPO achieved.
3. Write the operator-error runbook (migration dropped data at a known time) with exact commands, and rehearse it.
