## What NoSQL means

"NoSQL" groups stores that relax parts of the relational model for specific gains: flexible or absent schema, horizontal partitioning built in, simpler data models that map to application objects, and in some cases extreme scale or latency. The gains come with losses: joins (do them in the application or denormalise), multi-record transactions (limited or absent), ad-hoc queries (only along designed access paths), and constraints (your code is the only guard). The decision is architectural, not fashionable: what does this data need?

## Document stores: MongoDB

Documents (BSON) in collections, with a flexible schema (enforceable with JSON Schema validation, which you should use), secondary indexes (including compound, multikey on arrays, text, geospatial), an aggregation pipeline for queries, replica sets for HA (one primary, secondaries, automatic election), sharding for horizontal scale, and multi-document ACID transactions (since 4.0, with performance costs).

Modelling: **embed** data that is read together and owned by the parent (an order with its line items); **reference** data shared across parents or unbounded in size (a customer referenced by many orders; comments that grow forever). The 16 MB document limit and the "unbounded array" anti-pattern are the usual design failures. Denormalise deliberately and accept update anomalies (a product name copied into orders is a snapshot, which is often *correct* for orders).

```javascript
// Order document with embedded items and a referenced customer; schema validation enforced
db.createCollection("orders", { validator: { $jsonSchema: {
  bsonType: "object", required: ["tenantId", "customerId", "status", "items", "totalCents", "createdAt"],
  properties: {
    tenantId: { bsonType: "string" }, customerId: { bsonType: "string" },
    status: { enum: ["pending", "paid", "shipped", "cancelled"] },
    totalCents: { bsonType: "long", minimum: 0 },
    items: { bsonType: "array", maxItems: 200, items: { bsonType: "object", required: ["sku", "qty", "priceCents"] } }
  } } } });
db.orders.createIndex({ tenantId: 1, createdAt: -1 });
db.orders.createIndex({ tenantId: 1, customerId: 1, createdAt: -1 });
db.orders.find({ tenantId: "t_7", status: "pending" }).sort({ createdAt: -1 }).limit(50);
```

Consistency: reads from the primary are strongly consistent; reads from secondaries may lag. **Write concern** (`majority` for durability across nodes) and **read concern** (`majority` to avoid reading rolled-back writes) must be set deliberately; defaults have changed across versions and were historically weak. Operations: use Atlas or DocumentDB rather than self-hosting; enable authentication (exposed, unauthenticated MongoDB instances have been among the most common public data leaks), TLS, network isolation, backups with PITR, and alerting on replication lag and oplog window.

MongoDB fits: catalogues and content with heterogeneous attributes, event and log storage, rapid prototyping where the schema is genuinely evolving, teams fluent in it. It fits poorly: highly relational data with many-to-many relationships and reporting needs, where PostgreSQL with JSONB usually delivers both flexibility and integrity.

## Key-value and wide-column: DynamoDB

Part VII chapter 11 covered DynamoDB's AWS mechanics. The design discipline:

1. **List every access pattern** ("get order by ID", "list a tenant's orders by date", "list a customer's orders", "find pending orders older than an hour").
2. **Choose a partition key** with high cardinality and even traffic (tenant alone is dangerous: one big tenant becomes a hot partition; tenant + something, or order ID, spreads it).
3. **Use the sort key** for ranges and hierarchy (`ORDER#<timestamp>#<id>`, `ITEM#<n>`), enabling `begins_with` and `between` queries.
4. **Add GSIs** for alternative patterns (by customer, by status + date), accepting eventual consistency and extra write cost.
5. **Single-table design** co-locates related entities under shared keys to fetch them in one query; it is powerful and makes the data model hard to read for newcomers; document it in a table of entities → key patterns.
6. **No scans** in the request path; scans are for migrations and analytics exports.

Consistency: eventually consistent reads by default (cheaper), strongly consistent on request for the base table (not GSIs); **transactions** across up to 100 items; **conditional expressions** for optimistic concurrency and uniqueness (`attribute_not_exists(PK)`); item size 400 KB. Capacity: on-demand for unknown or spiky load, provisioned with autoscaling for steady high volume (significantly cheaper at scale). TTL, Streams, PITR, Global Tables as covered.

DynamoDB fits: serverless architectures, session/idempotency/rate-limit stores, event logs, high-scale key-based access, systems with stable, known access patterns. Poorly: reporting, ad-hoc queries, evolving relational models, teams expecting SQL flexibility.

## Consistency and CAP in one paragraph

Distributed stores choose, during a network partition, between answering with possibly stale data (availability) and refusing to answer (consistency) (Part IX chapter 5). Document and key-value stores expose this through read/write concerns and consistency flags; the defaults are often the weaker, faster choice. For money, inventory and anything with uniqueness constraints, use strong consistency and conditional writes, or keep that data in a relational system of record and use NoSQL for what tolerates staleness.

## The hybrid that usually wins

Most client systems: PostgreSQL as the system of record (integrity, transactions, reporting); Redis for sessions, caches and rate limits; S3 for blobs; a search engine only when PostgreSQL full-text search is insufficient; DynamoDB for specific high-scale or serverless components; JSONB columns for the "flexible attributes" that tempt people toward document stores. Introduce a second database only with a named reason (Part III chapter 1's "one tier doing everything" warning cuts both ways: too many stores is also a failure).

## Security specifics

- Authentication on (MongoDB `security.authorization`), TLS, private networking, least-privilege roles per application; no default ports exposed.
- Operator injection (Part IV chapter 11): validate types; never pass raw request objects as queries.
- Encryption at rest with KMS; field-level encryption for sensitive attributes.
- DynamoDB: IAM fine-grained access (condition keys on partition keys for per-tenant/per-user access), VPC endpoints, PITR on.
- Backups and restore tests as for any data store (chapter 9).

## Common mistakes

- Choosing NoSQL "to scale" for a system that will never exceed one PostgreSQL instance.
- Document schemas with unbounded arrays; 16 MB limit hit in production.
- Relational data forced into documents, then joins in application code everywhere.
- DynamoDB tables designed like SQL tables; scans in request paths; hot partitions.
- Default weak read/write concerns; reading rolled-back data.
- Unauthenticated MongoDB on a public IP.
- No schema validation at all; every document shape differs; code full of defensive checks.
- Two or three databases where one plus a cache would do.
