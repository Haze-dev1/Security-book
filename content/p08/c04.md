# Indexes and Query Execution Plans

:::objectives
- Explain how B-tree indexes work and why they make equality and range lookups fast, and what they cost on writes.

- Read `EXPLAIN (ANALYZE, BUFFERS)` output and recognise the common bad plans.
- Find slow queries in production and fix them methodically.
:::

## The problem

A query without a usable index reads every row (a sequential scan). On a thousand rows nobody notices; on ten million, a two-millisecond lookup becomes a two-second table scan that holds a connection, burns I/O, and under load takes the service down (Part V chapter 10's scenario). Conversely, an index on every column makes writes slow and wastes memory. Indexing is the art of matching structures to the queries the application actually runs.

## B-trees

A [[b-tree]] index stores the indexed column values in sorted order in a balanced tree whose leaves point at table rows. Finding a value is a few page reads from root to leaf (logarithmic in table size: a billion rows is roughly four levels), then following pointers to the heap for any columns not in the index. Because leaves are ordered, range queries (`BETWEEN`, `<`, `>`, prefix `LIKE 'abc%'`) and `ORDER BY` on the indexed columns are also fast. Equality on a non-leading column, `LIKE '%abc'`, or a function applied to the column (`lower(email) = …`) cannot use a plain B-tree on that column.

Every index costs: disk, memory (indexes compete with data for the buffer cache), and write amplification (every insert/update/delete touches every index on the table). An index that is never used is pure cost; `pg_stat_user_indexes` shows usage.

## Designing indexes

### Composite indexes and column order

An index on `(tenant_id, created_at)` serves `WHERE tenant_id = ?`, `WHERE tenant_id = ? AND created_at > ?`, and `WHERE tenant_id = ? ORDER BY created_at`, but not `WHERE created_at > ?` alone (the leading column is missing). Rule: **equality columns first, then the range or sort column**. For multi-tenant systems the tenant key leads almost every index. One well-chosen composite index usually beats several single-column indexes, because the planner can only combine single-column indexes with bitmap scans at extra cost.

### Partial indexes

Index only the rows a query cares about: `CREATE INDEX ON jobs (created_at) WHERE status = 'queued'` is tiny and perfect for the worker's `SELECT … WHERE status='queued' ORDER BY created_at`. Also the mechanism for unique constraints with soft deletes (chapter 3).

### Covering indexes

`CREATE INDEX ON orders (tenant_id, created_at) INCLUDE (status, total_cents)` lets a query that reads only those columns be answered entirely from the index (an **index-only scan**), never touching the heap, provided the visibility map says the pages are all-visible (so VACUUM matters here too).

### Expression indexes

`CREATE INDEX ON customers (lower(email))` serves `WHERE lower(email) = lower($1)`; `CREATE INDEX ON events ((payload->>'type'))` serves JSON attribute equality. The query must use the identical expression.

### Other index types (PostgreSQL)

- **GIN**: inverted index for JSONB containment (`@>`), arrays, full-text search; larger and slower to update.
- **GiST / SP-GiST**: geometric, range types, exclusion constraints, nearest-neighbour.
- **BRIN**: block-range summaries for huge, naturally ordered tables (append-only time series); tiny indexes, good for range scans over time.
- **Hash**: equality only; rarely better than B-tree.
- **pgvector (HNSW/IVFFlat)**: vector similarity for embeddings.

## Reading plans

`EXPLAIN` shows the planner's intent with cost estimates; `EXPLAIN (ANALYZE, BUFFERS)` runs the query and shows actual rows, times and I/O. Always use the second for diagnosis (on a copy of production data or in production with care; it executes writes too, so wrap in a rolled-back transaction).

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT o.id, o.total_cents FROM orders o
WHERE o.tenant_id = 't_7' AND o.created_at > now() - interval '30 days' AND o.status = 'paid'
ORDER BY o.created_at DESC LIMIT 50;
```

```text
Limit  (cost=0.56..95.12 rows=50 width=24) (actual time=0.041..0.412 rows=50 loops=1)
  Buffers: shared hit=58
  ->  Index Scan Backward using orders_tenant_created_idx on orders o  (cost=0.56..2345.11 rows=1240 width=24) (actual time=0.040..0.405 rows=50 loops=1)
        Index Cond: ((tenant_id = 't_7') AND (created_at > (now() - '30 days'::interval)))
        Filter: (status = 'paid')
        Rows Removed by Filter: 12
        Buffers: shared hit=58
Planning Time: 0.210 ms
Execution Time: 0.450 ms
```

Reading it: the index satisfied tenant and date (Index Cond) and the sort order (Backward scan, no Sort node); `status` was filtered after fetching (Rows Removed by Filter: 12, cheap here; if it removed 50,000 rows, add status to the index or a partial index); 58 buffer hits, zero reads: everything in cache; 0.45 ms. The estimate (1240 rows) versus actual (50, because of LIMIT) is fine.

Patterns that signal trouble:

| Plan feature | Meaning | Fix |
|---|---|---|
| `Seq Scan` on a large table with a selective filter | No usable index, or stale statistics, or the planner thinks the table is small | Add the index; `ANALYZE`; check the predicate is sargable |
| `Rows Removed by Filter` ≫ rows returned | Index not selective enough; filter applied after | Extend the composite index; partial index |
| `Sort` with `external merge Disk` | Sort spilled to disk | Index supporting the ORDER BY; raise `work_mem` for that query |
| `Nested Loop` with a large outer and inner `Seq Scan` | Missing index on the join key | Index the join column |
| `Hash Join` with `Batches: 8` | Hash table exceeded work_mem | More memory or reduce the joined set |
| Estimated rows off by 100× | Statistics stale or correlated columns | `ANALYZE`; `CREATE STATISTICS` for correlated columns; raise statistics target |
| `Bitmap Heap Scan` with huge `Recheck` | Many rows via several indexes | A better composite index |
| Buffers `read` ≫ `hit` | Working set not in cache | More memory; smaller indexes; the query reads too much |
| `loops=10000` on an inner plan | N+1 from the application, or a correlated subquery | Batch the query; rewrite with a join |

## Finding slow queries in production

1. `pg_stat_statements` ordered by `total_exec_time` (what costs the most overall) and by `mean_exec_time` (what is slow per call); `log_min_duration_statement` for the long tail; RDS Performance Insights for wait events and top SQL (Part VII chapter 11).
2. Reproduce with `EXPLAIN (ANALYZE, BUFFERS)` using realistic parameters (plans depend on values; a query fast for a small tenant may scan for a big one).
3. Fix in order: make the predicate sargable (no functions on the column unless expression-indexed; no implicit casts: `WHERE id = '123'` on a bigint column is fine, but `WHERE text_col = 123` is not); add or extend the right index; rewrite the query (avoid `SELECT *`, `OFFSET`, `NOT IN` on nullable columns, correlated subqueries); batch N+1 patterns in the application; consider a materialised view for heavy aggregates.
4. Verify in staging with production-shaped data, deploy, and watch `pg_stat_statements` again.

Creating an index on a live table: `CREATE INDEX CONCURRENTLY` avoids locking writes (takes longer, cannot run in a transaction; migration tools support it, chapter 7). Dropping unused indexes recovers write performance; confirm zero scans over a representative period first.

## Maintenance

Autovacuum keeps statistics fresh and dead tuples cleaned; monitor `n_dead_tup`, last autovacuum times, and bloat (`pgstattuple`, bloat queries); tune autovacuum to be more aggressive on hot tables (`autovacuum_vacuum_scale_factor` per table). `REINDEX CONCURRENTLY` fixes bloated indexes. Long-running transactions block vacuum (Part III chapter 13). Statistics targets can be raised for skewed columns.

## MySQL notes

InnoDB clusters the table on the primary key (secondary indexes point to the primary key, so a small primary key keeps secondaries small); `EXPLAIN FORMAT=JSON` and `EXPLAIN ANALYZE` (8.0.18+) show plans; the optimizer trace helps; covering indexes behave similarly; prefix indexes exist for long strings; the slow query log and Performance Schema replace `pg_stat_statements`.

## Common mistakes

- No index on foreign keys (PostgreSQL); joins and cascading deletes scan.
- Single-column indexes everywhere instead of the composite that matches the query.
- Wrong column order (range first, equality second).
- Functions on indexed columns in WHERE clauses.
- `OFFSET 100000` pagination (chapter: Part III chapter 2).
- Speculative indexes "just in case"; write amplification and cache pressure.
- Never looking at `pg_stat_statements`; discovering slow queries from users.
- `CREATE INDEX` without `CONCURRENTLY` on a production table; writes blocked for minutes.
- Testing plans on an empty development database where everything is a cheap sequential scan.
