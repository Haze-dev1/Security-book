# Migrations

:::objectives
- Manage schema changes as versioned, reviewed, repeatable migrations applied identically across environments.
- Apply zero-downtime patterns: expand/contract, backfills in batches, concurrent indexes, lock timeouts, and compatibility with running code.
- Handle data migrations and rollbacks realistically.
- Integrate migrations into the deployment pipeline safely.
:::

:::prereq
Chapters 3, 4 and 5; Part I chapter 13; Part X chapter 8 covers the pipeline side.

## The problem

Schemas change constantly: new columns, new tables, renamed fields, indexes, constraints. Applying changes by hand is unrepeatable and undocumented; applying them carelessly locks tables, breaks the running version of the application, or takes a production database offline for an hour while a column is rewritten. Migrations as code solve the first problem; the patterns in this chapter solve the second.

## Migrations as code

A migration tool (Alembic for SQLAlchemy, Django migrations, Flyway or Liquibase for JVM and SQL-first teams, Prisma Migrate, golang-migrate, Rails migrations, sqitch) keeps an ordered set of migration files in the repository and a table in the database recording which have been applied. `migrate up` applies pending ones in order, inside transactions where the database supports transactional DDL (PostgreSQL does; MySQL does not).

Rules: migrations are **immutable once merged** (fix forward with a new migration); every migration is **reviewed** like code, with the generated SQL inspected (`alembic upgrade --sql`); migrations are **tested** against a production-shaped database in staging; the application version N must run against schema N−1 and N (the deploy applies the migration, then rolls the code; Part VII chapter 15); and **no migration is run by hand** in production, ever: the pipeline runs it.

```python
# Alembic migration: additive, safe
def upgrade():
    op.add_column("orders", sa.Column("fulfilment_channel", sa.Text(), nullable=True))     # nullable: no table rewrite, no lock on reads
    op.execute("ALTER TABLE orders ADD CONSTRAINT orders_fulfilment_channel_check CHECK (fulfilment_channel IN ('web','store','partner')) NOT VALID")   # add constraint without scanning
    # validated in a later migration after backfill: ALTER TABLE ... VALIDATE CONSTRAINT (takes only a SHARE UPDATE EXCLUSIVE lock)

def downgrade():
    op.drop_constraint("orders_fulfilment_channel_check", "orders")
    op.drop_column("orders", "fulfilment_channel")
```

## What locks, what rewrites

PostgreSQL DDL takes locks; the dangerous ones are `ACCESS EXCLUSIVE` (blocks everything, including reads) and long rewrites. Know the categories:

| Operation | Lock / cost (PostgreSQL ≥ 12) | Safe approach |
|---|---|---|
| Add nullable column, no default | Brief ACCESS EXCLUSIVE, metadata only | Fine |
| Add column with constant default | Brief; stored as metadata (fast since PG 11) | Fine |
| Add column NOT NULL on a populated table | Needs a default or a backfill; `SET NOT NULL` scans the table | Add nullable → backfill in batches → add `CHECK (col IS NOT NULL) NOT VALID` → `VALIDATE` → `SET NOT NULL` (PG 12+ uses the validated check to skip the scan) |
| Change column type | Full table rewrite under ACCESS EXCLUSIVE | Add new column, dual-write, backfill, switch reads, drop old (expand/contract) |
| Rename column/table | Brief lock, but breaks running code immediately | Avoid; add new, migrate, drop old; or ensure code handles both via a view |
| Add index | Blocks writes for the build | `CREATE INDEX CONCURRENTLY` (outside a transaction; handle failure leaving an INVALID index) |
| Add foreign key | Scans the referenced table under lock | `ADD CONSTRAINT … NOT VALID`, then `VALIDATE CONSTRAINT` |
| Add unique constraint | Index build blocks writes | Create unique index CONCURRENTLY, then add constraint USING INDEX |
| Drop column | Brief lock; space reclaimed later | Fine, after code stops using it |
| Large UPDATE/DELETE | Long transaction, locks, WAL flood, replication lag | Batch (chapter 1's pattern), sleep between batches, monitor lag |

Even "brief" ACCESS EXCLUSIVE locks queue behind any running query on the table and then block all queries behind them: a 5-minute report running when the migration starts freezes the application for 5 minutes. Always run migrations with `SET lock_timeout = '3s'` (and retry), and run them when long queries are not running or after terminating them deliberately.

MySQL: online DDL (`ALGORITHM=INPLACE, LOCK=NONE`) covers many operations; `pt-online-schema-change` and `gh-ost` for the rest; no transactional DDL, so a failed multi-statement migration leaves a half-applied state to repair.

## Expand and contract

The pattern for any change that is not purely additive:

```flow

  "title": "Renaming orders.channel to orders.fulfilment_channel without downtime",
  "actors": [{"id":"m1","label":"Migration 1 (expand)"},{"id":"vN","label":"App vN+1"},{"id":"bf","label":"Backfill job"},{"id":"vN2","label":"App vN+2"},{"id":"m2","label":"Migration 2 (contract)"}],
  "steps": [
    {"from":"m1","to":"m1","label":"add fulfilment_channel (nullable)","title":"Expand the schema","detail":"Additive change; old code ignores the new column; new code can start using it. Deployed before any code that depends on it."},
    {"from":"vN","to":"vN","label":"write both columns; read old","title":"Dual write","detail":"The application writes channel and fulfilment_channel on every insert/update and still reads channel. Both old (vN) and new (vN+1) code work against this schema during the rolling deploy."},
    {"from":"bf","to":"bf","label":"UPDATE … SET fulfilment_channel = channel WHERE fulfilment_channel IS NULL LIMIT batches","title":"Backfill in batches","detail":"A job copies existing rows in batches of a few thousand with pauses, watching replication lag and lock waits. Idempotent and resumable. May take hours on big tables; that is fine."},
    {"from":"vN2","to":"vN2","label":"read new; write both (or new only)","title":"Switch reads","detail":"Once the backfill completes and a verification query shows no mismatches, deploy code that reads fulfilment_channel. Keep writing both until you are confident; then write only the new column."},
    {"from":"m2","to":"m2","label":"add NOT NULL/constraints; drop channel","title":"Contract","detail":"A later migration (days or weeks later, after any rollback window has passed) validates constraints on the new column and drops the old one. Rollback of the application to vN+1 is still safe until this step runs.","dashed":true}
  ]
}
```

Every step is deployable and reversible on its own; the application never sees a schema it cannot handle. It is more steps than a rename, and it is the only way to change live schemas without downtime.

## Data migrations and backfills

Separate schema migrations (fast, in the deploy) from data migrations (slow, idempotent, run as jobs). A backfill: processes in bounded batches by primary key range; commits each batch; sleeps briefly; records progress so it can resume; verifies at the end; is safe to re-run; and runs off-peak with replication lag monitored. Never a single `UPDATE` over millions of rows in a migration file: it holds locks, bloats, lags replicas, and if it fails at 99% it rolls back everything.

## Rollbacks

Down migrations exist in theory; in practice, data-destroying downgrades (dropping a column with data) are rarely safe, and most teams **roll forward**: a new migration that fixes the problem. The expand/contract discipline makes application rollback safe without touching the schema at all, which is the real goal (Part X chapter 8). Write down migrations for the additive steps (cheap), test them, and treat the contract step as a point of no return that you schedule deliberately. For catastrophic data mistakes, PITR (chapter 9), not downgrade scripts.

## In the pipeline

Order: build artifact → run migration task (new image, migration command, `lock_timeout` set, one instance only, exit code checked) → deploy application → verify. Staging first, always, against a database restored from a recent production snapshot (anonymised), so the migration's duration and lock behaviour are known before production. Record the migration's start and end in the deploy log. Give the migration role DDL privileges and the application role none (chapter 10). Alert on migrations that take longer than expected (a `statement_timeout` for DDL that is generous but finite).

## Common mistakes

- Running migrations by hand in production psql.
- `ALTER TABLE … TYPE` on a large table during business hours; hour-long outage.
- `CREATE INDEX` without `CONCURRENTLY` on a live table.
- Renames that break the running version mid-deploy.
- Giant single-transaction backfills.
- No `lock_timeout`; a quick migration queues behind a report and freezes everything.
- Migrations in the application's startup path, racing across replicas (Part VI chapter 3).
- Contract step run immediately, destroying the rollback path.
- Never testing migration duration on production-sized data.
