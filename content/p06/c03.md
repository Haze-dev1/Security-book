# Dockerfiles and Multi-Stage Builds

:::objectives
- Write Dockerfiles for Python and Node applications that are small, cache-friendly, reproducible and secure.
- Use multi-stage builds to separate build-time tooling from the runtime image.
- Handle dependencies, build secrets, non-root users, signals and health checks correctly.
- Recognise the Dockerfile anti-patterns that cause slow builds, huge images and production bugs.
:::

:::prereq
Chapters 1 and 2; Part I chapters 6 and 9.
:::

## The problem

A Dockerfile is a build script whose output ships to production. Most of them are written once, copied between projects, and never reviewed; they run as root, include compilers and test dependencies, rebuild everything on every change, and bake in secrets. The patterns below fix all of that and are reusable across projects.

## A production Python Dockerfile

```dockerfile
@file: Dockerfile (FastAPI + uv, multi-stage)
# syntax=docker/dockerfile:1.7
ARG PYTHON_VERSION=3.12.7
FROM python:${PYTHON_VERSION}-slim-bookworm AS base
ENV PYTHONDONTWRITEBYTECODE=1 PYTHONUNBUFFERED=1 PIP_DISABLE_PIP_VERSION_CHECK=1

# ---------- build stage: compilers, dependency resolution ----------
FROM base AS build
RUN apt-get update && apt-get install -y --no-install-recommends build-essential libpq-dev \
 && rm -rf /var/lib/apt/lists/*
COPY --from=ghcr.io/astral-sh/uv:0.4.18 /uv /usr/local/bin/uv
WORKDIR /app
COPY pyproject.toml uv.lock ./
RUN --mount=type=cache,target=/root/.cache/uv \
    uv sync --locked --no-dev --no-install-project            # deps first: cached until lockfile changes
COPY . .
RUN --mount=type=cache,target=/root/.cache/uv uv sync --locked --no-dev   # install the project itself

# ---------- runtime stage: minimal ----------
FROM base AS runtime
RUN apt-get update && apt-get install -y --no-install-recommends libpq5 curl tini \
 && rm -rf /var/lib/apt/lists/* \
 && groupadd --system --gid 10001 app && useradd --system --uid 10001 --gid app --home /app --shell /usr/sbin/nologin app
WORKDIR /app
COPY --from=build --chown=app:app /app/.venv /app/.venv
COPY --from=build --chown=app:app /app /app
ENV PATH="/app/.venv/bin:$PATH" PORT=8000
USER app
EXPOSE 8000
HEALTHCHECK --interval=30s --timeout=3s --start-period=10s --retries=3 CMD curl -fsS http://127.0.0.1:8000/health/ready || exit 1
ENTRYPOINT ["tini", "--"]
CMD ["gunicorn", "app.main:app", "-c", "gunicorn.conf.py", "--bind", "0.0.0.0:8000"]
LABEL org.opencontainers.image.source="https://github.com/client/app" \
      org.opencontainers.image.description="Client App API"
```

Line by line, what each decision prevents:

- **`# syntax=`** enables BuildKit features (cache and secret mounts).
- **Pinned base** by exact version (digest-pin in CI for full reproducibility, chapter 2).
- **Build stage** has compilers and headers; **runtime stage** has only the shared libraries the application needs (`libpq5`, not `libpq-dev`). The final image contains no compiler, no `uv`, no build cache.
- **Dependencies before code**: the `uv sync` layer is cached until the lockfile changes; code changes rebuild only the last layers. `--locked` fails the build if the lockfile is stale.
- **Cache mounts** keep the package cache between builds without storing it in a layer.
- **Non-root user** with a fixed UID (useful for volume permissions and Kubernetes `runAsUser`); files owned by it via `--chown`.
- **`tini`** as PID 1 reaps zombies and forwards signals (Part I chapter 6); exec-form `CMD` so gunicorn receives SIGTERM.
- **`HEALTHCHECK`** gives Docker and Compose a readiness signal (ECS and Kubernetes use their own probes, but it costs nothing).
- **`PYTHONUNBUFFERED`** so logs stream to stdout immediately.
- **Labels** for provenance.

## A production Node Dockerfile

```dockerfile
# syntax=docker/dockerfile:1.7
FROM node:22.11.0-bookworm-slim AS base
ENV NODE_ENV=production

FROM base AS deps
WORKDIR /app
COPY package.json package-lock.json ./
RUN --mount=type=cache,target=/root/.npm npm ci --ignore-scripts        # exact lockfile install, no install scripts

FROM base AS build
WORKDIR /app
COPY --from=deps /app/node_modules ./node_modules
COPY . .
RUN npm run build && npm prune --omit=dev                                # compile TS, drop devDependencies

FROM base AS runtime
RUN apt-get update && apt-get install -y --no-install-recommends tini curl && rm -rf /var/lib/apt/lists/*
WORKDIR /app
COPY --from=build --chown=node:node /app/dist ./dist
COPY --from=build --chown=node:node /app/node_modules ./node_modules
COPY --chown=node:node package.json ./
USER node                                                                # the node image ships a non-root 'node' user (uid 1000)
EXPOSE 3000
HEALTHCHECK CMD curl -fsS http://127.0.0.1:3000/health/ready || exit 1
ENTRYPOINT ["tini", "--"]
CMD ["node", "--max-old-space-size=384", "dist/server.js"]              # heap cap below the container limit (Part I ch.7)
```

## Build secrets

Private package registries and private Git dependencies need credentials at build time. Never use `ARG`/`ENV` for them (they persist in image history). Use BuildKit secret mounts, which expose a file during one `RUN` and leave no trace:

```dockerfile
RUN --mount=type=secret,id=npmrc,target=/root/.npmrc npm ci --ignore-scripts
RUN --mount=type=ssh pip install git+ssh://git@github.com/client/private-lib.git
```

```bash
docker build --secret id=npmrc,src=$HOME/.npmrc --ssh default -t app .
```

## Configuration at runtime, not build time

Images are environment-agnostic: no environment-specific URLs, no `ENV DATABASE_URL`, no copied `.env`. Configuration arrives from the orchestrator (ECS task definition, Kubernetes env/ConfigMap/Secrets) or a secrets manager at start (Part I chapter 8; chapter 6). The only `ENV` in a Dockerfile are runtime behaviour flags (`PYTHONUNBUFFERED`, `NODE_ENV`, `PATH`).

## .dockerignore

```
.git
.github
node_modules
.venv
__pycache__
*.pyc
.env*
!.env.example
tests/fixtures/large
coverage
*.md
```

It shrinks the build context (faster uploads to the daemon), keeps secrets and junk out of layers, and avoids cache invalidation from irrelevant files. Treat it like `.gitignore`: review it.

## Running tests in the build

A `test` stage (`FROM build AS test; RUN pytest`) that CI targets with `docker build --target test` ensures tests run against the exact dependencies in the image. Keep the runtime stage free of test code and test dependencies.

## Entrypoint scripts

Sometimes start-up needs logic (wait for a dependency, render a config template, run migrations in a job). Keep entrypoint scripts tiny, `set -euo pipefail`, and end with `exec "$@"` so the application replaces the shell and receives signals. Do not run migrations from the API container's entrypoint in multi-replica deployments (races; failures take down every replica); run them as a separate one-shot task before the rollout (Part X chapter 8).

```bash
#!/usr/bin/env bash
set -euo pipefail
# optional: wait for DB to accept connections (bounded)
for i in $(seq 1 30); do pg_isready -h "$DATABASE__HOST" -q && break; sleep 1; done
exec "$@"
```

## Anti-patterns

- `FROM python:latest` / `FROM node` with no tag.
- Single stage with `build-essential` shipped to production.
- `COPY . .` before installing dependencies.
- `RUN apt-get update` in its own layer (stale indexes on rebuild) or without cleaning lists.
- Running as root; `chmod -R 777` to fix permission issues.
- Shell-form `CMD` (`CMD gunicorn …`), so PID 1 is `sh` and signals are lost.
- Secrets via `ARG`/`ENV`/`COPY .env`.
- `EXPOSE` as if it opened ports (it is documentation; publishing is a runtime decision).
- Health check hitting `/` (heavy) or omitted entirely.
- Pinning nothing, or pinning the base but not dependencies.
- Huge contexts without `.dockerignore`.

## Exercises

1. Convert a single-stage Dockerfile from a project into the multi-stage pattern; compare image size, CVE count and rebuild time after a one-line code change.
2. Add a `test` stage and run it in CI; make the build fail when a test fails.
3. Replace a shell-form CMD with tini plus exec-form; time `docker stop` before and after and observe the exit code.
