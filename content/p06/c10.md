# Ingress, Gateway API, ConfigMaps, Secrets and Persistent Volumes

:::objectives

- Provide persistent storage with PersistentVolumeClaims, StorageClasses and CSI drivers, and know when not to.

## Getting traffic in

### Ingress

An Ingress object declares HTTP routing rules (host, path → Service) and TLS. It does nothing by itself; an **ingress controller** (AWS Load Balancer Controller, ingress-nginx, Traefik, HAProxy) watches Ingress objects and configures a real proxy or cloud load balancer.

```yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: api
  namespace: prod
  annotations:
    kubernetes.io/ingress.class: alb                                   # or spec.ingressClassName
    alb.ingress.kubernetes.io/scheme: internet-facing
    alb.ingress.kubernetes.io/target-type: ip                          # route straight to pod IPs
    alb.ingress.kubernetes.io/listen-ports: '[{"HTTP":80},{"HTTPS":443}]'
    alb.ingress.kubernetes.io/ssl-redirect: "443"
    alb.ingress.kubernetes.io/certificate-arn: arn:aws:acm:eu-west-1:123456789012:certificate/…
    alb.ingress.kubernetes.io/healthcheck-path: /health/ready
    alb.ingress.kubernetes.io/group.name: prod-shared                  # several Ingresses share ONE ALB
    external-dns.alpha.kubernetes.io/hostname: api.client.com
spec:
  ingressClassName: alb
  rules:
    - host: api.client.com
      http:
        paths:
          - path: /
            pathType: Prefix
            backend: { service: { name: api, port: { name: http } } }
```

On EKS the AWS Load Balancer Controller turns this into an ALB with target groups pointing at pod IPs (so Part II chapter 13 applies directly: health checks, deregistration delay, security groups). The `group.name` annotation is how you avoid one ALB per Ingress. With ingress-nginx instead, one NLB fronts the Nginx pods, which route internally; TLS is then terminated in-cluster with certificates from **cert-manager** (ACME via DNS-01/HTTP-01, or a private CA) stored in Secrets, and **external-dns** creates Route 53 records from Ingress hostnames.

### Gateway API

The Gateway API is the successor to Ingress: role-separated resources (**GatewayClass** by the platform, **Gateway** by cluster operators, **HTTPRoute**/**GRPCRoute**/**TCPRoute** by application teams), richer matching (headers, methods, weights for canaries), and portable semantics across implementations (AWS Gateway API Controller for VPC Lattice, Envoy Gateway, Istio, Cilium, ingress-nginx's Gateway support). New platforms should prefer it; Ingress remains widely deployed and supported.

```yaml
apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
metadata: { name: api, namespace: prod }
spec:
  parentRefs: [{ name: shared-gateway, namespace: infra }]
  hostnames: [api.client.com]
  rules:
    - matches: [{ path: { type: PathPrefix, value: /v2 } }]
      backendRefs: [{ name: api-v2, port: 80, weight: 90 }, { name: api-v2-canary, port: 80, weight: 10 }]
    - matches: [{ path: { type: PathPrefix, value: / } }]
      backendRefs: [{ name: api, port: 80 }]
```

## ConfigMaps and Secrets

**ConfigMaps** hold non-secret configuration as key-value pairs or whole files, consumed as environment variables (`envFrom`) or mounted files. **Secrets** have the same shape and are intended for sensitive values; by default they are **base64-encoded, not encrypted**, stored in etcd, and readable by anyone with RBAC access to Secrets in the namespace. Hardening: enable envelope encryption of Secrets in etcd (EKS: KMS encryption for secrets, now default on new clusters); restrict RBAC on Secrets tightly; mount as files (tmpfs) rather than env where possible; and prefer an **external secrets store** as the source of truth.

```yaml
apiVersion: v1
kind: ConfigMap
metadata: { name: api-config, namespace: prod }
data:
  LOG_LEVEL: info
  FEATURES__NEW_CHECKOUT: "false"
  gunicorn.conf.py: |
    workers = 2
    timeout = 30
---
# External Secrets Operator: sync from AWS Secrets Manager into a Kubernetes Secret
apiVersion: external-secrets.io/v1
kind: ExternalSecret
metadata: { name: api-db, namespace: prod }
spec:
  refreshInterval: 1h
  secretStoreRef: { name: aws-secretsmanager, kind: ClusterSecretStore }
  target: { name: api-db }
  data:
    - secretKey: url
      remoteRef: { key: prod/app/db, property: url }
```

Alternatives: the **Secrets Store CSI driver** mounts secrets from AWS Secrets Manager/Parameter Store directly as files (optionally also syncing to a Kubernetes Secret); or the application fetches secrets itself using its pod's IAM role (IRSA/Pod Identity), which keeps Kubernetes out of the secret path entirely (Part IV chapter 17).

Config changes and rollouts: env-based config requires a pod restart to pick up changes; mounted ConfigMap files update in place (eventually), which the app must watch. A common pattern is to hash the ConfigMap into a pod annotation so a config change triggers a rolling update (Helm `checksum/config`, or Kustomize's configMapGenerator with hashed names).

## Persistent storage

Most application pods should be stateless and need no persistent volumes (data in RDS, S3, ElastiCache). When something in the cluster needs disk (a self-managed database, a message broker, Prometheus), Kubernetes abstracts storage:

- **PersistentVolumeClaim (PVC)**: a request for storage of a size and access mode, bound to a **PersistentVolume** provisioned dynamically by a **StorageClass**.
- **StorageClass**: names a CSI driver and parameters (EBS gp3 with encryption; EFS; etc.). The default class provisions on demand.
- **CSI drivers**: EBS CSI (block, single-AZ, one node at a time: `ReadWriteOnce`), EFS CSI (shared NFS: `ReadWriteMany`), others.
- **StatefulSet**: pods with stable names and one PVC each, for databases and brokers; ordered startup; use only when a managed service is not an option.

```yaml
apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata: { name: gp3-encrypted }
provisioner: ebs.csi.aws.com
parameters: { type: gp3, encrypted: "true", iops: "3000", throughput: "125" }
volumeBindingMode: WaitForFirstConsumer          # provision in the AZ where the pod lands
allowVolumeExpansion: true
reclaimPolicy: Retain                            # keep the EBS volume if the PVC is deleted (safer for data)
---
apiVersion: v1
kind: PersistentVolumeClaim
metadata: { name: prometheus-data, namespace: monitoring }
spec:
  accessModes: [ReadWriteOnce]
  storageClassName: gp3-encrypted
  resources: { requests: { storage: 100Gi } }
```

Gotchas: EBS volumes are AZ-bound, so a pod with a PVC can only be scheduled in that AZ (use `WaitForFirstConsumer` and topology spread); `ReadWriteOnce` means one node, so a Deployment with 2 replicas sharing one EBS PVC fails; `reclaimPolicy: Delete` (the usual default) deletes the disk when the PVC is deleted, which has destroyed data during cleanups; backups of PVCs need a tool (Velero, EBS snapshots via the CSI snapshotter). The honest recommendation for client projects: run stateful services as managed AWS services and keep the cluster stateless, except for monitoring stacks you are prepared to operate.

## Common mistakes

- One ALB per Ingress; `group.name` unused; cost balloons.
- TLS certificates managed by hand in Secrets; expiry outages. Use ACM (ALB) or cert-manager.
- Kubernetes Secrets treated as encrypted; broad RBAC on Secrets.
- Secrets copied into manifests in Git (base64 is not encryption); use ESO/CSI or sealed/encrypted manifests (SOPS).
- ConfigMap changed, pods not restarted, config "not applied".
- Databases on PVCs in the cluster without backups or expertise.
- `reclaimPolicy: Delete` on data you care about.
- Deployments with `ReadWriteOnce` PVCs and more than one replica.

## Exercises

1. On EKS (or a local cluster with ingress-nginx), expose two services through one Ingress/Gateway with host- and path-based routing and TLS from cert-manager or ACM.
2. Install External Secrets Operator (or the CSI driver) and sync a secret from AWS Secrets Manager (or a local stand-in) into a pod as a file; rotate the source and confirm the pod sees the new value.
3. Create a StorageClass with Retain, a PVC, and a StatefulSet; delete the StatefulSet and PVC and confirm the volume survives; then clean it up deliberately.
