# Secrets, Configuration, Resource Limits and Production Containers

:::objectives
- Inject configuration and secrets into containers without baking them into images or exposing them more than necessary.
- Set CPU and memory requests and limits that keep services stable, and tune runtimes to respect them.
- Distinguish development images and settings from production ones.
- Configure logging, health checks, restart policies and graceful shutdown for production containers.
:::

:::prereq
Chapters 3 and 5; Part I chapters 6, 7 and 8; Part IV chapter 17.
:::

## The problem

The same image must run in development, staging and production, so everything that differs must come from outside the image at runtime. Containers also share hosts, so an unbounded container can take the host down. And a container that does not stop cleanly, log properly or report health will fail in ways orchestrators cannot handle. This chapter is the production checklist for a container's runtime configuration.

## Configuration injection

Three mechanisms, in order of preference for secrets:

1. **Environment variables** from the orchestrator (ECS task definition `environment`, Kubernetes `env` and `envFrom` ConfigMaps). Fine for non-secret configuration. For secrets they are acceptable but visible to every process in the container, to `docker inspect`, to the ECS/Kubernetes API readers, and to crash dumps.
2. **Files mounted at runtime**: Docker Compose `secrets:` (files under `/run/secrets`), Kubernetes Secrets mounted as volumes (tmpfs), the Secrets Store CSI driver syncing from AWS Secrets Manager. Not in the environment; readable only by processes with file access; rotatable in place (mounted files update).
3. **Fetched by the application at start** from Secrets Manager/Parameter Store using the task role (Part IV chapter 17). Nothing stored by the orchestrator; audited per read; rotation handled by re-fetching.

ECS supports a hybrid that is the practical default: the task definition's `secrets` field references a Secrets Manager or Parameter Store ARN; the ECS agent fetches it with the **task execution role** and injects it as an environment variable at start. Simple, no SDK code, auditable. Rotation requires a new deployment or task restart.

```json
"containerDefinitions": [{
  "name": "api",
  "image": "123456789012.dkr.ecr.eu-west-1.amazonaws.com/client/app:3f9a1c4",
  "environment": [{"name": "ENV", "value": "prod"}, {"name": "LOG_LEVEL", "value": "info"}],
  "secrets": [
    {"name": "DATABASE_URL", "valueFrom": "arn:aws:secretsmanager:eu-west-1:123456789012:secret:prod/app/db-AbCdEf:url::"},
    {"name": "SECRET_KEY", "valueFrom": "arn:aws:ssm:eu-west-1:123456789012:parameter/prod/app/secret_key"}
  ],
  "cpu": 512, "memory": 1024, "memoryReservation": 768,
  "essential": true,
  "portMappings": [{"containerPort": 8000, "protocol": "tcp"}],
  "healthCheck": {"command": ["CMD-SHELL", "curl -fsS http://127.0.0.1:8000/health/ready || exit 1"], "interval": 15, "timeout": 5, "retries": 3, "startPeriod": 20},
  "stopTimeout": 30,
  "linuxParameters": {"initProcessEnabled": true},
  "readonlyRootFilesystem": true,
  "mountPoints": [{"sourceVolume": "tmp", "containerPath": "/tmp"}],
  "logConfiguration": {"logDriver": "awslogs", "options": {"awslogs-group": "/client/prod/api", "awslogs-region": "eu-west-1", "awslogs-stream-prefix": "api"}}
}]
```

Whichever mechanism: never `COPY .env` into the image, never pass secrets as build args, never log the environment, and validate configuration at start-up so a missing secret fails fast (Part I chapter 8).

## Resource requests and limits

A container with no memory limit can consume the host; one with too low a limit is killed under normal load. Set both and size them (Part I chapter 7):

- **Memory limit** = measured peak RSS × 1.3 (headroom), rounded up. Exceeding it is an OOM kill (exit 137). In Kubernetes set `requests.memory` equal to `limits.memory` for predictable scheduling (memory is incompressible).
- **CPU**: Kubernetes `requests.cpu` guarantees a share; `limits.cpu` throttles above it (CFS quota), which can add latency even when the node is idle. Many teams set CPU requests and omit CPU limits for latency-sensitive services, relying on requests for fair scheduling. ECS Fargate requires choosing a task CPU/memory combination; containers within share it.
- **Runtime tuning**: JVM `-XX:MaxRAMPercentage=75`, Node `--max-old-space-size` at ~75% of the limit, Python worker counts sized to memory, Go `GOMEMLIMIT`. Runtimes that ignore the cgroup limit are the number one cause of container OOM kills.
- **PIDs**: a `pids` limit prevents fork bombs (`--pids-limit`, Kubernetes `podPidsLimit`).
- **Ephemeral storage**: bound it (Kubernetes `ephemeral-storage` requests/limits) so a log-writing bug cannot fill the node; prefer read-only root filesystems with explicit writable mounts.

```bash
docker run -d --memory=1g --memory-swap=1g --cpus=1.0 --pids-limit=512 --read-only --tmpfs /tmp:rw,size=64m app:3f9a1c4
docker stats                              # live CPU/memory per container
```

## Development versus production

| Aspect | Development | Production |
|---|---|---|
| Image | `build` stage with dev deps, debug tools; bind-mounted code | `runtime` stage; code baked in; minimal packages |
| Command | hot reload (`--reload`, `nodemon`) | production server (gunicorn, node) with tuned workers |
| User | often root for convenience (avoid even here) | non-root, fixed UID |
| Filesystem | writable | read-only root, explicit tmp/data mounts |
| Config | `.env` file, localhost dependencies | orchestrator-injected env/secrets, managed services |
| Logging | human-readable, debug level | JSON to stdout, info level |
| Debug ports | exposed on localhost | never |
| Limits | loose | measured and enforced |

Use the same Dockerfile with different targets, and the same configuration keys with different values, so that the only differences are deliberate.

## Logging

Containers log to **stdout/stderr**; the runtime collects it. Docker's `json-file` driver stores logs locally (bound them: `--log-opt max-size=50m --log-opt max-file=5`, or they fill the disk); `awslogs` ships to CloudWatch; `fluentd`/FireLens routes to anything. Kubernetes nodes collect container stdout to files that an agent (Fluent Bit) ships. Never write log files inside containers; if software insists, mount a volume and ship from there. Structured JSON lines with request IDs (Part XI chapter 1).

## Health checks

Define a readiness endpoint and point the orchestrator at it: Docker `HEALTHCHECK`, ECS container `healthCheck` plus ALB target group checks, Kubernetes readiness/liveness/startup probes (chapter 11). Readiness should reflect ability to serve (config loaded, dependencies reachable within a short timeout), fail during shutdown, and be cheap. A liveness check should only detect a wedged process, not dependency failures, or you restart healthy containers during a database blip.

## Shutdown and restarts

PID 1 must handle SIGTERM (tini/`--init`/exec-form CMD, Part I chapter 6); the stop timeout (`docker stop -t`, ECS `stopTimeout`, Kubernetes `terminationGracePeriodSeconds`) must exceed the application's drain time. Restart policies: Docker `--restart unless-stopped` for single-host deployments; orchestrators restart by default and back off on crash loops. A container that restarts constantly is a failure to investigate, not a success of the restart policy.

## Read-only root filesystem

`--read-only` (Docker), `readonlyRootFilesystem: true` (ECS), `securityContext.readOnlyRootFilesystem: true` (Kubernetes) prevents a compromised process from modifying the application or dropping tools. Provide writable `tmpfs` for `/tmp` and any cache directories; applications that write to their own directory need fixing or an explicit mount. Pair with non-root and dropped capabilities (chapter 7).

## Timezone, locale, DNS

Containers default to UTC (keep it). Set `LANG=C.UTF-8` if the application needs it. DNS inside containers comes from the runtime (`/etc/resolv.conf` injected); on ECS/EKS it resolves VPC and cluster names; `ndots:5` in Kubernetes causes several lookups per external name, which matters for latency-sensitive high-volume services (use fully qualified names with a trailing dot, or tune `dnsConfig`).

## Common mistakes

- Secrets in images or build args; `.env` copied in.
- No memory limit, or a limit the runtime ignores (JVM/Node defaults).
- CPU limits causing throttling latency with idle nodes.
- Logs to files inside containers; `json-file` driver unbounded on the host.
- Liveness probes that check the database and restart healthy pods during outages.
- Root user, writable root filesystem, all capabilities.
- Stop timeout shorter than drain; dropped requests on every deploy.
- Same image for dev and prod but with debug tooling and dev dependencies shipped to prod.

## Exercises

1. Run an ECS task (or Compose service) with secrets from Secrets Manager (or Compose `secrets:`), read-only root filesystem, tmpfs `/tmp`, and measured memory limits. Verify `docker inspect`/the task definition reveals no secret values.
2. Run a Node or JVM container with a 512 MB limit and default runtime settings; allocate until it dies; then set the heap flag and repeat.
3. Configure logging to CloudWatch (or bounded json-file) and a readiness probe that fails on SIGTERM; deploy twice and confirm zero failed requests in a load test during the rollout.
