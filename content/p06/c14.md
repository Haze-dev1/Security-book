# Kubernetes Failure Scenarios and When Not to Use Kubernetes

:::objectives
- Diagnose the recurring Kubernetes failures (CrashLoopBackOff, Pending pods, OOMKilled, evictions, DNS and networking faults, failed rollouts, node pressure) with a fixed procedure.
- Recognise the operational cost of Kubernetes honestly and evaluate alternatives for a given client.
- Make and document the platform decision as an engineer, not as a fashion choice.
:::

:::prereq
Chapters 8 to 13; Part V chapter 13.
:::

## The diagnostic procedure

Every Kubernetes problem is a controller that is not converging or a pod that is not healthy, and the cluster tells you why if you ask in the right order:

```bash
kubectl get pods -n prod -o wide                                   # 1. what state are things in? which nodes?
kubectl describe pod <pod> -n prod                                 # 2. Events at the bottom: scheduling, pulls, probes, kills
kubectl logs <pod> -n prod --previous --tail=200                   # 3. what did the crashed container say?
kubectl get events -n prod --sort-by=.lastTimestamp | tail -30     # 4. what else is happening?
kubectl rollout status deployment/<d> -n prod                      # 5. is a rollout stuck?
kubectl get nodes; kubectl describe node <node> | sed -n '/Conditions/,/Events/p'   # 6. node pressure? NotReady?
kubectl top pods -n prod --sort-by=memory; kubectl top nodes       # 7. resources
kubectl get endpointslices -n prod -l kubernetes.io/service-name=<svc>   # 8. does the Service have ready endpoints?
kubectl debug -it <pod> --image=nicolaka/netshoot --target=<container> -n prod   # 9. look from inside
```

## The scenarios

### CrashLoopBackOff

The container exits repeatedly; Kubernetes restarts with exponential backoff (10 s → 5 min). Almost always application-level: bad config or missing env/secret (fail-fast validation prints the reason), cannot reach a dependency at start, wrong command or entrypoint, missing file, permission denied under non-root, port already in use within the pod. `logs --previous` holds the answer; if the container dies before logging (exec format error, missing binary), `describe` shows the exit code and reason.

### Pending pods

`describe` → `FailedScheduling` with the reason: insufficient CPU/memory (requests too large or cluster full: autoscaler not working, max nodes reached, Spot unavailable); no node matches `nodeSelector`/affinity; taints without tolerations; PVC in another AZ or unbound; pod topology constraints unsatisfiable. Fix the request, the constraint, or the capacity.

### ImagePullBackOff

Wrong image name or tag (check the typo and whether the tag exists in the registry); registry authentication (node role lacks ECR pull permission, or missing `imagePullSecrets` for private registries); Docker Hub rate limiting (use a pull-through cache); network path to the registry blocked (private subnets without a NAT or VPC endpoint for ECR). `describe` shows the exact pull error.

### OOMKilled

Exit code 137 with reason `OOMKilled`: the container exceeded its memory limit. Compare `kubectl top` or metrics history with the limit; fix runtime heap flags (JVM, Node); find leaks (Part I chapter 7); raise the limit only with evidence. Node-level OOM (no limit set and the node ran out) shows as the kernel killing processes; set limits.

### Evicted pods

`Evicted` status with `The node was low on resource: memory` or `ephemeral-storage`: node pressure evicts pods, lowest priority and most over-request first. Causes: requests far below actual usage (set memory requests equal to limits), logs filling the node disk (ephemeral-storage limits, log rotation), too many pods per node. Evicted pods remain as records; clean them up and fix the pressure.

### Readiness never passes

Pod Running but 0/1 Ready: probe path or port wrong, app listening on 127.0.0.1 instead of 0.0.0.0, app genuinely not ready (cannot reach database), startup slower than the startup probe allows. `describe` shows `Readiness probe failed: ...` with the HTTP status or connection error. Check from inside with `kubectl debug` and `curl localhost:8000/health/ready`.

### Liveness restart storms

Restarts climbing on all pods at once, with `Liveness probe failed`: the probe is too strict or checks a dependency that blipped. Loosen thresholds and remove dependency checks from liveness (chapter 11).

### Service has no endpoints / 503 from ingress

`kubectl get endpointslices` empty: selector labels mismatch (`spec.selector` vs pod labels: the single most common typo), pods not Ready, wrong `targetPort`. Ingress 503/502: Service wrong, pods unready, or the ALB target group health check path failing (check the ALB console target health; the controller's logs explain annotation problems).

### DNS failures

`getent hosts` fails inside pods, intermittent `Name or service not known`: CoreDNS pods unhealthy or under-replicated (scale with the cluster; check their logs for `i/o timeout` to upstream), NetworkPolicy blocking UDP/TCP 53 to kube-system, `ndots` causing many lookups and timeouts under load (use FQDNs with trailing dots or tune `dnsConfig`), node-local DNS cache missing on large clusters. `kubectl -n kube-system logs -l k8s-app=kube-dns`.

### Node NotReady

Kubelet not reporting: node out of resources, kubelet crashed, network partition, instance terminated (Spot), disk full. Pods on it go Unknown and are rescheduled after the eviction timeout (5 minutes by default). Check the node's conditions and the cloud console; drain and replace rather than repair.

### Rollout stuck

`rollout status` hangs; `progressDeadlineExceeded`: new pods never become Ready (see above), PDB blocking (`maxUnavailable: 0` with a PDB that cannot be satisfied), insufficient capacity for the surge pod, image pull failing. `kubectl rollout undo` restores service while you investigate.

### Certificate and ingress controller faults

cert-manager stuck (`kubectl describe certificate`: challenge failing because DNS or HTTP route is wrong), ALB controller failing to reconcile (annotation typos, IAM permissions of the controller's role, subnet tags missing for auto-discovery). Controller logs are the source.

### Resource exhaustion by one tenant

Without `ResourceQuota` and `LimitRange` per namespace, one team's runaway job consumes the cluster. Set quotas per namespace and default limits for pods that omit them.

## The honest cost of Kubernetes

What you take on with a cluster, beyond the application:

- **Upgrades**: three Kubernetes releases a year, each supported about 14 months on EKS; every upgrade touches the control plane, node images, add-ons and often the platform components (ingress controller, cert-manager, policy engine, autoscaler, observability), with API deprecations breaking manifests. Budget several engineer-days per upgrade, several times a year, forever.
- **Platform components**: a dozen controllers to install, configure, secure, monitor and upgrade before the first application runs well.
- **Expertise**: debugging requires understanding the material in chapters 8–13; a team without it will be stuck during incidents.
- **Baseline cost**: the control plane fee plus minimum nodes plus the platform pods' resources before any application load; small clusters are proportionally expensive.
- **Security surface**: chapter 13's checklist is the minimum.
- **Multi-tenancy pitfalls**: quotas, network policies and RBAC for every team.

What you get: a uniform platform for many services with self-healing, scaling, rollouts and a vast ecosystem; portability across clouds and on-premises; a vocabulary and tooling your clients' platform teams may already use.

:::fde
Rule of thumb for engagements: if the client already runs Kubernetes with a competent platform team, deploy into it and follow their conventions. If they do not, do not introduce it for a single application or a handful of services; ECS Fargate (or a PaaS) gives the same application outcomes with a fraction of the operational surface, and the client can actually operate it after you leave. Write the decision down as an ADR with the triggers that would change it (number of services, multi-cloud, a platform team being hired). The worst outcome is a cluster nobody upgrades.
:::

## Common mistakes

- Choosing Kubernetes for two services and a two-person team.
- Upgrading the cluster without the add-ons and platform components.
- No alerts on Pending pods, NotReady nodes or failed rollouts.
- Diagnosing from the application logs while the answer is in `describe` events.
- Clusters left on versions past end of support.
- Treating a managed control plane as a managed platform.

## Exercises

1. On a local cluster, create each failure deliberately (bad tag, bad selector, memory limit too low, probe path wrong, default-deny without DNS) and diagnose each in under five minutes using only the procedure.
2. Write the upgrade runbook for an EKS cluster: pre-checks (deprecated APIs with `pluto` or `kubent`), add-on versions, node rotation, verification, rollback options.
3. Draft the platform-choice ADR for a hypothetical client with three services, no platform team, and an AWS account; include the triggers that would justify Kubernetes later.
