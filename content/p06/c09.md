## The problem

Three objects carry most of the daily work in Kubernetes: the Pod (what runs), the Deployment (how many and how to update), and the Service (how traffic finds them). Getting their specs right is the difference between a service that self-heals and rolls out cleanly and one that flaps, drops requests on deploy, or cannot be reached.

## Pods

A pod is one or more containers that share a network namespace (one IP, `localhost` between them), optionally share volumes, and are scheduled together on one node. Most pods have one application container; sidecars (log shippers, proxies) share the pod.

```yaml
apiVersion: v1
kind: Pod                      # you rarely create bare pods; this shows the spec a Deployment templates
metadata:
  name: api-example
  labels: { app: api, version: "3f9a1c4" }
spec:
  serviceAccountName: api                       # identity for RBAC and IAM (IRSA/Pod Identity)
  automountServiceAccountToken: false           # unless the app calls the Kubernetes API
  securityContext:
    runAsNonRoot: true
    runAsUser: 10001
    runAsGroup: 10001
    fsGroup: 10001
    seccompProfile: { type: RuntimeDefault }
  containers:
    - name: api
      image: 123456789012.dkr.ecr.eu-west-1.amazonaws.com/client/app@sha256:9f3a…   # by digest, or immutable tag
      ports: [{ name: http, containerPort: 8000 }]
      env:
        - { name: ENV, value: prod }
        - { name: DATABASE_URL, valueFrom: { secretKeyRef: { name: api-db, key: url } } }
      envFrom:
        - configMapRef: { name: api-config }
      resources:
        requests: { cpu: "250m", memory: "512Mi" }
        limits:   { memory: "512Mi" }           # memory limit = request; CPU limit omitted (chapter 6)
      readinessProbe:
        httpGet: { path: /health/ready, port: http }
        periodSeconds: 5
        failureThreshold: 3
      livenessProbe:
        httpGet: { path: /health/live, port: http }
        periodSeconds: 10
        failureThreshold: 3
      startupProbe:
        httpGet: { path: /health/ready, port: http }
        periodSeconds: 5
        failureThreshold: 30                    # up to 150 s to start before liveness kicks in
      securityContext:
        allowPrivilegeEscalation: false
        readOnlyRootFilesystem: true
        capabilities: { drop: [ALL] }
      volumeMounts:
        - { name: tmp, mountPath: /tmp }
      lifecycle:
        preStop: { exec: { command: ["sh", "-c", "sleep 5"] } }   # let endpoint removal propagate before SIGTERM (see rollouts)
  terminationGracePeriodSeconds: 30
  volumes:
    - name: tmp
      emptyDir: { medium: Memory, sizeLimit: 64Mi }
  topologySpreadConstraints:
    - maxSkew: 1
      topologyKey: topology.kubernetes.io/zone
      whenUnsatisfiable: ScheduleAnyway
      labelSelector: { matchLabels: { app: api } }
```

Pod lifecycle: **Pending** (not yet scheduled or pulling images) → **Running** → **Succeeded/Failed** (for jobs) or replaced. Containers restart within the pod on crash (with backoff: **CrashLoopBackOff**). Pods are not repaired; they are replaced. Anything that must survive lives outside the pod.

Init containers run to completion before the app containers (schema checks, waiting for dependencies, fetching config); use them sparingly and never for migrations in multi-replica deployments.

## Deployments

A Deployment manages ReplicaSets, which manage pods from a template. Changing the template (new image) creates a new ReplicaSet and shifts replicas over according to the strategy.

```yaml
apiVersion: apps/v1
kind: Deployment
metadata: { name: api, namespace: prod }
spec:
  replicas: 3
  revisionHistoryLimit: 10                      # old ReplicaSets kept for rollback
  selector: { matchLabels: { app: api } }
  strategy:
    type: RollingUpdate
    rollingUpdate: { maxSurge: 1, maxUnavailable: 0 }   # add one new pod, wait until Ready, then remove one old: zero capacity loss
  minReadySeconds: 10                           # a pod must stay Ready this long before counting as available
  progressDeadlineSeconds: 600                  # rollout stalls → marked failed (alert on this)
  template:
    metadata: { labels: { app: api } }
    spec: { ... the pod spec above ... }
```

```bash
kubectl apply -f api.yaml
kubectl rollout status deployment/api -n prod            # blocks until complete or failed; use in CI
kubectl rollout history deployment/api -n prod
kubectl rollout undo deployment/api -n prod               # back to previous ReplicaSet
kubectl rollout undo deployment/api --to-revision=4 -n prod
kubectl set image deployment/api api=…/app:NEWTAG -n prod  # imperative; prefer applying manifests from Git
kubectl scale deployment/api --replicas=5 -n prod          # or let the HPA do it (chapter 11)
```

How a rolling update avoids dropped requests: a new pod starts; its readiness probe passes; it is added to the Service endpoints; an old pod is selected for termination; it is **removed from endpoints** and **sent SIGTERM** at roughly the same time (the removal propagates asynchronously to kube-proxy and ingress controllers); the `preStop` sleep gives propagation a few seconds so no new requests arrive at a pod already draining; the app drains and exits within `terminationGracePeriodSeconds`. Readiness failing during shutdown (Part I chapter 6) and the preStop delay together make rollouts clean. Chapter 11 covers strategies in depth.

## Services

Pods have ephemeral IPs. A Service provides a stable virtual IP and DNS name that load-balances to the pods matching its selector, tracked via EndpointSlices.

```yaml
apiVersion: v1
kind: Service
metadata: { name: api, namespace: prod }
spec:
  type: ClusterIP                              # internal only (default)
  selector: { app: api }
  ports: [{ name: http, port: 80, targetPort: http }]
```

- **ClusterIP**: reachable inside the cluster at `api.prod.svc.cluster.local:80`. The default for service-to-service traffic; an Ingress or Gateway routes external traffic to ClusterIP services (chapter 10).
- **NodePort**: also opens a port (30000–32767) on every node. Rarely used directly in cloud; a building block.
- **LoadBalancer**: asks the cloud controller to provision a load balancer (on EKS with the AWS Load Balancer Controller: an NLB, or an ALB via Ingress) pointing at the pods. One per service, so costly if used for every service; prefer one Ingress/Gateway fronting many services.
- **Headless** (`clusterIP: None`): DNS returns pod IPs directly; used by StatefulSets and client-side load balancing (gRPC).
- **ExternalName**: a CNAME alias to an external hostname (e.g., an RDS endpoint), useful for indirection.

Traffic path: client resolves `api.prod.svc` via CoreDNS → ClusterIP → kube-proxy rules on the client's node DNAT to a ready pod IP → CNI routes to the pod. Only **Ready** pods are in the endpoints, which is why readiness probes are the key to zero-downtime deploys. Long-lived connections (HTTP/2, gRPC, WebSockets) pin to one pod; use an L7 proxy or client-side balancing for even distribution.

```bash
kubectl get endpointslices -n prod -l kubernetes.io/service-name=api     # which pod IPs are behind the Service
kubectl run -it --rm debug --image=nicolaka/netshoot -n prod -- curl -s http://api/health/ready
```

## Labels, selectors and namespaces

Labels (`app`, `version`, `tier`, `team`) connect objects: Services select pods by label; Deployments own pods by label; policies and monitoring filter by label. Keep a consistent scheme (the `app.kubernetes.io/*` recommended labels). Namespaces separate environments or teams within a cluster with their own RBAC, quotas and network policies; `prod` and `staging` in one cluster is common for small teams, separate clusters for stricter isolation.

## Reading the diagnostics

```bash
kubectl get pods -n prod -o wide                       # status, restarts, node, IP
kubectl describe pod api-7c9d-xyz -n prod              # events at the bottom: scheduling, pulls, probe failures, OOMKilled
kubectl logs api-7c9d-xyz -n prod --previous           # logs of the crashed previous container instance
kubectl get events -n prod --sort-by=.lastTimestamp | tail -20
kubectl top pods -n prod                               # resource usage (metrics-server required)
kubectl exec -it api-7c9d-xyz -n prod -- sh            # if the image has a shell; else kubectl debug
kubectl debug -it api-7c9d-xyz -n prod --image=nicolaka/netshoot --target=api   # ephemeral debug container sharing the pod's namespaces
```

| Status / event | Meaning | Look at |
|---|---|---|
| `Pending` with `FailedScheduling` | No node fits (resources, taints, affinity, PVC zone) | Requests vs node capacity; cluster autoscaler |
| `ImagePullBackOff` / `ErrImagePull` | Wrong image name/tag, registry auth, rate limit | Image reference, pull secrets, ECR permissions on the node role |
| `CrashLoopBackOff` | Container exits repeatedly | `logs --previous`; config, missing secret, bad command |
| `OOMKilled` (exit 137) | Exceeded memory limit | Limit vs usage; runtime heap flags |
| `Readiness probe failed` | App not ready; wrong path/port; slow start | Probe config, app logs, startup probe |
| `Liveness probe failed` → restarts | Probe too strict or app wedged | Liveness should not check dependencies |
| `Evicted` | Node pressure (memory/disk) | Requests = limits for memory; ephemeral storage limits |
| `Terminating` for a long time | Finalizers, or app ignoring SIGTERM | Grace period, PID 1 handling |

## Common mistakes

- Missing resource requests (scheduler packs blindly) or missing memory limits.
- Liveness probes that check the database; cascade restarts.
- `maxUnavailable: 1` with 2 replicas; half capacity during every deploy.
- No `preStop` delay and no readiness failure on shutdown; 502s on rollout.
- Mutable image tags; `rollout undo` goes "back" to the same bytes.
- One LoadBalancer Service per microservice.
- Bare pods in production (no controller to replace them).
- Forgetting `progressDeadlineSeconds` and alerts on stalled rollouts; CI "succeeds" while pods crash.
