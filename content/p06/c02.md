## The problem

An image is the deployable artifact of the container era: the thing CI builds, the registry stores, and the orchestrator runs. Understanding its structure explains why builds are fast or slow, why "the same tag" can run different code, why images bloat, and how to get the reproducibility that Part I promised.

## Layers and content addressing

An image is an ordered list of read-only **layers** (each a tarball of filesystem changes) plus a **config** (environment, entrypoint, user, exposed ports) and a **manifest** that lists them. Every layer and the manifest are identified by the SHA-256 **digest** of their content. Two images sharing base layers share them on disk and in the registry; a one-line code change produces one new layer and reuses the rest.

```bash
docker image inspect python:3.12-slim --format '{{json .RootFS.Layers}}' | jq      # layer digests
docker history --no-trunc myapp:2.4.0                                            # which Dockerfile instruction created each layer and its size
docker manifest inspect myapp:2.4.0                                              # the manifest (and multi-arch index)
```

The digest `sha256:…` of the manifest identifies the exact image. It never changes. A **tag** (`myapp:2.4.0`, `python:3.12-slim`, `latest`) is a mutable pointer to a manifest: the registry owner can move it at any time. This is the key fact for reproducibility (Part I chapter 9): deploy by digest, or by a tag you control and never move (an immutable tag such as the Git SHA).

```bash
docker pull python:3.12-slim
docker inspect --format '{{index .RepoDigests 0}}' python:3.12-slim     # python@sha256:2b5d...
# Dockerfile: pin by digest for a reproducible base
FROM python:3.12-slim@sha256:2b5d3a1b...
```

**Multi-architecture images**: a tag can point at an *index* listing manifests per platform (`linux/amd64`, `linux/arm64`); the client picks its own. Build with `docker buildx build --platform linux/amd64,linux/arm64` so the same tag runs on x86 hosts and Graviton/Apple Silicon.

## Registries

A registry is an HTTP service storing manifests and blobs (layers), addressed as `host/namespace/repository:tag` or `@digest`. Docker Hub (`docker.io/library/python`), GitHub Container Registry (`ghcr.io`), Amazon ECR (`123456789012.dkr.ecr.eu-west-1.amazonaws.com/app`), Google Artifact Registry, and self-hosted options (Harbor, the OCI distribution reference). Clients authenticate (`docker login`, ECR tokens from `aws ecr get-login-password`), pull manifests, then fetch only the layers they do not have.

### Amazon ECR in practice

```bash
aws ecr create-repository --repository-name client/app --image-scanning-configuration scanOnPush=true \
    --image-tag-mutability IMMUTABLE --encryption-configuration encryptionType=KMS
aws ecr get-login-password | docker login --username AWS --password-stdin 123456789012.dkr.ecr.eu-west-1.amazonaws.com
docker tag app:local 123456789012.dkr.ecr.eu-west-1.amazonaws.com/client/app:$(git rev-parse --short HEAD)
docker push 123456789012.dkr.ecr.eu-west-1.amazonaws.com/client/app:$(git rev-parse --short HEAD)
aws ecr describe-images --repository-name client/app --query 'sort_by(imageDetails,&imagePushedAt)[-3:].[imageTags,imageDigest,imageScanStatus.status]'
```

Settings that matter: **immutable tags** (a pushed tag cannot be overwritten; `latest` becomes impossible, which is the point); **scan on push** (basic scanning free; enhanced scanning via Inspector adds continuous rescanning and language packages); **encryption** with KMS; a **lifecycle policy** expiring untagged images after a day and keeping the last N tagged releases (registries fill up quietly and cost per GB); **repository policies** granting pull to the ECS task execution role or EKS nodes and push only to CI; **replication** to other regions for DR or multi-region deployments; **pull-through cache** rules so your hosts pull public images (Docker Hub, ECR Public, Quay) through ECR, avoiding rate limits and keeping copies under your control.

```json
{ "rules": [
  { "rulePriority": 1, "description": "expire untagged after 1 day", "selection": { "tagStatus": "untagged", "countType": "sinceImagePushed", "countUnit": "days", "countNumber": 1 }, "action": { "type": "expire" } },
  { "rulePriority": 2, "description": "keep last 30 tagged", "selection": { "tagStatus": "tagged", "tagPrefixList": [""], "countType": "imageCountMoreThan", "countNumber": 30 }, "action": { "type": "expire" } }
] }
```

Keep enough history for rollback (the last several releases) and for forensics (the image that was running when an incident occurred).

## Pulling reproducibly in production

ECS task definitions and Kubernetes manifests reference images. Reference by immutable tag *and* record the digest, or by digest outright (`image: …/app@sha256:…`). Kubernetes `imagePullPolicy: IfNotPresent` with a mutable tag is a classic source of "nodes running different code"; use unique tags or digests and `Always` is then unnecessary. For ECS, each deployment should create a new task definition revision pointing at the new tag; the revision history is your rollback list.

## Keeping images small

Why size matters: pull time on every scale-out and deploy (a 1.5 GB image takes a minute to pull cold; 80 MB takes seconds), attack surface (fewer packages, fewer CVEs), storage and transfer cost.

- Start from minimal bases: `python:3.12-slim` (~120 MB) rather than `python:3.12` (~1 GB); `node:22-alpine` or `-slim`; distroless (`gcr.io/distroless/*`, no shell, no package manager) for compiled languages and for runtimes with care; `scratch` for static Go/Rust binaries.
- Multi-stage builds (chapter 3) so build tools never reach the final image.
- One `RUN` for package installs with cleanup in the same layer (`apt-get install … && rm -rf /var/lib/apt/lists/*`); a later `RUN rm` does not shrink earlier layers.
- `.dockerignore` excluding `.git`, `node_modules`, test data, local env files (also a security control: `.env` files must never be copied in).
- Inspect with `docker history` and tools like `dive` to find the fat layers.

Alpine note: musl libc instead of glibc; some Python wheels and native modules misbehave or compile slowly. `-slim` Debian images are often the better trade for Python; Alpine shines for Go and Node.

## Layer caching and build performance

Docker reuses a layer if the instruction and all inputs are unchanged and every previous layer was reused. Order Dockerfile instructions from least to most frequently changing: base image, system packages, dependency manifests and install, then application code. Copying the whole source before installing dependencies invalidates the dependency layer on every code change. BuildKit's cache mounts (`RUN --mount=type=cache,target=/root/.cache/pip`) keep package caches between builds without baking them into layers; registry-backed cache (`--cache-to type=registry`) shares cache across CI runners. Chapter 3 shows the patterns.

## Image metadata

OCI labels record provenance: `org.opencontainers.image.source` (repo URL), `.revision` (commit), `.version`, `.created`. Set them in CI. Together with SBOMs and signatures (Part IV chapter 20), they make "what is this image?" answerable from the registry alone.

## Common mistakes

- Deploying `latest` or any mutable tag; different nodes run different code; rollback target unknown.
- No lifecycle policy; the registry quietly costs hundreds a month.
- Full base images with build tools in production; 1 GB pulls and hundreds of CVEs.
- Secrets or `.env` copied into images (they are in a layer forever, even if deleted later).
- `COPY . .` before dependency installation, destroying the cache.
- Mixing `apt-get update` and `install` in separate layers, producing stale package indexes.
- Pulling public images directly in production without a cache; Docker Hub rate limits break deploys.
- Forgetting multi-arch when moving to Graviton; `exec format error` at runtime.

## Exercises

1. Build an image, record its digest, retag it as `latest`, build a different image and push it as `latest` too; show that the digest changed while the tag did not. Then enable immutable tags on an ECR repository and observe the push rejection.
2. Compare image sizes and `docker history` for the same application on `python:3.12`, `python:3.12-slim` and a distroless base; run a scanner on each and compare CVE counts.
3. Write an ECR lifecycle policy and a pull-through cache rule; pull a public image through the cache and confirm it appears in your registry.
