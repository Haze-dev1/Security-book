# Health Probes, Autoscaling and Rolling Deployments

:::objectives
- Design readiness, liveness and startup probes that make rollouts clean and avoid restart storms.
- Configure the Horizontal Pod Autoscaler and cluster autoscaling (Cluster Autoscaler, Karpenter) so capacity follows demand.
- Use PodDisruptionBudgets and topology spread for availability during node maintenance and failures.
- Choose and tune rollout strategies (rolling, blue-green, canary) in Kubernetes, and roll back fast.
:::

:::prereq
Chapters 9 and 10; Part I chapter 6; Part II chapter 13.
:::

## The problem

Kubernetes' self-healing and scaling only work as well as the signals you give it. Wrong probes restart healthy pods or send traffic to unready ones; wrong autoscaling thrashes or never scales; missing disruption budgets let a node drain take out every replica at once; a rollout strategy chosen by default drops requests. This chapter is the tuning guide.

## Probes

```compare
    ["liveness", "Is the process wedged beyond recovery?", "Container restarted (with backoff)", "A trivial in-process check: the event loop responds", "Dependencies (database, cache); anything that fails during load spikes"]
  ]

```

The classic failure: a liveness probe that calls the database. The database has a 30-second hiccup; every pod fails liveness; Kubernetes restarts them all; cold starts amplify the outage. Liveness should fail only when a restart would help. Readiness including dependencies is a trade: it stops sending traffic to pods that would fail anyway (good) but if the dependency is down for everyone, all pods go unready and the load balancer returns 503 instead of the app's own error (sometimes fine, sometimes worse). Many teams make readiness check only local state plus a cached dependency status, and surface dependency health via metrics (Part XI chapter 5).

Timing: `periodSeconds` 5–10, `failureThreshold` 3 for readiness; `startupProbe` with `failureThreshold` sized to the slowest legitimate start (JVM: 60 × 5 s); liveness `periodSeconds` 10–20 with threshold 3. Probes cost a request each; keep endpoints cheap.

## Horizontal Pod Autoscaler

The HPA adjusts a Deployment's replica count to hold a metric at a target: CPU utilisation (relative to **requests**, so requests must be set honestly), memory, or custom/external metrics (requests per second from the ingress, queue depth from SQS via KEDA or the external metrics API).

```yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata: { name: api, namespace: prod }
spec:
  scaleTargetRef: { apiVersion: apps/v1, kind: Deployment, name: api }
  minReplicas: 3                             # ≥ number of AZs for availability
  maxReplicas: 30
  metrics:
    - type: Resource
      resource: { name: cpu, target: { type: Utilization, averageUtilization: 60 } }
    - type: Pods
      pods: { metric: { name: http_requests_per_second }, target: { type: AverageValue, averageValue: "200" } }
  behavior:
    scaleUp:   { stabilizationWindowSeconds: 0,  policies: [{ type: Percent, value: 100, periodSeconds: 60 }] }    # double fast
    scaleDown: { stabilizationWindowSeconds: 300, policies: [{ type: Pods, value: 2, periodSeconds: 120 }] }       # shrink slowly
```

Rules: target 50–70% CPU to leave headroom for the scale-up delay (pods take time to start and warm); scale up fast and down slow; set `minReplicas` for availability, not cost; do not set the Deployment's `replicas` field when an HPA manages it (every `apply` would reset it); for workers, scale on queue depth (KEDA makes this straightforward: `ScaledObject` on SQS queue length, scaling to zero when idle). Vertical Pod Autoscaler recommends (or sets) requests from observed usage; use it in recommendation mode to right-size.

## Cluster autoscaling

The HPA adds pods; something must add nodes when pods go Pending. **Cluster Autoscaler** grows and shrinks node groups (ASGs) based on pending pods and utilisation. **Karpenter** (AWS-originated, now CNCF) provisions right-sized nodes directly from pending pod requirements in seconds, consolidates underused nodes, and mixes instance types and Spot; it is the better default on EKS for most teams. Both need pods with accurate **requests**, PodDisruptionBudgets so consolidation does not break availability, and limits on how far they may scale (cost guardrails). Fargate profiles avoid node management entirely for pods matching a selector, at a higher per-pod price and with some limitations (no DaemonSets, no privileged, slower start).

## Availability during disruptions

Nodes get drained for upgrades, Spot reclaims, autoscaler consolidation. Protect services:

- **PodDisruptionBudget**: `minAvailable: 2` (or `maxUnavailable: 1`) stops voluntary evictions from taking too many replicas at once. Without a PDB, a node drain can evict all replicas of a 2-replica service together.
- **Topology spread** across zones and nodes (chapter 9's `topologySpreadConstraints`), or pod anti-affinity, so one AZ or node failure leaves capacity.
- **Replicas ≥ 2**, ideally 3 across 3 AZs, for anything user-facing.
- **Graceful shutdown** handling (chapter 9) so evictions do not drop requests.

```yaml
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata: { name: api, namespace: prod }
spec:
  minAvailable: 2
  selector: { matchLabels: { app: api } }
```

## Rollout strategies

**Rolling update** (Deployment default): `maxSurge`/`maxUnavailable` control the pace. `maxSurge: 25%, maxUnavailable: 0` keeps full capacity; `maxUnavailable: 25%` saves resources at the cost of capacity. Combined with clean probes and shutdown, this is zero-downtime for most services. Monitor `rollout status` in CI and alert on `progressDeadlineExceeded`.

**Blue-green**: run the new version as a separate Deployment (green) alongside the old (blue); switch the Service selector (or the Ingress backend) when green is verified; keep blue for instant rollback. Costs double capacity briefly; gives atomic switch and trivial rollback. Argo Rollouts and Flagger automate it.

**Canary**: route a small percentage of traffic (via Gateway API weights, a service mesh, or Argo Rollouts/Flagger with an ingress that supports weighting) to the new version; watch error rate and latency metrics; promote in steps or abort automatically. The strongest protection against bad releases; requires good metrics and an L7 router that supports weights. Part X chapter 7 compares strategies platform-independently.

**Recreate**: stop all old pods, then start new ones. Downtime; only for singletons that cannot run two versions.

## Rollback

`kubectl rollout undo` returns to the previous ReplicaSet in seconds; with GitOps (Argo CD, Flux) you revert the Git commit and the controller reconciles, which keeps the audit trail. Rollback is only safe if the previous version is compatible with the current database schema (expand/contract migrations, Part X chapter 8) and with any config changes shipped alongside. Test rollback in staging as part of every release.

## Common mistakes

- Liveness probes checking dependencies.
- Readiness and liveness pointing at the same heavy endpoint.
- No startup probe; slow apps killed by liveness during start.
- HPA on CPU with no requests set (percentages meaningless) or with `replicas` hard-coded in manifests fighting the HPA.
- Scale-down as fast as scale-up; flapping.
- No PDB; node drains cause outages.
- `minReplicas: 1`; a single pod restart is downtime.
- Rollout "succeeded" in CI because nobody waited for `rollout status`.
- Rollback attempted after an incompatible migration.

## Exercises

1. Configure startup, readiness and liveness probes for an app with a slow start; simulate a dependency outage and confirm pods go unready but are not restarted.
2. Set up an HPA on CPU (and, with KEDA, on queue depth for a worker); load test and graph replicas, CPU and latency; tune the target and scale-down policy.
3. Create a PDB, then drain a node (`kubectl drain`) and observe that evictions respect it; remove the PDB and repeat to see the difference.
