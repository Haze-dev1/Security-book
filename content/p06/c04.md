# Docker Compose

:::objectives
- Define a complete local development environment (application, database, cache, proxy, workers) in one Compose file.
- Use networks, volumes, healthchecks, dependency ordering, profiles and overrides correctly.
- Keep development close to production without using Compose as a production orchestrator.
- Troubleshoot Compose stacks quickly.
:::

:::prereq
Chapters 2 and 3; Part I chapter 11.
:::

## The problem

A new engineer should be able to clone a repository and run the whole system locally in minutes, with the same database engine, cache and message broker as production (Part I chapter 11). Doing that by hand (install PostgreSQL 16, Redis 7, set up users, configure ports) takes a day and produces machine-specific drift. Docker Compose describes the set of containers, their networks and volumes in one file, and starts them with one command. It is the standard tool for local development and integration tests, and a reasonable choice for single-host deployments of small systems; it is not an orchestrator for production fleets.

## A complete development stack

```yaml
@file: docker-compose.yml
name: clientapp
services:
  db:
    image: postgres:16.4
    environment:
      POSTGRES_USER: app
      POSTGRES_PASSWORD: app            # development only; never real credentials in this file
      POSTGRES_DB: app
    ports: ["127.0.0.1:5432:5432"]       # bind to localhost so the dev DB is not exposed on the LAN
    volumes:
      - pgdata:/var/lib/postgresql/data
      - ./db/init:/docker-entrypoint-initdb.d:ro       # extensions, roles on first start
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U app -d app"]
      interval: 5s
      timeout: 3s
      retries: 10
    command: ["postgres", "-c", "log_statement=all", "-c", "log_min_duration_statement=200"]   # see slow queries in dev

  redis:
    image: redis:7.4-alpine
    command: ["redis-server", "--maxmemory", "128mb", "--maxmemory-policy", "allkeys-lru"]
    ports: ["127.0.0.1:6379:6379"]
    healthcheck: { test: ["CMD", "redis-cli", "ping"], interval: 5s, retries: 10 }

  localstack:                          # S3/SQS/Secrets Manager emulation for local AWS integration
    image: localstack/localstack:3.8
    environment: { SERVICES: "s3,sqs,secretsmanager", DEFAULT_REGION: eu-west-1 }
    ports: ["127.0.0.1:4566:4566"]
    volumes: ["./localstack/init:/etc/localstack/init/ready.d:ro"]   # create buckets/queues on start
    profiles: ["aws"]                    # only started with --profile aws

  api:
    build:
      context: .
      target: build                      # dev uses the build stage (has dev deps); prod uses runtime
    command: uvicorn app.main:app --host 0.0.0.0 --port 8000 --reload
    env_file: .env                       # developer's local config (gitignored); .env.example documents keys
    environment:
      DATABASE__HOST: db                 # service names resolve via Compose DNS
      REDIS_URL: redis://redis:6379/0
      AWS_ENDPOINT_URL: http://localstack:4566
    volumes:
      - .:/app                           # live code for --reload
      - /app/.venv                       # anonymous volume: keep the image's venv, don't shadow it with the host dir
    ports: ["8000:8000"]
    depends_on:
      db: { condition: service_healthy }
      redis: { condition: service_healthy }
    develop:
      watch:                             # Compose Watch: sync/rebuild on file changes (alternative to bind mounts)
        - action: sync
          path: ./app
          target: /app/app

  worker:
    build: { context: ., target: build }
    command: python -m app.worker
    env_file: .env
    environment: { DATABASE__HOST: db, REDIS_URL: redis://redis:6379/0, AWS_ENDPOINT_URL: http://localstack:4566 }
    volumes: [".:/app", "/app/.venv"]
    depends_on: { db: { condition: service_healthy }, redis: { condition: service_healthy } }

  proxy:
    image: caddy:2.8-alpine
    volumes: ["./dev/Caddyfile:/etc/caddy/Caddyfile:ro", "caddy_data:/data"]
    ports: ["443:443", "80:80"]
    depends_on: [api]
    profiles: ["proxy"]                  # optional: test the real proxy config locally with internal TLS

volumes:
  pgdata:
  caddy_data:
```

```bash
docker compose up -d                       # start core services
docker compose --profile aws up -d         # include LocalStack
docker compose logs -f api worker          # follow logs
docker compose exec api pytest             # run tests inside the api container
docker compose exec db psql -U app         # database shell
docker compose ps; docker compose top
docker compose down                        # stop, keep volumes;   down -v removes data (deliberate!)
docker compose build --no-cache api        # rebuild after Dockerfile changes
docker compose config                      # render the effective config after overrides and env substitution
```

## Concepts that make it work

- **Networks**: Compose creates a project network; services reach each other by service name (`db`, `redis`) via embedded DNS. Published `ports` are only for reaching services from the host. Add a second network to isolate groups when needed.
- **Volumes**: named volumes (`pgdata`) persist data across container recreation and are managed by Docker; bind mounts (`.:/app`) share host directories for live code. The anonymous volume trick (`/app/.venv`) preserves a directory from the image that would otherwise be hidden by the bind mount.
- **Healthchecks and `depends_on` conditions**: `service_healthy` waits for the dependency to be *ready*, not just started, removing the "connection refused on first start" race. Applications should still retry on start-up; real environments do not have Compose ordering.
- **Profiles**: optional services (LocalStack, proxy, observability stack) started on demand.
- **Overrides**: `docker-compose.override.yml` is merged automatically (developer-local tweaks); `-f docker-compose.yml -f docker-compose.ci.yml` for CI variants (no bind mounts, no ports, `target: runtime`, test command).
- **Env substitution**: `${VAR:-default}` in the file, values from the shell or a `.env` next to the file (distinct from `env_file:` for a service).
- **Resource limits**: `deploy.resources.limits` is honoured by `docker compose` for local parity with production limits (useful to catch memory issues early).

## Integration tests with Compose

CI can bring up the stack and run tests against real services:

```yaml
@file: docker-compose.ci.yml
services:
  api:
    build: { context: ., target: test }
    command: pytest -q --junitxml=/reports/junit.xml
    volumes: ["./reports:/reports"]
    environment: { DATABASE__HOST: db, REDIS_URL: redis://redis:6379/0 }
    ports: []
```

```bash
docker compose -f docker-compose.yml -f docker-compose.ci.yml run --rm --build api
docker compose -f docker-compose.yml -f docker-compose.ci.yml down -v
```

Testcontainers (per-test ephemeral containers from code) is the alternative when tests need isolated databases per test class.

## Compose in production (and its limits)

For a single-host deployment (Part V chapter 14 variation), `docker compose up -d` with a production file (images from the registry by immutable tag, no bind mounts, `restart: unless-stopped`, resource limits, logging driver configured, secrets from files or an external store, Caddy as the proxy) is legitimate and widely used for small systems. What it lacks: multi-host scheduling, rolling deploys with health gating (recreating a service drops connections briefly), autoscaling, secret management beyond files, and self-healing across hosts. When you need those, you need an orchestrator (chapters 8–14) or a managed container service (Part VII chapter 8). Do not stretch Compose into a fleet manager with scripts.

## Troubleshooting Compose stacks

| Symptom | Likely cause | Check |
|---|---|---|
| `connection refused` to db on first start | Dependency not ready | `depends_on` with `service_healthy`; app retry logic |
| Code changes not reflected | Bind mount path wrong, or `--reload` missing, or Compose Watch not running | `docker compose exec api ls /app`; `docker compose watch` |
| `ModuleNotFoundError` after bind mount | Host dir shadowed the image's venv/node_modules | Anonymous volume for `/app/.venv` or `/app/node_modules` |
| Port already allocated | Another process/stack on the port | `ss -ltnp`; change host port |
| Permission denied on volume | UID mismatch between container user and host files | Match UIDs, or `user: "${UID}:${GID}"`, or fix ownership |
| Data vanished | `down -v`, or a volume name changed with the project name | `docker volume ls`; set `name:` |
| Slow on macOS/Windows | Bind mount filesystem overhead | Compose Watch sync, fewer mounted paths, named volumes for deps |
| Service exits immediately | Wrong command, missing env, crash | `docker compose logs svc`; `docker compose run --rm svc sh` |

## Common mistakes

- Real credentials in the Compose file committed to Git.
- Database ports published on `0.0.0.0` on a laptop on a shared network (Part V chapter 7 showed Docker bypasses ufw).
- `depends_on` without health conditions; flaky first starts.
- `down -v` in a habit; development data lost repeatedly (or worse, run against a production host).
- Compose stacks diverging from the production Dockerfile targets and environment variables.
- Using Compose to manage multi-host production.

## Exercises

1. Write a Compose file for a project with database, cache, API and worker, with healthchecks and profiles. Time a fresh clone to a running stack.
2. Add a CI override that runs the test stage against the stack and produces a JUnit report; run it locally and in CI.
3. Introduce a dependency race by removing the health condition; observe the failure; add application-level retry so the service survives without Compose ordering.
