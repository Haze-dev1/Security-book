# Image Security

:::objectives
- Build images that minimise attack surface: minimal bases, non-root users, no secrets, pinned and scanned dependencies.
- Harden the runtime: dropped capabilities, read-only filesystems, seccomp and AppArmor profiles, no privileged mode.
- Scan, sign and verify images, and keep them patched through rebuilds.
- Recognise the container-specific misconfigurations that lead to host compromise.
:::

:::prereq
Chapters 1, 2, 3 and 6; Part IV chapter 20.
:::

## The problem

Containers made it easy to ship an entire userland with the application, and therefore easy to ship a userland full of unpatched packages, running as root, with the Docker socket mounted "for convenience". Image security is the discipline of shipping as little as possible, as an unprivileged user, verified and current, and of running it with the fewest privileges the kernel can grant.

## Build-time hardening

1. **Minimal base**: `-slim`, distroless or `scratch`. Fewer packages, fewer CVEs, no shell for an attacker to use (distroless), smaller pulls.
2. **Pin** base images by digest and dependencies by lockfile (chapter 2; Part I chapter 9).
3. **Non-root user** with a fixed UID (`USER 10001`); files owned appropriately; no `sudo` in the image.
4. **No secrets** in layers: BuildKit secret mounts for build-time credentials; `.dockerignore` for `.env`, keys, `.git`.
5. **Multi-stage** so compilers, package managers and dev dependencies never reach the runtime image (chapter 3).
6. **No unnecessary tools**: `curl`/`wget` only if health checks need them (or use a tiny static health binary), no `ssh`, no package manager in the final stage where possible.
7. **Labels and SBOM**: provenance metadata and a generated SBOM attached to the image (Part IV chapter 20).
8. **Scan in CI** and fail on critical/high with fixes available; rescan continuously in the registry (ECR enhanced scanning) because CVEs are published after you built.

```dockerfile
# Distroless runtime for a Python app (no shell, no package manager)
FROM python:3.12-slim AS build
# ... install deps into /app/.venv as in chapter 3 ...
FROM gcr.io/distroless/python3-debian12:nonroot
COPY --from=build --chown=nonroot:nonroot /app /app
WORKDIR /app
ENV PATH="/app/.venv/bin:$PATH"
USER nonroot
ENTRYPOINT ["/app/.venv/bin/python", "-m", "gunicorn", "app.main:app", "-c", "gunicorn.conf.py"]
```

Trade-offs: distroless has no shell, so `docker exec … sh` does not work (use `kubectl debug` ephemeral containers or a debug variant image); some tools expect `/bin/sh`. For many Python stacks, `slim` with aggressive cleanup is a pragmatic middle ground.

## Runtime hardening

The kernel primitives from chapter 1 become flags:

```bash
docker run -d \
  --user 10001:10001 \
  --read-only --tmpfs /tmp:rw,noexec,nosuid,size=64m \
  --cap-drop ALL --cap-add NET_BIND_SERVICE \          # only if binding <1024; otherwise drop everything
  --security-opt no-new-privileges:true \              # setuid binaries cannot escalate
  --security-opt seccomp=default.json \                # Docker's default profile is applied automatically; a custom one tightens further
  --security-opt apparmor=docker-default \
  --pids-limit 256 --memory 512m --cpus 1 \
  --network appnet -p 127.0.0.1:8000:8000 \
  app:3f9a1c4
```

Kubernetes expresses the same in the pod `securityContext` (chapter 13): `runAsNonRoot`, `runAsUser`, `readOnlyRootFilesystem`, `allowPrivilegeEscalation: false`, `capabilities.drop: [ALL]`, `seccompProfile: RuntimeDefault`. ECS: `user`, `readonlyRootFilesystem`, `linuxParameters.capabilities.drop`, and Fargate's platform applies restrictions by default (no privileged, no host mounts).

### Never do these

- **`--privileged`**: disables nearly all isolation; the container can load kernel modules, access all devices, and trivially escape. Only for a few infrastructure agents, never for applications.
- **Mounting the Docker socket** (`/var/run/docker.sock`) into a container: equivalent to root on the host. CI runners and "Docker-in-Docker" setups do this casually; use rootless builders (BuildKit, Kaniko) or dedicated build hosts.
- **Host network/PID/IPC namespaces** for applications.
- **Host path mounts** of sensitive directories (`/`, `/etc`, `/var/lib/docker`).
- **Adding `SYS_ADMIN`** or other powerful capabilities to "make something work".
- **Running as root** because a port is below 1024 (use a higher port behind the load balancer, or `NET_BIND_SERVICE`).

## Scanning and policy

- **CI**: Trivy or Grype against the built image; fail on CRITICAL/HIGH with `--ignore-unfixed` to avoid blocking on vulnerabilities with no fix (track them separately).
- **Registry**: ECR scanning on push and continuous (enhanced); alerts on new critical findings for images in production.
- **Admission**: in Kubernetes, policies (Kyverno, Gatekeeper, Pod Security Admission) reject pods that run as root, mount host paths, or use unsigned images.
- **Runtime**: Falco or GuardDuty Runtime Monitoring detect anomalous behaviour (a shell spawned in a web container, outbound connections to unexpected hosts, writes to binaries).

```bash
trivy image --severity CRITICAL,HIGH --ignore-unfixed --exit-code 1 123456789012.dkr.ecr.eu-west-1.amazonaws.com/client/app:3f9a1c4
trivy image --format cyclonedx --output sbom.json …/client/app:3f9a1c4
docker scout cves …/client/app:3f9a1c4          # alternative scanner
```

Triage honestly: a CVE in a library the application never loads is lower priority than a medium in the HTTP parser. Record exceptions with expiry dates (Part IV chapter 20).

## Signing and verification

Sign images in CI with Sigstore cosign (keyless via the CI's OIDC identity, or a KMS key) and verify at deploy time: Kubernetes admission (policy-controller, Kyverno `verifyImages`), or a deploy step that runs `cosign verify` before updating the ECS service. Attach SBOM and provenance attestations. The deployer then refuses anything not built by your pipeline from your repository.

```bash
cosign sign --yes …/client/app@sha256:…                          # keyless: identity bound to the CI workflow
cosign verify --certificate-identity-regexp 'https://github.com/client/app/.github/workflows/build.yml@refs/heads/main' \
              --certificate-oidc-issuer https://token.actions.githubusercontent.com …/client/app@sha256:…
```

## Patching: rebuild, do not patch in place

Containers are immutable; you do not `apt upgrade` inside a running container. Patching means rebuilding the image with updated base layers and dependencies, scanning, and redeploying. Automate a **scheduled rebuild** (weekly, plus on base-image security advisories) even when the application code has not changed; otherwise a service that has not deployed in three months runs three months of unpatched libraries. Dependabot/Renovate for base image tags and dependencies; a nightly CI job that rebuilds `main` and alerts on new findings.

## Secrets and configuration

Chapter 6 covered injection. Security specifics: secrets as files (tmpfs) rather than environment where feasible; never `docker inspect`-visible in CI logs; no secrets in image labels or `ENV`; scan images for accidentally included secrets (`trivy image --scanners secret`).

## Supply chain for images

Base images from official or verified publishers only (Docker Official Images, Chainguard, distroless, the language's official images); pull through a cache you control (ECR pull-through cache); verify base image signatures where published; pin by digest. A compromised or typosquatted base image is total compromise of everything built on it.

## Common mistakes

- Root user; full base image; no scan.
- `--privileged` or the Docker socket in application or CI containers.
- Images rebuilt only when code changes; libraries years old.
- Scanner output ignored or every finding treated equally.
- Secrets in `ENV` or layers.
- `latest` base tags; surprise breakage and unknown content.
- Health check tooling (`curl`) as an excuse to keep a full toolset in the image.
- Debug images (with shells and tools) deployed to production instead of the hardened variant.

## Exercises

1. Scan a full-base image and a hardened multi-stage variant of the same app; compare CVE counts; move to a slim or distroless base and rescan.
2. Run the application with the full runtime hardening flag set; fix whatever breaks (writable paths, capabilities) properly rather than loosening.
3. Sign an image with cosign in CI and add a verification step to the deploy; try deploying an unsigned image and confirm the refusal.
