## The problem

Before containers, deploying an application meant making a server match the developer's machine: the right Python, the right system libraries, the right configuration files, in the right places, for every application sharing the server, without conflicts. Virtual machines solved isolation at the cost of a full operating system per application (gigabytes, minutes to boot). Containers deliver most of the isolation with none of the overhead by using features the Linux kernel already had: a process can be given a private view of the filesystem, network, process tree and hostname, and a hard limit on resources, while sharing the kernel with everything else on the host.

The outcome that mattered for the industry: the **image** became the unit of deployment. Build once, run the identical bytes everywhere (Part I chapters 1 and 9). "Works on my machine" became "ships in my container".

## A container is a process

There is no container object in the Linux kernel. A container is an ordinary process (tree) started with a particular combination of kernel features:

## Seeing it from the host

```bash
docker run -d --name demo --memory=256m --cpus=1 -p 8080:80 nginx:1.27
PID=$(docker inspect -f '{{.State.Pid}}' demo)

# namespaces: the container's processes live in different namespaces from your shell
sudo ls -l /proc/$PID/ns/            # net, pid, mnt, uts... each a distinct inode vs. /proc/self/ns/
sudo nsenter -t $PID -n ip addr      # enter its network namespace: its own eth0 with 172.17.0.x
sudo nsenter -t $PID -p -m ps aux    # its process tree: nginx is PID 1 there
ps -o pid,user,cmd -p $PID           # from the host it is just a process (often running as root!)

# cgroups: the limits are files
cat /sys/fs/cgroup/system.slice/docker-$(docker inspect -f '{{.Id}}' demo).scope/memory.max    # 268435456
cat /sys/fs/cgroup/system.slice/docker-*/cpu.max                                               # 100000 100000 (1 CPU)
cat /sys/fs/cgroup/system.slice/docker-*/memory.current

# overlay filesystem: layers merged into one root
docker inspect -f '{{.GraphDriver.Data.MergedDir}}' demo
sudo ls $(docker inspect -f '{{.GraphDriver.Data.UpperDir}}' demo)    # the writable layer: what the container changed

# capabilities and seccomp
docker inspect -f '{{.HostConfig.CapAdd}} {{.HostConfig.CapDrop}}' demo
grep -E 'Cap(Eff|Bnd)|Seccomp' /proc/$PID/status
```

The last `ps` line is the one to remember: by default the process inside runs as root, and that is root on the host kernel, constrained only by namespaces, capabilities and seccomp. Chapter 7 is about closing that gap.

## What containers give you

- **Reproducible artifacts**: the image contains the runtime, libraries and code; the host needs only a container runtime.
- **Isolation of dependencies**: two applications with conflicting library versions coexist.
- **Density and speed**: start in milliseconds; dozens per host; share the kernel and image layers.
- **Portability**: the same image runs on a laptop, CI, ECS, Kubernetes.
- **Declarative resource limits**: memory and CPU bounds per process tree.
- **An ecosystem**: registries, orchestrators, scanners, a common vocabulary with clients.

## What containers do not give you

- **A security boundary equal to a VM.** Treat a container as a process with extra isolation. Multi-tenant workloads running untrusted code need microVMs or sandboxed runtimes.
- **Persistence.** The writable layer vanishes with the container; data belongs in volumes or external stores (chapter 5).
- **Freedom from operations.** Images must be rebuilt for patches (chapter 7), hosts must still be maintained (unless Fargate), orchestration adds its own complexity (chapters 8–14).
- **Performance isolation by default.** Without limits, one container can starve the host; with limits, you must size them (Part I chapter 7).

## Runtimes and standards

The Open Container Initiative (OCI) standardises the **image format** and the **runtime specification**. `runc` is the reference low-level runtime that creates the namespaces and cgroups; `containerd` (used by Docker and Kubernetes) and `CRI-O` manage images and containers above it; Docker adds the build tooling, CLI and daemon; Podman offers a daemonless, rootless alternative with a Docker-compatible CLI. Images built with any OCI tool run on any OCI runtime, which is why "Docker image" and "container image" are used interchangeably.

**Rootless containers** (Podman default, Docker rootless mode) run the daemon and containers as an unprivileged user with user namespaces, closing the "root in the container is root on the host" gap at some cost in features and performance.

## Common misconceptions

- "Containers are lightweight VMs." They share the kernel; the isolation model is different and weaker.
- "Root inside the container is harmless." It is root on the host kernel with fewer capabilities; escapes have happened via kernel bugs and misconfiguration (mounted Docker socket, `--privileged`).
- "The container has its own OS." It has its own userland files; the kernel is the host's. An Alpine image on an Ubuntu host runs on Ubuntu's kernel.
- "Data written inside the container is saved." Only until the container is removed.
