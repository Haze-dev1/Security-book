# Kubernetes Security

:::objectives
- Apply a defence-in-depth baseline to a cluster: authentication and RBAC, pod security standards, network policies, secrets handling, supply chain controls, node and control-plane hardening.
- Map Kubernetes identities to cloud IAM safely (IRSA / Pod Identity) and avoid over-privileged service accounts.
- Use admission policy to make the secure configuration the only configuration.
- Audit a cluster against the common misconfigurations.
:::

:::prereq
Chapters 7 to 12; Part IV chapters 1, 7, 17 and 18.
:::

## The problem

A Kubernetes cluster concentrates every workload, secret and credential of a platform behind one API. Its defaults favour getting things running: pods run as root, every pod can talk to every pod, service accounts are auto-mounted, and anyone with `kubectl` access to a namespace can read its Secrets. A cluster secured only by its defaults is a single compromised container away from a full platform breach. The controls below are layered so that each failure is contained.

## Authentication and RBAC

Humans authenticate via the identity provider (EKS: IAM principals through SSO mapped by **access entries** with access policies, or OIDC directly). Map groups, not individuals; keep `cluster-admin` for a break-glass group with alerts on use. Developers get namespace-scoped roles: read pods/logs, maybe `exec` in staging, no Secrets read in production.

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata: { name: developer, namespace: prod }
rules:
  - apiGroups: [""]
    resources: [pods, pods/log, services, configmaps, events]
    verbs: [get, list, watch]
  - apiGroups: [apps]
    resources: [deployments, replicasets]
    verbs: [get, list, watch]
  # no secrets; no pods/exec in prod; no create/delete
---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata: { name: developers, namespace: prod }
subjects: [{ kind: Group, name: "eng-developers", apiGroup: rbac.authorization.k8s.io }]
roleRef: { kind: Role, name: developer, apiGroup: rbac.authorization.k8s.io }
```

Audit RBAC: `kubectl auth can-i --list --as=system:serviceaccount:prod:api`; tools like `rbac-lookup`, `kubectl-who-can`. Watch for wildcards (`verbs: ["*"]`), `cluster-admin` bindings, and permission to create pods or `pods/exec` (which is effectively root in the namespace and, with host mounts, on the node).

## Workload identity: pods and AWS

Each service account that needs AWS access gets its own IAM role via **IRSA** (IAM Roles for Service Accounts: the cluster's OIDC provider issues projected tokens the SDK exchanges with STS) or **EKS Pod Identity** (an agent on the node brokers role credentials per pod; simpler setup, fewer IAM trust policy edits). Either way: one role per workload, resource-scoped policies (Part IV chapter 18), and **no workload permissions on the node instance role**. Block pods from the node's IMDS (set hop limit to 1 on nodes, or use the VPC CNI's network policy, or Pod Identity's IMDS restrictions) so a pod cannot steal node credentials.

```yaml
apiVersion: v1
kind: ServiceAccount
metadata:
  name: api
  namespace: prod
  annotations:
    eks.amazonaws.com/role-arn: arn:aws:iam::123456789012:role/prod-api      # IRSA
automountServiceAccountToken: false   # pods that do not call the Kubernetes API should not have a token at all
```

## Pod security

The **Pod Security Standards** define three profiles: privileged, baseline, restricted. **Pod Security Admission** (built-in) enforces them per namespace via labels:

```yaml
apiVersion: v1
kind: Namespace
metadata:
  name: prod
  labels:
    pod-security.kubernetes.io/enforce: restricted
    pod-security.kubernetes.io/enforce-version: latest
    pod-security.kubernetes.io/warn: restricted
    pod-security.kubernetes.io/audit: restricted
```

`restricted` requires: non-root, no privilege escalation, all capabilities dropped (NET_BIND_SERVICE allowed), seccomp RuntimeDefault or Localhost, no host namespaces or host paths, restricted volume types. The pod spec in chapter 9 complies. Platform namespaces (CNI, logging agents) legitimately need `privileged` or `baseline`; keep them separate.

For richer policy (require labels, restrict registries, verify signatures, forbid `latest`, require resource limits, mutate defaults), use **Kyverno** or **OPA Gatekeeper**:

```yaml
apiVersion: kyverno.io/v1
kind: ClusterPolicy
metadata: { name: restrict-registries }
spec:
  validationFailureAction: Enforce
  rules:
    - name: only-our-ecr
      match: { any: [{ resources: { kinds: [Pod] } }] }
      validate:
        message: "images must come from our ECR and not use :latest"
        pattern:
          spec:
            containers:
              - image: "123456789012.dkr.ecr.eu-west-1.amazonaws.com/* & !*:latest"
```

Admission policy turns "we recommend non-root" into "non-root or it does not run".

## Network policy

Default Kubernetes networking is flat: a compromised frontend pod can connect to the database pod or the internal admin service directly. **NetworkPolicy** restricts pod-to-pod and egress traffic, enforced by a capable CNI (enable the VPC CNI's network policy feature on EKS, or run Calico/Cilium).

```yaml
# Default deny all ingress and egress in the namespace
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata: { name: default-deny, namespace: prod }
spec:
  podSelector: {}
  policyTypes: [Ingress, Egress]
---
# Allow DNS egress for everything (needed once default deny is on)
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata: { name: allow-dns, namespace: prod }
spec:
  podSelector: {}
  policyTypes: [Egress]
  egress:
    - to: [{ namespaceSelector: { matchLabels: { kubernetes.io/metadata.name: kube-system } } }]
      ports: [{ protocol: UDP, port: 53 }, { protocol: TCP, port: 53 }]
---
# api: ingress from the ingress controller / ALB; egress to RDS and the Internet on 443
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata: { name: api, namespace: prod }
spec:
  podSelector: { matchLabels: { app: api } }
  policyTypes: [Ingress, Egress]
  ingress:
    - from: [{ ipBlock: { cidr: 10.20.0.0/18 } }]              # ALB nodes in public subnets (target-type ip)
      ports: [{ port: 8000 }]
  egress:
    - to: [{ ipBlock: { cidr: 10.20.128.0/22 } }]              # data subnets (RDS, ElastiCache)
      ports: [{ port: 5432 }, { port: 6379 }]
    - to: [{ ipBlock: { cidr: 0.0.0.0/0, except: [10.0.0.0/8, 169.254.169.254/32] } }]   # Internet, never metadata
      ports: [{ port: 443 }]
```

Start with default deny plus DNS in a new namespace, add allows per service, and test with a debug pod. Cilium adds L7 and DNS-name-based policies and visibility (Hubble) if you need them.

## Secrets

Chapter 10: external store as source of truth; etcd encryption with KMS; RBAC denying `get secrets` to developers in production; `automountServiceAccountToken: false`; no secrets in Git or Helm values; scan manifests for leaked secrets.

## Supply chain

Only images from your registry (policy above); signatures verified at admission (Kyverno `verifyImages` with cosign; or Sigstore policy-controller); scanned in CI and continuously (chapter 7); SBOMs attached; base images pinned. Platform charts pinned and reviewed (chapter 12).

## Node and control plane

Nodes: private subnets, no SSH (SSM if needed), minimal AMIs (EKS-optimised, Bottlerocket), regular rotation via managed node group updates or Karpenter drift, IMDSv2 required with hop limit 1, encrypted root volumes, security groups allowing only cluster traffic. Control plane: audit logging enabled and shipped; API endpoint private or CIDR-restricted; cluster version within support; add-ons current.

## Runtime detection and audit

Enable **Kubernetes audit logs** (EKS control plane logging: `audit`, `authenticator`) and alert on: `exec`/`attach` into production pods, Secret reads by humans, RBAC changes, creation of privileged pods, access denied spikes. **Falco** or **GuardDuty EKS Runtime Monitoring** detects shells in containers, unexpected outbound connections, writes to sensitive paths, and privilege escalation attempts.

## The audit checklist

```checklist
# Kubernetes cluster security review
- API endpoint private or CIDR-restricted; control plane audit logs on and shipped.
- Humans authenticate via SSO; RBAC by group; no cluster-admin for daily use; no wildcard verbs in application roles.
- Secrets encrypted in etcd with KMS; developers cannot read production Secrets; external store is the source of truth.
- Each workload has its own ServiceAccount and IAM role (IRSA/Pod Identity); node role grants nothing to workloads; pod access to IMDS blocked.
- Application namespaces enforce Pod Security 'restricted'; platform namespaces separated.
- Admission policy: approved registries only, no :latest, resource requests/limits required, signatures verified.
- Default-deny NetworkPolicies with explicit allows; egress to metadata endpoint blocked.
- Images scanned in CI and continuously; critical findings block; base images pinned by digest.
- Nodes private, no SSH, IMDSv2 hop limit 1, encrypted disks, rotated on a schedule; cluster version in support; add-ons current.
- Runtime detection (Falco/GuardDuty) and alerts on exec, Secret reads, RBAC changes.
- automountServiceAccountToken false where the API is not used.
- PDBs and topology spread for availability (not security, but reviewed together).
```

## Common mistakes

- Workload AWS permissions on the node role.
- Pod Security not enforced; most pods root with all capabilities.
- Flat network; no NetworkPolicy; metadata endpoint reachable from pods.
- `cluster-admin` bound to a group everyone is in.
- Secrets readable by developers; secrets in Helm values in Git.
- Public API endpoint with `0.0.0.0/0`.
- Audit logs off; no idea who ran `kubectl exec` in prod.
- Clusters left on unsupported versions because upgrades are scary.

## Exercises

1. On a local cluster, label a namespace `restricted` and try to deploy a root container; fix the spec until it is admitted.
2. Apply default-deny network policies and allow only what your app needs; verify with a debug pod that the database port is unreachable from an unrelated pod.
3. Run a cluster audit tool (kube-bench for CIS, Polaris or Kubescape for workloads) and triage the findings against the checklist.
