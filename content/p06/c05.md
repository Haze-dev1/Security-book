## The problem

Two things confuse everyone who starts running containers: the container has its own network, so "localhost" means something different inside and outside; and the container's filesystem is disposable, so data written inside vanishes when it is replaced. Both are consequences of the isolation from chapter 1, and both have standard solutions once the model is clear.

## Networking

### Bridge networks

By default Docker creates a virtual bridge (`docker0`, 172.17.0.0/16) and gives each container a network namespace with a virtual Ethernet pair: one end in the container (`eth0`, an IP on the bridge), one end on the host attached to the bridge. Containers on the same bridge talk directly by IP; the host NATs outbound traffic to its own IP (masquerade); inbound traffic reaches a container only through **published ports** (DNAT rules from a host port to the container's port).

```bash
docker network ls; docker network inspect bridge          # default bridge: no DNS between containers by name
docker network create appnet                               # user-defined bridge: containers resolve each other by name
docker run -d --name db --network appnet postgres:16
docker run -it --rm --network appnet postgres:16 psql -h db -U postgres     # 'db' resolves via Docker's embedded DNS (127.0.0.11)
docker run -d --name api --network appnet -p 127.0.0.1:8000:8000 app:2.4.0   # publish to the host's loopback only
```

Rules of thumb: always use a user-defined network (name resolution, isolation from unrelated containers); publish ports only for what the host or the outside must reach, and bind them to `127.0.0.1` unless the service is meant to be public; remember that publishing bypasses host firewalls like ufw (Part V chapter 7); inside a container, `localhost` is the container itself, and reaching the host requires `host.docker.internal` (Docker Desktop) or the bridge gateway IP (Linux, or `--add-host=host.docker.internal:host-gateway`).

### Other modes

- **host**: the container shares the host's network namespace; no isolation, no port mapping, best performance. Used for monitoring agents and some network tools. Not available on Docker Desktop in the same way.
- **none**: no network at all; for build steps and sandboxed processing.
- **macvlan/ipvlan**: containers get addresses on the physical network; rare in cloud.
- **overlay**: multi-host networks (Swarm); superseded in practice by orchestrator networking.

### In ECS and Kubernetes

ECS **awsvpc** mode gives every task its own elastic network interface and VPC IP; containers in a task share that namespace (talk via `localhost`); security groups attach per task; no port mapping, the task IP:port is the endpoint; the ALB targets task IPs. ECS **bridge** mode (EC2 only) is the Docker model with dynamic host ports. Service discovery via Cloud Map DNS or ECS Service Connect.

Kubernetes gives each **pod** an IP (containers in a pod share it and talk via `localhost`), every pod can reach every pod without NAT (the CNI plugin's job: VPC CNI on EKS assigns real VPC IPs), **Services** provide stable virtual IPs and DNS names (`orders.default.svc.cluster.local`) load-balancing to pods, and **NetworkPolicies** restrict traffic (chapter 13). ## Volumes and persistence

The container's writable layer is deleted with the container. Anything that must outlive it goes elsewhere:

```bash
docker volume create pgdata
docker run -d --name db -v pgdata:/var/lib/postgresql/data postgres:16      # named volume
docker run -d -v $(pwd)/config:/etc/app:ro app                               # bind mount, read-only
docker run -d --mount type=tmpfs,destination=/run/secrets,tmpfs-size=1m app  # tmpfs
docker volume inspect pgdata                                                 # host path under /var/lib/docker/volumes
docker run --rm -v pgdata:/data -v $(pwd):/backup alpine tar czf /backup/pgdata-$(date +%F).tgz -C /data .   # backup a volume
```

Design rule for production: **application containers are stateless**; databases, caches and object storage are managed services or dedicated stateful deployments with their own persistence and backup story (Part VIII, Part V chapter 11). Volumes on container hosts are for development and for single-host deployments where you accept the operational burden.

### Ownership and permissions

Files on a volume carry UIDs from whoever wrote them. A container running as UID 10001 cannot write to a bind-mounted host directory owned by UID 1000 (`Permission denied`), and files it creates appear as an unknown UID on the host. Options: run the container with the host user's UID (`--user $(id -u):$(id -g)` in development), `chown` the mount point at image build time or in an entrypoint, Kubernetes `fsGroup` (which makes the volume group-writable by the pod's group), or named volumes initialised from the image (Docker copies the image's directory contents and ownership into an empty named volume on first use, which bind mounts do not do).

### Performance

Overlay writable layers are slow for databases; volumes bypass the overlay. On macOS and Windows, bind mounts cross a VM boundary and are slow for large trees (`node_modules`); use named volumes for dependencies and Compose Watch for code. EBS-backed volumes via CSI drivers in Kubernetes behave like EBS (chapter 10).

## Debugging connectivity in containers

```bash
docker exec -it api sh -c 'ss -ltnp'                        # what is the app bound to? 127.0.0.1 = unreachable from outside
docker inspect -f '{{range .NetworkSettings.Networks}}{{.IPAddress}} {{end}}' api
docker exec -it api getent hosts db                         # does the name resolve?
docker exec -it api sh -c 'timeout 3 sh -c "exec 3<>/dev/tcp/db/5432" && echo open'   # port reachable?
docker run --rm -it --network container:api nicolaka/netshoot    # full toolkit in the app's network namespace
docker port api                                             # published ports
sudo iptables -t nat -L DOCKER -n                           # the DNAT rules behind publishing
```

Checklist: bind address inside (0.0.0.0), same network as the peer, name resolution, port published if host access is needed, host firewall/security group for external access.

## Debugging data problems

"My data disappeared": the container was recreated (new writable layer) without a volume; the volume name changed (Compose project name); `down -v`; a bind mount path was wrong so writes went to the layer. "Permission denied": UID mismatch. "Database refuses to start": the data directory is not empty or has wrong ownership (PostgreSQL requires the directory owned by its user with mode 700).

## Common mistakes

- Using the default bridge and trying to resolve containers by name.
- Publishing database ports on `0.0.0.0` on a shared network.
- Stateful data in the writable layer; lost on deploy.
- Bind-mounting host paths in production, tying images to hosts.
- Ignoring UID mismatches and "fixing" with `chmod 777`.
- Expecting Docker named volumes to be backed up by anything other than your own job.
- `localhost` confusion between host, container and pod.
