- Know what a managed Kubernetes service (EKS) runs for you and what remains yours.
:::

## The problem

One host runs containers fine with Docker. Ten hosts raise questions Docker cannot answer: which host runs which container, what happens when a host dies, how traffic finds containers that move, how to roll out a new version without downtime, how to scale from 3 to 30 replicas and back, how to inject configuration and secrets uniformly, and how to isolate teams and workloads. An **orchestrator** answers them by taking a declaration of what you want running and continuously making it so across a cluster of machines.

ECS, Nomad and Kubernetes are orchestrators. Kubernetes won the general-purpose space; ECS remains the simpler, AWS-native choice (Part VII chapter 8). This chapter explains Kubernetes because its model (desired state, controllers, reconciliation) is the vocabulary of modern infrastructure, even if a given client never runs it.

## The declarative model

You do not tell Kubernetes "start three containers"; you submit an object saying "there should be three replicas of this pod spec". Controllers watch the API, compare desired state with actual state, and take actions to converge: start a pod, kill a pod, update a load balancer. If a node dies, the controller notices fewer replicas than desired and schedules replacements elsewhere. If you change the image tag, the deployment controller performs a rolling update. The same mechanism handles crashes, scaling, upgrades and drift. Infrastructure as code (Part X) applies the identical idea to cloud resources.

Every piece of Kubernetes (and most of its ecosystem: operators, cert-manager, external-dns, autoscalers) is a controller following this pattern. When you debug Kubernetes, you are asking "which controller is not converging, and what does it say in its events?"

## Objects you will use

Namespaces (logical partitions for RBAC, quotas, naming); Pods (chapter 9); Deployments and ReplicaSets (stateless apps); StatefulSets (stable identities and storage for databases and brokers you run yourself); DaemonSets (one pod per node: log shippers, agents); Jobs and CronJobs (batch and scheduled work); Services and Ingress/Gateway (traffic, chapters 9–10); ConfigMaps and Secrets (chapter 10); PersistentVolumeClaims (storage, chapter 10); ServiceAccounts, Roles and RoleBindings (identity and RBAC, chapter 13); HorizontalPodAutoscaler and PodDisruptionBudget (chapter 11); NetworkPolicy (chapter 13); Custom Resource Definitions (extensions: certificates, databases, anything an operator manages).

## Managed Kubernetes: EKS

With EKS, AWS runs the control plane (API server, etcd, scheduler, controller manager) across AZs, patches it, backs up etcd, and exposes an endpoint; you pay an hourly fee per cluster (around $0.10/hour, roughly $73/month, before any nodes) and manage the rest: **nodes** (managed node groups of EC2 instances, Fargate profiles for serverless pods, or Karpenter for just-in-time provisioning), the **add-ons** (VPC CNI, CoreDNS, kube-proxy, EBS CSI driver: versioned, upgraded by you), **cluster version upgrades** (Kubernetes releases three times a year; EKS supports each for about 14 months with extended support at extra cost; upgrades are your recurring chore), **IAM integration** (IAM principals mapped to Kubernetes RBAC via access entries; pods get AWS permissions via IAM Roles for Service Accounts or Pod Identity), **networking** (VPC IPs per pod, which eats subnet space; plan /20s or prefix delegation), **observability** (Container Insights, Prometheus), and **everything you deploy into it** (ingress controller, cert-manager, external-dns, autoscalers, policy engines, logging agents). The control plane is the easy part; the platform you build on it is the work.

## What Kubernetes is for

A platform for teams to deploy many services consistently with self-healing, scaling, rollouts, service discovery, configuration and policy, on any cloud or on-premises, with a vast ecosystem. The cost is operational: a platform team's worth of components to install, upgrade and secure, a steep learning curve, and quarterly version upgrades. Chapter 14 weighs when it is worth it; for many client projects it is not, and ECS Fargate or a PaaS delivers the same application outcomes with a fraction of the surface.

## Common misconceptions

- "Kubernetes makes apps reliable." It restarts and reschedules; your app still needs health checks, graceful shutdown, statelessness and sane limits.
- "EKS is fully managed." The control plane is; nodes, add-ons, upgrades and the platform layer are yours.
- "A pod is a container." A pod is one or more containers sharing a network namespace and storage; it is the scheduling unit.
- "kubectl apply is a deploy." It records desired state; the rollout is what controllers then do, and you must watch it (`kubectl rollout status`).

## Exercises

1. Create a local cluster (kind or k3d). Apply a Deployment with 3 replicas; delete a pod and watch the ReplicaSet replace it; `kubectl get events --watch` to see the controllers talk.
2. Scale the Deployment to 10 on a cluster that cannot fit them; read the Pending pods' events to see the scheduler's reasoning.
3. List everything you would need to install on a bare EKS cluster to run a production web service (ingress, certificates, DNS, logging, metrics, autoscaling, policy); estimate the time to set up and the monthly cost.
