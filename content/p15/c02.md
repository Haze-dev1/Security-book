# Security Review Checklist

:::objectives
- Review an application and its deployment for security systematically, covering design, code, dependencies, infrastructure, identity, data and operations.
- Produce findings with evidence, severity and remediation, suitable for a client security team or an internal review.
:::

:::prereq
Part IV (all); [Secure Development Lifecycle and Compliance Awareness](#/p12/c07); [Identifying Infrastructure Risks and Assessing Security Posture](#/p13/c04).
:::

## How to use this checklist

Use it for design reviews (sections 1–2), pre-release reviews (all), and periodic reviews (all, with emphasis on 5–8). For each item, record evidence or a finding (severity, exposure, impact, remediation, owner, date). Items reference the handbook chapters that explain the control. Pair with automated scanning (Part X chapter 3); the checklist covers what scanners cannot.

```checklist
# Security Review Checklist
## 1. Threat model and design
- Data flow diagram with trust boundaries exists and matches the implementation
- STRIDE (or equivalent) applied to each boundary crossing; threats, mitigations and accepted risks recorded
- Abuse cases written for the main features and converted into tests
- Data classified; the most sensitive data has the smallest footprint (minimisation, pseudonymisation)
- Security requirements from the client and regulations listed and traced to controls
## 2. Authentication
- Identity delegated to the agreed IdP (OIDC/SAML); no bespoke password store unless justified (and then Argon2id, breached-password checks, rate limits)
- MFA enforced for staff and administrators; phishing-resistant for privileged roles
- Session cookies: Secure, HttpOnly, SameSite; server-side sessions with rotation on login and privilege change; absolute and idle timeouts
- JWTs: algorithm allowlist, issuer and audience validated, short lifetimes, kid handling safe, no sensitive data in claims; revocation strategy for refresh tokens
- OAuth/OIDC flows: authorisation code with PKCE; state and nonce validated; redirect URIs exact-match; tokens never in URLs or logs
- Account recovery and MFA reset flows are slow, multi-channel and audited
- Service credentials: scoped, rotated, stored in a secret manager, never shared between environments
## 3. Authorisation
- Every endpoint enforces authorisation server-side; default deny
- Resource-level ownership checks on every object access (no IDOR); 404 rather than 403 for other tenants' objects where existence is sensitive
- Role and permission model documented; privilege escalation paths tested (user → admin, tenant A → tenant B)
- Multi-tenant: tenant context established once and enforced in data access; RLS or equivalent floor; cross-tenant test suite in CI
- Mass assignment prevented (explicit allowlists for writable fields)
- Admin and support interfaces separately protected, audited, with break-glass procedures
## 4. Input handling and output
- Validation of all inputs by type, length, range and format at the boundary; reject rather than sanitise where possible
- SQL and NoSQL queries parameterised; no string-built queries (lint rule in place)
- Command execution avoided; where unavoidable, no shell, argument arrays, allowlists
- Path handling: canonicalisation, allowlisted roots, no user-controlled paths
- SSRF: outbound URL allowlists, DNS resolution checks, metadata endpoint blocked, IMDSv2 enforced
- Deserialisation of untrusted data avoided or constrained to safe formats and schemas
- File uploads: content-type verified by content, size limits, malware scan, re-encoding of images, separate serving domain, no execution
- Output encoding by context; templating auto-escapes; CSP in place; no inline scripts without nonces
- CSRF protection for cookie-authenticated state changes (SameSite plus tokens)
- CORS: explicit origin allowlist; no wildcard with credentials
- Request size, depth and rate limits; JSON parser limits
## 5. Cryptography and secrets
- TLS 1.2+ everywhere including internal; certificates automated and monitored for expiry
- Standard libraries only; no custom crypto; AEAD ciphers for encryption at rest in the application
- Keys in KMS/HSM; key policies reviewed; rotation plan; separate keys per environment and, where required, per tenant
- Secrets never in code, config files, images, environment dumps, logs, tickets or chat; secret scanning on push and in history
- Password hashing with Argon2id or bcrypt with tuned parameters (if passwords exist)
- Randomness from CSPRNGs for tokens, IDs that must be unguessable, and nonces
## 6. Dependencies and build
- Lockfiles committed; installs reproducible; private registry proxy where available
- SCA on every PR; critical/high fixable blocked; exceptions with justification and expiry
- Container images: pinned bases by digest, minimal, non-root, read-only root, scanned on build and schedule, rebuilt regularly
- CI: pinned actions, minimal permissions, no secrets to fork PRs, OIDC to cloud, ephemeral runners
- Artefacts signed with provenance; verified at deploy time
- SBOM generated and retained per release
## 7. Infrastructure and platform
- Accounts: separate per environment; organisation guardrails; CloudTrail/Config/GuardDuty enabled and centralised
- IAM: least privilege per workload; no long-lived human keys; MFA; permission boundaries; access reviews
- Network: private subnets for non-edge; security groups minimal and group-referenced; no 0.0.0.0/0 on admin ports; VPC endpoints; egress controlled
- Data stores not publicly accessible; encrypted; deletion protection; backups isolated
- Compute hardened: no SSH where avoidable, SSM instead; IMDSv2; patched; containers with dropped capabilities and seccomp
- Kubernetes (if used): RBAC least privilege, network policies, pod security standards, no privileged pods, secrets encrypted at rest, admission policies
- Edge: WAF managed rules and rate rules; DDoS protection; origin locked to the CDN
- Infrastructure as code scanned; drift detection; state encrypted and access-controlled
## 8. Logging, monitoring and response
- Security-relevant events logged: authentication outcomes, authorisation failures, admin actions, data exports, configuration changes
- Logs free of secrets and PII; structured; shipped off-host; tamper-evident; retained per policy
- Detection: alerts for brute force, anomalous access, privilege changes, disabled logging, new principals, impossible travel where applicable
- Incident response runbook including credential compromise, data exposure and client notification obligations; rehearsed
- Vulnerability management SLAs defined and tracked; disclosure channel published
## 9. Data protection and privacy
- Personal data inventory; purpose and lawful basis documented; minimisation applied
- Retention schedule implemented in code; deletion and export flows tested across every store including backups' horizon
- Production data never in non-production environments; anonymisation pipeline if derived data is needed
- Third-party processors listed with agreements; data transfers compliant
- Breach notification obligations known and in the incident runbook
## 10. Verification
- Automated: SAST, SCA, secret scanning, IaC scanning, container scanning, DAST against staging, all green or with accepted exceptions
- Authorisation test matrix in CI (roles × endpoints × own/other resources)
- Penetration test with cross-tenant and business-logic objectives completed; findings remediated
- Security review sign-off recorded with reviewers, date and open items
```

## Writing findings

Use the structure from Part XIII chapter 4: title, severity, evidence (resource, code location, request/response), exposure, impact in business terms, remediation with effort, owner and date. Group by severity; lead with blockers; include what was reviewed and found adequate so the report shows coverage, not only problems.
