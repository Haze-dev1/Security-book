# Production Readiness Checklist

:::objectives
- Use a single, complete checklist to decide whether a system is ready for production, and to find the gaps before launch rather than after.
- Treat each item as a question requiring evidence, not a box to tick.
:::

:::prereq
[What Production-Ready Actually Means](#/p01/c15); [Production Readiness Reviews and Rollback Plans](#/p13/c11).
:::

## How to use this checklist

Work through it two to three weeks before go-live with independent reviewers (Part XIII chapter 11). For each item record one of: **evidence** (a link to the dashboard, test run, document or configuration), **gap** (owner and date), or **accepted risk** (signed by the risk owner). The checklist state is saved in your browser so you can return to it; export your notes into the project's readiness record.

Not every item applies to every system. Mark items not applicable with a reason; "we did not think about it" is not a reason.

```checklist
# Production Readiness Checklist
## 1. Requirements and ownership
- Functional requirements and acceptance criteria documented and tested
- Non-functional requirements quantified: availability target, latency targets, throughput, data retention, RPO/RTO
- SLOs defined with SLIs measured at the edge; dashboard shows current attainment
- Service ownership record exists: owning team, on-call, escalation, authority
- Support model and hours agreed with the client; contacts exchanged
- Risk register current; every accepted risk has a named signatory and review date
## 2. Architecture and design
- Architecture diagram with trust boundaries, Regions, accounts and integrations current
- Significant decisions recorded as ADRs
- Single points of failure identified; each either removed or accepted in writing
- Every dependency has a documented failure mode and degradation behaviour
- Capacity plan: expected peak, headroom, scaling mechanism, quotas raised
- Data model reviewed; indexes for known access patterns; growth and archival plan
## 3. Security
- Threat model completed and mitigations implemented
- Authentication via the agreed identity provider; MFA enforced for staff and admins
- Authorisation enforced server-side on every endpoint; resource ownership checks; cross-tenant tests in CI
- Input validation and output encoding; injection classes tested (SQL, command, SSRF, path, deserialisation)
- Secrets in a secret manager; none in code, configuration files, images, logs or tickets; rotation owners named
- Encryption in transit everywhere (TLS 1.2+, internal included); encryption at rest with managed keys and reviewed key policies
- Security headers and CSP verified; cookies with Secure, HttpOnly, SameSite
- Dependencies and container images scanned; no critical/high fixable findings; exceptions have expiry
- Pipeline hardened: pinned actions, least-privilege tokens, OIDC to cloud, signed artefacts verified at deploy
- Penetration test completed; high and critical findings closed or accepted in writing
- Audit logging of security-relevant events, tamper-evident, shipped to the SIEM, retained per policy
- WAF and rate limiting on public endpoints; bot and abuse controls where relevant
- Least-privilege IAM for every workload identity; no wildcard policies; access reviews scheduled
- Network: private subnets for non-edge components; security groups reference groups not CIDRs; no public databases or caches
- Data classification done; personal data minimised; retention and deletion implemented and tested; DPA and processor agreements in place
## 4. Reliability
- Multi-AZ for every stateful component; stateless services across at least two AZs
- Health checks: liveness checks the process only; readiness checks dependencies with bounded timeouts; graceful shutdown implemented
- Timeouts on every outbound call; retries only for idempotent operations with backoff and jitter; circuit breakers on fragile dependencies
- Load test at expected peak plus headroom passed with SLOs met; breaking point known
- Autoscaling configured with tested bounds and cooldowns
- Idempotency for all externally triggered writes; duplicate delivery tested
- Database migrations expand/contract; lock timeouts; rehearsed on production-sized data
- Disaster scenarios documented with RTO/RPO; Region failure plan if required
## 5. Observability
- Structured logs with request and trace IDs; no PII or secrets (sampled and verified); retention set
- RED metrics per route with bounded cardinality; USE metrics for resources
- Distributed tracing across services and queues with sampling that keeps errors
- Dashboards: service overview, golden signals, dependencies, SLO and error budget
- Alerts for SLO burn rates and critical symptoms; each links to a runbook; routed to a staffed destination; tested by firing
- Alert for silence (no traffic, no heartbeat, queue age) and for expiry (certificates, tokens, licences)
- Synthetic probes of critical journeys from outside
## 6. Operability
- Deployment fully automated via pipeline; build once, promote by digest; no manual production steps
- Rollback tested within the last month; previous artefact identifiable from deployment records
- Progressive delivery (canary or blue-green) with automatic rollback on SLO regression for production
- Feature flags for risky behaviour with safe defaults and owners
- Configuration validated at startup; schema documented; environment differences explained
- Runbooks for deploy, rollback, scale, rotate secrets, restore, and each alert; followed literally in a rehearsal
- On-call rotation staffed with escalation and response targets; handoff process defined
- Incident process agreed with the client: severity definitions, communication cadence, status page
- Cost: budget alarms, tags on every resource, monthly cost review owner
- Patching and dependency update cadence defined with an owner; platform end-of-life dates tracked
## 7. Recoverability
- Backups automated for every data store; isolated in a separate account with immutability; encrypted
- Restore performed and timed within the last 30 days; content verified
- RTO and RPO demonstrated for the agreed scenarios
- Rebuild from IaC tested in a clean account
- Secrets, keys, configuration and IaC backed up outside the primary account
## 8. Compliance and documentation
- Compliance obligations identified; required controls mapped to evidence sources
- Change management process agreed and evidence capture working (deployment records retained immutably)
- Environment documentation per environment with last-verified dates
- Architecture, operations, configuration, API and onboarding documentation complete and current
- Data map: what data is where, classification, retention, processors
- Handover or operational acceptance plan agreed, with the receiving team identified
## 9. Launch
- Launch plan with steps, owners, times, abort criteria and rollback
- Communication plan: internal, client stakeholders, customers, status page drafts
- Hypercare period defined with heightened on-call and daily check-ins
- Go/no-go decision recorded with evidence and sign-offs
```

## Severity guide for gaps

Treat as **no-go** until fixed: no backups restored; no monitoring or alerting to a staffed destination; critical or high security findings open without accepted risk; secrets in code or configuration; no rollback path; single-AZ stateful components for a system with an availability requirement; no owner. Treat as **conditions** with dates: documentation gaps, missing synthetic probes, cost review cadence, non-critical runbooks. Everything else is judgement, recorded.
