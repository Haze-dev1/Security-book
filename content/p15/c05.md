# Architecture Decision Record Examples

:::objectives
- Provide an ADR template and six complete examples covering the decisions most client projects face: hosting platform, tenancy, authentication, database, messaging and observability.
- Show the level of context and consequence detail that makes an ADR useful years later.
:::

:::prereq
[Design Documents, Architecture Reviews and ADRs](#/p12/c03).
:::

## Template

```markdown
# ADR NNNN: <decision in one line>

Date: YYYY-MM-DD · Status: Proposed | Accepted | Deprecated | Superseded by ADR-XXXX · Deciders: <roles> · Consulted: <roles>

## Context
What situation, constraints and forces make this decision necessary now. Numbers where possible.

## Options considered
1. <option> — summary; why it loses or wins on the forces above.
2. ...

## Decision
What we will do, precisely, including the boundaries of the decision.

## Consequences
Positive, negative and neutral outcomes; follow-up work; what becomes easier and harder.

## Review
Conditions or date under which this decision should be revisited.
```

## ADR 0001: Host the client portal on ECS Fargate in the client's AWS account

```markdown
Date: 2026-02-10 · Status: Accepted · Deciders: FDE lead, client IT manager · Consulted: client finance, our platform team

## Context
The client (120 staff, one IT generalist, no engineers) needs a client portal handling confidential documents with 99.5% business-hours availability and a 300–500 USD/month infrastructure budget. They require data and infrastructure in an AWS account they own. There is no platform team to operate Kubernetes. Load is small (≤ 50 concurrent users).

## Options considered
1. Single EC2 instance with Docker Compose — ~40 USD/month; single point of failure; someone must patch the host; rejected because the client cannot operate it and confidentiality raises the cost of an unpatched host.
2. App Runner — simple and cheap; rejected because the client's security policy requires private subnets and a WAF in front, which App Runner only partly supports at the time of decision.
3. ECS Fargate (2 tasks, 2 AZs) + ALB + RDS Multi-AZ — ~200–250 USD/month; no hosts to patch; rolling deploys; fits the policy.
4. EKS — rejected: control-plane cost exceeds total compute; operational skills absent; no requirement needs it.

## Decision
Option 3. One container image for web and API; scheduled jobs as ECS scheduled tasks from the same image; Terraform in the client's repository; CI via GitHub Actions with OIDC roles; CloudFront + WAF in front of the ALB.

## Consequences
+ No server patching; Multi-AZ resilience; deploys and rollbacks automated.
+ Fits budget with ~50% headroom.
− Fargate premium over EC2 (~2×) accepted for operational simplicity.
− Client's IT generalist needs training on the runbooks and the ECS console (handover plan).
− NAT Gateway is the largest fixed cost; VPC endpoints added to reduce processing charges.

## Review
Revisit if monthly cost exceeds 400 USD, if the client hires engineers, or if more than three services emerge.
```

## ADR 0002: Hybrid tenancy — shared PostgreSQL with RLS for self-serve tiers, database per tenant for enterprise

```markdown
Date: 2026-03-02 · Status: Accepted · Deciders: platform lead, security lead, product · Consulted: enterprise sales, SRE

## Context
2,000 tenants from 5 to 20,000 seats; enterprise prospects require dedicated data stores and per-tenant keys; self-serve tiers must onboard in seconds and cost cents. Cross-tenant data exposure is the top risk in the threat model. Migration tooling must remain manageable.

## Options considered
1. Shared schema + application filtering — cheapest; one query bug is a breach; rejected as sole control.
2. Schema per tenant — thousands of schemas slow migrations and tooling; rejected.
3. Database per tenant for all — onboarding takes minutes and minimum DB cost per tenant breaks the free tier economics; rejected for self-serve.
4. Hybrid: shared pool with tenant_id + RLS for self-serve; dedicated databases for enterprise; identical application code with connection routing from the registry.

## Decision
Option 4. RLS policies on all tenant tables; app role without BYPASSRLS; repository layer sets tenant context per transaction; registry holds pool/database routing per tenant; migration runner handles the shared pool plus the fleet of dedicated databases in waves; live migration tooling from shared to dedicated.

## Consequences
+ Cents-per-tenant economics for self-serve; strong isolation and per-tenant keys for enterprise; one codebase.
+ RLS floor means a missed filter returns nothing rather than another tenant's data.
− Migration orchestration across N+1 databases; connection management via RDS Proxy.
− A forgotten tenant context yields empty results (fail closed), confusing in development; mitigated by repository design and tests.
− Large self-serve tenants may need moving to dedicated; tooling required (built in Q2).

## Review
Revisit at 10,000 tenants or if a dedicated-only model becomes contractually universal.
```

## ADR 0003: Delegate authentication to a managed identity provider; no bespoke password store

```markdown
Date: 2026-01-20 · Status: Accepted · Deciders: security lead, product, FDE lead

## Context
The platform needs customer sign-in (email + MFA, passkeys), social login, and enterprise SSO (OIDC/SAML per tenant) with SCIM. Authentication is the highest-consequence security surface; our team is small. Compliance requires MFA and audit of authentication events.

## Options considered
1. Build on a web framework's auth library — fastest to start; we then own password storage, MFA, recovery, federation, and their hardening forever; rejected.
2. Self-hosted Keycloak — full-featured and free; we operate and patch a critical system; acceptable where residency forbids SaaS.
3. Managed IdP (Cognito / Auth0 / Entra External ID) — protocols, MFA, federation, hardening and uptime provided; per-MAU cost; some flows constrained.

## Decision
Option 3 (Cognito in the client's AWS Region for residency), with Keycloak as the fallback where a client forbids managed SaaS identity. Applications are OIDC relying parties; APIs validate access tokens locally via cached JWKS; sessions server-side in first-party web apps; per-tenant IdP federation configured through the control plane.

## Consequences
+ We own integration and tenancy mapping, not cryptography and recovery flows.
+ MFA, passkeys and SAML federation available immediately.
− Vendor constraints on customising flows; per-MAU cost at scale (modelled: acceptable to 500k MAU).
− Token lifetimes and revocation designed around the vendor's capabilities (10-minute access tokens, refresh rotation).
− Two supported IdPs (Cognito, Keycloak) double integration testing.

## Review
Revisit if MAU cost exceeds the modelled threshold or if a required flow is unsupported.
```

## ADR 0004: PostgreSQL as the system of record; DynamoDB only for specific high-write, simple-access tables

```markdown
Date: 2026-01-28 · Status: Accepted · Deciders: tech lead, data lead

## Context
The domain is relational (organisations, users, documents, invoices, approvals) with transactional requirements (money, inventory-style reservations) and ad hoc reporting. Two tables (sessions, usage events) have very high write rates with key-based access only. The team knows PostgreSQL well.

## Options considered
1. PostgreSQL for everything — simple; the high-write tables add load and bloat to the primary.
2. DynamoDB for everything — forces access-pattern-first design on a relational domain; weak for reporting and transactions across entities; rejected.
3. PostgreSQL as the system of record; DynamoDB for sessions and usage events; derived read models and search in OpenSearch fed by change events.

## Decision
Option 3. RDS/Aurora PostgreSQL Multi-AZ; schema ownership per service module within one cluster (no database-per-service yet); DynamoDB with TTL for sessions and usage events; OpenSearch for search; no cross-store transactions (outbox pattern for events).

## Consequences
+ Transactions and reporting where the domain needs them; cheap, scalable storage for the two hot tables.
− Two data stores to operate and back up; consistency between them is eventual by design.
− Reporting queries routed to a read replica; a warehouse later if analytics grows.

## Review
Revisit when write volume to PostgreSQL approaches instance limits or when service boundaries require separate databases.
```

## ADR 0005: SQS with an outbox for asynchronous work; Kafka deferred

```markdown
Date: 2026-02-15 · Status: Accepted · Deciders: tech lead, SRE

## Context
Order placement, notifications, file processing and integrations need asynchronous, reliable processing with retries and dead-lettering. Peak is a few hundred messages per second; no requirement for replay of history or multiple independent consumers of the same ordered stream today. Operations capacity is limited.

## Options considered
1. Database table as a queue — simple; polling load and locking at scale; acceptable for very low volume only.
2. SQS (standard and FIFO where ordering matters) + SNS fan-out + outbox from PostgreSQL — managed, cheap, DLQs, visibility timeouts; no replay.
3. Kafka (MSK) — replay, ordered partitions, many consumers; operational weight and cost; over-provisioned for current needs.

## Decision
Option 2. Transactional outbox in PostgreSQL publishes events; a relay process publishes to SNS; SQS queues per consumer with DLQs and redrive; FIFO queues for per-entity ordering where required; idempotent consumers keyed by event ID.

## Consequences
+ Low operational burden; exactly-once effects via idempotency; isolation between consumers.
− No replay of historical events (archive events to S3 from the relay for future backfills).
− FIFO throughput limits per message group; monitored.

## Review
Revisit if replay, stream processing or more than ~5,000 messages/s sustained becomes a requirement.
```

## ADR 0006: OpenTelemetry instrumentation with Prometheus/Grafana and CloudWatch; vendor backend optional

```markdown
Date: 2026-02-20 · Status: Accepted · Deciders: SRE lead, tech lead · Consulted: finance

## Context
We deploy into many client accounts with different observability expectations; some mandate CloudWatch, some have Datadog, some have nothing. Telemetry cost is a significant line. We need one instrumentation approach.

## Options considered
1. Vendor SDK (Datadog) everywhere — fast; lock-in; unacceptable in clients that forbid the vendor.
2. CloudWatch only — native but weak for application metrics and traces; costly custom metrics.
3. OpenTelemetry in applications; Collector per deployment routes to the client's backend (Prometheus/Grafana + Loki + Tempo by default; CloudWatch/X-Ray or a vendor when mandated).

## Decision
Option 3. OTel SDKs and auto-instrumentation; Collector as agent and gateway with redaction and tail sampling; default backend Amazon Managed Prometheus + Managed Grafana + CloudWatch Logs for AWS deployments; dashboards and alert rules as code, parameterised per client.

## Consequences
+ One instrumentation investment; backends swappable per client; redaction centralised.
− Collector fleet to operate per deployment; sampling and cardinality discipline required.
− Managed Grafana per-user pricing; shared dashboards per client to contain cost.

## Review
Revisit annually against telemetry cost and client requirements.
```

## Writing your own

Record a decision when a new engineer would ask "why?", when it is costly to reverse, or when it was contested. Keep the context honest, including the constraints that made a weaker option win; list real alternatives; name consequences you dislike. Supersede rather than edit. Store under `docs/adr/` and link from the architecture document.
