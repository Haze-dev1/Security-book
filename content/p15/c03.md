# Deployment Runbook Template

:::objectives
- Provide a runbook template for production deployments that anyone authorised can follow literally, with verification and rollback built in.
- Adapt it per system and keep it accurate by using it every time.
:::

:::prereq
[Production Change Management](#/p12/c08); [Complete Sample Pipeline Walkthrough](#/p10/c10); [Environment Configuration and Deployment Documentation](#/p13/c10).
:::

## How to use this template

Copy it into `docs/runbooks/deploy-<service>.md`, replace every bracketed placeholder, delete sections that do not apply, and keep it next to the pipeline code. Every deployment follows it literally; any deviation is a documentation fix in the same pull request. Where the pipeline automates a step, the runbook names the pipeline action and what to check, not the underlying commands.

```markdown
# Deployment runbook: [service name] — [environment]

**Owner**: [team] · **Last verified**: [date] by [name] · **Pipeline**: [link] · **Dashboard**: [link] · **Rollback**: see section 7

## 1. Scope and classification
- What this runbook covers: deploying a new version of [service] to [environment] via [pipeline/CodeDeploy/Argo].
- Change class: Standard (automated, no per-change approval) / Normal (approval required in the [environment] gate).
- Not covered: infrastructure changes (see infra runbook), database contract migrations (see migration runbook), configuration-only changes (see config runbook).

## 2. Pre-conditions (all must be true)
- [ ] CI green on main for the commit; image digest known: `sha256:[...]`
- [ ] Image signature and provenance verified (pipeline job `verify` green)
- [ ] Release notes written; ticket(s) linked
- [ ] No active incident on [service] or its dependencies (check #incidents and status page)
- [ ] Inside the deployment window: [e.g. Mon–Thu 09:00–16:00 local]; not in a change freeze (calendar link)
- [ ] On-call engineer aware and available for the hypercare window
- [ ] Any required migration is expand-only and has been rehearsed in staging (migration record link)
- [ ] Previous deployment record identified (for rollback): [link], digest `sha256:[...]`

## 3. Communication
- Before: post in #[releases] — "Deploying [service] [version] to [environment] at [time]; expected impact: none; rollback: redeploy [previous]."
- During: progress at each milestone below.
- After: completion message with the deployment record link.
- If a problem occurs: declare per the incident process; status page if customer-visible.

## 4. Steps
| # | Action | Who | Expected result | Check |
|---|---|---|---|---|
| 1 | Trigger pipeline `deploy.yml` for [environment] with digest | Deployer | Run starts; `migrate` job begins | Pipeline UI |
| 2 | Migration job completes | Pipeline | Exit 0; migration log shows applied versions | Job log; `SELECT * FROM schema_migrations ORDER BY applied_at DESC LIMIT 3` via the read-only runner |
| 3 | Approve the [environment] gate (Normal changes) | Approver (not the deployer) | Approval recorded | Environment history |
| 4 | Deployment starts: new task definition / replica set created | Pipeline | New tasks become healthy within [N] minutes | ECS/Kubernetes events; target group health |
| 5 | Traffic shift begins ([10%] canary for [5] minutes) | CodeDeploy / Rollouts | Error ratio and p95 for canary within thresholds | Dashboard panel "canary vs stable" |
| 6 | Traffic shift completes (100%) | CodeDeploy / Rollouts | All traffic on new version; old tasks draining | Dashboard version panel shows single version |
| 7 | Smoke tests run | Pipeline | `smoke.sh` passes | Job log |
| 8 | Deployment record written | Pipeline | Record in [bucket/table] with digest, approvers, outcome | Link in job output |

Milestone posts: after step 2 ("migration done"), after step 6 ("100% traffic"), after step 8 ("deployment complete").

## 5. Verification (within 15 minutes of completion)
- [ ] `/health` and `/ready` return 200 through the public endpoint
- [ ] Version endpoint or header shows the new version: `curl -sI https://[host]/health | grep x-version`
- [ ] Error ratio ≤ [0.5%] and p95 ≤ [SLO] on the dashboard for 10 minutes
- [ ] No new error signatures in logs: Logs Insights query [link]
- [ ] Synthetic probes green from all locations
- [ ] Background workers consuming: queue age < [60 s]
- [ ] (If applicable) feature-specific check: [describe]

## 6. Hypercare
- Duration: [2 hours] after completion; on-call watches the dashboard; deployer remains reachable.
- Abort criteria during hypercare (roll back if any): error ratio > [1%] for 3 minutes; p95 > [2× SLO] for 5 minutes; any customer-impacting defect confirmed; any data integrity alert.

## 7. Rollback
- Decision: on-call or deployer may roll back without approval during hypercare; later, as a Normal change.
- Automatic: CodeDeploy/Rollouts rolls back on alarm [names] during traffic shift. Confirm in the deployment events; the record will show `rolled_back`.
- Manual: trigger `deploy.yml` with `workflow_dispatch`, environment [env], digest = previous digest from section 2. Expected duration: [5] minutes.
- Data: migrations in this release are expand-only; rolling back the application is safe. If a contract migration shipped (it should not in this path), see the migration runbook's recovery section before rolling back.
- Verify after rollback: repeat section 5.
- Communicate: #[releases] and incident channel; status page if it was used.

## 8. After the deployment
- [ ] Release notes published to [location]
- [ ] Ticket(s) moved to Done
- [ ] Any deviations from this runbook fixed in the runbook (PR link)
- [ ] If rolled back: incident declared or postmortem scheduled per policy

## 9. Known issues and gotchas
- [e.g. "First deploy after a secret rotation requires a forced new deployment; see rotation runbook."]
- [e.g. "Canary analysis needs at least 50 req/min; outside business hours use the extended 15-minute canary."]

## 10. Contacts
- Service owner: [team/channel]
- On-call: [schedule link]
- Platform team (pipeline/cluster issues): [channel]
- Client approver (if applicable): [name, contact, response expectation]
```

## Variants

- **Kubernetes with Argo Rollouts**: steps 4–6 become `kubectl argo rollouts get rollout [name] --watch`; promotion may be manual (`promote`) if the strategy pauses; rollback is `kubectl argo rollouts undo`.
- **Lambda**: deployment is publishing a version and shifting the alias with CodeDeploy; rollback shifts the alias back.
- **Static frontend**: deployment is an S3 sync plus CloudFront invalidation; rollback re-syncs the previous build artefact; verification checks the asset hash in `index.html`.
- **Client-approved deployments**: add the client's approval step and their communication channel; record their approver in the deployment record.
