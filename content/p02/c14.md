## The problem

HTTP's request-response model does not fit everything. A chat app needs the server to push messages the instant they arrive; a dashboard wants live metrics; a long-running job needs to report progress; services calling each other thousands of times a second want less overhead than JSON over HTTP/1.1. Several protocols extend or replace plain HTTP for these cases, and each one has infrastructure consequences: connection counts, proxy configuration, load balancer timeouts and stateful servers.

A useful rule: if the server only needs to push, use **SSE**; it is plain HTTP, works through everything, and reconnects itself. Use **WebSockets** only when the client must also send a high volume of messages with low latency. Use **gRPC** between services you control, not to browsers.

## Server-Sent Events

The client opens a normal GET; the server responds with `Content-Type: text/event-stream` and keeps the response open, writing events as text:

```http
HTTP/1.1 200 OK
Content-Type: text/event-stream
Cache-Control: no-cache
X-Accel-Buffering: no

event: job.progress
id: 42
data: {"job":"j_123","pct":40}

event: job.progress
id: 43
data: {"job":"j_123","pct":55}

: heartbeat
```

```python
# FastAPI SSE endpoint
from fastapi.responses import StreamingResponse
import asyncio, json

@app.get("/jobs/{job_id}/events")
async def job_events(job_id: str, request: Request):
    async def gen():
        last = int(request.headers.get("Last-Event-ID", 0))
        async for ev in subscribe(job_id, since=last):          # e.g. Redis stream / pubsub
            yield f"event: {ev.type}\nid: {ev.id}\ndata: {json.dumps(ev.data)}\n\n"
            if await request.is_disconnected(): break
    return StreamingResponse(gen(), media_type="text/event-stream",
                             headers={"Cache-Control": "no-cache", "X-Accel-Buffering": "no"})
```

```javascript
const es = new EventSource('/jobs/j_123/events');       // cookies are sent; custom headers are not
es.addEventListener('job.progress', (e) => update(JSON.parse(e.data)));
es.onerror = () => { /* browser reconnects automatically, sending Last-Event-ID */ };
```

Infrastructure: disable proxy buffering for the route (chapter 12), set read timeouts long or send a comment heartbeat (`: ping`) every 15–30 s to keep proxies, NATs and the ALB idle timeout (60 s default) from closing the stream. Browsers limit HTTP/1.1 connections per host to six, so SSE over HTTP/2 (which multiplexes) avoids starving the rest of the page.

## WebSockets

A WebSocket starts as an HTTP request with `Upgrade: websocket` and `Connection: Upgrade`; the server replies `101 Switching Protocols`, and from then on the TCP connection carries WebSocket frames in both directions until either side closes. Messages are framed (text or binary) with no HTTP semantics; you design the message protocol.

```javascript
// Server (Node, ws library) with heartbeat to detect dead clients
import { WebSocketServer } from 'ws';
const wss = new WebSocketServer({ server, path: '/ws' });
wss.on('connection', (ws, req) => {
  const user = authenticate(req);                // cookie or token in query/first message; reject early
  if (!user) return ws.close(4401, 'unauthorized');
  ws.isAlive = true;
  ws.on('pong', () => { ws.isAlive = true; });
  ws.on('message', (buf) => handle(user, JSON.parse(buf)));
});
setInterval(() => wss.clients.forEach((ws) => {   // every 30 s: terminate silent clients, ping the rest
  if (!ws.isAlive) return ws.terminate();
  ws.isAlive = false; ws.ping();
}), 30_000);
```

Infrastructure requirements: the proxy must forward the Upgrade headers (`proxy_set_header Upgrade $http_upgrade; Connection "upgrade"` in Nginx; ALB supports WebSockets natively on HTTP/HTTPS listeners); idle timeouts must exceed your ping interval; and each connection consumes a file descriptor and some memory on a specific server for its lifetime.

### Scaling WebSockets

Persistent connections make servers stateful: user A is connected to server 1; a message for A arriving at server 2 must be routed to server 1. The standard solution is a **pub/sub backplane**: every server subscribes to a channel (Redis Pub/Sub, Redis Streams, SNS/SQS, Kafka); a message for A is published; the server holding A's connection delivers it. Connection counts per server are bounded by memory and file descriptors (tens of thousands per modest instance), so capacity planning is "connections per instance × instances", and deployments must handle mass reconnection (clients reconnect with randomised backoff, or storms follow). Managed alternatives: API Gateway WebSocket APIs, AppSync, Pusher, Ably.

Authentication: browsers cannot set custom headers on WebSocket handshakes, so authenticate via the session cookie (SameSite rules apply), a short-lived token in the first message, or a one-time ticket in the URL (never a long-lived token in the URL; it lands in logs). Check `Origin` on the handshake to prevent cross-site WebSocket hijacking.

## gRPC

gRPC is an RPC framework: you define services and messages in Protocol Buffers, generate typed clients and servers for many languages, and calls travel as HTTP/2 streams with binary payloads. It supports unary calls and client-, server- and bidirectional streaming, deadlines propagated across hops, and rich status codes.

```protobuf
syntax = "proto3";
service Orders {
  rpc GetOrder (GetOrderRequest) returns (Order);
  rpc WatchOrder (GetOrderRequest) returns (stream OrderEvent);   // server streaming
}
message GetOrderRequest { string id = 1; }
message Order { string id = 1; string status = 2; repeated LineItem items = 3; }
```

Why teams use it internally: strict contracts with generated code, small fast messages, streaming, deadlines and cancellation built in. Why not to browsers: browsers cannot speak raw gRPC (no control over HTTP/2 framing); grpc-web requires a proxy (Envoy) and loses some streaming modes. Why not for public APIs: tooling and debuggability (`curl` cannot easily call it; use `grpcurl`), and partners expect REST/JSON.

Infrastructure: gRPC needs HTTP/2 **end to end**. An ALB supports gRPC target groups (protocol version gRPC) with gRPC-aware health checks and routing on service/method paths; Nginx proxies gRPC with `grpc_pass`; a plain L7 proxy that downgrades to HTTP/1.1 breaks it. Because one HTTP/2 connection carries many calls, L4 load balancing (NLB, Kubernetes Service) pins all of a client's calls to one backend; use an L7 balancer or client-side load balancing for even distribution. Always set deadlines on calls; a gRPC call without a deadline can wait forever.

## Design considerations common to all

- **Reconnection**: clients must reconnect with exponential backoff and jitter, and resume from a cursor (`Last-Event-ID`, a sequence number) so no events are lost or duplicated. Servers must tolerate reconnect storms after a deploy.
- **Backpressure**: a slow consumer must not make the server buffer unboundedly. Bound per-connection queues; drop or coalesce low-value updates (the latest metric value supersedes old ones); close abusive connections.
- **Idle and dead connections**: TCP will not tell you a client vanished. Use protocol-level pings and close on missed pongs.
- **Observability**: track active connections per instance, messages per second, send-queue depth, reconnect rate. These are your capacity and health signals.
- **Deploys**: a rolling deploy disconnects every client on the old instances. Drain gracefully (send a "reconnect" message, close with a code), and stagger instance replacement so reconnects spread out.
- **Authorization per message**, not just per connection: a connection opened by user A must not be able to subscribe to user B's channel because the server forgot to check on subscribe.

## Common mistakes

- WebSockets where SSE would do, inheriting bidirectional complexity for a one-way feed.
- Proxy buffering left on for SSE; streams arrive in 8 KB bursts or at the end.
- Load balancer idle timeout at 60 s with no heartbeat; connections drop silently every minute.
- Long-lived tokens in WebSocket URLs.
- Pub/sub backplane missing; works perfectly with one instance, breaks at two.
- gRPC behind an HTTP/1.1-only proxy, or L4-balanced so one backend takes all traffic.
- No deadlines on gRPC calls; no reconnect backoff on clients.
