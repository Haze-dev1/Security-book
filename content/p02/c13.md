## The problem: one server is not enough

A single server has three limits. **Capacity**: CPU, memory, connections and bandwidth are finite; past a point, latency climbs and requests fail. **Availability**: when it reboots for a kernel patch, crashes, or its Availability Zone has a bad day, the service is down. **Deployability**: replacing the running process means downtime unless something else is serving meanwhile.

You can buy a bigger server ([[vertical scaling]]): simple, no code changes, but it has a ceiling, gets expensive quickly, and still leaves one point of failure. Or you can run several identical servers ([[horizontal scaling]]) and put something in front that spreads traffic across them and avoids the broken ones. That something is a load balancer, and it quietly solves all three problems: capacity (add servers), availability (route around failures and AZ outages), and deployability (rolling updates behind a stable endpoint).

Horizontal scaling requires the servers to be [[stateless service|stateless]] (or share state through a database, cache or session store), which is why Part I chapter 14 and this part's cookie chapter insisted on it.

## Layer 4 versus Layer 7

A **Layer 4** load balancer works on TCP/UDP connections. It sees IP addresses and ports, picks a backend, and forwards packets (or proxies the connection) without reading the payload. Fast, protocol-agnostic, preserves end-to-end TLS. It cannot route by URL, inspect headers, or retry a failed HTTP request.

A **Layer 7** load balancer terminates the connection, parses HTTP, and makes decisions per *request*: route `/api` to one pool and `/` to another, by hostname, by header; add forwarding headers; terminate TLS; redirect HTTP to HTTPS; return fixed responses; integrate with a WAF; authenticate users (ALB can do OIDC); and multiplex many client connections into fewer backend connections.

Default to the ALB for HTTP services. Use an NLB for databases, MQTT, game servers, SMTP, or when a client's firewall must allow-list a fixed IP. You can chain them: an NLB with static IPs forwarding to an ALB target group.

## Health checks

The load balancer's health check is the single most important configuration you will set. It decides when a target gets traffic and when it is removed.

Design the endpoint well:

- **Readiness, not liveness**: `/health/ready` should return 200 only when the instance can serve real requests: configuration loaded, database reachable (a cheap `SELECT 1` with a short timeout, or a cached dependency status), caches warm enough, not shutting down. Part XI chapter 5 discusses the tradeoff of including dependencies.
- **Cheap and fast**: it runs every 10–30 seconds per target per load balancer node. Do not run heavy queries.
- **Fail during shutdown**: return 503 as soon as SIGTERM arrives (Part I chapter 6).
- **Return 200 explicitly**; ALB defaults to expecting 200 but you can set `200-299`.

Tune the parameters: interval 10 s, healthy threshold 2, unhealthy threshold 2 gives roughly 20 s to detect a dead target and 20 s to readmit a recovered one. The default 30 s interval with threshold 5 means 2.5 minutes of sending traffic to a dead target. Deregistration delay: 10–30 s for APIs (as long as your longest request), longer only for long-polling or uploads.

## Distribution algorithms

- **Round robin**: each new request to the next target. Fine when requests are similar.
- **Least outstanding requests** (ALB option): send to the target with the fewest in-flight requests. Better when request costs vary or targets differ in capacity; the usual recommendation for APIs.
- **Weighted** (target groups with weights): canary deployments, blue-green traffic shifting.
- **Flow hash** (NLB): 5-tuple hash so a connection always goes to the same target; inherent to L4.
- **Least connections / IP hash / consistent hashing**: common in Nginx and HAProxy; consistent hashing matters for cache tiers where you want the same key on the same node.

## Session affinity (stickiness)

Stickiness routes the same client to the same target, via a load-balancer cookie (ALB `AWSALB`) or an application cookie. It exists for applications that keep session state in process memory. Costs: uneven load, loss of sessions on deploy or scale-in, and complexity. Prefer shared session stores (chapter 11) and leave stickiness off; enable it only as a bridge for legacy applications you cannot change, and document it as debt.

## TLS at the load balancer

The ALB terminates TLS with ACM certificates: one per listener plus additional certificates served by SNI, or a wildcard. Enable HTTP→HTTPS redirect on the :80 listener as a redirect action. Choose a modern security policy. To targets, speak HTTP on the private network, or HTTPS if policy demands (the ALB will not validate the target's certificate name, so self-signed works). Chapter 9's diagram covers the options.

## Connection handling

The ALB keeps connections to targets alive and reuses them. Two timeouts matter: the ALB **idle timeout** (default 60 s) applies to client and target connections; your target's keep-alive timeout must be longer (e.g. 120 s) or you get intermittent 502s. For long-running requests (large uploads, slow reports) raise the idle timeout, but anything over a minute should become asynchronous.

The ALB generates `X-Forwarded-For`, `X-Forwarded-Proto`, `X-Forwarded-Port`, and `X-Amzn-Trace-Id` (a request ID you should log). Enable access logs to S3; they include target processing time and the status code the *target* returned versus what the ALB returned, which separates "app is slow" from "ALB is slow".

## Failure modes and what the status codes mean

| You see | Meaning | Look at |
|---|---|---|
| 502 from ALB | Target closed connection, sent malformed response, or connection refused; or all targets unhealthy with fail-open | Target logs, keep-alive timeout, crashes, security group |
| 503 from ALB | No registered targets, or targets all unhealthy (in some configurations), or ALB cannot scale fast enough | Target group health, target count, sudden traffic spikes |
| 504 from ALB | Target did not respond within idle timeout | Slow queries, blocked workers |
| 460 | Client closed before ALB responded | Client timeouts shorter than server latency |
| 463 | Too many X-Forwarded-For entries | Proxy chain / abuse |
| Targets flapping healthy/unhealthy | Health check too strict, dependency check timing out, CPU starvation | Health check logs, resource metrics |
| Traffic uneven | Stickiness, long-lived connections (HTTP/2, WebSockets) pinning clients | Per-target request count metrics |
| Slow deploys | Deregistration delay 300 s | Lower it |

## Cost

An ALB costs an hourly rate (≈$0.0225/h, about $16/month in us-east-1) plus Load Balancer Capacity Units based on new connections, active connections, processed bytes and rule evaluations; small APIs land around $18–25/month. An NLB is similar. The cost that surprises people is running one ALB *per service*: ten microservices with ten ALBs cost $200/month before any traffic. Share one ALB across services with host- and path-based rules, or use an ingress controller behind a single ALB. Verify current prices in the AWS Pricing Calculator.

## Load balancing elsewhere

Nginx and HAProxy as software load balancers on your own hosts (chapter 12 plus `upstream` blocks with several servers and `max_fails`/`fail_timeout`); Kubernetes Services (L4, kube-proxy) and Ingress/Gateway controllers (L7); client-side load balancing in gRPC and service meshes (the client knows all endpoints and picks one); DNS round robin and Route 53 weighted/latency routing (coarse, TTL-bound, no health awareness unless health checks are configured); and global load balancing across regions via Route 53 or AWS Global Accelerator (anycast IPs in front of regional ALBs/NLBs).

## Walkthrough: deploying behind an ALB

The complete, repeatable version is Part VII chapter 15; the shape is:

1. VPC with public subnets (ALB) and private subnets (targets) in at least two AZs.
2. Security groups: `sg-alb` allows 443 (and 80) from `0.0.0.0/0`; `sg-app` allows 8000 from `sg-alb` only.
3. ACM certificate for `api.client.com`, DNS-validated.
4. ALB in the public subnets with `sg-alb`; :80 listener redirecting to :443; :443 listener with the certificate and a modern policy.
5. Target group `api` on HTTP :8000, health check `/health/ready`, interval 10 s, thresholds 2/2, deregistration delay 20 s, algorithm least outstanding requests.
6. Backends (ECS service or ASG) registered to the target group, in private subnets with `sg-app`, binding `0.0.0.0:8000`, keep-alive timeout 120 s, honouring `X-Forwarded-Proto`.
7. Route 53 alias `api.client.com` → ALB.
8. Alarms: target 5xx rate, ALB 5xx count, p99 latency, unhealthy host count.
9. Verify: `curl -I https://api.client.com/health/ready`; kill one task and confirm traffic continues; deploy and confirm zero 5xx.

## Common mistakes

- Health check hitting `/` (which may return a 302 redirect or heavy HTML) instead of a dedicated readiness path.
- Default 30 s interval and 5-check thresholds: minutes of traffic to dead targets.
- Deregistration delay left at 300 s; deploys take forever and scale-in is sluggish.
- Target keep-alive shorter than ALB idle timeout.
- Security group on targets open to the whole VPC instead of the ALB's group.
- Stickiness as a design rather than a bridge.
- One ALB per microservice.
- Pointing DNS at ALB IPs.
- Using an ALB for a protocol that is not HTTP and wondering why it does not work.

## Exercises

1. In an AWS sandbox (delete afterwards), create an ALB with two targets. Stop one target's process and time how long the ALB takes to stop sending traffic with default health check settings; then with interval 10 s and threshold 2.
2. Configure a target with a 5-second HTTP keep-alive timeout behind an ALB with a 60-second idle timeout, load test, and observe 502s in the ALB access logs. Fix and repeat.
3. Design the listener rules for one ALB serving `api.client.com/*`, `app.client.com/*` and `admin.client.com/*` (with OIDC authentication) to three target groups. Write them as Terraform or CloudFormation.
