# DNS Resolution

:::objectives
- Trace a DNS query from a browser through recursive resolvers to authoritative servers and back.
- Use the major record types correctly: A, AAAA, CNAME, ALIAS, MX, TXT, NS, SOA, SRV, CAA.
- Design records and TTLs for deployments, migrations and failover, and understand why "DNS propagation" is mostly a myth about caching.
- Diagnose DNS failures with `dig` and avoid the outages DNS causes.
:::

## The problem

Humans and configuration files use names; packets use addresses. Addresses change: load balancers scale, servers are replaced, providers migrate. DNS is the indirection layer that lets `api.client.com` keep working while everything behind it changes. It is also a globally distributed, heavily cached database with eventual consistency, and when it is wrong, *everything* is down while every server reports healthy. "It's always DNS" is a joke because it is so often true.

## The hierarchy

DNS names are read right to left: `api.client.com.` is the `api` label inside `client` inside `com` inside the root (the trailing dot, usually implicit). Each level is a **zone** served by **authoritative name servers** that hold the records for that zone and delegate sub-zones via NS records.

- **Root servers** (13 named letters, hundreds of anycast instances) know the authoritative servers for every top-level domain.
- **TLD servers** (`.com`, `.io`, `.de`) know the authoritative servers for each registered domain.
- **Your zone's authoritative servers** (Route 53, Cloudflare, your registrar) hold the actual records.

## Record types

| Type | Maps | Example | Notes |
|---|---|---|---|
| **A** | name → IPv4 | `api 60 A 52.95.110.1` | Multiple A records = round robin |
| **AAAA** | name → IPv6 | `api 60 AAAA 2600:1f18::1` | Required for dual-stack |
| **CNAME** | name → another name | `www CNAME client.com.` | Cannot coexist with other records on the same name; **cannot be used at the zone apex** (`client.com` itself) |
| **ALIAS / ANAME** | name → another name, resolved server-side | `client.com ALIAS alb-123.eu-west-1.elb.amazonaws.com` | Provider-specific (Route 53 Alias, Cloudflare CNAME flattening); works at the apex; Route 53 aliases to AWS resources are free of query charges |
| **MX** | domain → mail servers | `@ MX 10 mail.protonmail.ch.` | Priority value; lower is preferred |
| **TXT** | name → text | `@ TXT "v=spf1 include:_spf.google.com ~all"` | SPF, DKIM, DMARC, domain verification for ACM, Google, etc. |
| **NS** | zone → authoritative servers | `@ NS ns-123.awsdns-45.com.` | Delegation; set at the registrar for the apex |
| **SOA** | zone metadata | serial, refresh, minimum (negative-cache TTL) | One per zone |
| **SRV** | service → host:port | `_sip._tcp SRV 10 60 5060 sip.example.com.` | Used by some service discovery; HTTP does not use it |
| **CAA** | which CAs may issue certs | `@ CAA 0 issue "amazon.com"` | Prevents mis-issuance; set it |
| **PTR** | IP → name (reverse) | in `in-addr.arpa` zones | Matters for outbound mail servers |

## TTLs and the "propagation" myth

A TTL is the number of seconds a resolver may cache a record. When you change a record, no message is sent to the world's resolvers; each one simply keeps the old answer until its copy expires. "Waiting for propagation" is waiting for caches to expire, and the wait is bounded by the *old* TTL, not the new one.

Strategy for a planned change (migrating a load balancer, moving providers):

1. Days before: lower the TTL from 3600 to 60. Wait for the old TTL to expire everywhere (an hour).
2. Make the change. Within ~60 s, nearly all resolvers see it. Some misbehaving resolvers ignore TTLs; keep the old endpoint serving (or redirecting) for a day.
3. Afterwards: raise the TTL back if the record is stable, to reduce query volume and resolver dependence.

Typical TTLs: 60–300 s for records that participate in failover or point at things that change (load balancers, blue/green switches); 3600–86400 s for stable records (MX, TXT, NS). Route 53 Alias records to AWS resources inherit the resource's TTL (60 s for ALBs) automatically.

Negative caching: an NXDOMAIN ("does not exist") answer is cached too, for the SOA minimum TTL. Creating a record and testing it *before* it exists can poison your own resolver's cache for minutes; test with `dig @authoritative-server` first.

## Deployments and DNS

- **Point names at load balancers via ALIAS/CNAME**, never at instance IPs. ALB and NLB IPs change (NLBs can have static EIPs if you need them for allow-lists).
- **Apex domains** (`client.com`) cannot use CNAME; use the provider's ALIAS feature or redirect the apex to `www` with a small static redirector.
- **Health-checked failover**: Route 53 can return a secondary record when a health check fails (failover routing), route users to the nearest healthy region (latency routing), or split traffic by percentage (weighted routing) for gradual migrations. These all depend on TTLs; a 60 s TTL means up to 60 s of users still going to the dead endpoint, plus resolver misbehaviour.
- **Certificate validation**: ACM and Let's Encrypt DNS-01 challenges work by asking you to publish a TXT or CNAME record; automation (Route 53 integration, cert-manager) makes this hands-free.
- **Internal DNS**: inside a VPC, Route 53 private hosted zones let you name internal services (`db.internal.client.com`) without exposing records publicly; ECS Service Connect and Kubernetes CoreDNS provide service discovery names (`orders.svc.cluster.local`). The VPC resolver lives at the base of the VPC CIDR plus two (`10.20.0.2`).

## Security

- **DNS is unauthenticated** by default; a resolver can be fed forged answers (cache poisoning) and queries are visible to anyone on the path. DNSSEC signs zones so resolvers can verify answers (Route 53 supports signing; adoption is partial). DNS over HTTPS/TLS encrypts the client-to-resolver leg.
- **Dangling records** are a common takeover vector: a CNAME pointing at a deprovisioned S3 bucket, Heroku app or Elastic Beanstalk environment can be claimed by an attacker who registers that resource name, giving them a page on your domain (subdomain takeover). Delete records when you delete resources; audit periodically.
- **CAA records** limit which certificate authorities can issue for your domain.
- **Registrar security**: the registrar account controls the NS records, and therefore everything. MFA, registry lock, and a shared ownership model (not a departed contractor's personal account) are essential. Domains expire; set auto-renew and calendar reminders, and make sure the payment card is not an individual's.
- **Email authentication records** (SPF, DKIM, DMARC) are DNS-based; without them your domain can be spoofed for phishing against your own client.

## Debugging with dig

```bash
dig api.client.com                      # full answer with sections and TTL
dig +short api.client.com               # just the answer
dig +trace api.client.com               # walk from root to authoritative: shows delegation problems
dig @ns-123.awsdns-45.com api.client.com   # ask the authoritative server directly (bypasses caches)
dig @1.1.1.1 api.client.com             # compare a public resolver with your local one
dig api.client.com AAAA                 # IPv6
dig -x 52.95.110.1                      # reverse lookup
dig client.com NS +short; dig client.com SOA +short
dig api.client.com +noall +answer +ttlid    # watch TTL count down on repeated queries
```

Reading status codes: `NOERROR` with no answer section means the name exists but has no record of that type (common: querying A for a name that only has a CNAME to something without A). `NXDOMAIN`: the name does not exist (typo, wrong zone, record not created, delegation broken). `SERVFAIL`: the resolver could not get an answer (authoritative servers down, DNSSEC validation failure, broken delegation). `REFUSED`: the server will not answer you (asking an authoritative server recursively, or ACLs).

## Common mistakes

- Creating a hosted zone without updating the registrar's NS records.
- CNAME at the apex (rejected by compliant providers) or CNAME coexisting with other records.
- High TTLs on records you need to change quickly during an incident.
- Testing a record before it exists and caching the NXDOMAIN locally.
- Dangling CNAMEs to deleted cloud resources.
- Domain registered under an individual's account and card; expires silently.
- Hard-coding resolver IPs or disabling caching in applications, then hammering the resolver (and hitting Route 53 Resolver's per-ENI query limits).

## Exercises

1. Run `dig +trace` for a domain you manage and for a well-known domain. Identify each delegation step and the final authoritative answer.
2. Lower a record's TTL, change it, and measure with `dig +ttlid` against two different resolvers how long each takes to return the new value.
3. Audit a zone you control for dangling records: list every CNAME and ALIAS target and verify each resolves to a resource you still own.
