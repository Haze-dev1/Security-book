## The problem

Application servers are good at running your code and bad at everything else: terminating TLS efficiently, serving static files, absorbing slow clients, enforcing request size limits, compressing responses, routing several applications on one host, and presenting a stable public surface while backends change. A reverse proxy does all of that in front of your application. Nearly every production web deployment has at least one, whether it is Nginx on a VM, an ALB, a Kubernetes ingress controller, or a CDN.

## Forward versus reverse

A **forward proxy** acts for *clients*: the client is configured to send requests to the proxy, which fetches from the Internet on its behalf. Uses: corporate egress control and filtering, caching, anonymity, giving private-subnet servers a controlled path out (Squid, or an explicit proxy with an allow-list of destinations). You meet forward proxies in client environments where all outbound traffic must pass through one, and `HTTPS_PROXY` environment variables suddenly matter.

A **reverse proxy** acts for *servers*: clients connect to it believing it is the server; it forwards to one or more backends. Everything in this chapter is about reverse proxies.

## Nginx: a production configuration, annotated

```nginx
@file: /etc/nginx/conf.d/app.conf
# Upstream: where the application listens. keepalive keeps connections to it open.
upstream app {
    server 127.0.0.1:8000;
    keepalive 32;
}

# Redirect all HTTP to HTTPS (ACME HTTP-01 challenge excepted if you use certbot --webroot)
server {
    listen 80; listen [::]:80;
    server_name api.client.com;
    location /.well-known/acme-challenge/ { root /var/www/acme; }
    location / { return 301 https://$host$request_uri; }
}

server {
    listen 443 ssl http2; listen [::]:443 ssl http2;
    server_name api.client.com;

    ssl_certificate     /etc/letsencrypt/live/api.client.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/api.client.com/privkey.pem;
    include /etc/nginx/snippets/tls-modern.conf;      # protocols, ciphers, stapling (chapter 9)

    # Security headers (chapter: Security Headers and CSP)
    add_header Strict-Transport-Security "max-age=63072000; includeSubDomains" always;
    add_header X-Content-Type-Options nosniff always;
    add_header Referrer-Policy strict-origin-when-cross-origin always;

    client_max_body_size 10m;            # 413 for anything larger; protects the app's memory
    client_body_timeout 15s;             # slow-upload defence
    client_header_timeout 15s;

    access_log /var/log/nginx/api.access.log json_combined;   # structured; define the format in nginx.conf
    error_log  /var/log/nginx/api.error.log warn;

    gzip on; gzip_types application/json text/css application/javascript; gzip_min_length 1024;

    # Static assets: served directly, cached for a year (filenames are fingerprinted)
    location /static/ {
        alias /srv/app/static/;
        expires 1y;
        add_header Cache-Control "public, immutable";
        access_log off;
    }

    # API: proxy to the application
    location / {
        proxy_pass http://app;
        proxy_http_version 1.1;
        proxy_set_header Connection "";                 # required for upstream keepalive

        # Tell the application who really called and how
        proxy_set_header Host              $host;
        proxy_set_header X-Real-IP         $remote_addr;
        proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_set_header X-Request-ID      $request_id;    # correlation ID generated per request

        proxy_connect_timeout 5s;
        proxy_send_timeout    30s;
        proxy_read_timeout    30s;      # 504 if the app takes longer; must exceed the slowest legit request
        proxy_buffering on;             # absorb slow clients; turn off per-location for streaming
        proxy_next_upstream error timeout http_502 http_503;   # retry safe failures on another upstream (only idempotent!)
    }

    # Streaming endpoint (SSE): no buffering, long read timeout
    location /events {
        proxy_pass http://app;
        proxy_http_version 1.1;
        proxy_set_header Connection "";
        proxy_buffering off;
        proxy_cache off;
        proxy_read_timeout 1h;
        add_header X-Accel-Buffering no;
    }

    # WebSockets
    location /ws {
        proxy_pass http://127.0.0.1:8001;
        proxy_http_version 1.1;
        proxy_set_header Upgrade $http_upgrade;
        proxy_set_header Connection "upgrade";
        proxy_set_header Host $host;
        proxy_read_timeout 1h;
    }
}
```

Essential operations:

```bash
sudo nginx -t && sudo systemctl reload nginx     # validate, then zero-downtime reload
sudo tail -f /var/log/nginx/api.error.log         # upstream errors appear here with reasons
```

### What each piece prevents

- **Buffering** (`proxy_buffering on`): Nginx reads the whole response from the app quickly and dribbles it out to a slow client, freeing the application worker. Without it, a few slow mobile clients can hold all your Gunicorn workers. The exception is streaming, where buffering breaks the feature.
- **`client_max_body_size`**: a 2 GB upload to an endpoint expecting 1 MB JSON would otherwise be read into the application's memory.
- **Timeouts**: `proxy_read_timeout` is where 504s come from; set it with your slowest legitimate operation in mind, and move anything slower to a background job.
- **Upstream keepalive** (`keepalive 32` plus `Connection ""`): avoids a TCP handshake per request to the backend.
- **`proxy_next_upstream`**: retries on another backend when one fails; only safe for idempotent requests, and Nginx by default does not retry non-idempotent methods after a partial send (`non_idempotent` flag changes that; leave it off).

## Caddy: the same thing in ten lines

Caddy obtains and renews certificates automatically, defaults to modern TLS, HTTP/2 and HTTP/3, and redirects HTTP to HTTPS without configuration.

```caddy
@file: /etc/caddy/Caddyfile
api.client.com {
    encode zstd gzip
    header {
        Strict-Transport-Security "max-age=63072000; includeSubDomains"
        X-Content-Type-Options nosniff
        Referrer-Policy strict-origin-when-cross-origin
    }
    request_body { max_size 10MB }

    handle_path /static/* {
        root * /srv/app/static
        file_server
        header Cache-Control "public, max-age=31536000, immutable"
    }

    handle /ws* {
        reverse_proxy 127.0.0.1:8001
    }

    handle {
        reverse_proxy 127.0.0.1:8000 {
            header_up X-Request-ID {http.request.uuid}
            transport http { dial_timeout 5s; response_header_timeout 30s }
            # Caddy sets X-Forwarded-For/Proto/Host automatically
            flush_interval -1        # disable buffering for streaming (per-route if needed)
        }
    }
    log { output file /var/log/caddy/api.log; format json }
}
```

For a single VM or small client deployment, Caddy removes an entire class of operational risk (certificate expiry) and configuration error (weak TLS). Nginx remains the choice when you need its ecosystem, fine-grained tuning, or it is already the client's standard. Both are excellent; pick one and know it well.

## Client identity through proxies

The application sees the proxy's address as the TCP peer. The real client IP, scheme and host arrive in headers set by the proxy. Two rules:

1. **The application trusts these headers only from its own proxies.** If an attacker can reach the application directly (or if the proxy forwards client-supplied `X-Forwarded-For` unchanged), they can forge any IP, bypassing rate limits and poisoning audit logs. Bind the application to localhost or a private network; configure the framework's trusted-proxy list (`ProxyHeadersMiddleware` / `--forwarded-allow-ips` in uvicorn, `app.set('trust proxy', ...)` in Express, `SECURE_PROXY_SSL_HEADER` in Django) to the proxy's address only.
2. **`X-Forwarded-For` is a list.** `client, proxy1, proxy2`. The rightmost entries were added by proxies you control; the leftmost is client-supplied and unverifiable unless your edge overwrites it. Take the entry just before your own proxies.

For TCP proxies (NLB, HAProxy TCP mode) that cannot add HTTP headers, the **PROXY protocol** prepends a line with the original addresses to the connection; both sides must enable it.

## Behind a cloud load balancer

Often there are two proxies: an ALB in front, then Nginx or the application. The ALB terminates TLS and sets `X-Forwarded-For/Proto/Port`; Nginx should *append* to those headers (`$proxy_add_x_forwarded_for`) and pass `X-Forwarded-Proto` through rather than overwriting it with `$scheme` (which would be `http` on the ALB-to-Nginx hop). Health checks from the ALB arrive at Nginx; route `/health` to the application and exclude it from access logs if it is noisy.

## Rate limiting and basic protections at the proxy

```nginx
# in http {}: 10 requests/second per client IP, bursts of 20, for the API zone
limit_req_zone $binary_remote_addr zone=api:10m rate=10r/s;
limit_conn_zone $binary_remote_addr zone=conn:10m;
# in location /api/ {}
limit_req zone=api burst=20 nodelay;
limit_conn conn 50;
limit_req_status 429;
```

Proxy-level limits are a blunt first line (per-IP, which NAT makes unfair); application-level limits per user or API key are the precise ones (Part III chapter 5). Use both.

## Debugging proxy problems

| Symptom | Likely cause | Check |
|---|---|---|
| 502 Bad Gateway | App not running, wrong port, app closed connection, response too large for buffers | `error.log`: "connect() failed (111: Connection refused)" or "upstream prematurely closed" |
| 504 Gateway Timeout | App slower than `proxy_read_timeout` | App logs for the slow request; raise timeout or move work async |
| 413 Payload Too Large | `client_max_body_size` | Raise deliberately, or fix the client |
| Redirect loop to HTTPS | App not honouring `X-Forwarded-Proto` | App's proxy settings; the header value reaching the app |
| Wrong client IP in logs | Trusted-proxy config | Dump headers at the app; verify the proxy sets them and the app trusts only the proxy |
| Streaming stalls then arrives all at once | Buffering | `proxy_buffering off`, `X-Accel-Buffering: no` |
| WebSocket closes after 60 s | `proxy_read_timeout` or ALB idle timeout | Raise timeouts; add application pings |
| Works with curl, fails in browser | Missing CORS or security header interaction | Browser console |
| Headers with underscores vanish | Nginx drops them by default | Rename to hyphens or `underscores_in_headers on` |

```bash
# See exactly what the app receives (temporary debugging endpoint or tcpdump on the loopback)
sudo tcpdump -i lo -A -s0 'tcp port 8000' | grep -iE 'x-forwarded|host:'
```

## Common mistakes

- Application reachable directly on its port from the network, bypassing every proxy protection.
- Trusting `X-Forwarded-For` from everyone.
- Buffering on for streaming endpoints; buffering off for everything (slow clients exhaust workers).
- No `client_max_body_size` (Nginx defaults to 1 MB, which also surprises people the other way).
- `proxy_read_timeout` raised to 10 minutes to "fix" a slow endpoint instead of making it asynchronous.
- Overwriting `X-Forwarded-Proto` behind an ALB.
- Forgetting `proxy_http_version 1.1` and `Connection ""` for keepalive, or the Upgrade headers for WebSockets.
- Reloading Nginx without `nginx -t`, taking the site down with a typo.

## Exercises

1. Put Nginx or Caddy in front of a small app locally. Confirm the app sees `X-Forwarded-For` and `X-Forwarded-Proto`. Then try to forge `X-Forwarded-For` from curl and verify your framework ignores it.
2. Add an endpoint that sleeps 40 seconds; observe the 504 with a 30-second `proxy_read_timeout`. Decide how you would redesign the endpoint rather than raising the timeout.
3. Serve a server-sent events endpoint through the proxy. Make it stream correctly by adjusting buffering, and verify with `curl -N`.
