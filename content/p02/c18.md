## The problem

"The API is slow" is the most common complaint and the least specific. Slowness has at least four distinct physical causes with different remedies, and most engineers reach for the wrong one: they optimise database queries when the user is 200 ms away, or buy bandwidth when the problem is round trips. This chapter gives you the vocabulary and the arithmetic to diagnose performance before touching code.

## Definitions

- **Latency**: time for a unit of data to travel from source to destination (one-way), or the time for a request to get a response (round-trip time, RTT). Measured in milliseconds. Set by distance, hops and queueing.
- **Bandwidth**: the capacity of a link, in bits per second. A 1 Gbps link can carry a gigabit per second *if* the protocol can use it.
- **Throughput**: what you actually achieve: bytes per second transferred, or requests per second served. Always at or below bandwidth; often far below, limited by latency, loss and protocol behaviour.
- **Jitter**: variation in latency. Matters for real-time media; a buffer absorbs it at the cost of added latency.
- **Packet loss**: fraction of packets that do not arrive. Even 0.1% has outsized effects on TCP throughput over long paths.

The intuition: bandwidth is how wide the pipe is; latency is how long the pipe is; throughput is how much water you actually move, which depends on both and on how the protocol behaves.

## The physics of latency

Light in fibre travels about 200,000 km/s, two-thirds of its speed in vacuum. Round trip across:

| Path | Distance | Theoretical RTT | Typical measured RTT |
|---|---|---|---|
| Same data centre | < 1 km | ~0 | 0.1–0.5 ms |
| Between AZs in a region | tens of km | < 1 ms | 1–2 ms |
| London ↔ Frankfurt | 640 km | 6 ms | 10–15 ms |
| New York ↔ London | 5,600 km | 56 ms | 70–80 ms |
| New York ↔ Sydney | 16,000 km | 160 ms | 200–250 ms |
| Geostationary satellite | 72,000 km round trip | 480 ms | 550–650 ms |

Measured RTTs exceed the theoretical because fibre routes are longer than great circles, and each router adds queueing and processing. Nothing you do on a server reduces these numbers; only moving the endpoint closer (regions, CDNs, edge compute) does.

## Why round trips dominate small requests

A new HTTPS request costs: DNS (0–1 RTT), TCP handshake (1 RTT), TLS 1.3 handshake (1 RTT), request and first byte (1 RTT), plus server processing. For a Sydney user hitting Virginia (200 ms RTT): 600–800 ms before the server has even done any work, for a response that takes 5 ms to compute. With a warm, reused connection it is 200 ms plus 5. This is why:

- **Connection reuse** (HTTP keep-alive, HTTP/2, connection pools) is the first performance tool.
- **Fewer, larger requests** beat many small ones over high-latency links (and HTTP/2 multiplexing mitigates the many-small-requests cost).
- **Sequential dependent calls are latency multipliers**: a page that loads HTML, then JS, then calls an API that calls another service, each dependent on the last, pays an RTT per step. Parallelise what can be parallel.
- **Chatty service-to-service calls** across regions are architectural errors; keep tightly coupled services in the same region (ideally same AZ for the hottest paths, accepting the availability trade).

## Why throughput falls short of bandwidth

TCP's congestion window limits how much data is in flight per RTT. Maximum throughput of one connection ≈ window ÷ RTT. With a 64 KB window and 100 ms RTT: 640 KB/s ≈ 5 Mbps, regardless of a 10 Gbps link. Modern stacks scale windows into megabytes, but loss resets growth. The Mathis formula gives the loss-limited ceiling: throughput ≈ (MSS ÷ RTT) × (1.22 ÷ √loss). At 100 ms RTT, 1,460-byte segments and 1% loss, that is about 1.4 Mbps per connection. Hence:

- Long-distance, lossy paths need **parallel connections** or **BBR** congestion control to fill a link; or, better, move the data closer (CDN, regional buckets, S3 Transfer Acceleration).
- Inside a region, loss is near zero and RTT is ~1 ms, so throughput approaches the link rate; EC2 instance bandwidth limits (which scale with instance size and are burstable on small types) become the ceiling.
- **Bandwidth-delay product** (bandwidth × RTT) is the buffer size needed to keep a link full: 1 Gbps × 100 ms = 12.5 MB. Kernel defaults handle this now; very fast long links may still need tuning (`net.ipv4.tcp_rmem/wmem`).

## Serialisation and payload size

Time to transmit a payload = size ÷ bandwidth, added to latency. On a 10 Mbps mobile link, a 2 MB JavaScript bundle costs 1.6 s of pure transmission; on 100 ms RTT with slow start it costs several more RTTs. Compression (gzip/Brotli for text), smaller payloads (pagination, field selection, binary formats), image optimisation and code splitting attack this term. For APIs, a 1 MB JSON response that the client discards 90% of is a design problem visible in every metric.

## Server-side latency

Once the request arrives: queueing for a worker (visible as time between accept and handler start), middleware, business logic, database round trips (each one ~0.5–2 ms within a region; an N+1 query loop of 200 queries is 200–400 ms), calls to external APIs (tens to hundreds of ms, highly variable), serialisation, and the response write. Measure these separately; traces (Part XI) do exactly this.

## Percentiles, not averages

Latency is skewed: most requests are fast, a tail is slow. The average hides the tail; the tail is what users remember and what SLOs are set on. Report p50, p95, p99 (and p99.9 for high-traffic systems). A p99 of 2 s means 1% of requests, often *the same unlucky users repeatedly*, wait 2 s or more. Tail latency compounds: a page making 10 parallel API calls experiences the p99 of the slowest, so at the page level the "p99" becomes roughly the p90 of each call. This is why high-fan-out systems obsess over tails.

## Building a latency budget

A latency budget allocates a target (say, p95 under 300 ms for an API call as seen by a user in the same continent) across components so you can see what dominates.

## Measuring

```bash
# Round trip to a host (ICMP; may be blocked)
ping -c 10 api.client.com
# Per-hop latency and where it jumps
mtr -rwc 50 api.client.com
# HTTP phases
curl -o /dev/null -s -w 'dns=%{time_namelookup} tcp=%{time_connect} tls=%{time_appconnect} ttfb=%{time_starttransfer} total=%{time_total} size=%{size_download}\n' https://api.client.com/api/items
# Raw bandwidth between two hosts you control
iperf3 -s   # on one;   iperf3 -c <host> -P 4   # on the other, 4 parallel streams
# Retransmissions as a loss proxy
nstat -az TcpRetransSegs
# Load test percentiles (Part XI chapter 8)
k6 run --vus 50 --duration 60s script.js
```

In the browser, the Network panel and the Resource Timing API expose the same phases per request; `Server-Timing` headers let your backend report its internal breakdown to the browser and to synthetic monitors.

## Design levers, ranked

1. **Eliminate round trips**: connection reuse, HTTP/2 or HTTP/3, batching, avoiding sequential dependent calls, caching DNS and auth lookups.
2. **Move closer**: CDN for static and cacheable content; regional deployments for users in distant markets; edge compute for lightweight personalisation.
3. **Shrink payloads**: compression, pagination, sparse fieldsets, image formats, code splitting.
4. **Parallelise**: fan out independent calls; stream responses so the first bytes arrive early.
5. **Make the server fast**: indexes, N+1 elimination, caching hot reads, async for slow dependencies.
6. **Bound the tail**: timeouts, hedged requests for idempotent calls, load shedding, avoiding GC pauses and cold starts on the hot path.

## Common mistakes

- Optimising server code when 80% of the time is network distance.
- Reporting average latency; missing a tail that affects every heavy user.
- Serving a global audience from one region with no CDN.
- Chatty cross-region service calls.
- Sequential `await`s on independent operations.
- Unbounded response sizes.
- Load testing from the same data centre and declaring the app "fast".

## Exercises

1. Measure `curl` phase timings to the same endpoint from your machine and from a cloud instance in another region. Attribute the difference.
2. Take a slow endpoint you know and build its latency budget from a trace or from timing logs. Identify the dominant term and propose a fix that does not involve "make the code faster".
