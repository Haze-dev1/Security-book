## The problem

Your database lives in a private subnet with no public address, as it should. Now a developer needs to run a query, a client's on-premises system needs to call your API without exposing it to the Internet, two VPCs need to talk, and an auditor asks how administrators reach production. "Private connectivity" is the set of mechanisms for reaching things that are deliberately unreachable from the public Internet, and each mechanism trades security, cost and convenience differently.

## What a VPN does

A Virtual Private Network creates an encrypted tunnel between two endpoints over an untrusted network, and makes remote networks appear local by routing traffic for their address ranges through the tunnel. Packets to `10.20.128.10` on your laptop are encrypted, sent to the VPN gateway's public address, decrypted there and forwarded into the VPC. Authentication is by certificates, pre-shared keys or an identity provider.

Protocols: **IPsec** (the standard for site-to-site between routers and cloud gateways; complex but universal), **WireGuard** (modern, minimal, fast, in the Linux kernel; the basis of Tailscale and many self-hosted setups), **OpenVPN** (older, flexible, widely supported including AWS Client VPN), and TLS-based vendor VPNs.

### Site-to-site

Connects two networks: a client's office or data centre to your VPC. AWS Site-to-Site VPN pairs a Virtual Private Gateway (or Transit Gateway) with the client's firewall as a "customer gateway" over two IPsec tunnels for redundancy. Routing is static or via BGP. Throughput per tunnel is limited (1.25 Gbps). Address ranges must not overlap, which is why chapter 3 insisted on planning CIDRs.

### Client VPN

Connects individual users' devices. AWS Client VPN (OpenVPN-based, authenticates with certificates, Active Directory or SAML) or self-hosted WireGuard/OpenVPN on a small instance. Users get a tunnel into the VPC for administrative access. Costs: per-endpoint-hour plus per-connection-hour for AWS Client VPN; a self-hosted WireGuard instance costs a few dollars a month but is yours to patch.

### Mesh and zero-trust networks

Tailscale, ZeroTier, Cloudflare WARP/Access and similar build an identity-based mesh where every device authenticates to a control plane and connects peer-to-peer over WireGuard, with access control lists per user and service. They remove the "once inside, everything is reachable" weakness of classic VPNs and are quick to set up; the trade is dependency on a third party's control plane for your access path.

For most AWS deployments the recommended default is **SSM Session Manager** for shell access and port forwarding, with no SSH ports open anywhere, plus a client VPN or zero-trust proxy if the team needs routine access to many internal tools.

```bash
# Shell on a private instance, no SSH, no open ports, fully logged
aws ssm start-session --target i-0abc123
# Port-forward to a private RDS instance through an instance in the VPC
aws ssm start-session --target i-0abc123 \
  --document-name AWS-StartPortForwardingSessionToRemoteHost \
  --parameters '{"host":["prod-db.cluster-xyz.eu-west-1.rds.amazonaws.com"],"portNumber":["5432"],"localPortNumber":["15432"]}'
psql "host=localhost port=15432 dbname=app user=readonly sslmode=require"
# Shell into a Fargate task
aws ecs execute-command --cluster prod --task <id> --container api --interactive --command /bin/sh
```

Requirements: the instance role includes `AmazonSSMManagedInstanceCore`; the instance can reach the SSM endpoints (via NAT or VPC interface endpoints for `ssm`, `ssmmessages`, `ec2messages`); the user has IAM permission scoped to the instances they may reach, ideally with MFA conditions; session logging is enabled.

If you must run a bastion: smallest instance, SSH keys only (no passwords), `AllowUsers` restricted, MFA via SSH certificates or an IdP, fail2ban, security group limited to known ranges, no other software, logs shipped off-host, and replace it regularly from a fresh image. Prefer `ssh -J` (ProxyJump) over agent forwarding; forwarding your agent to a bastion lets anyone with root there use your keys.

## Connecting networks

### VPC peering

A direct, non-transitive connection between two VPCs (same or different accounts/regions). Traffic stays on the AWS network. Each VPC adds routes for the other's CIDR; security groups can reference peered groups in the same region. Non-transitive means A↔B and B↔C does not give A↔C. Fine for a handful of VPCs; a mess beyond that.

### Transit Gateway

A regional hub that VPCs, VPNs and Direct Connect attach to, with route tables controlling who can reach whom. Transitive, scalable, auditable; hourly cost per attachment plus per-GB. The standard for organisations with many VPCs or a hybrid network.

### Direct Connect

A dedicated physical link from a client's data centre to AWS via a partner location. Consistent latency and bandwidth (1–100 Gbps), traffic off the public Internet, lower data-transfer prices for heavy volumes; weeks to provision and significant fixed cost. Usually paired with a VPN as backup. Relevant when a client has serious on-premises systems; an FDE rarely provisions it but often works within it.

### PrivateLink and interface endpoints

[[privatelink]] exposes a service (yours, behind an NLB, or an AWS service) as an elastic network interface inside the consumer's VPC. The consumer connects to a private IP; traffic never leaves AWS; no CIDR overlap concerns, no peering, no routing changes. This is how you offer a client's VPC private access to your SaaS API, and how your VPC reaches Secrets Manager, ECR or CloudWatch without a NAT gateway. Each interface endpoint has an hourly cost per AZ plus per-GB; gateway endpoints for S3 and DynamoDB are free.

## Security principles for private connectivity

- **A private network is not a trusted network.** Encrypt in transit (TLS) over VPNs and peering too; authenticate every request. Private links reduce exposure; they do not replace application security. This is the core of [[zero trust]].
- **Least privilege at the network layer still applies**: a VPN user should reach the tools they need, not the whole VPC. Use security groups referencing the VPN's address pool narrowly, and client VPN authorization rules.
- **Audit every administrative session**: SSM logs by default; bastions and VPNs need deliberate logging.
- **Avoid split-brain address plans**: overlapping CIDRs force NAT hacks that nobody understands a year later.
- **Rotate and revoke**: VPN certificates and WireGuard keys for people who leave; SSM access via IAM groups tied to the identity provider so offboarding is automatic.
- **Do not expose internal admin tools publicly behind "only we know the URL".** Put them behind the VPN or an identity-aware proxy.

## Common mistakes

- SSH open to the Internet on production instances because "the bastion was too much work" (SSM is less work).
- Agent forwarding to shared bastions.
- A single VPN pre-shared key shared on a chat channel.
- Client VPN users landing in a network where every security group allows the VPC CIDR.
- Overlapping CIDRs discovered at VPN setup time, after infrastructure is deployed.
- Relying on peering for a dozen VPCs, producing an unreadable mesh.
- NAT gateway bills for traffic to AWS services that interface endpoints would carry privately (cost and security both improved).

## Exercises

1. Set up SSM Session Manager on a test instance in a private subnet with no inbound security group rules. Open a shell and port-forward to a database or a local service. Find the session log in CloudWatch.
2. Build a WireGuard tunnel between two VMs (or a VM and your laptop) and route a private range through it. Inspect the tunnel with `wg show`.
3. Write the discovery questions you would ask a client before designing connectivity between their network and your VPC (address ranges, existing VPN/Direct Connect, firewall change process, who owns the customer gateway).
