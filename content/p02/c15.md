## The problem

A server offers services on ports. Every open port reachable from an untrusted network is an attack surface: a database with a weak password, an admin interface, a debug endpoint, SSH exposed to password guessing. Firewalls restrict *which* sources can reach *which* ports, turning "everything is reachable unless the application defends itself" into "nothing is reachable unless explicitly allowed". They are the first and cheapest layer of [[defense in depth]], and most of the catastrophic breaches of exposed databases needed only a firewall rule to prevent.

## Stateless and stateful filtering

A **stateless** filter evaluates each packet alone against rules on source/destination address, protocol and port. To allow a TCP connection it needs *two* rules: inbound to the server port, and outbound from the server port back to the client's [[ephemeral port|ephemeral ports]] (1024–65535), because it does not know the reply belongs to an existing connection. AWS Network ACLs are stateless.

A **stateful** filter tracks connections. When an inbound packet is allowed and a connection is established, the return traffic is allowed automatically. One rule ("allow inbound 443 from anywhere") suffices; replies just work. AWS security groups, Linux `nftables`/`iptables` with conntrack, `ufw`, and nearly all modern firewalls are stateful.

Stateful filters hold a connection table with timeouts (minutes for established TCP, seconds for UDP). Idle connections dropped from the table die silently, the same phenomenon as NAT in chapter 4; keep-alives are the cure.

## Default deny

The correct posture: **deny everything, then allow the minimum**. Inbound: only the ports the public needs (443, maybe 80 for redirects) from everywhere; administrative access (SSH) from specific addresses or via a bastion/VPN; internal services only from the components that use them. Outbound: ideally restricted too (a compromised server that cannot reach the Internet cannot download tools or exfiltrate data), though outbound allow-lists are operationally demanding and most teams start with outbound open and tighten for sensitive tiers.

### Security groups done right

- Reference other security groups as sources instead of IP ranges wherever possible. "Allow 5432 from sg-app" stays correct as the app tier scales.
- One security group per role (alb, app, db, bastion), not one per instance and not one giant shared group.
- Inbound rules only for what the role serves. No SSH on application or database groups; use SSM Session Manager (chapter 16) or a bastion group.
- Security groups allow only; there are no deny rules. Everything not allowed is denied. Rules are evaluated as a union across all groups attached to an interface.
- Default outbound is "allow all". Restrict outbound on database and sensitive tiers (e.g., allow only to the VPC and to AWS service endpoints) when you can manage it.
- Audit regularly: `0.0.0.0/0` on anything other than 80/443 on a load balancer is a finding. AWS Config rules and Security Hub flag these automatically.

### Network ACLs

Use them for coarse, subnet-level intent: data subnets accept traffic only from app subnet CIDRs; deny a known-malicious range; comply with a policy requiring subnet-level controls. Remember ephemeral ports (allow 1024–65535 inbound for return traffic from outbound connections, and outbound for replies to inbound connections) or you will spend an afternoon on a mystery timeout. Rules are numbered and the first match wins; leave gaps for insertion.

## Host firewalls on Linux

Even behind security groups, a host firewall adds defence against misconfigured cloud rules and documents intent on the machine itself. `ufw` (Ubuntu) is a friendly front end; `nftables` is the modern kernel interface (`iptables` is its legacy predecessor, still everywhere).

```bash
# ufw: default deny inbound, allow outbound, open what we serve
sudo ufw default deny incoming
sudo ufw default allow outgoing
sudo ufw allow from 203.0.113.0/29 to any port 22 proto tcp comment 'SSH from office'
sudo ufw allow 80/tcp comment 'HTTP redirect'
sudo ufw allow 443/tcp comment 'HTTPS'
sudo ufw limit 22/tcp                    # rate-limit SSH connection attempts
sudo ufw enable
sudo ufw status numbered
```

```bash
# nftables equivalent (/etc/nftables.conf), stateful with conntrack
table inet filter {
  chain input {
    type filter hook input priority 0; policy drop;
    ct state established,related accept
    iif lo accept
    ip protocol icmp accept
    ip6 nexthdr icmpv6 accept
    tcp dport 22 ip saddr 203.0.113.0/29 accept
    tcp dport { 80, 443 } accept
    log prefix "nft-drop " limit rate 5/minute
  }
  chain forward { type filter hook forward priority 0; policy drop; }
  chain output  { type filter hook output  priority 0; policy accept; }
}
```

Docker manipulates iptables directly and **bypasses ufw** for published ports: `-p 5432:5432` exposes the container to the world even if ufw denies 5432. Either bind published ports to localhost (`-p 127.0.0.1:5432:5432`), rely on cloud security groups, or configure Docker's `DOCKER-USER` chain. This is a frequent, nasty surprise on single-VM deployments.

## Egress control

Outbound filtering is where mature environments differentiate themselves. Options in increasing strictness: security group outbound rules (by port/destination SG), route tables that keep private subnets off the Internet entirely (with VPC endpoints for AWS services), a NAT instance or AWS Network Firewall with domain allow-lists, or an explicit forward proxy that only permits known hosts. For client systems handling sensitive data, "the database tier cannot reach the Internet" is both a strong control and a simple one to implement with route tables and security groups.

## Web application firewalls

A [[waf]] inspects HTTP requests after TLS termination and blocks patterns: SQL injection and XSS signatures, known bad bots, request floods (rate-based rules), geographic restrictions, and custom rules (block requests without a required header, or to admin paths from outside an IP set). AWS WAF attaches to ALB, CloudFront, API Gateway and AppSync; managed rule groups cover the common cases. Treat WAF as a shield that buys time and reduces noise, not as security: it can be bypassed by encoding tricks, it produces false positives (legitimate payloads containing SQL keywords), and it never fixes the underlying vulnerability. Start in count mode, review what would be blocked, then enforce.

## Debugging filtered traffic

The signature of a firewall is a **timeout**: packets dropped silently. (Some firewalls reject with RST or ICMP, giving "connection refused" or "unreachable" quickly, which is kinder to debuggers.)

```bash
# From the client side
nc -vz -w 3 10.20.128.10 5432          # times out → filtered somewhere; refused → reachable, nothing listening
# AWS: Reachability Analyzer traces a path and names the blocking SG/NACL/route
aws ec2 create-network-insights-path --source eni-app --destination eni-db --destination-port 5432 --protocol tcp
# VPC Flow Logs show REJECT records with the interface and ports
# On the host: are packets arriving at all? (if yes, the host firewall or the app is the problem)
sudo tcpdump -ni eth0 'tcp port 5432 and tcp[tcpflags] & tcp-syn != 0'
sudo nft list ruleset | grep -n 5432; sudo ufw status
sudo journalctl -k | grep 'nft-drop'    # logged drops
```

Method: confirm the destination is listening (`ss -ltn` on the target); confirm packets reach the target (`tcpdump` there); if not, walk outward: host firewall, security group of the target, NACL of the target subnet, route tables, security group outbound of the source, NACL of the source subnet. Reachability Analyzer does this walk for you in AWS.

## Red flags in a client environment

- Security group rules with `0.0.0.0/0` on 22, 3389, 3306, 5432, 6379, 27017, 9200.
- A single "default" security group used by everything, allowing all traffic within itself.
- Databases with public IPs or in public subnets "temporarily".
- Firewall exceptions documented in nobody's head but a departed contractor's.
- Docker-published ports on a public VM with only ufw for protection.
- WAF in count mode for two years.

Part XIII chapter 4 shows how to assess these without touching anything.

## Common mistakes

- Opening SSH to the world "to make deployment easier".
- Stateless NACLs without ephemeral port rules; hours lost to a one-way connection.
- Security groups by CIDR for internal tiers, breaking when IPs change.
- Allowing all traffic within the VPC CIDR, which makes lateral movement trivial after one compromise.
- Assuming ufw protects Docker-published ports.
- Treating the WAF as the security strategy.
- Not logging drops, so attacks and misconfigurations are both invisible.
