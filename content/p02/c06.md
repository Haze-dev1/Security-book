## The problem

IP delivers packets unreliably and out of order. Applications want a reliable, ordered byte stream (a file transfer, an HTTP response) or, sometimes, fast delivery of small independent messages where a lost one should simply be forgotten (a voice packet, a DNS query). TCP and UDP are the two answers, and nearly everything else is built on one of them.

## UDP: datagrams

UDP adds only ports and a checksum to IP. Each `sendto()` becomes one datagram; it may arrive, or not, in any order. No connection, no retransmission, no congestion control. Costs: none beyond IP. Used by DNS (small query, small answer; retry at the application), real-time media (a late packet is useless, so why retransmit), NTP, game state, and as the substrate for [[quic]].

For most backend engineers the operational facts about UDP are: it is stateless, so firewalls track it with timeouts (chapter 15); it is trivially spoofable, which is why it is used in amplification attacks and why your UDP services should never respond with more data than they receive to unauthenticated clients; and large UDP datagrams get fragmented at the IP layer, which is fragile across the Internet, so protocols keep them under ~1,200–1,400 bytes.

## TCP: a reliable byte stream

TCP provides: connection establishment and teardown; ordered, loss-free delivery via sequence numbers and acknowledgements; flow control so a fast sender does not overwhelm a slow receiver; congestion control so senders back off when the network is congested; and a byte stream abstraction with no message boundaries (your application must frame messages itself, which HTTP does with `Content-Length` or chunked encoding).

### Data transfer, acknowledgements and retransmission

Each byte has a sequence number. The receiver acknowledges the next byte it expects; the sender keeps unacknowledged data until acked and retransmits on a timeout or on receiving duplicate ACKs (fast retransmit). Selective acknowledgements (SACK) let the receiver report exactly which ranges arrived. A retransmission timeout stalls the stream; on a lossy link this is the "reliable connection that sometimes freezes for a second" you see on hotel Wi-Fi.

### Flow control

The receiver advertises a **window**: how many more bytes it can buffer. The sender never has more than that in flight. A slow consumer (an application that does not read from the socket) shrinks the window to zero and the sender stops. This is [[backpressure]] at the transport layer, and it is why a slow client downloading a large response ties up a server worker in blocking servers.

### Congestion control

The sender also maintains a **congestion window** estimating how much the *network* can take. It starts small (slow start: roughly 10 segments, ~14 KB) and grows per round trip until loss or delay signals congestion, then shrinks. Algorithms differ (CUBIC is the Linux default; BBR models bandwidth and delay and is often better on lossy or long paths). Two practical results:

- **Small transfers are dominated by round trips, not bandwidth.** The first 14 KB go in one RTT; a 100 KB response needs several RTTs of window growth. Keeping initial HTML and critical API responses small has outsized effect on perceived latency.
- **Loss on a long path collapses throughput.** The bandwidth-delay product and loss rate set a ceiling; a 1% loss on a 100 ms path can limit a single TCP stream to a few Mbps regardless of link speed. Chapter 18.

### Teardown

Either side sends FIN; the other acks and, when done, sends its own FIN, which is acked. The side that closed first waits in TIME-WAIT (2 × maximum segment lifetime, 60 s on Linux) so delayed packets from this connection cannot be mistaken for a new one using the same ports. A **RST** (reset) aborts a connection abruptly: sent when a segment arrives for a non-existent connection, when a process exits with unread data, or by firewalls and load balancers that want to drop you immediately. Clients see `ECONNRESET` / "connection reset by peer".

## Half-open connections and keep-alives

If a host crashes or a NAT entry expires, the other side may believe the connection is still established indefinitely; nothing in TCP detects an idle dead peer. **TCP keep-alive** sends probes after an idle period (Linux default 2 hours, far too long; set `net.ipv4.tcp_keepalive_time=60` or enable at the socket level with shorter intervals). Databases, message brokers and load balancers each have their own idle timeouts; a connection pool must either keep connections warmer than the shortest timeout in the path or validate connections before use. This is the root cause behind a large share of "first request after idle fails" bugs.

## Timeouts you must set

| Timeout | Default (often) | Set it to | Why |
|---|---|---|---|
| Connect | OS default: minutes | 1–5 s | A dropped SYN should fail fast and be retried against another target |
| Read / response | none (infinite) in many libraries | Per call: 2–30 s | An unresponsive upstream must not hold your worker forever |
| Idle (keep-alive) | Varies: ALB 60 s, Nginx 75 s, Node 5 s | Server idle > client idle | Avoid races where the server closes as the client reuses |
| Total request | none | Based on SLO | Bound the worst case end to end |

The ALB-to-backend idle timeout race is a classic: the ALB keeps connections to targets idle for 60 s by default; if the backend's keep-alive timeout is shorter (Node's historical 5 s), the backend closes just as the ALB sends a request, producing intermittent 502s. Rule: **the backend's idle timeout must exceed the load balancer's.**

## TCP versus UDP versus QUIC

| Property | TCP | UDP | QUIC (over UDP) |
|---|---|---|---|
| Connection | yes, 1 RTT | none | yes, 1 RTT including TLS (0 for resumed) |
| Reliability / order | yes, one stream | no | yes, per stream; streams independent |
| Head-of-line blocking | yes (one lost segment stalls everything) | n/a | no across streams |
| Encryption | separate (TLS) | separate | built in (TLS 1.3) |
| Middlebox friendliness | excellent | good | some networks block or throttle UDP 443 |
| Typical use | HTTP/1.1, HTTP/2, databases, SSH, SMTP | DNS, media, games | HTTP/3, some VPNs |

Choose TCP by default for anything request-response or stream-like. Choose UDP when loss is acceptable and latency is paramount, or when you are implementing a protocol with its own reliability (QUIC, WireGuard). HTTP/3 (chapter 8) gives you QUIC's benefits through the CDN or load balancer without changing your backend, which still speaks HTTP/1.1 or HTTP/2.

## Observing TCP

```bash
# Retransmissions and resets system-wide
nstat -az | grep -E 'TcpRetransSegs|TcpOutRsts|TcpExtListenOverflows|TcpExtTCPAbortOnTimeout'
# Per-connection details: RTT, congestion window, retransmits
ss -ti dst 203.0.113.7
# Watch a handshake and close live
sudo tcpdump -ni any 'tcp port 443 and (tcp[tcpflags] & (tcp-syn|tcp-fin|tcp-rst) != 0)'
# Timing of each phase of an HTTPS request
curl -o /dev/null -s -w 'dns %{time_namelookup}  tcp %{time_connect}  tls %{time_appconnect}  ttfb %{time_starttransfer}  total %{time_total}\n' https://example.com/
```

## Common mistakes

- No connect timeout on HTTP clients, so a blackholed upstream hangs workers for minutes.
- Backend keep-alive timeout shorter than the load balancer's, producing intermittent 502s.
- Database connection pools without keep-alive or validation, failing on the first request after idle through NAT or a firewall.
- Interpreting `ECONNRESET` as "the network is flaky" when a proxy or the peer process is actively rejecting (check for crashes, limits, idle timeouts).
- Sending large UDP datagrams that fragment and are dropped.
- Assuming a successful `send()` means the peer received the data; it means the kernel buffered it.

## Exercises

1. Use `tcpdump` to capture a complete `curl` to an HTTP (not HTTPS) site. Identify SYN, SYN-ACK, ACK, the request, the response, FIN/ACK exchanges. How many packets did a one-request connection take?
2. Configure a Node or Python HTTP server with a 2-second keep-alive timeout behind Nginx with a 60-second upstream keep-alive; load test with keep-alive enabled and look for 502s. Then fix the ordering.
3. Set a 1-second connect timeout in your HTTP client and point it at a blackholed address (e.g., `10.255.255.1`). Measure how long the failure takes with and without the timeout.
