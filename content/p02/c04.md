## The problem

IP addresses say *where* a packet should go. Something must decide *how* it gets there at each step, and physical networks deliver frames to hardware addresses, not IP addresses. Meanwhile, the world has far more devices than public IPv4 addresses, so most hosts use private addresses that cannot be routed on the Internet. Three mechanisms resolve this: routing tables choose the next hop, ARP finds its hardware address, and NAT bridges private and public address spaces.

## MAC addresses and the local segment

A MAC address (`3c:22:fb:ab:cd:ef`, 48 bits) identifies a network interface on its local segment: the set of hosts that can exchange Ethernet frames directly through switches without crossing a router. A subnet normally corresponds to one segment. MAC addresses are only meaningful locally; routers replace them at every hop.

Switches build a table of which MAC address is reachable through which port by watching source addresses on incoming frames, and forward frames only to the right port. A frame to an unknown MAC is flooded to all ports; a frame to the broadcast MAC `ff:ff:ff:ff:ff:ff` reaches every host on the segment.

## ARP: from IP to MAC

A host that wants to send to `10.0.1.1` on its own subnet needs that host's MAC address. It broadcasts an ARP request ("who has 10.0.1.1?"), the owner replies ("10.0.1.1 is at 3c:22:…"), and the mapping is cached for a few minutes.

```bash
ip neigh show            # the ARP cache (Linux); 'arp -a' on older systems
# 10.0.1.1 dev eth0 lladdr 0a:58:0a:00:01:01 REACHABLE
```

ARP has no authentication: any host can claim any IP (ARP spoofing), which lets an attacker on the same segment intercept traffic. This is one reason switched, segmented networks and encrypted protocols matter even internally, and why cloud providers implement their own secured equivalents rather than real ARP. IPv6 uses Neighbor Discovery (NDP) for the same purpose.

## Routing: deciding the next hop

Every host has a routing table. For each outgoing packet, the kernel finds the most specific matching route (longest prefix match) and uses it:

```bash
ip route
# default via 10.0.1.1 dev eth0 proto dhcp metric 100
# 10.0.1.0/24 dev eth0 proto kernel scope link src 10.0.1.57
# 172.17.0.0/16 dev docker0 proto kernel scope link src 172.17.0.1
```

Reading it: packets to `10.0.1.0/24` go directly out `eth0` (the destination is on-link; ARP for its MAC); packets to Docker's `172.17.0.0/16` go to the `docker0` bridge; everything else (`default`, i.e. `0.0.0.0/0`) is sent to the gateway `10.0.1.1`, whose MAC is found by ARP. A packet to `8.8.8.8` therefore gets an Ethernet header addressed to the gateway and an IP header addressed to 8.8.8.8.

Routers do the same with bigger tables. Core Internet routers hold about a million prefixes learned via BGP; your VPC router holds a handful of routes you define.

### VPC route tables

AWS exposes this directly. Each subnet is associated with one route table:

| Destination | Target | Meaning |
|---|---|---|
| `10.20.0.0/16` | local | Everything in the VPC is reachable directly (always present) |
| `0.0.0.0/0` | igw-… | Public subnet: Internet via the Internet Gateway |
| `0.0.0.0/0` | nat-… | Private subnet: outbound Internet via a NAT Gateway |
| `192.168.0.0/16` | vgw-… / tgw-… | Client office network via VPN or Transit Gateway |
| `pl-…` (S3 prefix list) | vpce-… | S3 traffic via a Gateway Endpoint, never leaving AWS |

A "public subnet" is nothing more than a subnet whose route table sends `0.0.0.0/0` to an Internet Gateway *and* whose instances have public IPs. A "private subnet" has no such route. An "isolated subnet" has no default route at all. The names are conventions; the route table is the reality.

## NAT: sharing public addresses

Network Address Translation rewrites addresses in packets as they cross a device, keeping a table to reverse the mapping on replies. The dominant form is **source NAT with port translation** (NAPT, "masquerading"): many private hosts share one public address, distinguished by translated source ports.

Where you meet NAT:

- **Home and office routers**: everyone in the building shares one or a few public IPs.
- **Carrier-grade NAT** in mobile networks: thousands of users per IP, which makes IP-based blocking and rate limiting hit innocent users.
- **AWS NAT Gateway**: lets instances in private subnets reach the Internet for updates and third-party APIs while remaining unreachable from it. It is a managed NAPT device with a fixed Elastic IP per AZ, which is also how you give a client's firewall a stable source address to allow-list.
- **Internet Gateway**: performs one-to-one NAT between an instance's private IP and its public/Elastic IP. The instance itself never sees its public address on its interface, which confuses people who look for it with `ip addr`.
- **Docker**: containers on a bridge network are NATed to the host's IP for outbound; `-p 8080:80` is inbound DNAT (port forwarding).
- **Kubernetes**: pods often egress via SNAT to the node's IP; Services implement DNAT via iptables or IPVS.

### Consequences of NAT

1. **Inbound connections to NATed hosts need explicit mappings.** This is a security feature (private subnets are unreachable by default) and a complication (webhooks to a service in a private subnet require a public entry point such as a load balancer).
2. **Protocols embedding IP addresses in payloads break** (classic FTP, SIP) and need application-layer gateways. Modern protocols avoid this.
3. **Idle connections expire** from NAT tables. Set TCP keep-alives below the NAT timeout (for AWS NAT Gateway, idle TCP connections time out after 350 seconds; the client should send keep-alives more often, e.g. every 60–300 s).
4. **Port exhaustion**: one public IP has ~64,000 ports. A NAT Gateway supports 55,000 simultaneous connections to each unique destination; an application opening many short-lived connections to one external API can exhaust them (symptom: `ErrorPortAllocation` metric, connection timeouts). Fix with connection pooling and keep-alive, or add more NAT gateways/IPs.
5. **Source identification is unreliable**: the server sees the NAT's address. For logging the real client behind *your own* proxies, use `X-Forwarded-For` or the PROXY protocol (chapter 12), and never trust those headers from arbitrary sources.

:::cost
NAT Gateways cost roughly $0.045 per hour per gateway plus $0.045 per GB processed (us-east-1 list pricing; verify current numbers). For a small deployment the hourly charge alone (~$32/month per AZ) often exceeds the compute bill, and data-heavy workloads (pulling container images, writing to S3 through NAT) add up fast. Use VPC Gateway Endpoints for S3 and DynamoDB (free), Interface Endpoints for ECR, Secrets Manager and CloudWatch when traffic volume justifies their hourly cost, and consider one NAT Gateway for non-production environments (accepting the single point of failure) instead of one per AZ. ## Putting it together on a Linux host

To see routing and NAT working locally:

```bash
# Which interface and gateway would be used for a destination?
ip route get 8.8.8.8
# 8.8.8.8 via 10.0.1.1 dev eth0 src 10.0.1.57 uid 1000

# Docker's NAT rules (iptables) on a host
sudo iptables -t nat -L POSTROUTING -n -v | head
# MASQUERADE  all  --  *  !docker0  172.17.0.0/16  0.0.0.0/0

# Your public address as seen from outside (what the NAT shows the world)
curl -s https://checkip.amazonaws.com
```

## Common mistakes

- Expecting to reach a private-subnet instance from the Internet without a load balancer or bastion.
- Looking for an EC2 instance's public IP in `ip addr` output (it is applied by the Internet Gateway, not the instance).
- Long-lived connections through NAT without keep-alives, dying mysteriously after a few minutes idle.
- Hard-coding IP-based allow-lists at a client's firewall for traffic that comes from autoscaling instances with changing IPs; route it through a NAT Gateway with an Elastic IP instead.
- Forgetting that `0.0.0.0/0 → igw` without a public IP on the instance does not provide Internet access, and that a public IP without that route does not either.
- Routing all private-subnet traffic to S3 through the NAT Gateway and paying per GB for it.
