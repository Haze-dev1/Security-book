# Network Debugging Toolkit

:::objectives
- Apply a systematic method to any "cannot connect" or "it is slow" report, from DNS to application.
- Use curl, dig, ping, traceroute/mtr, ss, nc, openssl and tcpdump with the flags that matter.
- Read the output of each tool and know what it does and does not prove.
- Debug inside containers and cloud environments where some tools are missing or some protocols blocked.
:::

:::prereq
All previous chapters in this part.
:::

## The method

Every network problem is diagnosed by the same ladder, bottom to top, stopping at the first rung that fails. Write down what each step *proved* before moving on; the most common debugging failure is skipping a step on assumption.

1. **Am I on the network?** `ip addr`, `ip route`, `ping <gateway>`, `ping 1.1.1.1`.
2. **Does the name resolve, and to what?** `dig +short name`, compare resolvers.
3. **Can I reach the host at all?** `ping` (if ICMP allowed), `mtr`.
4. **Can I open a TCP connection to the port?** `nc -vz host port`; refused versus timeout.
5. **Does TLS negotiate?** `openssl s_client -servername`.
6. **Does the application respond correctly?** `curl -v`, status, headers, body, timing.
7. **Is the server side seeing it?** `ss`, `tcpdump`, application and proxy logs on the target.
8. **Where is the time going?** `curl -w` phases, `mtr`, traces.

## The tools

### curl

The most important tool you own. Key flags:

```bash
curl -v https://api.client.com/health                 # verbose: request, response headers, TLS info
curl -sS -o /dev/null -w '%{http_code}\n' URL          # just the status code
curl -sS -D - -o /dev/null URL                         # response headers only
curl -i -X POST -H 'Content-Type: application/json' -d '{"a":1}' URL
curl --max-time 5 --connect-timeout 2 URL              # never debug without timeouts
curl -L URL                                            # follow redirects
curl --resolve api.client.com:443:10.20.64.12 https://api.client.com/   # test a specific backend with correct SNI/Host
curl -H 'Host: api.client.com' http://10.20.64.12:8000/health         # hit a backend directly behind a proxy
curl -k URL                                            # ignore cert errors: for diagnosis ONLY
curl --cacert internal-ca.pem URL                      # trust a private CA properly
curl -w '@curl-format.txt' -o /dev/null -s URL         # timing breakdown (format file with time_* variables)
curl --http2 / --http3 / --http1.1                     # force protocol versions
curl -x http://proxy:3128 URL                          # through a forward proxy (or HTTPS_PROXY env)
curl --trace-ascii - URL                               # everything on the wire, for the truly stuck
```

`--resolve` is the trick for testing a new load balancer or server before changing DNS, and for isolating "is it DNS or the server".

### dig (and alternatives)

```bash
dig +short api.client.com A; dig +short api.client.com AAAA
dig api.client.com                    # full: status, flags (aa = authoritative), TTL, resolver used
dig @1.1.1.1 api.client.com           # ask a different resolver
dig @ns-123.awsdns-45.com api.client.com   # ask the authoritative server (bypasses caches)
dig +trace api.client.com             # delegation chain
dig -x 52.95.110.1                    # reverse
# Minimal containers without dig:
getent hosts api.client.com; nslookup api.client.com; python3 -c 'import socket;print(socket.getaddrinfo("api.client.com",443))'
```

### ping and mtr / traceroute

```bash
ping -c 5 host                        # RTT and loss; ICMP may be blocked (no reply ≠ down)
traceroute -n host; tracepath host    # hops; '* * *' = hop does not reply (normal) or path blocked
mtr -rwzc 100 host                    # traceroute + ping combined, 100 cycles, report mode: shows per-hop loss and latency
```

Reading `mtr`: loss that appears at a middle hop *and persists to the destination* is real; loss only at one middle hop that disappears later is that router de-prioritising ICMP (ignore it). A latency jump between two hops that persists is the long link (an ocean, or a congested segment).

### ss (and lsof)

```bash
ss -ltnp                               # listening TCP + process
ss -lunp                               # listening UDP
ss -tan state established | wc -l      # connection count
ss -tanp '( dport = :5432 or sport = :5432 )'   # everything involving PostgreSQL
ss -tan | awk 'NR>1{print $1}' | sort | uniq -c  # state histogram: CLOSE-WAIT pile-ups = app leak
ss -ti dst 10.20.128.10                # per-connection TCP internals: rtt, cwnd, retrans
sudo lsof -i :8000                     # who owns the port (alternative view)
```

### nc (netcat) and bash's /dev/tcp

```bash
nc -vz -w 3 host 443                   # port open? (refused vs timeout is the key distinction)
nc -l 9000                             # listen: test that *inbound* reaches you (then nc host 9000 from elsewhere)
nc -u -vz host 53                      # UDP "test" (unreliable: no response ≠ closed)
printf 'GET / HTTP/1.1\r\nHost: x\r\n\r\n' | nc host 80    # raw HTTP
timeout 3 bash -c 'exec 3<>/dev/tcp/host/443' && echo open   # when nc is absent
```

### openssl s_client

```bash
openssl s_client -connect host:443 -servername host </dev/null 2>/dev/null | openssl x509 -noout -dates -subject -issuer
openssl s_client -connect host:443 -servername host -showcerts </dev/null    # chain
openssl s_client -connect host:443 -tls1_2 </dev/null; ... -tls1_3           # protocol support
openssl s_client -connect host:443 -servername host -alpn h2 </dev/null | grep ALPN   # HTTP/2 negotiated?
openssl s_client -connect host:5432 -starttls postgres </dev/null            # STARTTLS protocols (postgres, smtp, imap)
```

### tcpdump (and Wireshark)

Packet capture is the ground truth. Capture narrowly and read in Wireshark when possible.

```bash
sudo tcpdump -ni any 'host 10.20.128.10 and port 5432'               # live, numeric, all interfaces
sudo tcpdump -ni eth0 -w /tmp/cap.pcap 'tcp port 443' -c 2000         # save 2000 packets for Wireshark
sudo tcpdump -ni any 'tcp[tcpflags] & (tcp-syn|tcp-rst) != 0'          # only handshakes and resets
sudo tcpdump -ni any -A 'tcp port 8000'                                # ASCII payload (plain HTTP only)
sudo tcpdump -ni any 'icmp'                                            # unreachable messages tell you who blocked you
sudo tcpdump -ni any 'udp port 53'                                     # DNS traffic
# In a Fargate task without tcpdump: run a sidecar with tools, or use VPC Flow Logs / Traffic Mirroring
```

What capture answers: Did the SYN leave? Did a SYN-ACK come back? Did we get a RST (and from whom)? Are retransmissions happening? Is TLS failing before or after the certificate? Is the application taking long to answer after the request arrived (server latency) or is the network slow (long gaps between segments)?

### Cloud-specific

- **VPC Flow Logs**: ACCEPT/REJECT per flow with ENI, ports and bytes. The REJECT records answer "which security group or NACL is dropping this".
- **Reachability Analyzer**: static analysis of the path between two ENIs; names the blocking component.
- **ALB access logs and target health descriptions**: distinguish ALB-generated errors from target errors.
- **Route 53 Resolver query logs**: what names your VPC asked for and what it got.
- **CloudWatch metrics**: NAT `ErrorPortAllocation`, ALB `TargetConnectionErrorCount`, EC2 network allowance exceeded metrics.

## Debugging inside containers

Slim images lack most tools. Options: `docker exec` into a debug container sharing the target's network namespace (`docker run --rm -it --network container:<id> nicolaka/netshoot`), Kubernetes `kubectl debug` ephemeral containers, ECS Exec plus a toolbox sidecar, or the `/dev/tcp` and `getent` fallbacks above. Also remember: `localhost` inside a container is the container; `host.docker.internal` reaches the host on Docker Desktop; container DNS names resolve only within their network.

## Distinguishing failure types

| Observation | Means | Next step |
|---|---|---|
| `Could not resolve host` / NXDOMAIN | DNS | `dig` against authoritative; check zone and delegation |
| `Connection refused` immediately | Reached host; nothing on port | `ss -ltnp` on target; bind address; wrong port |
| `Connection timed out` | Packets dropped | Firewall/SG/NACL/route; `tcpdump` on target to see if SYNs arrive |
| `No route to host` / `Network unreachable` | Routing/ICMP unreachable | `ip route`; VPC route tables; the ICMP sender tells you where |
| `Connection reset by peer` | RST mid-connection | Process crash, idle timeout, proxy limit, load balancer draining; check both ends' logs |
| TLS: `certificate verify failed` | Cert, chain or trust store | `openssl s_client`; serve full chain; correct CA |
| TLS: `handshake failure` | Protocol/cipher mismatch | Test versions with `-tls1_2`/`-tls1_3` |
| HTTP 502 | Proxy could not get a valid upstream response | Proxy error log; upstream alive? keep-alive race? |
| HTTP 503 | No healthy upstream / overload | Target health; capacity |
| HTTP 504 | Upstream too slow | Upstream latency; timeouts |
| Slow but succeeds | Latency/throughput | `curl -w` phases; `mtr`; traces |
| Works from A, not from B | Path difference | Compare DNS answers, egress IPs, proxies, MTU |
| Connection opens, hangs on data transfer | MTU/fragmentation (VPN, tunnels) | `ping -M do -s 1472 host`; lower MTU or enable MSS clamping |

## Hygiene

- Always set timeouts in debugging commands; a hung terminal teaches nothing.
- Record commands and outputs in the incident channel as you go.
- Capture before changing anything; a fix without a diagnosis is a coin flip.
- Do not use `-k`/`verify=False` to make a problem "go away" in code; it is for one-off diagnosis.
- Remove debug sidecars and firewall exceptions you added.

## Exercises

1. Pick a public site. Run the full ladder: `dig`, `mtr`, `nc`, `openssl s_client`, `curl -v`, `curl -w` phases. Write one line stating what each step proved.
2. Break a local service in four different ways (stop it, bind to loopback behind a proxy, firewall the port, expire a self-signed certificate) and for each, record which tool and which message identified it.
3. Capture a failing connection with `tcpdump -w`, open it in Wireshark, and annotate the packet that reveals the failure.
