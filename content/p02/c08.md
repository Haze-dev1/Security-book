## The problem

HTTP began as a way to fetch hypertext documents and became the universal application protocol: APIs, mobile backends, microservice calls, webhooks, streaming. Frameworks hide most of it, which is fine until a load balancer returns 502, a proxy strips a header, a client caches a response it should not have, or performance collapses because every request opens a new connection. The engineers who can read HTTP on the wire fix those in minutes.

## Anatomy of HTTP/1.1

A request is text:

```http
POST /api/v1/orders HTTP/1.1
Host: api.client.com
Content-Type: application/json
Content-Length: 58
Authorization: Bearer eyJhbGciOi...
Accept: application/json
User-Agent: client-app/2.4.0

{"customer_id":"c_123","items":[{"sku":"A1","qty":2}]}
```

The **request line** gives the method, the path (plus query string) and the version. **Headers** are case-insensitive name-value pairs ending at a blank line. The **body** follows, with its length declared by `Content-Length` or sent in chunks with `Transfer-Encoding: chunked`. `Host` is mandatory in HTTP/1.1 and is how one IP serves many sites (virtual hosting) and how a load balancer picks a target group.

A response mirrors it:

```http
HTTP/1.1 201 Created
Content-Type: application/json; charset=utf-8
Content-Length: 142
Location: /api/v1/orders/o_789
Cache-Control: no-store
X-Request-Id: 7f3a9c2e-...
Date: Tue, 14 Mar 2026 10:21:07 GMT

{"id":"o_789","status":"pending", ...}
```

### Methods

| Method | Semantics | Safe | Idempotent | Body |
|---|---|---|---|---|
| GET | Retrieve | yes | yes | no |
| HEAD | GET without body | yes | yes | no |
| OPTIONS | Capabilities; CORS preflight | yes | yes | no |
| POST | Create or process; non-idempotent action | no | **no** | yes |
| PUT | Replace the resource at this URL | no | yes | yes |
| PATCH | Partial update | no | not by definition | yes |
| DELETE | Remove | no | yes | rarely |

"Safe" means no side effects (browsers and crawlers prefetch GETs; a GET that deletes something will be triggered by a link preview). "Idempotent" means repeating has the same result; proxies and clients may retry idempotent requests automatically after a network failure but must not retry POST. Part III chapters 2 and 3 build on this.

### Status codes

- **1xx** informational: `100 Continue`, `101 Switching Protocols` (WebSocket upgrade).
- **2xx** success: `200 OK`, `201 Created`, `202 Accepted` (queued for async processing), `204 No Content`, `206 Partial Content`.
- **3xx** redirection: `301` permanent (cached, method may change to GET), `302`/`303` temporary (use `303 See Other` after POST), `304 Not Modified` (conditional request hit), `307`/`308` temporary/permanent preserving method and body.
- **4xx** client errors: `400 Bad Request`, `401 Unauthorized` (actually "unauthenticated": missing or invalid credentials), `403 Forbidden` (authenticated but not allowed), `404 Not Found`, `405 Method Not Allowed`, `409 Conflict`, `410 Gone`, `412 Precondition Failed`, `413 Payload Too Large`, `415 Unsupported Media Type`, `422 Unprocessable Content` (valid JSON, invalid semantics), `429 Too Many Requests`.
- **5xx** server errors: `500 Internal Server Error`, `501 Not Implemented`, `502 Bad Gateway` (proxy got an invalid response or connection failure from upstream), `503 Service Unavailable` (overloaded or down; include `Retry-After`), `504 Gateway Timeout` (upstream too slow).

The 502/503/504 distinction is diagnostic gold when a load balancer is involved: 502 means the backend connection failed or returned garbage (crashed process, wrong port, backend closed idle connection); 503 from an ALB means no healthy targets; 504 means the backend accepted but did not respond within the idle timeout (slow query, deadlock).

### Persistent connections and head-of-line blocking

HTTP/1.0 opened a TCP connection per request. HTTP/1.1 made connections persistent by default (`Connection: keep-alive`), so many requests share one connection, amortising the handshake costs from chapter 6. But requests on one connection are sequential: the second cannot start until the first response completes ([[head-of-line blocking]]). Browsers open six parallel connections per host to compensate, and web performance folklore (domain sharding, sprite sheets, bundling) grew around that limit.

## HTTP/2

HTTP/2 (2015) keeps HTTP semantics (same methods, status codes, headers) and changes the wire format:

- **Binary framing** instead of text.
- **Multiplexing**: many concurrent streams over one TCP connection, interleaved; no application-level head-of-line blocking. One connection per origin.
- **Header compression (HPACK)**: repeated headers (cookies, user agent) cost a few bytes.
- **Stream prioritisation** and **server push** (push is now effectively dead; browsers removed it).
- Browsers require TLS for HTTP/2 (`h2`); the ALPN extension negotiates it during the TLS handshake.

What it means for infrastructure: a client makes one TCP+TLS connection and sends everything over it. Load balancers typically terminate HTTP/2 from clients and speak HTTP/1.1 to backends (ALB does this by default; it can also use HTTP/2 or gRPC to targets). One remaining weakness: a single lost TCP segment stalls *all* streams until retransmitted, because TCP delivers in order.

## HTTP/3

HTTP/3 runs over [[quic]] instead of TCP: UDP-based, TLS 1.3 built in, independent streams so one loss does not block others, faster connection setup (1 RTT, 0 for resumption), and connection migration (your phone switches from Wi-Fi to cellular without dropping the connection). Browsers discover it via the `Alt-Svc` header or DNS HTTPS records and try it on UDP 443.

For most backends, HTTP/3 is something the CDN or edge handles: CloudFront, Cloudflare and others terminate HTTP/3 from users and talk HTTP/1.1 or HTTP/2 to your origin. You get most of the benefit (faster, more resilient last mile) without changing your servers. Enabling it at the edge is usually a checkbox. Some corporate networks block UDP 443; clients fall back to HTTP/2 automatically.

## Headers that matter in operations

**Forwarding and identity behind proxies**: `X-Forwarded-For` (client IP chain), `X-Forwarded-Proto` (`https` when TLS was terminated upstream), `X-Forwarded-Host`, and the standard `Forwarded` header. Your application must trust these *only* from your own proxy (chapter 12), and use them for logging, rate limiting and generating absolute URLs. Getting `X-Forwarded-Proto` wrong produces redirect loops (the app thinks it is on HTTP and redirects to HTTPS, forever).

**Correlation**: `X-Request-Id` or `traceparent` (W3C Trace Context). Generate at the edge if absent; log on every hop. Part XI.

**Content**: `Content-Type` with charset; `Accept` for negotiation; `Content-Encoding: gzip`/`br` for compression (compress text, never already-compressed images; never compress responses containing secrets alongside attacker-controlled input over TLS without care, the BREACH attack).

**Size and safety**: `Content-Length` limits enforced by the proxy (`client_max_body_size` in Nginx) protect against memory exhaustion; `413` is the right answer for oversize uploads.

**Caching**: `Cache-Control` is the master switch.

| Directive | Meaning | Use for |
|---|---|---|
| `no-store` | Never cache anywhere | Authenticated API responses, anything personal |
| `no-cache` | Cache but revalidate before use | HTML shells that must be fresh but can use 304 |
| `private` | Browser only, not shared caches | Per-user responses that may be cached locally |
| `public, max-age=31536000, immutable` | Cache for a year, never revalidate | Fingerprinted static assets (`app.3f9a1c.js`) |
| `max-age=60, stale-while-revalidate=300` | Serve for 60 s, then serve stale while refreshing | Semi-static API data |
| `s-maxage=300` | Shared cache (CDN) TTL, overrides max-age there | CDN tuning |
| `Vary: Accept-Encoding, Authorization` | Cache key includes these request headers | Prevent serving one user's response to another |

Conditional requests save bandwidth: the server sends `ETag` or `Last-Modified`; the client resends with `If-None-Match` / `If-Modified-Since`; the server replies `304 Not Modified` with no body. `If-Match` with an ETag on PUT implements optimistic concurrency (Part III chapter 2).

The CDN disaster everyone eventually has: a response for an authenticated user cached at the edge and served to other users. Cause: a `Cache-Control: public` default or a CDN configured to cache everything, with a missing `Vary` or missing `private`/`no-store` on personal endpoints. Chapter 17.

## Bodies: streaming, chunked encoding, ranges

`Transfer-Encoding: chunked` lets a server send a response of unknown length piece by piece, which is how streaming responses (server-sent events, long generated reports, LLM token streams) work over HTTP/1.1. Proxies may buffer the whole response before forwarding unless told not to (`proxy_buffering off` in Nginx; ALB streams by default but has idle timeouts). `Accept-Ranges`/`Range: bytes=0-1023` enable resumable downloads and video seeking; S3 and CloudFront support them natively.

## Reading HTTP on the wire

```bash
curl -v https://api.client.com/health            # headers both ways, TLS details
curl -sI https://api.client.com/                  # HEAD: headers only
curl -s -D - -o /dev/null https://api.client.com/ # response headers, discard body
curl --http2 -v https://...; curl --http3 -v https://...   # force versions (curl must be built with support)
curl -H 'If-None-Match: "abc123"' -i https://...  # test conditional requests
# Raw HTTP/1.1 by hand (plain HTTP only)
printf 'GET /health HTTP/1.1\r\nHost: localhost\r\nConnection: close\r\n\r\n' | nc localhost 8000
```

## Common mistakes

- State-changing GET endpoints (triggered by prefetchers and link previews).
- Returning 200 with `{"error": ...}` in the body, defeating monitoring, caching and client logic.
- `401` for authorization failures and `403` for missing credentials (or 404 to hide existence, which is sometimes right, but be deliberate).
- Missing `Cache-Control: no-store` on authenticated responses that then get cached by a CDN or browser.
- Trusting `X-Forwarded-For` from any source, allowing clients to spoof their IP for rate limits and audit logs.
- Backend keep-alive timeout below the load balancer's (chapter 6), causing 502s.
- Buffering proxies breaking streaming responses; request body size limits mismatched between proxy and app.
- Redirect loops from missing `X-Forwarded-Proto` handling.

## Exercises

1. Using `curl -v`, inspect the full request and response headers for three different sites. Identify the HTTP version negotiated, the server, caching directives and any forwarding or request-ID headers.
2. Write a minimal HTTP/1.1 response by hand with `nc -l 8000` and connect a browser to it. Get it to render; then break `Content-Length` and observe what happens.
3. Put Nginx in front of a streaming endpoint (server-sent events) with default settings and observe buffering. Fix it with `proxy_buffering off` and `X-Accel-Buffering: no`.
