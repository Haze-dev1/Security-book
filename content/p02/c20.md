# What Happens When You Type a URL

:::objectives
- Narrate, in order and in detail, every system that participates in loading `https://app.client.com/orders/123`.
- Connect each step to the chapter that explains it and to the failure it can produce.
- Use this walk-through as a diagnostic map: given a symptom, name the step.
:::

:::prereq
This chapter is the capstone of Part II. It is readable on its own, but every step links back to the chapter that explains the mechanism.
:::

## The scenario

A user in Berlin on a laptop opens a browser and types `app.client.com/orders/123`, then presses Enter. The application is a React single-page app served from S3 through CloudFront, calling an API on an ALB in `eu-west-1` (Ireland), backed by FastAPI on ECS Fargate and PostgreSQL on RDS. The user has logged in before, so a session cookie exists.

The whole thing takes about 600 ms. Here is everything that happens.

    {"from":"net","to":"net","label":"cache check","title":"HTTP cache lookup","detail":"For an SPA, `/orders/123` is served by the same `index.html` as every route (CloudFront rewrites it).     {"from":"net","to":"os","label":"getaddrinfo(app.client.com)","title":"Name resolution begins","detail":"The browser's own DNS cache misses (TTL expired).     {"from":"os","to":"rec","label":"A? AAAA? app.client.com","title":"Recursive resolution","detail":"The resolver has `client.com`'s NS records cached but not this name. It asks a Route 53 authoritative server, which returns the CloudFront alias: a set of A and AAAA records for the nearest CloudFront edge (Route 53 and CloudFront choose edges by the resolver's location, or the client subnet if EDNS Client Subnet is passed). TTL 60 s. The resolver caches and replies. Total: 20–40 ms on a cold cache, under 1 ms when warm.","note":"If the registrar's NS records are wrong, the record is missing, or the resolver is broken, the user sees DNS_PROBE_FINISHED_NXDOMAIN and nothing you have built is ever contacted."}

}

## Phase 2: connecting to the edge

```flow
{
  "title": "Phase 2 — TCP, TLS and the first HTTP request to CloudFront",
  "actors": [{"id":"b","label":"Browser"},{"id":"home","label":"Home router (NAT)"},{"id":"isp","label":"ISP + transit"},{"id":"cf","label":"CloudFront edge (Frankfurt)"}],
  "steps": [
    {"from":"b","to":"home","label":"SYN → 13.224.x.x:443 (via gateway)","title":"Routing the first packet","detail":"The destination is not on the local subnet, so the laptop sends the frame to its default gateway's MAC (found via ARP, cached). The home router performs NAT: source 192.168.1.20:52113 becomes 91.64.22.10:40211 and the mapping is recorded. Chapter 4.","note":"The TCP SYN retries after 1 s, 3 s, 7 s… if nothing comes back. A firewall drop here manifests as a long hang, then ERR_CONNECTION_TIMED_OUT."},
    {"from":"home","to":"isp","label":"routed by BGP toward AWS","title":"Across the Internet","detail":"ISP routers forward by longest-prefix match toward the prefix CloudFront announces for this edge. Because CloudFront uses anycast and many edges, the packet reaches Frankfurt in about 8 ms one-way instead of Ireland in 15 or Virginia in 45. Chapter 1."},
    {"from":"isp","to":"cf","label":"SYN arrives; SYN-ACK; ACK","title":"TCP handshake (1 RTT ≈ 16 ms)","detail":"The edge's kernel completes the three-way handshake. Shield Standard's DDoS mitigation sits here, absorbing SYN floods before they reach anything you pay for. The connection is ESTABLISHED. Chapter 6.","note":"HTTP/3 clients would instead send a QUIC Initial over UDP 443 and merge this step with the next."},
    {"from":"b","to":"cf","label":"TLS ClientHello (SNI app.client.com, ALPN h2)","title":"TLS 1.3 handshake (1 RTT)","detail":"The browser offers TLS 1.3, cipher suites, an X25519 key share, SNI naming the host, and ALPN preferring h2. The edge selects the certificate for app.client.com (issued by ACM in us-east-1, auto-renewed), returns its key share, the certificate chain, a signature proving possession of the key, and Finished. The browser validates the chain to a root in its trust store, checks the SAN matches, checks dates. Chapters 9 and 10.","note":"An expired certificate, a missing intermediate, or a name mismatch stops everything here with NET::ERR_CERT_*. The browser also notes the HSTS header later to keep upgrading."},
    {"from":"b","to":"cf","label":"HTTP/2 GET /orders/123 (+ cookies, If-None-Match)","title":"The first request","detail":"Over the encrypted HTTP/2 connection, the browser sends GET /orders/123 with headers: Host (as :authority), Accept, Accept-Encoding: br, gzip, User-Agent, Cookie (the session cookie, because app.client.com set it host-only with Secure and SameSite=Lax; this is a same-site top-level navigation, so Lax permits it), and If-None-Match with the cached index.html ETag. Chapters 8 and 11.","note":"Roughly 60 ms have elapsed: DNS ~25, TCP ~16, TLS ~16, request in flight."}
  ]
}
```

## Phase 3: the edge decides

```flow
{
  "title": "Phase 3 — CloudFront behaviours, S3 origin, and the SPA shell",
  "actors": [{"id":"cf","label":"CloudFront edge"},{"id":"waf","label":"AWS WAF"},{"id":"fn","label":"CloudFront Function"},{"id":"s3","label":"S3 origin (eu-west-1)"}],
  "steps": [
    {"from":"cf","to":"waf","label":"evaluate request","title":"Web application firewall","detail":"The request passes through the WAF web ACL attached to the distribution: managed rule groups for common attacks, a rate-based rule (2,000 requests per 5 minutes per IP), and a geo rule. `/orders/123` with a normal browser signature passes. A request with `' OR 1=1` in the query would be blocked here with a 403 before touching the origin. Chapter 15.","note":"WAF false positives are a real failure mode: a legitimate search containing SQL-like text can be blocked. Count mode first, then enforce."},
    {"from":"cf","to":"fn","label":"viewer-request function","title":"SPA routing at the edge","detail":"A CloudFront Function rewrites any path without a file extension to `/index.html`, so the S3 origin is asked for the shell regardless of the client-side route. Without this, S3 would return 403/404 for `/orders/123` and users refreshing a deep link would see an error. Chapter 17."},
    {"from":"cf","to":"cf","label":"cache key: /index.html","title":"Cache lookup","detail":"The behaviour for the default path has a cache policy with a 60-second TTL and a key of path only (no cookies, no query strings; forwarding cookies for static content would destroy the hit rate and risk leaking per-user content). The edge checks: is a fresh `/index.html` present? It is (another user loaded the app 20 s ago). Cache hit.","note":"Had the app been deployed 30 s ago without invalidating `/index.html`, this user would receive the previous version for up to a minute. Fingerprinted assets make that harmless; the old shell references assets that still exist."},
    {"from":"cf","to":"s3","label":"(on a miss) GET /index.html via OAC","title":"Origin fetch, if needed","detail":"On a miss, the edge (or Origin Shield) fetches from the private S3 bucket using Origin Access Control: a signed request that the bucket policy accepts only from this distribution. The bucket itself has Block Public Access on; nobody can read it directly. S3 returns the object with its ETag and the Cache-Control header set at upload time.","dashed":true},
    {"from":"cf","to":"cf","label":"ETag matches If-None-Match","title":"304 Not Modified","detail":"The cached object's ETag matches what the browser sent, so the edge returns 304 with no body: the browser's cached index.html is still valid. Bytes saved; one round trip spent. Response headers from the response headers policy are added: Strict-Transport-Security, Content-Security-Policy, X-Content-Type-Options, Referrer-Policy. Chapters 8 and Part IV chapter 15."}
  ]
}
```

## Phase 4: the application boots in the browser

```flow
{
  "title": "Phase 4 — parsing HTML, fetching assets, running JavaScript",
  "actors": [{"id":"b","label":"Browser"},{"id":"cf","label":"CloudFront edge"}],
  "steps": [
    {"from":"b","to":"b","label":"parse index.html","title":"HTML parsing and the preload scanner","detail":"The browser parses the shell: a `<div id=root>`, a `<link rel=stylesheet href=/assets/app.8bd2.css>`, a `<script type=module src=/assets/app.3f9a.js>`, a `<link rel=preconnect href=https://api.client.com>`. The preload scanner starts fetching the CSS and JS immediately. The preconnect hint makes the browser open TCP+TLS to the API host now, in parallel, so the first API call later will not pay the handshake."},
    {"from":"b","to":"cf","label":"GET /assets/app.3f9a.js, app.8bd2.css (same h2 connection)","title":"Fingerprinted assets","detail":"Both requests multiplex over the existing HTTP/2 connection: no new handshakes. The `/assets/*` behaviour has a year-long TTL and `immutable`; the browser already has these exact files cached from a previous visit (the hashes have not changed since the last deploy), so these requests are served from the browser's disk cache without a network round trip at all. On a first visit they would be edge hits served Brotli-compressed in a few tens of milliseconds.","note":"Chapter 17: because the filename encodes the content hash, there is never a stale-asset problem and never a need to invalidate them."},
    {"from":"b","to":"b","label":"execute app.js","title":"JavaScript runs","detail":"React boots, reads the route `/orders/123`, renders a loading state, and the data layer issues `fetch('https://api.client.com/v1/orders/123', { credentials: 'include' })`. About 120 ms have elapsed since Enter.","note":"A 2 MB unsplit bundle on a slow mobile connection would spend seconds here before this fetch even starts. Chapter 18."},
    {"from":"b","to":"b","label":"CORS decision","title":"Is a preflight needed?","detail":"`app.client.com` and `api.client.com` are different origins. The request is a GET with no custom headers beyond the safelisted ones, so it is a 'simple' request: no OPTIONS preflight. The browser sends it, and will only let the JavaScript read the response if the API returns `Access-Control-Allow-Origin: https://app.client.com` and `Access-Control-Allow-Credentials: true`. A PUT with `Content-Type: application/json` would have required a preflight round trip first. Part IV chapter 14."}
  ]
}
```

## Phase 5: the API call

```flow
{
  "title": "Phase 5 — from the browser to the ALB to FastAPI to PostgreSQL and back",
  "intro": "This is the path your code lives on. Every arrow is a trust boundary and a latency contribution.",
  "actors": [{"id":"b","label":"Browser"},{"id":"alb","label":"ALB (public subnets)"},{"id":"task","label":"ECS task: FastAPI"},{"id":"redis","label":"ElastiCache Redis"},{"id":"rds","label":"RDS PostgreSQL"}],
  "steps": [
    {"from":"b","to":"alb","label":"GET /v1/orders/123 (reused TLS connection)","title":"Reaching the API","detail":"DNS for api.client.com returned a Route 53 alias to the ALB (its two or three node IPs in public subnets, one per AZ). Thanks to the preconnect, a TLS 1.3 connection to the ALB already exists; the request goes straight out. The ALB's security group allows 443 from anywhere; a Network ACL on the subnet allows it too. Chapters 7, 13, 15.","note":"The ALB terminates TLS with its ACM certificate. From here inward, the request is HTTP on the private VPC network."},
    {"from":"alb","to":"alb","label":"listener rules, target selection","title":"Load balancer logic","detail":"Listener :443 → rule `path /v1/*` → target group `api`. The ALB picks a healthy target using least-outstanding-requests across three Fargate tasks in three AZs; task 3 was marked unhealthy two minutes ago after two failed `/health/ready` checks and is excluded. The ALB adds `X-Forwarded-For: 91.64.22.10`, `X-Forwarded-Proto: https`, `X-Forwarded-Port: 443`, and `X-Amzn-Trace-Id`.","note":"If all targets were unhealthy, the ALB would fail open and the user would see a 502 or 503 within a second. If the target's keep-alive were shorter than the ALB's 60 s idle timeout, this is where intermittent 502s would be born."},
    {"from":"alb","to":"task","label":"HTTP :8000 over a kept-alive connection","title":"Into the private subnet","detail":"The ALB node opens (or reuses) a connection to task IP 10.20.80.33:8000. The task's security group allows 8000 only from the ALB's security group. The request enters Uvicorn, which hands it to FastAPI's ASGI stack. Chapters 5, 12, 15."},
    {"from":"task","to":"task","label":"middleware chain","title":"Middleware","detail":"In order: request ID middleware (reuses X-Amzn-Trace-Id as the correlation ID and binds it to the logger), proxy headers middleware (trusts X-Forwarded-* because the ALB is the only path in), CORS middleware (notes the Origin header), rate limiting (per session, Redis-backed), then authentication: the session cookie `__Host-sid` is read. Part III chapter 4."},
    {"from":"task","to":"redis","label":"GET sess:8f3c1d…","title":"Session lookup","detail":"Redis in a private data subnet returns the session JSON in under a millisecond: user_id u_42, tenant t_7, created 3 hours ago. The TTL is refreshed. If Redis were down, the application would return 503 (fail closed) rather than treating the user as anonymous. Chapter 11."},
    {"from":"task","to":"task","label":"route handler, authorization","title":"Business logic and the authorization check","detail":"The handler `get_order(order_id)` runs. Before returning anything it verifies that order 123 belongs to tenant t_7 and that user u_42 may view it. This resource-level check is the step that, when forgotten, produces IDOR data leaks. Part IV chapter 7."},
    {"from":"task","to":"rds","label":"SELECT … WHERE id=$1 AND tenant_id=$2 (pooled conn, TLS)","title":"The database query","detail":"A parameterised query goes over a connection from the application's pool (size 10 per task; 3 tasks × 10 = 30 of RDS's max_connections) to the RDS primary in a data subnet, security group allowing 5432 only from the task security group, TLS required (`sslmode=verify-full`). The query hits an index on (tenant_id, id) and returns in 1.5 ms. Part VIII.","note":"An unindexed query here, or pool exhaustion under load, is the most common source of API latency after external calls."},
    {"from":"task","to":"alb","label":"200 OK, JSON, Cache-Control: no-store","title":"Response leaves the application","detail":"The handler serialises the order to JSON (Pydantic), the response middleware adds `Cache-Control: no-store`, `Access-Control-Allow-Origin: https://app.client.com`, `Access-Control-Allow-Credentials: true`, `X-Request-Id`, and structured log line is emitted: request id, user, tenant, route, status 200, duration 6 ms. Metrics counters for the route increment. Part XI."},
    {"from":"alb","to":"b","label":"200 OK over TLS","title":"Back to the browser","detail":"The ALB forwards the response, records it in its access log (target processing time 6 ms, ALB total 8 ms), and the encrypted response crosses the Internet back to Berlin: ~20 ms. Total API call: about 45 ms. About 170 ms have elapsed since Enter; React renders the order."}
  ]
}
```

## Where the time went

| Phase | Approximate time | Dominated by |
|---|---|---|
| DNS (cold) | 25 ms | Resolver round trips |
| TCP + TLS to CloudFront | 32 ms | 2 RTTs to Frankfurt |
| Shell request (304) | 20 ms | 1 RTT |
| Assets | 0 ms | Browser cache |
| JavaScript boot | 60 ms | CPU on the laptop |
| API: network to Ireland and back | 35 ms | Distance |
| API: ALB + middleware + Redis + PostgreSQL + serialise | 8 ms | Your code (fast, indexed) |
| Render | 20 ms | Browser |
| **Total to interactive** | **~200 ms** | Mostly round trips you avoided paying twice |

Remove the preconnect and the browser cache and the total doubles. Move the API to Virginia and it doubles again. Add an N+1 query loop and the 8 ms becomes 300. That is the lesson of chapter 18 in one table.

## Exercises

1. Open your browser's developer tools, Network panel, and load an application you operate. For the document request and one API call, read the timing breakdown (queueing, DNS, connect, TLS, waiting, download) and map each to a phase above.
2. Take an application you have deployed and write its own version of this walk-through. Every place you cannot explain what happens is a gap in your understanding of your own system; note it and find the chapter.
3. Pick three rows from the diagnostic map and, in a sandbox, deliberately cause each symptom. Confirm the symptom matches and practise the diagnosis with the chapter 19 toolkit.
