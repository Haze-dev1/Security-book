# Ports, Sockets and Connections

:::objectives

- Diagnose "address already in use", ephemeral port exhaustion, and file descriptor limits.
- Configure bind addresses correctly inside containers and on servers.
:::

## The problem

An IP address identifies a host; a host runs many programs. Ports are the kernel's way of delivering a segment to the right one. Sockets are the programming interface over all of this. Nearly every "my service does not respond" or "connection refused" conversation is really about ports, bind addresses and socket states, so precision here pays off daily.

## Ports

A port is a 16-bit number (0–65535) in the TCP or UDP header. By convention:

- **0–1023**: well-known ports, require root or `CAP_NET_BIND_SERVICE` to bind on Linux. 22 SSH, 53 DNS, 80 HTTP, 443 HTTPS, 25/587 SMTP.
- **1024–49151**: registered ports. 3306 MySQL, 5432 PostgreSQL, 6379 Redis, 8080 alternative HTTP, 9090 Prometheus, 27017 MongoDB.
- **49152–65535** (Linux default `32768–60999`): [[ephemeral port|ephemeral ports]], assigned by the kernel to the client side of outgoing connections.

TCP and UDP port spaces are independent: TCP 53 and UDP 53 are different endpoints (DNS uses both).

## Sockets

A **socket** is a kernel object a program creates to communicate, referenced by a [[file descriptor]]. Servers follow the sequence `socket()` → `bind(address, port)` → `listen(backlog)` → `accept()` in a loop; clients do `socket()` → `connect(address, port)`. Each `accept()` returns a *new* socket for that one client; the listening socket keeps listening.

A TCP connection is uniquely identified by the **4-tuple** (source IP, source port, destination IP, destination port). This is why one server port can hold thousands of simultaneous connections: each has a different client IP or client port. It also bounds the number of connections between one client IP and one server port to the number of ephemeral ports (about 28,000 on default Linux), which matters for proxies and load generators.

## Bind addresses

`bind()` takes an address as well as a port. The address decides which interfaces accept connections:

- `127.0.0.1:8000`: only connections from the same host. Right for a database that only a local app uses, or a dev server. **Wrong inside a container that must be reached from outside it**, because the container's loopback is not the host's.
- `0.0.0.0:8000`: all IPv4 interfaces. Standard for a service inside a container (the container's network namespace is already the isolation boundary) and for servers behind a firewall.
- `10.0.1.57:8000`: one specific interface. Used on multi-homed hosts to listen only on the internal network.
- `[::]:8000`: all IPv6 interfaces (and usually IPv4 too, via dual-stack).

:::warning
The most common "it works locally but the container returns connection refused" bug is a server bound to `127.0.0.1` inside the container. Docker's port mapping reaches the container's `eth0`, not its loopback. Bind to `0.0.0.0` in containers.
:::

Conversely, on a bare server with a public IP, binding a database or admin interface to `0.0.0.0` without a firewall exposes it to the Internet. Many breaches (exposed Redis, MongoDB, Elasticsearch instances) were simply default binds on public hosts.

## Connection states

`ss -tan` shows every TCP socket with its state. The ones that matter:

| State | Meaning | Operational note |
|---|---|---|
| LISTEN | Waiting for connections | `ss -ltnp` lists them with the process |
| SYN-SENT / SYN-RECV | Handshake in progress | Many SYN-RECV = backlog filling or SYN flood |
| ESTABLISHED | Open connection | Count them per service for capacity |
| FIN-WAIT / CLOSE-WAIT | Closing | Many CLOSE-WAIT = *your application* is not closing sockets after the peer did (leak) |
| TIME-WAIT | Closed, waiting ~60 s to ensure stray packets die | Normal; thousands are fine; the side that closes first holds it |

```bash
ss -ltnp                                  # listening sockets with process
ss -tan state established | wc -l         # open connections
ss -tan | awk 'NR>1{print $1}' | sort | uniq -c   # count by state
ss -tn state established '( dport = :5432 )'      # connections to PostgreSQL
ss -s                                     # summary
```

## The listen backlog

Connections that have completed the handshake but not yet been `accept()`ed queue in the **backlog**. Its size is the smaller of the application's `listen()` argument and the kernel's `net.core.somaxconn` (default 4096 on modern kernels, 128 on old ones). When it overflows, new connections are dropped (clients see slow connects or timeouts, not refusals). Signs: `ss -ltn` showing `Recv-Q` near `Send-Q` on a listening socket, and `nstat -az TcpExtListenOverflows` increasing. Causes: the application is too slow to accept (event loop blocked, workers saturated). Raise the backlog as a stopgap; fix the saturation as the cure.

## "Address already in use"

`bind()` fails if another socket already holds that address:port. Causes, in order of frequency:

1. **The previous instance is still running.** `ss -ltnp | grep :8000` shows the owner; stop it properly.
2. **A connection in TIME-WAIT on that port** after a restart. Servers set `SO_REUSEADDR` so the listening socket can be rebound anyway; most frameworks do this for you.
3. **A port mapping conflict in Docker**: `-p 8000:8000` when the host's 8000 is taken. Change the host side.
4. **Two services configured with the same port** by a copy-paste error in the unit file.

## Ephemeral port exhaustion

A process making many short-lived outbound connections to the same destination (a proxy without keep-alive, a load test, an app that opens a new database connection per request) runs out of ephemeral ports when the old ones sit in TIME-WAIT. Symptoms: `connect(): Cannot assign requested address (EADDRNOTAVAIL)`, latency spikes, intermittent failures. Fixes: reuse connections (HTTP keep-alive, connection pools), widen the range (`net.ipv4.ip_local_port_range = 1024 65535`), or enable `net.ipv4.tcp_tw_reuse = 1` for outgoing connections. Through a NAT Gateway the same limit applies per destination at the gateway (chapter 4).

## File descriptor limits

Every socket is a file descriptor. The per-process limit (`ulimit -n`, often 1024 by default) caps connections; a busy proxy or WebSocket server needs tens of thousands. Set `LimitNOFILE=65536` in the systemd unit, or `ulimits` in the container spec. Symptom: `Too many open files`, `EMFILE`, accept failures under load. If raising the limit only delays the error, you have a leak: connections not closed (see CLOSE-WAIT above).

## Containers and port publishing

Inside a container the process binds `0.0.0.0:8000` in its own network namespace. `docker run -p 8080:8000` creates a DNAT rule from the host's 8080 to the container's 8000. In ECS with the `awsvpc` network mode, each task gets its own elastic network interface and IP, so the container port is reached directly on the task IP with no mapping; the ALB target group points at `task-ip:8000`. In Kubernetes, a Service maps a stable virtual IP and port to pod IPs and container ports.

Health checks follow the same rules: an ALB health check targets the task IP and the container port; it must hit a path the application serves on the interface it bound to.

## Practical commands

```bash
# Is anything listening on 8000, and who?
ss -ltnp 'sport = :8000'
# Can I connect? (from the same host, then from another host)
nc -vz localhost 8000; nc -vz 10.0.1.57 8000
# Who is connected to my service right now, by client IP?
ss -tn state established '( sport = :8000 )' | awk 'NR>1{split($4,a,":"); print a[1]}' | sort | uniq -c | sort -rn | head
# Which process owns a connection?
sudo ss -tnp | grep 5432
# Current limits for a running process
cat /proc/$(pgrep -o myapp)/limits | grep 'open files'
```

## Exercises

1. Start a Python server with `python3 -m http.server 8000 --bind 127.0.0.1` inside a container with `-p 8000:8000`. Observe the failure from the host, then fix the bind and repeat.
2. Lower `ulimit -n` to 64 for a shell, start a server in it, and open 100 connections with a loop of `nc`. Record the exact error and the `ss` state of the extra connections.
3. Use `ss -tan` while running a load test against a local service without keep-alive. Watch TIME-WAIT grow. Enable keep-alive in the load tool and compare.
