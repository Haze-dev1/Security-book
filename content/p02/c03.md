# IP Addresses, CIDR and Subnetting

:::objectives
- Read and write IPv4 and IPv6 addresses and CIDR prefixes fluently.
- Perform subnet calculations by hand and explain what network, broadcast and host ranges are.
- Design an address plan for a VPC that will not need renumbering in three years.
- Recognise the private, loopback, link-local and special ranges you will meet in production.
:::

:::prereq
Chapters 1 and 2.
:::

## The problem

Every host needs an address that routers can use to deliver packets. Addresses must be unique within the network they are routed in, allocated hierarchically so routing tables stay small, and divided into subnets that match physical or administrative boundaries. Getting the address plan wrong is one of the few infrastructure mistakes that is genuinely expensive to fix later: renumbering a VPC that peers with a client's network, or two merged companies both using `10.0.0.0/16`, costs weeks.

## IPv4 addresses

An IPv4 address is 32 bits, written as four decimal octets: `203.0.113.7`. In binary:

```
203      .0        .113      .7
11001011 .00000000 .01110001 .00000111
```

There are 2^32 ≈ 4.3 billion addresses, which ran out around 2011. The Internet still runs mostly on IPv4 thanks to [[nat]] and careful allocation.

## CIDR notation

`10.0.1.0/24` means: the first 24 bits are the **network prefix** (fixed for every address in the block); the remaining 8 bits are the **host part** (vary within the block). The block therefore contains 2^8 = 256 addresses from `10.0.1.0` to `10.0.1.255`.

The **subnet mask** is the same information as 32 bits with 1s for the prefix: /24 is `255.255.255.0`, /16 is `255.255.0.0`, /20 is `255.255.240.0`. CIDR replaced the older class A/B/C system (where /8, /16 and /24 were the only sizes) so that blocks can be any size.


Rules of thumb:

- Each step **down** in prefix length (/24 → /23) **doubles** the addresses; each step up halves them.
- /32 is a single address (used for "this one host" in firewall rules). /0 is everything (`0.0.0.0/0` means "any address", used for default routes and, dangerously, open security groups).
- The first address of a block is the **network address**; the last is the **broadcast address**; neither is assignable to a host in classic networking. AWS additionally reserves the first three usable addresses (router, DNS, future use) so a VPC subnet has 2^n − 5 usable addresses: a /24 gives 251, a /28 gives 11.

### Subnetting by hand

Split `10.0.0.0/16` (65,536 addresses) into /20 subnets (4,096 each): there are 2^(20−16) = 16 of them. The /20 boundary falls on multiples of 16 in the third octet: `10.0.0.0/20`, `10.0.16.0/20`, `10.0.32.0/20`, …, `10.0.240.0/20`.

Which /20 contains `10.0.37.200`? 37 ÷ 16 = 2 remainder 5, so it is in the third block: `10.0.32.0/20` (range 10.0.32.0 to 10.0.47.255).

Does `10.0.1.37/27` describe the network address? /27 blocks are 32 addresses, boundaries at 0, 32, 64, … in the last octet. 37 is inside `10.0.1.32/27` (32–63); so `10.0.1.37` is a host, not the network address, and the network is `10.0.1.32/27`.

Common sizes:

| Prefix | Addresses | Usable (classic) | Usable (AWS) | Typical use |
|---|---|---|---|---|
| /16 | 65,536 | 65,534 | 65,531 | A whole VPC |
| /20 | 4,096 | 4,094 | 4,091 | A large subnet (AWS default VPC subnets) |
| /24 | 256 | 254 | 251 | A typical subnet |
| /26 | 64 | 62 | 59 | Small subnet, e.g. for load balancers |
| /28 | 16 | 14 | 11 | Smallest AWS subnet; endpoints, NAT gateways |
| /32 | 1 | 1 | — | A single host in a rule |

## Special and private ranges

| Range | Name | Meaning |
|---|---|---|
| `10.0.0.0/8` | RFC 1918 private | ~16.7 M addresses for internal networks |
| `172.16.0.0/12` | RFC 1918 private | 172.16.0.0–172.31.255.255; AWS default VPC uses 172.31.0.0/16 |
| `192.168.0.0/16` | RFC 1918 private | Home and small office networks |
| `127.0.0.0/8` | Loopback | `127.0.0.1` is "this machine"; never leaves the host |
| `169.254.0.0/16` | Link-local | Self-assigned when DHCP fails; **AWS metadata service at 169.254.169.254** |
| `100.64.0.0/10` | Carrier-grade NAT | ISPs' internal space; also Tailscale |
| `0.0.0.0/0` | Default | "Any" or "all addresses" |
| `224.0.0.0/4` | Multicast | Rarely used in clouds |

Private addresses are not routed on the public Internet; a packet from `10.0.1.5` sent to the Internet must be translated to a public address (chapter 4). That is the entire reason your VPC can use `10.0.0.0/16` and so can every other customer's.

:::security
`169.254.169.254` is the EC2 instance metadata service, which returns IAM role credentials to anything on the instance that can make an HTTP request to it. Server-side request forgery attacks (Part IV chapter 12) target this address specifically. IMDSv2 (session tokens, hop limit 1) is the mitigation; enforce it on every instance.
:::

## IPv6

IPv6 addresses are 128 bits, written as eight groups of four hex digits, with leading zeros dropped and one run of zero groups collapsed to `::`:

```
2001:0db8:0000:0000:0000:0000:0000:0001
2001:db8::1
```

There are 2^128 addresses (340 undecillion); the design assumption is that every network gets a /64 (18 quintillion addresses) and every site a /56 or /48. Subnetting below /64 is unusual. Key ranges: `::1` loopback, `fe80::/10` link-local, `fc00::/7` unique local (the private analogue), `2000::/3` global unicast.

Practical realities in late 2026: most clouds support dual-stack (IPv4 and IPv6 on the same resources); some AWS services and many client corporate networks are still IPv4-only; IPv6-only VPC subnets exist and remove the NAT gateway cost for IPv6 egress. Public-facing endpoints should be dual-stack (an ALB with `dualstack` IP type) because a meaningful share of mobile users are on IPv6-first networks. Internally, IPv4 private addressing remains the default for most client environments. Design so you *can* enable IPv6 (choose dual-stack load balancers, do not hard-code `0.0.0.0/0` as the only "anywhere" in security policies; add `::/0`).

## Designing a VPC address plan

Principles:

1. **Pick a block that does not collide** with anything you might connect to: the client's office networks, their other VPCs, VPN peers, partner networks. Ask before choosing. `10.0.0.0/16` collides with everyone; `10.173.0.0/16` collides with fewer.
2. **Size for growth, then double it.** A /16 per VPC is free and gives room for many subnets. AWS allows secondary CIDRs later, but peered networks and route tables make expansion painful.
3. **Reserve space per Availability Zone and per tier**, aligned to powers of two so that summarisation works in route tables and firewall rules.
4. **Document it** in the architecture docs with a table. Future engineers will thank you.

## Addresses in practice

- **Dynamic vs static**: hosts get addresses from DHCP (in AWS, every instance gets a private IP from its subnet automatically). Public IPv4 addresses on EC2 change on stop/start unless you allocate an [[elastic ip]]. Load balancers have changing IPs behind a DNS name, which is why you point DNS at them with aliases, never with hard-coded IPs.
- **Multiple addresses per interface** are normal: loopback, link-local, one or more global.
- **Firewall rules** use CIDR. `0.0.0.0/0` on an inbound rule means the whole Internet. Restricting SSH to a client's office `/29` is the difference between a hardening item passed and a breach.
- **Rate limiting and abuse detection by IP** is weak because of NAT (a university on one IP) and mobile carriers (a user's IP changes constantly). Use it as one signal, not the signal.

## Common mistakes

- Choosing `10.0.0.0/16` or `192.168.0.0/24` for a VPC that later needs a VPN to a client office using the same range.
- Subnets too small for autoscaling (Fargate tasks and ENIs each take an IP; EKS pods take many).
- Forgetting AWS reserves five addresses per subnet; a /28 holds 11 tasks, not 14.
- Hard-coding IP addresses of cloud resources instead of DNS names.
- Opening security groups to `0.0.0.0/0` on database or SSH ports.
- Ignoring IPv6 so that a dual-stack requirement later forces a redesign.
