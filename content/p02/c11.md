## The problem

HTTP is stateless: each request stands alone. Yet applications need to know that this request comes from the same user who logged in five minutes ago. Cookies are the browser-side mechanism for carrying a small piece of state, and sessions are the server-side pattern built on top. Because cookies are attached automatically by the browser, they are also the mechanism behind cross-site request forgery and a prime target for theft via XSS. Part IV chapters 4 and 9 cover the attacks in depth; this chapter establishes how the mechanism works.

## How cookies work

A server sets a cookie with a response header; the browser stores it and attaches it to subsequent requests that match its scope.

```http
HTTP/1.1 200 OK
Set-Cookie: __Host-session=8f3c1d...; Path=/; Secure; HttpOnly; SameSite=Lax; Max-Age=86400
```

```http
GET /api/me HTTP/1.1
Host: app.client.com
Cookie: __Host-session=8f3c1d...
```

The browser decides whether to send a cookie based on the request's **host** (matching Domain), **path**, **scheme** (Secure), **cross-site context** (SameSite), and **expiry**. The server cannot see cookies that were not sent and cannot read cookies set by other sites.

## Attributes

| Attribute | Effect | Recommendation |
|---|---|---|
| `Domain=client.com` | Sent to `client.com` and all subdomains | **Omit it.** Without Domain, the cookie is host-only (sent only to the exact host that set it). Setting it widens exposure to every subdomain, including ones hosting user content or third-party tools. |
| `Path=/api` | Sent only for URLs under the path | Use `/`. Path is not a security boundary (pages on the same origin can read each other's cookies via script). |
| `Expires` / `Max-Age` | Persistent cookie; otherwise a session cookie deleted when the browser closes (often not, with session restore) | Set `Max-Age` explicitly for login sessions (hours to days) and rely on server-side expiry too. |
| `Secure` | Only sent over HTTPS | **Always.** |
| `HttpOnly` | Not accessible to JavaScript (`document.cookie`) | **Always for session cookies.** Blocks the most direct XSS theft path. |
| `SameSite=Strict` | Never sent on cross-site requests, even top-level navigation | Strongest CSRF protection; breaks "arrive from an email link and be logged in". |
| `SameSite=Lax` | Sent on top-level GET navigations from other sites; not on cross-site POSTs, iframes, fetches | **Default choice.** Good CSRF protection with normal UX. Modern browsers default to Lax when unspecified. |
| `SameSite=None` | Sent cross-site; requires `Secure` | Only for cookies that must work in third-party contexts (embedded widgets, some SSO flows). |
| `__Host-` prefix | Browser enforces: Secure, Path=/, no Domain | **Use it** for session cookies. Prevents subdomain cookie injection. |
| `__Secure-` prefix | Browser enforces Secure | Use when you need Domain set. |

A production session cookie: `Set-Cookie: __Host-sid=<random>; Path=/; Secure; HttpOnly; SameSite=Lax; Max-Age=43200`.

### Size and count limits

Browsers cap cookies around 4 KB each and a few dozen per domain, and *every* cookie is sent with *every* request to matching hosts, including static assets. A 3 KB cookie on a page with 50 asset requests costs 150 KB of upload per page view. Keep cookies small (an opaque ID), and serve static assets from a cookieless domain or a CDN path that the cookie's scope does not cover.

## Server-side sessions

The session pattern: the cookie holds an opaque, random **session ID**; the server looks it up in a store (Redis, database, in-memory for a single process) to find the user and any state.

```python
# FastAPI sketch with Redis-backed sessions
import secrets, json
from fastapi import FastAPI, Request, Response, HTTPException

SESSION_TTL = 60 * 60 * 12

async def create_session(redis, user_id: str) -> str:
    sid = secrets.token_urlsafe(32)                          # 256 bits of randomness
    await redis.set(f"sess:{sid}", json.dumps({"uid": user_id, "created": now()}), ex=SESSION_TTL)
    return sid

def set_session_cookie(resp: Response, sid: str):
    resp.set_cookie("__Host-sid", sid, max_age=SESSION_TTL, path="/", secure=True, httponly=True, samesite="lax")

async def current_user(request: Request, redis):
    sid = request.cookies.get("__Host-sid")
    data = sid and await redis.get(f"sess:{sid}")
    if not data: raise HTTPException(401)
    await redis.expire(f"sess:{sid}", SESSION_TTL)           # sliding expiry
    return json.loads(data)["uid"]
```

Properties: **revocable** (delete the key and the user is logged out everywhere); **small cookie**; **server holds the state**, so it needs a shared store once you have more than one server (sticky sessions are a fragile alternative). Requirements: IDs with at least 128 bits of entropy from a cryptographic RNG; **rotate the ID on login** (and on privilege change) to defeat session fixation; absolute and idle expiry; delete on logout; store minimal data.

## Stateless tokens

The alternative is to put signed state *in* the cookie or in an `Authorization: Bearer` header: a [[jwt]] or an encrypted, signed cookie (Rails, Django's signed cookies). The server verifies the signature and trusts the contents without a lookup. Benefits: no shared store, easy horizontal scaling, usable across services. Costs: **cannot be revoked** before expiry without reintroducing a store (a denylist), tokens grow with claims, and any bug in signature verification is catastrophic. Part IV chapter 5 covers the pitfalls.

## Cookies versus Authorization headers for SPAs

Single-page apps calling an API can store a token in JavaScript memory or localStorage and send it in the `Authorization` header, or rely on an HttpOnly cookie set by the API. Cookies are immune to theft via XSS (HttpOnly) but exposed to CSRF (mitigated by SameSite and tokens); header tokens are immune to CSRF but any XSS can steal them from storage. For a browser frontend on the same site as its API, **HttpOnly, SameSite=Lax cookies** are the safer default. For third-party or mobile clients, bearer tokens in headers. Never store long-lived tokens in localStorage.

## Cookies across subdomains and origins

- `app.client.com` and `api.client.com` are different **origins** (for the same-origin policy) but the same **site** (for SameSite). A `SameSite=Lax` cookie set by `api.client.com` without a Domain attribute is host-only: sent to api.client.com from fetches made by the page at app.client.com (same site, so SameSite permits it; `credentials: 'include'` and CORS with `Access-Control-Allow-Credentials` are required). Part IV chapter 14.
- A cookie set with `Domain=client.com` is sent to every subdomain. If any subdomain is less trusted (user-generated content, a vendor's tool, a forgotten staging host), it can read and *set* cookies for the whole domain (cookie tossing). The `__Host-` prefix defends against injected cookies.
- Public suffixes (`github.io`, `amazonaws.com`, `elb.amazonaws.com`) are on the Public Suffix List; browsers refuse Domain cookies at that level, so apps on raw load balancer hostnames cannot share cookies. Use your own domain.

## Load balancers and sessions

With server-side sessions in a shared store, any instance can serve any request: the stateless-service goal. If the store is unavailable, every user is logged out; make Redis highly available (Multi-AZ ElastiCache) or fall back gracefully. **Sticky sessions** (ALB stickiness cookies `AWSALB`/`AWSALBAPP`) route a user to the same target, which lets you keep sessions in process memory, but a deploy or scale-in logs users out and load distributes unevenly. Use stickiness as a temporary bridge for legacy apps, not a design.

## Operational considerations

- Session store sizing: sessions × size × TTL. Set TTLs; sessions without expiry fill Redis.
- Logging: never log `Cookie` or `Set-Cookie` headers in full. Redact at the proxy and in application loggers.
- Clock skew affects expiry checks on tokens; sessions in a store are immune.
- GDPR-style consent applies to non-essential cookies (analytics), not to strictly necessary session cookies, but document what you set and why.
- Rotation: when a user changes password or you detect compromise, invalidate all their sessions (store a per-user session generation number, or index sessions by user ID).

## Common mistakes

- Session cookie without `HttpOnly` or `Secure`.
- Setting `Domain=client.com` out of habit, exposing the cookie to every subdomain.
- Predictable or short session IDs; or using a database auto-increment ID.
- Not rotating the session ID at login (session fixation).
- Sessions in process memory behind a round-robin load balancer, "fixed" with stickiness.
- Huge cookies carrying serialized user objects.
- `SameSite=None` on the session cookie to make an embedded iframe work, removing CSRF protection everywhere.
- Logging cookies.
