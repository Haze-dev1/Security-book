# CDNs and Edge Networks

:::objectives
- Explain how a CDN serves content from the edge and what it can and cannot cache.
- Design cache keys, TTLs, invalidation and origin configuration so that users get fast responses and never someone else's data.
- Use CloudFront (or an equivalent) in front of static sites, APIs and media correctly.
- Recognise when a CDN is unnecessary and when it is essential.
:::

## The problem

Physics sets a floor on latency: a user in Sydney fetching from a server in Virginia waits 200 ms per round trip, and a page needs several. Meanwhile your origin serves the same static files millions of times, and a traffic spike or attack hits it directly. A Content Delivery Network places servers in hundreds of cities, answers users from the nearest one, caches what can be cached, absorbs floods, and terminates TLS close to the user so even uncacheable API calls get faster handshakes. In exchange you take on a new class of bugs: cache poisoning, stale content, and the infamous "user A sees user B's account page".

## What to cache

- **Fingerprinted static assets** (`app.3f9a1c.js`, `logo.8bd2.png`): cache forever (`max-age=31536000, immutable`). The filename changes when content changes, so invalidation is never needed. Every modern bundler does this.
- **HTML shells and unfingerprinted files** (`/index.html`): short TTL (seconds to minutes) or `no-cache` with ETag revalidation, so deploys take effect quickly.
- **Public API responses** (product catalogue, public feeds): short `s-maxage` with `stale-while-revalidate`, keyed carefully on query parameters.
- **Media and downloads**: long TTLs; range requests supported.
- **Personal or authenticated responses**: **never** at a shared cache. `Cache-Control: private, no-store`, and configure the CDN behaviour for those paths to bypass caching entirely regardless of headers.

## Cache keys and the "wrong user's data" disaster

The cache key decides which requests share a cached response. Too narrow (every header included) and nothing is ever a hit; too broad and responses leak between users. The classic incident: a CDN configured to cache based on URL only, an API endpoint `/api/account` that varies by session cookie, and a missing `no-store`. User A's account JSON is cached and served to users B through Z for the TTL.

Defences, all of them:

1. Mark personal responses `Cache-Control: private, no-store` at the application.
2. Configure CDN behaviours per path: `/api/*` with caching disabled (CloudFront "CachingDisabled" policy) and all headers, cookies and query strings forwarded.
3. Include the relevant varying inputs in the cache key for anything that is cached and varies (`Vary: Accept-Encoding`; for per-language content, the `Accept-Language` header or a path prefix). Never include cookies in the cache key for public content (it destroys the hit rate); never cache content that depends on cookies.
4. Test it: fetch an authenticated endpoint as user A, then as user B, through the CDN, and compare; check the `X-Cache`/`Age` response headers to confirm misses.

## TTLs, invalidation and deploys

Caches expire by TTL. To change content before expiry you **invalidate** (CloudFront: create an invalidation for paths; first 1,000 paths per month free, then per path) or **purge** (Cloudflare, Fastly: fast and cheap, often tag-based). Invalidation is slow (seconds to minutes) and blunt; design to need it rarely:

- Fingerprint assets so they never need invalidation.
- Give HTML a short TTL and invalidate only `/index.html` on deploy (one path).
- For APIs, prefer short TTLs plus `stale-while-revalidate` over invalidation storms.
- Version public API responses in the URL (`/v2/catalogue`) when their shape changes.

Deploy order for a static site: upload new fingerprinted assets, then upload the new `index.html` referencing them, then invalidate `/index.html` (and `/`). Never delete old assets immediately; users with the old HTML cached still need them.

## CloudFront specifics

- **Origins**: S3 (use Origin Access Control so the bucket is private and only CloudFront can read it), ALB, any custom HTTP origin, Lambda/API Gateway. Multiple origins with path-based behaviours: `/api/*` → ALB, `/*` → S3.
- **Behaviours**: per path pattern, with cache policy (what is in the key, TTLs), origin request policy (what is forwarded to origin), response headers policy (security headers added at the edge), compression, viewer protocol policy (redirect HTTP to HTTPS), allowed methods (enable PUT/POST/DELETE for API behaviours).
- **Certificates** must be in `us-east-1` (ACM) for CloudFront, regardless of origin region.
- **Edge functions**: CloudFront Functions (lightweight, viewer request/response: URL rewrites, header manipulation, redirects) and Lambda@Edge (heavier, can call origins: auth at the edge, A/B routing). Also the place to implement SPA routing (serve `/index.html` for unknown paths) and security headers.
- **WAF and Shield**: attach AWS WAF to the distribution; Shield Standard is automatic. Rate-based rules at the edge stop floods before they reach the ALB.
- **Logging**: standard logs to S3 or real-time logs to Kinesis; `x-edge-result-type` tells you hit/miss/error rates per request.
- **Cost**: data transfer out from CloudFront is cheaper than from EC2/ALB in most regions, there is a permanent free tier (1 TB/month out), and requests are billed per 10,000. For most client sites CloudFront *reduces* the bill. Verify current prices.

```yaml
# Minimal CloudFront behaviour design for a SPA + API
behaviours:
  - path: /api/*
    origin: alb
    cache_policy: CachingDisabled
    origin_request_policy: AllViewer         # forward headers, cookies, query strings
    allowed_methods: [GET, HEAD, OPTIONS, PUT, POST, PATCH, DELETE]
  - path: /assets/*
    origin: s3
    cache_policy: CachingOptimized           # long TTL, compression, key = path only
  - path: default (*)
    origin: s3
    cache_policy: custom (TTL 60s)           # index.html and friends
    function: spa-rewrite (viewer-request)  # /some/route -> /index.html
    response_headers_policy: security-headers
```

## When you need a CDN and when you do not

Need it: public-facing sites and apps with users in more than one region; heavy static or media traffic; anything that must survive traffic spikes or attacks; hosting a static frontend on S3 (CloudFront is how you get HTTPS and a custom domain there).

Do not need it: an internal tool used by 30 people in one office; a backend API consumed only by servers in the same region; a staging environment. Adding a CDN there adds a cache layer to debug and a certificate to manage without benefit.

## Debugging through a CDN

```bash
curl -sI https://cdn.client.com/app.js | grep -iE 'x-cache|age|cache-control|via|etag'
# X-Cache: Hit from cloudfront   Age: 3421
curl -sI -H 'Pragma: no-cache' ...               # some CDNs bypass on this; CloudFront does not by default
curl -sI --resolve cdn.client.com:443:<origin-ip> https://cdn.client.com/app.js   # talk to origin directly
```

Common problems: stale content after deploy (no invalidation of HTML); 403 from S3 origin (OAC/bucket policy mismatch or missing object; CloudFront caches errors too, set short error TTLs); CORS failures because the `Origin` header was not forwarded or `Vary: Origin` missing; cookies not reaching the API behind a caching behaviour; mixed-content when the origin generates `http://` links.

## Common mistakes

- Caching authenticated responses at the edge.
- Forwarding all cookies and headers to the origin for static content, so nothing caches.
- Unfingerprinted assets with long TTLs; users stuck on old JavaScript for a day.
- Deleting old assets right after deploy.
- Certificate requested in the wrong region for CloudFront.
- Long error-caching TTLs that keep serving a 500 after the origin recovered.
- Leaving S3 buckets public because CloudFront "needs" it; use Origin Access Control.
- Treating the CDN's WAF as the whole security story.

## Exercises

1. Deploy a static site to S3 behind CloudFront with Origin Access Control and HTTPS. Verify `X-Cache` headers for an asset on first and second request. Change `index.html`, observe staleness, then invalidate it.
2. Put an API behind a CloudFront behaviour with caching disabled. Prove with two different sessions that responses are not shared. Then deliberately enable caching on that behaviour in a sandbox and demonstrate the leak, so you recognise it.
3. Design the behaviours, TTLs and deploy procedure for a SPA with versioned assets, an HTML shell, a public catalogue API (cacheable 30 s) and an authenticated API.
