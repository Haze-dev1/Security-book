- Diagnose handshake failures with `openssl s_client` and read a TLS error message precisely.
:::

## The problem

Every packet between a user and your server crosses networks owned by strangers: coffee shop Wi-Fi, ISPs, exchange points, transit providers. Without protection, anyone on the path can read the traffic (passwords, tokens, personal data), modify it (inject scripts, change a payment amount) or impersonate the server. TLS solves all three for any TCP-based protocol: HTTPS is HTTP inside TLS, and the same layer protects SMTP, PostgreSQL connections, gRPC and more.

## What TLS guarantees

1. **Confidentiality**: the application data is encrypted with keys only the two endpoints know.
2. **Integrity**: any modification in transit is detected and the connection fails.
3. **Server authentication**: the client verifies it is talking to the holder of a private key that a trusted certificate authority has bound to the hostname. Optionally, **client authentication** (mTLS) verifies the client too.

What it does not do: hide *that* you are connecting, or to whom (IP addresses and, usually, the hostname via SNI are visible); protect data once decrypted at a load balancer or server; prevent attacks on the application itself; or help if the client is tricked into trusting a bad CA (corporate TLS interception, malware-installed roots).

### Why the handshake matters operationally

- **Latency**: one RTT on top of TCP's one (or one total with QUIC). For a user 100 ms away, each new HTTPS connection costs ~200 ms before the request. Connection reuse and session resumption are not optimisations; they are the difference between a snappy and a sluggish API.
- **CPU**: the asymmetric operations (key exchange, signature) cost real CPU per handshake. A server handling many short connections spends more on TLS than on HTTP. Terminating at a load balancer offloads this; keep-alive reduces it.
- **Failures are loud and specific**: a handshake error has a reason code. Learn to read it.

## TLS 1.2 and earlier

TLS 1.2 (2008) is still widely supported and acceptable with modern cipher suites (ECDHE key exchange, AES-GCM or ChaCha20). It costs two round trips and allows weak configurations if you are careless (RSA key exchange without forward secrecy, CBC ciphers vulnerable to padding oracles). TLS 1.0 and 1.1 are deprecated, broken, disabled in browsers and forbidden by PCI DSS. SSLv3 and SSLv2 are ancient history. Configure servers for TLS 1.2 and 1.3 only; use 1.3-only where every client is modern (service-to-service).

Terminating at the load balancer is the right default for web applications. Re-encrypt to backends when policy requires it. Use passthrough only when you need something the L7 path cannot provide.

## Mutual TLS

In mTLS the client also presents a certificate, and the server validates it against a CA it trusts. It authenticates *machines* strongly without passwords or tokens: service-to-service inside a mesh (Istio, Linkerd, App Mesh do this automatically), client systems calling your API from a known fleet, or devices. Costs: a private CA, certificate distribution and rotation for every client, and load balancer support (ALB supports mTLS with a trust store; NLB passthrough lets the backend do it). For human users, mTLS is rare; passkeys and SSO cover that.

## Configuring TLS well

A server configuration that passes modern scanners (Mozilla's "intermediate" profile is the usual reference):

```nginx
ssl_protocols TLSv1.2 TLSv1.3;
ssl_ciphers ECDHE-ECDSA-AES128-GCM-SHA256:ECDHE-RSA-AES128-GCM-SHA256:ECDHE-ECDSA-AES256-GCM-SHA384:ECDHE-RSA-AES256-GCM-SHA384:ECDHE-ECDSA-CHACHA20-POLY1305:ECDHE-RSA-CHACHA20-POLY1305;
ssl_prefer_server_ciphers off;          # let modern clients pick; TLS 1.3 suites are not configurable here
ssl_session_timeout 1d;
ssl_session_cache shared:SSL:10m;       # resumption: ~40k sessions
ssl_session_tickets off;                # or rotate ticket keys; static keys weaken forward secrecy
ssl_stapling on; ssl_stapling_verify on; # OCSP stapling
ssl_certificate     /etc/letsencrypt/live/api.client.com/fullchain.pem;   # leaf + intermediates
ssl_certificate_key /etc/letsencrypt/live/api.client.com/privkey.pem;
add_header Strict-Transport-Security "max-age=63072000; includeSubDomains; preload" always;
```

On an ALB, the equivalent is choosing a **security policy**: `ELBSecurityPolicy-TLS13-1-2-2021-06` (TLS 1.2 + 1.3, strong ciphers) is a good default; avoid policies allowing TLS 1.0/1.1 unless a specific legacy client forces it, and document that exception. Caddy does all of this automatically with sane defaults (chapter 12).

**HSTS** (`Strict-Transport-Security`) tells browsers to never use plain HTTP for the domain again for `max-age` seconds, defeating downgrade attacks and the one unencrypted first request. Start with a short max-age, confirm nothing breaks, then raise it; `preload` submits the domain to a browser-shipped list and is effectively irreversible.

**Redirect HTTP to HTTPS** at the load balancer or proxy with a 301, and serve HSTS on the HTTPS response. Do not serve the application over HTTP at all.

## Certificates in brief

The server's certificate binds its public key to one or more hostnames (SANs), is signed by an intermediate CA, which is signed by a root CA trusted by clients. The server must send the **full chain** (leaf plus intermediates, not the root); a missing intermediate is the most common cause of "works in Chrome, fails in curl/Python" (browsers fetch missing intermediates; libraries do not). Certificates expire (publicly trusted ones are limited to 398 days and the industry is moving toward much shorter lifetimes, which makes automation mandatory). Chapter 10 covers issuance, renewal and revocation.

## Diagnosing TLS

```bash
# Full handshake detail, with SNI; look for 'Verify return code: 0 (ok)'
openssl s_client -connect api.client.com:443 -servername api.client.com </dev/null 2>/dev/null | head -40
# Show the certificate chain and dates
openssl s_client -connect api.client.com:443 -servername api.client.com -showcerts </dev/null 2>/dev/null \
  | openssl x509 -noout -subject -issuer -dates -ext subjectAltName
# Test a specific protocol version
openssl s_client -connect host:443 -tls1_2 </dev/null; openssl s_client -connect host:443 -tls1_3 </dev/null
# What curl sees
curl -vI https://api.client.com 2>&1 | grep -E 'SSL connection|subject|issuer|expire|ALPN'
# Days until expiry (handy for monitoring scripts)
echo | openssl s_client -connect host:443 -servername host 2>/dev/null | openssl x509 -noout -enddate
```

Reading errors:

| Error | Meaning | Fix |
|---|---|---|
| `certificate has expired` | notAfter is in the past | Renew; fix the automation that should have |
| `hostname mismatch` / `ERR_CERT_COMMON_NAME_INVALID` | Requested name not in SANs | Issue a cert covering the name; check SNI is being sent |
| `unable to get local issuer certificate` | Chain incomplete or unknown CA | Serve intermediates; or install the private CA in the client |
| `self-signed certificate` | No trusted CA signed it | Use a real cert, or explicitly trust it for internal use |
| `handshake failure` / `no shared cipher` | No common protocol or cipher | Modernise one side; check TLS versions |
| `unrecognized name` | Server has no cert for the SNI name | Server config missing a vhost; wrong hostname |
| `certificate verify failed: ... CA` on a corporate network | TLS interception proxy | Add the corporate root to the client's trust store (and know that it is there) |
| `wrong version number` | Talking TLS to a plain-HTTP port or vice versa | Check the port and scheme |

## Common mistakes

- Serving only the leaf certificate without intermediates.
- Allowing TLS 1.0/1.1 "for compatibility" with no evidence any client needs it.
- Terminating TLS at the load balancer and then having the application generate `http://` links because it ignored `X-Forwarded-Proto`.
- Letting certificates expire because renewal was manual or the automation broke silently; no expiry monitoring.
- Disabling certificate verification in clients (`verify=False`, `rejectUnauthorized: false`, `-k`) to make an error go away, permanently.
- Using a wildcard certificate's private key on many loosely controlled hosts; compromise of one compromises the wildcard.
- Accepting 0-RTT data for non-idempotent requests.

## Exercises

1. Use `openssl s_client -showcerts` against a site and count the certificates in the chain. Identify the leaf's SANs, the intermediate, and verify the root is in your system trust store.
2. Run a TLS scanner (e.g., `testssl.sh`, or an online scanner against a host you own) on a server you control. Fix every item it flags.
3. Deliberately misconfigure a local Nginx with only the leaf certificate. Reproduce the "works in browser, fails in curl" behaviour, then fix it.
