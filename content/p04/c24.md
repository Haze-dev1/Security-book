# How Client Data Leaks Actually Happen

- Build the habits and automated checks that make the common leaks structurally impossible.
- Respond correctly when a leak is discovered.

## The pattern

Public breach reports and incident post-mortems repeat the same dozen stories with different logos. Almost none involve novel attacks. They involve a default left in place, a check forgotten in one endpoint, a credential in the wrong file, a copy of data in a place with no controls, or a vendor nobody reviewed. This chapter is the catalogue, each entry with how it happens, how it is found (usually by someone else), and the structural fix. Treat it as the review you run on every system before launch and every quarter after.

## 1. The public bucket

**How**: an S3 bucket (or Azure blob, GCS bucket) created with public read for a quick demo, a static site, or a CDN origin; backups, exports or user uploads land in it later; a researcher or a scanner enumerates bucket names and lists it. Variants: a presigned URL with a one-year expiry shared in a support ticket; a bucket policy allowing `s3:GetObject` to `*` on the whole bucket to fix a 403.

**Fix**: Block Public Access at the account level; CloudFront with Origin Access Control for anything served publicly; presigned URLs with minutes of validity; AWS Config rule `s3-bucket-public-read-prohibited` alerting; periodic listing of every bucket's policy. Part III chapter 9, Part VII chapter 10.

## 2. Credentials in a repository

**How**: an AWS access key, a database URL with password, a Stripe secret, or a private key committed in a config file, a notebook, a test fixture or a commit "removed later". The repository is public, or becomes public, or a contractor's laptop is stolen, or a former employee still has a clone. Automated scanners find keys on GitHub within minutes of a push and use them for crypto-mining or data theft.

**Fix**: secret scanning on every push and across history (chapter 20); pre-commit hooks; secrets manager and IAM roles so keys do not exist (chapters 17–18); treat any committed secret as compromised and rotate immediately. Review access to repositories at offboarding.

## 3. Missing authorization on one endpoint (IDOR)

**How**: `GET /api/invoices/{id}` checks login but not ownership; invoices are numbered sequentially; a user (or a scraper) iterates. Variants: the export endpoint, the PDF endpoint, the mobile API that was "internal", the GraphQL field resolver, the batch endpoint that checks only the first ID.

**Fix**: central authorization at the resource level with default deny; tenant-scoped loading; RLS; random IDs; the authorization matrix test on every route (chapters 7 and 21).

## 4. The exposed database or admin tool

**How**: MongoDB, Elasticsearch, Redis or PostgreSQL bound to `0.0.0.0` with a default or no password on a VM with a public IP, or in a public subnet with a `0.0.0.0/0` security group rule "temporarily". Internet-wide scanners find it within hours. Variants: an admin dashboard (Grafana, pgAdmin, Kibana, a Django admin) on a public URL with default credentials; a Kubernetes dashboard; a Jenkins instance.

**Fix**: private subnets for data stores; security groups referencing application groups only; no public IPs on anything but load balancers; admin tools behind SSO and VPN or identity-aware proxy; Docker port-binding discipline; Config rules on open security groups (Part II chapter 15, Part V chapter 7, Part VII chapter 6).

## 5. Logs and error trackers full of personal data

**How**: request bodies logged at INFO; exceptions carrying record contents sent to an error tracker; query strings with emails and tokens in access logs; logs shipped to a third-party tool with broad staff access and years of retention. The "leak" is often internal over-access, then an exposed logging dashboard or a vendor breach.

**Fix**: structured logging with allow-listed fields; redaction middleware; `no-store` for tokens in URLs (never put them there); retention; DPAs and access control for log vendors; PII tagging (chapters 22–23, Part XI chapter 1).

## 6. The CDN or cache serving the wrong user's page

**How**: a caching layer configured by URL only, an authenticated endpoint without `Cache-Control: no-store`, a `Vary` header missing: user B receives user A's account page. Variants: a reverse proxy cache enabled broadly; an in-process cache keyed without the tenant.

**Fix**: `private, no-store` on personal responses; CDN behaviours disabling cache for authenticated paths; cache keys including every varying dimension (Part II chapters 8 and 17, Part III chapter 8).

## 7. Backups and exports in the wrong place

**How**: nightly database dumps copied to a developer's laptop, a shared drive, an unencrypted bucket, or an FTP server set up years ago; a one-off CSV export for a client sent by email and forwarded; a staging environment seeded from production and left running with weak auth.

**Fix**: backups encrypted, in a dedicated bucket with Object Lock and restricted access, deleted on schedule; exports via short-lived presigned URLs with audit; synthetic or masked data in lower environments (Part V chapter 11, Part I chapter 11, chapter 23).

## 8. Third-party and supply chain exposure

**How**: an analytics script loaded from a compromised CDN skims form input (Magecart-style); a vendor with API access to your customer data is breached; a dependency update exfiltrates environment variables from CI; a browser extension on a staff laptop.

**Fix**: Subresource Integrity and CSP for third-party scripts; minimal, scoped vendor access with DPAs and reviews; pinned, scanned dependencies with release-age delays; OIDC instead of long-lived CI keys; inventory of every processor (chapters 15, 20, 23).

## 9. Over-privileged cloud identities

**How**: an application role with `AdministratorAccess`; a Lambda that can read every bucket; a CI user with `*`; instance metadata exposed via SSRF to a role that can read Secrets Manager wholesale. One foothold becomes the whole account.

**Fix**: least-privilege roles per workload, resource-scoped; IMDSv2; permission boundaries and SCPs; IAM Access Analyzer; GuardDuty for credential misuse (chapters 12 and 18, Part VII chapters 2 and 12).

## 10. Phished or shared human credentials

**How**: an engineer's console password without MFA phished; a shared "admin" login on a sticky note; a departed contractor's account still active; SMS MFA defeated by SIM swap.

**Fix**: SSO with phishing-resistant MFA (passkeys/security keys) for everything administrative; no shared accounts; offboarding tied to the identity provider; access reviews (chapters 6 and 8, Part VII chapter 3).

## 11. Verbose errors and debug endpoints

**How**: a stack trace with connection strings shown to users; a `/debug` or `/metrics` endpoint exposing environment variables; Spring Boot Actuator or Django debug mode in production; GraphQL introspection and verbose errors leaking schema and data.

**Fix**: production error handling that returns IDs only; debug modes off by configuration validation; metrics and admin endpoints bound internally or behind auth; scanners for known debug paths (Part III chapter 12, chapter 15).

## 12. The forgotten system

**How**: an old microservice, a demo environment, a client's previous vendor's VM, a marketing site on a legacy CMS, a dangling DNS record pointing at a released cloud resource (subdomain takeover). Nobody patches it, nobody monitors it, it still has access to something.

**Fix**: asset inventory (every domain, account, host, service, with an owner); decommissioning procedures that delete DNS records, credentials and data; periodic external attack-surface scans of all your domains (Part II chapter 7, Part XIII chapter 12).

## The afternoon audit

```checklist
# Leak-pattern audit
## Storage
- Block Public Access enabled at the account level; no bucket policy grants public read; presigned URLs expire in minutes.
- Backups encrypted, in restricted buckets with retention and Object Lock where appropriate; no copies on laptops, drives or email.
- Lower environments contain no raw production PII.
## Credentials
- Secret scanning on all repositories and history; zero findings or all rotated.
- No long-lived cloud access keys for humans; CI uses OIDC; roles are resource-scoped; IMDSv2 enforced.
- All administrative access via SSO with phishing-resistant MFA; no shared accounts; offboarding verified.
## Network
- Data stores and admin tools have no public IPs and no 0.0.0.0/0 rules; security groups reference application groups.
- Admin dashboards behind SSO and VPN/identity-aware proxy; default credentials changed.
## Application
- Authorization matrix test covers every endpoint × role × foreign resource; tenant-scoped loading and RLS in place.
- Personal responses carry no-store; CDN caching disabled for authenticated paths; cache keys include tenant.
- Debug modes off; errors return IDs only; introspection and debug endpoints disabled or protected.
- Security headers, CSP and SRI for third-party scripts.
## Data handling
- Logs, error trackers and analytics redact PII and tokens; retention set; vendors under DPA.
- Data inventory current; every processor listed and reviewed.
## Inventory
- Every domain, account, host and service has an owner; dangling DNS records removed; decommissioning procedure followed.
```

## When a leak is discovered

1. **Contain**: close the exposure (make the bucket private, revoke the credential, disable the endpoint, take the system offline if needed). Minutes matter.
2. **Preserve evidence**: snapshot logs and configurations before changing more; note times.
3. **Scope**: what data, how many subjects, what period, who accessed it (audit logs, access logs, CloudTrail, provider logs). Be precise and honest; "we cannot tell" is a finding about logging.
4. **Notify**: the client's leadership and legal/DPO immediately; regulators and subjects per their decision and the legal timelines; affected third parties.
5. **Rotate** anything that might have been exposed alongside.
6. **Remediate** the pattern, not just the instance; add the automated check that would have caught it.
7. **Postmortem** blamelessly (Part XI chapter 7); update the audit checklist above with whatever was new.

## The habit that prevents most of this

Before every launch and every quarter, run the afternoon audit with fresh eyes, preferably someone who did not build the system. Automate what can be automated (Config rules, secret scanning, the authorization test, header checks, bucket policy checks) so the audit becomes a review of alerts rather than a hunt. The patterns above are boring precisely because the fixes are known; the only question is whether anyone checked.

## Exercises

2. Automate five checklist items (bucket policies, open security groups, secret scanning, header check, authorization matrix) as CI or Config alerts.
