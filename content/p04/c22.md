# Audit Logging

:::objectives
- Distinguish audit logs from application and access logs, and know what each must record.
- Design an audit event schema and emit events for every security-relevant action.
- Store audit logs so they are tamper-evident, retained appropriately, searchable and free of secrets and excess personal data.
- Use audit logs in investigations, compliance evidence and anomaly detection.
:::

:::prereq
Chapters 3, 7 and 17; Part XI chapter 1.
:::

## The problem

When a client asks "who exported our customer list on March 3rd?", "did anyone view this patient's record?", or "when did this user gain admin rights?", application logs rarely answer. They record what the system did for debugging, at whatever level a developer chose, rotated after a week. An **audit log** answers *who did what to which resource, when, from where, and with what outcome*, for every action that matters, in a store that nobody can quietly edit. It is also what turns a suspected breach into a scoped incident instead of a worst-case assumption.

## Three kinds of logs

| Log | Purpose | Content | Retention | Access |
|---|---|---|---|---|
| **Application logs** | Debugging, operations | Errors, warnings, traces, timings | Days to weeks | Engineers |
| **Access logs** | Traffic analysis, security monitoring | Every request: IP, path, status, latency, user agent | Weeks to months | Engineers, security |
| **Audit logs** | Accountability, compliance, forensics | Security-relevant actions by identified actors | Months to years (by regulation/contract) | Restricted; append-only |

Audit events are emitted deliberately from code at the point of the action, not derived from debug logs. They can flow through the same pipeline as other logs but land in a separate, protected store.

## What to audit

Authentication: login success/failure (with method), MFA enrolment/removal, logout, password change/reset, session revocation, account lockout, recovery actions.

Authorization and identity: role or permission changes, group membership changes, API key creation/revocation, SSO configuration changes, impersonation ("log in as user") start and end.

Data access and change: create/update/delete of business records (at least for sensitive entities), **reads of sensitive records** (health, financial, PII) where regulation or the threat model demands, exports and bulk downloads, report generation, search over personal data.

Administrative and configuration: changes to settings, feature flags, integrations, webhook endpoints, billing, retention policies; deployments and infrastructure changes (from CI/CD and CloudTrail).

Security events: rate limit triggers, authorization denials, signature verification failures, suspicious patterns.

The test: if this action appeared in a breach report, would you need to know who did it?

## Event schema

```json
{
  "event_id": "01HZX…",                       // unique, for dedup and reference
  "occurred_at": "2026-03-14T10:21:07.412Z",  // UTC, from a synced clock
  "action": "order.export.requested",         // noun.verb, stable vocabulary
  "outcome": "success",                       // success | failure | denied
  "actor": {"type": "user", "id": "u_42", "tenant_id": "t_7", "roles": ["admin"], "session_id_hash": "9f3a…", "impersonated_by": null},
  "target": {"type": "export", "id": "exp_01HZX…", "tenant_id": "t_7", "count": 12840},
  "context": {"request_id": "7f3a…", "ip": "91.64.22.10", "user_agent_family": "Chrome 124", "mfa_age_s": 320, "origin": "web"},
  "changes": {"status": {"from": "pending", "to": "paid"}},   // for updates: field-level before/after, excluding secrets and large blobs
  "reason": null,                              // free text supplied by actor for sensitive manual actions (support access)
  "schema_version": 1
}
```

Design notes: actor and target carry tenant IDs so multi-tenant queries are easy; the outcome field makes denials visible (a burst of `denied` is probing); `impersonated_by` records support staff acting as users; `changes` records diffs for updates without logging entire records; hash rather than store session IDs; keep user agents coarse; never include passwords, tokens, secrets, card numbers or full documents.

## Emitting events

Emit from the service layer at the point where the action succeeds or is denied, inside the same transaction as the business change where the store is the database (so the audit row and the change commit or roll back together), or via the outbox to an external store.

```python
# audit.py
async def record(db, *, action: str, actor: Principal, target: dict, outcome: str = "success", changes: dict | None = None, reason: str | None = None):
    event = {
        "event_id": ulid(), "occurred_at": utcnow_iso(), "action": action, "outcome": outcome,
        "actor": {"type": "user", "id": actor.id, "tenant_id": actor.tenant_id, "roles": sorted(actor.roles),
                  "impersonated_by": actor.impersonated_by},
        "target": target, "context": request_context(),           # request_id, ip, ua family, mfa age
        "changes": redact(changes), "reason": reason, "schema_version": 1,
    }
    await db.execute("INSERT INTO audit_events (event_id, tenant_id, occurred_at, action, actor_id, target_type, target_id, outcome, payload) "
                     "VALUES ($1,$2,$3,$4,$5,$6,$7,$8,$9)", event["event_id"], actor.tenant_id, event["occurred_at"], action,
                     actor.id, target.get("type"), target.get("id"), outcome, json.dumps(event))
    audit_logger.info("audit", **event)                            # also to the log pipeline → immutable archive

# in the service
async def change_role(p: Principal, user_id: str, new_role: str, db):
    user = await users.get(db, p.tenant_id, user_id)
    authorize(p, Action.USER_ROLE_CHANGE, user)
    old = user.role
    async with db.transaction():
        await users.set_role(db, p.tenant_id, user_id, new_role)
        await audit.record(db, action="user.role.changed", actor=p, target={"type": "user", "id": user_id, "tenant_id": p.tenant_id},
                           changes={"role": {"from": old, "to": new_role}})
```

Make denials auditable too: the `authorize` function's denial path records `outcome: denied` (rate-limited to avoid floods, or sampled, but counted).

## Storage: tamper-evidence and retention

An audit log that administrators can edit is a story, not evidence. Properties to aim for:

- **Append-only**: the application role can `INSERT` into `audit_events` but not `UPDATE` or `DELETE` (database grants). Admins do not have write access to the audit store in normal operation.
- **Off-box copy**: ship events to a store outside the application's blast radius: CloudWatch Logs with a retention policy, then S3 with **Object Lock** (WORM) for the long-term archive; or a dedicated logging account. An attacker who compromises the application should not be able to erase their tracks.
- **Integrity**: hash chaining (each event includes the hash of the previous) or periodic signed digests (S3 Object Lock plus CloudTrail log file validation for AWS events) makes tampering detectable.
- **Retention**: by regulation and contract: often 1 year hot, 6–7 years cold for financial and health contexts; GDPR requires you not to keep personal data longer than necessary, so define retention per event type and purge on schedule (chapter 23).
- **Access control**: reading audit logs is itself a sensitive action; restrict and log it.
- **Clock discipline**: NTP everywhere; UTC; consistent timestamps across services.

## Cloud and infrastructure audit

Your application's audit log covers business actions; the platform's covers infrastructure. On AWS: **CloudTrail** for every API call (enable in all regions, log to a dedicated account bucket with Object Lock and log file validation, include data events for sensitive S3 buckets); **AWS Config** for configuration history; **VPC Flow Logs** for network; **RDS/pgAudit** for database statements where required; **SSM Session Manager** logs for shell access; **ALB access logs**. Together they answer who changed the infrastructure and who touched the data store directly.

## Using audit logs

- **Investigations**: "show every action by actor X between T1 and T2", "every access to target Y", "every export in tenant Z". Index by actor, target, action and time; keep the hot window queryable (OpenSearch, CloudWatch Logs Insights, or the database table with indexes).
- **Detection**: alerts on privilege changes outside change windows, on impersonation, on exports above a threshold, on bursts of denials, on logins from new geographies for admins, on audit pipeline failures (silence is an alert).
- **Compliance evidence**: SOC 2, ISO 27001, HIPAA and PCI all ask for audit trails of access and changes; export samples and retention proofs on request.
- **Customer-facing**: enterprise tenants want their own audit log (who in their organisation did what); expose it per tenant via API and UI, read-only.

## Privacy in audit logs

Audit logs are personal data too. Minimise: IDs rather than names and emails where possible (resolve at display time), coarse user agents, IP addresses only where justified (and consider truncation), no document contents. Define retention and honour deletion obligations where the law requires, balancing against legal-hold and integrity requirements (often: pseudonymise the actor rather than delete the event).

## Common mistakes

- Relying on debug logs rotated weekly as the audit trail.
- Audit rows writable and deletable by the application role or by admins.
- Logging secrets, tokens or full records into audit events.
- No denials recorded, so probing is invisible.
- No off-box copy; attacker deletes the evidence.
- Timestamps in local time, or servers with drifted clocks.
- Audit pipeline failures unnoticed for months.
- Reads of sensitive data not audited because "it is just a read".
