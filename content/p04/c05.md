## The problem

JWTs became popular because they look simple: a self-contained, signed blob of claims that any service can verify without a database. That same property is their weakness: a token is valid until it expires regardless of what happened to the user, and every service that verifies tokens must do so perfectly, because a single accepting bug is a universal skeleton key. Many "JWT vulnerabilities" are really library misuse and design mistakes; this chapter shows how to avoid both.

## Anatomy

A JWS compact token is `base64url(header).base64url(payload).base64url(signature)`.

```widget:jwt
{}
```

- **Header**: `{"alg": "RS256", "typ": "JWT", "kid": "2026-03-key-1"}`. The algorithm and a key identifier.
- **Payload**: claims. Registered ones: `iss` (issuer), `sub` (subject), `aud` (audience), `exp` (expiry), `nbf` (not before), `iat` (issued at), `jti` (token ID). Plus custom claims (`tenant_id`, `roles`, `scope`).
- **Signature**: over `header.payload` with the algorithm and key.

The payload is **not encrypted**; anyone can read it. JWE (encrypted JWTs) exist but are rare; assume everything in a JWT is visible to the holder and to anyone who intercepts it. Never put secrets or sensitive personal data in a JWT.

## Algorithms

- **HS256/384/512**: HMAC with a shared secret. Whoever can verify can also forge. Appropriate only when issuer and verifier are the same service (or a tightly controlled pair) and the secret is long (≥ 256 bits) and random.
- **RS256** (RSA), **ES256** (ECDSA P-256), **EdDSA** (Ed25519): asymmetric. The issuer signs with a private key; verifiers need only the public key, usually published at a JWKS URL (`/.well-known/jwks.json`). Correct for multi-service verification and for anything an identity provider issues. ES256 and EdDSA produce smaller tokens and are faster than RSA.
- **none**: unsigned. Must never be accepted.

## The classic vulnerabilities

**`alg: none`**: early libraries honoured a header saying the token was unsigned. Fix: the verifier specifies the permitted algorithms; the header is never trusted to choose.

**Algorithm confusion (RS256 → HS256)**: the verifier is configured with an RSA *public* key and a library that accepts whatever `alg` the token names. The attacker signs with HS256 using the public key (which is public) as the HMAC secret; the library "verifies" it with the same public key. Fix: same as above, pin algorithms; use library APIs that bind a key to a specific algorithm.

**Weak HMAC secrets**: `secret`, the app name, a 12-character string. Offline brute force recovers it and the attacker mints tokens. Fix: 256+ random bits from a secrets manager; prefer asymmetric.

**`kid` injection**: the key ID header used to look up a key from a path or SQL (`kid: "../../etc/passwd"`). Fix: `kid` selects from a known set only.

**Missing claim validation**: not checking `exp` (tokens never expire), `aud` (a token for service A accepted by service B), `iss` (a token from any issuer accepted), `nbf`. Fix: validate all of them explicitly.

**JWKS fetched insecurely or cached forever**: a `jku` header pointing at an attacker's key set; or key rotation breaking verification because the cache never refreshes. Fix: fetch JWKS only from the configured issuer's URL over TLS, cache with a TTL and refresh on unknown `kid`, never follow `jku`/`x5u` from the token.

**Tokens in URLs or localStorage**: logged, leaked via referrers, stolen by XSS. Fix: `Authorization` header from memory for SPAs with short lifetimes, or HttpOnly cookies.

**Unrevocable long-lived tokens**: a 24-hour token for a user who was just fired, or whose account was just compromised. Fix: short lifetimes (5–15 minutes) plus a revocable refresh mechanism.

## Verifying correctly

```python
# PyJWT with explicit algorithm pinning, JWKS, and full claim validation
import jwt
from jwt import PyJWKClient

jwks = PyJWKClient(f"{settings.issuer}/.well-known/jwks.json", cache_keys=True, lifespan=3600)

def verify_access_token(token: str) -> dict:
    signing_key = jwks.get_signing_key_from_jwt(token)          # selects by kid from the trusted JWKS only
    return jwt.decode(
        token,
        signing_key.key,
        algorithms=["RS256", "ES256"],                            # pinned; header cannot choose 'none' or HS256
        audience=settings.api_audience,                           # e.g. "https://api.client.com"
        issuer=settings.issuer,                                   # e.g. "https://auth.client.com/"
        leeway=30,                                                # seconds of clock skew tolerance
        options={"require": ["exp", "iat", "sub", "aud", "iss"]},
    )
```

```javascript
// jose (Node): same discipline
import { createRemoteJWKSet, jwtVerify } from 'jose';
const JWKS = createRemoteJWKSet(new URL(`${ISSUER}/.well-known/jwks.json`));
export async function verifyAccessToken(token) {
  const { payload } = await jwtVerify(token, JWKS, { issuer: ISSUER, audience: AUDIENCE, algorithms: ['RS256', 'ES256'], clockTolerance: 30 });
  return payload;
}
```

Then authorise using the `sub` (and tenant/scope claims) against the resource, as in chapter 3. Claims about roles are only as fresh as the token; for anything sensitive, look up current permissions.

## Issuing correctly

If your service issues tokens (an auth service, or a backend minting tokens for its own API):

- Use ES256 or RS256 with keys in a KMS or at least generated and stored in a secrets manager; publish the public keys at a JWKS endpoint with `kid`s.
- Rotate keys: publish the new key, start signing with it, keep the old one in the JWKS until all tokens signed with it have expired, then remove it.
- Set `iss`, `aud` (specific to the API), `sub` (stable user ID, not email), `exp` (short), `iat`, `jti` (unique, for denylisting if needed).
- Minimal claims: identity and coarse scope. Not the user's full profile; not roles that change often unless lifetimes are very short.
- Never issue tokens that grant more than the session that requested them.

## Revocation strategies

1. **Short lifetimes + refresh tokens**: access tokens live 5–15 minutes; a long-lived, revocable, rotating [[refresh token]] (stored server-side, hashed) mints new ones. Revoke the refresh token and the user is out within minutes. The standard design.
2. **Denylist by `jti`**: store revoked token IDs until their `exp`; check on each request. Reintroduces a lookup; fine at modest scale.
3. **Per-user generation claim**: include `gen` in the token; store the current generation per user in a cache; reject tokens with old generations. A cheap lookup that enables "log out everywhere".
4. **Accept the window**: for low-risk, read-only, short-lived tokens, accept that revocation takes effect at expiry.

If you find yourself adding a database lookup on every request to make JWTs revocable, consider whether a plain session (chapter 4) was the simpler answer all along.

## When to use JWTs

Good fits: access tokens issued by an identity provider (OIDC), consumed by APIs; service-to-service tokens with short lifetimes; signed one-time links (password reset, email verification) with `exp` and `jti`; stateless API tokens for third-party consumers at scale where a central session store is impractical.

Poor fits: browser sessions for a single application (a session cookie is simpler and revocable); long-lived tokens of any kind; tokens carrying permissions that must be revoked instantly; anything where "stateless" is the only argument.

## Storage on clients

- **SPA**: access token in memory (not localStorage), refreshed via a refresh-token flow using an HttpOnly cookie or the BFF pattern (the browser talks to a backend-for-frontend that holds tokens server-side and uses a session cookie). The BFF pattern is increasingly the recommended approach for browser apps.
- **Mobile**: secure storage (Keychain, Keystore) for refresh tokens; access tokens in memory.
- **Servers**: in memory, fetched from the token endpoint as needed; never on disk unencrypted.

## Common mistakes

- `jwt.decode(token, verify=False)` or `decode()` without the key "just to read the claims", then trusting them.
- Accepting algorithms from the header.
- HS256 with a short, guessable secret shared across environments.
- No `aud` check; tokens from a mobile app accepted by the admin API.
- Lifetimes of hours or days with no revocation.
- Roles in the token, role revoked, token still valid.
- Tokens in URLs or localStorage.
- Trusting the `email` claim as the user key instead of `sub`.
