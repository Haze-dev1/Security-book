## The problem

Authorization logic is scattered by default: an `if user.is_admin` here, a `WHERE owner_id = ?` there, a role check in a decorator somewhere else. Each new endpoint is a chance to forget one. The result is OWASP's top category, Broken Access Control, and its most frequent form, [[idor]]: a user changes an ID in a URL and reads someone else's data. The fix is structural: one policy layer, one way to ask "may this principal do this action on this resource?", applied to every request, with default deny and tests.

## Models

### Role-based access control (RBAC)

Principals have roles (`admin`, `manager`, `member`, `support`); roles have permissions (`orders:read`, `orders:cancel`, `users:invite`). Authorization asks whether any of the principal's roles grants the permission. Simple to reason about, easy to audit ("who can cancel orders?"), coarse: it cannot express "only *your* orders" without a second mechanism.

Design tips: define permissions as the vocabulary (`resource:action`), roles as bundles of permissions, and assign roles to principals *within a scope* (tenant, project): "Ana is admin of tenant 7 and member of tenant 9." Avoid role explosion by keeping roles few and permissions granular.

### Attribute-based access control (ABAC)

Rules over attributes: principal attributes (tenant, department, clearance), resource attributes (owner, tenant, status, classification), action, environment (time, IP, MFA freshness). "A member may cancel an order if the order's tenant is the member's tenant, the member owns the order, and the order's status is pending." Expressive; harder to audit ("who can do X?" requires evaluating rules over data); essential for ownership and state-based rules.

### Relationship-based access control (ReBAC)

Permissions derived from relationships in a graph: document → folder → team → user. "Anyone who is a viewer of a parent folder can view the document." Google's Zanzibar model; implemented by OpenFGA, SpiceDB, Ory Keto. Powerful for collaboration products with sharing and hierarchy; introduces a new service to run.

### In practice

Most applications need **RBAC for coarse capability plus ABAC for ownership, tenancy and state**: "Does the principal have `orders:cancel` in this tenant? Is this order in this tenant? Does the principal own it or hold a role that bypasses ownership? Is the order cancellable?" Start there; adopt ReBAC when sharing hierarchies become the product.

## A central policy layer

```python
# policy.py — one place, default deny, pure functions, exhaustively tested
from dataclasses import dataclass
from enum import Enum

class Action(str, Enum):
    ORDER_READ = "order:read"; ORDER_CANCEL = "order:cancel"; ORDER_REFUND = "order:refund"
    USER_INVITE = "user:invite"

ROLE_PERMISSIONS = {
    "owner":   {Action.ORDER_READ, Action.ORDER_CANCEL, Action.ORDER_REFUND, Action.USER_INVITE},
    "admin":   {Action.ORDER_READ, Action.ORDER_CANCEL, Action.ORDER_REFUND, Action.USER_INVITE},
    "member":  {Action.ORDER_READ, Action.ORDER_CANCEL},
    "support": {Action.ORDER_READ},
}

@dataclass(frozen=True)
class Principal:
    id: str
    tenant_id: str
    roles: frozenset[str]
    mfa_age_s: int | None

class Denied(Exception): pass

def authorize(p: Principal, action: Action, resource) -> None:
    """Raise Denied unless allowed. Resource is the loaded object (tenant-scoped)."""
    # 1. Tenant boundary: no cross-tenant access, ever.
    if getattr(resource, "tenant_id", None) != p.tenant_id:
        raise Denied("cross-tenant")
    # 2. Capability: does any role grant the action?
    if not any(action in ROLE_PERMISSIONS.get(r, set()) for r in p.roles):
        raise Denied("missing permission")
    # 3. Ownership / state rules (ABAC)
    if action is Action.ORDER_CANCEL:
        is_privileged = p.roles & {"owner", "admin"}
        if not is_privileged and resource.owner_id != p.id:
            raise Denied("not owner")
        if resource.status not in ("pending", "paid"):
            raise Denied("not cancellable")
    if action is Action.ORDER_REFUND:
        if p.mfa_age_s is None or p.mfa_age_s > 600:
            raise Denied("step-up required")
    # default: allowed only if we got here
```

```python
# usage in the service layer
async def cancel_order(p: Principal, order_id: str, db):
    order = await orders.get(db, p.tenant_id, order_id)          # tenant-scoped load; None → 404
    if order is None: raise NotFound()
    authorize(p, Action.ORDER_CANCEL, order)                       # raises Denied → 403 (or 404 if hiding existence)
    await orders.cancel(db, p.tenant_id, order_id, expected_status=order.status)
    await audit.record(p, "order.cancelled", order_id)
```

Properties of this design:

- **Default deny**: the function raises unless every check passes; adding a new action without rules denies it until rules exist.
- **Resource-aware**: ownership, tenant and state are checked against the loaded resource.
- **Centralised and pure**: no I/O inside `authorize`; trivially unit-testable with a table of (principal, action, resource, expected).
- **Separated from loading**: `orders.get` is already tenant-scoped (and RLS backs it), so cross-tenant resources are never even loaded.
- **Audit on the way out**.

For list endpoints, authorization becomes a *filter*: the query includes tenant and, for non-privileged roles, ownership predicates. Never load everything and filter in memory.

## Preventing IDOR specifically

1. Load by `(tenant_id, id)`, never by `id` alone, in every repository method.
2. Authorise against the loaded resource before returning or mutating.
3. Use unguessable IDs (UUIDv7, random slugs) so enumeration is impractical; this is defence in depth, not the control.
4. Apply the same discipline to sub-resources and indirect references: `/orders/123/invoice.pdf`, `/attachments/9f3a`, `?export_id=`, batch endpoints that take lists of IDs (check every ID), and background jobs that receive IDs.
5. Return 404 for resources outside the caller's scope when existence is sensitive; 403 when the resource is known to exist for the caller but the action is not allowed.
6. Test horizontally: for each endpoint, as user B, request user A's resource IDs.

## Scopes for API tokens

OAuth scopes and API-key scopes limit what a *credential* may do, independently of what the *user* may do. The effective permission is the intersection: a token with `orders:read` held by an admin may only read orders. Implement scopes as an additional check in the policy layer (`action in token.scopes`), and issue tokens with the minimum scopes a client needs.

## Policy engines

When rules multiply, externalising them helps:

- **Open Policy Agent (OPA)** with the Rego language: a general-purpose policy engine, used for Kubernetes admission, API authorization, infrastructure policy. Decisions via a local sidecar or library.
- **Cedar** (AWS, used by Amazon Verified Permissions): a readable policy language with formal verification properties; good for application authorization with a managed option.
- **Casbin**: library-embedded, model + policy files, many languages; good for RBAC/ABAC inside the app.
- **OpenFGA / SpiceDB**: ReBAC services for relationship-heavy products.

Benefits: policies as data, reviewable and testable separately, consistent across services. Costs: another language to learn, latency if remote, and the temptation to put resource-loading logic into the engine. For a single application with a handful of rules, a well-structured in-code policy module is usually better; adopt an engine when many services must agree or when the product's sharing model is a graph.

## Administration and audit

Expose role assignments as data with an admin UI and an API; record who changed whose roles and when; review access periodically (quarterly for enterprise clients); support "least privilege by default" on invite; and give tenants' own admins self-service so your support team is not the bottleneck (and not a privileged path into every tenant). Log every denial with principal, action and resource; spikes indicate probing.

## Common mistakes

- Authorization checks only in the UI or only by URL pattern.
- `get_by_id` without tenant scope, then checking ownership afterwards (or forgetting to).
- Batch endpoints that check the first ID only.
- Roles cached in the session and never refreshed after revocation.
- Allow-by-default: a new action nobody wrote rules for is permitted.
- Sequential IDs as the only barrier.
- Support staff with a global role that bypasses tenant boundaries silently.
- Policy spread across decorators, handlers and SQL with no single source of truth.
