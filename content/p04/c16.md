:::objectives
- Choose the right primitive for each job: hashing, HMAC, symmetric authenticated encryption, asymmetric encryption, digital signatures, key exchange, randomness.
- Use modern, misuse-resistant APIs correctly and recognise the classic misuses (ECB, reused nonces, unauthenticated encryption, non-cryptographic randomness, home-made schemes).
- Implement encryption at rest and in transit with managed services and libraries, not by hand.
- Know enough to evaluate claims, read a library's documentation critically, and avoid designing your own protocol.

## The problem

Application engineers do not need to design ciphers; they need to pick the right tool from a small kit and use it without the handful of mistakes that make strong algorithms useless. Nearly every cryptographic failure in applications is a *misuse*: AES in ECB mode, a nonce reused, encryption without authentication, `random.random()` for a token, MD5 for integrity, a secret key committed to Git, or a bespoke protocol that looked fine. This chapter is the kit and the rules of use.

## Hashes and MACs

A **hash** maps arbitrary input to a fixed digest; it is one-way and collision-resistant. Uses: content addressing (Git, Docker layers), integrity of downloads (compare against a published digest *obtained securely*), deduplication, commitment schemes. Not for passwords (chapter 8) and not for authentication: anyone can compute a hash of modified data.

A **MAC** adds a secret key: only holders of the key can produce a valid tag, so a valid tag proves both integrity and origin. HMAC-SHA256 is the standard (webhook signatures in Part III chapter 10, signed cookies, CSRF tokens). Compare tags with a constant-time function (`hmac.compare_digest`, `crypto.timingSafeEqual`); a normal `==` leaks the match position through timing.

```python
import hmac, hashlib, secrets
def sign(msg: bytes, key: bytes) -> str: return hmac.new(key, msg, hashlib.sha256).hexdigest()
def verify(msg: bytes, key: bytes, tag: str) -> bool: return hmac.compare_digest(sign(msg, key), tag)
token = secrets.token_urlsafe(32)        # 256 bits for session IDs, reset tokens, API keys
```

## Symmetric encryption

Use an **AEAD** (authenticated encryption with associated data): it encrypts *and* authenticates, so tampered ciphertext is rejected rather than decrypted into garbage or, worse, into attacker-chosen plaintext (padding oracle attacks on unauthenticated CBC are the textbook example). AES-GCM and ChaCha20-Poly1305 are the standard choices.

The critical rule: **never reuse a nonce with the same key.** AES-GCM's 96-bit nonce must be unique per encryption under a key; reuse leaks the XOR of plaintexts and breaks authentication. Use a counter you can guarantee is unique, or random nonces with a key that encrypts a bounded number of messages (keep well under 2^32 random nonces per key), or XChaCha20-Poly1305 with its 192-bit nonce where random nonces are safe at any practical scale. Rotate keys periodically regardless.

```python
# cryptography library: AES-256-GCM with random nonce and associated data
from cryptography.hazmat.primitives.ciphers.aead import AESGCM
import os
key = AESGCM.generate_key(bit_length=256)              # from KMS/secrets manager in production
def encrypt(plaintext: bytes, aad: bytes) -> bytes:
    nonce = os.urandom(12)
    return nonce + AESGCM(key).encrypt(nonce, plaintext, aad)    # store nonce alongside ciphertext
def decrypt(blob: bytes, aad: bytes) -> bytes:
    nonce, ct = blob[:12], blob[12:]
    return AESGCM(key).decrypt(nonce, ct, aad)                    # raises InvalidTag on tampering
```

**Associated data** binds context to the ciphertext without encrypting it: encrypt a user's document with `aad = user_id + document_id`, and a ciphertext moved to another record fails to decrypt. Use it.

Higher-level misuse-resistant APIs save you from these details: libsodium/PyNaCl `SecretBox`, Google Tink, or Fernet (AES-CBC+HMAC with built-in versioning; fine, if older). Prefer them over assembling primitives.

## Asymmetric cryptography

Public/private key pairs: anyone can encrypt to or verify from the public key; only the private key decrypts or signs.

- **Signatures** (Ed25519 preferred; ECDSA P-256 widely supported; RSA-PSS for compatibility): JWTs, software artifacts, webhooks where the receiver should not hold a secret capable of forging, audit log integrity. Verify with the correct public key *for that identity*, obtained from a trusted source; a signature from an unknown key proves nothing.
- **Encryption**: rarely used directly. Encrypt data with a fresh symmetric key and encrypt *that key* to the recipient's public key (hybrid encryption; libsodium's sealed box or HPKE do this correctly). RSA-OAEP if you must use RSA; never PKCS#1 v1.5 encryption padding in new code.
- **Key exchange**: X25519 ECDH; you encounter it inside TLS, SSH, WireGuard and Signal, almost never directly.

Key sizes in 2026: Ed25519/X25519 (fixed), P-256, RSA ≥ 2048 (3072 for long-lived keys). Post-quantum algorithms (ML-KEM for key exchange, ML-DSA for signatures) are being deployed in TLS hybrids and will reach application libraries; design so that algorithms can be changed (version your formats).

## Randomness

Security tokens, salts, nonces, session IDs, API keys and password reset codes must come from a **cryptographically secure** random number generator: `secrets` in Python, `crypto.randomBytes`/`crypto.randomUUID` in Node, `SecureRandom` in Java, `/dev/urandom` or `getrandom()` at the OS level. `random` (Python), `Math.random` (JS) and `java.util.Random` are predictable and have been exploited to forge tokens. Use at least 128 bits (256 for long-lived tokens). UUIDv4 from a library that uses the CSPRNG is fine as an unguessable identifier; UUIDv1/v7 contain timestamps and are not secrets.

## Encryption at rest

Managed services do this well; use them: RDS/EBS/S3 encryption with KMS keys (SSE-KMS gives per-key audit and access control), encrypted ElastiCache, encrypted backups and snapshots, encrypted EFS. This protects against disk theft, decommissioning mistakes and some misconfigured-access scenarios; it does **not** protect against an attacker with database credentials, because the database decrypts transparently for anyone who can query it.

**Application-level (field) encryption** closes that gap for the most sensitive fields (national IDs, tokens for third-party systems, health data): encrypt in the application with a data key from KMS via [[envelope encryption]], store ciphertext in the database, decrypt only when needed. Costs: you cannot index or search encrypted fields (deterministic encryption or blind indexes, HMAC of the value, allow equality lookups at the cost of revealing equality), key rotation requires re-encryption or key versioning, and bugs are harder to debug. Apply it to a short list of fields chosen in the threat model, not to everything.

## Encryption in transit

TLS everywhere (Part II chapter 9), including internal hops where policy requires; database connections with `sslmode=verify-full`; message brokers and caches with TLS enabled; SSH or SSM for administration. Certificate validation on, always. Mutual TLS where machine identity must be strong.

## Key management

Keys are the secret; algorithms are public. Chapter 17 is devoted to it. The short rules: keys in a KMS or secrets manager, never in code or config files; separate keys per purpose and environment; rotation with key versioning so old data remains decryptable; access to keys audited; the application receives keys at runtime via an authenticated path (IAM role), not via a file on disk when avoidable.

## Rules of use

1. Use a high-level, maintained library (libsodium/PyNaCl, Tink, `cryptography`, Node's `crypto` with AEAD modes, Web Crypto). Do not implement primitives.
2. Do not design protocols. Compose only in ways the library documents; when in doubt, use the library's highest-level construct.
3. Authenticate everything you encrypt (AEAD), and authenticate before you decrypt or parse.
4. Never reuse nonces; never reuse keys across purposes; never derive keys by truncating or concatenating.
5. Constant-time comparisons for secrets.
6. CSPRNG for anything an attacker must not guess.
7. Version your formats (`v1:` prefix, key ID) so algorithms and keys can rotate.
8. Keep secrets out of logs, URLs, error messages and client code.
9. Verify signatures against pinned expected keys and algorithms.
10. Have a cryptographer or a security review look at anything that goes beyond these patterns.

## Common mistakes

- AES-ECB (identical blocks produce identical ciphertext; the penguin picture) or CBC without a MAC.
- Static or reused IV/nonce.
- `random`/`Math.random` for tokens.
- MD5 or SHA-1 for signatures or integrity of security-relevant data.
- `hash(secret + data)` instead of HMAC.
- Comparing MACs with `==`.
- Using RSA to encrypt payloads directly.
- Encrypting with a key derived from a password without a KDF, or hard-coding keys.
- Believing at-rest encryption protects against SQL injection or stolen database credentials.
- Rolling a custom token format when a signed, versioned standard exists.
