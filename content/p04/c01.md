## The problem

Security failures are rarely exotic. They are an S3 bucket left public, a database with a default password reachable from the Internet, an API endpoint that forgot to check who owns the record, a dependency with a known vulnerability nobody updated, a secret in a Git repository, an admin account without MFA. Each is simple. Each happens constantly. They happen because security was treated as a layer to add rather than a set of principles applied to every decision, and because the people building the system never deliberately asked "how would I break this?"

This part teaches the mechanisms. This chapter teaches the principles that make the mechanisms coherent.

## What you are protecting: the CIA triad

- **Confidentiality**: data is readable only by those authorised. Breaches: data leaks, credential theft, exposed backups.
- **Integrity**: data and systems are modified only by those authorised, in intended ways. Breaches: tampered orders, injected code, altered logs.
- **Availability**: the system works when needed. Breaches: outages, denial of service, ransomware.

Every control serves at least one. Encryption serves confidentiality; signatures and checksums serve integrity; redundancy and rate limiting serve availability. When you evaluate a design, ask of each asset: what is the impact if this is disclosed, altered, or unavailable? That question is the seed of a threat model (chapter 2) and of every prioritisation decision afterwards.

Two more properties appear in regulated contexts: **authenticity** (we know who did it) and **non-repudiation** (they cannot deny it), both served by authentication and audit logging.

## Principles

### Least privilege

Every identity (human, service, process) gets exactly the permissions required for its function, for exactly as long as needed. A web application's database role can read and write its tables, not drop them, not read other schemas. An ECS task role can read one secret and write to one bucket prefix. A developer has read access to production logs, not to the production database. A CI pipeline can deploy to staging automatically and to production only after approval.

Why it works: the damage from any compromise is bounded by the privileges of what was compromised. An SQL injection in an application whose database role cannot read `users.password_hash` leaks far less than one whose role is the superuser.

Where it is violated most: `AdministratorAccess` on everything "to get it working", shared root database accounts, wildcard IAM policies (`"Action": "s3:*", "Resource": "*"`), containers running as root, long-lived credentials with broad scope.

### Defense in depth

Assume any single control will fail: the developer will forget the check, the firewall rule will be wrong, the library will have a bug. Layer independent controls so that a failure of one is caught by another. The database is in a private subnet *and* has a security group *and* requires TLS *and* uses least-privilege roles *and* has row-level security *and* is encrypted at rest *and* has audit logging. An attacker must defeat all of them; a mistake in one is not a breach.

Depth does not mean redundancy of the *same* control; two firewalls with the same rule set add nothing. It means different kinds of controls at different layers: network, identity, application, data, monitoring.

### Secure by default

The default configuration should be the safe one; enabling the dangerous option must be explicit and visible. New S3 buckets block public access. New endpoints require authentication unless marked public. Input models reject unknown fields. Cookies are `Secure; HttpOnly; SameSite=Lax` unless overridden. Debug modes are off. Frameworks that are secure by default (parameterised queries, auto-escaping templates) eliminate whole vulnerability classes; choosing them is a security decision.

The corollary: **make the secure path the easy path.** If obtaining a secret safely takes an afternoon of IAM wrangling and pasting it into an environment variable takes a minute, people will paste. Platform work that makes the right thing easy is some of the highest-leverage security work there is.

### Fail closed

When a security control cannot make a decision, it denies. The session store is unreachable: the request is rejected as unauthenticated, not admitted as anonymous. The authorization service times out: 503, not "allow". The signature cannot be verified because the key is missing: reject. Failing open for availability's sake turns every dependency outage into an authentication bypass.

Availability-critical paths need availability engineering (redundancy, caching of allow decisions with short TTLs), not weakened security.

### Minimise attack surface

Every open port, endpoint, dependency, feature flag, admin page, installed package and user account is a potential entry point. Remove what is not needed: no SSH on application hosts, no debug endpoints in production, no unused dependencies, no dormant accounts, no sample applications on servers. Smaller systems are easier to secure and to audit.

### Separation of duties and privilege boundaries

No single person or credential should be able to do everything. The engineer who writes code does not approve their own production deploy; the account that runs the application cannot alter audit logs; development and production are different AWS accounts. Boundaries limit both malice and accident.

### Complete mediation

Every access to every resource is checked, every time, in one place. Not "we checked at login" (privileges change); not "the UI hides the button" (the API is reachable directly); not "that endpoint is internal" (networks get crossed). Authorization lives in a layer every request passes through, and the check is at the resource level.

### Do not trust the client

Reiterated because it is violated daily: anything that runs on the user's device is under the user's control. Prices, roles, tenant IDs, validation results, hidden fields and "disabled" buttons are suggestions. The server validates, authorises and computes everything that matters.

### Keep it simple; use proven mechanisms

Security mechanisms are hard to get right; novel ones are almost always wrong. Do not write your own cryptography, session management, password hashing or token format. Use the framework's authentication, a maintained library's JWT verification, the cloud provider's KMS. Complexity hides bugs; the simplest design that meets the requirement is the most secure.

### Assume breach; detect and respond

Perfect prevention does not exist. Design so that when (not if) something is compromised, you *notice* (audit logs, anomaly alerts, integrity checks), *contain* (least privilege, segmentation, short-lived credentials that expire), and *recover* (backups, rotation procedures, incident response plans). A system that can be breached silently and permanently is worse than one that can be breached briefly and visibly.

## Thinking like an attacker

A short exercise for any design: trace the data flows, mark every trust boundary (Part I chapter 1), and at each one ask:

1. Who can send data across this boundary? Only who I expect?
2. What if the data is malformed, enormous, or malicious?
3. What if the sender lies about who they are?
4. What if the same request arrives twice, or out of order?
5. What does the receiving side have access to that the sender should not?
6. What would I see in the logs if this boundary were abused?

Then, for the most valuable assets (credentials, personal data, money), ask the attacker's favourite question: **what is the cheapest path to it?** It is usually not a zero-day in TLS. It is a leaked key in a repository, a phished admin, a misconfigured bucket, an unauthenticated internal endpoint, or an employee's laptop. Chapter 24 catalogues the real patterns.

## Security as an operational property

A system is not secure because it was built securely; it is secure because it is *operated* securely: patched, monitored, credentials rotated, access reviewed, incidents handled, backups tested. Part IV concentrates on building; Parts X, XI and XIII return to operating. For a Forward Deployed Engineer, the handover is where this becomes acute: a secure system handed to a client that cannot operate it decays into an insecure one within months. Design for the operator you are actually handing to.

## Applying the principles: a worked example

A client wants an endpoint for support staff to look up any customer's order by email address.

- **Least privilege**: a `support` role with read-only access to the order-lookup endpoint, not admin.
- **Complete mediation**: the endpoint checks the role on every call and logs who looked up whom (audit).
- **Confidentiality**: the response omits payment details the support flow does not need (data minimisation).
- **Defense in depth**: rate-limited per user (a stolen support account cannot dump the customer list), behind the identity provider's MFA, reachable only from the corporate network or VPN.
- **Secure by default**: the lookup requires an exact email match, not a wildcard search, unless explicitly expanded with approval.
- **Assume breach**: an alert fires if any support user performs more than N lookups per hour.
- **Do not trust the client**: the support UI's tenant selector is irrelevant; the server derives the tenant from the support user's assignment.

None of this is exotic; all of it is just principles applied before writing the handler.

## Exercises

1. For a system you operate, list its five most valuable assets and rate the impact of disclosure, alteration and unavailability for each. This is the first table of a threat model.
2. Audit one IAM policy, one database role and one container's user in your system against least privilege. Write down the excess privileges.
3. Find one place where your system fails open (a security decision that defaults to allow on error). Fix it or document the risk.
