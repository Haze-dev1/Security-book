## The problem

A browser runs code from many sites at once. Without rules, a script on `evil.example` could make requests to `bank.example` using the user's cookies and *read the responses*: balances, messages, anything the user can see. The **same-origin policy (SOP)** is the browser rule that prevents this. But legitimate applications need cross-origin access too: an SPA on `app.client.com` calling `api.client.com`. **CORS** (Cross-Origin Resource Sharing) is the mechanism by which a server tells browsers which origins may read its responses. Misconfigured CORS silently reopens the hole SOP closed.

## Origins

An **origin** is the triple (scheme, host, port). `https://app.client.com` and `https://api.client.com` are different origins; so are `http://app.client.com` and `https://app.client.com`; and `https://app.client.com:8443`. A **site** (for cookies' SameSite) is coarser: both `app.client.com` and `api.client.com` are the site `client.com`. Keep the two concepts separate; CORS is about origins.

## What the same-origin policy does

- Scripts can **send** requests anywhere (forms, images, scripts, fetch), but can only **read** responses from their own origin, unless the response opts in via CORS.
- Scripts cannot read another origin's DOM, cookies, or `localStorage`.
- Some cross-origin reads are allowed historically: loading images, scripts, stylesheets, iframes (you can embed, not read).

Consequence for security thinking: SOP protects **confidentiality of responses**, not **integrity of requests**. That is why CSRF exists (chapter 9) and why CORS does not prevent it.

### Simple requests

GET, HEAD and POST with only safelisted headers and a content type of `application/x-www-form-urlencoded`, `multipart/form-data` or `text/plain` are sent **without preflight** (because HTML forms could always send them). The browser then checks the response's `Access-Control-Allow-Origin` before letting the script read it. This is why a JSON API should reject non-JSON content types: a `text/plain` POST sneaks past preflight.

### The headers

| Header | Direction | Meaning |
|---|---|---|
| `Origin` | request | The requesting page's origin (set by the browser; cannot be forged by page script) |
| `Access-Control-Allow-Origin` | response | The one origin allowed to read, or `*` (never with credentials) |
| `Access-Control-Allow-Credentials: true` | response | Cookies and `Authorization` may be sent and the response read |
| `Access-Control-Allow-Methods` / `-Headers` | preflight response | What the actual request may use |
| `Access-Control-Expose-Headers` | response | Which response headers script may read beyond the safelisted few (e.g. `X-Request-Id`, `RateLimit-Remaining`) |
| `Access-Control-Max-Age` | preflight response | Cache the preflight (browsers cap at 2 hours; 600 s is typical) |
| `Vary: Origin` | response | Tell caches/CDNs the response differs per origin |

## Configuring correctly

```python
# FastAPI / Starlette
app.add_middleware(
    CORSMiddleware,
    allow_origins=["https://app.client.com", "https://admin.client.com"],   # exact origins from config; per environment
    allow_credentials=True,
    allow_methods=["GET", "POST", "PUT", "PATCH", "DELETE"],
    allow_headers=["Content-Type", "Authorization", "X-CSRF-Token", "Idempotency-Key"],
    expose_headers=["X-Request-Id", "RateLimit-Limit", "RateLimit-Remaining"],
    max_age=600,
)
```

```javascript
// Express
app.use(cors({ origin: ['https://app.client.com'], credentials: true, methods: ['GET','POST','PUT','PATCH','DELETE'],
               allowedHeaders: ['Content-Type','Authorization','X-CSRF-Token'], exposedHeaders: ['X-Request-Id'], maxAge: 600 }));
```

Rules:

- **Exact origin allow-list from configuration**, per environment. Localhost origins only in development config.
- **Never `Access-Control-Allow-Origin: *` with `Allow-Credentials: true`** (browsers refuse the combination, but some servers reflect the request origin to emulate it; see below).
- **Never reflect the `Origin` header unconditionally.** `allow_origins=["*"]` plus credentials in some middlewares becomes "echo whatever origin asked", which lets any site read authenticated responses. Validate against the list and echo only matches.
- **Beware regex and suffix matching**: `/client\.com$/` matches `evilclient.com`; `.endswith("client.com")` matches `notclient.com`. Match full origins.
- **`null` origin**: sandboxed iframes and some file:// contexts send `Origin: null`; never allow it.
- **Apply to error responses too**, or the frontend cannot read the error.
- **Preflights must not require auth** and should be cheap; answer at the edge or in middleware before authentication.
- **CDNs**: `Vary: Origin` or disable caching of CORS'd responses, or one origin's allow header gets cached and served to another.

## Public APIs

An API meant to be called from any website (a public data API with no cookies) can use `Access-Control-Allow-Origin: *` *without* credentials. Authentication then happens via an `Authorization` header the calling script sets explicitly; since no cookies are involved, there is no CSRF and nothing to leak from the user's ambient session.

## CORS and authentication designs

- **Cookie-based session across origins** (`app.client.com` → `api.client.com`): CORS with exact origins and credentials, `SameSite=Lax` cookies (same site, so they are sent), plus CSRF protection (custom header requirement or token). Works well.
- **Cookie-based across different *sites*** (`app.example` → `api.client.com`): cookies need `SameSite=None; Secure`, which removes SameSite CSRF protection and runs into third-party cookie blocking. Avoid: put the API under the same site, or use a BFF, or use header tokens.
- **Header tokens**: no cookies, CORS still needed to read responses, no CSRF, but XSS exposure of the token (chapter 10). Common for mobile and third-party clients.
- **Same origin via reverse proxy**: serve the frontend and `/api` from one origin (CloudFront behaviours or Nginx locations). Eliminates CORS entirely for first-party apps and is often the simplest, safest design.

## What CORS does not do

- Does not prevent CSRF (chapter 9).
- Does not protect non-browser clients: `curl` ignores CORS entirely. Server-side authorization is unaffected and still required.
- Does not hide the API: the request reaches the server; only the response reading is gated.
- Does not replace authentication.

## Debugging

The browser console reports `blocked by CORS policy` with the specific reason: missing header, origin mismatch, credentials with wildcard, header not allowed, preflight failed (often a 401/404 on OPTIONS, or a redirect). Reproduce with `curl -i -X OPTIONS -H 'Origin: https://app.client.com' -H 'Access-Control-Request-Method: PUT' https://api…` and inspect the response headers; then the real request with `-H 'Origin: …'`. If curl shows the right headers but the browser still fails, check error responses and CDN caching.

## Common mistakes

- Reflecting any origin with credentials.
- Wildcard with credentials via middleware shortcuts.
- Suffix or regex matching of origins.
- Allowing `null`.
- Preflight blocked by authentication or redirected to HTTPS (preflights do not follow redirects well: serve CORS on both schemes or ensure clients use HTTPS).
- Missing CORS headers on 4xx/5xx responses.
- Missing `Vary: Origin` behind a CDN.
- Treating CORS as the API's security.
