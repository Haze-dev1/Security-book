# The OWASP Top 10 Walkthrough

:::objectives
- Map each OWASP Top 10 category to the concrete vulnerabilities, code patterns and controls covered in this book.
- Use the list as a review checklist for your own applications and for client questionnaires.
- Understand what the list is (awareness and prioritisation) and what it is not (a complete standard).
:::

:::prereq
Chapters 1 to 18.

## What the list is

The [[owasp]] Top 10 is a periodically updated awareness document ranking the most impactful web application risk categories by prevalence and severity across large datasets of real applications. It is not a standard or a complete checklist (the OWASP Application Security Verification Standard, ASVS, is the checklist); it is the shared vocabulary for "the things that actually go wrong" and the list every client security questionnaire references. The 2021 edition is the most widely cited; a 2025 edition has been published with similar categories and a reshuffled order, adding emphasis on supply chain and on mishandling of exceptional conditions. The categories below use the 2021 names with notes on later changes, because the underlying weaknesses are stable and all of them map to chapters in this book.

## A01: Broken Access Control

The most common category. Users act outside their intended permissions: IDOR, missing function-level checks, privilege escalation, tenant boundary violations, CORS misconfiguration, forced browsing to admin pages, JWT or cookie tampering.

Controls: central authorization with default deny at the resource level (chapter 7), tenant-scoped loading and row-level security (Part III chapter 15), exact CORS allow-lists (chapter 14), verified sessions and tokens (chapters 4 and 5), tests for horizontal and vertical access.

Checklist: Does every endpoint that touches a resource check ownership/tenant against the verified principal? Are list endpoints filtered by scope in the query? Are there tests as another user and another tenant?

## A02: Cryptographic Failures

Sensitive data exposed because of missing or weak cryptography: plaintext transport, weak algorithms, hard-coded keys, unsalted or fast password hashes, missing at-rest encryption, poor randomness, certificates not validated.

Controls: TLS everywhere with validation (Part II chapters 9–10), Argon2id/bcrypt (chapter 8), AEAD and CSPRNG via maintained libraries (chapter 16), KMS and secrets management (chapter 17), data classification so you know what needs protecting (chapter 23).

Checklist: Is every hop encrypted and validated? Are passwords hashed with a slow algorithm? Are keys outside code? Is randomness cryptographic? Which fields need application-level encryption?

## A03: Injection

SQL, NoSQL, OS command, LDAP, XPath, template and header injection; XSS is folded into this category in 2021.

Controls: parameterised queries and allow-listed identifiers (chapter 11), argument arrays without shells and path canonicalisation (chapter 12), context-aware output encoding plus CSP (chapters 10 and 15), schema validation at the boundary (Part III chapter 2), safe deserialization and XML parsers (chapter 13).

Checklist: Grep for string-built queries, `shell=True`, `innerHTML`/`|safe`, unsafe loaders. Is SAST in CI? Are database roles least-privilege?

## A04: Insecure Design

Flaws in the design rather than the implementation: missing threat modeling, business logic abuse (unlimited coupon reuse, race conditions in transfers, password reset by guessable questions), lack of rate limits on sensitive flows, trusting the client for business rules.

Controls: threat modeling (chapter 2), explicit requirements for abuse cases, rate limiting and quotas (Part III chapter 5), idempotency and atomic operations against races (Part III chapters 3 and 13), secure defaults (chapter 1), design review (Part XII chapter 3).

Checklist: Does a threat model exist? Are abuse cases written down? Which flows have no rate limit? Where does the client compute anything that matters?

## A05: Security Misconfiguration

Default credentials, unnecessary features and ports, verbose errors, missing headers, cloud storage open to the world, outdated or absent hardening, XML external entities (merged here in 2021).

Controls: secure-by-default infrastructure as code with policy checks (Part X chapters 5–6), server and container hardening (Part V chapter 4, Part VI chapter 7), security headers (chapter 15), error handling that hides internals (Part III chapter 12), AWS Config and Security Hub baselines (Part VII chapter 12), disabling DTDs (chapter 13).

Checklist: Any public buckets or 0.0.0.0/0 on non-web ports? Debug modes off? Headers present? Defaults changed? Config drift detected?

## A06: Vulnerable and Outdated Components

Known-vulnerable libraries, frameworks, base images and runtimes; unknown inventory; no patch process.

Controls: lockfiles and reproducible builds (Part I chapter 9), dependency and image scanning with SBOMs (chapter 20), automated update PRs, base image refresh cadence, runtime patching (Part V chapter 12).

Checklist: Is there an inventory (SBOM)? Does CI fail on critical CVEs? When was the base image last rebuilt? Who owns updates?

## A07: Identification and Authentication Failures

Credential stuffing, weak passwords, missing MFA, session fixation, sessions that never expire, tokens in URLs, insecure recovery.

Controls: chapters 3, 4, 5, 6 and 8 in full: rate limits, breached-password checks, MFA with phishing-resistant options, session rotation and expiry, federation for enterprise users, recovery flows designed as alternative logins.

Checklist: Is MFA available and enforced for admins? Is login rate-limited per account and IP? Does the session rotate at login and die at logout? Is recovery as strong as login?

## A08: Software and Data Integrity Failures

Trusting updates, plugins, CI pipelines and serialized data without integrity verification; insecure deserialization (merged here); compromised dependencies; unsigned artifacts; pipelines that can be modified by untrusted PRs.

Controls: safe deserialization (chapter 13), signed and pinned dependencies and provenance (chapter 20), protected branches and reviewed pipeline changes (Part X chapters 2 and 9), signed container images and artifacts, integrity checks on downloaded resources (Subresource Integrity for CDN scripts).

Checklist: What enters production without a signature or hash check? Can an unreviewed PR change the pipeline or deploy? Are serialized formats safe?

## A09: Security Logging and Monitoring Failures

Attacks that go unnoticed: no audit logs for logins and sensitive actions, logs without context, logs not centralised or not retained, no alerting, no incident response plan.

Controls: audit logging (chapter 22), structured logs with correlation IDs (Part XI chapter 1), alerting on authentication anomalies and error spikes (Part XI chapter 5), CloudTrail and GuardDuty (Part VII chapter 12), incident response procedures (Part XI chapter 6, Part XV chapter 4).

Checklist: Can you answer "who accessed record X last month"? Would you notice 10,000 failed logins? Are logs tamper-evident and retained? Has the incident process been exercised?

## A10: Server-Side Request Forgery

Fetching attacker-influenced URLs from the server, reaching internal services and cloud metadata.

Controls: chapter 12 in full: scheme/port allow-lists, resolved-IP checks with pinning, no redirects, response bounds, network isolation of fetchers, IMDSv2, minimal instance roles; webhook destination validation (Part III chapter 10).

Checklist: Where does the server fetch URLs from user input? Is IMDSv2 enforced? Can fetchers reach internal networks?

## Beyond the ten

Things the list under-represents that this book covers because they cause client incidents: tenant isolation (Part III chapter 15), cloud IAM misconfiguration (Part VII chapter 2), secrets in repositories (chapters 17 and 20), backup exposure and recoverability (Part V chapter 11), and operational decay after handover (Part XIII). The 2025 edition's additions ("Software Supply Chain Failures" as its own category; "Mishandling of Exceptional Conditions") map to chapter 20 and to Part III chapter 12 respectively.

## Using the list with clients

Client questionnaires ask "how do you address the OWASP Top 10?" The honest, useful answer is a table: category, the specific controls in your system, how each is verified (test, scan, review), and the evidence (links to CI checks, policies, logs). The chapter references above are that table's skeleton. Avoid "we follow OWASP best practices" without specifics; reviewers see through it.

```checklist
# OWASP Top 10 self-assessment (one line of evidence per item)
## A01 Broken Access Control
- Central authorization with default deny; resource-level ownership and tenant checks on every endpoint.
- Automated tests for horizontal (other user) and vertical (other role) access.
## A02 Cryptographic Failures
- TLS with certificate validation on every hop; HSTS on public endpoints.
- Argon2id/bcrypt for passwords; AEAD for application encryption; CSPRNG for tokens; keys in KMS/secrets manager.
## A03 Injection
- Parameterised queries everywhere; identifiers allow-listed; no shell invocation with user input; path canonicalisation.
- Output encoding by default; CSP enforced; SAST in CI.
## A04 Insecure Design
- Threat model exists and is maintained; abuse cases documented; rate limits on sensitive flows; races closed with atomic operations.
## A05 Security Misconfiguration
- Infrastructure as code with policy checks; no public storage; security headers; debug off; errors sanitised; config drift detection.
## A06 Vulnerable Components
- Lockfiles; dependency and image scanning failing on critical CVEs; SBOM produced; update cadence owned.
## A07 Authentication Failures
- MFA available (enforced for admins); rate limiting on login and recovery; session rotation and expiry; federation for enterprise users.
## A08 Integrity Failures
- No unsafe deserialization; signed/pinned dependencies and images; protected pipeline configuration; SRI for third-party scripts.
## A09 Logging and Monitoring Failures
- Audit log for authentication and sensitive actions; centralised, retained, tamper-evident; alerts on anomalies; incident process exercised.
## A10 SSRF
- URL fetches validated on resolved IPs with pinning; no redirects; fetchers network-isolated; IMDSv2 enforced.
```

## Exercises

1. Complete the self-assessment above for a system you operate, with one piece of evidence per line. Lines without evidence are your backlog.
2. Take a client security questionnaire (or a public one such as the CAIQ) and map each question to a chapter and a control in your system.
3. Read the current OWASP Top 10 and ASVS Level 2 requirements for authentication; identify three ASVS requirements your system does not meet.
