# Security Testing

:::objectives
- Build a layered security testing programme: unit tests for security logic, SAST, SCA, secret scanning, DAST, and periodic penetration testing.
- Write security-focused automated tests that prevent regressions in authentication, authorization, injection and tenant isolation.
- Scope and commission a penetration test responsibly, and act on its results.
- Test only what you are authorised to test.
:::

:::prereq
Chapters 7, 10, 11, 14 and 20; Part XII chapter 5.
:::

## The problem

Security controls regress. A refactor drops a tenant filter; a new endpoint skips the authorization dependency; a framework upgrade changes a default; a CSP exception is added during a crunch and never removed. Without tests, each regression is found by an attacker or an auditor. Security testing is ordinary testing applied to the properties this part has described, plus specialised tools for the classes of bugs ordinary tests do not find.

:::danger Authorisation
Test only systems you own or have explicit, written authorisation to test, within the agreed scope and time window. Scanning or probing a client's production system without a signed agreement is illegal in most jurisdictions and will end the engagement. For client systems, propose a test plan, get it approved in writing, test in staging or a dedicated window, and never use techniques that could disrupt service. Part XIII chapter 4 covers assessing a client's posture without testing.
:::

## Security-focused automated tests

The highest-value investment, because they run on every change. Patterns:

```python
# Authorization matrix: every endpoint × every role × own/other/other-tenant resource
import pytest

ENDPOINTS = [("GET", "/v1/orders/{id}"), ("PATCH", "/v1/orders/{id}"), ("DELETE", "/v1/orders/{id}"), ("GET", "/v1/orders/{id}/invoice")]
ROLES = ["member", "support", "admin"]

@pytest.mark.parametrize("method,path", ENDPOINTS)
@pytest.mark.parametrize("role", ROLES)
def test_cannot_access_other_tenant_resource(client, make_user, make_order, method, path, role):
    me = make_user(tenant="t_1", role=role)
    other = make_order(tenant="t_2")
    r = client.request(method, path.format(id=other.id), auth=me)
    assert r.status_code in (403, 404), f"{role} {method} {path} leaked cross-tenant"

@pytest.mark.parametrize("method,path", ENDPOINTS)
def test_member_cannot_access_other_users_resource_in_same_tenant(client, make_user, make_order, method, path):
    me = make_user(tenant="t_1", role="member")
    other = make_order(tenant="t_1", owner=make_user(tenant="t_1"))
    r = client.request(method, path.format(id=other.id), auth=me)
    assert r.status_code in (403, 404)

def test_unauthenticated_rejected(client, all_routes):
    for method, path in all_routes:                                # introspect the router so new routes are covered automatically
        if path.startswith("/health"): continue
        r = client.request(method, path.replace("{id}", "x"))
        assert r.status_code == 401, f"{method} {path} is reachable without auth"
```

# Mass assignment, injection canaries, headers, CSRF
def test_privileged_fields_rejected(client, user):
    r = client.patch("/v1/me", json={"name": "x", "is_admin": True, "tenant_id": "t_9"}, auth=user)
    assert r.status_code == 422

@pytest.mark.parametrize("payload", ["' OR 1=1 --", "\"><svg onload=alert(1)>", "../../etc/passwd", "{\"$ne\": null}"])
def test_hostile_input_handled(client, user, payload):
    r = client.get("/v1/orders", params={"q": payload}, auth=user)
    assert r.status_code in (200, 400, 422)
    assert payload not in r.text or r.headers["content-type"].startswith("application/json")   # never reflected as HTML

def test_security_headers_present(client):
    r = client.get("/")
    for h in ["strict-transport-security", "content-security-policy", "x-content-type-options", "referrer-policy"]:
        assert h in r.headers, h
    assert "frame-ancestors" in r.headers["content-security-policy"]

def test_mutation_without_csrf_header_rejected(client, user_session_cookie):
    r = client.post("/v1/orders", json={}, cookies=user_session_cookie)   # no X-CSRF-Token
    assert r.status_code == 403

def test_login_rate_limited(client):
    for _ in range(10): client.post("/login", json={"email": "a@x.test", "password": "wrong"})
    r = client.post("/login", json={"email": "a@x.test", "password": "wrong"})
    assert r.status_code == 429 and "retry-after" in r.headers

Add tests for: session rotation at login; logout invalidation; password reset token single-use and expiry; webhook signature verification (valid, tampered, replayed); SSRF validator against the encoded-IP list; RLS blocking unscoped queries; presigned URL expiry; idempotency key behaviour; audit events emitted for sensitive actions.

## Static analysis

SAST tools pattern-match source for dangerous constructs. Semgrep (with community and OWASP rulesets, plus your own rules for project-specific sinks), Bandit (Python), ESLint security plugins, CodeQL (deep dataflow analysis; free for public repos, available via GitHub Advanced Security), gosec, Brakeman (Rails). Run on every PR; start with a small high-signal ruleset to avoid alert fatigue; write custom rules when you find a bug class ("never call `render_template_string` with a variable"; "every router must include the auth dependency").

## Dynamic scanning

DAST tools (OWASP ZAP, Burp Suite's scanner, Nuclei for known misconfigurations) crawl and attack a running application. Run nightly against staging with an authenticated session (ZAP supports scripted auth), import the OpenAPI spec so the scanner knows every endpoint, and triage results into tickets. Expect false positives; expect it to miss authorization logic. It excels at headers, reflected XSS, outdated software banners and forgotten debug endpoints.

## Infrastructure and configuration

Scan infrastructure code before apply (Checkov, tfsec/Trivy, cfn-nag, Prowler for live accounts) and watch live configuration continuously (AWS Config rules, Security Hub standards such as the AWS Foundational Security Best Practices, GuardDuty). Part X chapter 6 and Part VII chapter 12. These catch the misconfigurations that dominate cloud breaches: public buckets, open security groups, unencrypted storage, IAM wildcards, missing logging.

## Penetration testing

A **penetration test** is a time-boxed, authorised, manual (tool-assisted) attack on a defined scope by people whose job is to think like attackers. It finds what automation cannot: chained weaknesses, business logic abuse, authorization gaps that require understanding the product. Commission one before a major launch, annually for anything handling sensitive data, and after significant architectural change; many clients and compliance regimes require it.

Scoping well: define targets (URLs, APIs, accounts, excluding third-party services unless they permit it), environment (staging with production-like data shape, or production in a window with safeguards), rules of engagement (no denial of service, no social engineering unless agreed, hours, emergency contacts), what the testers get (credentials for each role, documentation, source code for a grey/white-box test, which is more efficient than black-box), and the deliverable (report with severity, reproduction steps, remediation advice; a retest of fixes).

Acting on results: triage into the normal workflow with deadlines by severity (critical: days; high: weeks); fix the class, not the instance (one IDOR usually means a pattern); add regression tests; retest; share a summary with the client. A report that sits in a folder is a liability: it proves you knew.

Notify the cloud provider if required by their policy (AWS permits testing of most services on your own resources without prior approval; some simulated attacks, like DDoS, require it).

## Bug bounties and disclosure

Publish a `security.txt` (RFC 9116) and a disclosure policy so researchers can reach you. A bounty programme (HackerOne, Bugcrowd, self-run) rewards findings; it suits mature products with a response process, not early-stage systems where the backlog would overwhelm you.

## Measuring

Track: security test coverage of endpoints (every route in the authorization matrix?), SAST/SCA findings open by severity and age, mean time to remediate, DAST findings trend, pentest findings by class over time, secret-scanning hits (should trend to zero). Present these to clients as evidence of a working programme, not as a one-time certificate.

## Common mistakes

- Running scanners and ignoring their output.
- Security tests as a separate suite nobody runs; integrate into the main CI.
- Testing production without authorisation or safeguards.
- Pentest once, before launch, then never, while the system changes monthly.
- Fixing the one IDOR the pentest found and leaving the pattern.
- No `security.txt`, so a researcher who finds something cannot tell you.
- Trusting a clean DAST run as proof of security.
