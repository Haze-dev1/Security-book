# Security Headers and Content Security Policy

:::objectives
- Deploy the full set of browser security headers with correct values and understand what each one prevents.
- Design, roll out and maintain a Content Security Policy that blocks XSS without breaking the application.
- Configure headers at the right layer (CDN, load balancer, proxy or application) and verify them.
- Avoid the misconfigurations that make headers decorative.
:::

:::prereq
Chapters 9, 10 and 14.
:::

## The problem

Browsers ship with many protections turned off for compatibility: they will happily execute inline scripts, load your page in a hostile iframe, send referrers to third parties, sniff content types, and connect over plain HTTP. A handful of response headers turn these protections on. They cost nothing, take an afternoon to deploy, and they are the difference between an XSS bug being an incident and being a log line. Security scanners and client questionnaires will check for them, but the reason to deploy them is that they work.

## The headers

| Header | Value | Prevents |
|---|---|---|
| `Strict-Transport-Security` | `max-age=63072000; includeSubDomains; preload` | Downgrade to HTTP, cookie theft over plaintext (Part II chapter 9) |
| `Content-Security-Policy` | see below | XSS execution, data exfiltration, clickjacking (`frame-ancestors`), mixed content |
| `X-Content-Type-Options` | `nosniff` | Browsers treating JSON/text/uploads as HTML or scripts |
| `X-Frame-Options` | `DENY` (legacy; CSP `frame-ancestors` supersedes) | Clickjacking in old browsers |
| `Referrer-Policy` | `strict-origin-when-cross-origin` (or `no-referrer`) | Leaking URLs (with tokens, IDs) to third parties |
| `Permissions-Policy` | `camera=(), microphone=(), geolocation=(), payment=()` | Injected content using powerful APIs; third-party iframes requesting them |
| `Cross-Origin-Opener-Policy` | `same-origin` | Cross-window attacks (tab-napping, Spectre-class leaks) |
| `Cross-Origin-Resource-Policy` | `same-origin` (or `same-site`) | Other origins loading your resources as sub-resources |
| `Cross-Origin-Embedder-Policy` | `require-corp` (only if you need cross-origin isolation) | Needed for SharedArrayBuffer; often omitted |
| `Cache-Control` | `no-store` on authenticated responses | Caching personal data (Part II chapter 8) |
| `X-XSS-Protection` | `0` or omit | Legacy filter; deprecated and harmful; do not set to 1 |

Remove headers that leak information: `Server` versions, `X-Powered-By`, `X-AspNet-Version`.

## Content Security Policy in depth

CSP tells the browser where each kind of resource may come from and whether inline code may run. Its main job is to make injected script inert.

### A strong, practical policy for a SPA

```http
Content-Security-Policy:
  default-src 'none';
  script-src 'self' 'nonce-{random}' 'strict-dynamic';
  style-src 'self' 'nonce-{random}';
  img-src 'self' data: https://cdn.client.com;
  font-src 'self';
  connect-src 'self' https://api.client.com wss://rt.client.com;
  frame-ancestors 'none';
  base-uri 'none';
  form-action 'self';
  object-src 'none';
  upgrade-insecure-requests;
  report-to csp-endpoint
```

Reading it: nothing is allowed by default; scripts may come from our origin or carry this response's nonce, and scripts loaded by trusted scripts are trusted (`strict-dynamic`); styles likewise; images from us, data URIs and our CDN; XHR/fetch/WebSocket only to our API and realtime hosts; nobody may frame us; `<base>` cannot be injected to redirect relative URLs; forms may only submit to us; no plugins; HTTP sub-resources are upgraded; violations are reported.

### Nonces versus hashes versus host lists

- **Nonces**: a fresh random value per response, placed on each legitimate `<script>` and `<style>` tag and in the header. Requires server-side rendering of the HTML (or an edge function) to inject the nonce. The strongest practical approach.
- **Hashes**: `'sha256-…'` of each inline script's content. Works for static HTML with fixed inline scripts (and for inline event handlers via `'unsafe-hashes'`, sparingly).
- **Host allow-lists** (`script-src cdn.example.com`): weak; many CDNs host libraries with JSONP endpoints or Angular templates that allow bypasses. Use `strict-dynamic` with nonces/hashes instead, and keep host lists for images, fonts and connections.

`'unsafe-inline'` for scripts disables XSS protection entirely; `'unsafe-eval'` allows `eval` and friends. Both should be absent from `script-src`. For `style-src`, `'unsafe-inline'` is a common compromise when CSS-in-JS libraries demand it; the risk (CSS injection exfiltration) is lower but not zero.

### Rolling out

1. Start with `Content-Security-Policy-Report-Only` carrying the target policy, plus a report endpoint (`report-to`/`report-uri`) or a service (report-uri.com, Sentry).
2. Browse the application; collect violations for a week; fix each (move inline scripts to files or add nonces; replace inline handlers with `addEventListener`; allow-list legitimate third-party hosts; remove the ones you do not need).
3. Switch to enforcing. Keep report-only for a *stricter* candidate policy alongside, so you can tighten continuously.
4. Monitor reports in production: a spike indicates either a deploy that broke the policy or an actual injection attempt.

### Static SPA with nonces

A static `index.html` on S3 cannot carry a per-request nonce by itself. Options: a CloudFront Function or Lambda@Edge injects a nonce into the HTML and the header per request; or use hashes for the (few, fixed) inline scripts in the shell and `'self'` plus `strict-dynamic` for the bundle; or render the shell from a small server. Modern bundlers (Vite, Next.js) document CSP integration.

### Trusted Types

`Content-Security-Policy: require-trusted-types-for 'script'; trusted-types default dompurify` makes DOM XSS sinks (`innerHTML`, `eval`, `script.src`) reject raw strings; only values created by an allowed policy (e.g., sanitised by DOMPurify) are accepted. Supported in Chromium-based browsers; a strong addition for new frontends.

## Where to set headers

- **CDN / edge** (CloudFront response headers policy, Cloudflare): applies to everything including static files; cheap; one place to audit. Best for static sites and as a baseline.
- **Load balancer**: ALBs cannot add arbitrary response headers (they can for some; check current capabilities), so this is usually not the layer.
- **Reverse proxy** (Nginx `add_header … always`, Caddy `header`): good for VM deployments. Remember `always` so the headers are on error responses too, and that `add_header` in a nested block *replaces* the parent's headers in Nginx.
- **Application middleware** (Helmet for Express, `secure` for Python, framework settings): necessary when values vary per response (nonces) and good as a defence in depth under the edge configuration.

Set them in one authoritative place and let others reinforce only where needed; conflicting values (two CSP headers) combine restrictively and confusingly.

## Verification

```bash
curl -sI https://app.client.com | grep -iE 'strict-transport|content-security|x-content-type|x-frame|referrer-policy|permissions-policy|cross-origin'
```

Then: Mozilla Observatory or securityheaders.com for a graded report; browser dev tools console for CSP violations; a test page that tries to iframe your app; a test that fetches an authenticated API response and checks `Cache-Control`.

Add an automated check in CI or synthetic monitoring that asserts the expected headers on the home page and an API endpoint; headers regress silently when someone changes the CDN configuration.

## API-only responses

APIs returning JSON still benefit: `X-Content-Type-Options: nosniff`, `Cache-Control: no-store`, `Content-Security-Policy: default-src 'none'; frame-ancestors 'none'` (harmless and defends against a JSON response being rendered), HSTS, and `Content-Type: application/json; charset=utf-8` always (a JSON endpoint that reflects input with `text/html` is an XSS).

## Common mistakes

- `script-src 'unsafe-inline'` because the first attempt broke the app; the CSP then protects nothing.
- CSP set but `frame-ancestors` omitted; relying on `X-Frame-Options` alone.
- Headers on 200 responses only (Nginx without `always`).
- HSTS with `preload` before confirming every subdomain serves HTTPS, locking out an HTTP-only internal host.
- Allow-listing `*.cloudfront.net` or `*.amazonaws.com`, which includes every other customer's content.
- Reporting endpoint absent, so violations (and attacks) are invisible.
- Multiple conflicting CSP headers from CDN and application.
- `Server: nginx/1.24.0` and `X-Powered-By: Express` advertising versions.

## Exercises

1. Run a header scanner against an application you own; implement every missing header at the edge or proxy; rescan.
2. Deploy a nonce-based CSP in report-only mode with a reporting endpoint. Fix violations until enforcement is possible; then enforce and keep a stricter report-only candidate.
3. Write a CI check (a small script or a synthetic monitor) that fails if any required header is missing from the home page and an API endpoint.
