# Authentication versus Authorization

:::objectives
- Separate identity, authentication, session management and authorization as distinct problems with distinct controls.
- Choose an authentication architecture (sessions, tokens, federated identity) appropriate to the clients and risks of a system.
- Design authorization so it is enforced centrally, at the resource level, and testable.
- Avoid the conflations that produce the most common access-control bugs.
:::

:::prereq
Chapters 1 and 2; Part II chapter 11.
:::

## The problem

"Auth" is one word for two different questions, and systems that blur them fail in predictable ways. **Authentication** answers "who is this?" **Authorization** answers "may they do this?" A system can authenticate perfectly and authorise nothing (every logged-in user sees every record: the classic [[idor]]). A system can authorise meticulously against an identity that was never verified (trusting a `user_id` header). Most access-control vulnerabilities, which top the OWASP list, come from treating "logged in" as the end of the question.

## Authentication architectures

### Session-based (chapter 4)

Login verifies the credential, creates a server-side session, sets an HttpOnly cookie with the session ID. Every request looks up the session. Revocable, simple, the right default for browser applications talking to their own backend.

### Token-based (chapter 5)

Login (or a token endpoint) issues a signed token the client presents in an `Authorization: Bearer` header. Verifiable without a lookup, good for APIs consumed by many services and mobile clients, hard to revoke; mitigated with short lifetimes and refresh tokens.

### Federated identity (chapter 6)

Your application does not verify passwords at all. An identity provider (Okta, Entra ID, Google, Auth0, Cognito, the client's corporate IdP) authenticates the user, including MFA, and tells your application who they are via OpenID Connect or SAML. Your application then creates its own session. This is the right answer for anything enterprise: clients want their staff managed in their own directory, with their own MFA policy and offboarding.

### Machine authentication (chapter 18)

Services authenticate to each other with cloud IAM (SigV4 signatures from roles), mTLS, or short-lived service tokens; API consumers use API keys or OAuth client credentials. Never with a shared human user's password.

## Authorization: the part everyone under-builds

Authentication yields a principal. Authorization needs three more inputs: the **action** (read, update, approve), the **resource** (order 123, belonging to tenant 7, in state `pending`), and sometimes **context** (time, IP, MFA freshness). Models:

- **Role-based (RBAC)**: principals have roles; roles grant permissions. "Support agents can read orders." Simple, auditable, coarse.
- **Attribute-based (ABAC)**: rules over attributes of principal, resource and context. "A user may read an order if order.tenant_id == user.tenant_id and (user.role == 'admin' or order.owner_id == user.id)."
- **Relationship-based (ReBAC)**: permissions follow relationships in a graph (Google Zanzibar, OpenFGA, SpiceDB). "Users who are editors of the folder containing this document may edit it."

In practice most applications need RBAC for coarse roles *plus* resource-level ownership and tenant checks, which is a simple form of ABAC. Chapter 7 goes deep. The non-negotiable rule: **every request that touches a resource verifies that this principal may perform this action on this specific resource**, in a central layer, before the action, with deny as the default.

## Where things go wrong

**Confusing authenticated with authorised.** `@login_required` on an endpoint that then does `Order.get(id)` with no ownership check. Any logged-in user can read any order by changing the ID. This is IDOR, OWASP's number one category.

**Authorization by obscurity.** "Nobody knows the admin URL." "The mobile app never calls that endpoint." Attackers read JavaScript and proxy mobile traffic.

**Trusting identity from the client.** A `X-User-Id` header, a `user_id` in the body, a `role` claim in a token that was never verified, a tenant ID in the URL used without checking it matches the session.

**Authorization in the wrong place.** Checks in the UI only; checks in middleware by URL pattern that miss new endpoints or alternate paths (`/api/orders/123` protected, `/api/v2/orders/123` not); checks scattered through handlers and forgotten in one.

**Privilege that outlives its grant.** Role changes or offboarding not reflected until the token expires (hours later, or never); sessions not invalidated on password change; API keys of departed staff still valid.

**Vertical versus horizontal confusion.** Testing that a user cannot become admin (vertical) while never testing that user A cannot see user B's data (horizontal).

## Design rules

1. Derive the principal from the verified credential or session only. Everything about identity comes from the server side.
2. Make authorization a function: `authorize(principal, action, resource) -> allow | deny`, called in one place (service layer or a policy layer), with default deny and tests.
3. Load the resource first, then check, then act. Checks that do not see the resource cannot check ownership.
4. Return 404 for "not yours" when existence is sensitive; otherwise 403. Be consistent.
5. Re-check on every request. Cache role lookups briefly if needed, with invalidation on change.
6. Separate authentication strength from authorization: sensitive actions can require recent authentication or MFA (step-up).
7. Log authentication events (success, failure, MFA, logout) and authorization denials.
8. Test authorization explicitly: for each endpoint, a test that the wrong principal is denied, including cross-tenant.

## Common mistakes

- `login_required` as the only access control.
- Role checks by URL prefix only.
- Tenant from the URL, trusted.
- Tokens with roles that are never re-validated after role changes.
- No tests for horizontal access.
- A separate admin login with its own password database instead of SSO.
- Treating API keys as user identities with full user privileges.

## Exercises

1. Inventory every endpoint in a service. For each, write down the authorization rule in one sentence. Any endpoint whose rule is "logged in" alone, and which touches a resource, is a finding.
2. Write a test for each endpoint that attempts access as a different user and as a different tenant. Run them.
3. Design the authentication architecture for a product with consumer users, enterprise SSO users, a mobile app, and partner API consumers. One paragraph per client type.
