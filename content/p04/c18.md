# API Keys and Service Credentials

:::objectives
- Issue, store, scope, rotate and revoke API keys for consumers of your API.
- Handle credentials your services use to call other systems, and replace static keys with identity-based access wherever possible.
- Apply IAM roles for AWS workloads correctly: instance profiles, task roles, execution roles, cross-account roles.
- Detect and respond to credential misuse.
:::

:::prereq
Chapters 3, 5 and 17.
:::

## The problem

Machines need to authenticate too: a partner's system calling your API, your worker calling a payment provider, your application reading from S3, your CI deploying to production. Machine credentials outnumber human ones, live longer, are copied more freely, and are rarely rotated. Leaked machine credentials are the entry point in a large share of cloud breaches, often harvested from public repositories, CI logs, container images and laptops. The two moves that matter: scope every credential narrowly, and replace static credentials with short-lived, identity-derived ones wherever the platform allows.

## API keys you issue

For consumers who call your API programmatically (partner systems, customer integrations, your own mobile apps in some designs), API keys are the simplest mechanism. Done well:

- **Generation**: 256 bits from a CSPRNG, encoded (`base62`/`base64url`), with a recognisable **prefix** (`ck_live_…`, `ck_test_…`) so keys are identifiable in logs and by secret scanners (GitHub's scanning partner programme recognises prefixed formats). Show the full key **once** at creation.
- **Storage**: store only a hash (SHA-256 is adequate for high-entropy random keys; the slow hashes of chapter 8 are for low-entropy passwords). Store a short **key ID** or the prefix in plaintext for lookup and display (`ck_live_a8f3…`). Lookup: find by key ID, then compare hash in constant time.
- **Scope**: each key carries the tenant it belongs to, a set of permissions (scopes), optional IP allow-list, optional expiry. The effective permission is key scope ∩ tenant entitlements.
- **Rotation**: allow multiple active keys per tenant so consumers can create a new one, switch, then revoke the old. Record `last_used_at` so unused keys can be identified and pruned.
- **Revocation**: immediate, server-side, by key ID. Keys are looked up per request, so revocation takes effect instantly (unlike JWTs).
- **Transport**: `Authorization: Bearer <key>` or a custom header; never in query strings (logged everywhere).
- **Rate limiting and audit** per key (Part III chapter 5; chapter 22).
- **Environments**: test-mode keys that only touch sandbox data, distinguished by prefix.

```python
import secrets, hashlib, hmac
PREFIX = "ck_live_"
def issue_key(tenant_id: str, scopes: list[str]) -> tuple[str, dict]:
    raw = secrets.token_urlsafe(32)
    key_id = secrets.token_hex(6)                                 # public identifier for lookup/display
    full = f"{PREFIX}{key_id}_{raw}"
    record = {"key_id": key_id, "tenant_id": tenant_id, "scopes": scopes,
              "hash": hashlib.sha256(full.encode()).hexdigest(), "created_at": now(), "last_used_at": None, "revoked_at": None}
    return full, record     # return `full` to the user once; persist `record`

def authenticate_key(presented: str, repo) -> dict | None:
    try: _, key_id, _ = presented.split("_", 2) if presented.startswith(PREFIX) else (None, None, None)
    except ValueError: return None
    rec = repo.find_by_key_id(key_id) if key_id else None
    if not rec or rec["revoked_at"]: return None
    if not hmac.compare_digest(rec["hash"], hashlib.sha256(presented.encode()).hexdigest()): return None
    repo.touch_last_used(key_id)
    return rec
```

When consumers act **on behalf of users** (a third-party app accessing a user's data), use OAuth 2.0 (chapter 6) rather than per-user API keys; when a machine acts as itself, API keys or OAuth client credentials are both fine.

## Credentials your services hold

Your services call databases, caches, queues, cloud APIs, payment providers, email services. For each, the question is: can this be identity-based instead of a stored secret?

| Target | Static secret | Identity-based alternative |
|---|---|---|
| AWS services (S3, SQS, KMS, Secrets Manager…) | IAM user access keys | **IAM role** on the instance/task/function; SDK obtains temporary credentials automatically |
| RDS PostgreSQL/MySQL | Password in Secrets Manager | IAM database authentication (15-minute tokens) |
| Another AWS account | Shared keys | Cross-account role assumption via STS |
| GitHub Actions → AWS | Access keys in repo secrets | OIDC federation: short-lived role credentials per job |
| Kubernetes workload → AWS | Node role shared by all pods | IAM Roles for Service Accounts (IRSA) / Pod Identity |
| Service → service inside your platform | Shared API token | mTLS via mesh, signed service tokens, IAM SigV4 for internal ALBs |
| Third-party SaaS (Stripe, SendGrid) | API key in Secrets Manager (unavoidable) | Scope it minimally; rotate; some support OAuth or IP restrictions |

**IAM roles** are the central mechanism on AWS. A role is an identity with a permission policy and a trust policy saying who may assume it. Compute services assume roles automatically: an EC2 **instance profile**, an ECS **task role** (what your code can do) distinct from the **task execution role** (what the ECS agent needs: pull images, fetch secrets, write logs), a Lambda execution role, an EKS service account role. The SDK's default credential chain finds these without configuration; your code contains no credentials at all.

```json
// Task role policy: exactly what this service does, on exactly these resources
{
  "Version": "2012-10-17",
  "Statement": [
    {"Effect": "Allow", "Action": ["s3:GetObject", "s3:PutObject"], "Resource": "arn:aws:s3:::client-prod-uploads/*"},
    {"Effect": "Allow", "Action": ["sqs:SendMessage"], "Resource": "arn:aws:sqs:eu-west-1:123456789012:jobs"},
    {"Effect": "Allow", "Action": ["secretsmanager:GetSecretValue"], "Resource": "arn:aws:secretsmanager:eu-west-1:123456789012:secret:prod/app/*"},
    {"Effect": "Allow", "Action": ["kms:Decrypt", "kms:GenerateDataKey"], "Resource": "arn:aws:kms:eu-west-1:123456789012:key/0f1e…",
     "Condition": {"StringEquals": {"kms:ViaService": "secretsmanager.eu-west-1.amazonaws.com"}}}
  ]
}
```

Rules for roles: one role per workload; resource ARNs, not `*`; no `iam:*` or `sts:AssumeRole` on `*`; permission boundaries for roles that teams create themselves; IAM Access Analyzer and CloudTrail-based "last accessed" data to prune unused permissions; IMDSv2 enforced so SSRF cannot steal instance credentials (chapter 12).

## Humans and long-lived keys

IAM **users with access keys** should not exist for humans: use IAM Identity Center (SSO) with short-lived sessions (Part VII chapter 3). For the rare automation that cannot federate, an IAM user with one key, minimal policy, rotation every 90 days, and an alert on use from unexpected locations. Root account access keys: delete them; root has MFA (hardware) and is used only for the handful of tasks that require it.

## Cross-account access for client deployments

:::fde
When you deploy into a client's AWS account, you do not want their long-lived keys on your laptop or in your CI. Have the client create a **role in their account** with a trust policy allowing your account (or your CI's OIDC identity) to assume it, with an **external ID** to prevent the confused-deputy problem, MFA or session-duration conditions as agreed, and a permission policy scoped to what the deployment needs. You assume it for a session (one hour by default, up to twelve), do the work, and the session expires. The client sees every action in their CloudTrail under that role, can revoke access by deleting the role, and never shared a secret. Part XIII chapter 9 details the arrangement.
:::

## Detecting misuse

- CloudTrail: alert on credential use from new IP ranges or regions, on `AssumeRole` by unexpected principals, on IAM policy changes, on access key creation.
- GuardDuty: detects credential exfiltration patterns (instance credentials used from outside AWS), unusual API activity, and known-bad IPs.
- Provider dashboards: unusual spend or volume on third-party API keys (SMS pumping, compute abuse).
- Your own API: per-key anomaly detection (sudden volume, new endpoints, geographic shift) and `last_used_at` reviews.
- Secret scanning on repositories and CI logs; honeytokens (fake credentials that alert when used) in places attackers look.

## When a key is compromised

Same drill as chapter 17: revoke/rotate first, then investigate usage, then contain, then clean up. For API keys you issued to a customer: revoke, notify them, help them rotate, and review what the key accessed. For cloud keys: disable the key or revoke the role's sessions (`aws iam put-role-policy` with a deny on sessions issued before a timestamp, the "revoke sessions" button), then investigate CloudTrail for the exposure window.

## Common mistakes

- Storing API keys in plaintext in the database.
- Keys in query strings; keys with no prefix; keys that cannot be rotated without downtime.
- One key per customer with every permission, forever.
- IAM users with access keys baked into AMIs, images, config files or CI.
- Shared node roles in Kubernetes giving every pod every permission.
- `"Resource": "*"` on task roles.
- Confusing task role with task execution role and granting both broad access.
- No `last_used_at`; thousands of orphaned keys.
- Cross-account roles without external IDs or with `"Principal": "*"`.

## Exercises

1. Implement API key issuance, hashed storage, scoped authentication, rotation (multiple active keys) and revocation; add `last_used_at` and a report of keys unused for 90 days.
2. Find every IAM user with access keys in an AWS account you control; replace each with a role or federation, or document why it must remain and set rotation.
