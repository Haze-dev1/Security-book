# Password Storage, MFA and Passkeys

:::objectives
- Store passwords so that a database breach does not yield usable credentials: Argon2id or bcrypt, correctly parameterised.
- Implement password policy, breach checking, rate limiting and recovery flows that resist the attacks seen in practice.
- Add TOTP and WebAuthn/passkeys as second (or primary) factors, with safe enrolment and recovery.
- Avoid the account-recovery weaknesses that undo everything else.
:::

:::prereq
Chapters 4 and 16 (hashing concepts are summarised here; chapter 16 goes deeper).

## The problem

Databases leak. When yours does, the password table decides whether the incident is "rotate some secrets" or "every user's credentials, reused on their bank, are in an attacker's hands". Meanwhile, attackers do not usually crack passwords at all; they *stuff* credentials leaked from other sites, *phish* users, and abuse *account recovery*. Password storage, rate limiting, MFA and recovery design are one system; a weakness in any part is a weakness in all.

## Storing passwords

Never store passwords, encrypted or otherwise. Store a **slow, salted hash** computed by a function designed for passwords:

- **Argon2id** (winner of the Password Hashing Competition): memory-hard, resists GPU and ASIC attacks. Current recommendation: memory 64 MB (`m=65536`), 3 iterations, parallelism 4 (or 19 MB with 2 iterations for constrained systems; OWASP publishes current minimums). Tune so one verification costs about 50–200 ms on your servers.
- **bcrypt**: older, widely available, CPU-hard only; cost factor 12–13 today. Truncates input at 72 bytes (pre-hash with SHA-256 if you allow longer passwords, carefully). Acceptable; prefer Argon2id for new systems.
- **scrypt** and **PBKDF2** (≥ 600,000 iterations for SHA-256): acceptable where mandated (FIPS environments often require PBKDF2).

Never: MD5, SHA-1, SHA-256 alone (fast hashes are brute-forced at billions per second), unsalted anything, home-made schemes, or a "pepper" as a substitute for a slow hash (a pepper, a server-side secret added to the hash input, is a fine *addition* if stored in a secrets manager, not in the database).

```python
# argon2-cffi
from argon2 import PasswordHasher, exceptions
ph = PasswordHasher(time_cost=3, memory_cost=65536, parallelism=4)   # tune to ~100 ms

def hash_password(password: str) -> str:
    return ph.hash(password)        # returns "$argon2id$v=19$m=65536,t=3,p=4$<salt>$<hash>" with a random salt

def verify_password(stored: str, password: str) -> tuple[bool, str | None]:
    try:
        ph.verify(stored, password)
    except exceptions.VerifyMismatchError:
        return False, None
    new_hash = ph.hash(password) if ph.check_needs_rehash(stored) else None   # upgrade parameters transparently at login
    return True, new_hash
```

Verification of an unknown user should take the same time as a real one (verify against a dummy hash) so response timing does not reveal which accounts exist. Parameters embedded in the hash string let you raise cost over time: on successful login, rehash with current parameters if the stored one is weaker.

## Password policy that helps

Modern guidance (NIST SP 800-63B): minimum length 8 (12+ for admins), maximum at least 64, allow any printable characters including spaces and Unicode, **no composition rules** (forced symbols produce `Password1!`), **no periodic forced rotation** (produces predictable increments), **check against breached-password lists** (Have I Been Pwned's k-anonymity API, or a local corpus) at set time and optionally at login, block the most common passwords and context-specific ones (the company name), and show a strength meter. Encourage password managers: do not disable paste.

## Rate limiting and lockout

Credential stuffing is thousands of username/password pairs tried at machine speed. Defences, layered: per-IP and per-account rate limits (Part III chapter 5); progressive delays after failures; CAPTCHA or proof-of-work after a few failures; device/IP reputation; **MFA** (which turns a correct stuffed password into nothing). Hard lockout after N failures is a denial-of-service vector (attackers lock out victims); prefer temporary slowdowns and notifications ("new login attempt failed; was this you?"). Monitor failure rates globally; a spike is an attack in progress.

## Multi-factor authentication

Factors: something you know (password), have (phone, key), are (biometric unlocking a device). MFA adds a second, independent factor. Options from weakest to strongest:

| Method | Phishing-resistant | Notes |
|---|---|---|
| SMS / voice codes | No | SIM swap, SS7 interception, phishable in real time. Better than nothing; not for admins or high-value accounts. Also costs money and invites "SMS pumping" fraud via unprotected enrolment endpoints. |
| Email codes / magic links | No | Only as strong as the mailbox; useful as passwordless for low-risk apps. |
| [[totp]] (authenticator apps) | No (codes can be phished in real time) | Cheap, offline, universally supported. Good default second factor. |
| Push notifications with number matching | Partially | Resists blind approval fatigue; still phishable by sophisticated proxies. |
| **WebAuthn / FIDO2: passkeys and security keys** | **Yes** | Cryptographic challenge bound to the origin; cannot be phished or replayed. The gold standard. |

### TOTP implementation notes

Generate a 160-bit random secret per user; show it as a QR code (`otpauth://totp/App:user?secret=…&issuer=App&digits=6&period=30`); require the user to enter one valid code before enabling (proves enrolment); store the secret encrypted at rest (KMS or application-level encryption) because it is a credential; accept the current window ±1 step for clock drift; **prevent replay** by recording the last used time step per user and rejecting codes at or before it; rate-limit verification (a 6-digit code has a million possibilities, brute-forceable in minutes without limits).

### WebAuthn / passkeys

The browser and the device's authenticator generate a key pair per site (the relying party ID, your domain). Registration stores the public key and credential ID; authentication signs a server-issued random challenge, which the server verifies with the stored public key, checking the origin, RP ID, challenge, and the signature counter if present. Because the authenticator will only sign for the exact origin, phishing sites get nothing useful. Passkeys are WebAuthn credentials synchronised across a user's devices (iCloud Keychain, Google Password Manager, 1Password), making them practical for consumers; hardware security keys (YubiKey) are the non-synced variant for high assurance.

Implementation: use a library (`py_webauthn`, `@simplewebauthn/server`) and the browser's `navigator.credentials` API; store credential ID, public key, sign count, transports and a user-chosen name per credential; allow multiple credentials per user; support passkeys as a passwordless primary factor where appropriate, with conditional UI (autofill) for a smooth experience. Serve over HTTPS on your real domain (RP ID must match).

## Account recovery: the weak link

Every recovery path is an alternative login. Attackers target it because it is usually weaker than the front door.

- **Password reset by email**: generate a random, single-use, short-lived (15–60 min) token; store only its hash; send a link; on use, require a new password, invalidate the token and all other reset tokens, invalidate all sessions, and notify the user. Rate-limit requests. Respond identically whether the email exists or not. Never include the token in logs or analytics (strip query strings).
- **MFA recovery**: provide single-use backup codes at enrolment (hashed in storage), encourage multiple passkeys/devices, and make the "lost my device" path deliberately slow and verified (delay with notifications to all known channels, identity verification by support with a documented procedure). A recovery path that bypasses MFA with just an email makes MFA decorative.
- **Security questions**: do not. Answers are guessable or public.
- **Support-assisted recovery**: document the procedure, require evidence, log every action, and audit it; social engineering of support staff is a primary attack on high-value accounts.
- **Email change**: confirm on both old and new addresses; the old address is the recovery anchor.

## Passwordless

Magic links and passkeys remove passwords entirely. Magic links inherit email's weaknesses and are fine for low-risk consumer apps. Passkeys are the strong option and are now practical for most audiences; offer them as the preferred method with a password or email fallback during transition.

## Monitoring and hygiene

Notify users on new-device logins, password changes, MFA changes and recovery events. Log all of these as audit events. Expire sessions on password change. Periodically rehash to current parameters. Keep an eye on breach notification feeds for your users' domains if you run B2B.

## Common mistakes

- Fast hashes (SHA-256) or unsalted hashes.
- bcrypt with the 72-byte truncation unknown, allowing `password…` plus garbage to verify.
- Forced 90-day rotation and complexity rules.
- Unlimited TOTP verification attempts; no replay protection.
- SMS as the only MFA, especially for admins.
- Reset tokens stored in plaintext, long-lived, or reusable; sessions not invalidated on reset.
- MFA bypassable through recovery or support.
- TOTP secrets stored in plaintext in the users table.
- Different error messages or timings revealing account existence.
