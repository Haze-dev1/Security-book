## The problem

A query built by concatenating strings lets the data become part of the command. The database cannot tell which parts the developer wrote and which parts the user supplied. SQL injection is more than twenty-five years old, trivially prevented, and still causes major breaches every year because of one `f-string` in a corner of the codebase.

## The mechanism

:::vulnerable
```python
# Building SQL with string formatting
def find_user(db, email: str):
    return db.execute(f"SELECT id, email, role FROM users WHERE email = '{email}'").fetchone()
```

With `email = "' OR 1=1 --"` the query becomes:

```sql
SELECT id, email, role FROM users WHERE email = '' OR 1=1 --'
```

which returns the first user (often an admin). With `'; DROP TABLE users; --` on a driver that allows multiple statements, it deletes the table. With `' UNION SELECT id, password_hash, 'x' FROM users --` it exfiltrates hashes. Blind variants (`' AND (SELECT SUBSTR(password_hash,1,1) FROM users WHERE role='admin')='a' --`) extract data one character at a time from responses or timing, which automated tools do in minutes.
:::

:::secure
```python
# Parameterised query: the driver sends the SQL and the values separately
def find_user(db, email: str):
    return db.execute("SELECT id, email, role FROM users WHERE email = %s", (email,)).fetchone()
```

The database receives the statement with a placeholder and the value as a typed parameter. No matter what the string contains, it is a string compared with `email`. It cannot change the query's structure.
:::

Placeholder syntax varies (`%s` for psycopg, `$1` for asyncpg, `?` for sqlite3 and JDBC, `:name` for named parameters); the principle is identical. The wrong pattern is any of `+`, `%` formatting, `.format()`, f-strings or template literals that put *data* into *SQL text*.

## ORMs and query builders

SQLAlchemy, Django ORM, Prisma, Knex, ActiveRecord and friends parameterise automatically when you use their APIs:

```python
# SQLAlchemy: parameterised
stmt = select(User).where(User.email == email)
# Django: parameterised
User.objects.filter(email=email)
```

They stop protecting you when you drop to raw SQL with formatting:

:::vulnerable
```python
session.execute(text(f"SELECT * FROM users WHERE email = '{email}'"))   # raw + f-string
User.objects.raw(f"SELECT * FROM users WHERE email = '{email}'")
User.objects.extra(where=[f"email = '{email}'"])
prisma.$queryRawUnsafe(`SELECT * FROM users WHERE email = '${email}'`)
```
:::

:::secure
```python
session.execute(text("SELECT * FROM users WHERE email = :email"), {"email": email})
User.objects.raw("SELECT * FROM users WHERE email = %s", [email])
await prisma.$queryRaw`SELECT * FROM users WHERE email = ${email}`     # tagged template: parameterised
```
:::

Lint rules (Semgrep, Bandit, ESLint plugins) catch most raw-SQL-with-interpolation patterns; make them fail the build.

## Where parameters cannot be used

Parameters work for *values*. They do not work for identifiers (table and column names), keywords (`ASC`/`DESC`), or structural choices. Dynamic sorting and filtering are where injection survives in "parameterised" codebases:

:::vulnerable
```python
order = request.args.get("sort", "created_at")
db.execute(f"SELECT * FROM orders ORDER BY {order}")      # sort=id; DROP TABLE orders --
```
:::

:::secure
```python
SORTABLE = {"created_at": "created_at", "total": "total", "status": "status"}
col = SORTABLE.get(request.args.get("sort", "created_at"))
if col is None: raise ValidationFailed("unsupported sort")
direction = "DESC" if request.args.get("dir") == "desc" else "ASC"
db.execute(f"SELECT * FROM orders WHERE tenant_id = %s ORDER BY {col} {direction}", (tenant_id,))
```
The identifier comes from an **allow-list mapping**, never from the input itself; values remain parameters.
:::

Other cases: `LIKE` patterns (parameterise the value and escape `%` and `_` in it if the user should not control wildcards); `IN (...)` lists (expand to one placeholder per value, or use array parameters: `WHERE id = ANY(%s)` in PostgreSQL); table names per tenant (allow-list or quote with the driver's identifier quoting, e.g. `psycopg.sql.Identifier`); `LIMIT`/`OFFSET` (cast to int and bound); stored procedures that build dynamic SQL internally (`EXECUTE format(...)` with `%I`/`%L` quoting in PostgreSQL).

## Second-line defences

Because one mistake is enough, assume one will happen and limit it:

- **Least-privilege database roles**: the application role has `SELECT/INSERT/UPDATE/DELETE` on its tables only; no `DROP`, no `superuser`, no access to other schemas, no `pg_read_file`, no `COPY TO PROGRAM`. Separate roles for migrations (DDL) and runtime (DML). Chapter 7 of Part VIII.
- **Row-level security** so even a successful injection cannot cross tenants (Part III chapter 15).
- **No stacked queries**: most drivers disable multiple statements per call by default; keep it that way.
- **Input validation**: type and format checks at the boundary (an ID matches `^ord_[a-z0-9]{20}$`) reduce the attack surface; they are not the primary control because legitimate strings contain quotes.
- **Error handling**: never return database errors to clients; detailed errors turn blind injection into easy injection.
- **Statement timeouts** limit time-based blind extraction and damage from heavy injected queries.
- **Query logging and anomaly detection**: unusual query shapes (`UNION`, `pg_sleep`, `information_schema` access from the app role) are detectable with database audit logging (pgAudit) or a WAF in front.
- **WAF rules** catch common payloads; they are bypassable and noisy, a complement only.

## NoSQL and other query languages

Injection is not about SQL; it is about mixing data into any interpreted command:

- **MongoDB**: `db.users.find({ email: req.body.email })` where `email` is `{ "$ne": null }` matches everything; `$where` with string JavaScript is injectable. Validate types (strings must be strings) and never pass raw request objects as queries.
- **LDAP** filters, **XPath**, **GraphQL** resolvers that build strings, **Elasticsearch** query DSL from user JSON, **Redis** commands built from strings, and **shell commands** (chapter 12) share the pattern. The fix is always the same: structured APIs with parameters, allow-listed structure, and typed validation.
- **ORM filter injection**: Django's `filter(**request.GET)` lets users filter on arbitrary fields including `password_hash__startswith`. Allow-list filterable fields (Part III chapter 2).

## Testing and review

- Grep for SQL text combined with interpolation: `execute(f"`, `execute("..." % `, `.format(`, template literals with `${` inside SQL strings, `queryRawUnsafe`, `extra(`, `raw(` with formatting.
- Run SAST (Semgrep rulesets for SQL injection; Bandit B608) in CI.
- Use `sqlmap` in a sandbox against your own test deployment to confirm endpoints are not injectable; never against systems you do not own.
- Add integration tests feeding canonical payloads (`' OR 1=1 --`, `'; SELECT pg_sleep(5) --`) to every string parameter and asserting normal behaviour (not errors, not delays).
- Review database role grants against least privilege.

## Common mistakes

- Parameterising most queries and formatting one: the reporting endpoint, the admin search, the migration script.
- Dynamic `ORDER BY` and column selection from input.
- Escaping quotes manually instead of parameterising (escaping is error-prone and charset-dependent).
- Application connecting as the database owner or superuser.
- Returning raw database errors to clients.
- Treating ORM usage as a guarantee while using its raw escape hatches.
- Validating input and believing that makes concatenation safe.

## Exercises

1. In a sandbox, write the vulnerable `find_user` and exploit it with a UNION payload to read another table. Fix it and confirm the payload is now a harmless string.
2. Implement dynamic sorting and filtering with allow-lists for a list endpoint; try to inject through `sort` and `filter` parameters.
3. Create a least-privilege runtime role for your application's database and a separate migration role; verify the runtime role cannot DROP or read other schemas.
