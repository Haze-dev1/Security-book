# Secure Dependency Management and Supply Chain Security

:::objectives

- Operate a dependency vulnerability programme: inventory (SBOM), scanning, triage, update cadence, and exceptions.
- Harden the build pipeline: pinned actions, minimal permissions, provenance and signing.
- Evaluate new dependencies before adopting them.

## The problem

Your application is a thin layer of your code over a thick layer of other people's code, built by tools you did not write, fetched from registries you do not control, assembled by a pipeline with credentials to production. An attacker who compromises any link runs code inside your system with your privileges, without ever touching your code. Supply chain attacks have hit widely used npm and PyPI packages, build tools, CI actions and container base images; the targets are everyone downstream.

## Inventory: the SBOM

You cannot patch what you do not know you have. A [[sbom]] (CycloneDX or SPDX format) lists every component in an artifact with versions and hashes. Generate it in CI for every build (`syft`, `cyclonedx-*` tools, `npm sbom`, `trivy sbom`), attach it to the artifact, and store it. When the next critical vulnerability is announced, the question "are we affected, where?" becomes a query over SBOMs rather than a week of archaeology. Clients in regulated sectors increasingly require SBOMs as a deliverable.

## Scanning and triage

- **Software composition analysis (SCA)**: compares your dependency tree against vulnerability databases. Tools: `npm audit`, `pip-audit`, `osv-scanner`, Trivy, Grype, Snyk, Dependabot alerts, GitHub's dependency review. Run in CI on every PR and on a schedule against main (new CVEs appear without code changes).
- **Image scanning**: Trivy/Grype on built images; ECR's built-in scanning (basic or enhanced via Inspector) on push and continuously.
- **Policy**: fail the build on critical/high findings with a *fix available*; warn on the rest; require an explicit, time-boxed exception record for anything accepted. Without a policy, scanners become noise and get ignored.
- **Triage**: not every CVE in a dependency is exploitable in your usage (the vulnerable function may never be called). Reachability analysis helps; so does VEX (Vulnerability Exploitability eXchange) to record "not affected, because…". Prioritise by exploitability (known exploited vulnerabilities lists), exposure (Internet-facing?), and privilege.
- **Cadence**: automated update PRs (Dependabot, Renovate) grouped weekly for minors/patches, immediate for security fixes, scheduled for majors; base images rebuilt monthly and on CVE; runtimes updated on their security releases. Measure mean time to remediate critical findings and keep it under days.

## Hardening the pipeline

```yaml
# GitHub Actions: supply-chain hygiene
name: build
on: { push: { branches: [main] }, pull_request: {} }
permissions: { contents: read }                                  # default deny; grant per job
jobs:
  build:
    runs-on: ubuntu-24.04
    permissions: { contents: read, id-token: write, packages: write }   # OIDC for cloud, push for registry
    steps:
      - uses: actions/checkout@<full-commit-sha>                  # pinned to SHA, not @v4
      - uses: actions/setup-node@<full-commit-sha>
        with: { node-version-file: .nvmrc }
      - run: npm ci --ignore-scripts                               # lockfile, no install scripts
      - run: npm audit --audit-level=high
      - run: npx osv-scanner --lockfile=package-lock.json
      - name: Safe use of untrusted input
        env: { PR_TITLE: ${{ github.event.pull_request.title }} } # pass via env, never interpolate into run:
        run: echo "Title length: ${#PR_TITLE}"
      - uses: aws-actions/configure-aws-credentials@<sha>
        with: { role-to-assume: arn:aws:iam::123456789012:role/ci-build, aws-region: eu-west-1 }   # OIDC, no stored keys
      - run: docker build --pull -t "$ECR/app:${GITHUB_SHA}" . && docker push "$ECR/app:${GITHUB_SHA}"
      - run: syft "$ECR/app:${GITHUB_SHA}" -o cyclonedx-json > sbom.json
      - run: trivy image --exit-code 1 --severity CRITICAL,HIGH --ignore-unfixed "$ECR/app:${GITHUB_SHA}"
      - run: cosign sign --yes "$ECR/app@$(docker inspect --format='{{index .RepoDigests 0}}' "$ECR/app:${GITHUB_SHA}" | cut -d@ -f2)"
```

Principles: least privilege for the workflow token; actions pinned by SHA (with a bot to update them); untrusted inputs never in shell interpolation; forks cannot reach secrets; OIDC federation instead of stored cloud keys; artifacts immutable, scanned, signed; production deployments from protected environments with required reviewers (Part X).

## Provenance and signing

**Provenance** is a signed statement of how an artifact was built: the source repository and commit, the builder, the build instructions. The SLSA framework defines levels; GitHub's artifact attestations and Sigstore's `cosign attest` produce them. **Signing** (cosign with keyless OIDC-based identities or KMS keys) lets deployers verify an image came from your pipeline and was not replaced. Verification happens at deploy time: a Kubernetes admission policy (Kyverno, Sigstore policy-controller) or a deploy script step refusing unsigned or unattested images. For client deliverables, a signed image plus SBOM plus provenance is the modern equivalent of a release with checksums.

## Evaluating a new dependency

Before adding a package, ask: Is it necessary, or is it twenty lines you can write? Who maintains it, how many maintainers, how active, how responsive to security reports? How many transitive dependencies does it pull in? Does it have install scripts or native code? Is it widely used (downloads, dependents)? Is there a security policy and a history of CVEs handled well? What licence (copyleft obligations matter for client deliverables)? Record the decision for anything significant. Removing dependencies is as valuable as updating them.

## Vendoring, mirrors and air gaps

For clients with restricted networks, run a proxying registry (CodeArtifact, Artifactory, Nexus, Verdaccio) that caches approved packages, enforces allow-lists, and keeps builds working when the public registry is down or a package is yanked. For truly air-gapped environments, vendor dependencies and base images into the client's registry through a controlled, scanned import process.

## Incident response for a compromised dependency

When a package you use is reported malicious: identify affected artifacts via SBOMs; determine whether the malicious version was ever installed (lockfile history, build logs); if yes, assume compromise of every environment that ran it, rotate every secret those environments could access (chapter 17), inspect for persistence, and rebuild from clean sources; pin to a known-good version; communicate to clients if their environments were affected.

## Common mistakes

- No lockfile, or `npm install` in CI.
- Actions referenced by mutable tags; broad `permissions: write-all`.
- Stored cloud access keys in CI secrets.
- Scanners that only warn; findings ignored for months.
- No SBOM; "are we affected?" takes days.
- Base images on floating tags, never rebuilt.
- Treating a compromised dependency as "just update it" without rotating secrets.
- Adding a dependency for trivial functionality that pulls in 300 transitive packages.

## Exercises

1. Generate an SBOM for one of your artifacts and scan it. Write a triage decision (fix, exception with date, not affected with reason) for each high finding.
2. Harden a GitHub Actions workflow: SHA-pinned actions, minimal permissions, OIDC to AWS, untrusted input via env only, signed image with cosign. Verify the signature in a deploy step.
3. Set up Renovate or Dependabot with grouping and a minimum release age; merge one week's updates through your test suite.
