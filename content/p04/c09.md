## The problem

Browsers attach cookies automatically to requests to the matching site, regardless of which page initiated the request. A page on `evil.example` can make the victim's browser send `POST https://bank.example/transfer` with the victim's bank cookie attached. The bank sees a well-formed, authenticated request. That is [[csrf|cross-site request forgery]]: the attacker does not steal the credential; they borrow the browser that holds it.

What makes an endpoint vulnerable: it authenticates by cookie (or HTTP Basic auth, which browsers also send automatically), it changes state, and it accepts requests that a cross-site form or image can produce (GET, or POST with form content types) without any proof that the request came from your own pages.

## Defence 1: SameSite cookies

`SameSite=Lax` (the modern browser default when unspecified, but set it explicitly): the cookie is not sent on cross-site POSTs, iframes, images, or fetches; it *is* sent on top-level GET navigations (clicking a link to your site). This blocks the classic form-POST attack entirely, as long as your state-changing endpoints are not GET. `SameSite=Strict` also blocks the cookie on cross-site top-level navigations, which breaks "click a link from email and be logged in" but is appropriate for high-security sessions or a second "sensitive actions" cookie.

Limits: `Lax` does not protect GET endpoints that change state (never have those); some older browsers ignore SameSite; subdomains count as same-site, so an XSS or an attacker-controlled subdomain (`user-content.client.com`) can still forge requests; and `SameSite=None` cookies (needed for embedded third-party contexts) have no protection. Therefore SameSite is the first layer, not the only one.

## Defence 2: anti-CSRF tokens

The server requires a secret the attacker cannot obtain to accompany every state-changing request. Because the same-origin policy prevents `evil.example` from *reading* your pages or responses, a token embedded in your page or readable by your JavaScript is unavailable to the attacker.

- **Synchroniser token**: a random per-session token stored server-side; embedded in forms as a hidden field (and exposed to JavaScript for fetch requests via a meta tag or an endpoint); compared on every POST/PUT/PATCH/DELETE. Frameworks implement this (Django, Rails, Spring Security).
- **Double-submit cookie**: the token is set in a cookie *and* sent in a header or body; the server checks they match. Stateless. Vulnerable to cookie injection from subdomains unless the token is also signed/HMAC'ed with a server secret and bound to the session (the "signed double-submit" variant).
- **Custom header requirement for APIs**: a request with a custom header (`X-Requested-With`, `X-CSRF-Token`) cannot be made cross-site without a CORS preflight, which your server will refuse for foreign origins. So an API that *only* accepts JSON with a custom header, and rejects form content types, is CSRF-resistant for browser clients that follow CORS. This relies on correct CORS configuration (chapter 14) and on rejecting `text/plain` and form bodies.

```python
# Starlette/FastAPI sketch: signed double-submit, bound to the session
import hmac, hashlib, secrets

def csrf_token_for(session_id: str) -> str:
    nonce = secrets.token_urlsafe(16)
    sig = hmac.new(settings.csrf_key, f"{session_id}:{nonce}".encode(), hashlib.sha256).hexdigest()
    return f"{nonce}.{sig}"

def verify_csrf(session_id: str, token: str) -> bool:
    try: nonce, sig = token.split(".", 1)
    except ValueError: return False
    expected = hmac.new(settings.csrf_key, f"{session_id}:{nonce}".encode(), hashlib.sha256).hexdigest()
    return hmac.compare_digest(expected, sig)

class CSRFMiddleware:
    SAFE = {"GET", "HEAD", "OPTIONS"}
    async def __call__(self, request, call_next):
        if request.method not in self.SAFE and request.cookies.get("__Host-sid"):
            token = request.headers.get("X-CSRF-Token") or (await request.form()).get("csrf_token") if request.headers.get("content-type","").startswith("application/x-www-form-urlencoded") else request.headers.get("X-CSRF-Token")
            if not token or not verify_csrf(request.cookies["__Host-sid"], token):
                return JSONResponse({"title": "CSRF check failed", "status": 403}, status_code=403)
        return await call_next(request)
```

The frontend reads the token (from a meta tag rendered server-side, or from a `GET /csrf` endpoint that returns it for the current session) and sends it in `X-CSRF-Token` on every mutating request.

## Defence 3: origin verification

Browsers send `Origin` on cross-origin requests (and `Referer` more generally). Reject state-changing requests whose `Origin` (or, failing that, `Referer`) does not match your own origins. Cheap, effective as a layer; not sufficient alone because some requests lack both headers and some proxies strip them.

## Defence 4: safe method semantics

GET, HEAD and OPTIONS must never change state. `<img src="/logout">` logs the user out; `<img src="/orders/123/delete">` deletes an order; link prefetchers trigger both. This is an HTTP rule (Part II chapter 8) and a CSRF defence at once.

## Special cases

**Login CSRF**: the attacker logs the victim into the *attacker's* account (forged login POST with attacker credentials), so the victim's subsequent actions (saving a card, uploading documents) land in the attacker's account. Defence: CSRF-protect the login form too (a pre-login session with a token), and rotate sessions at login.

**Logout CSRF**: an annoyance more than a breach, but protect it anyway.

**JSON APIs with cookie auth**: reject form content types; require a custom header; configure CORS strictly; SameSite cookies. With all three, token-based CSRF protection is often unnecessary, but many teams keep it for defence in depth.

**Bearer-token APIs**: not vulnerable to CSRF (the browser does not attach `Authorization` headers automatically), but vulnerable to token theft via XSS if tokens are in JavaScript-accessible storage. Pick your poison deliberately: HttpOnly cookies plus CSRF defence, or header tokens plus strict XSS defence.

**Clickjacking**: a related attack where your page is framed invisibly on the attacker's site and the user is tricked into clicking. Defence: `Content-Security-Policy: frame-ancestors 'none'` (or `'self'`) and the legacy `X-Frame-Options: DENY` (chapter 15).

**WebSockets**: the handshake carries cookies and is not subject to CORS; verify the `Origin` header on the handshake (cross-site WebSocket hijacking).

## Cookie configuration summary

```http
Set-Cookie: __Host-sid=<random>; Path=/; Secure; HttpOnly; SameSite=Lax; Max-Age=43200
Set-Cookie: __Host-csrf=<token>; Path=/; Secure; SameSite=Strict          (double-submit variant; readable by JS, so no HttpOnly)
```

Never set `Domain` on session cookies; never use `SameSite=None` on them; never carry session IDs in URLs.

## Testing

- For each mutating endpoint: craft a cross-site form POST from a different origin (a local HTML file on another port) while logged in. Expect rejection.
- Remove the CSRF header from a legitimate fetch; expect 403.
- Verify GET endpoints change nothing (grep for handlers on GET that write).
- Confirm cookie attributes in responses.
- Attempt login CSRF.
- Check frame-ancestors with a test page that iframes your app.
- Automated scanners (ZAP) detect missing tokens; manual tests catch logic.

## Common mistakes

- Relying on CORS to prevent CSRF (CORS controls reading, not sending).
- State-changing GET endpoints.
- `SameSite=None` on the session cookie to fix an embedded widget.
- Double-submit tokens without signing, defeated by subdomain cookie injection.
- CSRF tokens checked only on some endpoints (the new one was forgotten).
- Login form without CSRF protection.
- Accepting `text/plain` or form bodies on JSON APIs, enabling simple-request CSRF.
- Trusting `Referer` alone.
