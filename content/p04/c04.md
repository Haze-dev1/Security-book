# Session-Based Authentication

:::objectives
- Implement server-side sessions that resist fixation, hijacking, replay and brute force.
- Choose session storage, lifetimes, rotation and invalidation policies deliberately.
- Build login, logout, "log out everywhere", remember-me and step-up authentication correctly.
- Test the session layer against the attacks that actually occur.
:::

## The problem

After a user proves who they are once, every subsequent request must be tied to that proof without re-entering a password. The session is that tie, and because it is a bearer secret (whoever presents it is treated as the user), its generation, transport, storage, lifetime and termination are all security-critical. Session bugs are quiet: nothing crashes, the attacker simply becomes someone else.

## Implementation

```python
# sessions.py — Redis-backed sessions with rotation, sliding + absolute expiry, generation-based invalidation
import secrets, json, time
IDLE_TTL = 60 * 60 * 2          # 2 hours idle
ABSOLUTE_TTL = 60 * 60 * 12     # 12 hours max

class SessionStore:
    def __init__(self, redis): self.r = redis

    async def create(self, user_id: str, generation: int, mfa: bool) -> str:
        sid = secrets.token_urlsafe(32)
        now = int(time.time())
        data = {"uid": user_id, "gen": generation, "created": now, "auth_time": now, "mfa": mfa}
        await self.r.set(f"sess:{sid}", json.dumps(data), ex=IDLE_TTL)
        await self.r.sadd(f"user_sessions:{user_id}", sid)        # for listing/revoking per user
        return sid

    async def load(self, sid: str, current_generation_for) -> dict | None:
        raw = await self.r.get(f"sess:{sid}")
        if not raw: return None
        data = json.loads(raw)
        now = int(time.time())
        if now - data["created"] > ABSOLUTE_TTL: await self.destroy(sid, data["uid"]); return None
        if data["gen"] != await current_generation_for(data["uid"]): await self.destroy(sid, data["uid"]); return None
        await self.r.expire(f"sess:{sid}", IDLE_TTL)              # sliding idle window
        return data

    async def rotate(self, old_sid: str, data: dict) -> str:       # at login and privilege change
        new_sid = secrets.token_urlsafe(32)
        pipe = self.r.pipeline()
        pipe.set(f"sess:{new_sid}", json.dumps(data), ex=IDLE_TTL); pipe.delete(f"sess:{old_sid}")
        pipe.srem(f"user_sessions:{data['uid']}", old_sid); pipe.sadd(f"user_sessions:{data['uid']}", new_sid)
        await pipe.execute()
        return new_sid

    async def destroy(self, sid: str, user_id: str):
        await self.r.delete(f"sess:{sid}"); await self.r.srem(f"user_sessions:{user_id}", sid)

    async def destroy_all(self, user_id: str):                      # "log out everywhere" / password change
        sids = await self.r.smembers(f"user_sessions:{user_id}")
        if sids: await self.r.delete(*[f"sess:{s}" for s in sids])
        await self.r.delete(f"user_sessions:{user_id}")
        # also: UPDATE users SET session_generation = session_generation + 1 (belt and braces)
```

## Attacks and defences

**Session fixation**: the attacker sets a known session ID in the victim's browser (via a link or subdomain cookie injection) before login; after login the attacker uses the same ID. Defence: issue a new ID at login (rotation), never accept session IDs from URLs, use the `__Host-` prefix so subdomains cannot plant cookies.

**Session hijacking via theft**: XSS reading the cookie (defeated by HttpOnly), network sniffing (Secure plus HSTS), malware on the device (not solvable by you; short lifetimes and anomaly detection limit damage). Binding sessions to IP addresses breaks mobile users; binding to a coarse fingerprint (user agent) with re-authentication on change is a reasonable soft signal.

**Brute force on session IDs**: impossible with 256-bit random IDs; trivial with sequential or timestamp-based IDs. Use the CSPRNG.

**Brute force on login**: rate limits per account and IP, progressive delays, lockout with care (attackers can lock out victims), CAPTCHA after failures, breached-password checks, MFA.

**CSRF**: SameSite=Lax cookies block most; add a synchroniser token or double-submit cookie for state-changing requests when supporting older clients or SameSite=None (chapter 9).

**Session not invalidated**: on logout (cookie cleared but server session alive: it can be replayed), password change, role change, account compromise. Invalidate server-side; implement "log out everywhere".

**Replay after expiry**: absolute expiry caps a stolen session's lifetime; idle expiry ends abandoned sessions; both enforced server-side (the cookie's Max-Age is advisory).

**Privilege change without rotation**: a user becomes admin mid-session; rotate the ID and refresh the principal.

## Lifetimes

| Context | Idle | Absolute | Step-up window |
|---|---|---|---|
| Consumer web app | 1–7 days (with remember-me) | 30 days | 10 min for payment/credential changes |
| B2B SaaS | 2–8 hours | 12–24 hours | 5–15 min |
| Admin / internal tools | 15–60 minutes | 8–12 hours | Every sensitive action |
| Banking-style | 5–15 minutes | 1 hour | Per transaction |

**Remember me** should be a separate, long-lived, single-use token (series + token, rotated on each use, stored hashed) that can *create* a new session, rather than a session that lasts a month. Theft of a remember-me token is then detectable (the legitimate user's next use fails because the series was consumed) and revocable.

## Storage

Redis (ElastiCache Multi-AZ) is the standard: fast, TTL-native, shared across instances. Treat it as a hard dependency for authentication (fail closed if unreachable) and therefore make it highly available. A database table works at lower scale (index on session ID, periodic cleanup of expired rows). In-process memory only for single-instance prototypes. Store minimal data (IDs, timestamps, auth context); load user details from the user table per request or cache them briefly. Never store the password or raw tokens in the session.

## Concurrent sessions

Decide: unlimited (default for web), limited (banking often allows one), or visible (a "your active sessions" page listing device, location hint, last seen, with per-session revoke). The `user_sessions` set above enables the page and the revocation.

## Logging and monitoring

Log login success and failure (with account and IP hints, never the password), MFA events, logouts, session revocations, and step-up prompts. Alert on failure spikes (credential stuffing), on logins from new countries for admins, and on impossible travel if you have geo data. These logs are also the audit trail chapter 22 requires.

## Testing the session layer

- Login issues a new session ID (fixation test: pre-login ID ≠ post-login ID).
- Cookie has Secure, HttpOnly, SameSite, no Domain, `__Host-` prefix.
- Logout invalidates server-side (replay the old cookie: expect 401).
- Password change invalidates other sessions.
- Idle and absolute expiry enforced server-side even if the cookie is still present.
- Unknown session IDs produce 401 without timing leaks.
- Rate limiting on login works per account and per IP.

## Common mistakes

- Session IDs in URLs (leaked via logs, referrers, bookmarks).
- Not rotating at login.
- Logout that only clears the cookie.
- Sessions that never expire, or expire only client-side.
- Storing roles in the session and never refreshing them; role revocation is ignored for hours.
- Session store as a soft dependency, failing open when Redis is down.
- Binding to IP and breaking mobile users, then removing all binding.
- Separate admin sessions with weaker rules.
