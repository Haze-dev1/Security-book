## The problem

Cryptography reduces the problem of protecting data to the problem of protecting keys. Secrets management is the same problem for credentials: database passwords, API keys, signing keys, certificates. The failure modes are mundane and devastating: a key in a Git history, a `.env` file on a laptop, an environment variable dumped by a debug endpoint, a secret never rotated after a contractor left, a backup of a backup containing everything. The solution is structural: secrets live in one audited place, are delivered to workloads through identity rather than copies, rotate on a schedule, and are never written down anywhere else.

## Envelope encryption and KMS

A [[kms]] holds **master keys** (customer managed keys, CMKs) in hardware security modules. You never see the key material; you call the service to encrypt, decrypt, sign or generate keys, and every call is authorised by IAM and logged in CloudTrail.

Encrypting every record by calling KMS would be slow and expensive. [[envelope encryption]] solves this:

AWS services use this internally for S3, EBS, RDS and Secrets Manager encryption; the AWS Encryption SDK and S3 client-side encryption do it for your own data. Key policies and grants control who may use each key; a key per environment and per data classification is a sane default; multi-region keys exist for DR scenarios.

## Secrets management

A secrets manager (AWS Secrets Manager, Parameter Store SecureString, HashiCorp Vault, cloud equivalents) stores secrets encrypted with KMS, controls access with IAM, versions them, audits every read, and can rotate them automatically.

For most client deployments on AWS: Parameter Store for configuration and low-churn secrets, Secrets Manager for database credentials with rotation and anything needing cross-account access. Vault when the client already runs it or needs dynamic credentials across clouds.

## Getting secrets into workloads

The hierarchy from worst to best (Part I chapter 8 introduced it):

1. In code or images: never.
2. In a file on the host, restricted permissions: acceptable for a single VM with no better option; weak audit, manual rotation.
3. **Injected by the platform at start**: ECS task definitions reference a Secrets Manager or Parameter Store ARN in `secrets`; the agent fetches it with the *task execution role* and sets it as an environment variable in the container. Kubernetes: External Secrets Operator syncs into Secrets, or the Secrets Store CSI driver mounts them as files. Simple and standard. Downside: environment variables are visible to the whole process tree and in some debug outputs; rotation requires a restart.
4. **Fetched by the application at runtime** via SDK using its IAM role: `GetSecretValue` at start-up and on a refresh interval or on authentication failure. Enables rotation without redeploy, fine-grained audit, and keeps secrets out of the environment. Cache in memory with a TTL; handle the brief window during rotation where both old and new versions are valid (Secrets Manager's `AWSCURRENT`/`AWSPREVIOUS` staging labels exist for this).
5. **No long-lived secret at all**: IAM database authentication (RDS issues 15-minute tokens to the role), IAM roles for AWS services, workload identity federation to third parties (OIDC from GitHub Actions to AWS, Part X chapter 2), Vault dynamic secrets. Nothing to leak, nothing to rotate manually.

```python
# Runtime fetch with caching and rotation tolerance (boto3)
import boto3, json, time
class SecretCache:
    def __init__(self, ttl=300): self.c = boto3.client("secretsmanager"); self.ttl = ttl; self.cache = {}
    def get(self, name: str) -> dict:
        v = self.cache.get(name)
        if v and time.time() - v[0] < self.ttl: return v[1]
        val = json.loads(self.c.get_secret_value(SecretId=name)["SecretString"])
        self.cache[name] = (time.time(), val); return val
    def invalidate(self, name): self.cache.pop(name, None)      # call on auth failure, then retry once

# usage: on PostgreSQL auth failure, invalidate and reconnect with the fresh value
```

## Rotation

Rotation limits the window a leaked secret is useful and proves the rotation procedure works before you need it in anger.

- **Database credentials**: Secrets Manager rotation with the alternating-users strategy (two users; rotate the inactive one, then swap) avoids downtime; applications must re-read on failure. Or use IAM authentication and skip the problem.
- **API keys to third parties**: most providers allow two active keys; create the new, deploy, delete the old. Schedule quarterly or per policy; immediately on suspicion.
- **Signing keys (JWT, webhooks)**: publish the new public key (JWKS) or share the new secret, sign with the new, keep the old for verification until all tokens expire, then retire. Key IDs (`kid`) make this clean.
- **KMS keys**: enable automatic annual rotation of the key material; old versions remain usable for decryption transparently. Re-encrypting existing data is unnecessary for KMS rotation; it is necessary if you suspect the *data key* leaked.
- **TLS certificates**: Part II chapter 10; automated.
- **Human credentials**: SSO with MFA; access keys for IAM users should not exist (chapter 18).

Track every secret in an inventory: name, location, owner, consumers, rotation method, last rotated, rotation deadline. Alert when a deadline passes.

## Access control and audit

- One IAM role per workload with permission to read exactly its secrets (resource ARNs, not `*`); condition keys to restrict by tag or VPC endpoint.
- Humans read production secrets rarely, via a break-glass path (a role requiring MFA, with alerting on assumption), never routinely.
- CloudTrail logs every `GetSecretValue`, `Decrypt` and `GenerateDataKey`; alert on reads from unexpected principals or volumes, and on key policy changes.
- Separate KMS keys and secrets per environment; staging must not be able to read production secrets.
- Encryption context on every KMS call (tenant, purpose) so misuse is both prevented and visible in logs.

## When a secret leaks

1. **Rotate immediately.** Do not debate, do not first purge Git history; rotation is the only thing that ends the exposure.
2. **Revoke** the old credential at the provider (delete the key, disable the user, revoke the token).
3. **Assess** what the credential could access and look for use: CloudTrail, provider logs, database audit logs, since the earliest possible exposure.
4. **Contain** related exposure: anything the leaked secret could have unlocked (other secrets readable with it) is now suspect.
5. **Clean up** the leak location (purge from Git with `git filter-repo`, delete the paste, rotate anything else in the same file), and add scanning (Part X chapter 3) so it does not recur.
6. **Record** it as an incident with a postmortem; "a secret was in Git" is a process failure, not an individual one.

Keys pushed to public repositories are found and abused by automated scanners within minutes; speed matters.

## Secrets in development and CI

Developers use separate, low-privilege development secrets (or local stand-ins: a local database, a sandbox API key), never production values. CI gets secrets from the platform's secret store, scoped per environment, with production secrets only in protected environments requiring approval (Part X chapter 9). Prefer OIDC federation so CI holds no long-lived cloud credentials at all. Secret scanning runs on every push and on the whole history.

## Common mistakes

- Secrets in Git, Docker images, build args, CloudFormation templates or Terraform state in a public or shared bucket.
- Production secrets in developers' `.env` files.
- One secret for all environments.
- Secrets logged at start-up ("Connecting with password=…") or in error messages.
- Applications with `secretsmanager:*` on `*`.
- No inventory; secrets of departed staff and old integrations still valid.
- Rotation never tested until the night it is needed.
- Treating a leaked secret as handled once it is deleted from the repository.
