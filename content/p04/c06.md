## The problem

Two different needs share a toolbox. First: an application wants to access a user's data in *another* system (read their calendar, post on their behalf) without receiving their password for that system. That is **delegated authorization**, which [[oauth 2.0]] solves. Second: an application wants to let users log in with an identity managed elsewhere (their company directory, Google) instead of a local password. That is **federated authentication**, which [[openid connect]] adds on top of OAuth. Enterprise clients call the second one **SSO**, and expect you to support it.

Getting these wrong produces account takeover: a mis-validated ID token, a redirect URI that an attacker can control, a missing state parameter. The flows are well-specified; the failures are in skipped steps.

## Roles and vocabulary

- **Resource owner**: the user.
- **Client**: your application (the one asking for access or identity). *Confidential* clients can keep a secret (server-side apps); *public* clients cannot (SPAs, mobile apps).
- **Authorization server**: the identity provider (IdP) that authenticates the user and issues tokens.
- **Resource server**: the API that accepts access tokens.
- **Access token**: a credential for calling the resource server. Opaque or JWT; the client should treat it as opaque.
- **ID token** (OIDC): a JWT *for the client* stating who the user is and how they authenticated.
- **Refresh token**: a long-lived credential to obtain new access tokens.
- **Scopes**: strings naming the access requested (`openid profile email`, `orders:read`).

### Flows to avoid

- **Implicit flow** (`response_type=token`): tokens delivered in the URL fragment. Leaks tokens via history and referrers; no client authentication. Deprecated; use authorization code with PKCE for SPAs.
- **Resource owner password credentials**: the app collects the user's IdP password and exchanges it directly. Defeats the purpose (the app sees the password; no MFA or federation). Removed in OAuth 2.1.
- **Client credentials** is fine, but only for machine-to-machine access with no user involved (chapter 18).

## Integrating with an identity provider

Practical steps for an application supporting enterprise SSO:

1. **Use a maintained library** for the client side (authlib for Python, openid-client for Node, framework integrations). Do not hand-roll token validation.
2. **Use discovery**: fetch `/.well-known/openid-configuration` for endpoints and JWKS; cache; refresh on key rotation.
3. **Register redirect URIs exactly** (no wildcards). One per environment.
4. **Per-tenant IdP configuration**: enterprise SaaS stores issuer, client ID, client secret (in the secrets manager) and role mappings per tenant. Route users to their tenant's IdP by email domain or a tenant-specific login URL. Validate that the `iss` in the returned token is the one configured for *that* tenant.
5. **Just-in-time provisioning**: create the local user on first login with the IdP's claims, or require pre-provisioning via SCIM (chapter below).
6. **Role mapping**: map IdP groups (`groups` claim, or a custom claim) to application roles; re-evaluate on every login and, if roles can change mid-session, periodically. Default to the least privileged role when no mapping matches.
7. **Offboarding**: a user removed at the IdP must lose access. With JIT provisioning, this happens at their next login attempt only; to be prompt, implement **SCIM** (System for Cross-domain Identity Management), which lets the IdP push user create/update/deactivate events to your app, or at minimum short sessions plus periodic revalidation.
8. **Account linking**: a user with a local password who later arrives via SSO: link accounts only after verifying ownership (they are logged into the local account, or email verified by both), or you create an account-takeover path via unverified emails.
9. **Testing**: Keycloak or a local Cognito user pool as a test IdP; test wrong `state`, wrong `nonce`, wrong `aud`, expired token, unregistered redirect.

## Providers

- **Amazon Cognito**: user pools as an IdP with federation to social and SAML/OIDC providers; cheap; integrates with ALB authentication and API Gateway. Rough edges in customisation.
- **Okta, Auth0, Entra ID (Azure AD), Google Workspace, Ping, OneLogin**: enterprise IdPs your clients already run. Your job is usually to be a *relying party* to these.
- **Keycloak**: open-source IdP you can self-host; useful for on-premises or air-gapped client environments.
- **ALB authentication**: an ALB can perform the OIDC flow itself and pass identity headers to targets (`x-amzn-oidc-data`); convenient for internal tools, with the caveat that the backend must verify the ALB's JWT signature and only accept it from the ALB.

## SAML in brief

Older enterprises run SAML 2.0 rather than OIDC. Concepts map: the IdP, the service provider (you), assertions (XML documents signed by the IdP containing the user's identity and attributes), the browser-redirect binding. Dangers: XML signature wrapping attacks and comment-injection bugs in parsers; use a maintained library (python3-saml, passport-saml, or let your IdP broker handle SAML and present OIDC to your app, which Cognito, Auth0 and Keycloak all do). Validate the assertion signature, the audience, the recipient, the time window and the `InResponseTo` when using SP-initiated flows. Metadata exchange (XML files) and certificate rotation are the operational chores.

## Security checklist for OIDC clients

```checklist
# OIDC relying party checklist
- Authorization code flow with PKCE (S256); no implicit, no password grant.
- Exact redirect URI registration per environment; HTTPS only.
- Random state and nonce stored server-side and verified on callback.
- ID token: signature via discovered JWKS, iss, aud == client_id, exp, nonce, azp if present.
- Users keyed by (iss, sub), never by email alone; email_verified respected.
- Client secrets in a secrets manager; rotated; none in frontend code.
- Access tokens treated as opaque by the client; sent only to the intended resource server.
- Own session established after login; tokens not stored in localStorage.
- Role mapping with least-privilege default; re-evaluated at login.
- Offboarding: SCIM or short sessions with revalidation; IdP-side deactivation tested end to end.
- Account linking only after ownership verification.
- Logout clears the local session; RP-initiated logout if single logout required.
```

## Common mistakes

- Missing `state` check (login CSRF, code injection).
- Missing `nonce` or `aud` validation on the ID token.
- Wildcard or loosely matched redirect URIs (open redirect → code theft).
- Keying users by email and trusting unverified emails from the IdP.
- Storing tokens in localStorage.
- Using the implicit flow for SPAs.
- Treating the IdP's access token as proof of identity for *your* API (it is for the IdP's APIs; use the ID token for identity and issue your own session or tokens).
- Not handling offboarding; departed employees retain access via long sessions.
- SAML libraries that are unmaintained or hand-written XML parsing.

## Exercises

1. Run Keycloak locally, register your app as a confidential client with PKCE, and implement login with a library. Verify each validation step by deliberately breaking it (wrong state, wrong nonce, wrong audience).
2. Add per-tenant IdP configuration and route users by email domain. Test that a token from tenant A's IdP cannot log into tenant B.
3. Implement a SCIM `/Users` endpoint (create, update, deactivate) and test deactivation ends access promptly.
