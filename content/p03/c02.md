# REST API Design

:::objectives
- Design resource-oriented HTTP APIs with consistent naming, methods, status codes and error shapes.
- Implement pagination, filtering, sorting and field selection that perform well and do not leak data.
- Validate input rigorously at the boundary and return actionable errors.
- Version an API and evolve it without breaking clients.
:::

:::prereq
Part II chapter 8; Part I chapter 13.
:::

## The problem

An API is a contract with people you cannot talk to: mobile apps you cannot force to update, a client's integration team, your own frontend six months from now. Inconsistency costs every consumer time; ambiguity causes bugs; a careless change breaks production for someone else. Good API design is mostly about being boringly predictable, and about doing the hard things (pagination, errors, versioning) the same way every time.

## Resources and URLs

Model the domain as **resources** (nouns) with identifiers, and use HTTP methods as the verbs:

```
GET    /v1/orders                 list orders (filtered, paginated)
POST   /v1/orders                 create an order
GET    /v1/orders/{id}            fetch one
PATCH  /v1/orders/{id}            partial update
PUT    /v1/orders/{id}            full replacement (less common)
DELETE /v1/orders/{id}            delete (or soft-delete)
GET    /v1/orders/{id}/items      sub-resource collection
POST   /v1/orders/{id}/cancel     action that does not map to CRUD: a verb sub-resource, used sparingly
```

Conventions that prevent arguments: plural nouns; lower-case, hyphenated path segments; identifiers that are opaque and non-sequential (UUIDv7 or prefixed IDs like `ord_01HZX…`) so URLs do not reveal volume or invite enumeration; nesting at most two levels deep; no verbs in URLs except for genuine actions that would otherwise be awkward (`/cancel`, `/approve`, `/search` with complex bodies).

Use the methods by their semantics (Part II chapter 8): GET is safe and cacheable; PUT and DELETE are idempotent; POST is for creation and non-idempotent actions, and should support an idempotency key when it causes side effects (chapter 3).

## Status codes and responses

| Situation | Code | Body |
|---|---|---|
| Fetched | 200 | the resource |
| Created | 201 + `Location` header | the resource |
| Accepted for async processing | 202 | a job resource with a status URL |
| Deleted, nothing to return | 204 | empty |
| Malformed request (bad JSON, wrong types) | 400 | error |
| Unauthenticated | 401 + `WWW-Authenticate` | error |
| Authenticated but forbidden | 403 (or 404 to avoid confirming existence) | error |
| Not found | 404 | error |
| State conflict (duplicate, version mismatch) | 409 | error with details |
| Valid JSON, invalid semantics | 422 | error with field details |
| Rate limited | 429 + `Retry-After` | error |
| Server bug | 500 | generic error with request ID |
| Dependency down | 503 + `Retry-After` | error |

Return a **consistent error shape**. RFC 9457 (Problem Details) is a good standard:

```json
{
  "type": "https://api.client.com/errors/validation",
  "title": "Validation failed",
  "status": 422,
  "detail": "One or more fields are invalid.",
  "instance": "/v1/orders",
  "request_id": "7f3a9c2e-...",
  "errors": [
    {"field": "items[0].qty", "message": "must be at least 1", "code": "min"},
    {"field": "customer_id", "message": "unknown customer", "code": "not_found"}
  ]
}
```

Never leak internals in errors: stack traces, SQL, file paths, library versions. Log them server-side with the request ID; return the ID to the user so support can correlate.

## Validation at the boundary

Every input (path, query, headers, body) is validated against a schema before any logic runs: types, required fields, lengths, ranges, formats, enums, and *unknown fields rejected or ignored deliberately*. With FastAPI and Pydantic this is the natural style; with Express use zod or similar.

```python
from pydantic import BaseModel, Field, ConfigDict
from typing import Literal

class LineItemIn(BaseModel):
    model_config = ConfigDict(extra="forbid")
    sku: str = Field(min_length=1, max_length=64, pattern=r"^[A-Z0-9-]+$")
    qty: int = Field(ge=1, le=10_000)

class OrderCreate(BaseModel):
    model_config = ConfigDict(extra="forbid")          # reject unexpected fields (mass assignment defence)
    customer_id: str = Field(pattern=r"^cus_[a-z0-9]{20}$")
    items: list[LineItemIn] = Field(min_length=1, max_length=200)
    currency: Literal["EUR", "USD", "GBP"]
    notes: str | None = Field(default=None, max_length=2000)

@app.post("/v1/orders", status_code=201, response_model=OrderOut)
async def create_order(body: OrderCreate, user: User = Depends(current_user)):
    ...
```

Separate **input models** from **output models** from **database models**. The output model is an allow-list of what leaves the system; it is how you avoid returning `password_hash` or another tenant's fields by accident when someone adds a column.

Semantic validation (does the customer exist, is the SKU purchasable, does the user own the customer) happens after schema validation, inside the service layer, and yields 404/409/422 as appropriate.

## Pagination

Never return unbounded collections. Two schemes:

**Offset pagination** (`?page=3&page_size=50` or `?offset=100&limit=50`): simple, allows jumping to a page, but `OFFSET` in SQL gets slower as the offset grows (the database still reads and discards the skipped rows), and inserts or deletes between requests cause skipped or duplicated items.

**Cursor (keyset) pagination**: the response includes an opaque cursor encoding the last item's sort key; the next request passes it. Constant time at any depth, stable under concurrent writes, cannot jump to arbitrary pages. The right default for APIs and infinite scroll.

```json
GET /v1/orders?limit=50&cursor=eyJjcmVhdGVkX2F0IjoiMjAyNi0wMy0wMVQxMDoyMTowN1oiLCJpZCI6Im9yZF8wMUhaWCJ9

{
  "data": [ ... 50 orders ... ],
  "next_cursor": "eyJjcmVhdGVk…",
  "has_more": true
}
```

```sql
-- keyset: sort by a unique, indexed combination; the cursor carries the last (created_at, id)
SELECT * FROM orders
WHERE tenant_id = $1 AND (created_at, id) < ($2, $3)
ORDER BY created_at DESC, id DESC
LIMIT 51;   -- fetch one extra to know has_more
```

Enforce a maximum `limit` (100 is typical); clamp silently or reject above it. Always include the tenant or owner filter *inside* the query, never applied after fetching.

## Filtering, sorting and field selection

Filtering: `?status=shipped&created_after=2026-01-01`. Allow-list filterable fields; map each to a parameterised predicate; never interpolate field names from input into SQL. Sorting: `?sort=-created_at,total` with an allow-list of sortable columns, each backed by an index. Field selection (`?fields=id,status,total`) and embedding (`?include=customer`) reduce payloads but complicate caching; add them when a real client needs them. Full-text or complex search: a `POST /v1/orders/search` with a structured body is acceptable when query strings become unwieldy.

## Concurrency control

Two clients updating the same resource overwrite each other unless you prevent it. **Optimistic concurrency**: include a version (`ETag` or a `version` field) in responses; clients send `If-Match: "v7"` on updates; the server rejects with 412 or 409 if the version changed. Cheap and sufficient for most APIs. Pessimistic locking is for workflows that genuinely need exclusive editing.

## Versioning

Breaking changes (Part I chapter 13) require a version boundary. Options:

- **URL path** (`/v1/`, `/v2/`): explicit, cacheable, easy to route and document. The common choice.
- **Header** (`Accept: application/vnd.client.v2+json` or a custom header): cleaner URLs, harder to test in a browser, easy to forget.
- **Date-based** (Stripe style, `Version: 2026-03-01`): fine-grained, requires a translation layer per version.

Whichever you pick: additive changes (new optional fields, new endpoints, new enum values with documented "ignore unknown" behaviour) do **not** bump the version; removals, renames, type changes and semantic changes do. Keep old versions running for a published deprecation period, measure their usage, and tell consumers with `Deprecation` and `Sunset` headers. Resist versioning per-endpoint; version the API.

## Documentation and contracts

Generate OpenAPI from the code (FastAPI does this; for Express use a schema-first tool) and publish it. Chapter 14 covers contract testing and client generation. A good API has: a quick-start, authentication instructions, the error format, pagination rules, rate limits, a changelog and a sandbox.

## Rate limits and quotas

Return `429` with `Retry-After` and expose `RateLimit-Limit`/`RateLimit-Remaining`/`RateLimit-Reset` headers so clients can behave. Chapter 5 covers implementation.

## Security notes for API design

- Authorization on every endpoint, at the resource level (does this user own this order?), not just "is logged in". Part IV chapter 7.
- Do not expose internal IDs that reveal counts or enable enumeration; use random identifiers.
- Reject unknown fields on input to block mass assignment (Part IV chapter 13).
- Limit payload sizes and array lengths in schemas; a 50 MB JSON body is a denial of service.
- Return the same 404 for "does not exist" and "exists but not yours" when existence itself is sensitive.
- Treat all query parameters as untrusted; they are logged, so never accept secrets in them.

## Common mistakes

- 200 for everything with an `error` field in the body.
- Unbounded list endpoints, or offset pagination on tables with millions of rows.
- Sequential integer IDs in URLs with no ownership check.
- Returning database rows directly (every column, including sensitive ones).
- Inconsistent naming across endpoints (`customerId`, `customer_id`, `CustomerID`).
- Versioning on day one with `/v1/`, then making breaking changes within v1 anyway.
- Error messages that leak stack traces or SQL.
- GET endpoints with side effects.
