## The problem

Files are large, slow to transfer, and dangerous: a 500 MB upload through your API ties up a worker for minutes and fills its memory; a file named `report.pdf` may be a web shell; a bucket misconfigured for convenience leaks every client document. Object storage (S3 and its equivalents) solves scale and durability; the engineering is in how your application hands files to it and controls who can read them.

## Object storage basics

S3 stores **objects** (bytes plus metadata) under **keys** in **buckets**. It is not a filesystem: keys are flat strings, "folders" are a display convention based on `/`, there is no rename (copy and delete), and listing is paginated and relatively slow. It is extremely durable (designed for eleven nines), highly available, effectively infinite, and cheap for storage with costs for requests and egress. Access is via authenticated HTTP API calls, or via [[presigned url|presigned URLs]] that embed a time-limited signature so an unauthenticated client can perform exactly one operation on exactly one key.

Strong read-after-write consistency applies to all operations; what you PUT is immediately readable.

```python
# Presigned POST with constraints (boto3)
def presign_upload(s3, bucket: str, key: str, max_bytes: int, content_type: str):
    return s3.generate_presigned_post(
        Bucket=bucket, Key=key,
        Fields={"Content-Type": content_type, "x-amz-server-side-encryption": "aws:kms"},
        Conditions=[
            {"Content-Type": content_type},
            ["content-length-range", 1, max_bytes],
            {"x-amz-server-side-encryption": "aws:kms"},
        ],
        ExpiresIn=300,
    )
```

## Validation and safety

Trust nothing about an uploaded file:

- **Size**: enforced by the presigned policy and re-checked on complete.
- **Type**: the `Content-Type` header is client-supplied. Detect the real type from content (magic bytes: `python-magic`, `file-type` in Node) and compare with an allow-list. Reject mismatches.
- **Name**: never use the client's filename as a key or on disk; generate IDs and store the original name as metadata, sanitised for display. Path traversal via filenames (Part IV chapter 12) is a classic.
- **Content**: parse images with a library that rejects malformed data (and re-encode them to strip payloads); treat SVGs as dangerous (they can contain scripts; serve with `Content-Disposition: attachment` or sanitise); treat HTML uploads as dangerous; scan documents for malware; limit archive extraction (zip bombs: cap total extracted size and file count).
- **Metadata**: strip EXIF (GPS coordinates in photos are personal data).
- **Serving**: serve user content from a **different origin** than the application (a separate domain or CloudFront distribution) so that any HTML or script that slips through cannot access your cookies. Set `Content-Disposition: attachment` for downloads and `X-Content-Type-Options: nosniff`.

## Bucket design

- **One bucket per environment per purpose** (uploads, exports, backups), not one bucket for everything and not one per tenant (you will hit account bucket limits; use key prefixes for tenants).
- **Key layout**: `{tenant_id}/{entity}/{object_id}/{variant}` keeps tenant isolation visible and makes IAM policies with prefix conditions possible. High request rates are fine with any prefix layout today; the old advice about random prefixes is obsolete.
- **Block Public Access** on at the account and bucket level. Always. Public distribution goes through CloudFront with Origin Access Control.
- **Encryption at rest**: SSE-S3 by default (free) or SSE-KMS with a customer-managed key for sensitive client data and auditability (KMS request costs apply; use bucket keys to reduce them).
- **Versioning**: on for buckets with irreplaceable content; protects against accidental deletes and overwrites. Pair with lifecycle rules to expire old versions.
- **Lifecycle rules**: transition cold data to Infrequent Access or Glacier tiers; expire temporary uploads that never completed after a day; expire old versions; abort incomplete multipart uploads after 7 days (otherwise they silently accumulate charges).
- **Object Lock** for compliance retention where regulations require immutability.
- **Access logging / CloudTrail data events** for sensitive buckets.
- **Bucket policies**: deny unencrypted uploads, deny non-TLS access (`aws:SecureTransport`), allow only the application role and the CloudFront OAC.

## Access control for reads

Options for letting users read their files:

1. **Presigned GET URLs** from the API after an authorization check; short expiry (minutes); the URL can be shared within that window, which is usually acceptable.
2. **CloudFront signed URLs or signed cookies** for media-heavy apps: the CDN caches and serves, signatures enforce access, and the origin stays private.
3. **Streaming through the API**: authorise, then proxy bytes. Simple and fully controlled, but every byte flows through your servers; acceptable for small, sensitive documents, wrong for video.

Never grant read via public ACLs or by guessing that long random keys are unguessable; "security by obscure URL" fails the moment a URL is logged, cached or shared.

## Cost and performance

Storage is cheap (around $0.023/GB/month for Standard in us-east-1); requests cost per thousand; egress to the Internet costs per GB (through CloudFront it is cheaper and includes a free tier). Multipart uploads of incomplete objects, forgotten versions, and lifecycle rules that never ran are the typical waste. Use S3 Storage Lens or an inventory to see what you are paying for. For performance, use multipart for large objects, parallel part uploads, and Transfer Acceleration for distant users if measurement shows benefit.

## Alternatives and local development

GCS and Azure Blob are equivalent with similar presigned mechanisms. MinIO runs an S3-compatible server locally for development and tests; LocalStack also emulates S3. Keep the storage client behind a small interface so tests can use a local bucket.

## Common mistakes

- Streaming uploads through the API; workers blocked and memory exhausted.
- Trusting the client's `Content-Type` and filename.
- Public buckets, or presigned URLs with week-long expiry.
- Serving user uploads from the application's origin (XSS via uploaded HTML/SVG).
- One bucket for all environments; staging tests delete production files.
- No lifecycle rule for incomplete multipart uploads or abandoned pending uploads.
- Processing files inline in the request (virus scan, thumbnailing) instead of a worker.
- Forgetting CORS on the bucket for browser uploads.
- EXIF location data served back to the world.
