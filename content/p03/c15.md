## The problem

A SaaS product serves many customers (tenants) from shared infrastructure. The economics depend on sharing; the trust depends on perfect separation. A tenant must never see, modify or degrade another tenant's data or service. The failure mode is not hypothetical: a large share of SaaS data-leak incidents are tenant-isolation bugs, usually a query missing a `WHERE tenant_id = ?`. Isolation therefore cannot rely on developers remembering; it must be structural.

Hybrids are common: shared schema for the long tail of small tenants, database-per-tenant for enterprise tenants who pay for it ("cells" or "pods"), with the application supporting both via a tenant → connection routing layer.

## Shared schema done safely

The shared-schema model is the most common and the most dangerous, so its enforcement deserves detail.

### 1. Tenant context from identity, never from input

The tenant is derived from the authenticated principal (session or token claims) at the start of the request and stored in request context. It is **never** taken from a URL parameter, header or body supplied by the client. A request to `/tenants/t_99/orders` by a user of `t_7` is rejected at the authorization layer because the path tenant does not match the principal's tenant (or the principal's set of permitted tenants for multi-tenant users).

### 2. Every table carries tenant_id; every query filters on it

Make it structural: a repository layer whose methods *require* the tenant (`orders.list(tenant_id, ...)`), with no generic "find by id" that omits it. Composite primary keys `(tenant_id, id)` or at minimum composite indexes with `tenant_id` first, and foreign keys that include `tenant_id` so a line item cannot reference another tenant's order.

### 3. Database-enforced row-level security as the backstop

PostgreSQL [[row-level security]] makes the database refuse to return or modify rows outside the current tenant, regardless of what the application's SQL says:

```sql
ALTER TABLE orders ENABLE ROW LEVEL SECURITY;
ALTER TABLE orders FORCE ROW LEVEL SECURITY;      -- applies to the table owner too
CREATE POLICY tenant_isolation ON orders
  USING (tenant_id = current_setting('app.tenant_id', true)::uuid)
  WITH CHECK (tenant_id = current_setting('app.tenant_id', true)::uuid);
```

```python
# per request/transaction: set the tenant on the connection, scoped to the transaction
async with conn.transaction():
    await conn.execute("SELECT set_config('app.tenant_id', $1, true)", str(tenant_id))   # 'true' = local to txn
    rows = await conn.fetch("SELECT * FROM orders WHERE status = 'open'")   # RLS adds tenant filter automatically
```

The application connects as a role that is *not* the table owner and does not have `BYPASSRLS`. A forgotten `WHERE` now returns zero rows instead of everyone's rows. Use `set_config(..., true)` so the setting is cleared at transaction end even with connection pooling; a leaked setting on a pooled connection is itself a cross-tenant bug. Test RLS explicitly: run a query with the wrong tenant set and assert it returns nothing.

### 4. Everything else keyed by tenant

- **Caches**: `tenant:{id}:…` in every key (chapter 8). Cache poisoning across tenants is a classic leak.
- **Object storage**: tenant prefix in every key; presigned URLs generated only after tenant checks; IAM policies with prefix conditions for per-tenant credentials if ever issued.
- **Search indexes**: a tenant field in every document and a mandatory filter in every query (Elasticsearch/OpenSearch document-level security or filtered aliases).
- **Background jobs**: the job payload carries the tenant; the worker sets the tenant context before any query. Jobs that iterate "all tenants" do so explicitly, one tenant context at a time.
- **Logs and metrics**: include tenant_id for debugging; never include another tenant's data in error messages.
- **Exports and reports**: generated within tenant context; file names and IDs unguessable.
- **Webhooks and emails**: templates rendered with tenant-scoped data only; recipient lists from the tenant's own records.
- **Third-party integrations**: per-tenant credentials stored encrypted and resolved by tenant.

### 5. Unique constraints and IDs

A `UNIQUE (email)` across the whole users table means tenant A can discover that someone exists in tenant B (and blocks legitimate reuse). Use `UNIQUE (tenant_id, email)`. Use random IDs (UUIDv7) so sequential IDs cannot be enumerated across tenants.

## Noisy neighbours and fairness

Shared resources need quotas: per-tenant rate limits (chapter 5), per-tenant concurrency limits on expensive operations, separate worker queues or weighted scheduling so one tenant's bulk import does not starve others, query timeouts, and storage quotas. Monitor resource usage per tenant so you can see who is expensive and move them to a dedicated cell if needed.

## Database-per-tenant mechanics

A tenant registry maps tenant → connection details (host, database, credentials in a secrets manager). The application resolves the tenant, obtains a connection from a per-tenant pool (bounded total pools; lazy creation; idle eviction), and runs. Migrations run across all tenant databases in a controlled loop with progress tracking and the ability to pause. Backups, monitoring and alerts are per database; automate them from the registry. Onboarding a tenant provisions a database via infrastructure code. Connection counts become the scaling constraint; PgBouncer or RDS Proxy per server helps.

## Testing isolation

- Unit tests for the repository layer asserting the tenant filter is present (or that RLS blocks).
- Integration tests that create two tenants, write data for both, and assert every list/get/update/delete endpoint returns or affects only the caller's tenant, including with manipulated IDs and path parameters.
- A periodic automated "cross-tenant probe" in staging that attempts access with mismatched tenants and alerts on any success.
- Code review checklist item: "Is every new table tenant-scoped, indexed by tenant, covered by RLS, and every new query filtered?"

## Choosing for a client

:::fde
Ask: How many tenants, and how big? Do contracts or regulations require physical separation or data residency? Does any tenant need custom versions or schedules? What is the operations budget? Most B2B products start shared-schema with RLS and per-tenant quotas, keep a clean tenant abstraction, and add a database-per-tenant tier when an enterprise customer requires it. Write the decision down as an ADR, including the triggers for moving to a stronger model. Part XIII chapter 8 gives the full decision process.
:::

## Common mistakes

- Tenant ID taken from the request instead of the identity.
- A single generic `get_by_id` that bypasses tenant filtering.
- RLS not forced for the owner role, or the app connecting as a superuser.
- Tenant setting leaking across pooled connections (session-level instead of transaction-level).
- Global unique constraints leaking existence.
- Cache keys and S3 keys without tenant prefixes.
- Background jobs running without tenant context, or iterating tenants and leaking context between iterations.
- No per-tenant quotas; one customer takes down everyone.
