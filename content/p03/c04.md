## The problem

Between "bytes arrived on a socket" and "my handler function ran" sits a stack of machinery you did not write and probably have not read. When a request is slow, mis-authenticated, missing a header, or logged without context, the cause is usually in that stack. Owning it is what separates "I write endpoints" from "I run a service".

## Ordering middleware

Middleware wraps like layers of an onion: the first registered is the outermost, running first on the way in and last on the way out. Getting the order wrong is a classic source of subtle bugs. A sound production order (outermost first):

1. **Request ID and logging context**: everything downstream, including error handlers and access logs, needs it.
2. **Proxy headers** (trusted proxies only): client IP and scheme must be correct before rate limiting, redirects and audit logs.
3. **Timing and metrics**: measures the whole stack.
4. **Error handling**: catches exceptions from everything inside and renders a consistent error. (In some frameworks the error handler is registered separately; conceptually it wraps the rest.)
5. **Security headers**: applied to every response, including errors.
6. **CORS**: preflights answered before authentication (an OPTIONS request carries no credentials).
7. **Body size limits and request timeout**.
8. **Authentication** (identify the principal).
9. **Rate limiting** (needs the principal).
10. **Routing, validation, dependencies, handler**.

Frameworks differ in syntax but the principle holds: context first, protection next, identity, then quota, then your code.

```python
# FastAPI / Starlette: add_middleware order is reversed (last added = outermost), so register inner-most first.
app = FastAPI(lifespan=lifespan)
app.add_middleware(RateLimitMiddleware)                          # innermost of the custom set
app.add_middleware(AuthMiddleware)
app.add_middleware(BodySizeLimitMiddleware, max_bytes=10 * 1024 * 1024)
app.add_middleware(CORSMiddleware, allow_origins=settings.allowed_origins, allow_credentials=True,
                   allow_methods=["GET","POST","PUT","PATCH","DELETE"], allow_headers=["Authorization","Content-Type","Idempotency-Key"])
app.add_middleware(SecurityHeadersMiddleware)
app.add_middleware(MetricsMiddleware)
app.add_middleware(ProxyHeadersMiddleware, trusted_hosts=settings.trusted_proxies)
app.add_middleware(RequestIDMiddleware)                          # outermost
```

```javascript
// Express: order of app.use() is execution order (first = outermost).
app.set('trust proxy', 1);                       // trust exactly one hop (the ALB/Nginx)
app.use(requestId());                            // generates/adopts X-Request-ID, attaches logger
app.use(metrics());
app.use(helmet());                               // security headers
app.use(cors({ origin: allowed, credentials: true }));
app.use(express.json({ limit: '10mb' }));
app.use(timeout('30s'));
app.use(authenticate());                         // sets req.user or leaves undefined
app.use(rateLimit({ keyGenerator: (req) => req.user?.id ?? req.ip }));
app.use('/v1', routes);
app.use(notFound);
app.use(errorHandler);                           // Express error middleware is registered last but conceptually wraps
```

## What belongs where

| Concern | Middleware | Handler / service |
|---|---|---|
| Request ID, logging context | ✓ | |
| Client IP / scheme from proxies | ✓ | |
| Security headers, CORS | ✓ | |
| Body size, request timeout | ✓ | |
| Authentication (who) | ✓ | |
| Authorization (may they do this?) | | ✓ (needs the resource) |
| Input validation (shape) | framework | |
| Semantic validation (exists, owned, allowed state) | | ✓ |
| Rate limiting | ✓ | ✓ for per-resource quotas |
| Transactions | per-request dependency | ✓ boundaries |
| Metrics, access logs | ✓ | business metrics in service |
| Error rendering | ✓ | raise typed exceptions |

Authorization in middleware ("admins only on /admin/*") is fine as a coarse gate but never a substitute for resource-level checks in handlers.

## Request IDs and structured logging

A request ID generated at the edge (CloudFront and ALB both provide one) and propagated through every log line and downstream call is the single highest-value observability feature you can add in an afternoon. Bind it to the logging context so handlers do not pass it around manually:

```python
import logging, contextvars, uuid
request_id_var = contextvars.ContextVar("request_id", default="-")

class RequestIDMiddleware:
    def __init__(self, app): self.app = app
    async def __call__(self, scope, receive, send):
        if scope["type"] != "http": return await self.app(scope, receive, send)
        headers = dict(scope["headers"])
        rid = headers.get(b"x-request-id", b"").decode() or headers.get(b"x-amzn-trace-id", b"").decode() or str(uuid.uuid4())
        token = request_id_var.set(rid)
        async def send_with_id(message):
            if message["type"] == "http.response.start":
                message["headers"].append((b"x-request-id", rid.encode()))
            await send(message)
        try: await self.app(scope, receive, send_with_id)
        finally: request_id_var.reset(token)

class ContextFilter(logging.Filter):
    def filter(self, record): record.request_id = request_id_var.get(); return True
```

Log as JSON with `timestamp, level, logger, message, request_id, user_id, tenant_id, route, status, duration_ms`. Part XI chapter 1.

## Timeouts and cancellation

A handler with no time bound is a liability: one slow dependency and the worker is gone. Set a request timeout (middleware or server level), per-call timeouts on every outbound request and query, and handle client disconnects (ASGI delivers `http.disconnect`; Starlette's `request.is_disconnected()`). Keep the server's timeout above the proxy's so that the proxy, not the application, reports 504 consistently, or below it so the application can return a clean 503 with a message; pick one and document it.

## Error handling

Convert every exception into a consistent response. Known business errors (not found, conflict, forbidden) are raised as typed exceptions carrying a status; unknown exceptions become 500 with a request ID and are logged at ERROR with the stack trace. Never return exception messages from unknown errors to clients; they leak internals. Validate that error responses still carry security headers and CORS headers, or browsers will show a confusing CORS error instead of the real one.

## Debugging the stack

- **Request never reaches the handler**: 404/405 from the router (path, trailing slash, method), 401 from auth middleware, 413 body limit, 422 validation. Enable debug logging for the middleware or add a temporary middleware that logs method, path and headers at entry.
- **Handler runs but the client sees something else**: a later middleware altered the response (compression, caching, error handler swallowing). Compare `curl` output with handler logs.
- **Wrong client IP or `http://` redirects**: proxy headers middleware missing or untrusted hop count wrong.
- **CORS error in the browser but curl works**: preflight not answered, credentials flag mismatch, error responses lacking CORS headers.
- **Slow with low CPU**: blocked event loop or pool exhaustion; look at where time is spent per stage with timing middleware.
- **Streaming broken**: a middleware that buffers the body (some gzip and logging middleware do).

## Common mistakes

- Logging middleware registered inside authentication, so failed auth attempts have no request ID.
- Trusting proxy headers from everyone (`trust proxy: true` in Express).
- CORS middleware inside auth, so preflights get 401.
- Security headers only on successful responses.
- No request timeout; no outbound timeouts.
- Catch-all exception handler that returns `str(exc)` to the client.
- Doing authorization in middleware by URL pattern and forgetting resource ownership.
- Heavy work (database lookups) in middleware that runs for static or health check routes.
