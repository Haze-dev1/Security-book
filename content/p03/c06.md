# Background Jobs and Asynchronous Processing

:::objectives
- Decide which work belongs on the request path and which should be deferred to background workers.
- Build a job system that is reliable: durable queueing, retries with backoff, idempotent handlers, dead-letter handling and visibility.
- Operate workers: scaling on queue depth, graceful shutdown, poison messages, scheduled jobs.
- Avoid the classic failures: lost jobs, duplicate side effects, unbounded retries and silent backlogs.
:::

:::prereq
Chapters 1 and 3; Part I chapter 6.
:::

## The problem

A user clicks "Export report". The export takes 40 seconds, calls a third-party API that is occasionally down, and emails the result. Doing all of that inside the HTTP request means the user stares at a spinner, the load balancer may time out, a worker is tied up, and a third-party hiccup fails the whole request. The request path must be fast and reliable; slow and unreliable work goes elsewhere. "Elsewhere" is a queue and a pool of worker processes, and getting the mechanics right is what separates a system that silently drops exports from one that always delivers.

## What to defer

| Defer to a job | Keep synchronous |
|---|---|
| Sending email, SMS, push notifications | Validating input |
| Calling third-party APIs that are slow or flaky | Reading and writing the primary record |
| Generating files: PDFs, exports, thumbnails, video transcodes | Returning the created resource |
| Webhook delivery to customers | Authorization decisions |
| Bulk operations, imports, recalculations | Anything the user needs in the response |
| Scheduled work: reports, cleanups, reconciliations | Reads that must be fresh |

The response tells the user what happened to their request (created, accepted) and, for long work, how to track it: `202 Accepted` with a job resource and status endpoint, or a notification when done.

## Implementation sketch

```python
# enqueue (inside the API handler)
async def create_export(req: ExportRequest, user: User, db, sqs):
    async with db.transaction():
        job_id = await db.fetchval(
            "INSERT INTO jobs (type, status, tenant_id, payload) VALUES ('export','queued',$1,$2) RETURNING id",
            user.tenant_id, json.dumps(req.model_dump()))
        # outbox pattern: record the intent to enqueue in the same transaction (see Part IX ch.6); simplest version below enqueues after commit
    await sqs.send_message(QueueUrl=settings.jobs_queue, MessageBody=json.dumps({"job_id": str(job_id)}),
                           MessageAttributes={"type": {"DataType": "String", "StringValue": "export"}})
    return JSONResponse({"job_id": str(job_id), "status_url": f"/v1/jobs/{job_id}"}, status_code=202)
```

```python
# worker loop
async def worker_loop(stop: asyncio.Event):
    while not stop.is_set():
        resp = await sqs.receive_message(QueueUrl=Q, MaxNumberOfMessages=5, WaitTimeSeconds=20, VisibilityTimeout=120)
        for m in resp.get("Messages", []):
            job_id = json.loads(m["Body"])["job_id"]
            try:
                await process(job_id)
                await sqs.delete_message(QueueUrl=Q, ReceiptHandle=m["ReceiptHandle"])   # ack only after success
            except RetryableError as e:
                log.warning("job retry", job_id=job_id, err=str(e))                       # not acked: redelivered after visibility timeout
            except Exception as e:
                log.exception("job failed", job_id=job_id)
                await mark_failed(job_id, str(e))                                           # not acked: SQS moves to DLQ after maxReceiveCount

async def process(job_id):
    async with db.transaction():
        job = await db.fetchrow("SELECT * FROM jobs WHERE id=$1 FOR UPDATE SKIP LOCKED", job_id)
        if not job or job["status"] in ("done", "cancelled"): return            # duplicate delivery: idempotent exit
        await db.execute("UPDATE jobs SET status='running', attempts=attempts+1, started_at=now() WHERE id=$1", job_id)
    result_key = await run_export(job)                                           # the actual work, with timeouts
    await db.execute("UPDATE jobs SET status='done', result_key=$2, finished_at=now() WHERE id=$1", job_id, result_key)
```

Key behaviours encoded there:

- **Ack after success**, never before. Crash mid-job → message reappears → retried.
- **Idempotent processing**: the job row's status guards against duplicate delivery; `FOR UPDATE SKIP LOCKED` prevents two workers running the same job concurrently.
- **Visibility timeout longer than the job's maximum duration** (or extended while working, via `ChangeMessageVisibility`); too short and the job runs twice in parallel.
- **Long polling** (`WaitTimeSeconds=20`) to avoid hammering the queue.
- **Failure classification**: retryable errors (timeouts, 5xx from partners) are left for redelivery; permanent errors (invalid data) are recorded and will dead-letter.

## Retries and backoff

Redelivery after a fixed visibility timeout is a crude retry. Better: compute a delay per attempt with [[exponential backoff]] and jitter and re-enqueue with `DelaySeconds` (SQS supports up to 15 minutes; for longer, store `run_after` in the job row and have a scheduler pick it up). Cap attempts (5–10). Make failure *visible*: a `jobs` dashboard of queued/running/failed counts and ages, an alert on dead-letter queue depth, and an alert on the oldest queued job's age (a backlog growing silently is the most common job-system incident).

## Scheduled jobs

Periodic work (nightly reports, hourly reconciliation, cleanup) uses a scheduler that enqueues a message: EventBridge Scheduler → SQS, or a cron process. Rules: the scheduler must run once (not on every API instance, or you get N copies), jobs must be idempotent and safe to re-run, and long schedules should be checked by an alert that fires if the job did *not* run (a missing nightly report is noticed by the client, not by your error logs). Avoid in-process `setInterval` schedulers in the API (Part I chapter 2 showed what happens) and cron on a single VM with no monitoring.

## Scaling and operating workers

- Scale worker count on **queue depth** (SQS `ApproximateNumberOfMessagesVisible`) or on **backlog per worker**. ECS and Kubernetes both support this (target tracking on a custom metric, or KEDA).
- **Concurrency per worker**: CPU-bound work (PDF rendering) wants one job per core; I/O-bound work (API calls) can run many concurrently with asyncio, bounded by a semaphore to protect downstream services.
- **Graceful shutdown**: on SIGTERM stop receiving, finish in-flight jobs (within the orchestrator's grace period), and exit. Jobs longer than the grace period must checkpoint or tolerate being retried.
- **Resource limits**: a job that loads a 2 GB file into memory kills the worker; stream, chunk, and bound.
- **Priority**: separate queues for urgent (user-facing) versus bulk work, with separate worker pools, so an import of a million rows does not delay password-reset emails.
- **Isolation**: one bad job type must not take down all workers; separate queues or pools per job family.

## Tooling

Python: Celery (mature, complex), RQ (simple, Redis), Dramatiq, arq (asyncio), or hand-rolled SQS consumers as above. Node: BullMQ (Redis), bee-queue, SQS consumers. Managed: SQS + ECS/Lambda, Step Functions for multi-step workflows, EventBridge for scheduling, Temporal for durable workflows with complex orchestration. Choose the simplest thing that gives you durability, retries, visibility and a DLQ. Hand-rolled consumers on SQS are often the right answer on AWS; a full workflow engine is right when jobs have many steps and long waits.

## Common mistakes

- Acknowledging the message before the work completes (lost on crash).
- Visibility timeout shorter than the job, causing concurrent duplicate processing.
- No DLQ; a poison message consumes workers forever.
- Non-idempotent handlers that send duplicate emails or charge twice on retry.
- In-memory queues (`asyncio.create_task` and forget) that vanish on deploy.
- Schedulers running on every instance.
- No alert on queue age; discovering a 12-hour backlog from a customer complaint.
- Jobs that hold database transactions open while calling slow external APIs.
- One worker pool for everything; one slow job type starves the rest.

## Exercises

1. Build the enqueue → worker → DLQ pipeline locally (ElasticMQ or LocalStack for SQS, or Redis with a simple list). Make a job fail permanently and watch it dead-letter after N attempts.
2. Kill a worker mid-job (SIGKILL) and verify the job is retried and completes exactly once in the database.
3. Add an "oldest message age" metric and alert, then stop the workers and confirm the alert fires.
