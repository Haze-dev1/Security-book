# Message Queues and Event-Driven Systems

:::objectives

- Choose among SQS, SNS, EventBridge, RabbitMQ, Kafka and Redis Streams for a given problem.
- Design event-driven integrations that stay debuggable.
:::

## The problem

Synchronous calls couple services in time: the caller waits, and if the callee is slow or down the caller fails. As systems grow, more components need to react to the same fact ("an order was placed": billing, inventory, email, analytics), and wiring each one as a synchronous call makes the order endpoint slower and more fragile with every consumer. Messaging decouples producers from consumers in time and in knowledge: the producer records that something happened; consumers react when they can. The cost is a new set of concerns: delivery semantics, ordering, duplicates, schema evolution and observability across asynchronous hops.

## Vocabulary

- **Message**: a unit of data sent through a broker. A **command** asks a specific receiver to do something ("SendInvoiceEmail"). An **event** states that something happened ("OrderPlaced"); the producer does not know or care who listens.
- **Queue** (point-to-point): each message is consumed by exactly one of possibly many competing consumers. Work distribution. SQS, RabbitMQ queues.
- **Topic** (publish/subscribe): each message is delivered to every subscriber. Fan-out. SNS, RabbitMQ exchanges, Kafka topics with consumer groups.
- **Stream**: an append-only, ordered log that consumers read at their own position and can replay. Kafka, Kinesis, Redis Streams.
- **Broker**: the server that stores and routes messages.
- **Consumer group**: a set of consumers sharing the work of a topic/stream, each partition read by one member.

## Delivery guarantees

Networks lose and duplicate messages (Part II chapter 1), so brokers offer a choice:

- **At-most-once**: fire and forget; a crash loses the message. Acceptable for metrics and ephemeral signals.
- **At-least-once**: the broker redelivers until acknowledged; duplicates are possible. The default for every durable system. Consumers must be [[idempotency|idempotent]] (chapter 3).
- **Exactly-once**: not achievable end to end across arbitrary systems. What exists is *effectively once*: at-least-once delivery plus idempotent processing, sometimes helped by broker features (SQS FIFO deduplication IDs, Kafka transactions within Kafka). Design for duplicates regardless.

**Ordering**: standard SQS does not guarantee order; SQS FIFO orders within a message group; Kafka orders within a partition; RabbitMQ orders within a queue for a single consumer. Ordering is per-key at best, never global at scale. Design events to carry a version or timestamp so consumers can detect staleness, and partition by the entity whose order matters (order ID, tenant ID).

## Patterns

### Work queue

### Fan-out

Publish `OrderPlaced` once to an SNS topic or EventBridge bus; each interested service has its own SQS queue subscribed (SNS → SQS fan-out). Each consumer processes independently with its own retries and DLQ. Adding a consumer never touches the producer.

### Outbox

Writing to the database and publishing to the broker are two operations; if the process dies between them, the event is lost (or, in the other order, published for a transaction that rolled back). The [[outbox pattern]] writes the event to an `outbox` table in the same transaction as the business change; a relay process publishes rows from the table and marks them sent. Exactly-once *recording*, at-least-once *publishing*. Part IX chapter 6.

### Event-carried state transfer versus notification

Events can carry full state (`OrderPlaced` with all items and amounts) so consumers need not call back, or just an ID (`OrderPlaced {order_id}`) so consumers fetch current state. Full-state events decouple more but grow and version harder; thin events keep consumers coupled to the producer's API. Many teams send enough state for common consumers and include the ID for the rest.

### Sagas

Multi-step business processes across services (reserve stock → charge → confirm) coordinate through events with compensating actions on failure (release stock if the charge fails). Part IX chapter 6.

## Schema and evolution

Messages outlive deployments: a consumer may read an event produced by last week's producer. Define schemas (JSON Schema, Avro, Protobuf), version them, and make changes additive: add optional fields, never rename or remove without a migration period. Include `event_type`, `event_version`, `event_id`, `occurred_at`, `producer` and a `trace_id` in an envelope around the payload. A schema registry (Confluent, EventBridge Schema Registry) formalises this at scale.

## Observability across asynchronous hops

Tracing breaks when a request becomes a message. Propagate the trace context in message attributes and continue the trace in the consumer, so one trace shows the API call, the queue wait, and the worker's processing (Part XI chapter 2). Log `event_id` everywhere. Measure per queue: depth, oldest message age, consumer errors, DLQ depth, and end-to-end latency from `occurred_at` to processed.

## Operational concerns

- **Poison messages**: always configure a DLQ and alert on it; redrive after fixing.
- **Backpressure**: consumers that cannot keep up should be scaled, and producers may need to slow or shed; unbounded queues hide problems until the backlog is hours long.
- **Message size**: SQS caps at 256 KB (1 MB extended with an S3 pointer library); large payloads go to S3 with a reference in the message (the claim-check pattern).
- **Security**: encrypt queues at rest (SQS SSE-KMS), restrict who can publish and consume with IAM, and validate message contents like any other input; a compromised producer can inject malicious messages.
- **Cost**: SQS is cheap per message but polling costs; use long polling and batching. Kafka clusters have a high fixed cost.
- **Local development**: LocalStack or ElasticMQ for SQS; Docker images for RabbitMQ, Redpanda (Kafka-compatible) and Redis.

## When not to use messaging

If the caller needs the result now, a queue adds latency and complexity without benefit. If there is one producer and one consumer in the same codebase with no slow work, a function call is better. If the team cannot operate the broker, pick a managed one or stay synchronous. Event-driven architecture is a tool for decoupling across time and teams, not a default.

## Common mistakes

- Assuming exactly-once delivery and writing non-idempotent consumers.
- Assuming global ordering.
- Publishing after commit without an outbox, losing events on crashes.
- No DLQ, or a DLQ nobody watches.
- Breaking schema changes that strand old messages.
- Kafka for a three-service system with a two-person team.
- Giant messages; secrets in messages; unencrypted queues.
- Debugging without event IDs or trace propagation.

## Exercises

1. Implement SNS → two SQS queues → two consumers locally with LocalStack. Make one consumer fail and confirm the other is unaffected and the failed messages dead-letter.
2. Add an outbox table and relay to an existing create endpoint. Kill the process between commit and publish and show the event is still delivered.
3. Design the event envelope and schema evolution policy for an `OrderPlaced` event, then make a compatible change and an incompatible one and explain how consumers experience each.
