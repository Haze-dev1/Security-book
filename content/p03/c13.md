# Transaction Boundaries

:::objectives
- Decide where a transaction begins and ends in a web request, a background job and a multi-step workflow.
- Apply the unit-of-work pattern so that a request's writes succeed or fail together.
- Avoid long transactions, lock contention and work-inside-transactions that cannot be rolled back.
- Handle operations that span a database and external systems without partial writes.
:::

:::prereq
Chapters 3, 6 and 12; Part VIII chapter 5 covers the database mechanics in depth.
:::

## The problem

Creating an order touches several tables: the order, its lines, an inventory reservation, an audit entry. If the process dies after the first insert, the database holds a headless order. Transactions exist to make a group of changes atomic. The engineering question is *where to draw the box*: too small and you get partial writes; too large and you hold locks while waiting on networks, serialise your throughput, and make the box impossible to roll back because it included an email.

## The unit of work

The dominant pattern for request handling: **one transaction per request** (per logical operation), opened when the handler begins its writes and committed when it finishes successfully; any exception rolls it back. Frameworks support this as a dependency or middleware:

```python
# FastAPI dependency providing a transactional session per request
async def get_uow(pool=Depends(get_pool)):
    async with pool.acquire() as conn:
        async with conn.transaction():          # BEGIN
            yield conn                          # handler runs here
        # COMMIT on normal exit; ROLLBACK if the handler raised

@app.post("/v1/orders", status_code=201)
async def create_order(body: OrderCreate, user=Depends(current_user), db=Depends(get_uow)):
    order_id = await orders.insert(db, body, user.tenant_id)
    await order_lines.insert_many(db, order_id, body.items)
    await inventory.reserve(db, body.items)           # raises Conflict if insufficient → rollback everything
    await audit.record(db, user, "order.created", order_id)
    await outbox.add(db, "OrderPlaced", {"order_id": str(order_id)})   # event recorded atomically; relayed later
    return {"id": str(order_id)}
```

Everything inside is all-or-nothing. The `outbox.add` line is how side effects that must *eventually* happen (publishing an event, sending an email) join the transaction without actually performing a non-rollbackable action inside it (Part IX chapter 6).

## What must not be inside a transaction

- **Network calls to other systems**: payment APIs, email, S3 uploads, other services. They cannot be rolled back, they are slow (holding locks and a connection for hundreds of milliseconds), and they fail independently. Record intent in the transaction; perform the call after commit (or from a worker reading the outbox); reconcile on failure.
- **User interaction or long computation**: a transaction open while rendering a PDF or awaiting a client is a transaction holding locks for seconds.
- **Unbounded loops**: processing a million rows in one transaction creates a giant undo log, blocks vacuum, and if it fails at row 999,999 you lose everything. Batch (1,000–10,000 rows per transaction) with restartable progress.

The rule of thumb: a transaction should contain database statements and pure computation only, and last milliseconds.

## Reads inside, outside, or alone

Read-only requests often need no explicit transaction (autocommit; each statement is its own), unless you need a consistent snapshot across several reads (a report summing several tables), in which case a read-only transaction at `REPEATABLE READ` gives one. Read-your-writes within a request is automatic inside the same transaction and connection; across requests, replica lag can break it (Part VIII chapter 8).

## Concurrency and locks

Transactions that touch the same rows wait for each other. Patterns that cause pain:

- **Hot rows**: a single `counters` row incremented by every request serialises all requests. Use per-shard counters, Redis, or append-only tallies.
- **Lock ordering**: transaction A updates row 1 then row 2; transaction B updates 2 then 1. Deadlock; the database kills one. Always touch rows in a consistent order (sort IDs before updating).
- **Check-then-act**: `SELECT stock; if ok: UPDATE stock` lets two transactions both see enough stock. Use atomic conditional updates (`UPDATE ... SET qty = qty - 1 WHERE qty >= 1` and check the row count) or `SELECT ... FOR UPDATE`, or serializable isolation with retry.
- **Long transactions** block others and, in PostgreSQL, prevent vacuum from cleaning dead rows, degrading the whole database. Set `idle_in_transaction_session_timeout` and `statement_timeout`.

```sql
-- Atomic reservation: no race, no explicit lock
UPDATE inventory SET reserved = reserved + $2
WHERE sku = $1 AND on_hand - reserved >= $2
RETURNING on_hand - reserved AS available;   -- zero rows returned means insufficient stock
```

## Background jobs

A job typically has several steps with external calls between them; one transaction cannot span them. Structure jobs as a sequence of small transactions with explicit state transitions recorded in the job row, so that a retry resumes from the last completed step rather than repeating the whole job:

```python
async def fulfil_order(job):
    order = await load(job.order_id)
    if order.state == "created":
        await capture_payment(order)                 # external, idempotent by key
        await transition(order, "created", "paid")   # tiny transaction with WHERE state='created' guard
    if order.state == "paid":
        await reserve_shipping(order)                # external
        await transition(order, "paid", "shipping_booked")
    if order.state == "shipping_booked":
        async with db.transaction():                 # local work can be one transaction
            await write_invoice(order); await outbox.add("OrderFulfilled", ...)
            await transition_in(db, order, "shipping_booked", "fulfilled")
```

The `WHERE state = ...` guard on each transition makes concurrent or duplicate executions safe: the second one updates zero rows and knows to stop.

## Across services

When an operation spans two services with separate databases, there is no shared transaction. Options, in increasing complexity: make one side the source of truth and the other eventually consistent via events; sagas with compensating actions (Part IX chapter 6); two-phase commit (rare, fragile, avoid). Design boundaries so that the common operations live inside one service's transaction; cross-service consistency is expensive and should be rare.

## ORMs and transaction scope

ORMs (SQLAlchemy, Prisma, Django) have their own session/transaction semantics; know them. Common traps: the ORM auto-commits per statement unless you open a transaction explicitly; lazy loading issues queries *after* the transaction closed (or inside it, holding it open); "savepoints" (nested transactions) are not real nested transactions. Keep the unit of work explicit and the ORM's session lifetime bound to it.

## Testing

Transactional tests (wrap each test in a transaction and roll back) are fast and isolate state, but they cannot test commit-dependent behaviour (outbox relays, triggers, read-after-commit). Keep a smaller set of integration tests that commit for real against a disposable database.

## Common mistakes

- An HTTP call to a payment provider inside the database transaction.
- No transaction around multi-table writes; partial orders in production.
- Transactions held open across `await`s on external I/O.
- Million-row updates in one transaction.
- Check-then-act races on stock, balances and unique names.
- Inconsistent lock ordering producing deadlocks under load that never appear in tests.
- Relying on the ORM's implicit behaviour without reading its documentation.
- Treating an email send as rollbackable.
