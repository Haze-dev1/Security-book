## The problem

Every public API faces the same cross-cutting demands: authenticate callers, stop any one of them from consuming all capacity, shape and route traffic, and present a stable surface while backends change. Implementing these in every service is repetitive and inconsistent; implementing them at the edge, once, is the idea of an API gateway. Rate limiting in particular is both a fairness mechanism and a safety mechanism: it stops bugs, abuse and traffic spikes from becoming outages.

## What an API gateway does

A gateway is a reverse proxy with API-specific features: routing by path and version; authentication and authorization offload (validating JWTs, API keys, OAuth scopes); rate limiting and quotas per consumer; request and response transformation; caching; schema validation; observability (per-route metrics, logging); and developer-facing features (keys, usage plans, documentation portals). Products: AWS API Gateway, Kong, Apigee, Tyk, Envoy-based gateways, Nginx with modules, and the ALB itself for a subset (routing, OIDC authentication, WAF).

When it earns its place: many backend services exposed under one API; external developers needing keys and quotas; a need to authenticate at the edge consistently; serverless backends (API Gateway + Lambda is a natural pair). When it does not: a single service behind an ALB where the middleware chapter already covers the needs. A gateway is another hop (latency, cost, config) and another place for drift; add it for a reason.

## AWS API Gateway in brief

Two flavours: **HTTP APIs** (cheaper, lower latency, JWT authorizers, Lambda and HTTP integrations) and **REST APIs** (more features: usage plans and API keys, request validation, caching, WAF, private endpoints, canary deployments; roughly three times the per-request price). Both bill per million requests plus data transfer, which is attractive at low volume and expensive at high volume compared with an ALB's hourly model: at tens of millions of requests per month, an ALB in front of ECS is usually cheaper; at a few million, API Gateway's zero-idle cost wins. Timeouts are capped (29 seconds default on REST APIs, with a quota-increase path), payloads are capped at 10 MB, and WebSocket APIs are a separate type. Treat the limits as design constraints: long operations become asynchronous jobs.

## Rate limiting: concepts

A **rate limit** bounds requests per time window per key (100 requests/minute per API key). A **quota** bounds a longer period (1 million requests/month per plan). A **concurrency limit** bounds in-flight requests (10 simultaneous per tenant), which protects against slow requests in a way rate limits do not.

Choose the **key** carefully: per authenticated principal (user, API key, tenant) for fairness; per IP as a fallback for unauthenticated routes, knowing that NAT and mobile carriers make IPs unfair in both directions; per route for expensive endpoints (login, search, export). Apply multiple layers: a generous global per-IP limit at the edge (WAF rate rule) to absorb floods, a per-tenant limit in the gateway or application for fairness, and tight per-route limits where abuse hurts (5 login attempts per minute per account).

### Algorithms

- **Fixed window**: count requests in each calendar minute; reset at the boundary. Simple; allows 2× bursts across a boundary (100 at 12:00:59 and 100 at 12:01:00).
- **Sliding window log**: store each request's timestamp; count those within the last N seconds. Exact; memory grows with rate.
- **Sliding window counter**: weight the previous window's count by its overlap with the current sliding window. Near-exact, constant memory. A common production choice.
- **[[token bucket]]**: a bucket holds up to B tokens, refilled at R per second; each request takes one; empty bucket means reject. Allows controlled bursts (B) with a sustained rate (R). The most widely used algorithm (AWS, Stripe, Nginx `limit_req` is a variant called leaky bucket).
- **Leaky bucket**: requests queue and drain at a fixed rate; smooths output. Nginx's `limit_req` with `burst` behaves this way.

```python
# Token bucket in Redis, atomic via Lua: returns [allowed, remaining, retry_after_ms]
TOKEN_BUCKET = """
local key, capacity, refill_per_ms, now, cost = KEYS[1], tonumber(ARGV[1]), tonumber(ARGV[2]), tonumber(ARGV[3]), tonumber(ARGV[4])
local data = redis.call('HMGET', key, 'tokens', 'ts')
local tokens = tonumber(data[1]) or capacity
local ts = tonumber(data[2]) or now
tokens = math.min(capacity, tokens + (now - ts) * refill_per_ms)
local allowed = 0
local retry = 0
if tokens >= cost then tokens = tokens - cost; allowed = 1
else retry = math.ceil((cost - tokens) / refill_per_ms) end
redis.call('HSET', key, 'tokens', tokens, 'ts', now)
redis.call('PEXPIRE', key, math.ceil(capacity / refill_per_ms) + 1000)
return {allowed, math.floor(tokens), retry}
"""

async def check_rate_limit(redis, key: str, capacity: int = 100, per_seconds: int = 60):
    refill_per_ms = capacity / (per_seconds * 1000)
    now_ms = int(time.time() * 1000)
    allowed, remaining, retry_ms = await redis.eval(TOKEN_BUCKET, 1, f"rl:{key}", capacity, refill_per_ms, now_ms, 1)
    return bool(allowed), remaining, retry_ms
```

```python
# Middleware usage
allowed, remaining, retry_ms = await check_rate_limit(redis, f"user:{user.id}", capacity=600, per_seconds=60)
headers = {"RateLimit-Limit": "600", "RateLimit-Remaining": str(remaining), "RateLimit-Policy": "600;w=60"}
if not allowed:
    headers["Retry-After"] = str(max(1, retry_ms // 1000))
    return JSONResponse({"title": "Too Many Requests", "status": 429}, status_code=429, headers=headers)
```

The Lua script makes read-modify-write atomic across many application instances; doing it in Python with two round trips would race. Redis is the standard distributed limiter store; in-process limiters (per instance) are acceptable only when you can tolerate N× the nominal limit across N instances.

### Responding well

Return `429 Too Many Requests` with `Retry-After` and the standard `RateLimit-*` headers so well-behaved clients back off. Log limited requests with the key, so you can distinguish abuse from a legitimate client that needs a higher tier. Never rate-limit health checks. For login and other sensitive routes, limit per account *and* per IP, and consider progressive delays rather than hard blocks to avoid letting attackers lock users out deliberately.

## Protecting downstream services

Rate limiting at the edge protects your API; your API also needs to protect what it calls. Per-tenant concurrency limits (semaphores) stop one tenant's bulk job from exhausting the database pool; client-side rate limiters toward third-party APIs keep you within their quotas; [[circuit breaker|circuit breakers]] stop hammering a failing dependency; and load shedding (returning 503 quickly when overloaded, based on queue depth or latency) keeps the service responsive for the requests it can serve. ## Quotas and tiers

Commercial APIs often combine a burst rate limit with monthly quotas per plan. Implement quotas as counters with a period key (`quota:tenant:2026-03`) incremented atomically, checked before processing, and surfaced in a usage endpoint and dashboard so clients are never surprised. Decide the behaviour at the limit (hard stop, soft overage billing, degrade features) with the business, not alone.

## Common mistakes

- Rate limiting only by IP, blocking a whole office or university while an attacker rotates IPs.
- Non-atomic counters across instances, so limits leak under load.
- Limits with no `Retry-After` and no headers; clients retry immediately in a tight loop.
- Limiting health checks or internal service calls accidentally.
- Fixed windows allowing double bursts on expensive endpoints.
- Using API Gateway for a high-volume service without modelling the per-request cost.
- No limits on login, password reset or OTP endpoints, enabling credential stuffing and SMS pumping.
