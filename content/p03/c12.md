# Configuration Management and Error Handling

:::objectives
- Structure application configuration so that every environment is explicit, validated and documented.
- Design an error taxonomy that separates expected business outcomes from bugs and from dependency failures.
- Decide what users see, what gets logged, what pages someone, and what is retried.
- Make failures observable and safe: no leaked internals, no swallowed exceptions, no partial writes.
:::

:::prereq
Part I chapter 8; chapter 4 of this part.
:::

## The problem

Two kinds of code decide whether a production system is pleasant or miserable to operate: the code that loads configuration, and the code that handles errors. Both are usually written last, in a hurry. Bad configuration code produces services that start in a broken state or behave differently per environment for reasons nobody can see. Bad error handling produces either users seeing stack traces, or silent failures that corrupt data while dashboards stay green.

## Configuration structure

Part I chapter 8 established the principles: config from the environment, typed and validated at start-up, secrets from a secrets manager. The application-level structure that makes this maintainable:

```python
# app/config.py — one object, sections per concern, documented, validated
class DatabaseSettings(BaseModel):
    url: PostgresDsn
    pool_min: int = Field(2, ge=1)
    pool_max: int = Field(10, ge=1, le=200)
    statement_timeout_ms: int = Field(10_000, ge=100)

class HttpClientSettings(BaseModel):
    connect_timeout_s: float = 2.0
    read_timeout_s: float = 10.0
    retries: int = Field(2, ge=0, le=5)

class FeatureFlags(BaseModel):
    new_checkout: bool = False
    export_v2: bool = False

class Settings(BaseSettings):
    model_config = SettingsConfigDict(env_nested_delimiter="__", extra="forbid")
    env: Literal["dev", "staging", "prod"]
    service_name: str = "orders-api"
    version: str = "dev"
    log_level: Literal["debug", "info", "warning", "error"] = "info"
    database: DatabaseSettings
    http: HttpClientSettings = HttpClientSettings()
    features: FeatureFlags = FeatureFlags()
    payments_api_key: SecretStr
    allowed_origins: list[AnyHttpUrl]

    @model_validator(mode="after")
    def prod_guards(self):
        if self.env == "prod" and self.log_level == "debug":
            raise ValueError("debug logging is not permitted in prod")
        return self
```

`DATABASE__POOL_MAX=20` maps to `settings.database.pool_max`. Everything has a type, a default where safe, and no default where a wrong guess is dangerous (the database URL, the API key). The validator shows environment guards: a few places where configuration *combinations* are forbidden.

Rules:

- **Load once, at start-up**; pass the settings object (or sub-sections) explicitly to components. Avoid reading `os.environ` deep in the code.
- **Fail fast with a complete list of problems**, not one at a time.
- **Document in one place**: a generated table of every setting, type, default and meaning (`python -m app.config --describe`, or docs generated from the model). Part XIII chapter 10's configuration matrix is built from this.
- **Expose a redacted config dump** at start-up in logs (secrets masked) so you can see what a running instance actually loaded.
- **Runtime flags** (feature toggles) are separate from start-up config and are read per request from a cached source with a safe default (Part X chapter 7).

## An error taxonomy

Not all errors are alike, and treating them alike is the root problem. Four categories:

| Category | Examples | HTTP | Log level | Alert? | Retry? |
|---|---|---|---|---|---|
| **Expected client outcome** | Validation failure, not found, forbidden, conflict, rate limited | 4xx | INFO (or none) | No (alert on *rate* anomalies) | No |
| **Dependency failure** | Database timeout, payment API 503, Redis unavailable | 503 / 502 / 504 | WARNING or ERROR | On rate/duration | Yes, if idempotent |
| **Bug** | Unhandled exception, assertion, null dereference | 500 | ERROR with stack trace | Yes, on any occurrence (or rate) | No |
| **Invariant violation / data corruption** | Negative balance found, duplicate primary key where impossible | 500 | CRITICAL | Immediately | No; stop and investigate |

Design the code so the category is explicit:

```python
class AppError(Exception):
    status = 500; code = "internal_error"; expose_message = False
class NotFound(AppError):          status = 404; code = "not_found";  expose_message = True
class Forbidden(AppError):         status = 403; code = "forbidden";  expose_message = True
class Conflict(AppError):          status = 409; code = "conflict";   expose_message = True
class ValidationFailed(AppError):  status = 422; code = "validation_failed"; expose_message = True
class DependencyUnavailable(AppError): status = 503; code = "dependency_unavailable"; expose_message = False; retryable = True

@app.exception_handler(AppError)
async def app_error_handler(request, exc: AppError):
    log = logger.bind(request_id=request_id_var.get(), code=exc.code)
    if exc.status >= 500: log.error("request failed", exc_info=exc)
    else: log.info("request rejected", detail=str(exc))
    body = {"type": f"https://api.client.com/errors/{exc.code}", "title": exc.code.replace("_", " "), "status": exc.status,
            "detail": str(exc) if exc.expose_message else "An internal error occurred.", "request_id": request_id_var.get()}
    headers = {"Retry-After": "5"} if getattr(exc, "retryable", False) else {}
    return JSONResponse(body, status_code=exc.status, headers=headers)

@app.exception_handler(Exception)        # anything unknown is a bug
async def unhandled_handler(request, exc):
    logger.bind(request_id=request_id_var.get()).exception("unhandled exception")
    metrics.increment("errors.unhandled", tags={"route": request.url.path})
    return JSONResponse({"type": "about:blank", "title": "Internal Server Error", "status": 500, "request_id": request_id_var.get()}, status_code=500)
```

Translate dependency exceptions at the boundary: a `psycopg.OperationalError` or `httpx.TimeoutException` becomes `DependencyUnavailable` in the repository or client layer, so handlers never see driver-specific exceptions and the HTTP layer renders 503 with `Retry-After` rather than 500.

## What users see

Users need: that something went wrong, whether it was their fault (and how to fix it), whether retrying will help, and a reference they can quote to support. They never need: stack traces, SQL, internal hostnames, library names, or the specific reason an authentication failed ("user not found" versus "wrong password" enables enumeration; say "invalid credentials").

For browser frontends, map error codes to friendly messages client-side; show the request ID in a small "reference" line; for 503s offer a retry; for 401s redirect to login once (not in a loop).

## What gets logged

Every 5xx with full context (request ID, route, user and tenant IDs, the stack trace, sanitised request summary). 4xx at INFO or sampled; a spike in 401/403/422 is itself a signal (attack, broken client). Never log request bodies wholesale (PII, secrets); log specific safe fields. Never log credentials, tokens, cookies or full card numbers; implement redaction in the logging layer as a backstop. Part XI chapter 1 covers structure; Part IV chapter 22 covers audit logs, which are a separate stream from error logs.

## What pages someone

Alert on **symptoms**, not on individual exceptions: 5xx rate above threshold, p99 latency above SLO, dependency error rate, queue age. Use error-tracking tools (Sentry and similar) to group unhandled exceptions by fingerprint and notify on *new* ones, which catches bugs introduced by a deploy without paging for every known noisy exception. Part XI chapter 5.

## Partial failure and data integrity

An error mid-operation must not leave half-written state. Within one database: wrap the operation in a transaction so an exception rolls everything back (chapter 13). Across systems (database plus external API): order operations so the irreversible external action happens last, or record intent first and reconcile (outbox, sagas), and make everything idempotent so retries complete the work. Never catch an exception, log it, and continue as if the operation succeeded; that is how silent corruption begins.

```python
# Anti-pattern: swallowing
try:
    await charge_card(order)
except Exception:
    logger.warning("charge failed")      # order proceeds as 'paid'?! No.
await mark_paid(order)

# Correct: fail the operation, keep state consistent, let the caller decide
try:
    await charge_card(order)             # idempotent via key
except PaymentDeclined as e:
    raise Conflict(f"payment declined: {e.reason}")
except PaymentProviderError as e:
    raise DependencyUnavailable("payment provider") from e
await mark_paid(order)
```

## Timeouts and cancellation as errors

A timeout is an error whose cause you do not know (the operation may have succeeded). Treat it as a dependency failure, make the operation idempotent, and surface it honestly ("we could not confirm your payment; please check before retrying"). Client disconnects cancel handlers in async frameworks; ensure cleanup runs (`finally`, context managers) so pool connections and locks are released.

## Health and readiness as error reporting

The readiness endpoint is where the service reports whether it *can* work: configuration loaded, dependencies reachable within a short timeout, not draining. Keep it cheap and honest; a readiness check that always returns 200 hides a service that cannot reach its database, and a check that calls every dependency deeply turns a Redis blip into a full outage via the load balancer (Part XI chapter 5 discusses the balance).

## Common mistakes

- `except Exception: pass`.
- Returning `str(exc)` from unknown exceptions to users.
- Driver exceptions leaking to handlers; database timeouts rendered as 500 instead of 503.
- Logging whole request bodies or headers.
- Distinct messages for "user not found" and "wrong password".
- Alerting on every exception instance; alert fatigue; then alerts ignored.
- Config read from `os.environ` scattered through the codebase with different defaults in each place.
- No request ID in error responses, so support cannot find the log.
