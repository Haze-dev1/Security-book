# API Contracts and OpenAPI

:::objectives
- Describe an HTTP API precisely with OpenAPI and keep the description in sync with the implementation.
- Generate clients, validate requests and responses, and publish documentation from one source.
- Detect breaking changes before they ship and practise contract testing between producers and consumers.
- Use contracts as the handshake between your team and a client's integration team.
:::

:::prereq
Chapter 2.
:::

## The problem

An API's behaviour lives in code; its consumers live elsewhere and read documentation that drifts. Integration teams guess at field types, break on undocumented enum values, and discover changes in production. A machine-readable contract fixes this by making the description the thing everyone builds from: the server validates against it, clients are generated from it, documentation renders from it, and a diff of it tells you whether a change is breaking.

## OpenAPI

[[openapi]] (formerly Swagger) is a JSON/YAML format describing paths, operations, parameters, request and response schemas (JSON Schema), authentication schemes and metadata. Version 3.1 aligns fully with JSON Schema.

```yaml
openapi: 3.1.0
info: { title: Orders API, version: 1.4.0 }
servers: [{ url: https://api.client.com/v1 }]
security: [{ sessionCookie: [] }]
paths:
  /orders/{orderId}:
    get:
      operationId: getOrder
      summary: Fetch one order
      parameters:
        - { name: orderId, in: path, required: true, schema: { $ref: '#/components/schemas/OrderId' } }
      responses:
        '200': { description: The order, content: { application/json: { schema: { $ref: '#/components/schemas/Order' } } } }
        '404': { $ref: '#/components/responses/NotFound' }
components:
  securitySchemes:
    sessionCookie: { type: apiKey, in: cookie, name: __Host-sid }
  schemas:
    OrderId: { type: string, pattern: '^ord_[0-9a-z]{20}$', examples: [ord_01hzx3k9m2p7q8r9s0t1] }
    Order:
      type: object
      required: [id, status, currency, total, items, created_at]
      additionalProperties: false
      properties:
        id: { $ref: '#/components/schemas/OrderId' }
        status: { type: string, enum: [pending, paid, shipped, cancelled], description: "Clients must tolerate new values." }
        currency: { type: string, enum: [EUR, USD, GBP] }
        total: { type: string, pattern: '^-?\d+\.\d{2}$', description: "Decimal string to avoid float rounding." }
        items: { type: array, items: { $ref: '#/components/schemas/LineItem' }, maxItems: 200 }
        created_at: { type: string, format: date-time }
  responses:
    NotFound:
      description: Resource not found
      content: { application/problem+json: { schema: { $ref: '#/components/schemas/Problem' } } }
```

Details that pay off: `operationId`s (they become client method names); `required` lists; `additionalProperties: false` on inputs; examples; the money-as-decimal-string convention; a documented statement about unknown enum values; a shared `Problem` schema for errors.

## Code-first or schema-first

**Code-first** (FastAPI, NestJS, Spring with annotations): the framework generates OpenAPI from typed handlers and models. Zero drift between code and spec; the spec is a build artifact you publish and diff. The right default when one team owns both.

**Schema-first**: write the spec, generate server stubs and validation, implement handlers. Better when the contract is negotiated with another team or client before implementation, or when several implementations must match. Tooling: `openapi-generator`, `oapi-codegen` (Go), `openapi-typescript`, `datamodel-code-generator` (Python).

Either way, **the spec is checked into version control, produced in CI, and diffed on every pull request.**

## Validation at runtime

Validate requests against the schema (FastAPI and Pydantic do this inherently; for Express, `express-openapi-validator`). Validate *responses* against the schema in non-production environments and in tests, so a handler that returns an undocumented field or a wrong type fails loudly before clients see it. Production response validation is a judgement call: it catches bugs but costs CPU and can turn a minor omission into an outage; many teams sample or enable it in staging only.

## Generated clients

From the spec, generate typed clients for the frontend (`openapi-typescript` plus a small fetch wrapper, or `orval`), for mobile (Swift/Kotlin generators) and for client integration teams. Typed clients turn API misuse into compile errors and make breaking changes visible as build failures in consumers. Publish clients with the same version as the API, or let consumers generate from the published spec.

## Breaking-change detection

Diff the spec between the base branch and the pull request in CI with a tool that understands compatibility (`oasdiff`, `openapi-diff`). Breaking: removed paths or operations, removed or renamed properties, type changes, new required request fields, narrowed enums on input, widened enums on output (debatable; documented tolerance makes it non-breaking), changed authentication. Non-breaking: new optional fields, new endpoints, new optional parameters, relaxed input constraints. Fail the build on breaking changes unless the PR is explicitly labelled as a new major version.

```yaml
# GitHub Actions step
- name: Check for breaking API changes
  run: |
    oasdiff breaking origin/main:openapi.yaml openapi.yaml --fail-on ERR
```

## Contract testing

Schema validation proves the response matches the spec; it does not prove the spec matches what a consumer *relies on*. [[contract test|Consumer-driven contract testing]] (Pact and similar) has each consumer record the interactions it depends on; the provider's CI replays them against the real implementation. A provider change that breaks a specific consumer fails *before* deploy, and you learn which consumer. Valuable when many services or teams integrate; for a single frontend and API owned by one team, generated types plus response validation usually suffice.

## Documentation

Render the spec with Swagger UI, Redoc, Scalar or Stoplight. FastAPI serves Swagger UI at `/docs` automatically; lock it behind authentication or disable it in production if the API is not public. Good docs add what the spec cannot express: authentication walkthrough, error-handling guidance, pagination semantics, rate limits, idempotency keys, webhooks, a changelog, and copy-pasteable curl examples. Tie them to the version.

## Contracts with client integration teams

:::fde
When a client's team will integrate with your API, the OpenAPI document is the agreement. Share it early (schema-first for the negotiated parts), version it, generate a client for them if they want one, provide a sandbox environment with test data, and publish a changelog with deprecation notices. In return, ask for *their* contract (the systems you must call) in the same form; if they cannot provide one, write it yourself from observation and have them confirm it. Most integration slippage traces back to an undocumented field or an assumed enum value.
:::

## Beyond REST

GraphQL has its schema (SDL) and introspection; gRPC has Protocol Buffers; AsyncAPI describes event-driven interfaces (queues and webhooks) the way OpenAPI describes HTTP. The principles are identical: one source of truth, generated artefacts, diffed in CI.

## Common mistakes

- A hand-written spec that drifts from the code within a month.
- Missing `required` and `additionalProperties`, so the schema validates anything.
- Floats for money.
- No breaking-change check in CI; discovering incompatibility from a client's bug report.
- Swagger UI exposed publicly on an internal API, leaking its surface.
- Enum values added without telling consumers to tolerate unknown values.
- Treating the spec as documentation only, rather than as the validation and generation source.

## Exercises

1. Export your API's OpenAPI document in CI, commit it, and add a breaking-change check with `oasdiff`. Make a breaking change in a branch and watch it fail.
2. Generate a TypeScript client from the spec and use it in the frontend for one endpoint; then remove a field in the API and observe the compile error.
3. Enable response validation in staging and run the test suite; fix every undocumented field it reveals.
