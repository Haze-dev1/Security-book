# Real-Time Applications

:::objectives
- Choose a real-time delivery mechanism and architecture appropriate to the product requirement.
- Design presence, fan-out, ordering and reconnection for live features.
- Scale connection-heavy services and keep them operable.
- Avoid real-time features that are more fragile than the problem they solve.
:::

:::prereq
Part II chapter 14; chapters 6 and 7 of this part.
:::

## The problem

"Real-time" covers a live dashboard that updates every few seconds, collaborative editing with sub-100 ms expectations, chat, notifications, and progress bars. Each has different tolerances for latency, ordering and loss, and the infrastructure that is right for one is wrong for another. The mistakes are usually in two directions: building WebSocket infrastructure for a feature that polling would serve, or bolting a real-time channel onto a stateless API without thinking about how messages find their recipient across many servers.

## Clarify the requirement first

| Question | Why it matters |
|---|---|
| How fresh must data be? Seconds, hundreds of ms, tens of ms? | Decides polling vs push vs persistent connection |
| Who sends? Server only, or client too, at what rate? | SSE vs WebSocket |
| How many concurrent users, and how many per "room"? | Connection capacity; fan-out cost |
| Must messages be ordered? Delivered exactly once? Persisted? | Sequence numbers, acks, history store |
| What happens offline? | Catch-up on reconnect; push notifications |
| Is presence (who is online) needed? | Heartbeats, expiry, consistent state across servers |

A dashboard refreshed every 10 seconds by polling a cached endpoint is cheap, stateless and robust. Do not build more than the requirement demands.

Separating the connection tier from the API means deploying the API does not disconnect every user, and connection servers can be sized for memory and file descriptors while API servers are sized for CPU.

## Ordering and delivery

Give every message a monotonically increasing sequence per channel (a database sequence, or a Redis Streams ID). Clients track the last sequence seen; on reconnect they request everything after it from the database (catch-up), then resume live. Servers deliver live messages with their sequence; a client that sees a gap requests the missing range. This turns the lossy live channel into effectively reliable delivery without needing the live channel itself to be reliable. Deduplicate on the client by sequence.

Acknowledgements and read receipts are application messages stored in the database, not a transport feature.

## Presence

"Who is online" is deceptively hard: connections drop without notice, a user has three tabs, and instances disagree. Standard approach: each connection server sets a key `presence:{user}` in Redis with a short TTL (30–60 s) and refreshes it on heartbeat; presence equals key exists; multiple connections are a count or a set with per-connection expiry. Publish presence changes on the backplane with debouncing so a flapping connection does not spam. Accept that presence is eventually consistent and approximate; design the UI accordingly ("last seen" rather than a hard online/offline binary).

## Fan-out and rooms

A message to a room of 10 users is cheap. A message to a channel with 100,000 subscribers spread over 50 connection servers means each server receives it once from the backplane and writes it to its local sockets; the cost is sockets × message size on egress. Hot channels need: coalescing (send the latest state rather than every intermediate update), rate limiting of publishers, and sometimes sharding channels. For broadcast-heavy products, consider managed services (AWS API Gateway WebSocket, AppSync subscriptions, Ably, Pusher) that have solved fan-out at scale.

## Collaborative editing

Concurrent edits to the same document need a merge strategy: Operational Transformation or CRDTs (Yjs, Automerge). These are well-trodden libraries; do not invent one. The server's job becomes relaying updates, persisting document state, and enforcing authorization per document.

## Scaling and operations

- Scale connection servers on connection count and memory, not CPU.
- Raise file descriptor limits; tune kernel socket buffers for many idle connections.
- Heartbeats below every idle timeout on the path (ALB 60 s default, NAT, proxies).
- Deployments: drain connections gradually (close a few percent at a time with a reconnect hint) to avoid reconnect storms that overload authentication.
- Metrics: connections per instance, messages in/out per second, backplane lag, reconnect rate, per-socket send-queue depth (slow clients), authentication failures.
- Backpressure: bound per-socket outgoing queues; disconnect clients that cannot keep up rather than growing memory.
- Multi-region: real-time across regions needs a global backplane or regional isolation with routing by room; this is where complexity explodes, so avoid unless required.

## Security

Authenticate at connect (cookie or short-lived token), check `Origin`, and authorise **every subscription** against the resource (user may join room 42 only if a member). Re-validate long-lived connections periodically or on permission change (publish a "revoke" event that the connection tier acts on). Rate-limit client messages per socket. Validate message schemas; a WebSocket message is as untrusted as a POST body. Never trust client-supplied sender IDs: the server stamps the sender from the authenticated connection.

## Common mistakes

- WebSockets for a feed that SSE or polling would serve.
- Business logic in the connection servers, coupling deploys to disconnections.
- No sequence numbers; lost messages are undetectable.
- Pub/Sub only, with no catch-up path from persistent storage.
- Presence via "connection closed" events alone (never fire on network death).
- Authorization only at connect, not per subscription.
- Idle timeout mismatches silently dropping connections every minute.
- Unbounded per-socket send buffers.

## Exercises

1. Build a channel server with sequence numbers and a catch-up endpoint. Disconnect a client, publish ten messages, reconnect and verify it receives exactly the missing ten in order.
2. Implement presence with Redis TTL keys and heartbeats. Kill a client with SIGKILL and measure how long until it shows offline.
3. Load test 5,000 idle WebSocket connections against one instance (a tool such as `k6` supports WebSockets) and record memory and file descriptor usage; derive a per-instance capacity.
