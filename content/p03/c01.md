## The problem

A program that runs on one machine has no architecture problem: everything is a function call. The moment users are elsewhere and data must outlive any single process, you must decide which parts run where, who owns which state, and how parts talk. Those decisions determine what you can scale, what you can secure, and what breaks when something fails. Multi-tier architecture is the accumulated answer to those questions, and understanding *why* each tier exists stops you from either skipping one you need or adding one you do not.

## Client-server

A **client** initiates requests; a **server** waits for and answers them. The browser is a client of your API; your API is a client of PostgreSQL; PostgreSQL is a client of the operating system's filesystem. The asymmetry matters:

- The server is **shared** and must handle many clients concurrently, fairly, and without one client's behaviour affecting another's.
- The client is **untrusted**. It runs on hardware you do not control, in software the user can modify. Nothing it sends can be believed without verification, and nothing it is told to hide is hidden. Every security rule in Part IV follows from this.
- The server is **available** at a known address; clients come and go. State that must persist lives on the server side.

Why not let the browser talk to the database directly? Because the client is untrusted: authorization, validation and rate limiting have to happen somewhere you control, before data is touched. (Products like Supabase and Firebase that *appear* to allow client-to-database access insert a policy layer, row-level security, that plays the role of the application tier.) Why not put business logic in the database? Some belongs there (constraints, transactions), but the database is the hardest tier to scale and deploy; keeping logic in stateless application servers keeps the expensive tier doing only what it must.

### Tiers versus layers

**Layers** are logical (presentation, domain, persistence code within one process). **Tiers** are physical (separate processes or machines). A monolith has many layers and one tier beyond the browser and database. Confusing the two leads people to think "clean architecture" requires separate services; it does not.

Every arrow in that diagram is a **trust boundary**: data crossing it is validated on the receiving side, authenticated where identity matters, and encrypted in transit. Every arrow is also a **failure mode**: the receiving side can be slow or down, so the caller has a timeout and a plan.

## Where state lives

State is the enemy of scaling and the friend of correctness; put each kind where it belongs.

| Kind of state | Lives in | Why |
|---|---|---|
| Durable business data | Primary database | Transactions, constraints, backups |
| Files and large blobs | Object storage | Cheap, durable, served directly; databases are bad at blobs |
| Sessions, rate limits, locks, hot cache | Redis | Fast, shared across instances, acceptable to lose |
| In-flight work | Queue | Durable handoff between tiers; retries |
| UI state | Client | Transient; never trusted |
| Configuration | Environment / parameter store | Per environment, versioned |
| Secrets | Secrets manager | Audited, rotated |
| **Nothing** | Application server memory | Instances are disposable |

The last row is the discipline that makes horizontal scaling, rolling deploys and auto-healing possible. In-process caches are fine as performance optimisations only if losing them is harmless.

## Scaling each tier

- **Presentation**: a CDN scales it essentially infinitely for static assets; server-rendered HTML scales like the application tier.
- **Application**: add instances behind the load balancer; autoscale on CPU or request count. The limit becomes the data tier's connection count, which is why connection pooling and proxies (Part VIII chapter 6) matter.
- **Workers**: scale on queue depth; they are the natural place to absorb bursts.
- **Data**: vertical scaling first (bigger RDS instance), then read replicas for read-heavy loads, then caching, then partitioning or a specialised store for the hot path. Each step is more work than the last; the application tier's statelessness buys time before you need them.

## Variants

- **Server-side rendering (SSR) and full-stack frameworks** (Next.js, Django templates, Rails): the presentation tier is a server process. It still should not hold state, and the API and data tiers remain. Often the SSR layer and the API are the same process early on.
- **Backend-for-frontend (BFF)**: a thin API tailored to one client (web, mobile) in front of shared services; useful when clients need very different shapes.
- **Serverless**: Lambda functions as the application tier; the same rules (stateless, data in managed stores) apply even more strictly, because instances live for milliseconds.
- **Two-tier (fat client to database)**: legacy desktop apps, and still sometimes proposed with "the database has security built in". Avoid for anything multi-user and Internet-facing.

## Mistakes that come from skipping the model

- **Business rules in the client only**: price computed in JavaScript and trusted by the API. Attackers submit their own price.
- **State in application memory**: sessions, uploaded files in local disk, in-memory job queues. Works with one instance; fails on the second instance or the first deploy.
- **Database exposed to the Internet** to let a dashboard tool or the frontend reach it.
- **Synchronous slow work in the request path**: PDF generation or third-party calls inside the HTTP handler; the API stalls when they do.
- **One tier doing everything**: the database as a queue, cache, file store and search engine. Each works until it does not, at the same time.
- **Chatty tiers**: the API calling the database 200 times per request, or the frontend calling the API 40 times per page.

## Exercises

1. Draw the tier diagram for an application you know. Mark every piece of state and where it lives. Anything in application memory that would be missed after a restart is a finding.
2. List every arrow in your diagram and, for each, write the timeout the caller uses and what happens when the callee is down. Blanks are incidents waiting to happen.
3. Identify one slow or unreliable operation currently in a request handler and sketch how it would move to a worker.
