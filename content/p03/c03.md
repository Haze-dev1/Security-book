## The problem

A client sends `POST /payments` to charge €50. The server charges the card, writes the record, and the response is lost: the user's Wi-Fi blipped, a load balancer timed out, the mobile app went to background. The client sees a timeout. Did the charge happen? It cannot know. If it retries, the customer may be charged twice; if it does not, an order may go unpaid. Every system that spans a network faces this, because networks lose replies (Part II chapter 1), and every robust system resolves it the same way: make the operation safe to repeat.

[[idempotency|An idempotent operation]] produces the same result whether performed once or many times. `DELETE /orders/123` is idempotent (the order is gone either way). `PUT /profile {name: "Ana"}` is idempotent. `POST /payments` is not, unless you make it so.

## Where duplicates come from

- Client retries after timeouts or 5xx responses (including automatic retries in HTTP libraries and SDKs).
- Users double-clicking submit buttons.
- Load balancers and proxies retrying idempotent methods (and sometimes misconfigured to retry POST).
- Message queues with at-least-once delivery: SQS, Kafka, RabbitMQ all redeliver on failure or visibility timeout expiry.
- Webhook providers retrying when your endpoint did not return 2xx fast enough.
- Replayed events during recovery or reprocessing.

Design assumption: **every message and request may arrive more than once**. Exactly-once delivery is not something networks provide; exactly-once *processing* is something you build with idempotency.

## Idempotency keys for HTTP APIs

The standard pattern, used by Stripe, Adyen and others:

1. The client generates a unique key (UUIDv4) per logical operation and sends it in a header: `Idempotency-Key: 5c8f…`.
2. On first sight, the server records the key (scoped to the authenticated caller), processes the request, and stores the response alongside the key.
3. On a repeat with the same key and the same request body, the server returns the stored response without re-executing.
4. Same key with a *different* body is an error (422/409): the client is misusing the key.
5. Keys expire after a window (24 hours is common) to bound storage.

```python
# FastAPI dependency: idempotency keys stored in PostgreSQL (same transaction as the business write)
from fastapi import Header, HTTPException, Request
import hashlib, json

async def idempotent(request: Request, idempotency_key: str = Header(..., alias="Idempotency-Key"), user=Depends(current_user)):
    body = await request.body()
    fingerprint = hashlib.sha256(body).hexdigest()
    async with db.transaction():
        row = await db.fetchrow(
            "INSERT INTO idempotency_keys (key, user_id, fingerprint, status) VALUES ($1,$2,$3,'in_progress') "
            "ON CONFLICT (key, user_id) DO UPDATE SET key = EXCLUDED.key RETURNING status, fingerprint, response_code, response_body, (xmax = 0) AS inserted",
            idempotency_key, user.id, fingerprint)
    if not row["inserted"]:
        if row["fingerprint"] != fingerprint:
            raise HTTPException(422, "Idempotency-Key reused with a different request body")
        if row["status"] == "in_progress":
            raise HTTPException(409, "Request with this Idempotency-Key is still processing")
        return StoredResponse(row["response_code"], row["response_body"])     # handler short-circuits and replays
    return None   # proceed; the handler must later UPDATE the row with the response in its transaction
```

Design details that matter:

- **Scope keys to the caller** (user, tenant or API key). Otherwise one client can replay or block another's operations by guessing keys.
- **Claim atomically.** Two identical requests arriving simultaneously must not both pass the check; use a unique constraint or `SET NX`.
- **Fingerprint the body** to detect key reuse with different content.
- **Store the full response**, including status and headers you care about, so the replay is faithful.
- **Write the key record and the business record in one transaction** when they live in the same database; if the key store is Redis and the data is PostgreSQL, handle the window where the write committed but the key update failed (treat `in_progress` with a stale timestamp as retryable after inspection, or reconcile).
- **Propagate** idempotency keys to downstream providers.
- **Document** the header, TTL, and behaviour for clients.

## Idempotent message consumers

Queues deliver at least once. A consumer that sends an email per message will send duplicates unless it remembers what it has processed:

```python
async def handle(msg):
    event_id = msg.attributes["event_id"]           # producer-assigned, stable across redeliveries
    async with db.transaction():
        inserted = await db.fetchval(
            "INSERT INTO processed_events (event_id) VALUES ($1) ON CONFLICT DO NOTHING RETURNING true", event_id)
        if not inserted:
            return                                   # duplicate: already processed, ack and move on
        await apply_business_change(msg)             # same transaction: all or nothing
    await send_email(msg)                            # side effect outside the transaction: still at-least-once!
```

That last line shows the limit: external side effects cannot be rolled back. Options: make the external call idempotent too (email providers accept idempotency keys or message IDs), record the intent in the transaction and let a separate step perform it with its own dedup, or accept rare duplicates for low-stakes actions. The [[outbox pattern]] (Part IX chapter 6) formalises this.

Also handle **ordering**: duplicates may arrive out of order relative to newer events. Carry a version or timestamp and ignore events older than the current state.

## Naturally idempotent designs

Prefer operations that are idempotent by construction:

- **PUT with full state** instead of POST with deltas: "set balance to 120" versus "add 20". (Though "set" has its own concurrency hazards; pair with `If-Match`.)
- **Upserts keyed by a natural identifier**: `INSERT … ON CONFLICT (external_id) DO UPDATE`.
- **Absolute instructions in jobs**: "ensure user X has role Y" rather than "grant role Y to X", so re-running is harmless.
- **Infrastructure as code** is idempotent by design: declare the desired state, apply repeatedly.
- **Conditional writes** in DynamoDB and S3 (`If-None-Match: *`) to create-once.

## Retries done right

Idempotency makes retries safe; retries still need discipline: a bounded number, [[exponential backoff]] with jitter, retrying only on retryable errors (timeouts, 429, 502/503/504, connection resets; never on 400/401/403/422), honouring `Retry-After`, and a total deadline. Part IX chapter 8 covers this fully. Retrying non-idempotent operations without keys is how you get duplicate orders.

## Common mistakes

- Treating POST as safe to retry "because the server probably didn't get it".
- Idempotency keys generated server-side (useless: the retry gets a new one) or derived from the request body (two legitimate identical requests collide).
- Keys not scoped per caller.
- Checking for the key, then inserting it, non-atomically; two concurrent requests both proceed.
- Storing only "key seen" without the response, so the replay returns a different answer.
- Consumers that dedupe in memory (lost on restart) or not at all.
- Forgetting that the downstream provider also needs an idempotency key.
