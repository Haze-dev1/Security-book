## The problem

Some data is read far more often than it changes: a product catalogue, a user's permissions, an exchange rate, a rendered page fragment. Recomputing or re-fetching it on every request wastes the most expensive resources you have (database CPU, third-party API quotas, user latency). A cache keeps a copy closer and cheaper. The price is the second-hardest problem in computer science: knowing when the copy is wrong.

## Cache-aside with Redis

The dominant application pattern: the application checks the cache; on a miss it loads from the source, stores the result with a TTL, and returns it.

```python
import json, asyncio, random
from redis.asyncio import Redis

async def get_product(redis: Redis, db, product_id: str) -> dict | None:
    key = f"product:v2:{product_id}"                 # include a schema version so you can change the shape safely
    cached = await redis.get(key)
    if cached is not None:
        return None if cached == b"__none__" else json.loads(cached)     # negative caching: remember misses briefly
    row = await db.fetchrow("SELECT ... FROM products WHERE id = $1", product_id)
    if row is None:
        await redis.set(key, "__none__", ex=30)
        return None
    data = serialise(row)
    ttl = 300 + random.randint(0, 60)                 # jitter so keys do not expire in lockstep
    await redis.set(key, json.dumps(data), ex=ttl)
    return data

async def update_product(redis, db, product_id, patch):
    await db.execute("UPDATE products SET ... WHERE id = $1", product_id)
    await redis.delete(f"product:v2:{product_id}")   # invalidate after the write commits; next read repopulates
```

Design decisions in that snippet:

- **Keys** are namespaced (`product:`), versioned (`v2`), and built from stable identifiers. Include the tenant when data is tenant-scoped: `tenant:{t}:product:{id}`, or you will serve one tenant's data to another.
- **TTL always.** Even data you invalidate explicitly gets a TTL as a safety net against missed invalidations. Jitter prevents mass expiry.
- **Negative caching** stops repeated lookups of missing items (and some enumeration attacks), with a short TTL.
- **Invalidate on write, do not update the cache from the write path** unless you are sure about ordering; delete-then-repopulate is simpler and avoids writing stale data from a slower concurrent request.
- **Serialization** is explicit; cache the shape the API returns, not ORM objects.

### Other patterns

- **Read-through / write-through**: the cache library itself loads and writes to the source; the application only talks to the cache. Convenient; makes the cache a dependency on the write path.
- **Write-behind**: writes go to the cache and are flushed to the database asynchronously. Fast writes; risk of data loss if the cache dies before flush. Rarely appropriate for business data.
- **Refresh-ahead**: proactively refresh popular keys before expiry. Smooths latency for hot items.

## Stampedes and hot keys

When a popular key expires, hundreds of concurrent requests miss simultaneously and all hit the database: a [[cache stampede]]. Mitigations:

- **Lock or single-flight**: the first miss acquires a short lock (`SET lock:key NX EX 5`) and recomputes; others wait briefly or serve stale. Within one process, coalesce concurrent loads of the same key.
- **Stale-while-revalidate**: store the value with a logical expiry earlier than the physical TTL; serve the stale value while one request refreshes.
- **Probabilistic early expiration**: each request recomputes early with a probability that rises as expiry nears.
- **Jittered TTLs** against synchronised expiry across many keys.

Hot keys (one key read a million times a second) can overload a single Redis shard; replicate hot values into in-process caches with very short TTLs, or shard the key (`key:{rand(0..9)}`) and read any.

## Consistency: what staleness costs

A cache is a copy; copies lag. Decide per data type how stale is acceptable: a product description can be a minute old; a user's permission revocation should take effect within seconds; an account balance must be read from the source for any financial decision. Use short TTLs plus explicit invalidation for sensitive data, and never cache anything where staleness causes harm you cannot tolerate: authorization decisions that must be immediate, inventory counts at checkout, idempotency records. When several things cache the same data (CDN plus Redis plus browser), the effective staleness is the sum.

Invalidation is hard because the writer must know every key that depends on the changed data. Keep dependencies simple (cache entities, not arbitrary query results), or use **tag-based invalidation** (track which keys belong to an entity and delete them together), or accept TTL-based eventual freshness for derived data.

## Redis in production

Treat Redis as **ephemeral by default**: the application must work (slower) if the cache is empty or unavailable. Wrap cache calls with short timeouts (50–100 ms) and fall through to the source on error; a cache outage must not become a service outage. For data that is *not* reconstructible (sessions, rate-limit counters you cannot lose), either accept the loss on failure or use Redis persistence (AOF) and Multi-AZ replication (ElastiCache with automatic failover). Set `maxmemory` and an eviction policy (`allkeys-lru` for pure caches; `volatile-lru` when some keys must never be evicted). Monitor hit ratio, evictions, memory, latency and connected clients. Part VIII chapter 11 covers Redis itself.

## Measuring

Hit ratio alone misleads; measure what the cache saves: database QPS and p99 with and without, origin cost, end-to-end latency. A cache with a 40% hit ratio on cheap queries may be worth nothing; one with 20% hits on a 2-second report is gold. Track per-key-family metrics (`product`, `permissions`), not one global number, and review periodically whether each cache still earns its complexity. Removing a cache that no longer helps is a legitimate improvement.

## Security

Caches hold copies of data with none of the database's row-level controls. Scope keys by tenant and user; never cache a response that depends on the requester under a key that omits the requester; encrypt Redis in transit and at rest (ElastiCache supports both) and require AUTH; do not cache secrets or tokens longer than needed; keep Redis in private subnets with a security group allowing only the application tier. Cached authorization data needs a tight TTL and invalidation on permission change.

## Common mistakes

- Caching without TTLs; stale forever after a missed invalidation.
- Tenant or user missing from the key; data leaks between customers.
- Cache as a hard dependency; Redis blip equals full outage.
- Unbounded in-process caches (memory leaks).
- Caching mutable, correctness-critical data (balances, permissions) with long TTLs.
- Stampedes on hot keys at expiry; no jitter.
- Caching ORM objects or responses with user-specific fields under shared keys.
- Measuring hit ratio and nothing else.
