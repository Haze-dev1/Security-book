# Webhooks

:::objectives
- Receive webhooks from third parties securely: signature verification, replay protection, idempotency and fast acknowledgement.
- Send webhooks to customers reliably: signing, retries with backoff, ordering, delivery logs and endpoint management.
- Design the operational tooling (replay, inspection, dead-lettering) that webhooks always end up needing.
:::

## The problem

Polling a provider every few seconds to ask "did the payment settle yet?" wastes both sides' resources and is slow. A [[webhook]] inverts the direction: the provider makes an HTTP request to a URL you register when something happens. Simple in concept, webhooks are a classic source of security holes (unauthenticated endpoints that do what any caller says), reliability bugs (lost or duplicated events) and operational pain (who delivered what, when, and why did it fail?). You will both receive them (Stripe, GitHub, identity providers) and send them (to your clients' systems).

## Receiving webhooks

A webhook endpoint is an unauthenticated, Internet-facing POST handler that triggers business logic. Treat it as hostile input until proven otherwise.

```python
# FastAPI: verify a Stripe-style signature over the raw body
import hmac, hashlib, time
from fastapi import Request, HTTPException

def verify_signature(raw: bytes, header: str, secret: str, tolerance_s: int = 300):
    parts = dict(p.split("=", 1) for p in header.split(","))
    ts, sig = parts.get("t"), parts.get("v1")
    if not ts or not sig: raise HTTPException(400, "malformed signature")
    if abs(time.time() - int(ts)) > tolerance_s: raise HTTPException(400, "stale signature")
    expected = hmac.new(secret.encode(), f"{ts}.".encode() + raw, hashlib.sha256).hexdigest()
    if not hmac.compare_digest(expected, sig): raise HTTPException(400, "invalid signature")

@app.post("/webhooks/stripe", status_code=200)
async def stripe_webhook(request: Request, db=Depends(get_db), queue=Depends(get_queue)):
    raw = await request.body()                                   # raw bytes, not parsed JSON
    verify_signature(raw, request.headers.get("Stripe-Signature", ""), settings.stripe_webhook_secret.get_secret_value())
    event = json.loads(raw)
    inserted = await db.fetchval(
        "INSERT INTO webhook_events (provider, event_id, type, payload) VALUES ('stripe',$1,$2,$3) ON CONFLICT DO NOTHING RETURNING true",
        event["id"], event["type"], raw.decode())
    if inserted:
        await queue.enqueue("process_webhook", provider="stripe", event_id=event["id"])
    return {"received": True}
```

Additional receiving concerns:

- **Secrets per provider and per environment**; rotate them (most providers support two active secrets during rotation).
- **Network allow-listing** of provider IPs is a weak secondary control (IP ranges change); signatures are the real control.
- **Endpoint URLs** should not be guessable but are not secrets; the signature is the secret.
- **Logging**: store raw events with headers for debugging and replay, redacting any PII you are not entitled to keep.
- **Local development**: tunnelling tools (ngrok, Cloudflare Tunnel) or provider CLIs (`stripe listen`) forward webhooks to your laptop. Use test-mode secrets.

## Sending webhooks

When your product notifies customers' systems, you become the provider, and your customers will judge your reliability and your documentation.

### Design

- **Event model**: `event_id` (unique, stable), `type` (`order.completed`), `created_at`, `api_version`, `data` (the object, or a reference and the fields that changed). Document every type with sample payloads.
- **Endpoint management**: customers register URLs (HTTPS only; validate the URL, and resolve and check the IP at send time to prevent SSRF against your own network: Part IV chapter 12), choose event types, and receive a signing secret they can rotate. Provide a test-send button.
- **Signing**: `X-Signature: t=<unix ts>,v1=<hex hmac-sha256(secret, "{t}.{raw body}")>`. Publish verification code in several languages.
- **Delivery**: from workers, with a short timeout (5–10 s), treating any non-2xx or timeout as failure. Expect customers to be slow and down.
- **Retries**: exponential backoff with jitter over hours or days (e.g., 1 min, 5 min, 30 min, 2 h, 12 h, 24 h, up to 72 h), then mark the endpoint failing and notify the customer. Do not retry forever; do disable endpoints that fail for days (with notification) to protect your workers.
- **Ordering**: deliver per endpoint in order where feasible but document that consumers must tolerate out-of-order and duplicate delivery. Include a version or sequence per object so they can detect staleness.
- **Delivery log**: every attempt with timestamp, response code, latency and truncated response body, visible to the customer in a dashboard and to you in support. Allow manual **replay** of an event.
- **Volume control**: batch or coalesce high-frequency events if customers request it; rate-limit per endpoint to avoid flooding them.

```python
# Worker: deliver one webhook attempt
async def deliver(attempt: Attempt, http: httpx.AsyncClient):
    body = attempt.payload_bytes
    ts = int(time.time())
    sig = hmac.new(attempt.endpoint.secret, f"{ts}.".encode() + body, hashlib.sha256).hexdigest()
    headers = {"Content-Type": "application/json", "X-Webhook-Id": attempt.event_id, "X-Webhook-Signature": f"t={ts},v1={sig}", "User-Agent": "ClientApp-Webhooks/1.0"}
    await assert_public_destination(attempt.endpoint.url)            # SSRF defence: resolve and reject private/link-local IPs
    try:
        r = await http.post(attempt.endpoint.url, content=body, headers=headers, timeout=8.0, follow_redirects=False)
        ok = 200 <= r.status_code < 300
        await record_attempt(attempt, status=r.status_code, body=r.text[:500], ok=ok)
    except httpx.HTTPError as e:
        ok = False
        await record_attempt(attempt, status=None, error=str(e)[:500], ok=False)
    if not ok:
        await schedule_retry(attempt)        # backoff schedule; disable endpoint after final failure
```

## Operational tooling you will need

Both sides eventually need: a searchable log of events and delivery attempts; the ability to replay an event (inbound: re-enqueue from the stored raw payload; outbound: resend); alerts on failing endpoints and on inbound processing backlog; and a status page or dashboard customers can see. Build the log table and the replay button on day one; you will use them during the first incident.

## Common mistakes

- Verifying the signature over a parsed-and-reserialised body (always fails, so someone disables verification).
- No signature verification at all; anyone can mark orders as paid.
- Running business logic inline; provider times out and retries; duplicates everywhere.
- No idempotency on inbound events.
- Trusting event payloads for state instead of re-fetching for critical decisions.
- Sending to customer URLs without SSRF checks (a customer registers `http://169.254.169.254/` and your worker reads your own cloud credentials).
- Retrying forever, or giving up after one attempt.
- No delivery log; support tickets become archaeology.
- Secrets in the URL (`?token=…`), which land in logs on both sides.
