## The system we are delivering

A Node.js API (the "portal" from the small-client case study) running on ECS Fargate behind an ALB with RDS PostgreSQL, in two environments (staging, production) in one AWS account per environment, infrastructure in Terraform, GitHub as the code host. The pipeline must: run checks on PRs in under ten minutes; build one signed image per merge; apply infrastructure changes through reviewed plans; run migrations before deploys; deploy to staging automatically and to production after approval; roll back automatically on alarms; write a deployment record.

## Repository layout

```text
portal/
├── .github/
│   ├── CODEOWNERS                 # infra/ and .github/ require platform team review
│   ├── dependabot.yml             # weekly grouped updates; actions pinned by SHA
│   └── workflows/
│       ├── ci.yml                 # PR: lint, test, SAST, secret scan, IaC scan
│       ├── build.yml              # main: build, scan, sign, attest, push
│       ├── infra.yml              # PR: terraform plan + policy; main: apply per environment
│       └── deploy.yml             # after build: migrate + deploy staging → approval → production
├── src/ ...
├── migrations/                    # versioned SQL, linted by squawk
├── Dockerfile
├── infra/
│   ├── modules/{network,postgres,ecs-service,observability}/
│   └── envs/{staging,production}/
├── scripts/
│   ├── deploy.sh                  # verify signature, render task definition, update service, wait, record
│   └── smoke.sh
└── docs/runbooks/
```

## Stage 1: pull request checks (ci.yml)

Jobs run in parallel and finish in about six minutes: `test` (matrix, coverage, junit artefact), `semgrep` (OWASP rules plus house rules), `gitleaks` (history), `checkov` on `infra/`, `squawk` on changed migrations, and `hadolint` on the Dockerfile. All are required status checks. Nothing here has cloud credentials, so forks and new contributors are safe.

## Stage 2: infrastructure plan and apply (infra.yml)

On PRs touching `infra/`, a job per environment assumes the **plan** role via OIDC, runs `terraform plan -out`, converts it to JSON, evaluates OPA policies, and posts a summarised plan as a PR comment (resource counts and every `-/+` line highlighted). On merge, the staging **apply** role applies the saved plan from the merge commit; the production apply job waits in the `production-infra` environment for a platform-team approval. Drift detection runs nightly as a plan expecting no changes and opens an issue if it finds any.

```yaml
# infra.yml (excerpt): plan on PR
  plan:
    strategy: { matrix: { env: [staging, production] } }
    permissions: { id-token: write, contents: read, pull-requests: write }
    steps:
      - uses: aws-actions/configure-aws-credentials@e3dd6a429d7300a6a4c196c26e071d42e0343502 # v4.0.2
        with: { role-to-assume: "arn:aws:iam::${{ vars[format('ACCOUNT_{0}', matrix.env)] }}:role/tf-plan", aws-region: eu-west-1 }
      - run: terraform -chdir=infra/envs/${{ matrix.env }} init -input=false
      - run: terraform -chdir=infra/envs/${{ matrix.env }} plan -input=false -lock-timeout=60s -out=tfplan
      - run: terraform -chdir=infra/envs/${{ matrix.env }} show -json tfplan > plan.json && conftest test plan.json -p infra/policy
      - uses: actions/upload-artifact@b4b15b8c7c6ac21ea08fcf65892d2ee8f75cf882 # v4.4.3
        with: { name: "tfplan-${{ matrix.env }}-${{ github.sha }}", path: infra/envs/${{ matrix.env }}/tfplan }
```

## Stage 3: build, scan, sign (build.yml)

On every merge to `main`: build the multi-stage image with registry cache, tag `sha-<sha>`, push to ECR (both accounts have replication from a shared tooling registry, or the build pushes to each), Trivy scan with `ignore-unfixed` and a failure on critical/high, cosign keyless signature, SLSA provenance attestation, SBOM uploaded as an artefact and attached to the image. Output: the digest.

@file: scripts/deploy.sh
```bash
#!/usr/bin/env bash
set -euo pipefail
ENV="$1"; DIGEST="$2"
IMAGE="123456789012.dkr.ecr.eu-west-1.amazonaws.com/portal@${DIGEST}"
CLUSTER="portal-${ENV}"; SERVICE="portal-api"; FAMILY="portal-api-${ENV}"

echo "Verifying signature and provenance for ${IMAGE}"
cosign verify "${IMAGE}" \
  --certificate-identity-regexp '^https://github.com/acme/portal/.github/workflows/build.yml@refs/heads/main$' \
  --certificate-oidc-issuer https://token.actions.githubusercontent.com > /dev/null
cosign verify-attestation --type slsaprovenance1 "${IMAGE}" \
  --certificate-identity-regexp '^https://github.com/acme/portal/.github/workflows/build.yml@refs/heads/main$' \
  --certificate-oidc-issuer https://token.actions.githubusercontent.com > /dev/null

echo "Rendering task definition"
CURRENT=$(aws ecs describe-task-definition --task-definition "${FAMILY}" --query taskDefinition)
PREVIOUS_IMAGE=$(echo "${CURRENT}" | jq -r '.containerDefinitions[0].image')
NEW=$(echo "${CURRENT}" | jq --arg img "${IMAGE}" '
  .containerDefinitions[0].image = $img
  | del(.taskDefinitionArn, .revision, .status, .requiresAttributes, .compatibilities, .registeredAt, .registeredBy)')
REVISION=$(aws ecs register-task-definition --cli-input-json "${NEW}" --query taskDefinition.taskDefinitionArn --output text)

echo "Deploying ${REVISION} to ${CLUSTER}/${SERVICE}"
if [ "${ENV}" = "production" ]; then
  # Blue-green via CodeDeploy (AppSpec references the new revision)
  DEPLOYMENT=$(aws deploy create-deployment --application-name "portal-${ENV}" \
    --deployment-group-name "portal-api" \
    --revision "revisionType=AppSpecContent,appSpecContent={content='$(jq -n --arg td "${REVISION}" \
      '{version:1,Resources:[{TargetService:{Type:"AWS::ECS::Service",Properties:{TaskDefinition:$td,LoadBalancerInfo:{ContainerName:"api",ContainerPort:8080}}}}]}' -c)'}" \
    --query deploymentId --output text)
  aws deploy wait deployment-successful --deployment-id "${DEPLOYMENT}"
else
  aws ecs update-service --cluster "${CLUSTER}" --service "${SERVICE}" --task-definition "${REVISION}" > /dev/null
  aws ecs wait services-stable --cluster "${CLUSTER}" --services "${SERVICE}"
fi

echo "Recording deployment"
python3 scripts/record_deployment.py --env "${ENV}" --image "${IMAGE}" --previous "${PREVIOUS_IMAGE}" \
  --sha "${GITHUB_SHA}" --run-url "${GITHUB_SERVER_URL}/${GITHUB_REPOSITORY}/actions/runs/${GITHUB_RUN_ID}"
```

## Rollback

Three paths, all rehearsed:

1. **Automatic**: CodeDeploy alarm rollback during the traffic shift (production) or ECS circuit breaker (staging). No human needed; the pipeline marks the run failed and the record says `rolled_back`.
2. **One command**: `scripts/deploy.sh production <previous digest>` run by the pipeline through a `workflow_dispatch` with the environment gate; the previous digest is in the last deployment record.
3. **Feature flag**: for behavioural changes, flip the flag first, then decide whether a deploy rollback is needed.

A rollback never requires a build, a migration reversal, or console clicks. Migrations are expand-only in the deploy path; contract migrations ship in later releases.

## What the auditor sees

For any production deployment: the record in the locked bucket → the pipeline run (approvals, test results, scan results) → the PR (reviews, CODEOWNERS approval, checks) → the commits (signed) → the image attestation (built by this workflow from this commit) → CloudTrail entries for `UpdateService`/`CreateDeployment` by the pipeline role. For infrastructure: the plan comment on the PR, the apply log, and the state version. Monthly report generated from the records.

## Failure modes and what catches them

| Failure | Caught by |
|---|---|
| Broken test or lint | PR checks; cannot merge |
| Vulnerable dependency | Dependabot PR; SCA gate on critical/high |
| Secret committed | Push protection; gitleaks in PR; rotation runbook |
| Dangerous migration | squawk lint; rehearsal in staging on restored data; lock_timeout |
| Terraform destroys a database | prevent_destroy; OPA deny on destroy of data resources; plan review |
| Unsigned or foreign image | cosign verify in deploy.sh fails; Config rule on task definitions |
| New version crashes on start | ECS circuit breaker (staging), CodeDeploy pre-traffic hook (production) |
| New version raises error rate | CodeDeploy alarm rollback during 10% shift |
| Staging and production differ | Same modules and image; drift detection nightly |
| Concurrent deploys | Concurrency groups on migrate and deploy jobs |
| Lost deployment history | Object-locked records independent of CI retention |

## Adapting for a client

Swap the pieces, keep the shape: GitLab CI or Azure DevOps for GitHub Actions; Kubernetes with Argo Rollouts for ECS and CodeDeploy; CloudFormation for Terraform; Jira change tickets created by the record writer for the board; the client's identity provider for approvals. The non-negotiables travel unchanged: build once by digest, short-lived credentials, signed artefacts verified at deploy, expand/contract migrations, automatic rollback on SLIs, approvals enforced by the pipeline, records retained outside the CI tool.
