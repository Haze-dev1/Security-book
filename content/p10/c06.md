## State: what it is and why it is dangerous

State maps resource addresses in code (`module.database.aws_db_instance.this`) to real resource IDs and their last known attributes. Without it Terraform cannot know what it manages. Three properties make state sensitive:

1. It often contains secrets in plain text: database passwords generated by resources, private keys, tokens returned by providers. Mark outputs `sensitive`, prefer `manage_master_user_password` style features where the secret never enters state, and treat the state store as a secret store.
2. It is a single point of coordination: concurrent applies without locking corrupt it.
3. Losing it does not destroy infrastructure but orphans it: Terraform will try to create everything again, colliding with existing names.

Isolation rules: **one state per environment per workload** (`portal/production`, `portal/staging`), so a mistake in staging cannot touch production state and plans stay fast; **separate state for foundational layers** (accounts, networking, DNS) consumed by workload states via `terraform_remote_state` or, better, by looking up outputs through data sources and SSM parameters to avoid tight coupling; the state bucket lives in a dedicated account or at least has a strict bucket policy, versioning, object lock for retention, access logging and KMS encryption with a key only the apply roles can use.

## Who may apply, and how

The role that runs `apply` can create and destroy anything in its policy; it is one of the most powerful identities in the organisation. Controls:

- **Separate plan and apply roles**: plan needs read-only plus state read; apply needs write. Pull requests run plan only; apply runs after merge and approval.
- **Per-environment roles** assumed via OIDC from the pipeline's environment (chapter 2), so a staging workflow cannot apply to production.
- **Scoped permissions**: the apply role for `portal` cannot touch the networking state or another workload's resources (permission boundaries and resource tags conditions help).
- **Break-glass**: human apply only in emergencies, through a time-bound role with session logging, and the change is reconciled in code afterwards.
- **Policy as code**: Open Policy Agent (Conftest), Sentinel, or Checkov rules evaluated against the plan JSON: no public buckets, no `0.0.0.0/0` on admin ports, required tags, approved instance types and Regions, no deletion of resources tagged `data=true` without a labelled exception.

```bash
# Evaluate a plan against OPA policies in CI
terraform plan -out=tfplan && terraform show -json tfplan > plan.json
conftest test plan.json --policy policy/        # fails the job on denied rules
```

## Protecting data

Resources that hold data (databases, buckets, queues with messages, KMS keys) deserve: `prevent_destroy`, provider-level deletion protection, final snapshots, and a review rule that any plan destroying them requires a second approver. KMS keys additionally need a deletion window and a policy that the apply role cannot schedule deletion. Buckets with versioning and object lock make accidental destroys recoverable.

:::danger The plan that destroys production
Every experienced team has a story: a renamed module, a changed `for_each` key or a provider upgrade produced a plan with `-/+` on the database and someone approved it at 17:55. The defences are mechanical (prevent_destroy, deletion protection) and procedural (plans on PRs, policy checks on destroys, a culture of reading plans). Rely on both.
:::

## Drift, import and recovery

- **Drift**: reality differs from state (console changes, auto-scaling, AWS-initiated updates). A scheduled plan detects it; decide per case to revert (apply) or adopt (update code, or `ignore_changes` for attributes legitimately managed elsewhere).
- **Import**: adopt existing resources with `import` blocks (declarative, reviewable) so a client's hand-built infrastructure comes under management incrementally.
- **State surgery**: `terraform state mv`, `rm`, and `moved` blocks for refactors; always with a backup (`terraform state pull > backup.json`) and never while another run could start.
- **Corrupted or lost state**: restore from bucket versioning; if truly lost, rebuild state by importing each resource (painful; this is why versioning and object lock are non-negotiable).
- **Provider upgrades**: read changelogs, run plan in staging first, expect attribute renames; pin with `~>` and upgrade deliberately.

## CloudFormation and CDK

**CloudFormation** is AWS's native declarative service: templates (YAML/JSON) become **stacks**; AWS stores the state. Strengths: no state to manage, deep integration (StackSets across accounts and Regions, drift detection built in, Service Catalog, automatic rollback on failure), and it is what many AWS-managed features emit. Weaknesses: AWS-only, verbose, slower feedback, resource coverage sometimes lags, and rollback behaviour can surprise (a failed update rolls back the whole stack). **CDK** generates CloudFormation from TypeScript/Python/Java with constructs that encode best practices (`cdk synth` produces the template; `cdk diff` is the plan). **SAM** is a CloudFormation dialect for serverless.

When to choose: Terraform/OpenTofu when managing more than AWS (DNS at Cloudflare, GitHub, Datadog, Kubernetes resources) or when a client's platform team has standardised on it; CloudFormation/CDK when the organisation is all-in on AWS, uses StackSets for organisation-wide guardrails, or when the team strongly prefers general-purpose languages. Mixing is common: Terraform for foundations, CDK for serverless application stacks. Avoid managing the same resource from two tools.

@file: template.yaml (CloudFormation excerpt)
```yaml
AWSTemplateFormatVersion: "2010-09-09"
Parameters:
  Environment:
    Type: String
    AllowedValues: [staging, production]
Resources:
  LogsBucket:
    Type: AWS::S3::Bucket
    DeletionPolicy: Retain
    UpdateReplacePolicy: Retain
    Properties:
      BucketName: !Sub "acme-portal-logs-${Environment}-${AWS::AccountId}"
      BucketEncryption:
        ServerSideEncryptionConfiguration:
          - ServerSideEncryptionByDefault: { SSEAlgorithm: aws:kms }
      PublicAccessBlockConfiguration:
        BlockPublicAcls: true
        BlockPublicPolicy: true
        IgnorePublicAcls: true
        RestrictPublicBuckets: true
      VersioningConfiguration: { Status: Enabled }
```

`DeletionPolicy: Retain` and `UpdateReplacePolicy: Retain` are CloudFormation's equivalents of `prevent_destroy` for data.

## Configuration management: inside the machine

Terraform provisions infrastructure; something else must configure what runs *inside* servers when you use servers at all. Options, in order of preference for new work:

1. **Don't**: use containers or managed services so there is no server to configure (Part VI, Part VII chapter 8).
2. **Immutable images**: bake an AMI with Packer (packages, agents, hardening) and replace instances rather than mutate them; configuration at boot limited to environment-specific values.
3. **cloud-init / user data**: small boot-time scripts to join a cluster or fetch configuration; keep them short and idempotent; secrets fetched from Secrets Manager, never embedded.
4. **SSM State Manager and Run Command**: AWS-native, agent-based, no inbound ports; good for patch baselines and compliance.
5. **Ansible**: agentless, SSH-based, idempotent playbooks; the standard for configuring fleets of long-lived servers and for on-premises; integrates with Terraform via dynamic inventory. Chef, Puppet and Salt fill the same role with agents.

Principles regardless of tool: idempotent runs, configuration in git, secrets from a vault at run time, and a clear boundary between "provision" (Terraform) and "configure" (Ansible/SSM) so neither fights the other.

@file: playbooks/harden.yml (Ansible excerpt)
```yaml
- hosts: app_servers
  become: true
  tasks:
    - name: Ensure unattended security upgrades
      apt:
        name: unattended-upgrades
        state: present
    - name: Disable password SSH auth
      lineinfile:
        path: /etc/ssh/sshd_config
        regexp: '^#?PasswordAuthentication'
        line: 'PasswordAuthentication no'
      notify: restart sshd
  handlers:
    - name: restart sshd
      service: { name: ssh, state: restarted }
```
