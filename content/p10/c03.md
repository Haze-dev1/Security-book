# Static Analysis, Dependency Scanning and Secret Scanning

:::objectives
- Place the right automated security checks at the right pipeline stage: linters and SAST on pull requests, dependency and container scanning on builds, secret scanning everywhere.
- Configure the tools so that findings are actionable and the signal stays trusted: severity thresholds, baselines, suppressions with justification.
- Understand what these scanners cannot find, so they complement rather than replace threat modelling and testing.
:::

## Stage placement

Fast, deterministic checks belong on the pull request where developers see them in minutes: linters, fast SAST rules, secret scanning, IaC scanning, SCA when the lockfile changed. Slow or noisy checks (deep CodeQL analysis, full image scans, DAST) run after merge or nightly and open issues rather than block. Everything that blocks must be fast and trusted, or developers will route around it.

## Static analysis in practice

@file: .github/workflows/security.yml
```yaml
name: Security checks

on:
  pull_request:
  push:
    branches: [main]
  schedule:
    - cron: "17 3 * * 1"   # weekly deep scan

permissions:
  contents: read
  security-events: write   # upload SARIF to the Security tab

jobs:
  semgrep:
    runs-on: ubuntu-24.04
    container: returntocorp/semgrep@sha256:REPLACE_WITH_PINNED_DIGEST
    steps:
      - uses: actions/checkout@11bd71901bbe5b1630ceea73d27597364c9af683 # v4.2.2
      - run: semgrep ci --config p/owasp-top-ten --config p/secrets --config .semgrep/ --sarif --output semgrep.sarif
      - uses: github/codeql-action/upload-sarif@f09c1c0a94de965c15400f5634aa42fac8fb8f88 # v3.27.5
        if: always()
        with: { sarif_file: semgrep.sarif }

  codeql:
    runs-on: ubuntu-24.04
    steps:
      - uses: actions/checkout@11bd71901bbe5b1630ceea73d27597364c9af683 # v4.2.2
      - uses: github/codeql-action/init@f09c1c0a94de965c15400f5634aa42fac8fb8f88 # v3.27.5
        with: { languages: javascript-typescript, queries: security-extended }
      - uses: github/codeql-action/analyze@f09c1c0a94de965c15400f5634aa42fac8fb8f88 # v3.27.5

  gitleaks:
    runs-on: ubuntu-24.04
    steps:
      - uses: actions/checkout@11bd71901bbe5b1630ceea73d27597364c9af683 # v4.2.2
        with: { fetch-depth: 0 }   # scan history, not just the tip
      - uses: gitleaks/gitleaks-action@83373cf2f8c4db6e24b41c1a9b086bb9619e9cd3 # v2.3.7
        env:
          GITHUB_TOKEN: ${{ secrets.GITHUB_TOKEN }}
```

A custom Semgrep rule turns your own secure-coding conventions into enforcement. For example, flag any raw SQL built with string formatting in a Python codebase:

@file: .semgrep/no-format-sql.yml
```yaml
rules:
  - id: no-format-sql
    languages: [python]
    severity: ERROR
    message: "SQL built with string formatting. Use parameterised queries (see handbook Part IV chapter 11)."
    patterns:
      - pattern-either:
          - pattern: $CUR.execute(f"...", ...)
          - pattern: $CUR.execute("..." % ..., ...)
          - pattern: $CUR.execute("..." + ..., ...)
          - pattern: $CUR.execute("...".format(...), ...)
```

## Dependency scanning that people act on

Raw CVE lists are overwhelming: a typical Node project has hundreds of transitive dependencies and dozens of open advisories at any moment, most unreachable from your code. Make the signal useful:

- **Automate the updates, not just the alerts**: Dependabot or Renovate open PRs with changelogs; group minor updates; auto-merge patch updates when CI passes for low-risk packages.
- **Gate on severity and fixability**: block the PR on critical/high vulnerabilities *with a fix available*; report the rest.
- **Use reachability or exploitability data** where the tool supports it (EPSS scores, VEX statements) to prioritise.
- **Lockfiles are mandatory** and are what scanners read; a project without a lockfile has no reproducible dependency set to scan.
- **Scan the built image**, not just the manifest: base image CVEs matter and are fixed by rebuilding on a newer base, which is why images are rebuilt on a schedule even without code changes.

@file: .github/workflows/image-scan.yml (excerpt)
```yaml
      - name: Scan image
        uses: aquasecurity/trivy-action@18f2510ee396bbf400402947b394f2dd8c87dbb0 # 0.29.0
        with:
          image-ref: ghcr.io/${{ github.repository }}@${{ needs.build.outputs.digest }}
          format: sarif
          output: trivy.sarif
          severity: CRITICAL,HIGH
          ignore-unfixed: true          # report only what a rebuild or upgrade can fix
          exit-code: "1"                # fail the job on findings at these severities
          trivyignores: .trivyignore    # documented, expiring exceptions
```

An exceptions file must carry justification and an expiry, reviewed like code:

@file: .trivyignore
```text
# CVE-2024-XXXXX: affects the HTTP/2 server mode of libfoo; we only use the client. Re-evaluate by 2026-12-31. Owner: platform team.
CVE-2024-XXXXX
```

## Secret scanning and push protection

Secrets in git history are permanent until rotated: deleting the commit does not help because clones, forks and caches keep it. Layers of defence:

1. **Pre-commit hooks** (gitleaks or detect-secrets) catch most mistakes before a commit exists.
2. **Push protection** on the hosting platform rejects pushes containing recognised secret patterns.
3. **Repository scanning**, including history, with alerts routed to owners.
4. **Automatic revocation**: many providers (AWS, GitHub, Stripe) participate in secret-scanning partner programmes and revoke leaked tokens within minutes; treat this as a safety net, not a plan.
5. **Response runbook**: a found secret is rotated first, then investigated (was it used?), then removed from history if the repository is public (history rewrite plus provider cache purge), then the root cause is fixed (why was a secret available to paste?).

:::danger Rotate before you investigate
When a credential appears in a repository, assume it is compromised. Rotate immediately, then look at CloudTrail or the provider's logs for use. Investigation first gives an attacker time.
:::

## IaC scanning

Infrastructure code misconfigurations are the cloud equivalent of injection bugs: public S3 buckets, security groups open to 0.0.0.0/0 on port 22, unencrypted databases, IAM wildcards. Checkov and Trivy evaluate Terraform and CloudFormation against hundreds of policies on the PR, before anything is deployed. Write custom policies for organisation rules (required tags, approved Regions, mandatory logging) and treat suppressions exactly like dependency exceptions: inline, justified, reviewed.

```hcl
resource "aws_s3_bucket" "logs" {
  bucket = "acme-portal-logs"
  # checkov:skip=CKV_AWS_144: Cross-region replication not required for logs; retention handled by lifecycle. Reviewed 2026-10.
}
```

## What scanners cannot find

Business-logic flaws (a user approving their own expense), authorisation gaps (missing ownership checks), design weaknesses (trusting an internal network), misuse of correct cryptography, race conditions, and anything specific to your domain. Scanners enforce hygiene so that human review time goes to these. A pipeline full of green scanner badges with no threat model is a false sense of security ([Threat Modeling and Trust Boundaries](#/p04/c02)).

## Keeping the signal trusted

- Start with a **baseline**: when introducing a scanner to an existing codebase, record current findings as the baseline, fail only on *new* findings, and burn down the backlog as planned work.
- **Tune rules** that produce false positives rather than teaching the team to ignore the tool.
- **Owner per finding**: route to the team that owns the code; unowned findings rot.
- **Metrics**: time to fix by severity, open findings trend, exceptions count and age.
- **One place to look**: upload SARIF to the platform's security tab or a central dashboard rather than scattering results across job logs.
