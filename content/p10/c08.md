# Database Migration Safety and Rollbacks

:::objectives
- Apply the expand/contract pattern so schema changes never break the running version or block rollback.
- Recognise which DDL operations lock tables or rewrite data on PostgreSQL and MySQL, and the safe alternatives.
- Run migrations from the pipeline with the right ordering, permissions, timeouts and verification, and plan the rollback for each kind of change.
:::

## Why database changes are the hard part of deployment

Application code can run two versions side by side and be rolled back by redeploying bytes. A database has one schema and one dataset shared by both versions, and a change to it is a change to reality that cannot be undone by deploying old code. Dropping a column destroys data; renaming it breaks the old version instantly; adding a `NOT NULL` column without a default fails for every existing row; a long `ALTER` on a big table locks writes for minutes. Migration safety is therefore about **ordering and compatibility**, not about writing SQL.

## Expand / contract

Every change becomes a sequence of small, backwards-compatible steps spread across deployments:

```flow
{
  "title": "Rename column 'name' to 'full_name' without downtime",
  "participants": ["Deploy 1 (migration)","App v2","Deploy 2 (backfill)","App v3","Deploy 3 (contract)"],
  "steps": [
    {"from":"Deploy 1 (migration)","to":"Deploy 1 (migration)","label":"EXPAND: ADD COLUMN full_name NULL","detail":"Additive, instant on PostgreSQL. App v1 ignores the new column; nothing breaks.","note":"Expand steps are always safe to roll back: the old app never knew the column existed."},
    {"from":"App v2","to":"App v2","label":"Dual-write: write both name and full_name; read name","detail":"Deployed with any strategy; compatible with v1 running concurrently because v1 keeps writing name."},
    {"from":"Deploy 2 (backfill)","to":"Deploy 2 (backfill)","label":"Backfill full_name = name in batches of 5,000","detail":"Batched with sleeps, idempotent, resumable; never one giant UPDATE that locks the table and bloats WAL."},
    {"from":"App v3","to":"App v3","label":"Read full_name; still write both","detail":"Verify with a check that no rows have full_name IS NULL AND name IS NOT NULL."},
    {"from":"Deploy 3 (contract)","to":"Deploy 3 (contract)","label":"CONTRACT: stop writing name; later DROP COLUMN name","detail":"Only after every running version reads full_name and after the rollback window for v3 has passed. Dropping is the only irreversible step, so it is last and separate.","note":"Rollback at any step before contract is a code redeploy, never a schema reversal."}
  ]
}
```

The pattern generalises: new table (create, dual-write, backfill, switch reads, drop old); change type (add new column of the new type, same dance); add constraint (add as `NOT VALID`, fix data, `VALIDATE`); split a table (same as new table). It costs more steps and more deploys. It buys the ability to deploy at any hour and to roll back the application freely.

## Operations that hurt (PostgreSQL)

| Operation | Problem | Safe approach |
|---|---|---|
| `ADD COLUMN ... NOT NULL` without default | Fails on existing rows | Add nullable, backfill, then `SET NOT NULL` (PostgreSQL 12+ uses a validated `CHECK` to avoid a full scan: add `CHECK (col IS NOT NULL) NOT VALID`, validate, then `SET NOT NULL`) |
| `ADD COLUMN ... DEFAULT <volatile>` | Table rewrite (constant defaults are instant since PG 11) | Use constant defaults; set volatile values in a backfill |
| `CREATE INDEX` | Blocks writes for the duration | `CREATE INDEX CONCURRENTLY` (cannot run in a transaction; can leave an invalid index on failure, which you must drop and retry) |
| `ALTER COLUMN TYPE` | Full rewrite with exclusive lock (except some widenings, e.g. varchar length increase) | New column + backfill + swap |
| `ADD FOREIGN KEY` / `CHECK` | Full scan with lock | Add `NOT VALID`, then `VALIDATE CONSTRAINT` (takes a weaker lock) |
| `DROP COLUMN` | Fast, but irreversible and breaks old code | Last step of contract, after rollback window |
| Rename | Instant but breaks every running old version | Never rename in place; expand/contract |
| Any DDL waiting for a lock | Queues behind long transactions and *blocks all new queries* behind it | `SET lock_timeout = '3s'` and retry; run when long transactions are absent |

:::warning The lock queue trap
`ALTER TABLE` needs an `ACCESS EXCLUSIVE` lock. If a long-running report holds a share lock, the ALTER waits, and every new query on the table queues behind the ALTER. A one-line migration can take the site down without "doing" anything. Always set `lock_timeout` so the migration fails fast and retries instead of queueing the world.
:::

MySQL (InnoDB) has online DDL for many operations (`ALGORITHM=INPLACE, LOCK=NONE`) but not all; `pt-online-schema-change` and `gh-ost` perform changes by building a shadow table and swapping. The same expand/contract logic applies.

## Running migrations from the pipeline

- **Migrations are versioned files in the repository**, applied by a tool that records which have run (Flyway, Liquibase, Alembic, Prisma Migrate, golang-migrate, Rails, Django). Never apply by hand.
- **Order**: run expand migrations *before* deploying the new application version, as a separate pipeline step or a pre-deploy job, with a lock so two deploys cannot migrate concurrently. Contract migrations run in a later release after the rollback window.
- **Permissions**: the migration role may alter schema; the application runtime role may not (Part VIII chapter 10). Credentials for migration come from the secret store at run time.
- **Timeouts**: `statement_timeout` and `lock_timeout` set in the migration session; retries with backoff for lock timeouts.
- **Transactions**: wrap each migration in a transaction where the database supports transactional DDL (PostgreSQL does; MySQL does not), except for operations that cannot run inside one (`CREATE INDEX CONCURRENTLY`).
- **Rehearsal**: run every migration against a production-sized copy (restored from backup) in staging and record its duration and lock behaviour; a migration that takes 40 minutes on real data is a different change from one that takes 40 ms.
- **Verification**: post-migration checks (row counts, constraint validity, application smoke tests) before the deploy proceeds.
- **Linting**: tools such as `squawk` (PostgreSQL) flag dangerous DDL in pull requests.

@file: .github/workflows/deploy.yml (migration step)
```yaml
  migrate:
    runs-on: ubuntu-24.04
    environment: production
    concurrency: { group: migrate-production, cancel-in-progress: false }
    steps:
      - uses: aws-actions/configure-aws-credentials@e3dd6a429d7300a6a4c196c26e071d42e0343502 # v4.0.2
        with: { role-to-assume: arn:aws:iam::123456789012:role/gha-portal-migrate-prod, aws-region: eu-west-1 }
      - name: Run migrations as a one-off ECS task
        run: |
          set -euo pipefail
          TASK=$(aws ecs run-task --cluster portal-prod --task-definition portal-migrate \
                   --launch-type FARGATE --network-configuration "$NETCONF" \
                   --overrides '{"containerOverrides":[{"name":"migrate","command":["npm","run","migrate:up"]}]}' \
                   --query 'tasks[0].taskArn' --output text)
          aws ecs wait tasks-stopped --cluster portal-prod --tasks "$TASK"
          CODE=$(aws ecs describe-tasks --cluster portal-prod --tasks "$TASK" --query 'tasks[0].containers[0].exitCode' --output text)
          test "$CODE" = "0"
```

The migration runs inside the VPC with the migration role's credentials, as a one-off task of the same image that is about to be deployed, so the migration files and the code are from the same commit.

## Backfills

Backfills are data migrations and need their own discipline: batched (a few thousand rows), keyed by primary key ranges, idempotent (`WHERE full_name IS NULL`), throttled (sleep between batches, watch replication lag), resumable (record progress), observable (rows per second, lag), and run outside the deploy pipeline as a job that can be paused. A backfill that runs as one `UPDATE` on 200 million rows holds locks for an hour, generates gigabytes of WAL, lags replicas and may fill the disk.

```python
# Batched, resumable backfill
last_id = load_checkpoint() or 0
while True:
    with conn.transaction():
        rows = conn.execute("""
            UPDATE users SET full_name = name
            WHERE id IN (SELECT id FROM users WHERE id > %s AND full_name IS NULL ORDER BY id LIMIT 5000)
            RETURNING id""", (last_id,)).fetchall()
    if not rows:
        break
    last_id = max(r[0] for r in rows)
    save_checkpoint(last_id)
    if replication_lag_seconds() > 5:
        time.sleep(5)
    time.sleep(0.2)
```

## Rollback planning per change type

| Change | Rollback |
|---|---|
| Expand (add nullable column/table/index) | Deploy old code; schema stays (harmless); optionally remove later |
| Backfill | Nothing to roll back; data is additive |
| Switch reads | Deploy old code (it reads the old column, still being written) |
| Contract (drop column/table) | **Not reversible**: restore from backup or PITR into a side database and copy data back. This is why contract is last and separate and why backups are verified before it |
| Data fix (UPDATE) | Pre-change snapshot of affected rows into a backup table; reverse script prepared and tested *before* running forward |

"Down migrations" that reverse DDL are useful in development and nearly useless in production: a down that drops a column loses data written since the up. Plan rollbacks as *forward* code deploys plus data preservation, not as schema reversal.

## Zero-downtime checklist

```checklist
# Before merging a migration
- Expand/contract: does the change work with both the current and the next application version running?
- Is any statement a table rewrite or a long lock on a large table? Replaced with the online alternative?
- lock_timeout and statement_timeout set? Retry on lock timeout?
- Rehearsed on a production-sized copy with duration recorded?
- Backfill batched, idempotent, throttled and resumable?
- Contract step scheduled for a later release after the rollback window?
- Rollback written and tested for this specific change?
- Backup verified recently if this is a destructive step?
- Migration role, not application role, used?
```
