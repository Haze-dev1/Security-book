## First principles: why pipelines exist

Software changes break things. The further a broken change travels before anyone notices, the more it costs to find and undo: a failing unit test on a laptop costs seconds; the same bug found by a customer costs an incident, a rollback, a postmortem and trust. A **pipeline** is a machine that moves every change through a fixed sequence of checks and environments, automatically, the same way every time, so that defects are caught as early and as cheaply as possible and so that the act of releasing is routine rather than heroic.

Three terms are often blurred:

- **Continuous integration (CI)**: every change is merged to the main branch frequently (at least daily) and each merge is automatically built and tested. The point is small, frequent integration so conflicts and regressions are small and recent.
- **Continuous delivery (CD)**: every change that passes CI produces a deployable artefact and *could* be released to production at the push of a button. Releases are a business decision, not a technical event.
- **Continuous deployment**: every change that passes the pipeline *is* released to production automatically, with no human gate. Requires excellent automated testing, progressive delivery and fast rollback.

Most organisations should aim for continuous delivery first; continuous deployment is appropriate once the pipeline's verdict is trusted more than a human's glance at a diff.

## Build once, promote many

The most important pipeline principle: produce one immutable artefact per commit and promote that same artefact through every environment. Rebuilding for production means production runs code that was never tested. Immutability comes from content-addressed tags (the git SHA or the image digest), never `latest`. Configuration differences between environments are injected at deploy time (environment variables, secrets, config files), never baked into the artefact ([Configuration Management and Error Handling](#/p03/c12)).

## Properties of a trustworthy pipeline

- **Reproducible**: same commit, same result. Pin tool versions, lock dependencies, avoid network fetches of unpinned resources, fix the base image by digest.
- **Hermetic**: jobs do not depend on state left on the runner. Ephemeral runners or clean workspaces; caches are an optimisation, not a dependency.
- **Fast**: PR checks under 10 minutes or developers stop waiting and start batching. Parallelise, cache dependencies, run the slow suites after merge, shard tests.
- **Deterministic tests**: a flaky test is worse than no test because it trains people to click "re-run" and ignore red. Quarantine and fix flakes with the same urgency as bugs.
- **Observable**: every run has logs, timing per step, test reports and a link from the deployment back to the commit, the PR and the approvals.
- **Secure**: the pipeline has production credentials and runs code from pull requests; it is a prime target ([Release Approvals, Supply Chain Security and Audit Trails](#/p10/c09)).
- **Fails loudly and specifically**: a red pipeline tells you which test, which line, which step, not "exit code 1".

## Environments and promotion

An **environment** is a named deployment target (dev, staging, production, or per-client) with its own secrets, infrastructure and protection rules. Promotion is the act of deploying an already-built artefact to the next environment. Protection rules enforce who may approve, which branches may deploy, and wait timers. Keep environments as alike as possible: the value of staging is proportional to how closely it resembles production, which is why infrastructure as code (chapter 5) matters so much for testing.

:::warning Staging is not a place to be different
Common anti-patterns: staging on a different database engine version, staging without TLS, staging with a single instance when production has many, staging sharing a database with development. Each difference is a class of bugs you will meet first in production.
:::

## The developer workflow this produces

1. Branch from main, make a small change, push. The PR pipeline runs lint, unit tests, type checks and security scans in a few minutes and reports inline.
2. Review and merge. The main pipeline builds the artefact, runs the full test suite, publishes the image with the SHA tag and deploys to dev automatically.
3. Integration and end-to-end tests run against dev; on success the artefact is promoted to staging automatically.
4. A release manager (or an automated policy) approves promotion to production during an allowed window; the deployment rolls out progressively with health checks and rolls back itself if error rates rise.
5. The change record, the deployment log and the artefact provenance are linked and retained.

:::fde Clients will ask for "a CI/CD pipeline" as a deliverable
What they need is the workflow above with their approval model embedded. Ask: who may approve production deploys? Are there change windows? What evidence does their audit function need? Which environments exist and who owns them? Then build the pipeline to produce that evidence automatically, so compliance is a by-product of shipping rather than a tax on it.
:::

## Common mistakes

- Rebuilding artefacts per environment, or deploying `latest`.
- Tests that depend on the order they run in, on the clock, or on external services without stubs.
- Long-lived cloud credentials stored as CI secrets instead of short-lived OIDC-federated roles (chapter 2).
- Pipelines that only engineers can read: no deployment history visible to the business or to auditors.
- Treating pipeline code as second-class: untested, unreviewed, copy-pasted YAML.
