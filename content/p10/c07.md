## The problem every strategy solves

A new version may be broken in ways tests did not catch. A deployment strategy limits how many users see the broken version, for how long, and how fast you can return to the old one. The dimensions that differ:

| Strategy | Exposure during rollout | Rollback speed | Extra capacity | Complexity | Fits |
|---|---|---|---|---|---|
| Recreate (stop old, start new) | 100%, with downtime | Redeploy old (minutes) | None | Trivial | Dev environments, batch jobs, single-instance tools |
| Rolling | Gradually 0→100% by instance | Redeploy old (minutes) or stop rollout | Small (surge) | Low | Default for stateless services |
| Blue-green | 0% then 100% at switch | Seconds (switch back) | 2× during deploy | Medium | Services where instant rollback matters; database-compatible releases |
| Canary | Small % then increasing | Seconds (shift weight back) | Small | Medium–high (needs metrics) | High-traffic services with good SLIs |
| Feature flags (dark launch) | Code deployed; feature off | Instant (flip flag) | None | Flag system and hygiene | Behavioural changes, gradual exposure by user or tenant |

All of them require **backwards-compatible changes** between adjacent versions, because old and new run concurrently during every strategy except recreate: API contracts, message formats, database schemas (chapter 8) and cache formats must all tolerate both versions.

## Rolling updates

Replace instances a few at a time; each new instance must pass health checks before the next old one is removed. On Kubernetes this is the `Deployment` default with `maxSurge` and `maxUnavailable`; on ECS it is the rolling update deployment type with `minimumHealthyPercent` and `maximumPercent`; on an Auto Scaling Group it is an instance refresh.

```yaml
# Kubernetes: conservative rolling update
spec:
  replicas: 6
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 1          # at most one extra pod during rollout
      maxUnavailable: 0    # never drop below desired capacity
  minReadySeconds: 20      # a pod must stay ready this long before counting
  template:
    spec:
      terminationGracePeriodSeconds: 45
      containers:
        - name: api
          readinessProbe: { httpGet: { path: /ready, port: 8080 }, periodSeconds: 5 }
          lifecycle:
            preStop: { exec: { command: ["sh", "-c", "sleep 10"] } }   # let the LB stop sending before shutdown
```

Rolling updates are only as safe as the readiness check: a `/ready` that returns 200 before the app can serve traffic, or that does not check critical dependencies, lets a broken version roll all the way out. Pair with **deployment circuit breakers**: ECS can roll back automatically when tasks fail to stabilise; Kubernetes `progressDeadlineSeconds` marks a stuck rollout, and tools like Argo Rollouts add metric analysis.

## Blue-green

Two identical environments: **blue** serves production; **green** receives the new version, is tested (smoke tests, synthetic transactions, a trickle of internal traffic), then the router switches all traffic to green. Blue stays warm for instant rollback, then becomes the next green.

On ECS, CodeDeploy implements blue-green natively with traffic shifting options, lifecycle hooks (run tests against green before switching) and automatic rollback on CloudWatch alarms; on Kubernetes, Argo Rollouts' `BlueGreen` strategy does the same with `prePromotionAnalysis`. Costs: double capacity during the deploy window and the need for every stateful dependency to serve both versions. Blue-green does *not* help with database rollbacks: switching back to blue does not un-run a migration.

## Canary releases

Send a small fraction of traffic (1%, then 5%, 25%, 50%, 100%) to the new version while comparing its SLIs to the baseline. If error rate or latency regress beyond a threshold, shift traffic back automatically. Canary analysis needs: metrics separated by version (label every metric with the version), enough traffic for statistical meaning in each step, defined success criteria, and a bake time per step.

@file: rollout.yaml (Argo Rollouts excerpt)
```yaml
apiVersion: argoproj.io/v1alpha1
kind: Rollout
spec:
  strategy:
    canary:
      canaryService: api-canary
      stableService: api-stable
      trafficRouting:
        alb: { ingress: api, servicePort: 80 }
      steps:
        - setWeight: 5
        - pause: { duration: 10m }
        - analysis:
            templates: [{ templateName: error-rate }]
        - setWeight: 25
        - pause: { duration: 15m }
        - analysis:
            templates: [{ templateName: error-rate }, { templateName: p95-latency }]
        - setWeight: 50
        - pause: { duration: 15m }
        - setWeight: 100
---
apiVersion: argoproj.io/v1alpha1
kind: AnalysisTemplate
metadata: { name: error-rate }
spec:
  metrics:
    - name: error-rate
      interval: 1m
      failureLimit: 2
      successCondition: result[0] < 0.01
      provider:
        prometheus:
          address: http://prometheus:9090
          query: |
            sum(rate(http_requests_total{service="api-canary",code=~"5.."}[2m]))
            / sum(rate(http_requests_total{service="api-canary"}[2m]))
```

Canary pitfalls: sticky sessions sending the same users to the canary (good for consistency, bad for sampling); background jobs and consumers that cannot be weighted (use flags or a separate canary consumer group); comparing the canary to a stale baseline (compare to the stable version *at the same time*, not to yesterday); and canaries at 1% of low traffic that see too few requests to detect anything.

## Feature flags: separating deploy from release

A **feature flag** is a runtime switch evaluated per request with a context (user, tenant, Region, percentage). Deploy the code dark (flag off), enable for internal users, then 1% of users, then specific tenants, then everyone, then remove the flag. Benefits: rollback becomes a configuration change in seconds without a deploy; features can be tested in production by a few people; risky migrations can run both paths and compare; operations gets **kill switches** for expensive features during incidents.

```python
# Flag evaluation with a typed context; the provider could be LaunchDarkly, Unleash, AWS AppConfig, OpenFeature...
from openfeature import api

client = api.get_client("portal")

def statement_view(user, tenant):
    ctx = EvaluationContext(targeting_key=user.id, attributes={"tenant": tenant.id, "plan": tenant.plan})
    if client.get_boolean_value("new-statement-renderer", False, ctx):
        return render_statement_v2(user)
    return render_statement_v1(user)
```

Flag hygiene, because flags rot into unmaintainable branches:

- Every flag has an owner, a purpose, a creation date and a planned removal date; a report lists flags older than 90 days.
- Flags are either **release flags** (temporary, removed after rollout) or **operational flags** (permanent kill switches, documented as such). Do not confuse them.
- Flag configuration changes are audited and reviewed like deploys (who turned what on for whom, when).
- Defaults are safe: if the flag service is unreachable, the code uses a sensible default and keeps working (fail static with the last known configuration).
- Test both paths while a flag exists; delete the old path and the flag promptly after full rollout.
- Never put secrets in flag payloads, and treat flag targeting data (user IDs, tenant IDs) as personal data.

## Choosing

- Stateless web services with good metrics: rolling by default, canary for high-traffic or high-risk services.
- Need instant full rollback or a pre-switch test environment: blue-green.
- Behavioural or UI changes, tenant-specific rollout, risky migrations: feature flags on top of any deployment strategy.
- Databases: none of these; use expand/contract migrations (chapter 8).
- Infrastructure changes (new instance type, OS upgrade): blue-green at the infrastructure level (new ASG or node group), shifting traffic gradually.

## Rollback is a first-class path

Whatever the strategy, rollback must be rehearsed, fast and one command: redeploy the previous digest (always know what it is), switch the listener, shift the weight, flip the flag. A rollback must not require a build. Deployment tooling records every deployment with the artefact digest, who approved it and the result, so "roll back to the last good version" is unambiguous. After a rollback, the incident process (Part XI) takes over; the pipeline stays frozen for that service until the cause is understood.
