## What an artefact is

An **artefact** is the deployable output of a build: a container image, a zip for Lambda, a wheel or npm package, a static site bundle, a Helm chart, a Terraform module version. Good artefacts share properties:

- **Immutable**: identified by content (digest) or by a tag that is never reassigned (git SHA, semantic version).
- **Self-describing**: carries labels or metadata naming the source commit, build time, builder and version.
- **Reproducible** (ideally bit-for-bit, practically "same inputs, same behaviour"): pinned bases and dependencies, no `apt-get upgrade` without a snapshot date, no build-time network fetches of unpinned resources.
- **Accompanied by evidence**: a software bill of materials (SBOM), a provenance attestation stating which workflow built it from which commit, and a signature.

```compare
  ]

```

Deploy by digest. A tag is a pointer; a digest is the artefact. Pipelines that pass `image@sha256:...` from the build job to the deploy job remove an entire class of "which version is running?" confusion and defeat tag-overwrite attacks. Registries should also have **tag immutability** enabled so a release tag can never be re-pushed.

## Fast, correct Dockerfiles

Layer caching rewards ordering by change frequency: things that rarely change (base image, system packages) first; dependency manifests next; source code last. A multi-stage build keeps compilers and dev dependencies out of the runtime image.

@file: Dockerfile
```dockerfile
# syntax=docker/dockerfile:1.7
ARG NODE_IMAGE=node:22.11.0-bookworm-slim@sha256:REPLACE_WITH_DIGEST

FROM ${NODE_IMAGE} AS deps
WORKDIR /app
COPY package.json package-lock.json ./
# Cache mount keeps the npm cache between builds without baking it into a layer.
RUN --mount=type=cache,target=/root/.npm npm ci --omit=dev

FROM ${NODE_IMAGE} AS build
WORKDIR /app
COPY package.json package-lock.json ./
RUN --mount=type=cache,target=/root/.npm npm ci
COPY . .
RUN npm run build && npm test

FROM gcr.io/distroless/nodejs22-debian12:nonroot@sha256:REPLACE_WITH_DIGEST AS runtime
WORKDIR /app
ENV NODE_ENV=production
COPY --from=deps /app/node_modules ./node_modules
COPY --from=build /app/dist ./dist
COPY package.json ./
USER nonroot
EXPOSE 8080
# OCI labels: populated by the build with --label or metadata-action
LABEL org.opencontainers.image.source="https://github.com/acme/portal" \
      org.opencontainers.image.revision="${GIT_SHA}"
CMD ["dist/server.js"]
```

Rules of thumb: pin base images by digest and let a bot propose updates; use `.dockerignore` to exclude `.git`, `node_modules`, secrets and test fixtures; never pass secrets as build args (they are visible in the image history) and use `--mount=type=secret` for private registries during build; run as a non-root user; prefer distroless or minimal bases for the runtime stage; keep one process per container.

## BuildKit caching in CI

CI runners start empty, so without remote caching every build is a full build. BuildKit exports cache to a registry or to the CI's cache store:

```yaml
      - uses: docker/build-push-action@4f58ea79222b3b9dc2c8bbdd6debcef730109a75 # v6.9.0
        with:
          context: .
          push: true
          tags: ${{ steps.meta.outputs.tags }}
          platforms: linux/amd64,linux/arm64
          cache-from: type=registry,ref=ghcr.io/acme/portal:buildcache
          cache-to: type=registry,ref=ghcr.io/acme/portal:buildcache,mode=max
          build-args: |
            GIT_SHA=${{ github.sha }}
          provenance: mode=max
          sbom: true
```

`mode=max` caches intermediate stages, not only the final layers, which is what makes multi-stage builds fast on the second run. Multi-platform builds produce a manifest list so the same tag runs on x86 and Graviton (arm64) instances; cross-building via QEMU is slow, so for large images use native runners per architecture and merge manifests.

## SBOMs, provenance and signatures

- **SBOM** (SPDX or CycloneDX): the inventory of packages in the artefact. Generated at build (Syft, BuildKit's `sbom: true`), attached to the image as an attestation and stored. When the next critical CVE lands, you query SBOMs to know which deployed images are affected within minutes, instead of rescanning everything.
- **Provenance** (SLSA): a signed statement of how the artefact was built: source repository and commit, builder identity, build parameters. Generated by the build system, not by the code it builds.
- **Signature** (Sigstore cosign): binds the digest to the identity of the workflow that built it. A deploy-time admission policy verifies the signature and provenance before anything runs (chapter 9).

```bash
# Verify an image was built by the expected workflow before deploying it
cosign verify ghcr.io/acme/portal@sha256:... \
  --certificate-identity-regexp '^https://github.com/acme/portal/.github/workflows/build.yml@refs/heads/main$' \
  --certificate-oidc-issuer https://token.actions.githubusercontent.com
```

## Non-container artefacts

- **Lambda zips and layers**: build in a container matching the Lambda runtime; include only runtime dependencies; publish versions and point aliases at them (the alias is the mutable pointer, the version the immutable artefact).
- **Static frontends**: content-hashed filenames for cache-busting, uploaded to S3 with long `Cache-Control` for hashed assets and short for `index.html`; the bundle is the artefact, the CloudFront invalidation is the deploy.
- **Libraries and packages**: semantic versions, published to a private registry (CodeArtifact, GitHub Packages, Artifactory) with provenance; never republish a version.
- **Helm charts and Terraform modules**: versioned in an OCI registry or module registry; consumers pin versions.

## Operating a registry

- **Access**: push only from CI identities (OIDC), pull by deploy identities, read-only for humans; no shared credentials.
- **Immutability**: tag immutability on; deletes restricted.
- **Retention**: lifecycle policies remove untagged and old dev images (cost and noise) while keeping every image that was ever deployed to production for the audit horizon.
- **Scanning**: scan on push and continuously (new CVEs apply to old images); alert owners.
- **Replication**: replicate to each Region you deploy in (pull latency, Regional isolation); for client-owned accounts, replicate or re-push into their registry so their production does not depend on yours.
- **Pull-through caches** for public bases to survive upstream rate limits and outages.

:::cost Registry costs are quiet but real
ECR charges per GB stored; a pipeline pushing a 400 MB image per commit for a year is terabytes. Lifecycle policies (keep last 30 untagged, keep all production-deployed tags) are part of the build pipeline design, not an afterthought.
:::

## Troubleshooting builds

- **Cache never hits**: `COPY . .` before dependency install, a file that changes every build (timestamps, build info) copied early, or cache export not configured. Inspect with `docker buildx build --progress=plain`.
- **Works locally, fails in CI**: different architecture (arm64 laptop vs amd64 runner), `.dockerignore` differences, uncommitted files, environment variables present locally.
- **Image too large**: dev dependencies in runtime stage, missing `.dockerignore`, build tools left in; use `docker history` and `dive` to see which layer grew.
- **"manifest unknown" at deploy**: the tag was never pushed for the platform requested, or the deploy references a tag from a different registry.
- **Rate limits** pulling public bases: authenticate or use a pull-through cache.
