:::objectives

- Protect the software supply chain end to end: source, dependencies, build, artefacts, deployment, with SLSA levels as the map.

## Approvals: the control that must not become theatre

Change management frameworks (ITIL, SOX, ISO 27001, PCI DSS) require that production changes are authorised, tested, reviewed by someone other than the author, and recorded. Done badly this is a weekly meeting where a board approves tickets nobody reads. Done well it is a pipeline whose gates *are* the controls and whose logs *are* the evidence.

Map the requirement to mechanisms:

| Requirement | Mechanism |
|---|---|
| Author cannot approve their own change | Branch protection: required reviews, dismiss stale approvals, `CODEOWNERS` for sensitive paths; the author's approval does not count |
| Changes are tested before production | Required status checks must pass before merge; promotion only from a successful build of `main` |
| Production deploys are authorised | Environment protection rules: required reviewers for `production`, deployment branch policy (`main` only), optional wait timer |
| Emergency changes are controlled | A documented break-glass path (a labelled PR with one reviewer, or a direct deploy by an on-call role) that raises an alert and requires a retrospective approval within 24 hours |
| Standard, low-risk changes are expedited | Pre-approved change types (dependency patch bumps, config within limits) deploy automatically if checks pass; recorded as standard changes |
| Segregation of duties | Developers cannot assume the production apply role; only the pipeline can, triggered by approvals from a distinct group |
| Records retained | Deployment history, approvals and plans exported to immutable storage for the audit horizon |

:::fde Negotiating with a change advisory board
Enterprise clients may insist that every production change be approved in a weekly meeting. The compromise that works: classify changes. Standard changes (defined, tested, low risk) flow through the pipeline with automated evidence and are reported to the board; normal changes need an approver from the board in the pipeline's environment gate; emergency changes follow the break-glass path. Show the board the dashboard of what deployed, when, by whom, with links to evidence. Most boards prefer this to reading tickets.
:::

The SolarWinds (build system compromise), Codecov (CI script tampering), event-stream and xz (maintainer takeover), and the 2025 wave of compromised GitHub Actions incidents each exploited one of these links. The answer is layered: no single control, but a chain in which each artefact can prove where it came from.

## SLSA: a maturity map

Supply-chain Levels for Software Artifacts (SLSA) defines build-provenance levels:

- **Level 1**: provenance exists (the build produces a statement of how the artefact was built).
- **Level 2**: provenance is generated by a hosted build platform and signed, so it cannot be forged by the build steps themselves.
- **Level 3**: the build runs on a hardened platform with isolation between builds and non-forgeable provenance; secrets are not accessible to user-defined build steps.

GitHub Actions with the official provenance generators or `actions/attest-build-provenance`, GitLab, and Google Cloud Build can reach Level 3 for typical projects. Consumers verify provenance before use: the deployment pipeline (or a Kubernetes admission controller such as Kyverno or Sigstore policy-controller) checks that the image's attestation names the expected repository, workflow and branch.

@file: .github/workflows/build.yml (attestation step)
```yaml
      - uses: actions/attest-build-provenance@ef244123eb79f2f7a7e75d99086184180e6d0018 # v1.4.4
        with:
          subject-name: ghcr.io/${{ github.repository }}
          subject-digest: ${{ steps.push.outputs.digest }}
          push-to-registry: true
```

@file: policy/verify-image.yaml (Kyverno excerpt)
```yaml
apiVersion: kyverno.io/v1
kind: ClusterPolicy
metadata: { name: verify-portal-images }
spec:
  validationFailureAction: Enforce
  rules:
    - name: verify-signature-and-provenance
      match: { any: [{ resources: { kinds: [Pod] } }] }
      verifyImages:
        - imageReferences: ["ghcr.io/acme/portal*"]
          attestors:
            - entries:
                - keyless:
                    subject: "https://github.com/acme/portal/.github/workflows/build.yml@refs/heads/main"
                    issuer: "https://token.actions.githubusercontent.com"
          attestations:
            - type: https://slsa.dev/provenance/v1
              conditions:
                - all:
                    - key: "{{ buildDefinition.externalParameters.workflow.repository }}"
                      operator: Equals
                      value: "https://github.com/acme/portal"
          mutateDigest: true   # rewrite tags to digests
```

On ECS without an admission controller, the deploy job performs the same `cosign verify` before calling `UpdateService`, and an AWS Config rule or EventBridge alarm flags task definitions whose image was not registered by the pipeline.

## Dependency supply chain specifics

- **Lockfiles and `npm ci`/`pip install --require-hashes`/`go mod verify`**: install exactly what was reviewed.
- **Private registry proxy** (CodeArtifact, Artifactory, Nexus) in front of public registries with an allowlist or quarantine for new packages and a block on names that collide with internal packages (dependency confusion).
- **Minimum release age**: configure Renovate or the proxy to ignore versions younger than a few days; most malicious releases are detected and pulled within 48 hours.
- **Scoped names** for internal packages, and reserve them on public registries.
- **Review dependency changes** like code: diff of lockfile, changelog, maintainer changes.
- **SBOM retention** per deployed artefact for incident response.
- **Base image provenance**: use official or distroless images, pinned by digest; rebuild on a schedule.

## Source integrity

- SSO with phishing-resistant MFA for the code host; no personal access tokens with broad scope; fine-grained tokens with expiry where automation needs them.
- Signed commits (SSH or GPG) or at least verified commits via the web UI, and a rule requiring verification on `main`.
- Rulesets: no force-push, no deletion, linear history, required checks, restrictions on who can modify workflow files and `CODEOWNERS`.
- Audit log streaming from the code host to the SIEM.

## Audit trails that answer questions

An auditor, an incident responder and a curious engineer all ask the same questions: *What is running in production right now, where did it come from, who approved it, and what changed between then and the incident?* Design for those queries:

- **Deployment record per environment**: artefact digest, source commit, PR number, approvers, pipeline run URL, timestamp, outcome, rollback link. Emit it from the deploy job to a store you control (DynamoDB table, append-only S3 log, or the change-management system via API) in addition to the CI platform's history, which has limited retention.
- **Infrastructure changes**: Terraform plan and apply logs retained; CloudTrail for everything that happened in the account, including break-glass.
- **Configuration and flag changes**: audited by the flag and configuration systems, exported.
- **Immutable retention**: S3 with object lock for the compliance period; access restricted and logged.
- **Linkability**: from a running task's image digest you can reach the commit, the PR, the reviewer and the tests. From a ticket you can reach every deployment it caused.

```python
# Deploy job: write the deployment record
record = {
    "environment": "production",
    "service": "portal",
    "image_digest": digest,
    "git_sha": sha,
    "pull_request": pr_number,
    "approved_by": approvers,              # from the environment approval event
    "pipeline_run": run_url,
    "deployed_at": now_iso(),
    "deployed_by": "github-actions/deploy.yml",
    "outcome": "succeeded",
    "previous_image_digest": previous,     # what 'roll back' means
}
s3.put_object(Bucket="acme-change-records", Key=f"portal/{now_iso()}-{sha}.json",
              Body=json.dumps(record), ObjectLockMode="COMPLIANCE", ObjectLockRetainUntilDate=retain_until)
```

Produce a monthly report automatically (deployments, emergency changes, failures, rollbacks, mean time to restore) for the change board. Compliance becomes a query, not a project.

## Common mistakes

- Approval gates that one person can both request and grant.
- Pipelines with admin-level cloud credentials for convenience.
- Verifying signatures in CI but not at deploy time, so a manually pushed image still runs.
- Deployment history living only in the CI platform with 90-day retention when the audit horizon is seven years.
- Treating a compromised action or dependency as "we updated it" without rotating every secret the pipeline could reach.
