# Environments: Development, Staging and Production

:::objectives
- Explain why multiple environments exist and what each is for.
- Design environment parity so that staging actually predicts production.
- Handle data in non-production environments without leaking personal information.
- Promote changes between environments in a controlled, auditable way.
:::

:::prereq
Chapters 8 and 10.
:::

## The problem

If the only place your code runs with real infrastructure is production, then production is where you discover that the migration locks a table for ten minutes, that the new library needs a system package the image lacks, or that the load balancer's health check path changed. Environments exist to move those discoveries earlier, to a place where they cost nothing.

But environments are expensive to run and easy to let rot. A staging environment that differs from production in a dozen unknown ways gives false confidence, which is worse than none.

## The standard set

| Environment | Purpose | Who uses it | Data |
|---|---|---|---|
| **Local / development** | Fast iteration, debugging | Each engineer | Synthetic, seeded |
| **CI / ephemeral** | Automated tests on every PR; disposable | Pipelines | Fixtures, test containers |
| **Preview / per-PR** (optional) | Review a feature in a live deployment before merge | Reviewers, product, client | Synthetic |
| **Staging / pre-production** | Final rehearsal: production-like infra, integration with real third-party sandboxes, migration dry run, acceptance testing | Team, QA, client | Anonymised or synthetic; never raw production PII |
| **Production** | Real users | Everyone | Real |

Some clients add **UAT** (user acceptance testing) as a separate stable environment where their staff validate releases on their own schedule, or a **DR** environment that mirrors production in another region. Resist adding environments without a clear question each one answers.

## Parity: what must match

The principle: **same artifact, same infrastructure shape, different configuration**.

Must match production:

- The container image or build artifact (promote the exact image; never rebuild).
- Runtime and dependency versions (guaranteed by the artifact).
- Database engine and major version (PostgreSQL 16 in prod, PostgreSQL 16 in staging; SQLite locally is a trap).
- Infrastructure topology: load balancer, private subnets, the same managed services, IAM roles with equivalent policies. Smaller instance sizes are fine; different *kinds* of components are not.
- Configuration *keys*: every variable production needs exists in staging with a staging value.
- Deployment mechanism: the same pipeline deploys to both; staging is the rehearsal of the production deploy.

May differ:

- Instance sizes, replica counts, autoscaling bounds (cost).
- Secrets and credentials (always different).
- External endpoints (payment sandbox versus live).
- Log verbosity and sampling.
- Domain names and certificates (`staging-api.client.com`).

Infrastructure as code (Part X) is what makes parity achievable: the same Terraform module with a different variables file produces structurally identical environments.

## Data in non-production

Copying the production database to staging is the fastest way to leak client data. Staging is less protected, more people have access, it is forgotten in backups, and nobody notices when a developer exports it to a laptop. Rules:

1. **Never copy raw production data containing personal information to a lower environment** without a documented anonymisation step and the client's agreement.
2. **Prefer synthetic data generators** that produce realistic volumes and shapes (Faker, custom seeders) and are committed with the code.
3. When production-like data is genuinely required (performance testing, reproducing a bug), use a **masking pipeline**: restore to an isolated database, run deterministic masking (replace names, emails, addresses, free text; preserve referential integrity and distributions), verify no PII remains, then load into staging. Automate and audit it.
4. Payment, health and regulated data: synthetic only, no exceptions.

Part IV chapter 23 covers the obligations behind this.

## Promotion

Changes move upward: a merge to `main` deploys to staging automatically; a production deploy is triggered by promotion of the *same* artifact after checks. Patterns:

- **Automatic to staging, manual approval to production** (GitHub Environments with required reviewers). Most client projects.
- **Fully automatic with canary** when the team has strong observability and rollback automation.
- **Scheduled release trains** when the client needs predictability (every Tuesday 10:00) or change-management approval.

The promotion step is where the audit trail lives: who approved, which artifact, which commit, when. Part X chapter 9.

## Keeping staging honest

Staging decays silently. Guard it:

- Deploy to staging on every merge, so it is never behind by more than one change.
- Run smoke tests and synthetic checks against staging just like production.
- Apply the same infrastructure code; forbid console changes in staging too.
- Periodically rebuild staging from scratch with the IaC to prove the code is complete (this also tests disaster recovery).
- Budget for it honestly. A staging environment at 20–30% of production cost is typical; cutting it to zero is a false economy on anything that matters.

## Ephemeral environments

Spinning up a complete environment per pull request (preview deployments) lets reviewers and clients click through a feature before merge. Feasible when infrastructure is code and cheap (containers, serverless, a shared database with per-PR schemas). Destroy on merge to control cost. Even without full previews, running integration tests against disposable containers in CI (Testcontainers, Docker Compose) captures most of the value.

## Local development

The local environment should mirror production *services* through Docker Compose (same database engine, Redis, message broker) while the application runs natively or in a container with hot reload. A `make dev` or `docker compose up` that works from a fresh clone in under five minutes is a strong signal of a healthy project; new team members and client engineers judge you by it.

```yaml
# docker-compose.yml (development)
services:
  db:
    image: postgres:16.4
    environment: { POSTGRES_USER: app, POSTGRES_PASSWORD: app, POSTGRES_DB: app }
    ports: ["5432:5432"]
    volumes: ["pgdata:/var/lib/postgresql/data"]
    healthcheck: { test: ["CMD-SHELL", "pg_isready -U app"], interval: 5s, retries: 10 }
  redis:
    image: redis:7.4-alpine
    ports: ["6379:6379"]
  api:
    build: { context: ., target: dev }
    command: uvicorn app.main:app --host 0.0.0.0 --reload
    env_file: .env
    volumes: [".:/app"]
    ports: ["8000:8000"]
    depends_on: { db: { condition: service_healthy }, redis: { condition: service_started } }
volumes: { pgdata: {} }
```

## Common mistakes

- SQLite locally, PostgreSQL in production: query behaviour, types and constraints differ.
- Staging on a different cloud account structure, so IAM problems appear only in production.
- Rebuilding the image for production instead of promoting the staging-tested one.
- Production data in staging (and then in a developer's laptop backup).
- Staging shared by five feature branches, so nobody knows what is deployed.
- Environment-specific code paths (`if ENV == "prod"`).
- Letting staging drift for months, then trusting it before a critical release.

## Exercises

1. List every configuration key your application needs. Mark which differ between staging and production and which are secrets. Compare against what is actually set in each environment; discrepancies are latent incidents.
2. Write a seed script that generates realistic synthetic data for your application (hundreds of users, thousands of records) and commit it.
3. Draft the promotion policy for a client project: trigger, approvers, checks, and how an emergency hotfix bypasses or accelerates it.
