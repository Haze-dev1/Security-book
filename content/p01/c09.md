## The problem

A modern application is mostly other people's code. A typical FastAPI service pulls in 60 to 120 packages; a React frontend over a thousand. Each is a version chosen by someone, downloadable from a registry you do not control, with transitive dependencies of its own. Three failure modes follow:

1. **"Works on my machine."** Your laptop resolved `requests>=2.28` to 2.31 in March; the CI runner resolved it to 2.32 in June and something changed.
2. **Breaking changes on rebuild.** A production hotfix rebuilds the image, picks up a new minor version of a library, and ships an unrelated regression.
3. **Supply chain compromise.** A maintainer account is hijacked and a malicious version is published; everyone who installs "the latest compatible version" that day is affected.

Lockfiles and reproducible builds address the first two. The third requires those plus scanning and discipline (Part IV chapter 20).

## How resolution works

You declare **direct dependencies** with version constraints (`fastapi>=0.110,<1`, `"express": "^4.19"`). The package manager reads each package's own declared dependencies, resolves a set of exact versions satisfying all constraints, downloads them from a registry (PyPI, npm, Maven Central), verifies checksums, and installs them.

Version specifiers follow [[semantic versioning]] conventions: `^4.19.0` in npm means `>=4.19.0 <5.0.0`; `~4.19.0` means `>=4.19.0 <4.20.0`; Python's `~=2.31` means `>=2.31, ==2.*`. These express *intent* ("any compatible version"), which is exactly what you do not want at build time.

## Lockfiles

A **lockfile** records the exact resolved version of every package, direct and transitive, with integrity hashes: `package-lock.json`, `pnpm-lock.yaml`, `yarn.lock`, `poetry.lock`, `uv.lock`, `Pipfile.lock`, `Cargo.lock`, `go.sum`. Installing from a lockfile skips resolution and installs precisely what is recorded, failing if a hash does not match.

Rules:

- **Commit the lockfile** for applications. (Libraries typically do not, so consumers can resolve against their own trees.)
- **Install from the lockfile in CI and Docker**, in a mode that refuses to update it: `npm ci` (not `npm install`), `pnpm install --frozen-lockfile`, `poetry install --sync` / `uv sync --locked`, `pip install -r requirements.txt` where the file was generated with hashes by `pip-compile --generate-hashes`.
- **Update deliberately**, in their own pull requests, with tests, not as a side effect of adding a feature.

```bash
# Python with uv (fast, lockfile-based)
uv init && uv add "fastapi>=0.110" "sqlalchemy>=2" "psycopg[binary]"
uv lock                       # writes uv.lock with exact versions and hashes
uv sync --locked              # CI/Docker: install exactly, fail if lock is stale

# Python with pip-tools
pip-compile --generate-hashes -o requirements.txt pyproject.toml
pip install --require-hashes -r requirements.txt

# Node
npm ci                         # exact install from package-lock.json; errors if out of sync
```

## Reproducible builds

A build is reproducible when the same source produces the same artifact regardless of when or where it runs. Lockfiles handle application dependencies. The remaining variables:

- **Runtime version.** Pin it: `FROM python:3.12.7-slim-bookworm`, `.nvmrc` / `engines`, `.python-version`. Better, pin the base image by digest: `FROM python:3.12.7-slim@sha256:...`, because tags are mutable and `3.12-slim` today is not `3.12-slim` next month.
- **System packages.** `apt-get install -y libpq5=16.4-1` pins; unpinned apt installs drift. Many teams accept apt drift but rebuild from scratch regularly and scan the result.
- **Build tools.** The compiler, bundler, and their plugins are dependencies too; lock them.
- **Time and randomness.** Timestamps embedded in artifacts break bit-for-bit reproducibility; `SOURCE_DATE_EPOCH` and deterministic bundler settings fix it. For most teams, "same versions of everything" is sufficient; bit-identical outputs matter for high-assurance supply chain verification.

```dockerfile
# Pinned, reproducible Python image (excerpt)
FROM python:3.12.7-slim-bookworm@sha256:2b5d3a1b2f2b9c2d4e4e8c6d1c8b1a0f5e6d7c8b9a0f1e2d3c4b5a6f7e8d9c0b AS base
ENV PYTHONDONTWRITEBYTECODE=1 PYTHONUNBUFFERED=1 PIP_NO_CACHE_DIR=1
COPY --from=ghcr.io/astral-sh/uv:0.4.18 /uv /usr/local/bin/uv
WORKDIR /app
COPY pyproject.toml uv.lock ./
RUN uv sync --locked --no-dev --no-install-project
COPY . .
```

(The digest above is illustrative; obtain the real one with `docker pull` and `docker inspect --format '{{index .RepoDigests 0}}'`.)

## Updating dependencies

Never updating is a security problem; updating everything constantly is a stability problem. A workable policy:

| Update type | Cadence | Process |
|---|---|---|
| Security advisories affecting you | Within days (critical: hours) | Dedicated PR, targeted bump, deploy |
| Patch and minor versions | Weekly or fortnightly batch | Automated PRs (Dependabot, Renovate) grouped by ecosystem, merged on green tests |
| Major versions | Planned | Read the changelog, dedicated branch, extra testing |
| Base images and runtimes | Monthly, plus on CVE | Rebuild, run full test suite, deploy to staging first |

Automated tools open the PRs; your tests decide whether to merge. This only works if the test suite is trustworthy, which is one more reason Part XII insists on it.

## Virtual environments and isolation

Python installs packages into a shared site-packages by default, so two projects on one machine conflict. Always use an isolated environment: `uv venv`/`python -m venv .venv`, Poetry, or a container. Node isolates per project in `node_modules` by design. In Docker images each container has its own tree, which is the ultimate isolation and why "it needs Python 3.11 but the server has 3.9" stopped being a daily problem.

## Vendoring and private registries

Some teams copy dependencies into the repository (vendoring) or run a private registry proxy (Artifactory, AWS CodeArtifact, Verdaccio) that caches public packages. Benefits: builds succeed even if the public registry is down or a package is unpublished; you can allow-list packages and scan them centrally; air-gapped client environments become feasible. Cost: another system to run. For regulated clients, a proxying registry is often a requirement.

## Supply chain risks in brief

- **Typosquatting**: `reqeusts` on PyPI. Check spelling, prefer well-known packages, use a curated allow-list where possible.
- **Dependency confusion**: an internal package name also published publicly with a higher version; the resolver picks the public one. Scope internal packages (`@company/`), configure the registry to never fall back to public for those names.
- **Hijacked maintainer accounts** publishing malicious versions. Lockfiles plus a delay before adopting brand-new versions (Renovate's `minimumReleaseAge`) protect you from same-day compromises.
- **Install scripts** (`postinstall` in npm, `setup.py` execution in Python) run arbitrary code at install time. `npm ci --ignore-scripts` where feasible; prefer wheels over sdists.
- **Transitive bloat**: every dependency is attack surface. Review what a new dependency pulls in (`npm ls`, `uv tree`) before adding it for a ten-line utility.

## Common mistakes

- `pip install -r requirements.txt` with unpinned ranges in CI, so each build resolves differently.
- `npm install` in Docker instead of `npm ci`, silently rewriting the lockfile inside the image.
- Base image tag `latest` or a floating minor tag.
- Adding a dependency for trivial functionality (left-pad).
- Letting Dependabot PRs pile up for months, then upgrading 40 packages at once.
- Running build tool installs as root in the final image.

## Exercises

1. Take a project without a lockfile. Install it today, record the versions, then regenerate in a clean environment and diff. If anything differs, you have found a time bomb.
2. Pin the base image of a Dockerfile by digest. Document how you will update it monthly.
3. Run `uv tree` or `npm ls --all` on a project and count the transitive dependencies. Identify three you did not know were there.
