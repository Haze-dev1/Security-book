## The problem

Memory failures are abrupt. CPU saturation makes things slow; memory exhaustion makes things die. A container that exceeds its limit is killed with no stack trace, the orchestrator restarts it, it serves traffic for twenty minutes and dies again, and the on-call engineer sees "healthy, restarting" in a loop. Understanding memory is how you turn that from a mystery into a ten-minute fix.

## How a process uses memory

A process's address space contains:

- **Text**: the program's machine code, read-only, shared between processes running the same binary.
- **Data and BSS**: global variables.
- **Heap**: dynamically allocated objects. Grows and shrinks as the runtime allocates (`malloc`/`new`) and frees. In garbage-collected runtimes, this is where your objects live.
- **Stack**: one per thread, holding local variables and call frames. Typically 8 MB maximum per thread on Linux; a thousand threads reserve 8 GB of *virtual* space (not physical). Deep recursion overflows it.
- **Memory-mapped files and shared libraries**: `libc`, the runtime's `.so` files, and any files mapped with `mmap`. Shared across processes.

All of this is **virtual**: addresses the process uses, mapped by the kernel to physical pages on first touch. Memory the process reserved but never touched costs nothing physical. This is why VSZ (virtual size) is nearly meaningless for capacity planning and RSS (resident set size) is what matters, with the caveat that RSS double-counts shared pages across processes. PSS (proportional set size, in `/proc/<pid>/smaps_rollup`) divides shared pages fairly.

```bash
ps -o pid,rss,vsz,cmd -p $(pgrep -d, -f gunicorn)      # RSS in KB
grep -E 'Rss|Pss|Swap' /proc/<pid>/smaps_rollup
```

## Garbage collection and why memory grows after deploy

In Python, Node, Java and Go, you allocate and the runtime frees unreachable objects. Two behaviours surprise people:

1. **Runtimes keep freed memory.** Allocators request memory from the kernel in large chunks and rarely return it. A process that briefly needed 800 MB will often stay at 800 MB RSS. Growth that plateaus is normal; growth that never plateaus is a leak.
2. **Garbage collection is lazy and heuristic.** Collectors run when allocation pressure reaches a threshold, not continuously. A JVM will happily grow its heap to the configured maximum before collecting aggressively. Memory graphs with a sawtooth pattern are healthy.

A **memory leak** in a GC language means objects remain reachable when they should not: an ever-growing list used as a cache, event listeners never removed, per-request data stored on a global, closures capturing large objects, unbounded `lru_cache` without `maxsize`. The classic symptom is RSS climbing linearly with request count and resetting only on restart.

## Page cache, buffers and "available"

Linux uses free RAM to cache files. `free -h`:

```
               total        used        free      shared  buff/cache   available
Mem:            15Gi       4.2Gi       1.1Gi       120Mi        10Gi        10Gi
```

Only 4.2 GB is used by processes; 10 GB is cache that will be reclaimed instantly when needed; **available** (10 GB) is the number to alert on. Databases depend on this cache heavily: PostgreSQL's performance on a server with lots of free RAM comes largely from the kernel caching table files.

## Swap

Swap is disk used as overflow memory. On servers it is a double-edged sword: it prevents OOM kills during brief spikes, but a server that is actively swapping becomes unusably slow, and a sluggish database is often worse than a restarted one. Many cloud images ship with no swap; Kubernetes historically required swap off. For a small client VM, a modest swap file with low `vm.swappiness` (10) is a reasonable safety net; for containers, rely on limits and right-sizing instead.

## Containers and cgroup limits

A container's memory limit is a [[cgroup]] limit. When the processes in the cgroup exceed it, the kernel's [[oom killer]] kills a process inside the container; the container runtime reports exit code 137 and `OOMKilled: true`. Three things to know:

- **The cgroup counts more than your heap**: it includes every process in the container, their stacks, shared libraries (counted once per cgroup), and, in cgroup v1, file page cache attributable to the container. Headroom of 25–40% above steady-state RSS is a sensible starting point.
- **Runtimes may not see the limit.** Older JVMs sized their default heap from the *host's* memory and were killed for using it; modern JVMs (11+) are container-aware and default to 25% of the cgroup limit, which is usually too small, so set `-XX:MaxRAMPercentage=75`. Node's default heap cap (roughly 2–4 GB depending on version and architecture) may exceed a small container's limit; set `--max-old-space-size` to about 75% of the limit in megabytes. Python has no heap cap at all; your worker count is the control.
- **Requests versus limits.** Kubernetes lets you request less than you limit. Memory is not compressible: if the node runs out, pods using more than their request are the first evicted. Set memory request equal to limit for predictable services.

```bash
# Inside a container: what is my limit and usage? (cgroup v2)
cat /sys/fs/cgroup/memory.max          # bytes, or "max"
cat /sys/fs/cgroup/memory.current
cat /sys/fs/cgroup/memory.events       # oom_kill counter
# From the host / orchestrator
docker inspect <id> --format '{{.State.OOMKilled}} {{.State.ExitCode}}'
kubectl describe pod <pod> | grep -A3 'Last State'
```

## Sizing a service

A method that works:

1. Measure RSS of one worker at idle and after a sustained load test (Part XI chapter 8) at target concurrency.
2. Total memory ≈ workers × per-worker peak RSS + runtime baseline + 25–40% headroom.
3. Set the container limit to that total and the worker count to match. For Gunicorn with 4 async workers at 150 MB peak each: 600 MB + headroom ≈ 800 MB to 1 GB.
4. Alert at 80% of the limit and on any OOM kill event.
5. Re-measure after major dependency upgrades; memory profiles change.

## Common mistakes

- Raising the memory limit repeatedly instead of finding the leak.
- Running the JVM in a container without `MaxRAMPercentage`, or Node without `--max-old-space-size`.
- Alerting on "used" memory including page cache.
- Setting Kubernetes memory requests far below limits, inviting eviction of the busiest pods.
- Unbounded in-process caches and per-request data stored globally.
- Loading an entire file or query result into memory when streaming would do.

## Exercises

1. Write a small web endpoint that appends each request body to a global list. Load it for 2 minutes while watching RSS. Then bound the list and repeat.
2. Run a JVM or Node container with a 512 MB limit and no heap flags; allocate aggressively until it dies. Record the exit code. Add the appropriate heap flag and repeat.
3. Use `memray` or `tracemalloc` on any Python service you own and identify the top three allocation sites.
