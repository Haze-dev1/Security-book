# Semantic Versioning and Release Management

:::objectives
- Apply semantic versioning correctly to libraries, services and APIs, and know when it does not apply.
- Produce releases with changelogs, tags and artifacts that can be traced from a running system back to source.
- Design a deprecation policy for APIs consumed by clients.
- Coordinate releases of interdependent components without breaking consumers.
:::

:::prereq
Chapters 9 and 10.
:::

## The problem

Version numbers are a communication protocol between producers and consumers of software. If `2.3.1` to `2.4.0` might break my integration, I must read every changelog and test every upgrade; if the convention guarantees it will not, I can upgrade with confidence. Release management is the discipline that makes the guarantee true, and that lets anyone answer "what exactly is running, and what changed since last week?"

## Semantic versioning

`MAJOR.MINOR.PATCH`, with optional pre-release (`2.0.0-rc.1`) and build metadata (`+build.42`):

- **PATCH**: backward-compatible bug fixes. Consumers upgrade freely.
- **MINOR**: backward-compatible new functionality. Consumers upgrade freely; may adopt new features.
- **MAJOR**: incompatible changes. Consumers must read the migration guide and change code.

`0.y.z` means "anything may change". Many projects stay there far too long; once anyone depends on you in production, release 1.0 and honour the contract.

What counts as breaking? For a library: removing or renaming a public function, changing a signature or return type, tightening accepted inputs, changing default behaviour, raising the minimum runtime version. For an HTTP API: removing a field or endpoint, renaming a field, changing a type, making an optional parameter required, changing error codes clients depend on, changing authentication. **Adding** fields, endpoints, optional parameters and enum values is usually compatible if consumers were told to ignore unknown fields and handle unknown enum values; say so in your API documentation.

## Versioning services versus libraries

A deployed service has one version running at a time (or two, during rollout), chosen by you. Its consumers do not pick a version; they get whatever is deployed. So the service's **build version** (often just the Git SHA or a date-based tag like `2026.03.14.1`) is for traceability, while its **API version** (`/v1/`, `/v2/`) is the contract consumers depend on. Part III chapter 2 covers API versioning in depth. Do not confuse the two: bumping the build version on every deploy is right; bumping the API version on every deploy is a disaster.

Libraries, SDKs, CLI tools, Terraform modules, Helm charts and container base images that others consume follow semantic versioning strictly.

## Release artifacts and traceability

A release ties together: a Git tag, a changelog entry, built artifacts (container image, wheel, zip) with immutable identifiers, and a record of where and when it was deployed. Make the chain visible:

```bash
# Tag and build
git tag -a v2.4.0 -m "Release 2.4.0"
git push origin v2.4.0
docker build -t registry/app:2.4.0 -t registry/app:sha-$(git rev-parse --short HEAD) \
  --label org.opencontainers.image.revision=$(git rev-parse HEAD) \
  --label org.opencontainers.image.version=2.4.0 .
```

```python
# /version endpoint: a production system should be able to say what it is
@app.get("/version")
def version():
    return {"version": settings.app_version, "commit": settings.git_sha, "built_at": settings.build_time}
```

The labels and the endpoint are populated at build time from the pipeline. During an incident, "which version is running?" should be answerable with one `curl`, not by asking around.

## Changelogs and release notes

Keep `CHANGELOG.md` in the "Keep a Changelog" format: sections per version with Added, Changed, Deprecated, Removed, Fixed, Security. Write for the consumer: what they will notice and what they must do. Automation (Conventional Commits with tools like `release-please` or `semantic-release`) can derive versions and changelog entries from commit messages like `feat:`, `fix:`, `feat!:`, which also forces thought about compatibility at commit time.

Release notes for clients are a different document: fewer internals, more "what this means for you", written by a human.

## Deprecation policy

When a client integrates against your API, removing anything becomes a negotiation. Publish a policy up front:

1. Mark deprecated elements in documentation and responses (`Deprecation` and `Sunset` HTTP headers; `@deprecated` in SDKs).
2. Announce with a date and a migration path; log usage of deprecated features so you know who is still calling them.
3. Maintain the deprecated behaviour for a stated period (commonly 6–12 months for external APIs; shorter for internal ones).
4. Remove in a major version, after confirming usage is zero or stakeholders have signed off.

## Coordinating releases across components

Frontend, backend and database rarely change in lockstep. Rules that keep rollouts safe:

- **Backend before frontend**: the API must accept the new requests before any client sends them, and keep accepting old ones until all clients have moved.
- **Expand, then contract** for databases: add columns and tables first (compatible with old code), deploy code that uses them, then remove old columns in a later release (Part X chapter 8).
- **Tolerant readers**: consumers ignore unknown fields; producers never remove fields without the deprecation process.
- **Feature flags** decouple deploy from release: ship the code dark, enable when all parts are in place.

## Release cadence

Frequent small releases are safer than rare large ones: each carries less change, is easier to review, and if it fails, the suspect set is small. Teams deploying many times a day have lower change-failure rates than teams deploying monthly, not despite the frequency but because of what frequency forces: automation, small batches, good rollback. For clients who require scheduled releases, keep the internal cadence high (staging continuously) and batch only the production promotion.

## Rollback and roll-forward

Every release needs an answer to "how do we undo this?" Rolling back the application means deploying the previous artifact, which must still exist and still be compatible with the current database schema (this is why migrations are expand-first). Rolling forward means fixing quickly and releasing a new version; sensible when the fix is obvious and rollback is risky. Decide which applies *before* deploying, and write it in the deployment ticket.

## Common mistakes

- Breaking changes in minor versions, training consumers to distrust your versions.
- Mutable tags (`latest`, or re-tagging `v1.2.0` to a new commit).
- Services with no `/version` endpoint, so incidents begin with archaeology.
- Removing API fields without a deprecation window because "nobody uses it" (someone does).
- Frontend released before backend; users see errors for the duration of the gap.
- Huge quarterly releases with dozens of changes and no idea which one broke things.
