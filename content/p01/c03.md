## The problem the operating system solves

A computer has a handful of CPUs, some memory, disks and network cards. Dozens or thousands of programs want to use them at the same time, written by people who do not trust each other, with bugs that would otherwise take the machine down. The operating system is the arbitration layer: it gives each program the illusion of its own machine, shares the real hardware fairly, enforces boundaries between programs, and offers a stable interface so programs do not need to know which brand of network card is installed.

Every server-side problem that is not a logic bug in your code is, in some way, an operating system problem: the disk is full, the process ran out of file descriptors, the kernel killed something for memory, the TCP backlog overflowed, the clock drifted, a permission was denied. Learning the OS is learning to read those symptoms.

## Kernel space and user space

The **kernel** is the privileged core that talks to hardware. Your programs run in **user space** with restricted privileges. A user-space program cannot touch hardware, other processes' memory or the kernel's memory directly. When it needs something, it makes a [[system call]]: a controlled transition into the kernel to request a service such as "open this file", "send these bytes on this socket" or "give me more memory".

## The scheduler

A server with 4 cores and 300 runnable threads needs to decide who runs. The scheduler gives each runnable thread a short time slice (milliseconds), switches between them (a **context switch**), and prioritises according to niceness and scheduling class. Threads waiting for I/O are not runnable and cost nothing until data arrives.

What this means for you:

- **Load average** (shown by `uptime`, `top`) is the average number of threads that are running or waiting to run (and on Linux, also those in uninterruptible disk wait) over 1, 5 and 15 minutes. A load of 4 on a 4-core machine means the CPUs are fully busy; a load of 12 means threads are queueing three deep. Load above core count with low CPU utilisation points at I/O wait, not CPU.
- **Context switches** are not free. Thousands of threads thrashing between each other spend their time in the scheduler rather than working. This is why event loops and goroutines exist: many logical tasks on few OS threads.
- **CPU steal** (`st` in `top`) on a virtual machine is time the hypervisor gave to someone else. Burstable instances (AWS `t3`) show this when credits run out.

```bash
# Snapshot of CPU, run queue (r), blocked (b), context switches (cs), wait (wa), steal (st)
vmstat 1 5
# procs -----------memory---------- ---swap-- -----io---- -system-- ------cpu-----
#  r  b   swpd   free   buff  cache   si   so    bi    bo   in   cs us sy id wa st
#  9  0      0 412340 102400 3981200    0    0     0    48 2311 9876 71 12 15  2  0
```

Reading that line: 9 runnable threads on (say) 4 cores, 71% user CPU, 12% system (kernel) CPU, 15% idle, 2% waiting on I/O. This server is CPU-bound in user code: profile the application.

## Virtual memory

Each process sees a private, contiguous address space; the kernel maps pages of that space onto physical RAM (or disk, if swapping) on demand. Two consequences you will meet in production:

1. **Memory numbers are confusing.** "Virtual size" (VSZ) is address space reserved; "resident set size" (RSS) is physical memory actually in use; shared libraries are counted in several processes at once. Container memory limits apply to the cgroup's accounting, which includes page cache in some configurations. Chapter 7 untangles this.
2. **The page cache.** Linux uses free RAM to cache file contents. A server showing 95% memory "used" with most of it as cache is healthy; the cache is given back instantly when a process needs it. `free -h` shows this as `buff/cache` and `available`. Alerting on "used memory" without excluding cache causes false alarms.

When memory truly runs out, the kernel invokes the [[oom killer]], picking a process (usually the largest) and killing it. In a container, the whole container is killed with exit code 137.

## The filesystem layer

Programs see files and directories; the Virtual File System (VFS) layer hides whether they are on an ext4 partition, an NFS share, a tmpfs in memory, or a FUSE mount. Important behaviours:

- **Everything is a file descriptor.** Open files, sockets, pipes and devices all consume entries in a per-process table with a limit (`ulimit -n`, commonly 1024 by default). A service that opens many connections or files without closing them hits "Too many open files" and starts failing in bizarre ways. Production services raise the limit (systemd `LimitNOFILE=65536`) and, more importantly, fix the leak.
- **Writes are buffered.** `write()` returns when the kernel has the data, not when it is on disk. Durability requires `fsync()`, which databases call religiously and which is why database disk latency matters so much.
- **Deleting an open file does not free space.** The directory entry disappears but the blocks remain until the last process closes it. Classic incident: disk 100% full, `du` finds nothing, because a rotated log file is still held open by a process. `lsof +L1` finds the culprit.
- **Permissions** are enforced here (chapter 5).

## The network stack

The kernel implements TCP, UDP and IP. Your program hands bytes to a socket; the kernel does segmentation, retransmission, congestion control and routing. Buffers sit between them: a send buffer per socket, a receive buffer per socket, and a **listen backlog** of connections that completed the handshake but have not yet been `accept()`ed by your program.

The backlog matters for web servers: if your process is too slow to accept connections, the backlog fills, and new connections are dropped or get a reset. Nginx and Gunicorn set it explicitly, bounded by the kernel's `net.core.somaxconn`. Part II goes deep on all of this; for now, know that "connection refused" and "connection timed out" are OS-level messages with specific meanings.

## Time

Servers keep time with a system clock disciplined by NTP (chrony or systemd-timesyncd). Drift of even a minute breaks TLS certificate validation at the margins, AWS API request signing (which rejects requests more than 5 minutes off), JWT expiry checks, and log correlation across machines. Containers share the host clock. Always run time synchronisation; on EC2 use the Amazon Time Sync Service at `169.254.169.123`.

Related: store and transmit timestamps in UTC; convert to local time only for display. Timezone bugs are a steady source of incidents that appear exactly twice a year.

## Users, privileges and isolation

The kernel enforces that a process running as user `app` cannot read files owned by `root` with mode 600, cannot bind ports below 1024 without a capability, cannot send signals to other users' processes, and cannot load kernel modules. Running services as root throws this protection away: a vulnerability in the application becomes a compromise of the machine. Chapter 5 and Part V cover users and permissions; Part VI covers the namespaces and cgroups that containers add on top.

## Real-world context

A typical investigation of "the API is slow" on a Linux host goes through the OS layers in order:

1. `uptime` and `top`: is the CPU saturated? Load vs cores? Steal?
2. `free -h` and `dmesg | grep -i oom`: memory pressure? OOM kills?
3. `df -h` and `df -i`: disk or inodes full?
4. `iostat -x 1`: disk latency (`await`) and utilisation?
5. `ss -s` and `ss -ltnp`: socket counts, listening ports, backlog overflow?
6. `journalctl -u myapp -n 200`: what did the service itself say?

Only then open the profiler. Part V chapter 13 expands this into a full method.

## Common mistakes

- Alerting on memory "used" including page cache, or on load average without reference to core count.
- Running services as root for convenience.
- Ignoring `ulimit -n` until the service hits "Too many open files" at peak traffic.
- Not running NTP in a custom AMI, then failing to call AWS APIs with "signature expired".
- Writing files into a container's filesystem (which is ephemeral and often small) instead of a volume or object storage.

## Exercises

1. On any Linux machine or container, run `strace -c python3 -c "print('hi')"` and look at how many system calls a trivial program makes. Then try `strace -e trace=openat` to see which files it opens at start-up.
2. Create a file, open it with `tail -f`, delete it from another terminal, and observe with `df` and `lsof +L1` that the space is still consumed. Close `tail` and watch it return.
3. Lower your shell's file descriptor limit with `ulimit -n 20` and start a small web server. Hit it with 50 concurrent connections. Record the exact error message so you recognise it in production.
