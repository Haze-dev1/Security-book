# Linux Essentials for Backend Engineers

:::objectives
- Navigate a Linux server confidently: filesystem layout, shell, pipes, redirection, text processing.
- Use the commands operators reach for daily to inspect processes, disk, memory, network and logs.
- Edit files safely on a server, transfer files, and run things in the background without losing them.
- Build the habits that keep you from destroying a production machine with one keystroke.
:::

:::prereq
Chapter 3. Access to any Linux shell: a VM, WSL, a Docker container (`docker run -it --rm ubuntu:24.04 bash`) or a cloud instance.
:::

## Why Linux

Essentially every server you will deploy to runs Linux: EC2 instances, ECS tasks, Kubernetes nodes, Lambda's execution environment, managed databases underneath their APIs. The shell is how you inspect them when dashboards are not enough. Comfort with Linux is the difference between diagnosing an incident in five minutes and guessing for an hour.

## The filesystem layout

Linux has a single tree rooted at `/`. Knowing where things live tells you where to look.

| Path | What lives there | Why you care |
|---|---|---|
| `/etc` | System and service configuration | `nginx/`, `ssh/sshd_config`, `systemd/system/`, `hosts`, `resolv.conf` |
| `/var/log` | Log files | Where logs go when not in journald; disk fills up here |
| `/var/lib` | Service state and data | PostgreSQL data, Docker images, apt state |
| `/opt`, `/srv` | Optional / served software | Common homes for your application code |
| `/home/<user>` | User home directories | `~/.ssh/authorized_keys` controls who can log in |
| `/tmp`, `/var/tmp` | Temporary files | Often cleared at boot; may be a small tmpfs in memory |
| `/proc`, `/sys` | Kernel and process info as files | `/proc/<pid>/`, `/proc/meminfo`, cgroup limits |
| `/dev` | Devices | `/dev/null`, `/dev/urandom`, disks like `/dev/nvme0n1` |
| `/usr/bin`, `/usr/local/bin` | Executables | Where `which python3` points |
| `/run` | Runtime state (sockets, PID files) | `/run/docker.sock`, `/run/postgresql/` |

## The shell: pipes, redirection and composition

The Unix philosophy is small tools composed with pipes. `|` sends one command's standard output into the next's standard input; `>` writes output to a file (`>>` appends); `2>` redirects standard error; `2>&1` merges errors into output.

```bash
# Count 5xx responses per endpoint from an access log, top 10
grep ' 5[0-9][0-9] ' /var/log/nginx/access.log \
  | awk '{print $7}' \
  | sort | uniq -c | sort -rn | head -10

# Save both stdout and stderr of a deploy script, and still see it live
./deploy.sh 2>&1 | tee deploy-$(date +%F-%H%M).log

# Discard noise
some_command > /dev/null 2>&1
```

Essential text tools, in the order you will reach for them: `grep` (search; `-r` recursive, `-i` case-insensitive, `-n` line numbers, `-E` extended regex, `-v` invert), `awk` (column extraction and arithmetic), `sed` (stream editing; `sed -i` edits in place, dangerous on config files without a backup), `cut`, `sort`, `uniq -c`, `wc -l`, `head`, `tail -f` (follow a growing log), `less` (page through; `/` searches, `F` follows like tail), `jq` (JSON), `xargs` (turn lines into arguments), `find` (locate files by name, age, size).

```bash
# Files larger than 500 MB, anywhere, for the "disk full" incident
sudo find / -xdev -type f -size +500M -exec ls -lh {} \; 2>/dev/null

# Remove logs older than 14 days (list first, then delete!)
find /var/log/myapp -name '*.log' -mtime +14 -print
find /var/log/myapp -name '*.log' -mtime +14 -delete

# Pretty-print and filter JSON logs
tail -n 1000 app.log | jq -c 'select(.level=="error") | {ts, msg, request_id}'
```

## Processes

```bash
ps aux                      # every process: user, PID, CPU, MEM, command
ps -ef --forest             # parent/child tree
pgrep -a gunicorn           # PIDs and command lines matching a name
top                         # live view; press 1 for per-core, M to sort by memory, k to kill
htop                        # friendlier top (install it)
kill -TERM <pid>            # ask politely (SIGTERM, the default)
kill -KILL <pid>            # force (SIGKILL); the process cannot clean up
pkill -f 'celery worker'    # signal by pattern; dangerous if the pattern is broad
nice -n 10 ./batch.sh       # lower priority for background work
```

Chapter 6 explains what signals mean to a running service. The rule for now: `kill -9` is a last resort; it skips graceful shutdown and can leave corrupted state or orphaned locks.

## Disk and memory

```bash
df -h                       # filesystem usage; look for 100%
df -i                       # inode usage; "no space left" with free space means inodes
du -sh /var/* 2>/dev/null | sort -rh | head   # what is using the space
free -h                     # memory; trust the "available" column
lsblk                       # block devices and mount points
mount | column -t           # what is mounted where, with options
```

## Networking (preview of Part II)

```bash
ip addr                     # interfaces and IPs (replaces ifconfig)
ip route                    # routing table; "default via" is your gateway
ss -ltnp                    # listening TCP ports and the owning process
ss -tn state established | wc -l   # how many open connections
curl -sS -o /dev/null -w '%{http_code} %{time_total}s\n' http://localhost:8000/health
dig +short api.example.com  # DNS answer
```

## Services and logs (preview of Part V)

```bash
systemctl status nginx      # is it running? recent log lines
sudo systemctl restart myapp
journalctl -u myapp -f      # follow a service's logs
journalctl -u myapp --since "1 hour ago" -p err   # errors in the last hour
sudo tail -f /var/log/nginx/error.log
```

## Users, sudo and permissions (preview of chapter 5)

```bash
whoami; id                  # who am I and which groups
sudo -i                     # root shell; use sparingly
sudo -u app ./manage.py migrate   # run one command as the service user
ls -la                      # permissions, owner, group
chmod 600 ~/.ssh/id_ed25519 # fix the single most common SSH permission error
chown -R app:app /srv/app   # hand a tree to the service user
```

## Editing files on a server

Use `nano` if you are not a vi user; `vim` if you are. Before editing a configuration file in production:

```bash
sudo cp /etc/nginx/nginx.conf /etc/nginx/nginx.conf.bak-$(date +%F)
sudo nano /etc/nginx/nginx.conf
sudo nginx -t              # validate before reload
sudo systemctl reload nginx
```

Better still: do not hand-edit production servers. Change the configuration in version control and let a deployment or configuration management tool apply it. Hand edits are how servers drift into unique, undocumented snowflakes.

## Moving files

```bash
scp ./build.tar.gz app@server:/srv/app/releases/      # copy over SSH
rsync -avz --delete ./dist/ app@server:/srv/app/dist/  # sync efficiently, mirror deletions
ssh app@server 'tar -czf - /srv/app/data' > backup.tgz # stream a tarball back
```

For cloud deployments you rarely copy files by hand; artifacts are container images pulled from a registry or packages fetched from S3. But `scp` and `rsync` remain useful for forensics and recovery.

## Long-running commands and sessions

A command started in an SSH session dies when the session drops. For anything that takes more than a minute:

```bash
tmux new -s deploy           # start a named session; Ctrl-b d detaches
tmux attach -t deploy        # reattach later
nohup ./long-job.sh > job.log 2>&1 &    # alternative without tmux
```

## Environment and shell configuration

`env` shows your environment variables; `export VAR=value` sets one for the current shell and its children. `~/.bashrc` and `~/.profile` run at login; service users typically have minimal ones. Chapter 8 covers configuration via environment in depth.

`$PATH` decides which `python3` runs. On a server with several Python versions, `which -a python3` and `python3 -c 'import sys; print(sys.executable)'` settle arguments.

## Package management

```bash
# Debian/Ubuntu
sudo apt update && sudo apt install -y nginx
apt list --upgradable
# RHEL/Amazon Linux/Fedora
sudo dnf install -y nginx
# Alpine (container images)
apk add --no-cache curl
```

Production servers install the minimum. Every package is attack surface and patch burden.

## Habits that prevent disasters

:::danger Commands that have destroyed production
- A recursive, forced remove of `"$DIR/"` when `$DIR` is unset expands to removing the root filesystem. Use `set -u` in scripts and the `${DIR:?}` form, which aborts if the variable is empty, so an unset variable can never widen the target.
- `chmod -R 777 .` to "fix a permission issue". It makes every file world-writable. Chapter 5 explains the right fix.
- `sed -i` on a config file without a backup, with a typo in the pattern.
- `kill -9 -1` kills every process you own. On a shared account, that is everything.
- Running a `DELETE` or `UPDATE` without `WHERE` in a database shell. Always `BEGIN;` first, check the row count, then `COMMIT;` or `ROLLBACK;`.
- Pasting a multi-line command into a terminal where the first line executes before you finish reading. Paste into an editor first.
:::

Positive habits:

1. **Look before you act.** `ls` before removing, `-print` before `-delete`, `--dry-run` when offered, `nginx -t` before reload.
2. **Prefer reversible operations.** Move instead of delete; copy before edit; snapshot before upgrade.
3. **Use a distinctive prompt or terminal colour for production.** Many incidents begin with "I thought I was on staging."
4. **Type the hostname into your commands when it matters:** `ssh prod-db-1` not `ssh !!`.
5. **Record what you did.** Shell history is not enough; write the commands into the incident channel as you run them.

1. In a throwaway container, generate a fake access log with `for i in $(seq 1 10000); do echo "$RANDOM GET /api/items/$((RANDOM%50)) $((RANDOM%2 ? 200 : 500))"; done > access.log` and write a one-line pipeline that lists the five endpoints with the most 500s.
