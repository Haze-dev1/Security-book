# Software Development Lifecycle and Engineering Documentation

:::objectives
- Describe how work flows from idea to operation in a professional engineering team and where quality is enforced at each stage.
- Choose the right lifecycle for a client project and explain the tradeoffs.
- Produce the small set of documents that keep a system understandable: README, architecture overview, runbooks, ADRs, API docs, changelog.
- Recognise documentation anti-patterns and keep docs alive.
:::

:::prereq
Chapters 10 and 11.
:::

## The problem

Code is a small fraction of software delivery. Deciding what to build, agreeing how it should behave, verifying it, deploying it, operating it and changing it safely over years all require process and shared understanding. Without them, teams ship the wrong thing, ship it broken, or ship it right and then lose the knowledge of how it works when the one person who knew leaves.

For a Forward Deployed Engineer the stakes are higher: the client will operate what you build, often with less context than you. Your process and your documents *are* part of the deliverable.

### Methodologies in practice

- **Agile / Scrum** (sprints of 1–2 weeks, backlog, reviews, retrospectives): good default when requirements evolve; gives clients a predictable demo cadence.
- **Kanban** (continuous flow, limits on work in progress): suits operations-heavy or support-heavy work.
- **Waterfall-ish phases** (fixed scope, formal sign-offs): still real in regulated or procurement-driven clients. Combine with iterative delivery inside each phase.
- **Shape Up, dual-track, and others**: variations on the same theme. Pick the ceremony level the client can sustain; more process than the team will follow is worse than less.

Regardless of label, the controls in the flow above are what matter: agreed requirements, reviewed design, reviewed and tested code, validated release, monitored operation, feedback loop.

## Definition of done

Agree, in writing, what "done" means for a ticket. A strong definition for production software:

```checklist
# Definition of done for a user-facing change
- Acceptance criteria met and demonstrated.
- Code reviewed and merged to main via pull request.
- Unit and integration tests added or updated; CI green.
- Security considerations noted in the PR (input validation, authorization, secrets).
- Database migrations are backward compatible and rehearsed in staging.
- Logging and metrics added for new behaviour; alerts updated if a new failure mode exists.
- Documentation updated: README, API docs, runbook, ADR if a decision was made.
- Feature flag or rollout plan defined for risky changes.
- Deployed to staging and smoke-tested.
- Release notes line written.
```

## Engineering documentation: the minimum set

Documentation fails when there is too much of it (nobody reads or maintains it) or when it lives in someone's head. The minimum set for a production system:

| Document | Answers | Lives in | Updated when |
|---|---|---|---|
| **README** | What is this, how do I run it locally, how do I test it, where is everything else | Repository root | Any onboarding friction |
| **Architecture overview** | Components, data flow, trust boundaries, hosting; one diagram plus two pages | `docs/architecture.md` | Structural change |
| **ADRs** | Why we chose X over Y | `docs/adr/NNNN-title.md` | Every significant decision |
| **API documentation** | Endpoints, schemas, auth, errors | Generated from OpenAPI | Every API change (automatically) |
| **Runbooks** | How to deploy, roll back, rotate a secret, restore a backup, handle each alert | `docs/runbooks/` | Every incident and every procedure change |
| **Configuration reference** | Every variable, its meaning, where it is set | `docs/configuration.md` or settings module docstrings | Every new setting |
| **Changelog / release notes** | What changed per version | `CHANGELOG.md`, release pages | Every release |
| **On-call and escalation** | Who to call, severity definitions | Shared wiki, linked from README | Team changes |

Part XV provides templates for several of these.

### Writing a README that works

```markdown
# Orders Service

Handles order creation, payment capture and fulfilment events for Client X.
Owner: Platform team (#orders-service). On-call: see docs/oncall.md.

## Run locally
    cp .env.example .env
    docker compose up -d db redis
    uv sync && uv run alembic upgrade head && uv run uvicorn app.main:app --reload
Open http://localhost:8000/docs

## Test
    uv run pytest            # unit + integration (uses docker compose db)
    uv run ruff check .      # lint

## Deploy
Merges to main deploy to staging automatically. Production: approve the
"production" job in GitHub Actions. Rollback: docs/runbooks/rollback.md.

## Architecture
See docs/architecture.md. Decisions: docs/adr/.
```

Short, concrete, commands that work. If the commands stop working, that is a bug.

### Diagrams

One good diagram beats five pages. Use the C4 model's first two levels: a **context** diagram (the system, its users, and external systems) and a **container** diagram (deployable units and data stores and how they communicate). Keep diagrams as text where possible (Mermaid, Structurizr, PlantUML) so they live in Git and get reviewed with the code they describe.

## Keeping documentation alive

- **Docs change in the same PR as the code.** Reviewers check for it. A "docs later" ticket is a doc that will never exist.
- **Test what can be tested**: README commands in CI, OpenAPI generated from code, runbooks exercised in game days.
- **Date and own everything.** A doc with a "last verified" date and an owner is trustworthy; an undated wiki page is a rumour.
- **Delete aggressively.** Wrong documentation is worse than none. If nobody can vouch for a page, archive it.
- **Write for the reader at 3 a.m.**: the on-call engineer who has never seen this service. Commands to copy, not prose to interpret.

## Common mistakes

- Skipping discovery and designing around assumptions; discovering the real requirement at acceptance.
- Design documents written after the code to justify it.
- "Definition of done" that stops at "merged".
- A 60-page architecture document nobody updates, and no README that runs.
- Runbooks written once and never tested; the restore procedure references a tool that was removed a year ago.
- Documentation in a tool the client cannot access after the engagement.

## Exercises

1. Write or rewrite the README of a project you own so that a new engineer can run and test it in under ten minutes using only the README. Have someone try.
2. Draft a definition of done with your team or for yourself; apply it to the last three things you shipped. What was missing?
3. Produce a C4 context and container diagram in Mermaid for your current project and commit it.
