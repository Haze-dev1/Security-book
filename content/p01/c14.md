# Monoliths, Modular Monoliths and Microservices

:::objectives
- Define the three architectural styles precisely and describe the operational cost of each.
- Recognise when microservices solve a real problem and when they create one.
- Design a modular monolith that can be split later without a rewrite.
- Advise a client honestly on which style fits their team and constraints.
:::

:::prereq
Chapters 1 and 11.
:::

## The problem

How you divide a system into deployable units determines how you build, test, deploy, scale, secure and debug it for years. The industry oscillated from monoliths to microservices and partly back, leaving many teams with distributed systems they did not need and cannot operate. Architecture should follow the problem and the team, not the conference circuit.

## The three styles

### Monolith

One codebase, one deployable, one process (or identical replicas of it), typically one database. Internal calls are function calls. A FastAPI application with routers for users, orders and billing, deployed as one container, is a monolith.

Strengths: simplest to develop, test, deploy and debug; transactions across features are trivial; refactoring across boundaries is an IDE operation; one set of infrastructure to secure and monitor.

Weaknesses: everything scales together (the PDF generator and the login endpoint share CPU); one bad deploy affects everything; large teams step on each other; the codebase can degrade into a tangle if modules are not enforced; a single runtime and language.

### Modular monolith

Still one deployable, but internally divided into modules with explicit boundaries: each module owns its tables, exposes a small interface, and is forbidden (by convention and by tooling) from reaching into another module's internals. Communication between modules goes through those interfaces, sometimes through in-process events.

This captures most of the organisational benefits claimed for microservices (clear ownership, independent evolution, enforced contracts) with none of the distributed-systems cost. It is also the best preparation for extracting a service later, because the seams already exist.

### Microservices

Many independently deployable services, each owning its data, communicating over the network (HTTP, gRPC, messages). Each can use its own language, scale independently and be deployed by its own team on its own schedule.

What you pay for that: every call across a boundary can fail, time out or be slow; data consistency across services needs sagas or eventual consistency instead of a transaction; debugging requires distributed tracing; each service needs its own pipeline, monitoring, secrets, scaling policy and on-call ownership; local development needs a way to run or mock a dozen services; versioning of inter-service contracts becomes a permanent concern; and the network itself must be secured service-to-service. Netflix-scale organisations absorb this with platform teams. A five-person team cannot.

## When microservices are justified

Real reasons, in rough order of frequency:

1. **Organisational scale**: many teams need to deploy independently without coordinating releases. Below roughly 30–50 engineers this rarely applies.
2. **Radically different scaling or runtime needs**: a GPU inference component, a high-throughput ingestion path, a legacy system in another language.
3. **Isolation requirements**: a component handling card data (PCI scope) or a tenant that requires physical separation.
4. **Independent failure domains** where part of the product must stay up when another part is down, *and* the team can build the resilience patterns that make that true.

Not reasons: "it is modern", "we might need to scale", "the CTO read about it", "the monolith is messy" (a messy monolith becomes a messy distributed system, which is strictly worse).

## Designing a modular monolith

```
app/
  modules/
    users/        api.py (public interface) · models.py · service.py · repository.py · events.py
    orders/       api.py · models.py · service.py · repository.py
    billing/      api.py · ...
  shared/         auth, db session, event bus, config
  main.py         mounts each module's router
```

Rules enforced by tooling (import-linter for Python, ESLint `no-restricted-imports` or Nx module boundaries for TypeScript, ArchUnit for Java):

- `orders` may import `users.api` but never `users.models` or `users.repository`.
- Each module owns its tables; migrations live with the module.
- Cross-module reads go through the interface; cross-module writes happen via events or explicit service calls, never by touching another module's tables.
- Shared code is small and stable; anything with business meaning belongs to a module.

With these in place, extracting `billing` into its own service later means replacing the in-process interface with an HTTP or message client, a task of days rather than months.

## Operating cost comparison

| Concern | Monolith | Modular monolith | Microservices |
|---|---|---|---|
| Pipelines to maintain | 1 | 1 | N |
| Deploy coordination | none | none | contract versioning, ordering |
| Transactions | native | native | sagas, outbox, idempotency |
| Debugging a request | stack trace | stack trace | distributed tracing across N services |
| Local development | `docker compose up` | same | N services or elaborate mocks |
| Security surface | one perimeter | one perimeter | service-to-service auth, N perimeters |
| Infrastructure cost | lowest | lowest | higher baseline (per-service minimum footprint) |
| Team size sweet spot | 1–15 | 1–40 | 40+ with a platform team |

## Advice for client projects

:::fde
Most client systems should start as a modular monolith deployed as a container behind a load balancer with a managed database, plus a separate worker process for background jobs (which is still the same codebase and image, just a different command). That design is cheap, secure, observable and can be operated by a small client team. Introduce a separate service only when you can name the specific problem it solves and the client's team can operate it. Write that reasoning down as an ADR so that the decision can be revisited when the facts change.
:::

If a client already runs microservices, your job is different: respect their contracts, use their platform tooling, and resist adding services for your feature unless their architecture calls for it.

## Common mistakes

- Starting a greenfield project with ten services and a Kubernetes cluster for two developers.
- Microservices sharing one database, combining the coupling of a monolith with the failure modes of a distributed system.
- Chatty synchronous call chains (A calls B calls C calls D) where one slow service degrades everything.
- No module boundaries in a monolith, so every change touches everything and extraction becomes impossible.
- Rewriting a monolith into services instead of strangling it incrementally (the strangler fig pattern: route new functionality to new services, migrate old functionality piece by piece behind a facade).

## Exercises

1. Map the modules of an application you work on. For each pair, list every place one reaches into another's internals (direct table access, imported private functions). Estimate the effort to enforce boundaries.
2. Add an import-boundary linter to a project and make it fail on an existing violation. Fix the violation through a proper interface.
3. Write an ADR (Part XV chapter 5 has the template) recommending an architecture style for a hypothetical client with a four-person engineering team and a compliance requirement to isolate payment processing.
