# What Production-Ready Actually Means

:::objectives
- State a rigorous definition of production readiness and derive concrete criteria from it.
- Assess a system against those criteria and prioritise gaps by risk.
- Run a lightweight production readiness review for a client deployment.
- Connect each criterion to the part of this book that teaches it.
:::

:::prereq
All previous chapters of Part I.
:::

## The definition

A system is **production-ready** when it can be operated by people other than its authors, under real load and hostile input, with its failures detected, contained and recovered within agreed limits, without exposing data it should not, at a cost its owners accept.

Every clause is load-bearing:

- *operated by people other than its authors*: documented, automated, ownership assigned.
- *real load*: capacity known, tested, scalable.
- *hostile input*: validated, authenticated, authorised, hardened.
- *failures detected*: observability and alerting.
- *contained*: isolation, limits, graceful degradation.
- *recovered within agreed limits*: backups, rollback, DR, SLOs.
- *without exposing data*: confidentiality controls, privacy obligations.
- *at a cost its owners accept*: budgeted, monitored, right-sized.

"The feature works" is necessary and nowhere near sufficient.

## The checklist

This is the full version of the checklist from chapter 1, organised by the stack above. Each item links to where it is taught. Use it as a review instrument, not a form to tick blindly: for every item, the reviewer should ask "show me."

```checklist
# Production readiness review
## Correctness
- Acceptance criteria written and demonstrated for each feature.
- Automated tests cover critical paths; CI is green and trusted.
- Input validation on every external boundary; schemas enforced.
- Concurrency and idempotency considered for writes and retries.
## Infrastructure
- All infrastructure defined as code; no console-only resources.
- Databases and internal services in private subnets; only the load balancer is public.
- Managed services preferred; any self-managed host has a patching plan.
- Resources tagged; budget and cost alerts configured.
## Delivery
- Pull requests with review and required checks; main is protected.
- Immutable artifact (image digest or version) promoted across environments.
- Deployment is automated and takes one action; rollback is documented and rehearsed.
- Database migrations are backward compatible and run before/after code as designed.
- Staging matches production in shape; smoke tests run after each deploy.
## Reliability
- Health checks reflect real readiness (dependencies checked where appropriate).
- Graceful shutdown implemented and verified under a rolling deploy.
- Timeouts, retries with backoff, and circuit breakers on all outbound calls.
- Resource limits set; no single point of failure for the agreed availability target.
- Load tested at expected peak with headroom; capacity plan documented.
## Security
- Threat model exists; trust boundaries documented.
- Authentication and resource-level authorization on every endpoint.
- Secrets in a secrets manager; none in code, images, logs or tickets.
- TLS on all public and internal traffic; security headers set.
- IAM least privilege for humans and workloads; no long-lived access keys.
- Dependencies locked and scanned; images scanned; base images current.
- Audit logging for security-relevant actions; logs free of PII and secrets.
- Data classified; retention and deletion defined; privacy obligations mapped.
## Observability
- Structured logs with request/correlation IDs shipped centrally.
- Metrics for rate, errors, duration and saturation per service; dashboards exist.
- Distributed tracing or at least correlated logs across services.
- Alerts are symptom-based, actionable, routed to a human, and each has a runbook.
## Recoverability
- Automated backups with retention; restore tested recently with timing recorded.
- RPO and RTO agreed with the client and achievable by the design.
- Disaster recovery plan documented; infrastructure can be recreated from code.
## Ownership
- Named service owner and on-call arrangement, including the client's role after handover.
- Runbooks for deploy, rollback, secret rotation, restore, and each alert.
- Architecture overview and ADRs current; README runs from a clean clone.
- Handover completed and acknowledged (Part XV chapter 6).
```

## Prioritising gaps

No real system passes every item on day one. Prioritise by **risk = likelihood × impact**, then by **cost to fix**:

1. **Fix before launch**: anything that can leak client data or lose it irrecoverably (public database, no backups, secrets in Git, missing authorization checks), and anything that prevents you from *knowing* about failures (no alerting at all).
2. **Fix within the first weeks**: rollback automation, load test, runbooks for the two or three most likely incidents, cost alerts.
3. **Schedule**: tracing, chaos testing, DR drills, advanced security tooling.

Write the gaps and the plan down. A readiness review that produces a list of accepted risks with owners and dates is a success; one that produces a "pass" with hidden gaps is a failure deferred.

## Running a readiness review

A lightweight format that works for client deployments:

1. **Two weeks before launch**, the delivering engineer completes the checklist with evidence (links, screenshots, commands run) and lists known gaps.
2. **A reviewer who did not build the system** (a colleague, or a senior engineer on the client side) spends two hours verifying a sample of items by asking to see them demonstrated: "Show me the restore." "Trigger the alert." "Deploy and roll back in staging now."
3. **The review meeting** (one hour, with the client's technical owner) walks through gaps, agrees which block launch, and records accepted risks.
4. **Output**: a short document: readiness status, gaps with owners and dates, accepted risks with the accepting person named. This becomes part of the handover.

Part XIII chapter 11 expands this into the full FDE process.

## A note on proportionality

An internal tool for five users does not need multi-region failover. A client's revenue-critical ordering system does not get away with manual backups. Readiness is relative to the agreed requirements, which is why Part IX begins with requirements and Part XIII with discovery. The sin is not having a modest design; it is having an unexamined one. Every item you skip should be a conscious, recorded decision.

## Exercises

1. Run the checklist against a system you have shipped. Be honest. Classify each gap into the three priority tiers.
2. For the top three gaps, write the one-paragraph plan: what, who, by when, how you will prove it is done.
3. Design a 30-minute "show me" session: pick five checklist items and write down exactly what you would ask to be demonstrated and what acceptable evidence looks like.
