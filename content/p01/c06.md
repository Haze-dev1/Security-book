## Why this matters for deployments

Every deployment, scale-down and crash recovery is a story about processes being told to stop and new ones starting. If your service does not handle that conversation properly, every deploy drops requests, corrupts a batch job, or leaves database connections dangling. "We see errors for 30 seconds on every release" is nearly always a signal-handling problem.

## The process lifecycle

A process is created by **fork** (the kernel clones the calling process) followed usually by **exec** (replacing the clone's program with a new one). The parent can **wait** for the child to finish and collect its **exit status**: 0 means success, anything else is failure by convention. Shells, systemd, Gunicorn and container runtimes all follow this pattern.

Exit codes you will meet:

| Code | Meaning |
|---|---|
| 0 | Success |
| 1, 2 | Generic errors (application-defined) |
| 126 / 127 | Not executable / command not found (shell) |
| 128 + N | Killed by signal N: **137** = 128+9 (SIGKILL, often the OOM killer), **143** = 128+15 (SIGTERM), 139 = 128+11 (SIGSEGV, a crash) |

So when ECS or Kubernetes reports a container exited with 137, the kernel killed it, usually for exceeding memory. 143 means it was asked to stop and complied. 1 means it decided to exit itself; read its logs.

When a process exits before its parent has waited for it, it becomes a **zombie**: a dead entry in the process table holding only its exit status. Zombies are harmless individually but a parent that never reaps children leaks process table entries. When a parent dies first, children are **orphaned** and adopted by PID 1, which must reap them. This is why PID 1 in a container matters (below).

## Threads

Threads are execution contexts within one process sharing its memory, file descriptors and signals. The kernel schedules threads, not processes. One misbehaving thread (infinite loop, deadlock) does not kill the process but can consume a core or hold a lock forever. Signals are delivered to the process and handled by whichever thread is not blocking them, which is why most runtimes handle signals in the main thread.

## Signals

A signal is an asynchronous message from the kernel or another process. The important ones:

| Signal | Number | Default action | Used for |
|---|---|---|---|
| SIGTERM | 15 | terminate | "Please shut down." Sent by `kill`, systemd, Docker, Kubernetes, ECS. **Catchable.** |
| SIGINT | 2 | terminate | Ctrl-C in a terminal. Catchable. |
| SIGKILL | 9 | terminate | Immediate death. **Not catchable.** Sent by the OOM killer and by orchestrators after the grace period. |
| SIGHUP | 1 | terminate | Terminal closed; many daemons repurpose it as "reload configuration". |
| SIGQUIT | 3 | core dump | Nginx uses it for graceful shutdown. |
| SIGUSR1/2 | 10/12 | terminate | Application-defined (log rotation, dumping stats). |
| SIGCHLD | 17 | ignore | A child exited; parents reap on this. |
| SIGSEGV | 11 | core dump | Invalid memory access: a crash. |
| SIGPIPE | 13 | terminate | Writing to a closed pipe/socket. Most runtimes ignore it and surface an error instead. |

A minimal FastAPI/uvicorn application already handles SIGTERM, but background tasks and connection pools need explicit hooks:

```python
# app/main.py
import asyncio, signal, logging
from contextlib import asynccontextmanager
from fastapi import FastAPI
from fastapi.responses import JSONResponse

log = logging.getLogger("app")
shutting_down = asyncio.Event()

@asynccontextmanager
async def lifespan(app: FastAPI):
    pool = await create_db_pool()            # startup
    worker = asyncio.create_task(background_loop(pool, shutting_down))
    app.state.pool = pool
    yield                                    # application runs
    log.info("shutdown: draining")           # SIGTERM received, in-flight requests finishing
    shutting_down.set()                      # tell background loop to stop at a safe point
    await asyncio.wait_for(worker, timeout=15)
    await pool.close()
    log.info("shutdown: complete")

app = FastAPI(lifespan=lifespan)

@app.get("/health/ready")
async def ready():
    if shutting_down.is_set():
        return JSONResponse({"status": "draining"}, status_code=503)
    return {"status": "ok"}
```

Node.js equivalent:

```javascript
const server = app.listen(8000);
let draining = false;
app.get('/health/ready', (req, res) => res.status(draining ? 503 : 200).end());

async function shutdown(sig) {
  console.log(`${sig} received, draining`);
  draining = true;
  server.close(async () => {          // stop accepting; wait for in-flight
    await db.end();                   // release pool
    process.exit(0);
  });
  setTimeout(() => process.exit(1), 20_000).unref();   // hard deadline below the orchestrator's
}
process.on('SIGTERM', () => shutdown('SIGTERM'));
process.on('SIGINT', () => shutdown('SIGINT'));
```

## PID 1 in containers

Inside a container the first process is PID 1 and inherits two special duties: it must reap orphaned zombies, and the kernel does not apply default signal actions to it, so an unhandled SIGTERM is simply ignored. Two consequences:

1. `CMD python app.py` gives your app PID 1. Fine if it handles SIGTERM. `CMD sh -c "python app.py"` makes a shell PID 1, which does **not** forward SIGTERM to its child; your app is SIGKILLed after the grace period on every deploy.
2. Processes that spawn children (Chrome for PDF rendering, shell-outs) leave zombies unless PID 1 reaps them.

Fixes: use the exec form (`CMD ["python", "app.py"]`), use `exec` in entrypoint scripts (`exec gunicorn ...`), or run a tiny init such as `tini` (`docker run --init`, or `ENTRYPOINT ["tini", "--"]`). Part VI returns to this.

## System calls: watching a process work

[[system call|System calls]] are the only way a process affects the world. `strace` shows them live, which makes it the ultimate "why is this program doing that" tool:

```bash
strace -f -p <pid> -e trace=network,file -s 200      # attach to a running process
strace -c ./myprog                                    # summary table of calls and time
strace -e trace=openat,connect python app.py 2>&1 | grep -v ENOENT
```

Typical findings: the app is reading a config file from the wrong path (`openat(... ) = -1 ENOENT`), connecting to the wrong database host (`connect(... sin_addr=...)`), or making thousands of tiny `write()` calls because logging is unbuffered.

`/proc/<pid>/` exposes the process from the kernel's view: `cmdline`, `environ` (its environment variables; readable only by the owner and root, which is why running as a separate user protects secrets), `fd/` (every open descriptor), `limits`, `status` (memory, threads, UID), `cgroup`. `lsof -p <pid>` lists open files and sockets in a readable form.

```bash
ls -l /proc/$(pgrep -o gunicorn)/fd | wc -l        # how many descriptors
cat /proc/$(pgrep -o gunicorn)/limits | grep 'open files'
sudo lsof -p <pid> -i                               # network connections of a process
```

## Real-world context

- Kubernetes sends SIGTERM, waits `terminationGracePeriodSeconds` (default 30), then SIGKILL. A `preStop` hook sleeping 5 seconds is a common trick to let endpoint removal propagate before the app starts draining.
- ECS does the same with `stopTimeout` (default 30 s, max 120 s). ALB deregistration delay should be lowered from its 300-second default so deploys do not take forever.
- Gunicorn and uWSGI handle SIGTERM/SIGQUIT for graceful stops and SIGHUP for reloads; Nginx uses SIGQUIT for graceful and SIGHUP to reload configuration without dropping connections.
- Celery and other job workers implement "warm shutdown" on SIGTERM: finish the current task, do not take new ones. Tasks longer than the grace period must be idempotent or checkpointed.

## Common mistakes

- Shell-form `CMD` or an entrypoint script without `exec`, so SIGTERM never reaches the application.
- Drain timeout longer than the orchestrator's kill deadline.
- Marking readiness healthy while draining, so the load balancer keeps sending requests to a process that is about to exit.
- Long-running jobs that cannot be interrupted safely, so every deploy either waits minutes or loses work.
- Catching SIGTERM and doing nothing (swallowing it), so the service can only be killed with SIGKILL.
- Assuming `exit code 137` is an application bug; it is a memory limit or external kill.
