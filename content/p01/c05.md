## The problem

Several programs share one machine: the web server, your application, a database, a backup agent, the SSH daemon, administrators logging in. If any of them can read or modify any file, then a vulnerability in the least important one compromises everything: the database password in your config, the private TLS key, the SSH host keys. Unix permissions are the oldest, simplest mechanism for limiting what each process can touch, and they still do most of the work on a modern server.

## Users and groups

Every process runs as a **user** (a numeric UID) and belongs to one primary **group** plus supplementary groups (GIDs). Every file has an owner user and an owner group. Names map to numbers through `/etc/passwd` and `/etc/group`; the kernel only knows the numbers, which is why files copied between machines or into containers sometimes show odd ownership.

```bash
id                                # uid=1000(deploy) gid=1000(deploy) groups=1000(deploy),27(sudo),999(docker)
getent passwd app                 # app:x:1001:1001::/srv/app:/usr/sbin/nologin
sudo useradd --system --home /srv/app --shell /usr/sbin/nologin app   # service account
sudo usermod -aG docker deploy    # add to a supplementary group (log out/in to take effect)
```

Two kinds of users matter on a server:

- **Human users** (`deploy`, `alice`): log in via SSH keys, have a shell, use `sudo` for privileged actions, and are individually identifiable in logs. Shared accounts destroy accountability.
- **Service users** (`app`, `postgres`, `www-data`): own and run a specific service, have no password and no login shell, and own only the files that service needs.

**root** (UID 0) bypasses all permission checks. Nothing you run routinely should be root. Services that must bind privileged ports (below 1024) get the specific capability instead (`CAP_NET_BIND_SERVICE` via systemd's `AmbientCapabilities=`) or sit behind a reverse proxy that handles port 443.

## Permission bits

`ls -l` shows a ten-character mode such as `-rwxr-x---`. The first character is the type (`-` file, `d` directory, `l` symlink). Then three triplets for **user** (owner), **group**, and **others**: read, write, execute.

```widget:chmod
{"value": "640"}
```

For **files**: `r` read contents, `w` modify, `x` execute as a program.

For **directories** the meanings change, and this trips people up: `r` list entry names, `w` create, delete or rename entries (regardless of the file's own permissions!), `x` traverse: enter the directory and access entries by name. A directory with `r` but no `x` lets you see names but not open them; with `x` but no `r` you can open a file if you already know its name.

Octal notation sums r=4, w=2, x=1 per triplet: `rw-r-----` is 640. Common production modes:

| Mode | Use |
|---|---|
| `600` | Private keys, `.env` files, secrets. Owner only. |
| `640` | Config readable by the service group (e.g. owned `root:app`). |
| `644` | Public static files, most source code. |
| `700` | Private directories such as `~/.ssh`. |
| `750` | Application directories: owner full, group traverse/read. |
| `755` | Executables and public directories. |
| `1777` | `/tmp`: world-writable with the sticky bit (see below). |

:::danger
`chmod -R 777` makes every file readable, writable and executable by everyone on the system. Any compromised process can then read your secrets and replace your code. It also usually does not fix the actual problem, which is almost always wrong *ownership*. Fix ownership with `chown`, then set sensible modes.
:::

## Special bits

- **setuid (4000)** on an executable: run with the file owner's privileges. `/usr/bin/passwd` is setuid root so users can change their own password. Never set it on your own scripts; it is a classic privilege-escalation vector. The kernel ignores setuid on scripts for this reason.
- **setgid (2000)** on a directory: new files inherit the directory's group rather than the creator's primary group. Useful for shared deploy directories so files created by `deploy` are owned by group `app`.
- **sticky (1000)** on a directory: only a file's owner can delete or rename it, even if the directory is world-writable. This is what makes `/tmp` safe for multiple users.

```bash
sudo chmod 2775 /srv/app/shared      # setgid: files created here get group 'app'
ls -ld /srv/app/shared               # drwxrwsr-x
```

## umask

New files are created with permissions masked by the process's **umask**. Default `022` yields 644 for files and 755 for directories; `077` yields 600/700. Service units can set `UMask=0027` so an application never accidentally creates world-readable files (uploaded documents, exported reports).

## Ownership for a web application

A layout that works for most single-server deployments:

```
/srv/app/                 root:app   750   # code; the service can read, not write
/srv/app/current -> releases/2026-03-01   # symlink switched on deploy
/srv/app/releases/        deploy:app 750   # deploy user writes new releases
/srv/app/shared/uploads/  app:app    750   # the only place the app writes
/etc/app/app.env          root:app   640   # secrets: readable by the app group, not writable by the app
/var/log/app/             app:app    750   # if not using journald
```

Principles embedded there:

1. **The application cannot modify its own code.** If an attacker achieves code execution through a bug, they cannot persist by editing files. (Immutable container images give this for free.)
2. **Secrets are readable, not writable, by the service**, and unreadable by everyone else.
3. **Writes are confined** to a directory that holds only data, served with no execute permission and never interpreted as code.
4. **Deployment uses a different user** from the one that runs the service.

## Access control lists and beyond

Classic permissions have one owner and one group. When that is not enough, POSIX ACLs add per-user and per-group entries (`setfacl -m u:backup:r /var/lib/pg_dumps`, inspect with `getfacl`). Mandatory access control systems (SELinux on RHEL-family, AppArmor on Ubuntu) add kernel-enforced policies that confine even root-owned services; a web server confined by SELinux cannot read `/home` regardless of file modes. When something is denied and permissions look right, check `ausearch -m avc` (SELinux) or `dmesg | grep apparmor`.

## Files that must be protected

- `~/.ssh/authorized_keys` (600, directory 700): controls who can log in as that user. sshd refuses to use it if permissions are too open.
- Private keys for SSH and TLS (600 or 640 with a dedicated group): a readable private key is a compromised key.
- `/etc/shadow` (640 root:shadow): password hashes.
- Database data directories (700 postgres:postgres): PostgreSQL refuses to start otherwise.
- Docker socket `/var/run/docker.sock` (660 root:docker): membership in `docker` group is equivalent to root, because a container can mount the host filesystem. Treat it as such.
- `.env` and config files containing credentials.

## Diagnosing "Permission denied"

```bash
# 1. Who am I, really? (sudo, su, systemd User= all change this)
id
# 2. What are the permissions on the file AND every directory above it?
namei -l /srv/app/shared/uploads/report.pdf
# 3. Is a MAC system denying it?
sudo dmesg | tail -20 | grep -iE 'apparmor|selinux|denied'
# 4. For services: what user does systemd run it as?
systemctl show myapp -p User,Group,UMask
# 5. For bind failures on low ports:
#    "Permission denied" on port 80/443 as non-root → need CAP_NET_BIND_SERVICE or a proxy
```

`namei -l` is underused: it prints the mode and owner of each path component, exposing the parent directory missing `x` that breaks access to a perfectly permissioned file.

## In containers

Containers inherit all of this. Images that run as root (the Docker default) run your application as UID 0 inside the container, which maps to UID 0 on the host unless user namespaces are enabled. Add a user in the Dockerfile and switch to it; mount volumes with matching ownership. Part VI chapter 7 covers this in detail. Kubernetes enforces it through `runAsNonRoot` and `fsGroup`.

## Common mistakes

- Running the application as root "because the port is 80".
- `chmod 777` to fix a deployment that ran as the wrong user.
- Private key with mode 644 committed to a repo and copied to a server.
- Shared `deploy` account used by five people with no way to tell who did what.
- Forgetting that a directory needs `x` for anything inside to be reachable.
- Adding CI users to the `docker` group on a shared host without realising it is root-equivalent.
