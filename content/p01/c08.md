# Environment Variables and Configuration

:::objectives
- Separate code, configuration and secrets, and explain why each lives in a different place.
- Load, validate and type-check configuration at start-up so a misconfigured service fails immediately and loudly.
- Manage configuration across development, staging and production without duplicating secrets.
- Avoid the leaks and outages that configuration causes.
:::

:::prereq
Chapters 4 and 6.
:::

## The problem

The same code must run on a laptop, in CI, in staging and in production, each with a different database, different credentials, different feature toggles and different log levels. Hard-coding any of those into the source means a rebuild per environment and secrets in Git. The [[twelve-factor app]] principle, "store config in the environment", became standard because it solved both problems at once: the artifact is identical everywhere and the environment supplies what differs.

Configuration is also a leading cause of incidents. A missing variable in one environment, a trailing newline in a secret, a URL that points at production from staging, a default that was fine on a laptop and catastrophic at scale. The techniques in this chapter are about making those failures impossible or immediate.

## Three categories

| Category | Examples | Where it lives | Changes |
|---|---|---|---|
| **Code** | Business logic, routes, defaults that never vary | The repository | Per release |
| **Configuration** | Database host, log level, feature flags, external URLs, worker count | Environment variables, config files, parameter store | Per environment, occasionally at runtime |
| **Secrets** | Database password, API keys, signing keys, TLS private keys | Secrets manager, injected at runtime | Rotated on schedule or compromise |

Configuration can live in version control (one file per environment, no secrets). Secrets must never be in version control, images, logs or error reports, and ideally never on disk in plain text.

## Environment variables

Every process has a set of name=value strings inherited from its parent. They are simple, universal, and supported by every runtime and platform (systemd `Environment=`, Docker `-e`, ECS task definitions, Kubernetes `env`, Lambda configuration).

```bash
export DATABASE_URL='postgresql://app:secret@db.internal:5432/app?sslmode=require'
export LOG_LEVEL=info
python -c 'import os; print(os.environ["LOG_LEVEL"])'
```

Limitations to design around:

- **Strings only.** Numbers, booleans and lists must be parsed. `DEBUG=false` is a non-empty string and therefore truthy in naive code.
- **Visible to the process tree.** Child processes inherit them; `/proc/<pid>/environ` exposes them to the same user and root; crash reporters and debug pages may dump them. Secrets in environment variables are acceptable in containers but less safe than file or API injection.
- **No structure.** Nested configuration becomes `DB__POOL__MAX_SIZE`-style names.
- **Set at start.** Changing them requires a restart, which is also a feature: configuration becomes part of the deployment and is auditable.

## .env files

A `.env` file holds `KEY=value` lines loaded into the environment by a library (`python-dotenv`, `dotenv` in Node) or by Docker Compose. Rules:

- `.env` is for **local development only** and is in `.gitignore`. Commit a `.env.example` with every key and a placeholder value so new developers know what to set.
- Production does not use `.env` files; the platform injects variables (and secrets come from a secrets manager).
- Quote values containing spaces or `#`; beware of trailing whitespace and Windows line endings, which have caused countless "invalid password" incidents.

```ini
# .env.example — copy to .env and fill in
DATABASE_URL=postgresql://app:password@localhost:5432/app
REDIS_URL=redis://localhost:6379/0
SECRET_KEY=change-me-generate-with-openssl-rand-hex-32
LOG_LEVEL=debug
STRIPE_API_KEY=sk_test_xxx
ALLOWED_ORIGINS=http://localhost:3000
```

## Typed, validated configuration

The single most effective practice: parse all configuration into a typed object at start-up and **refuse to start** if anything is missing or malformed. A service that starts with a bad config and fails on the first request is far worse than one that crashes immediately with a clear message, because the orchestrator will keep the broken version "healthy" while users suffer.

```python
# app/config.py — pydantic-settings (FastAPI ecosystem)
from pydantic import Field, PostgresDsn, AnyHttpUrl, SecretStr, field_validator
from pydantic_settings import BaseSettings, SettingsConfigDict

class Settings(BaseSettings):
    model_config = SettingsConfigDict(env_file=".env", env_file_encoding="utf-8", extra="forbid")

    env: str = Field(pattern="^(dev|staging|prod)$")
    database_url: PostgresDsn
    redis_url: str
    secret_key: SecretStr = Field(min_length=32)
    log_level: str = "info"
    allowed_origins: list[AnyHttpUrl] = []
    db_pool_size: int = Field(default=10, ge=1, le=100)
    request_timeout_s: float = 30.0
    stripe_api_key: SecretStr | None = None

    @field_validator("allowed_origins", mode="before")
    @classmethod
    def split_csv(cls, v):
        return [x.strip() for x in v.split(",")] if isinstance(v, str) else v

settings = Settings()   # raises a precise ValidationError listing every problem
```

```javascript
// config.js — zod in Node
import { z } from 'zod';
const schema = z.object({
  NODE_ENV: z.enum(['development', 'staging', 'production']),
  PORT: z.coerce.number().int().min(1).max(65535).default(8000),
  DATABASE_URL: z.string().url(),
  SECRET_KEY: z.string().min(32),
  LOG_LEVEL: z.enum(['debug', 'info', 'warn', 'error']).default('info'),
  FEATURE_NEW_CHECKOUT: z.coerce.boolean().default(false),
});
const parsed = schema.safeParse(process.env);
if (!parsed.success) { console.error('Invalid configuration:', parsed.error.flatten().fieldErrors); process.exit(1); }
export const config = parsed.data;
```

Notice `SecretStr`: it prints as `**********` in logs and reprs, so a careless `log.info(settings)` does not leak the key. Note `extra="forbid"`: a typo like `DATABSE_URL` fails fast instead of silently falling back to a default.

## Precedence and layering

A typical order, highest priority first: command-line flags → environment variables → environment-specific file → defaults in code. Keep it simple and document it. Resist building a configuration system with six layers; nobody will remember which wins.

## Secrets: where they come from in production

The progression from unsafe to safe:

1. Hard-coded in source. Never.
2. In a `.env` file on the server with mode 600. Acceptable for a single small VM if the file is not in Git and backups are encrypted; weak audit trail and rotation.
3. Platform-injected environment variables from a secrets manager (ECS `secrets` referencing Secrets Manager or Parameter Store; Kubernetes Secrets, ideally synced from an external store). The orchestrator fetches at start and the application just reads `os.environ`. Standard for containers.
4. Fetched by the application at start-up via SDK using an [[iam role]] (no credentials needed to get credentials). Enables rotation without redeploy, fine-grained audit of every read, and keeps secrets out of the environment entirely.
5. Short-lived credentials generated on demand (IAM database authentication, Vault dynamic secrets). The strongest model; more moving parts.

Part IV chapter 17 and Part VII chapter 12 cover the tooling. Whatever the mechanism, the application should receive secrets through one well-defined path and never log them.

## Feature flags and runtime configuration

Some configuration must change without a restart: turning a feature off during an incident, adjusting a rate limit, enabling a new checkout for 5% of users. That is a **feature flag** system (LaunchDarkly, Unleash, AWS AppConfig, or a database table with a cache). Keep the distinction: start-up config is validated once and immutable; runtime flags are read per request from a cached source with a safe default if the source is unreachable.

## Environment parity

Environments should differ *only* in configuration values, never in code paths. Code that says `if env == "prod": do_something_different()` is a bug waiting to be found only in production. The acceptable exceptions are observability settings (log level, sampling rate) and safety rails (refuse to run destructive migrations when `env == "prod"` without a flag).

## Common mistakes and incidents

- **Missing variable with a silent default.** `os.environ.get("DATABASE_URL", "postgresql://localhost/dev")` connects staging to a local database that does not exist, or worse, exists.
- **Secrets in build arguments.** `docker build --build-arg API_KEY=...` embeds the key in image history (`docker history` shows it). Use BuildKit secret mounts.
- **Secrets in logs.** Logging the full config object, or an HTTP client logging request headers including `Authorization`.
- **Trailing newline in a secret** copied from a file into a console. The password is `hunter2\n`. Strip on load, and prefer programmatic secret creation.
- **Same secret across environments.** A leaked staging key is a production key.
- **Environment variable injection via `.env` in a public static directory**, served by the web server. Never place `.env` under the web root.
- **Config drift between instances**: two servers in a fleet with different values because someone edited one by hand.

## Exercises

1. Add a typed settings module to an application you own. Remove one required variable and confirm the service exits with a clear message at start-up rather than on first request.
2. Grep your repository history for strings that look like secrets (`git log -p | grep -iE 'api[_-]?key|secret|password'`). If you find any, treat them as compromised: rotate them. Then add secret scanning (Part X chapter 3).
3. Design the configuration matrix for an application with three environments: list every key, which environment it varies in, and whether it is a secret.
