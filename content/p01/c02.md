## The problem: "run the code" is not one thing

When you type `python app.py` or `node server.js`, something turns text into CPU instructions. How that happens decides your start-up time, memory footprint, CPU efficiency, how many concurrent requests one process can handle, how you package and deploy it, and how you debug it when it is slow. Engineers who treat the runtime as a black box make predictable mistakes: they run one Python process on an 8-core machine and wonder why 7 cores idle; they block the Node event loop with a synchronous call and the whole server freezes; they ship a Go binary with no way to see what it is doing.

## Three ways to execute source code

### Ahead-of-time compilation

A **compiler** translates source into machine code for a specific CPU architecture and operating system before the program runs. Go, Rust, C and C++ work this way. The output is a binary: a file the kernel can load and jump into directly.

Consequences for production:

- **Deployment is a file copy.** A statically linked Go binary has no runtime dependencies. Container images can be built `FROM scratch` and weigh a few megabytes.
- **Start-up is instantaneous**, which matters for autoscaling and serverless cold starts.
- **Cross-compilation is required**: a binary built on an Apple Silicon laptop (arm64, macOS) will not run on an x86-64 Linux server. CI builds for the target platform.
- Errors like type mismatches are caught at build time rather than at 3 a.m.

### Interpretation

An **interpreter** reads the source (or a lightly processed form of it) and executes it step by step. CPython, the standard Python implementation, compiles each module to bytecode (`.pyc` files in `__pycache__`) and then runs that bytecode on a virtual machine written in C. Ruby and PHP behave similarly.

Consequences:

- **The runtime must be installed on the server**, at a compatible version, together with every dependency. This is why Python deployments historically broke so often and why containers became popular.
- **Start-up involves importing modules**, which can take seconds for large applications.
- **Execution is slower per instruction** than native code, often by an order of magnitude for pure-Python loops. Real applications spend most time in I/O or in C extensions (database drivers, JSON parsing, NumPy), so the gap matters less than benchmarks suggest.
- Many errors surface only when the line executes. Type checkers like mypy and Pyright recover some compile-time safety.

### Just-in-time compilation

A **JIT** runtime starts by interpreting and compiles hot code paths to machine code while the program runs, using observed types and branches to optimise. The JVM (Java, Kotlin), V8 (Node.js, browsers) and .NET work this way.

Consequences:

- **Warm-up**: the first few thousand requests are slower than steady state. Load tests and health checks must account for this; a JVM service can take 30 to 90 seconds to reach full speed.
- **Memory**: JIT runtimes hold compiled code, profiling data and large heaps. A trivial Java service may need 256 MB; the JVM's default heap sizing inside containers has caused countless out-of-memory kills, discussed in chapter 7.
- **Peak performance** can approach native code.

## What a runtime does for you

Whichever model, your code runs inside a **runtime**: the standard library plus machinery for memory management, concurrency and interaction with the operating system.

**Memory management.** Go, Java, Python and JavaScript all use garbage collection: the runtime tracks which objects are still reachable and frees the rest. You do not call `free()`, but you pay in CPU time and, with some collectors, in pauses. A service that allocates heavily can show periodic latency spikes exactly when the collector runs. Rust and C make you manage memory explicitly, trading ergonomics for predictability.

**Concurrency.** This is where runtimes differ most and where production behaviour is decided.

- **CPython and the GIL.** The Global Interpreter Lock allows only one thread to execute Python bytecode at a time within a process. Threads still help when work is I/O-bound (the lock is released while waiting on a socket), but CPU-bound work does not parallelise across threads. To use multiple cores you run **multiple processes**, which is why production Python servers (Gunicorn, uWSGI) fork workers. Recent Python versions have an optional free-threaded build, but as of late 2026 most production deployments still use the GIL build and the multi-process model.
- **asyncio** (Python) and **the event loop** (Node.js). A single thread runs many tasks cooperatively; each yields when it awaits I/O. Extremely efficient for thousands of concurrent connections that are mostly waiting. The catastrophic failure mode: one task does CPU-heavy or blocking synchronous work and every other request on that loop stalls. In Node, a synchronous `fs.readFileSync` in a request handler or a tight loop over a large array freezes the server for everyone.
- **JVM threads.** Real OS threads, one per request in traditional servlet containers, with virtual threads available in modern Java for very high concurrency. Thread pools must be sized; a pool of 200 threads each holding a database connection needs a connection pool that can supply them.
- **Goroutines.** Go multiplexes lightweight goroutines onto OS threads automatically. The runtime handles the scheduling, so writing concurrent servers is simple; the typical mistakes are data races (use `go test -race`) and unbounded goroutine creation.

## Processes: how the operating system sees your service

The kernel does not know about Python or Node. It knows **processes**: an address space, a set of open [[file descriptor|file descriptors]], environment variables, a user ID, a current directory and one or more threads scheduled onto CPUs. When you run a server, you are asking the kernel to create a process, load the runtime binary into it, and let the runtime load your code.

Everything about deployment is ultimately about processes:

- A **container** is a process with isolation applied (Part VI).
- A **systemd service** is a process the init system starts, supervises and restarts (Part V).
- A **deploy** stops old processes and starts new ones; a **graceful shutdown** means the process finishes in-flight requests after receiving SIGTERM before exiting (chapter 6).
- A **crash** is a process exiting unexpectedly; the supervisor's job is to notice and restart it, and yours is to find out why from the logs.

## Practical: running a FastAPI app in production

Development uses the auto-reloading single process:

```bash
uvicorn app.main:app --reload --port 8000
```

Production uses a process manager with multiple workers, no reload, and binding to all interfaces inside the container:

```bash
gunicorn app.main:app \
  --worker-class uvicorn.workers.UvicornWorker \
  --workers 4 \
  --bind 0.0.0.0:8000 \
  --timeout 30 \
  --graceful-timeout 20 \
  --max-requests 5000 --max-requests-jitter 500 \
  --access-logfile - --error-logfile -
```

Each flag encodes a production lesson:

| Flag | Lesson |
|---|---|
| `--workers 4` | Use the cores. Start with 1 async worker per core, then load test. |
| `--timeout 30` | A worker stuck for 30 seconds is killed and replaced; a hung request cannot wedge the server forever. Must exceed your slowest legitimate request. |
| `--graceful-timeout 20` | On SIGTERM, workers get 20 seconds to finish current requests. Must be below the orchestrator's kill deadline (ECS default 30 s, Kubernetes default 30 s). |
| `--max-requests` with jitter | Recycles workers periodically to bound memory leaks; jitter stops all workers restarting at once. |
| Logs to stdout/stderr | The container runtime or systemd collects them. Never write log files inside containers. |

The Node.js equivalent is running one process per core with the cluster module or, more commonly, running one Node process per container and letting the orchestrator run several containers. Node's event loop handles concurrency within each process; CPU-bound work goes to worker threads or a separate service.

## Real-world context

- **Serverless cold starts** are a direct consequence of runtime choice: a Go or Rust Lambda starts in tens of milliseconds, Python in a few hundred, a JVM in seconds without special tooling (SnapStart or GraalVM native images).
- **Right-sizing containers** depends on the runtime's memory model. A Node service usually fits in 256 to 512 MB; a Spring Boot service wants 1 GB or more. Guessing wrong means [[oom killer|OOM kills]].
- **Polyglot teams** standardise on a base image per runtime with the version pinned (`python:3.12-slim`, `node:22-alpine`), because "it worked locally on Python 3.11" is a real incident class.

## Security and operational considerations

- Runtimes have vulnerabilities. Patch them like any dependency: a Node or Python base image from a year ago carries known CVEs.
- Interpreted languages make `eval`-style code execution easy; never pass untrusted input to `eval`, `exec`, `pickle.loads` or template engines without sandboxing (Part IV).
- Debug servers (`--reload`, Werkzeug debugger, Node `--inspect` bound to 0.0.0.0) must never run in production. The Werkzeug debugger allows arbitrary code execution to anyone who reaches it.
- Expose runtime metrics: GC pauses, event loop lag, worker count, heap size. They explain latency spikes that application metrics cannot.

## Common mistakes

1. **One process on a multi-core machine** for a Python or Node service. Cores sit idle; throughput is a quarter of what you paid for.
2. **Blocking the event loop** with synchronous file or network calls, CPU-heavy loops, or a synchronous database driver in an async framework. Symptom: every request is slow at once, CPU is at 100% on one core.
3. **Too many workers** on a memory-constrained container, so the total exceeds the limit and the kernel kills the whole container.
4. **Unbounded concurrency** (async tasks or goroutines spawned per request without limit), overwhelming the database.
5. **Mismatched runtime versions** between CI, staging and production. Pin the version in one place (the Dockerfile) and let everything inherit it.

## Exercises

1. Run your application with one worker and with one worker per core. Load test both with a tool such as `hey` or `k6` (Part XI). Record requests per second and p99 latency. Explain the difference in terms of this chapter.
2. Introduce a deliberate 2-second synchronous sleep into one endpoint of an async service and observe what happens to *other* endpoints under concurrent load. Then make it `await asyncio.sleep(2)` and repeat.
3. Measure the memory of one worker at idle and after 10 minutes of traffic. Decide on a container memory limit and worker count that leaves 30% headroom.
