# From Source Code to Production: The Whole Picture

:::objectives
By the end of this chapter you will be able to:

- Describe every system a line of code passes through between a developer's editor and a user's browser.
- Explain what "production" means operationally, not just as a word for "the live site".
- Name the responsibilities that exist beyond writing code: build, release, deploy, operate, observe, secure, recover.
- Place every later chapter of this book on a single mental map.
:::

:::prereq
You can write a web application in at least one language and have used Git. No infrastructure experience is assumed.
:::

## The problem this chapter solves

Most developers learn programming from the inside out: a function, then a module, then an application that runs on their laptop. "Deployment" arrives later as a mysterious step where the application is "put on a server" and, hopefully, keeps working.

That gap is where most production incidents, security breaches and budget overruns live. The code was fine. What failed was the certificate that expired, the database connection pool that was exhausted, the environment variable that was missing in staging but present in production, the S3 bucket that was public, the deploy that ran a migration before the old code had stopped using the column.

This book is about everything that happens around and after the code. This first chapter gives you the whole map so that each subsequent chapter has a place to live.

## What "production" means

Production is not a place. It is a set of obligations. A system is "in production" when real people depend on it and someone is accountable for it. That accountability creates requirements that have nothing to do with features:

| Obligation | What it means in practice | Where you learn it |
|---|---|---|
| **Availability** | It is up when users need it, including at 3 a.m. and during a deploy. | Parts IX and XI |
| **Correctness under concurrency** | Two users saving at once do not corrupt each other's data. | Part VIII |
| **Security** | Only the right people can see and change the right data; mistakes do not leak client information. | Part IV |
| **Observability** | When something is wrong you can tell what, where and since when. | Part XI |
| **Recoverability** | Data can be restored and service can be rebuilt after a disaster, within an agreed time. | Parts V, VIII, XI |
| **Operability** | A person who did not write it can deploy it, scale it, patch it and roll it back from documentation. | Parts X, XII, XIII |
| **Cost control** | It costs what the client expects, and you can explain the bill. | Part VII |
| **Compliance** | Personal data is handled according to law and contract. | Parts IV and XII |

This is the difference between "working software" and "production-ready software". The last chapter of this part defines production readiness precisely and gives you a checklist; the rest of the book teaches you how to satisfy each item.

## Roles you will be playing

In a large company each of these layers has a dedicated team. As a Forward Deployed Engineer on a client project you are frequently all of them at once. This book uses these role names throughout, because knowing which hat you are wearing clarifies which decisions you are making.

- **Software engineer:** designs and writes the application, tests, API contracts.
- **Infrastructure / platform engineer:** provisions networks, compute, databases; writes infrastructure as code; builds pipelines.
- **Security engineer:** threat models, reviews authentication and authorization, manages secrets, scans dependencies, responds to vulnerabilities.
- **Site reliability engineer (SRE):** defines SLOs, builds observability, handles incidents, runs postmortems, plans capacity.
- **Database administrator:** schema design, indexing, backups, replication, performance.
- **Architect:** chooses between options under constraints of cost, risk, time and the client's capabilities; writes it down.

:::fde
A client rarely says "we need defense in depth and an RPO of five minutes." They say "it must not go down during the trade show" and "we can't lose orders." Your job is to translate. Part XIII is devoted to that translation, but keep the question in mind from the first chapter: for every technology you learn here, *what client outcome does it protect?*
:::

## A first look at production readiness

Here is a condensed version of the checklist you will build up over the book. Do not worry about the items you do not understand yet. Tick what you already do today, and come back after each part.

```checklist
# Production readiness: first pass
## Build and deploy
- Every change goes through a pull request with automated tests.
- The deployed artifact is immutable and identified by a commit SHA or version.
- Deployment is a single command or pipeline, and rollback is equally simple.
- Database migrations are backward compatible with the currently running code.
## Security
- No secrets in the repository, images or logs; all secrets come from a secrets store.
- Every request is authenticated and every data access is authorised at the resource level.
- Dependencies are locked and scanned; TLS is enforced everywhere.
- The database and internal services are not reachable from the Internet.
## Operations
- Structured logs with correlation IDs; metrics for latency, errors and saturation; alerts on symptoms users feel.
- Health checks reflect real readiness, not just "the process is running".
- Backups run automatically and a restore has actually been tested.
- There is a runbook a stranger could follow to deploy, roll back and recover.
## Ownership
- Someone is on call and knows it; incidents have a severity scale and a communication plan.
- Costs are tagged, budgeted and alerted.
- Architecture decisions are recorded with their reasoning.
```

## Common misconceptions to discard now

**"If it works on my machine and passes tests, it is done."** Tests prove the code does what you think in the environment you tested. Production adds concurrency, hostile input, network failure, expiry, partial deploys and other people's changes.

**"The cloud handles reliability for me."** AWS keeps its services running; you are responsible for running yours across Availability Zones, backing up your data, and configuring security. This is the [[shared responsibility model]].

**"Security is a feature we add at the end."** A system designed without trust boundaries cannot have them bolted on. The cheapest security work is done in design, the most expensive after a breach.

**"Kubernetes is how serious systems are deployed."** Many serious, profitable systems run on a handful of containers on a managed service, or even on two well-configured virtual machines. Complexity is a cost paid every day; buy it only when the problem demands it.

**"Monitoring means a dashboard."** A dashboard nobody is watching at 3 a.m. is decoration. Monitoring means alerts that page a human when users are affected, and the observability to find out why.

1. Finish Part I quickly for vocabulary.
