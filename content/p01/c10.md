# Git Workflows, Branching, Pull Requests and Releases

:::objectives
- Choose and operate a branching strategy appropriate to team size and release cadence.
- Run a pull request process that catches defects and preserves the reasoning behind changes.
- Use tags, protected branches and release branches to ship and hotfix safely.
- Recover from common Git mistakes without losing work.
:::

:::prereq
Working knowledge of basic Git: clone, commit, push, pull.
:::

## The problem

Several people change the same codebase at once, and the main branch must always be deployable. Git gives you the primitives; a **workflow** is the agreed set of rules for using them so that work integrates continuously, mistakes are caught before production, and anyone can answer "what exactly is running in production and why?"

## Branching strategies

### Trunk-based development

Everyone branches from `main`, keeps branches short-lived (hours to a couple of days), and merges back via pull request. `main` is always releasable; incomplete features are hidden behind [[feature flag|feature flags]]. Releases are cut from `main` by tag or by continuous deployment. This is the default recommendation for teams practising CI/CD, because long-lived branches diverge and merge pain grows with the square of branch lifetime.

### GitHub Flow

Trunk-based with the explicit rule: deploy from the branch *before* merging (or immediately after). Simple, suits web services with continuous deployment.

### Git Flow and release branches

Separate `develop` and `main`, with `release/x.y` and `hotfix/` branches. Heavier; appropriate when you ship versioned software to customers who upgrade on their own schedule (mobile apps, on-premise installs, client deliverables with formal acceptance). Many client projects are a hybrid: trunk-based development plus a `release/` branch per client acceptance milestone.

## Branch protection

Configure `main` so that it cannot be pushed to directly, requires a pull request with at least one approval, requires status checks (tests, lint, security scans) to pass, requires the branch to be up to date, and dismisses stale approvals when new commits are pushed. Include administrators. Enable signed commits if the client requires provenance. These settings turn the workflow from a convention into an enforced control, which auditors and clients care about.

## Pull requests that work

A pull request is a unit of change, a review conversation and a permanent record. Make all three good:

- **Small.** Under 400 changed lines reviews well; 2,000-line PRs get rubber-stamped. Split refactors from behaviour changes.
- **Described.** What changed, why, how it was tested, what reviewers should focus on, screenshots for UI, links to the ticket and any ADR. A template helps.
- **Self-reviewed first.** Read your own diff before requesting review; you will catch half the comments yourself.
- **Reviewed for the right things**: correctness, security (input validation, authorization, secrets), operability (logging, metrics, migrations), tests, clarity. Style is for linters. Part XII chapter 6 covers review in depth.
- **Merged cleanly.** Squash-merge for feature branches gives one meaningful commit per PR on `main`; rebase-merge keeps individual commits if they are curated. Avoid merge commits from `main` into the feature branch cluttering history; rebase the branch instead.

Commit messages: a short imperative subject line under 72 characters, a blank line, then the why. "Fix bug" is useless at 2 a.m.; "Retry S3 uploads on throttling errors (fixes intermittent export failures, see INC-42)" is gold.

## Tags and releases

A tag is an immutable name for a commit. Releases are tagged (`v2.4.1`) so that "what is in production" has an exact answer, the build pipeline can embed the version, and a rollback target is well defined. Annotated tags (`git tag -a v2.4.1 -m "..."`) record who and when. Many pipelines deploy *only* from tags or from `main` and embed the commit SHA into the artifact and a `/version` endpoint:

```bash
git describe --tags --always --dirty     # v2.4.1-3-g1a2b3c4  → 3 commits after v2.4.1
docker build --build-arg GIT_SHA=$(git rev-parse --short HEAD) -t app:$(git rev-parse --short HEAD) .
```

## Hotfixes

With trunk-based development a hotfix is just a small PR merged to `main` and deployed. With release branches: branch from the release tag, fix, tag `v2.4.2`, deploy, then merge or cherry-pick the fix into `main` so it is not lost. The step people forget is the merge back; a regression that was fixed in production and reappears in the next release is almost always a missed back-merge.

## Daily mechanics

```bash
git switch -c feature/export-csv main           # new branch from main
git fetch origin && git rebase origin/main      # keep up to date (before pushing, or force-with-lease after)
git push -u origin feature/export-csv
git push --force-with-lease                     # after a rebase; never plain --force on shared branches
git log --oneline --graph --decorate -20
git bisect start; git bisect bad; git bisect good v2.3.0   # find the commit that broke something
```

## Recovering from mistakes

- **Committed to the wrong branch**: `git switch -c correct-branch` then on the original `git reset --hard origin/original`.
- **Need to undo a merged commit**: `git revert <sha>` creates a new commit undoing it; never rewrite `main`.
- **Lost commits after a bad reset or rebase**: `git reflog` lists where HEAD has been; `git reset --hard <reflog-entry>` restores.
- **Committed a secret**: assume it is compromised the moment it is pushed. Rotate it first, then purge history with `git filter-repo` and force-push, coordinate with everyone who has a clone, and add secret scanning. Rotation is non-negotiable; history rewriting alone does not un-leak anything that was fetched or cached.
- **Large file committed by accident**: remove it with `git filter-repo`, then add it to `.gitignore` or Git LFS.

## Monorepos and multiple repos

One repository per deployable service is the simplest default for client work: clear ownership, simple CI, independent release cadence. A monorepo (all services in one repo) simplifies cross-cutting changes and shared code but requires tooling to build and test only what changed. Choose based on how often you change several services together; do not choose based on fashion.

## Git and security

- Every commit's author is a claim, not a proof, unless commits are signed (SSH or GPG signing, "Verified" badge). Require signed commits for high-assurance clients.
- Protected branches and required reviews are a control: no single person can push unreviewed code to production. Document this for compliance questionnaires.
- The repository is often the most sensitive asset a client gives you access to. Use SSO-backed access, least privilege (read for most, write for the team), and remove access promptly at offboarding.
- `.gitignore` is not a security control. Files that were committed before being ignored remain in history.

## Common mistakes

- Long-lived feature branches that merge with hundreds of conflicts.
- Force-pushing to shared branches, destroying colleagues' work.
- Enormous PRs reviewed in a minute.
- Fixing in production (hotfix branch) and forgetting to merge back.
- Tags that are moved after creation, so `v1.2.0` means different things to different people.
- Treating `.gitignore` as having removed already-committed secrets.

## Exercises

1. Configure branch protection on a test repository: required PR, one approval, required status check, include administrators. Try to push directly and observe the refusal.
2. Create a release tag, then simulate a hotfix on a release branch and merge it back to `main`. Verify with `git log --graph` that the fix exists in both.
3. Use `git reflog` to recover from a deliberate `git reset --hard HEAD~3`.
