# Testing Strategies

:::objectives
- Design a test portfolio (unit, integration, contract, end-to-end, non-functional) that gives fast, trustworthy feedback at reasonable cost.
- Write tests that catch real defects and survive refactoring, including tests for the behaviour that matters most in production: failures, boundaries and security.
- Manage test data, environments and flakiness so the suite stays a trusted gate.
:::

:::prereq
[CI/CD Fundamentals](#/p10/c01); [Technical Debt and Code Quality](#/p12/c04).

## What tests are for

Tests are automated evidence that the system behaves as intended, run on every change. They serve three purposes: catching regressions before users do, documenting behaviour in executable form, and enabling refactoring with confidence. A test that does none of these (asserts implementation details, duplicates another test, or is ignored when red) is cost without value.

The pyramid shape (many fast unit tests, fewer integration tests, very few end-to-end tests) holds because cost and flakiness rise with scope. Over-investing in end-to-end tests yields a slow, brittle suite that teams stop trusting; under-investing in integration tests yields unit tests that pass while the SQL is wrong. For backend services the sweet spot often leans toward integration tests against real databases in containers (Testcontainers), because that is where production bugs live.

## Writing good tests

- **Test behaviour, not implementation**: assert on outputs and observable effects, not on which internal methods were called. Mock at architectural boundaries (external HTTP, time, randomness), not inside your own code.
- **One reason to fail** per test; descriptive names that read as specifications: `test_approval_over_threshold_routes_to_finance`.
- **Arrange, act, assert** with the arrangement visible; builders or factories for test data, not hundred-line fixtures.
- **Boundaries and errors first**: exactly at the threshold, one over, empty, null, maximum size, duplicate, concurrent, timeout, dependency down. Happy paths rarely break; edges do.
- **Deterministic**: control time (inject a clock), seed randomness, avoid sleeps, isolate state between tests.
- **Fast**: a unit suite in seconds, integration suite in a few minutes, parallelised and sharded in CI.

```python
# Integration test with a real PostgreSQL via Testcontainers; tests the query, the constraint and the transaction
import pytest
from testcontainers.postgres import PostgresContainer

@pytest.fixture(scope="session")
def db_url():
    with PostgresContainer("postgres:16.4") as pg:
        run_migrations(pg.get_connection_url())
        yield pg.get_connection_url()

@pytest.fixture
def repo(db_url):
    conn = connect(db_url)
    conn.execute("BEGIN")             # each test runs in a transaction that is rolled back
    yield InventoryRepository(conn)
    conn.execute("ROLLBACK")

def test_reserve_fails_when_stock_insufficient(repo):
    repo.seed_stock(sku="A1", available=2)
    assert repo.reserve("A1", 2) is True
    assert repo.reserve("A1", 1) is False          # the conditional update returns zero rows
    assert repo.stock("A1").reserved == 2

def test_concurrent_reservations_never_oversell(db_url):
    seed(db_url, sku="A1", available=10)
    results = run_in_threads(50, lambda: InventoryRepository(connect(db_url)).reserve("A1", 1))
    assert sum(results) == 10                      # exactly ten succeed, forty fail
```

## Testing failure and security behaviour

Production incidents come from paths tests rarely cover. Deliberately test: dependency timeouts and errors (does the circuit breaker open? does the fallback return?), retries with idempotency (does a duplicate webhook produce one effect?), partial failures (message processed but acknowledgement lost), authorisation (user A cannot read B's resource: every endpoint, every role; the cross-tenant suite from Part IX chapter 16), input validation with hostile inputs (oversized, malformed, injection payloads), and configuration errors (missing variable fails fast at startup).

```python
@pytest.mark.parametrize("path", ["/orders/{id}", "/invoices/{id}", "/documents/{id}/download"])
def test_resource_of_other_tenant_is_not_found(client_as_tenant_a, tenant_b_resources, path):
    resp = client_as_tenant_a.get(path.format(id=tenant_b_resources[path]))
    assert resp.status_code == 404                 # not 403: do not confirm existence
    assert "tenant_b" not in resp.text
```

## Contract testing

When services are owned by different teams, end-to-end tests across all of them are slow and politically hard. Consumer-driven contracts (Pact, or OpenAPI-based tools like Schemathesis and Dredd) let the consumer specify what it needs and the provider verify it in its own pipeline; a provider change that breaks a consumer fails the provider's build. OpenAPI specifications ([API Contracts and OpenAPI](#/p03/c14)) are the shared artefact; validate requests and responses against them in tests and at runtime in non-production.

## End-to-end tests

Keep them to the critical journeys (sign in, core transaction, payment, export), run them against a deployed environment after each deploy (chapter 10 of Part X), make them resilient (stable selectors, explicit waits for state, retries only for known-unreliable external steps), and give them synthetic accounts and data. Playwright and Cypress for browsers; API-level journeys where a UI is not involved. When an end-to-end test fails, the question is "which lower-level test should have caught this?" and the answer is a new unit or integration test.

## Test data and environments

- **Never production data** in tests or lower environments without anonymisation; personal data in a test fixture is a breach waiting to happen ([Data Privacy and Personally Identifiable Information](#/p04/c23)).
- **Synthetic data generators** with realistic shapes and volumes; a seeded dataset for integration tests; large generated datasets for performance tests.
- **Ephemeral environments** per pull request where feasible (containers, preview environments) so tests do not fight over shared state.
- **Fixtures in code**, versioned with the tests, built with factories.

## Flakiness

A flaky test (passes and fails without code changes) is a defect. Quarantine it immediately (mark and exclude from the gate, open an issue), fix within days, and track flake rate. Common causes: shared mutable state, timing assumptions, order dependence, external services, resource leaks, non-deterministic data. Rerunning failed tests automatically hides the problem; do it only with a report of what was retried.

## Coverage

Coverage measures which lines executed, not whether behaviour was verified. Use it to find untested areas, not as a target to game. A sensible floor (70–85%) with attention to critical paths beats a mandated 100%. **Mutation testing** (mutmut, Stryker, PIT) measures whether tests detect injected bugs and is a far better signal of test quality for critical modules.

## Test-driven and behaviour-driven development

TDD (write a failing test, make it pass, refactor) produces testable designs and tight feedback; use it for logic-heavy code. BDD frameworks (Gherkin scenarios) are valuable when non-engineers co-own the specification; otherwise plain tests with good names suffice. Neither is a religion; the outcome that matters is a fast, trusted suite.

## Common mistakes

- Mocking your own database or internal classes, so tests pass while the real query fails.
- Testing getters and setters while leaving authorisation untested.
- End-to-end suites that take an hour and fail randomly.
- Coverage targets that produce assertion-free tests.
- Production data copied to staging "for realistic tests".
- Treating a red build as a nuisance to re-run.
