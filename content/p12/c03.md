# Design Documents, Architecture Reviews and ADRs

:::objectives
- Write design documents that get decisions made and reviewed before code is written.
- Run architecture reviews that improve designs without becoming gatekeeping theatre.
- Record decisions as Architecture Decision Records so future engineers know why, not just what.
:::

:::prereq
[Requirements Gathering and Technical Specifications](#/p12/c01); Part IX.
:::

## Design documents

A design document proposes how to solve a problem and invites critique while change is cheap. It differs from the specification (chapter 1): the spec defines what and why for stakeholders; the design doc defines how for engineers, often per significant component or change. Write one when a change affects more than one team, introduces a new system or dependency, touches security or data boundaries, is hard to reverse, or is expensive.

Structure that works:

```checklist
# Design document
- Context and problem: what and why now; links to requirements
- Goals and non-goals
- Proposed design: diagrams, components, data flow, APIs, data model, failure handling
- Alternatives considered: at least two real ones, with why they lose on the stated goals
- Cross-cutting concerns: security and privacy, reliability and SLOs, performance, cost, operability, observability, migration and rollout, testing
- Risks and open questions
- Timeline and milestones
- Reviewers and decision: who must approve, by when
```

Writing well: lead with the decision you want; one diagram worth a thousand words (Part IX style, with trust boundaries); concrete numbers (expected load, data size, latency budgets); show the alternatives honestly (a document whose alternatives are strawmen convinces nobody); keep it short enough to be read (four to eight pages for most designs); use comments in the document for review rather than meetings where possible.

## Architecture reviews

A review is a structured critique by people who did not write the design. Good reviews catch missing failure modes, security gaps, operability problems, cost surprises and inconsistency with the rest of the system. Bad reviews are a committee demanding conformance to their preferences, delaying work for weeks.

Make them good:

- **Early and light**: a 30-minute discussion of a one-page sketch before the full document; a review of the full document before implementation; a short post-implementation check that it matches.
- **Written first**: reviewers read and comment asynchronously; the meeting resolves disagreements only.
- **Checklist-based**: the same questions every time (below), so review quality does not depend on who shows up.
- **Advisory with clear decision rights**: the owning team decides unless the review finds a violation of agreed standards (security, data handling, platform constraints), which are documented and few.
- **Time-boxed**: a decision within a week; silence is consent after the deadline.
- **Blameless and specific**: "what happens when the queue is unavailable?" not "this is wrong".

```checklist
# Architecture review questions
- What is the user-facing failure when each component fails? Is it acceptable?
- Where are the trust boundaries and how is each crossing authenticated and authorised?
- What data is stored, where, for how long, with what classification and encryption?
- What are the SLOs and how will they be measured?
- How does it deploy, roll back, migrate data, and get observed in production?
- What does it cost at expected load and at 10× load?
- What is the blast radius of a bug or compromise?
- How will the team operate it at 03:00 with the on-call engineer who did not build it?
- What existing component or service already does this?
- What is deliberately not solved, and is that agreed?
```

## Architecture Decision Records

An ADR is a short document recording one significant decision: the context, the options, the decision, and its consequences. ADRs answer the question every engineer asks of an unfamiliar system: "why on earth did they do it this way?" Without them, teams relitigate settled decisions, or preserve decisions whose reasons no longer hold.

@file: docs/adr/0007-postgresql-rls-for-tenant-isolation.md
```markdown
# ADR 0007: Row-level security for tenant isolation in the shared database tier

Date: 2026-03-14 · Status: Accepted · Deciders: platform team, security lead · Supersedes: —

## Context
The SaaS platform serves ~2,000 tenants from a shared PostgreSQL pool for the self-serve tiers (ADR 0005 chose the hybrid tenancy model). Cross-tenant data exposure is the highest-impact risk in our threat model. Application-level filtering by tenant_id depends on every query being correct; a single omission is a breach. We need a defence that does not depend on individual queries.

## Options considered
1. Application-level filtering only, with code review and tests. Cheapest; one bug is a breach; rejected as sole control.
2. Schema per tenant. Stronger isolation; migration tooling becomes painful at thousands of schemas; connection pooling complexity; rejected.
3. Row-level security with a session variable set per request, plus application filtering. Adds a database-enforced floor; small per-query overhead (measured at <3% in benchmarks); requires discipline that the app role cannot BYPASSRLS and that the variable is set in every transaction.

## Decision
Option 3. Every tenant-scoped table has an RLS policy using current_setting('app.tenant_id'). The repository layer sets the variable inside each transaction from the verified tenant context. The application database role has no BYPASSRLS. Application-level filtering remains as the first line; RLS is the floor. A cross-tenant test suite and a canary tenant tripwire verify both.

## Consequences
+ A query that forgets the tenant filter returns nothing rather than another tenant's data.
+ Auditors get a database-enforced control to point to.
− Every transaction must set the variable; forgetting it returns empty results (fail closed), which is confusing in development; mitigated by the repository layer and a startup check.
− Bulk administrative operations need a separate role with explicit, audited use.
− Slight overhead on every query; acceptable.

## Review
Revisit if tenant count exceeds 10,000 or if a dedicated-database-only model is adopted.
```

Conventions: numbered, immutable once accepted (a new ADR supersedes and links), stored in the repository (`docs/adr/`), one decision per record, a page or less, statuses (Proposed, Accepted, Deprecated, Superseded). Write ADRs for choices of language or framework, database, tenancy model, authentication approach, hosting platform, messaging technology, major library adoption, and any decision a new engineer would question. Part XV chapter 5 has more examples.

## Keeping designs and reality aligned

Designs drift from implementation. Mitigations: review the implemented system against the design before launch (a short "as-built" note of differences); keep the architecture diagram in the repository and update it in the pull request that changes the architecture; make ADRs part of the definition of done for significant changes; run a yearly architecture refresh that marks obsolete decisions as deprecated.

:::fde Design documents are client deliverables
Clients value a design they can read, review and keep, far more than they value the code they cannot. A design document with alternatives and ADRs is also the evidence that you considered their constraints, which protects everyone when a decision is questioned a year later. Write for the client's future engineers, who will inherit the system.
:::

## Common mistakes

- Designing in code first and writing the document to justify it.
- Alternatives that are strawmen.
- Review boards that veto on taste.
- Decisions made in chat and never recorded.
- ADRs that record the decision but not the context; a year later nobody knows whether the reasons still hold.
- Diagrams that show boxes but not failure modes, trust boundaries or data flows.

## Exercises

1. Write a design document for one component of a system you know, with two real alternatives and the cross-cutting concerns section; have two colleagues review it asynchronously with the checklist.
2. Write three ADRs for decisions already embedded in a system you work on (database choice, auth approach, hosting), reconstructing the context honestly.
3. Run a 30-minute architecture review of someone else's design using only the checklist questions; note which questions found real gaps.
