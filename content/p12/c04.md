# Technical Debt and Code Quality

:::objectives
- Define technical debt precisely, distinguish deliberate from accidental debt, and make it visible and prioritised like any other work.
- Apply code quality practices that matter in production codebases: readability, structure, consistency, automated checks and refactoring discipline.
- Argue for quality investments in business terms.
:::

:::prereq
[Software Development Lifecycle and Engineering Documentation](#/p01/c12).
:::

## What technical debt is

Ward Cunningham's metaphor: shipping code that is not quite right to learn faster is like borrowing money; the interest is the extra effort every later change costs; the principal is the work to fix it. Debt is not the same as bad code. **Deliberate, prudent debt** ("we will ship the simple version and refactor when we know the real access patterns") is a good decision when recorded and repaid. **Reckless debt** ("we don't have time for tests") and **accidental debt** (the framework we chose is now unmaintained; the domain changed and the model did not) accumulate silently until velocity collapses and incidents rise.

Debt shows up as: changes that touch many files for small features, fear of modifying certain modules, long onboarding, recurring incidents from the same component, inability to upgrade dependencies, manual steps in deployment, and tests that are slow or flaky.

## Making debt visible

Debt that lives in engineers' heads cannot be prioritised. Record it:

- A **debt register** (issues with a `tech-debt` label, or a section of the architecture document): what the debt is, where, why it exists, its interest (what it costs per month in time or risk), and the estimated principal (effort to fix).
- **Metrics** that correlate with debt: change failure rate, lead time for changes, time to onboard, dependency age, test duration and flakiness, code coverage trends, hotspots (files with high churn and high complexity).
- **Decision records** when debt is taken deliberately: an ADR stating the shortcut, the trigger for repayment and the owner.

```text
Debt: Orders module builds SQL by string concatenation (legacy)
Where: src/orders/repository.py (14 call sites)
Why: predates the ORM adoption; never migrated
Interest: every schema change requires manual edits in 14 places (~1 day each); SAST flags 14 findings we suppress; injection risk if a parameter is ever user-controlled
Principal: ~5 days to migrate to parameterised queries + tests
Trigger: next schema change touching orders, or before the security audit in Q1
Owner: orders team
```

## Prioritising repayment

Compare interest to principal and to the risk. Pay down debt that is in the path of planned work (you will be in that code anyway), that causes incidents, that blocks security updates, or whose interest exceeds its principal within a year. Leave alone debt in stable code nobody touches. Allocate a fixed share of capacity (commonly 15–25%) to debt and reliability, agreed with product so it is not negotiated every sprint; tie larger repayments to business outcomes ("migrating off the unmaintained framework unblocks the enterprise SSO feature and removes 12 unpatched vulnerabilities").

## Code quality that matters

Quality is not aesthetics; it is the properties that make code cheap to change safely:

- **Readability**: names that say what and why; functions that do one thing at one level of abstraction; comments explaining intent and constraints, not restating code; consistent formatting enforced by tools so reviews never discuss it.
- **Structure**: clear module boundaries with explicit dependencies; business logic separated from I/O (frameworks, databases, HTTP) so it can be tested in isolation; no circular dependencies; a dependency direction (domain ← application ← infrastructure).
- **Simplicity**: the simplest design that meets today's requirements with room to change; no speculative abstraction ("we might need to support five databases").
- **Explicit error handling**: errors propagate with context; no silent catches; failures are visible in logs and metrics ([Configuration Management and Error Handling](#/p03/c12)).
- **Consistency**: one way to do each common thing in a codebase (HTTP client, logging, config, DB access), documented in a short engineering guide.
- **Tests as documentation**: tests describe behaviour and run fast (chapter 5).
- **Dependencies**: few, maintained, pinned, updated routinely.

Automate everything that can be automated so humans review design and correctness: formatters (Black, Prettier, gofmt), linters (Ruff, ESLint, golangci-lint), type checkers (mypy/pyright, TypeScript strict), complexity and duplication reports, dependency update bots, pre-commit hooks mirroring CI.

```toml
# pyproject.toml: quality tooling as configuration, enforced in CI
[tool.ruff]
line-length = 100
target-version = "py312"
[tool.ruff.lint]
select = ["E", "F", "I", "B", "UP", "S", "C90", "N", "PL"]   # includes bandit-style security rules (S) and complexity (C90)
[tool.ruff.lint.mccabe]
max-complexity = 10

[tool.mypy]
strict = true
plugins = ["pydantic.mypy"]

[tool.pytest.ini_options]
addopts = "-q --strict-markers --cov=src --cov-fail-under=80"
```

## Refactoring discipline

Refactoring changes structure without changing behaviour. Rules that keep it safe: tests first (characterisation tests around legacy code before touching it); small steps committed separately from behaviour changes so reviewers can verify "no behaviour change"; the **boy scout rule** (leave the code a little better than you found it) for incremental improvement; **strangler fig** for large replacements (route new behaviour to the new implementation, migrate old behaviour piece by piece, delete the old when empty); feature flags to switch implementations and compare; never a "big rewrite" branch that lives for months (it rots, and the old system keeps changing underneath it).

## Dependency and platform debt

The most dangerous debt is often invisible in your code: an end-of-life runtime, a framework major version behind, a database engine version losing support, an operating system without patches. It accrues security risk and eventually blocks everything (the Lambda runtime deprecation in the small-client scenario). Track versions and end-of-life dates for every platform component; schedule upgrades before they become emergencies; keep upgrades small and frequent (one major version at a time) rather than rare and enormous.

## Arguing for quality

Engineers lose quality arguments when they argue aesthetics. Win them with: incident counts and costs tied to the component; lead-time data showing features in that area take three times longer; security findings that cannot be fixed without the refactor; the business feature the debt blocks; the risk of the end-of-life platform in the client's compliance language. Propose bounded investments with measurable outcomes ("two weeks to migrate the orders repository; success is zero suppressed SAST findings and schema changes in one place") rather than open-ended "cleanup".

:::fde Inherited systems
As an FDE you will inherit codebases you did not write, often with no tests and no documentation. Resist the urge to rewrite. Characterise first (what does it actually do? tests, logging, traces), stabilise (CI, pinned dependencies, monitoring), then improve incrementally in the path of the client's priorities. Document the debt register for the client; it is part of the honest picture of what they own.
:::

## Common mistakes

- Treating all old code as debt and all new code as quality.
- Debt that is never written down, so it is never prioritised.
- Refactoring mixed with feature changes in one pull request.
- Big-bang rewrites.
- Quality rules enforced by humans in review instead of by tools.
- Ignoring platform end-of-life until a forced upgrade breaks production.

## Exercises

1. Build a debt register for a codebase you work on: ten entries with location, interest, principal, trigger and owner; rank them.
2. Add formatter, linter, type checker and complexity limits to a project's CI; fix the baseline; measure review comment counts before and after for a month.
3. Plan a strangler-fig migration for one legacy module: the seam, the routing, the order of migration, the deletion criteria.
