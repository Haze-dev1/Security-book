# Production Change Management

:::objectives
- Treat every production change (code, infrastructure, configuration, data, access) as a managed event with a plan, a verification and a rollback.
- Classify changes by risk and apply proportionate controls: automated for routine, reviewed and scheduled for significant, formal for high-risk.
- Execute changes safely with pre-checks, communication, monitoring windows and clear abort criteria.
:::

## Most incidents are changes

Studies and postmortem collections agree: the majority of production incidents follow a change made by the operator (deploys, configuration, infrastructure, data fixes, access changes). Change management is the discipline of making changes in ways that make the resulting incidents rare, small and quickly reversed, without freezing the system into irrelevance.

## What counts as a change

Everything that alters production behaviour or risk: application deploys; infrastructure applies; configuration and feature flag changes; secret rotation; database migrations and manual data fixes; scaling actions beyond autoscaling; DNS and certificate changes; firewall, WAF and security group changes; IAM and access grants; third-party configuration (payment provider settings, IdP settings); dependency and base image updates; scheduled job changes. Teams that manage only deploys get surprised by the "small config tweak" that took the site down.

## Classify by risk

| Class | Examples | Controls |
|---|---|---|
| **Standard** (pre-approved, routine, low risk, proven procedure) | Application deploy through the pipeline; dependency patch bumps; scaling within limits; flag changes to internal users | Fully automated pipeline with tests, scans, progressive rollout and automatic rollback; logged; no per-change approval |
| **Normal** (planned, moderate risk) | Schema migration; infrastructure change to shared resources; new IAM role; WAF rule change; flag rollout to all users | Written change plan; peer review; approval by the service owner; scheduled in a window; monitoring during and after; rollback tested |
| **High-risk** (wide blast radius, hard to reverse) | Database engine major upgrade; Region failover; network re-architecture; identity provider migration; data migration of customer records | All of the above plus rehearsal in staging on realistic data; go/no-go meeting; named roles (executor, verifier, communicator); stakeholder notification; extended hypercare |
| **Emergency** (to resolve an incident) | Hotfix; rollback; blocking an attacker; emergency scaling | Fastest safe path with two people where possible; incident commander authorises; recorded in the incident timeline; retrospective review within a business day |

The classification is agreed in writing with any change board; standard changes are the goal for most work, achieved by making the pipeline trustworthy (Part X). Standard does not mean unreviewed: the code was reviewed; the *deployment* needs no additional approval.

## The change plan

For normal and high-risk changes, a one-page plan answers:

```checklist
# Change plan
- What is changing and why; ticket and design links
- Blast radius: which systems, tenants, users, regions are affected; what breaks if it goes wrong
- Pre-conditions: backups verified, staging rehearsal done, dependencies confirmed, quotas checked, on-call aware
- Steps: exact commands or pipeline actions, in order, with expected outcomes and durations
- Verification: what to check after each step and at the end (dashboards, probes, queries), with pass criteria
- Abort criteria: the specific signals that mean stop and roll back, decided before starting
- Rollback: exact steps and how long they take; tested where possible
- Communication: who is told before, during, after; status page needed?
- Schedule: window, duration, who is executing, who is verifying, who is reachable
- Post-change: monitoring period (hypercare), when the change is declared successful, record updated
```

Writing the abort criteria before executing is the single most valuable line: under pressure, people continue hoping; a pre-decided threshold ("error ratio above 1% for 3 minutes, or any customer-facing data mismatch") removes the hope.

## Windows, freezes and timing

Deploy when people are awake and traffic is representative but not peak: mid-morning on a weekday for most services, so problems are visible, responders are fresh and the day remains to fix things. Avoid late Friday for anything non-standard. **Change freezes** around critical business periods (Black Friday, financial year end, a client's regulatory deadline) are legitimate for normal and high-risk changes; standard changes with automatic rollback can often continue, which is the argument for making deploys standard. Freezes that last weeks accumulate risk (a huge batch of changes released at once); keep them short.

## Executing safely

- **Two people** for anything high-risk or manual: one executes, one verifies and reads the plan aloud. Pair on production consoles.
- **Announce** in the operations channel before starting, at milestones and at completion; include the rollback trigger so others know when to shout.
- **Use the pipeline, not the console**, even for emergencies where possible; if a manual action is unavoidable, record the exact command and reconcile code afterwards.
- **One change at a time** per system; concurrent changes make attribution impossible.
- **Watch the dashboards** actively through the monitoring window (30 minutes for normal changes, hours for high-risk); do not change and leave.
- **Protect against yourself**: `--dry-run` first; read the plan's destroy lines twice; type the environment name into a confirmation; production credentials in a visually distinct shell; deletion protection on data stores; peer review of every command that writes data.
- **Data changes** (manual UPDATE/DELETE) get special treatment: run the SELECT first and count the rows; wrap in a transaction and inspect before commit; back up affected rows to a table first; have the reverse script ready; prefer a reviewed script in the repository to typing in a console.

```sql
-- Manual data fix protocol
BEGIN;
-- 1. Preserve
CREATE TABLE fix_2026_11_01_invoices_backup AS
  SELECT * FROM invoices WHERE status = 'paid' AND paid_at IS NULL;
-- 2. Inspect the count; compare with the ticket's expectation (expected: 37 rows)
SELECT count(*) FROM fix_2026_11_01_invoices_backup;
-- 3. Change
UPDATE invoices SET paid_at = updated_at
  WHERE id IN (SELECT id FROM fix_2026_11_01_invoices_backup);
-- 4. Verify: same count, no unexpected rows touched
SELECT count(*) FROM invoices WHERE status = 'paid' AND paid_at IS NULL;   -- expect 0
-- 5. Commit only if everything matched; otherwise ROLLBACK
COMMIT;
```

## Recording and reviewing

Every change leaves a record: what, when, who, approval, outcome, link to plan and pipeline run (Part X chapter 9's deployment record covers standard changes automatically). Review change outcomes monthly: change failure rate (changes causing incidents or rollbacks), lead time, emergency change count. A rising failure rate for a class means its controls are inadequate; a high emergency count means planning is failing; a long lead time for standard changes means the pipeline needs investment.

:::fde Changes in client environments
Agree the change classes, windows and approvals with the client in writing before the first deploy; identify who at the client approves normal and high-risk changes and how fast they respond (a two-week approval turnaround changes your delivery plan). Never make a production change in a client's environment that they do not know about, however small; "we just tweaked a setting" is how trust ends.
:::

## Common mistakes

- Managing deploys but not configuration, access, data or vendor-console changes.
- Approval processes so slow that engineers batch changes into huge, risky releases or bypass the process.
- No abort criteria, so bad changes run to completion.
- Console changes during incidents never reconciled into code; the next apply reverts the fix.
- Manual data fixes without backup, count check or transaction.
- Friday evening deploys of non-standard changes.
- Change freezes that create release avalanches.
