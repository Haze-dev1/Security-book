# Code Review

:::objectives
- Review code for what matters (correctness, security, operability, design, clarity) efficiently and kindly.
- Write pull requests that are easy to review and get merged quickly.
- Set team norms that make review a fast, valued practice rather than a bottleneck or a battleground.
:::

:::prereq
[Git Workflows, Branching, Pull Requests and Releases](#/p01/c10); [Testing Strategies](#/p12/c05).

## What review is for

Code review catches defects a second pair of eyes sees, spreads knowledge of the codebase, enforces shared standards, and produces the "reviewed by someone other than the author" evidence compliance requires. It is not for style (tools do that), not for demonstrating seniority, and not for redesigning the feature after it is built (that was the design review).

## Reviewing: where to spend attention

Review in order of consequence:

1. **Does it do the right thing?** Compare against the ticket and the acceptance criteria. Does the change solve the stated problem, no more and no less? Are there unstated behaviour changes?
2. **Correctness**: edge cases, error paths, concurrency, transactions, nulls, off-by-one, time zones, idempotency. Read the tests first; what is not tested is what to scrutinise.
3. **Security**: new inputs validated? Authorisation checked on new endpoints? Secrets, logging of sensitive data, injection, deserialisation, SSRF, CSRF, dependency additions? The OWASP list in Part IV chapter 19 is a review checklist.
4. **Operability**: logging and metrics for the new path; feature flag for risky changes; migration safety (Part X chapter 8); configuration documented; failure modes handled; rollback possible.
5. **Design**: fits the module boundaries; no duplication of an existing capability; abstractions justified; dependency direction respected.
6. **Clarity**: will the next person understand this? Names, comments explaining why, function size.
7. **Tests**: present, meaningful, at the right level, and they would fail if the behaviour broke.

Read the whole change before commenting; look at the surrounding code, not just the diff; run it locally for anything non-trivial; check what the tests do not cover. Time-box: a 400-line review deserves 30–60 focused minutes; beyond about 400 lines, review quality collapses, so ask for a split.

## Writing review comments

Comments are read by a colleague who worked hard on this. Be specific, explain why, distinguish severity, and offer a path:

| Weak | Strong |
|---|---|
| "This is wrong." | "If `items` is empty, `max()` raises here; we hit this when a cart is cleared mid-checkout. Guard or use `default=`?" |
| "Why not use X?" | "nit: `dict.get` would avoid the try/except here; not blocking." |
| "Security issue." | "blocking: `user_id` comes from the query string and is used in the lookup without checking it matches the session user; this is an IDOR (Part IV ch. 7). Use `request.user.id`." |
| "Add tests." | "Could we add a test for the 500 EUR boundary? The spec says ≥ 500 goes to finance and I think this does >." |

Prefix severity: **blocking** (must change before merge), **suggestion** (would improve; author decides), **nit** (trivial; take or leave), **question** (I do not understand; not a request). Praise specific good decisions; it teaches as much as criticism. Never comment on the person.

Approve with "approve with nits" when only trivial items remain; do not hold a change hostage for preferences. If you disagree on design, discuss synchronously and record the outcome in the PR; long comment wars are a signal to talk.

## Writing reviewable pull requests

The author controls review speed more than the reviewer:

- **Small**: one logical change; under 400 lines of substantive diff; split refactors from behaviour changes and mechanical changes (renames, formatting) into separate PRs.
- **Described**: what and why; link to the ticket and design; how it was tested; screenshots for UI; a note on risk and rollback; what the reviewer should focus on; what is deliberately out of scope.
- **Self-reviewed**: read your own diff as a reviewer first; remove debugging leftovers; add comments where a reader would wonder.
- **Green**: CI passing before requesting review; a red PR wastes reviewer time.
- **Responsive**: answer every comment (fix, or explain and resolve by agreement); do not force-push over a reviewed history without telling the reviewer (it destroys their diff context); re-request review when ready.
- **Stacked** when a feature is large: a chain of small PRs each reviewable alone.

```markdown
## What
Route expense approvals ≥ 500 EUR to finance review instead of auto-approving (ticket EXP-412).

## Why
Policy change effective Dec 1; see design doc link. Threshold is configurable per tenant (default 500).

## How tested
- Unit: boundary at 499.99 / 500.00 / 500.01; currency conversion for non-EUR claims.
- Integration: finance queue receives the claim; notification not sent to finance for < 500.
- Manual: staging with tenant acme (threshold 300) — screenshots below.

## Risk / rollback
Behind flag `approvals.finance-threshold`; default off. Rollback = disable flag. No migration.

## Reviewer focus
The currency conversion path (uses the rate at submission time, not approval time — is that the intended policy?).
```

## Team norms

Agree and write down: review turnaround expectation (first response within a working day; small PRs within hours); who reviews what (CODEOWNERS for sensitive paths; otherwise anyone on the team, rotating so knowledge spreads); what blocks (correctness, security, operability, standards) and what does not (style preferences, alternative designs of equal merit); how to escalate disagreement (a 15-minute call, then the tech lead decides); that review is work counted in capacity, not a favour done between tasks; that tools handle formatting and linting so humans do not; and that pair programming or mob programming can replace review for some changes with the pairing recorded.

Measure: PR size, time to first review, time to merge, number of review rounds. Long cycle times usually mean PRs too large or reviewers too scarce; fix the system, not the people.

## Reviewing infrastructure and configuration

Terraform plans, workflow files, Kubernetes manifests and configuration changes deserve the same rigour with a different checklist: what does the plan destroy or recreate; what permissions does this role gain; is this secret handled correctly; what happens to running traffic during this change; is the change reversible; does it match the environment it claims to target. The plan output on the PR (Part X chapter 10) is the artefact to read.

## AI-assisted review and generation

Automated review assistants catch some bugs, suggest tests and summarise diffs usefully; they also produce confident, wrong comments and miss context. Treat their output as a first-pass checklist, never as the approval. Code generated with assistants is reviewed with *more* scrutiny, not less: it is fluent, so errors hide well, and the author may understand it less deeply than code they typed. The author remains accountable for every line they submit.

## Common mistakes

- Reviewing style instead of correctness; arguing about names while an IDOR ships.
- Thousand-line PRs that get a glance and an approve.
- Reviews as power: nitpicking to assert seniority; blocking on preference.
- Authors treating comments as attacks; reviewers writing them as attacks.
- Rubber-stamping to meet turnaround targets.
- Not reading the tests.

## Exercises

1. Review a real pull request using the ordered checklist; write comments with severity prefixes; time yourself and note where attention went.
2. Rewrite a past large PR description using the template; split it into a stack of reviewable PRs on paper.
3. Draft your team's review norms (turnaround, blocking criteria, escalation, measurement) in one page and get agreement.
