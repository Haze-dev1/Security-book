# Health Checks and Alerting Strategies

:::objectives
- Design liveness, readiness and startup checks and external probes that reflect real ability to serve, without causing cascading restarts.
- Build an alerting system that pages only for urgent, actionable, user-impacting conditions and routes everything else appropriately.
- Write alerts and runbooks together, and measure alert quality to fight fatigue.
:::

## Health checks: three different questions

| Check | Question | Who asks | On failure | Should check |
|---|---|---|---|---|
| **Startup** | Has the process finished initialising? | Orchestrator | Keep waiting (up to a limit), do not route traffic | Config loaded, migrations verified, caches warmed |
| **Liveness** | Is the process alive and not wedged? | Orchestrator | Restart the container | Only the process itself: event loop responsive, no deadlock. **Never** dependencies |
| **Readiness** | Can this instance serve requests right now? | Load balancer / orchestrator | Remove from rotation, keep running | Critical local dependencies (DB pool can connect), not yet overloaded, not draining |
| **External probe** | Does the service work for a user from outside? | Synthetic monitor | Alert | Full path: DNS, TLS, edge, auth, a real read operation |

:::danger Liveness checks that check the database
If liveness fails when the database is unreachable, every instance restarts at once during a database blip, the restart storm hammers the recovering database, and a one-minute incident becomes a thirty-minute one. Liveness is about the process; readiness is about dependencies.
:::

```python
# Readiness: cheap, bounded, honest
@app.get("/ready")
async def ready():
    if shutting_down:                       # set by SIGTERM handler: drain before exit
        return JSONResponse({"status": "draining"}, status_code=503)
    checks = {}
    try:
        await asyncio.wait_for(db.execute("SELECT 1"), timeout=1.0)
        checks["db"] = "ok"
    except Exception as e:
        checks["db"] = f"fail: {type(e).__name__}"
    status = 200 if all(v == "ok" for v in checks.values()) else 503
    return JSONResponse({"status": "ok" if status == 200 else "degraded", "checks": checks, "version": VERSION}, status_code=status)

@app.get("/live")
async def live():
    return {"status": "alive"}               # if this responds, the event loop works
```

Design notes: time-box every dependency check; make readiness reflect *this instance's* ability, not global health (if the database is down for everyone, failing readiness everywhere removes all instances and turns 500s into 503s from the load balancer, which may or may not be what you want: decide explicitly, and often prefer serving degraded responses while readiness stays up); never make checks expensive (they run every few seconds per instance); exclude them from access logs and traces; return the version for deploy verification; handle SIGTERM by failing readiness first, waiting for the load balancer to notice, then stopping.

Load balancer health checks (ALB target group) should hit readiness, with intervals and thresholds tuned for the deploy strategy: 10-second interval, 2 healthy / 3 unhealthy thresholds, and a deregistration delay long enough for in-flight requests.

## Synthetic monitoring

Internal checks cannot see DNS mistakes, expired certificates, broken CDN configuration or a WAF rule blocking everyone. Synthetic probes (CloudWatch Synthetics, Grafana synthetic monitoring, Checkly, Pingdom, Blackbox exporter from multiple Regions) exercise the user path: resolve, connect, TLS, log in with a synthetic account, perform a read, validate the content, and time it. Probe the critical journeys every minute from at least two locations; alert when two consecutive probes from two locations fail. Probes are also the only availability measure that works when your own infrastructure is down.

## Alerting philosophy

An alert is a request for a human's attention. Paging someone at 03:00 is expensive (sleep, health, retention) and, if the alert was not actionable, corrosive: the next page gets a slower response. Rules:

1. **Page on symptoms, not causes**: users cannot log in (symptom) rather than CPU is 90% (cause, maybe harmless). SLO burn-rate alerts are the canonical symptom alerts.
2. **Every page is urgent, actionable and has a runbook**: if the responder would reasonably do nothing until morning, it is a ticket, not a page.
3. **Alert on the absence of good**, not only the presence of bad: no traffic, no heartbeats, no completed jobs.
4. **One incident, one page**: group related alerts; inhibit downstream alerts when the upstream cause fires (database down inhibits "API error rate").
5. **Severity levels with defined response**: page (respond in minutes, 24×7), urgent ticket (same business day), ticket (this week), info (dashboard only). Three or four levels, not ten.
6. **Thresholds from SLOs and capacity, not from guesses**; `for` durations to avoid flapping; hysteresis where appropriate.
7. **Test alerts**: fire them deliberately in staging and during game days; an alert that has never fired is a hypothesis.

## Routing and on-call tooling

Alertmanager (or the alerting features of Grafana, CloudWatch with SNS, or an incident platform such as PagerDuty, Opsgenie, incident.io) handles **grouping** (one notification for many firing alerts with the same labels), **inhibition**, **silences** (planned maintenance) and **routing** by labels to the right team and channel: pages to the on-call schedule with escalation if unacknowledged; tickets to the team's queue; informational alerts to a channel nobody is obliged to read.

```yaml
# alertmanager.yml (excerpt)
route:
  receiver: default-slack
  group_by: [alertname, service, env]
  group_wait: 30s
  group_interval: 5m
  repeat_interval: 4h
  routes:
    - matchers: [severity="page", env="production"]
      receiver: pagerduty-portal
      continue: true                       # also post to Slack
    - matchers: [severity="page", env="production"]
      receiver: slack-incidents
    - matchers: [severity="ticket"]
      receiver: jira-portal
inhibit_rules:
  - source_matchers: [alertname="DatabaseDown"]
    target_matchers: [alertname=~"PortalHighErrorRate|PortalHighLatency"]
    equal: [env]
receivers:
  - name: pagerduty-portal
    pagerduty_configs: [{ routing_key_file: /etc/alertmanager/pd-key, severity: critical }]
  - name: slack-incidents
    slack_configs: [{ api_url_file: /etc/alertmanager/slack-url, channel: "#incidents", send_resolved: true }]
  - name: jira-portal
    webhook_configs: [{ url: https://hooks.acme.example/jira }]
  - name: default-slack
    slack_configs: [{ api_url_file: /etc/alertmanager/slack-url, channel: "#portal-alerts" }]
```

## Alert and runbook, written together

An alert definition is incomplete without the runbook it links to. The runbook answers, in order: what this alert means for users; how to confirm it is real (dashboard links, queries); the likely causes in order of frequency; the exact mitigation steps for each, with commands; when and how to escalate; how to verify recovery; what to record. Keep runbooks in the repository next to the alert rules, reviewed in the same pull request, and test them during game days.

@file: docs/runbooks/portal/high-error-rate.md (excerpt)
```markdown
# PortalHighErrorRate

**User impact**: a portion of API requests fail with 5xx. Customers see errors on page loads or actions.

## Confirm
- Dashboard: Portal › Service (link) — error ratio panel and version annotation.
- Is it one route or all? `sum by (route) (rate(http_requests_total{service="portal-api",status_class="5xx"}[5m]))`
- Did a deploy happen in the last 30 minutes? Check the #releases channel / deployment records.

## Likely causes and actions
1. **Bad deploy** (most common): roll back — `gh workflow run deploy.yml -f env=production -f digest=<previous>` or wait for CodeDeploy automatic rollback. Verify error ratio falls within 5 minutes.
2. **Database saturation**: RDS dashboard — CPU, connections, lock waits. Kill long queries via the runbook `db-long-queries.md`. Scale if sustained.
3. **Downstream dependency** (payments, identity): check their status pages and our dependency panel. Enable the degradation flag `payments.offline-mode`.
4. **Traffic spike / attack**: WAF dashboard. Apply the rate-limit rule `emergency-rate-limit`.

## Escalate
- Not resolved in 20 minutes or customer-visible data issues: page the incident commander (`/ic page`).

## Verify and record
- Error ratio below 0.5% for 10 minutes; synthetic probes green.
- Record timeline in the incident channel; open a postmortem if SLO budget consumed > 5%.
```

## Measuring alert quality

Track per alert: fires per month, percentage acknowledged with action taken, percentage resolved as "no action needed", mean time to acknowledge, pages outside business hours. Review monthly: delete or demote alerts that are mostly noise; add `for` durations or better thresholds; convert cause-based alerts to symptom-based. A healthy on-call rotation sees a handful of pages per week, each meaningful. If responders are getting ten pages a night, the alerting system is the incident.

## Common mistakes

- Liveness checks that include dependencies (restart storms).
- Readiness checks that always return 200 (deploys roll broken versions out).
- Paging on CPU, memory or disk thresholds with no user impact.
- No alert for "service silent" or "certificate expiring".
- Alerts without runbooks; runbooks without alerts linking to them.
- Alert destinations that are a person's email or a departed engineer's phone (the small-client case study).
- Silences created and never expired.
