## Prometheus model

Prometheus **scrapes** HTTP endpoints (`/metrics`) on a schedule (15–60 s), stores samples locally as time series identified by metric name and label set, and evaluates **recording rules** (precomputed queries) and **alerting rules** (conditions that fire alerts to Alertmanager). Targets are discovered dynamically (Kubernetes, EC2, ECS, Consul, file). Long-term and multi-cluster storage comes from Thanos, Cortex/Mimir or Amazon Managed Prometheus via remote write.

```yaml
# prometheus.yml (excerpt)
global: { scrape_interval: 30s, evaluation_interval: 30s }
scrape_configs:
  - job_name: kubernetes-pods
    kubernetes_sd_configs: [{ role: pod }]
    relabel_configs:
      - source_labels: [__meta_kubernetes_pod_annotation_prometheus_io_scrape]
        action: keep
        regex: "true"
      - source_labels: [__meta_kubernetes_pod_label_app]
        target_label: service
      - source_labels: [__meta_kubernetes_pod_label_version]
        target_label: version
rule_files: [rules/*.yml]
alerting:
  alertmanagers: [{ static_configs: [{ targets: ["alertmanager:9093"] }] }]
remote_write:
  - url: https://aps-workspaces.eu-west-1.amazonaws.com/workspaces/ws-123/api/v1/remote_write
    sigv4: { region: eu-west-1 }
```

Exporters expose metrics for things that do not speak Prometheus natively: `node_exporter` (hosts), `postgres_exporter`, `redis_exporter`, `blackbox_exporter` (probes), `cloudwatch_exporter`/YACE (AWS metrics), `kube-state-metrics` (Kubernetes objects).

## PromQL that is actually correct

```text
# Request rate per service (per second, averaged over 5m)
sum by (service) (rate(http_requests_total[5m]))

# Error ratio per service: 5xx over all
sum by (service) (rate(http_requests_total{status_class="5xx"}[5m]))
  / sum by (service) (rate(http_requests_total[5m]))

# p95 latency per route from a histogram (server-side quantile over aggregated buckets)
histogram_quantile(0.95,
  sum by (le, route) (rate(http_request_duration_seconds_bucket[5m])))

# Saturation: CPU utilisation per pod against its limit
sum by (pod) (rate(container_cpu_usage_seconds_total{container!=""}[5m]))
  / sum by (pod) (kube_pod_container_resource_limits{resource="cpu"})

# Queue backlog growing: positive derivative over 10 minutes
deriv(jobs_queue_depth[10m]) > 0 and jobs_queue_depth > 1000

# Disk full prediction: will be full within 4 hours at the current rate
predict_linear(node_filesystem_avail_bytes{mountpoint="/data"}[1h], 4*3600) < 0

# Availability SLI over 30 days (good requests / all requests)
1 - (sum(increase(http_requests_total{status_class="5xx"}[30d])) / sum(increase(http_requests_total[30d])))
```

Rules of thumb: `rate()` for counters over a window at least 4× the scrape interval; never `rate()` a gauge; aggregate buckets with `sum by (le, ...)` *before* `histogram_quantile`; `increase()` for counts over a window; `avg` of percentiles is meaningless; `absent()` to alert when a metric disappears (the service stopped reporting is often the real incident); recording rules for anything used in dashboards and alerts so they are cheap and consistent.

```yaml
# rules/portal.yml: recording and alerting rules
groups:
  - name: portal.slo
    rules:
      - record: service:http_requests:rate5m
        expr: sum by (service) (rate(http_requests_total[5m]))
      - record: service:http_errors:ratio_rate5m
        expr: sum by (service) (rate(http_requests_total{status_class="5xx"}[5m])) / sum by (service) (rate(http_requests_total[5m]))
      - alert: PortalHighErrorRate
        expr: service:http_errors:ratio_rate5m{service="portal-api"} > 0.02
        for: 5m
        labels: { severity: page, team: portal }
        annotations:
          summary: "portal-api 5xx ratio {{ $value | humanizePercentage }} for 5m"
          runbook_url: https://runbooks.acme.example/portal/high-error-rate
      - alert: PortalNoTraffic
        expr: absent(service:http_requests:rate5m{service="portal-api"}) or service:http_requests:rate5m{service="portal-api"} < 0.1
        for: 10m
        labels: { severity: page, team: portal }
        annotations: { summary: "portal-api is receiving no traffic or not reporting" }
```

## Grafana

Grafana queries Prometheus, CloudWatch, Loki, Tempo, Elasticsearch and SQL databases in one place. Dashboards are JSON and belong in git, provisioned by the deployment (Grafana provisioning, Terraform provider or the Grafana Operator), not hand-edited in production. Use **variables** (`$service`, `$env`, `$region`) so one dashboard serves every service, and **links** from panels to traces and logs filtered by time range and labels.

A service dashboard that helps at 03:00 has, top to bottom:

1. **Header**: deployed version(s), active alerts, error budget remaining.
2. **Golden signals**: request rate, error ratio, p50/p95/p99 latency, saturation (CPU, memory, connections, queue depth), each as a time series with the SLO threshold drawn.
3. **Dependencies**: latency and error rate per downstream (database, cache, external APIs).
4. **Resources**: pods/tasks running vs desired, restarts, throttling, disk.
5. **Business**: orders per minute, logins per minute, whatever reveals user impact fastest.
6. **Logs panel** (Loki/CloudWatch) filtered to errors for the selected service and time.

Dashboards for different audiences: an **overview** per system (one row per service, status-coloured), **service** dashboards for on-call, **SLO** dashboards for the error budget conversation, and **capacity** dashboards for planning. Avoid pie charts, gauges without thresholds, and panels nobody has looked at in 90 days (Grafana reports usage).

:::tip Design dashboards for the question, not the data
During an incident the question is "is it us, is it a dependency, is it the platform, and when did it start?" A dashboard that answers those four in one screen with a version-change annotation overlay is worth fifty panels of everything.
:::

## CloudWatch

CloudWatch is the native sink for AWS service metrics (ALB request counts and 5xx, RDS CPU and connections, SQS queue age, Lambda errors and durations, ECS CPU/memory) and is the only source for many of them. Use it for:

- **AWS service metrics and alarms**: ALB `HTTPCode_Target_5XX_Count`, `TargetResponseTime` p95 via extended statistics, RDS `FreeStorageSpace`, SQS `ApproximateAgeOfOldestMessage`.
- **Composite alarms** to reduce noise (page only if both error rate *and* request count are abnormal).
- **Logs Insights** queries over structured JSON logs; **metric filters** to derive metrics from logs; **Embedded Metric Format** for high-cardinality-free custom metrics from Lambda.
- **Synthetics canaries** that probe endpoints from outside; **RUM** for browser-side latency.
- **Container Insights** for ECS/EKS resource metrics.

Costs: custom metrics are priced per metric per month and per API call; high-cardinality dimensions bill like Prometheus cardinality hurts. Alarms, dashboards and Logs Insights scans all cost; set log retention and use metric filters rather than scanning logs repeatedly. Grafana reads CloudWatch directly, so one dashboard can mix Prometheus application metrics with CloudWatch infrastructure metrics.

```hcl
# Terraform: the ALB 5xx alarm that pages and triggers CodeDeploy rollback
resource "aws_cloudwatch_metric_alarm" "alb_5xx_ratio" {
  alarm_name          = "portal-prod-alb-5xx-ratio"
  comparison_operator = "GreaterThanThreshold"
  evaluation_periods  = 3
  datapoints_to_alarm = 2
  threshold           = 2        # percent
  treat_missing_data  = "notBreaching"
  alarm_actions       = [aws_sns_topic.pager.arn]
  ok_actions          = [aws_sns_topic.pager.arn]

  metric_query {
    id          = "ratio"
    expression  = "IF(req > 10, 100 * err / req, 0)"   # ignore tiny traffic
    label       = "5xx %"
    return_data = true
  }
  metric_query {
    id = "err"
    metric { namespace = "AWS/ApplicationELB", metric_name = "HTTPCode_Target_5XX_Count", period = 60, stat = "Sum"
             dimensions = { LoadBalancer = aws_lb.main.arn_suffix } }
  }
  metric_query {
    id = "req"
    metric { namespace = "AWS/ApplicationELB", metric_name = "RequestCount", period = 60, stat = "Sum"
             dimensions = { LoadBalancer = aws_lb.main.arn_suffix } }
  }
}
```

Whatever the choice, keep instrumentation on OpenTelemetry and Prometheus formats so the backend can change.

## Common mistakes

- `rate()` windows shorter than two scrape intervals (gaps, zeros).
- Averaging percentiles across instances.
- Dashboards edited by hand in production and lost on upgrade.
- Alerts on raw CPU rather than on user-facing symptoms (chapter 5).
- Missing `absent()` alerts, so a dead service looks like a quiet one.
- Unbounded CloudWatch custom metric dimensions driving the bill.
