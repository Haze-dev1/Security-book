# Backup Verification, Disaster Recovery Testing, RPO and RTO

:::objectives
- Define recovery point and recovery time objectives per system from business impact, and design backups and recovery to meet them.
- Verify backups by restoring them, automatically and regularly, and test disaster recovery end to end.
- Protect backups from the failures and attackers that destroy primary data.
:::

## RPO and RTO from business impact

- **RPO (recovery point objective)**: the maximum acceptable data loss, measured as time. RPO of 1 hour means you may lose up to an hour of changes. Determined by how much work users can redo and how much data the business can lose legally and commercially.
- **RTO (recovery time objective)**: the maximum acceptable time to restore service after a disaster. Determined by cost of downtime per hour.

Both come from a **business impact analysis**, not from engineering preferences: what does an hour of lost orders cost? Can support staff re-enter data? Are there regulatory limits? Then the architecture follows:

| RPO | Mechanism |
|---|---|
| 24 h | Nightly snapshots |
| 1 h | Hourly snapshots or continuous log shipping with hourly checkpoints |
| 5 min | Continuous WAL archiving / PITR (RDS gives 5-minute RPO) |
| Seconds | Synchronous or near-synchronous replication (Multi-AZ, Aurora Global) |
| Zero | Synchronous replication with write acknowledgement from a second site; costly and latency-bound |

| RTO | Mechanism |
|---|---|
| Days | Rebuild from documentation (hope) |
| Hours | Restore from backup into infrastructure created by IaC |
| 15–60 min | Warm standby: infrastructure running at low capacity, data replicated, scripted promotion and DNS switch |
| Minutes | Hot standby or active-active with automated failover |

Document RPO and RTO per system in the production readiness review; the numbers drive cost and design, and they are what a client is really asking when they say "we need backups".

## What must be backed up

Everything required to rebuild service, not just the main database: databases (all of them, including the ones the team forgot: the auth service's, the queue broker's state), object storage (versioning plus replication; S3 is durable against hardware loss but not against deletion or bugs), configuration and secrets (Secrets Manager replication, Parameter Store exports), infrastructure definitions (git, which itself needs a backup outside the primary code host), container images (registry replication), DNS zone data, certificates and keys (KMS multi-Region keys; without the key, encrypted backups are noise), identity configuration (IdP settings, user directories), CI/CD configuration, and runbooks (readable when everything else is down: printed or in a separate account).

## Backup properties

- **Automated**: schedules in AWS Backup or native service features; never a human remembering.
- **Isolated**: copies in a separate AWS account (backup vault with cross-account copy) so that a compromised production account or a wrong `terraform destroy` cannot delete them; vault lock (WORM) for ransomware resistance.
- **Encrypted** with keys the backup account controls.
- **Multiple generations**: the 3-2-1 rule still applies (three copies, two media or accounts, one off-site or off-Region); retention tiers (daily for 35 days, weekly for a year, monthly for seven years as required).
- **Cross-Region** copies for Regional disasters, with the same isolation.
- **Monitored**: a backup job that fails silently for months is the classic finding; alert on job failure *and* on job absence.
- **Application-consistent**: for databases, use native mechanisms (snapshots with WAL, `pg_dump` in a consistent transaction) rather than copying files under a running database.

```hcl
# AWS Backup: plan with cross-account, cross-Region copies and vault lock
resource "aws_backup_vault" "primary" {
  name        = "portal-prod"
  kms_key_arn = aws_kms_key.backup.arn
}

resource "aws_backup_vault_lock_configuration" "primary" {
  backup_vault_name   = aws_backup_vault.primary.name
  changeable_for_days = 3            # after this, the lock is immutable (compliance mode)
  min_retention_days  = 35
  max_retention_days  = 2555
}

resource "aws_backup_plan" "portal" {
  name = "portal-prod"
  rule {
    rule_name         = "daily"
    target_vault_name = aws_backup_vault.primary.name
    schedule          = "cron(0 2 * * ? *)"
    lifecycle { delete_after = 35 }
    copy_action {
      destination_vault_arn = "arn:aws:backup:eu-central-1:210987654321:backup-vault:portal-dr"  # other account, other Region
      lifecycle { delete_after = 365 }
    }
  }
  rule {
    rule_name         = "monthly-archive"
    target_vault_name = aws_backup_vault.primary.name
    schedule          = "cron(0 3 1 * ? *)"
    lifecycle { cold_storage_after = 30, delete_after = 2555 }
  }
}

resource "aws_backup_selection" "tagged" {
  name         = "portal-prod-tagged"
  plan_id      = aws_backup_plan.portal.id
  iam_role_arn = aws_iam_role.backup.arn
  selection_tag { type = "STRINGEQUALS", key = "Backup", value = "true" }
}
```

## Verification: a backup is a hypothesis until restored

A backup you have not restored is not a backup. Verification is automated and continuous:

```flow
{
  "title": "Automated restore test (weekly)",
  "participants": ["Scheduler","Restore job","Temporary DB","Verifier","Report"],
  "steps": [
    {"from":"Scheduler","to":"Restore job","label":"trigger (EventBridge, Sunday 03:00)","detail":"Runs in the backup or a dedicated test account with least privilege: read backups, create temporary resources in an isolated VPC."},
    {"from":"Restore job","to":"Temporary DB","label":"restore latest snapshot / PITR to T-1h","detail":"Measure elapsed time: this is your empirical RTO component. Alert if it exceeds the plan."},
    {"from":"Verifier","to":"Temporary DB","label":"integrity and content checks","detail":"Schema version matches expected; row counts within tolerance of production metrics; checksums of reference tables; a sample of recent records present (proves RPO); application smoke test against the restored database with a test build."},
    {"from":"Verifier","to":"Report","label":"result, duration, data age","detail":"Written to a dashboard and the compliance evidence store; failure pages the owning team."},
    {"from":"Restore job","to":"Temporary DB","label":"destroy","detail":"Always, even on failure, with a safety net that deletes stragglers tagged restore-test older than a day."}
  ]
}
```

For object storage, verify by sampling objects from the replica and comparing checksums; for configuration and IaC, verify by building an environment from scratch in a sandbox account (which is also a DR test). Keep the verification result for auditors: dated proof that backups restore.

## Disaster recovery testing

A DR plan that has not been exercised will fail in ways nobody predicted: a hard-coded Region, a secret that was never replicated, a DNS TTL of 24 hours, a runbook step that requires the person who left. Test at increasing levels of realism:

1. **Tabletop**: walk through the plan with the team; find missing steps and dependencies.
2. **Component restore**: the automated restore test above; restore a single service into the DR Region.
3. **Partial failover**: move one non-critical service to the DR Region and serve real traffic for a day.
4. **Full failover exercise**: fail the whole system over in a maintenance window (or, for active-active, drain a Region); measure RTO and RPO; fail back.
5. **Unannounced game day**: for mature organisations, simulate a Regional outage without warning to responders (with leadership approval and a stop button).

Record every exercise: date, scope, measured RTO/RPO, what broke, actions. Regulators in finance and healthcare expect at least annual full tests with evidence.

## Recovering from the right disaster

Different disasters need different recoveries; plan for each:

| Disaster | Recovery path | Notes |
|---|---|---|
| Hardware / AZ loss | Multi-AZ failover, automatic | Minutes; RPO ≈ 0 |
| Region loss | Promote DR Region: data, compute, DNS | Rehearsed; RTO per plan |
| Accidental deletion or bad migration | PITR to just before the event, into a side database; copy affected data back | Do not overwrite the live database wholesale if other data changed since; surgical restore |
| Data corruption by application bug | Identify start time from logs; PITR before; replay or reconcile good writes | The hardest case; needs audit logs to know what changed |
| Ransomware / account compromise | Restore from isolated, vault-locked backups into a clean account; rotate everything; forensics on the old account | Isolation and immutability are what make this possible |
| Loss of the cloud account itself | Cross-account backups, IaC in git outside the account, documented rebuild | Rare but catastrophic; the backup account must have different credentials and owners |

## Common mistakes

- Backups in the same account as production, deletable by the same credentials.
- Never restoring; discovering at the worst moment that the snapshots are of the wrong database or that the encryption key was deleted.
- RPO/RTO never agreed with the business; engineering assumes nightly is fine while the business assumes nothing is ever lost.
- Backing up the database but not the object storage, secrets or configuration needed to use it.
- DNS TTLs and hard-coded endpoints that make failover take hours.
- Restoring over the live database and destroying the changes made since the incident.
