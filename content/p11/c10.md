# Production Incident Scenarios

:::objectives
- Practise diagnosing and mitigating realistic production incidents using the signals, tools and process from this part.
- Build the habit of forming hypotheses from evidence, choosing reversible mitigations first, and verifying from the user's perspective.
- Recognise the recurring shapes of incidents so the next unfamiliar one feels familiar.
:::

:::prereq
All previous chapters of this part; Parts V–X for the systems involved.
:::

## How to use this chapter

Each scenario presents the situation as an on-call engineer would see it. Work through the prompts before revealing; write down your hypothesis and your next command. The reveal gives one reasonable path, not the only one. In every scenario, keep the loop from chapter 6: what is the user impact, when did it start, what changed, how do we stop the bleeding, how do we confirm.

## Scenario 1: the slow Monday

```scenario
{
  "title": "p95 latency tripled since 08:30; no deploy today",
  "context": "Monday 09:10. PortalHighLatency is firing: p95 for /api/* went from 220 ms to 700 ms starting about 08:30. Error rate is normal. No deployments since Friday. Traffic is normal for a Monday.",
  "steps": [
    {"prompt": "No deploy and normal traffic. Where do you look first?", "reveal": "Dependencies and the database. The service dashboard's dependency panel shows PostgreSQL query latency up from 8 ms to 60 ms; everything else flat. Traces for slow requests confirm the database span dominates. Hypothesis: database-side change: plan regression, lock contention, missing index after data growth, or a background job."},
    {"prompt": "RDS: CPU 85% (normally 30%), read IOPS high, no lock waits. What now?", "reveal": "Performance Insights shows top wait events are I/O with one query dominating: a report query hitting the orders table with a sequential scan. pg_stat_statements confirms this query's mean time jumped. Nothing deployed, so why? Check whether autovacuum/analyze ran: a table that crossed a size threshold over the weekend (a bulk import Sunday night) caused the planner to switch from an index scan to a sequential scan because statistics were stale."},
    {"prompt": "Mitigation?", "reveal": "Run ANALYZE on the table (seconds, safe) to refresh statistics; latency drops within a minute as new plans are chosen. If it had not, options: kill the report job (feature kill switch), add the missing index CONCURRENTLY, or scale the instance temporarily. Verify p95 back to baseline and probes green."},
    {"prompt": "Postmortem factors?", "reveal": "Bulk import did not run ANALYZE afterwards; autovacuum thresholds too coarse for a fast-growing table; no alert on sequential scans or plan changes; the report query lacked an index all along and was saved by small data. Actions: ANALYZE in the import job, per-table autovacuum settings, index, and a slow-query alert."}
  ]
}
```

## Scenario 2: the deploy that passed

```scenario
{
  "title": "Error rate climbing 25 minutes after a successful canary",
  "context": "14:40. Deploy of version 5.12 finished at 14:10; canary analysis passed; 100% traffic since 14:15. At 14:35 PortalHighErrorRate fires: 3% 5xx and rising. Errors are 'connection pool exhausted' in logs.",
  "steps": [
    {"prompt": "First action?", "reveal": "Roll back. The deploy is the obvious change; the rollback is one command and reversible. Do it before understanding why; investigate from logs and traces afterwards. Announce in the incident channel."},
    {"prompt": "Rollback complete at 14:44; errors fall. Why did the canary pass?", "reveal": "Pool exhaustion is cumulative: a connection leak (a code path that acquires a connection and never returns it on an exception) takes time to drain the pool. The 5-minute canary at 10% traffic never reached the limit. Traces of errored requests before rollback show a new endpoint whose span ends with an exception after the DB span started."},
    {"prompt": "What changes beyond fixing the leak?", "reveal": "Add pool-utilisation metric and alert at 80%; make canary analysis include pool saturation and run longer (or require soak time at 100% with automatic rollback still armed); add a linter or wrapper making connection release structural (context managers) rather than manual."}
  ]
}
```

## Scenario 3: the silent queue

```scenario
{
  "title": "Customers report emails not arriving; no alerts fired",
  "context": "Tuesday 11:00. Support escalates: multiple customers have not received order confirmation emails since this morning. Dashboards show the API healthy. No alerts.",
  "steps": [
    {"prompt": "Why no alerts, and where do you look?", "reveal": "Asynchronous work is invisible to request-path SLIs. Check the queue: SQS ApproximateAgeOfOldestMessage is 3 hours and growing; ApproximateNumberOfMessagesVisible is 40,000. The email worker is not consuming. There was no alert on queue age, only on API errors."},
    {"prompt": "Why is the worker not consuming?", "reveal": "ECS shows the worker service with 0 running tasks and repeated task failures: 'secret not found'. CloudTrail shows the email provider secret was rotated at 07:50 by the automatic rotation Lambda, and the worker task definition references the secret by a version stage that the rotation did not update (a misconfigured rotation). Tasks crash on start and the service keeps retrying."},
    {"prompt": "Mitigation and recovery?", "reveal": "Fix the secret reference (or restore the previous version as AWSCURRENT), redeploy the worker; it drains the backlog. Watch for the provider's rate limits as 40,000 emails go out at once: throttle the worker concurrency so the provider does not block you. Consider whether 3-hour-old confirmations should still be sent (yes, with correct timestamps) and whether any messages went to the DLQ."},
    {"prompt": "What was missing?", "reveal": "Alerts on queue age and DLQ depth; an alert on ECS services with desired > running for more than 5 minutes; a test of secret rotation in staging; and a business SLI for 'confirmation emails sent within 5 minutes of order'."}
  ]
}
```

## Scenario 4: the certificate

```scenario
{
  "title": "All synthetic probes red at 00:02; internal checks green",
  "context": "Just after midnight. External probes fail with TLS errors from every location. The application dashboards show no traffic at all since 00:00 but no errors. ALB healthy.",
  "steps": [
    {"prompt": "TLS errors from outside, nothing inside. Hypothesis?", "reveal": "An expired certificate at the edge, or a DNS change. openssl s_client -connect portal.example:443 -servername portal.example shows 'certificate has expired' with a notAfter of today 00:00. The certificate on CloudFront was imported manually a year ago (not ACM-issued) and never renewed; the expiry alarm existed but was on the ACM-issued ALB cert, not the imported CloudFront one."},
    {"prompt": "Fix at 00:10?", "reveal": "Fastest: request an ACM certificate with DNS validation (minutes if the zone is in Route 53), attach it to the CloudFront distribution; propagation takes 5–15 minutes. Alternative: renew with the external CA and import. Communicate on the status page. Verify with probes from multiple locations and the openssl check."},
    {"prompt": "Prevention?", "reveal": "Use ACM-managed certificates everywhere possible (auto-renew); inventory every certificate (ACM, imported, on servers, in clients) with expiry monitoring 30 and 7 days out; a synthetic probe that checks days-to-expiry; forbid manual certificate imports without a renewal owner."}
  ]
}
```

## Scenario 5: the Region is fine, the account is not

```scenario
{
  "title": "Unusual API calls and a disabled CloudTrail",
  "context": "Thursday 03:20. GuardDuty: 'UnauthorizedAccess:IAMUser/InstanceCredentialExfiltration.OutsideAWS' and a CloudTrail finding that logging was stopped in us-east-1. The service is up and healthy.",
  "steps": [
    {"prompt": "What kind of incident is this and what is your first step?", "reveal": "A security incident, probably credential theft from an EC2 instance (SSRF to the metadata endpoint or a compromised host) followed by use from outside AWS. Declare a SEV1 security incident; engage the security lead; preserve evidence (do not terminate the instance; snapshot it; keep logs). Then contain: revoke the compromised role's sessions (attach a deny-all policy or use IAM's revoke sessions), rotate the credentials, re-enable CloudTrail, and check the organisation trail (which the attacker could not disable) for what they did."},
    {"prompt": "The organisation trail shows ListBuckets, GetObject on a backup bucket, and CreateUser attempts (denied by SCP). Next?", "reveal": "Assess data exposure: which objects were read, what they contained, whether encryption with a key the attacker could not use applied (it did not for that bucket: SSE-S3). Likely a reportable breach; involve legal and the client. Isolate the instance (security group with no egress), image it for forensics, find the entry point (application logs show SSRF attempts hours earlier against an 'import from URL' feature). Rotate every secret the role could reach."},
    {"prompt": "What made this contained rather than catastrophic?", "reveal": "IMDSv2 was not enforced on that instance (the gap); but SCPs blocked user creation and trail deletion at the organisation level, GuardDuty detected exfiltration quickly, and backups were in another account. Actions: enforce IMDSv2 everywhere, fix the SSRF (Part IV chapter 12), least-privilege the instance role, KMS encryption with restrictive key policies on sensitive buckets, and an incident runbook for credential theft."}
  ]
}
```

## Scenario 6: the slow leak

```scenario
{
  "title": "Tasks restart every ~6 hours; no user-visible impact yet",
  "context": "A ticket, not a page: ECS tasks for the API have been OOM-killed and restarted roughly every six hours for a week. Each restart causes a few seconds of errors. Memory climbs linearly after each start.",
  "steps": [
    {"prompt": "Approach?", "reveal": "A memory leak introduced recently; check which version started it from the deployment records versus the restart pattern (continuous profiling makes this a diff of heap profiles between versions). Take a heap snapshot at 2 hours and at 5 hours from one task and compare retained objects."},
    {"prompt": "The heap shows millions of entries in an in-process cache keyed by request ID. Cause?", "reveal": "A developer added a memoisation cache keyed on a per-request value, so it never hits and never evicts. Fix: bounded cache with TTL or correct key. Mitigation meanwhile: increase memory limit and schedule restarts (ugly but safe), or roll back if the version is recent."},
    {"prompt": "Why did nobody notice for a week?", "reveal": "Restarts were treated as noise; no alert on restart count; the brief error spikes were within budget. Actions: alert on restart rate, memory trend alerts (predict_linear to limit), and a check in review guidelines for unbounded caches."}
  ]
}
```

## Scenario 7: thundering retry

```scenario
{
  "title": "A 30-second dependency blip became a 40-minute outage",
  "context": "The payment provider had a 30-second outage at 16:00. Your checkout service's error rate stayed at 60% until 16:40, long after the provider recovered. Tasks were at 100% CPU.",
  "steps": [
    {"prompt": "What pattern is this?", "reveal": "A retry storm and cascading failure. During the blip, every checkout request retried three times with no backoff and no circuit breaker; queued requests piled up; when the provider recovered, the backlog plus live traffic plus retries exceeded capacity; timeouts caused more retries. Tasks saturated on CPU; health checks failed; restarts made it worse. See Resilience Patterns (Part IX chapter 8)."},
    {"prompt": "How do you break the loop live?", "reveal": "Shed load: enable the payments degradation flag (accept orders as 'payment pending'), or temporarily reduce traffic at the edge with a rate limit; scale out; let the backlog drain. Avoid restarting everything at once."},
    {"prompt": "Fixes?", "reveal": "Exponential backoff with jitter and a retry budget; circuit breaker on the provider client with a fallback; bounded concurrency and queue length for outbound calls; timeouts shorter than the caller's; load shedding when saturated; chaos test the dependency outage in staging."}
  ]
}
```

## Patterns to recognise

| Shape | Signature | First move |
|---|---|---|
| Bad deploy | Errors or latency within minutes of a release | Roll back |
| Resource exhaustion | Linear climb then cliff (connections, memory, disk, file handles) | Add headroom or restart safely; find the leak |
| Dependency failure | One downstream span slow or erroring; everything else fine | Degrade, circuit-break, inform |
| Data growth / plan change | Gradual latency growth, no deploy, DB CPU or I/O | ANALYZE, index, archive |
| Configuration / secret change | Sudden failures at a rotation or config push time | Revert the change |
| Expiry | Fails at midnight or on a round date; TLS, tokens, licences, domains | Renew; then inventory everything that expires |
| Capacity | Correlates with traffic; queueing latency; autoscaling lag | Scale; shed; raise quotas |
| Retry storm | Recovery slower than the cause; CPU saturated; error rate stuck | Shed load, backoff, breaker |
| Silent async failure | Queue age growing; users notice before monitoring | Fix consumer; alert on age and DLQ |
| Security | Unusual API calls, disabled logging, new principals | Contain, preserve, escalate |

## Exercises

1. Reproduce scenario 7 in a sandbox: a client with naive retries against a stub that fails for 30 seconds; observe the storm; add backoff, jitter and a breaker; compare recovery time.
2. Build the missing alerts from scenarios 3 and 6 (queue age, DLQ depth, desired-vs-running, restart rate, memory trend) for a service you run.
3. Write a new scenario from an incident you experienced in the same format, with prompts and reveals, and run it as a team exercise.
