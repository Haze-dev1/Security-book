# Performance Profiling, Load Testing and Capacity Planning

:::objectives
- Find where a system actually spends time and memory using profilers, traces and database tooling, instead of guessing.
- Design and run load tests that answer specific questions (capacity, breaking point, regression) with realistic traffic.
- Plan capacity from measurements and growth forecasts, with headroom, and know when to scale versus optimise.

## Measure before you optimise

Engineers are poor at guessing where time goes. The serialisation you suspected takes 2 ms; the "fast" cache lookup makes 40 sequential network calls. The discipline: reproduce the slow case, measure with a tool that attributes time or memory to code, fix the top item, measure again. Optimising anything not at the top of the profile is wasted effort until it is.

Start from the outside in: the trace shows which service and which span is slow; the span's attributes show which query or call; the profiler shows which function; the database's plan shows which operation. Each level narrows the search.

## Profiling applications

**CPU profilers** sample the call stack many times per second and show where time accumulates; **flame graphs** render the result (wide bars are hot). **Memory profilers** show allocations and retained objects. **Continuous profiling** (Pyroscope/Grafana, Parca, Datadog, Google Cloud Profiler) runs always-on sampling in production at low overhead and lets you compare profiles between versions or time windows, which is how you find the regression introduced last Tuesday.

```bash
# Python: sample a running process without restarting it
py-spy record -o profile.svg --pid 12345 --duration 30
py-spy top --pid 12345                     # live view of hottest functions

# Node: CPU profile via the inspector, then open in Chrome DevTools or speedscope
node --cpu-prof --cpu-prof-dir=./profiles dist/server.js
# or production-safe sampling with 0x / clinic flame

# Go: built-in pprof over HTTP (import _ "net/http/pprof")
go tool pprof -http=:8081 http://localhost:6060/debug/pprof/profile?seconds=30
go tool pprof -http=:8081 http://localhost:6060/debug/pprof/heap

# JVM: async-profiler (low overhead, safepoint-free) or JFR
./asprof -d 30 -f flame.html <pid>
java -XX:StartFlightRecording=duration=60s,filename=rec.jfr ...

# Linux, any language: perf for native code and the kernel
perf record -F 99 -g -p <pid> -- sleep 30 && perf script | stackcollapse-perf.pl | flamegraph.pl > perf.svg
```

What you typically find: serialisation of large objects, N+1 queries, synchronous calls that could be concurrent, regular expressions compiled per call, logging at debug level formatting strings nobody reads, lock contention, GC pressure from allocation churn, and blocking I/O on an event loop.

## Profiling the database

Most backend latency lives in the database. Tools: `EXPLAIN (ANALYZE, BUFFERS)` for a query's real plan and cost; `pg_stat_statements` for the queries consuming the most total time across the system (sort by `total_exec_time`, then `mean_exec_time`, then `calls`); slow query logs with thresholds; Performance Insights on RDS for wait-event analysis (CPU vs I/O vs locks); `pg_stat_activity` for what is running now; index usage statistics to find unused indexes (which cost writes) and missing ones (sequential scans on large tables).

```sql
-- Top queries by total time
SELECT round(total_exec_time::numeric, 0) AS total_ms, calls,
       round(mean_exec_time::numeric, 2) AS mean_ms, rows,
       left(query, 100) AS query
FROM pg_stat_statements
ORDER BY total_exec_time DESC
LIMIT 15;

-- Tables with many sequential scans and lots of rows (index candidates)
SELECT relname, seq_scan, seq_tup_read, idx_scan, n_live_tup
FROM pg_stat_user_tables
WHERE seq_scan > 1000 AND n_live_tup > 100000
ORDER BY seq_tup_read DESC;
```

## Load testing

A load test answers a question. Decide the question first:

- **Capacity**: how many requests per second can one instance (or the current fleet) serve within the latency SLO?
- **Breaking point**: what fails first as load increases, and how (gracefully or catastrophically)?
- **Soak**: does performance degrade over hours (leaks, fragmentation, connection exhaustion)?
- **Spike**: what happens when traffic jumps 5× in a minute (autoscaling lag, queueing)?
- **Regression**: did this release change latency or throughput at the same load?

Realism matters more than raw numbers: use production-like data volumes (a 1,000-row table behaves nothing like a 100-million-row one), realistic request mixes and parameters (random IDs, not the same one hitting the cache), think times and session behaviour for user-facing flows, and production-like infrastructure (a load test against a `t3.micro` database tells you about `t3.micro`). Run from outside the system under test with enough generator capacity that the generator is not the bottleneck.

@file: loadtest/checkout.js (k6)
```javascript
import http from "k6/http";
import { check, sleep } from "k6";
import { SharedArray } from "k6/data";

const users = new SharedArray("users", () => JSON.parse(open("./synthetic-users.json")));

export const options = {
  scenarios: {
    browse: {   // steady background traffic
      executor: "constant-arrival-rate", rate: 300, timeUnit: "1s", duration: "20m",
      preAllocatedVUs: 200, maxVUs: 600, exec: "browse",
    },
    checkout: { // ramp to find the breaking point
      executor: "ramping-arrival-rate", startRate: 5, timeUnit: "1s",
      stages: [{ target: 20, duration: "5m" }, { target: 60, duration: "10m" }, { target: 0, duration: "2m" }],
      preAllocatedVUs: 100, maxVUs: 400, exec: "checkout",
    },
  },
  thresholds: {
    "http_req_duration{scenario:browse}": ["p(95)<300"],
    "http_req_duration{scenario:checkout}": ["p(95)<1500"],
    "http_req_failed": ["rate<0.005"],
  },
};

export function browse() {
  const sku = Math.floor(Math.random() * 500000);
  const res = http.get(`${__ENV.BASE_URL}/products/${sku}`, { tags: { route: "product" } });
  check(res, { "200": (r) => r.status === 200 });
  sleep(Math.random() * 3);
}

export function checkout() {
  const u = users[Math.floor(Math.random() * users.length)];
  const headers = { Authorization: `Bearer ${u.token}`, "Content-Type": "application/json", "Idempotency-Key": crypto.randomUUID() };
  const res = http.post(`${__ENV.BASE_URL}/orders`, JSON.stringify({ cart: u.cart }), { headers, tags: { route: "order" } });
  check(res, { "201": (r) => r.status === 201 });
}
```

Use arrival-rate executors (open model) rather than fixed virtual users (closed model) for request-driven systems: real users do not slow down when your server does, so a closed model under-reports failure. Watch the system under test during the run (dashboards, traces, database waits), not just the generator's numbers. Record results against the commit and the infrastructure configuration; run a smaller regression test in the pipeline against staging on every release.

Other tools: Locust (Python, scriptable), Gatling (JVM, detailed reports), Artillery, wrk/hey/oha for quick single-endpoint checks, and AWS Distributed Load Testing for scaling generators.

## Reading results

Throughput rises with load until a resource saturates; latency then climbs steeply (queueing) while throughput flattens or falls (collapse from retries and context switching). The **knee** is your practical capacity; plan to operate below it with headroom. Identify the saturated resource: CPU (profile it), database (waits, locks, connections), connection pools (queue time), network (bandwidth, connection limits), downstream dependencies (their latency rises first), memory (GC pauses, swapping). Fix or scale that resource and run again; the bottleneck moves. Stop when the knee is comfortably above required capacity with the planned headroom.

Watch for **tail latency**: p99 that is 20× p50 indicates occasional pathological events (GC pauses, lock waits, cold caches, retries) that averaged metrics hide and that a fraction of users always hit.

## Capacity planning

Capacity planning turns measurements and forecasts into a provisioning plan:

1. **Measure** current peak demand (requests/s, concurrent users, data volume) and the resource consumption per unit of demand (CPU-seconds per request, IOPS per order, GB per customer).
2. **Forecast** demand: business growth, seasonality (month-end, holidays, marketing events), planned launches. Use the business's numbers, then add a margin for their optimism being wrong in either direction.
3. **Headroom**: run at 50–70% of capacity at peak so that one AZ loss, one bad deploy or one spike does not saturate; N+1 (or N+2) instances for availability regardless of load.
4. **Scaling plan**: what scales automatically (stateless compute via autoscaling on CPU or request count per target, with scale-out faster than scale-in), what scales with lead time (database instance class, provisioned IOPS, cache node size), and what needs architectural work (single-writer database, hot partitions).
5. **Limits**: service quotas (EC2 instances per Region, Lambda concurrency, RDS connections, ENIs), licence limits, downstream rate limits. Check them before the launch, not during.
6. **Cost**: capacity has a price; model it (Part VII chapter 4) and decide where reserved capacity or Savings Plans fit the baseline.
7. **Review** quarterly and before every major event; compare forecast to actual and recalibrate.

## Scale or optimise?

Optimising is right when a profile shows a clear, fixable hotspot, when the cost of the inefficiency is large and ongoing, or when scaling has hit an architectural limit. Scaling is right when engineering time is the scarce resource, when the load is temporary, or when the system is already reasonably efficient. A common mistake is spending weeks optimising code that runs on 200 USD per month of compute; another is scaling a database to the largest instance to hide a missing index. Compute the money on both sides.

## Common mistakes

- Load-testing against tiny datasets or non-production infrastructure and extrapolating.
- Closed-model tests that hide failure by slowing down with the server.
- Testing only the happy path at steady state; never spikes, soaks or failure injection.
- Reading averages; ignoring tails.
- Letting the load generator be the bottleneck.
- Capacity plans without service quotas or dependency limits.
- Autoscaling policies tuned to react after users already saw the slowdown; scale on leading indicators (request count per target, queue depth) with cooldowns tuned from spike tests.
