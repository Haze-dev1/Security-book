# Logs, Metrics and Traces

## First principles: you cannot fix what you cannot see

Production is a system you cannot attach a debugger to, running on machines you may never log into, serving users you cannot ask. Everything you know about it comes from **telemetry** the system emits about itself. Observability is the property of being able to answer new questions about the system's behaviour from that telemetry without shipping new code. Three signal types, each answering a different question:

| Signal | Answers | Shape | Cost driver |
|---|---|---|---|
| **Logs** | What happened, in detail, at this moment? | Timestamped events with fields | Volume (bytes); indexing |
| **Metrics** | How much, how often, how fast, over time? | Numeric time series with labels | Cardinality (unique label combinations) |
| **Traces** | Where did this request spend its time and where did it fail across services? | Trees of spans with timing and attributes | Volume; sampled |

They become powerful together: a metric alert says latency rose; the trace for a slow request shows the database span taking 2 s; the logs for that span's trace ID show the exact query and the lock wait. The glue is **shared identifiers**: a trace ID and request ID on every log line and span, service and version labels on every metric.

## Logs

A log line is a record of an event. In production, logs are **structured** (JSON or key=value) so machines can filter and aggregate them; prose logs are for humans reading one file, which nobody does at scale.

```python
# Unhelpful
logger.info(f"User {user.email} failed to pay invoice {inv.id}: {err}")

# Structured, queryable, no PII
logger.info("payment_failed",
            user_id=user.id, invoice_id=inv.id, provider="stripe",
            error_code=err.code, amount_minor=inv.amount, currency=inv.currency,
            trace_id=current_trace_id(), request_id=request.id)
```

```json
{"ts":"2026-11-01T09:14:02.113Z","level":"info","event":"payment_failed","service":"portal-api","version":"sha-3f2a9c1","env":"production",
 "user_id":"u_8c21","invoice_id":"inv_5519","provider":"stripe","error_code":"card_declined","amount_minor":12900,"currency":"EUR",
 "trace_id":"4bf92f3577b34da6a3ce929d0e0e4736","request_id":"req_01HZ...","region":"eu-west-1","host":"ip-10-20-3-41"}
```

Rules:

- **One event per line, JSON, to stdout**; the platform (container runtime, agent) ships it. Applications never manage log files in containers.
- **Standard fields on every line** added by the logging setup, not by each call site: timestamp (UTC, RFC 3339), level, service, version, environment, host, trace and request IDs, tenant ID where relevant.
- **Event names, not sentences**: `payment_failed` is a filter; "Failed to pay" is a regex.
- **Levels mean something**: `error` = something is wrong and someone may need to act; `warn` = unusual but handled; `info` = business-relevant events; `debug` = off in production unless enabled per request or per tenant. An `error` for an expected validation failure trains people to ignore errors.
- **No secrets, no personal data**: tokens, passwords, card numbers, full names, emails, addresses never appear in logs. Log identifiers and look the person up in the system of record under access control. Use redaction middleware for headers (`Authorization`, `Cookie`) and known sensitive fields; treat logs as a data store subject to retention and privacy rules ([Data Privacy and Personally Identifiable Information](#/p04/c23)).
- **Sampling and rate limiting** for noisy events: a retry loop logging 10,000 identical errors per second helps nobody and costs money.
- **Access logs** at the edge (ALB, Nginx) and request logs in the application with method, route (templated, not raw path), status, duration, bytes, user agent class, and IDs.

## Metrics

A metric is a named numeric measurement with labels, collected at intervals and stored as a time series. Three types cover almost everything:

- **Counter**: monotonically increasing count (requests, errors, bytes). Rates are derived (`rate(http_requests_total[5m])`).
- **Gauge**: a value that goes up and down (queue depth, connections, memory, temperature).
- **Histogram**: distribution of values in buckets (request duration), from which percentiles are computed server-side. Prefer histograms over client-side summaries so percentiles can be aggregated across instances.

```python
from prometheus_client import Counter, Histogram, Gauge

REQUESTS = Counter("http_requests_total", "HTTP requests", ["method", "route", "status_class"])
LATENCY = Histogram("http_request_duration_seconds", "Request duration", ["method", "route"],
                    buckets=(0.005, 0.01, 0.025, 0.05, 0.1, 0.25, 0.5, 1, 2.5, 5, 10))
QUEUE_DEPTH = Gauge("jobs_queue_depth", "Pending jobs", ["queue"])

@app.middleware("http")
async def metrics_middleware(request, call_next):
    route = request.scope.get("route").path if request.scope.get("route") else "unmatched"   # templated: /users/{id}
    with LATENCY.labels(request.method, route).time():
        response = await call_next(request)
    REQUESTS.labels(request.method, route, f"{response.status_code // 100}xx").inc()
    return response
```

:::danger Cardinality is the metric killer
Every unique combination of label values is a separate time series stored forever. Labelling by user ID, request ID, raw URL path, or email creates millions of series, slows every query and can take down the metrics backend. Labels are for *dimensions you will aggregate by* (route, method, status class, Region, version, tenant tier), never for identifiers. Identifiers go in logs and traces.
:::

Naming conventions: `<namespace>_<subject>_<unit>` with base units (`seconds`, `bytes`), suffix `_total` for counters; consistent labels across services (`service`, `version`, `env`, `region`) attached by the collector, not by each metric. The four golden signals for any service: **latency, traffic, errors, saturation**. RED (rate, errors, duration) for request-driven services; USE (utilisation, saturation, errors) for resources.

## Traces

A **trace** follows one request through every service it touches. Each unit of work is a **span** with a name, start and end time, parent span, status and attributes; spans form a tree; the trace ID is propagated across network calls in headers (W3C `traceparent`). Traces answer the questions metrics and logs cannot: which of the nine downstream calls was slow, whether calls happened in sequence that could be parallel, what the N+1 query pattern looks like in time.

```text
trace 4bf92f35... (total 1,840 ms)
└─ GET /orders/{id}                      portal-api        1,840 ms
   ├─ auth.verify_token                  portal-api            3 ms
   ├─ SELECT orders WHERE id=$1          postgres             12 ms
   ├─ GET /inventory/{sku}               inventory-svc       310 ms
   │  └─ SELECT stock WHERE sku=$1       postgres            298 ms   ← missing index
   ├─ GET /inventory/{sku}               inventory-svc       305 ms   ← sequential; could be parallel
   ├─ GET /inventory/{sku}               inventory-svc       301 ms
   └─ POST /pricing/quote                pricing-svc         890 ms
      └─ HTTP GET tax-provider           external            870 ms   ← no timeout
```

Instrumentation is mostly automatic with OpenTelemetry (chapter 2): HTTP servers and clients, database drivers, queues and gRPC are instrumented by libraries; you add spans around business operations and attributes that matter (tenant ID, order ID as a span attribute, not a metric label). Tracing is **sampled** (keep 1–10% of normal traces, 100% of errors and slow ones) because full tracing of every request is expensive.

## Connecting the signals

- The logging setup reads the active span and adds `trace_id` and `span_id` to every line.
- Metrics carry `service` and `version`; traces carry the same as resource attributes; dashboards link from a metric spike to traces in that window to logs with those trace IDs.
- **Exemplars** attach a trace ID to a histogram bucket observation, so a latency chart can jump straight to a representative slow trace.
- Request IDs returned to clients in a response header let support correlate a user's complaint to the exact trace.

## Costs and retention

Telemetry is often the second-largest infrastructure bill. Control it by design: log at `info` what the business needs and `debug` only on demand; sample traces; keep metric cardinality bounded; set retention per signal (logs 30 days hot, archived to S3 for a year; metrics downsampled after 15 days; traces 7 days); route high-volume low-value logs (health checks, access logs for static assets) to cheap storage or drop them. Review the top ten log sources monthly.

## Common mistakes

- Unstructured logs that need regex at 03:00.
- Logging the full request body "for debugging" (secrets, PII, gigabytes).
- Metric labels with unbounded values.
- No trace propagation across queues (the consumer starts a new trace; the story breaks).
- Different services using different field names for the same thing (`userId`, `user_id`, `uid`).
- Telemetry that lives only on the host that just died.
