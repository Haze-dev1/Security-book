# Server Hardening and User Management

:::objectives
- Reduce a server's attack surface systematically: packages, services, ports, users, privileges, kernel settings.
- Configure sudo, user accounts and groups for accountability and least privilege.
- Apply automatic security updates, intrusion prevention and host auditing.
- Use benchmarks (CIS) and scanners to verify and to produce evidence for clients.
:::

:::prereq
Chapters 2 and 3; Part I chapter 5; Part II chapter 15.
:::

## The problem

A freshly installed server is configured for convenience and compatibility, not security: more packages than needed, services listening on all interfaces, permissive defaults, a user who can do everything. Hardening is the process of removing what is not needed and constraining what remains, so that a vulnerability in one component does not become control of the machine. It is mostly a checklist, best applied by building hardened images and configuring with code rather than by hand on each server.

## Principles applied to a host

- **Minimise**: install only what the service needs; remove compilers, docs, unused daemons from production images.
- **Least privilege**: services run as dedicated users; humans use personal accounts and `sudo`; nothing runs as root that does not need to.
- **Default deny**: host firewall, `sshd` restrictions, mandatory access control where available.
- **Patch**: automatic security updates for the OS; a schedule for kernel reboots.
- **Observe**: auth logs, auditd for sensitive operations, file integrity monitoring where required, logs shipped off-box.
- **Immutable where possible**: rebuild from a hardened image rather than patching in place; treat a compromised host as disposable.

## A hardening pass

```checklist
# Linux server hardening baseline (Ubuntu/Debian flavour; adapt for RHEL-family)
## Accounts and privileges
- Personal accounts for every human; no shared logins; root login disabled; root password locked.
- sudo via group membership with logging; NOPASSWD only for automation accounts with narrowly scoped commands.
- Service accounts are system users with nologin shells and no home directories unless required.
- Password policy irrelevant where keys/SSO are used; lock password auth for all human accounts (`passwd -l`).
- Remove or disable unused default accounts; audit `/etc/passwd` for UID 0 entries other than root.
## SSH
- Keys only; root login off; AllowGroups; modern algorithms; fail2ban; firewall limited to bastion/VPN (chapter 3).
## Packages and services
- Minimal install; `apt list --installed` reviewed; remove compilers, build tools and unused daemons on production hosts.
- `ss -ltnup`: every listening socket is intended, bound to the narrowest interface (127.0.0.1 for local-only services).
- Unattended security updates enabled with automatic reboot in a window (or a managed patching process).
## Network
- Host firewall default-deny inbound (ufw/nftables), allow only required ports; outbound restricted on sensitive tiers.
- IPv6 configured or disabled deliberately, not ignored.
- sysctl hardening: ignore ICMP redirects and source routing, enable reverse path filtering, log martians, disable IP forwarding unless a router.
## Filesystem
- Separate volume for data and logs; `noexec,nosuid,nodev` on /tmp and data mounts where feasible.
- World-writable files and directories reviewed (`find / -xdev -perm -0002 -type f`); setuid binaries reviewed and minimised.
- Secrets files 600/640 with correct ownership; application code not writable by the service user.
## Kernel and MAC
- AppArmor (Ubuntu) or SELinux (RHEL) in enforcing mode with profiles for exposed services.
- Core dumps restricted; kernel pointer hiding; `kernel.yama.ptrace_scope=1`.
## Logging and auditing
- journald persistent; auth logs shipped to a central store; auditd rules for sudo, user/group changes, sshd config, and secret files.
- Time synchronised (chrony).
- File integrity monitoring (AIDE, Wazuh, or cloud equivalents) on regulated hosts.
## Verification
- CIS benchmark scan (OpenSCAP, Lynis, or a commercial scanner) run and findings triaged; evidence stored.
```

## Users, groups and sudo

```bash
# Human user, in the ssh-users and sudo groups, key-based only
sudo adduser --disabled-password --gecos "Ana Lopez" ana
sudo usermod -aG ssh-users,sudo ana
sudo install -d -m 700 -o ana -g ana /home/ana/.ssh
echo 'ssh-ed25519 AAAA... ana@laptop' | sudo tee /home/ana/.ssh/authorized_keys >/dev/null
sudo chmod 600 /home/ana/.ssh/authorized_keys && sudo chown ana:ana /home/ana/.ssh/authorized_keys

# Service account
sudo useradd --system --home /srv/app --shell /usr/sbin/nologin --no-create-home app

# Offboarding: lock, expire, remove keys, kill sessions; keep the UID reserved so file ownership stays attributable
sudo usermod -L -e 1 ana && sudo gpasswd -d ana sudo && sudo gpasswd -d ana ssh-users
sudo pkill -KILL -u ana
```

Sudo configuration lives in `/etc/sudoers.d/` (edit with `visudo -f` to validate):

```sudoers
@file: /etc/sudoers.d/10-ops
Defaults    logfile=/var/log/sudo.log, log_input, log_output        # record commands (and optionally sessions)
Defaults    timestamp_timeout=5, passwd_tries=3
%sudo       ALL=(ALL:ALL) ALL                                        # humans: full sudo with password/MFA
deploy      ALL=(root) NOPASSWD: /bin/systemctl restart app, /bin/systemctl reload nginx, /usr/bin/journalctl -u app *
```

The `deploy` line shows least-privilege automation: the CI user may restart exactly two services and read one log, nothing else, without a password. Avoid `NOPASSWD: ALL` for anything that is not a tightly controlled automation identity; avoid wildcards that allow argument injection (`/bin/systemctl *` would allow `systemctl start evil`).

## Automatic updates

```bash
sudo apt install unattended-upgrades
sudo dpkg-reconfigure -plow unattended-upgrades
# /etc/apt/apt.conf.d/50unattended-upgrades: security origin enabled; set
#   Unattended-Upgrade::Automatic-Reboot "true"; Unattended-Upgrade::Automatic-Reboot-Time "03:30";
#   Unattended-Upgrade::Mail "ops@client.com";
sudo systemctl status unattended-upgrades
```

Security patches apply daily; kernel updates take effect at the scheduled reboot. Behind a load balancer, stagger reboot times across instances. For RHEL-family, `dnf-automatic` with `apply_updates = yes`. In managed fleets, AWS Systems Manager Patch Manager schedules and reports patching (Part VII chapter 13). For immutable fleets, rebuild the AMI weekly and roll the Auto Scaling Group instead (chapter 12).

## Intrusion prevention and detection

- **fail2ban**: watches logs and bans IPs after repeated failures (SSH, Nginx auth, custom apps). Reduces noise and slows brute force; not a substitute for keys and firewalls.
- **auditd**: kernel-level audit of system calls and file access by rule. Minimal useful rule set: changes to `/etc/passwd`, `/etc/shadow`, `/etc/sudoers*`, `/etc/ssh/sshd_config*`, use of `sudo`, loading kernel modules, and access to your secrets directory.
- **AIDE / Wazuh / OSSEC**: file integrity monitoring: a baseline of file hashes, alerts on change. Mandatory in PCI scope; valuable anywhere a host is long-lived.
- **GuardDuty and cloud-level detection** see credential misuse and network anomalies that host tools miss; use both.
- **Log shipping**: everything above is useless if the attacker can delete local logs; ship to CloudWatch or a logging account in near real time.

## Mandatory access control

AppArmor and SELinux confine processes to profiles regardless of Unix permissions: a confined Nginx cannot read `/home` even as root. Ubuntu ships AppArmor enforcing with profiles for common daemons; RHEL ships SELinux enforcing with targeted policy. Keep them on; when something is denied, read the audit log and adjust the policy or file contexts rather than disabling the system (`setenforce 0` "to make it work" is how MAC dies). Container runtimes apply default AppArmor/seccomp profiles too (Part VI chapter 7).

## Benchmarks and evidence

The **CIS Benchmarks** for each distribution enumerate hundreds of settings with rationale; Level 1 is the practical baseline, Level 2 for high-security environments. Scanners (OpenSCAP with the CIS or DISA STIG profiles, Lynis, cloud marketplace scanners, AWS Inspector for CVEs) produce reports you can hand to a client as evidence. Hardened base images (CIS-hardened AMIs, your own Packer-built AMI applying the benchmark via Ansible) make compliance a property of the image rather than per-server effort.

## Containers change the picture

On Fargate or Kubernetes, most host hardening is the platform's job (Fargate) or applies to node images (EKS-optimised or Bottlerocket AMIs, which are minimal and immutable by design). Your hardening moves to the image and the pod specification: non-root, read-only root filesystem, dropped capabilities, seccomp, no privileged containers (Part VI chapter 7 and chapter 13). The principles are identical; the surface shifts.

## Common mistakes

- Shared accounts; `NOPASSWD: ALL` for everyone.
- Disabling AppArmor/SELinux at the first denial.
- Services bound to `0.0.0.0` that only need localhost.
- No automatic security updates; kernels years old.
- Logs only on the host; wiped by the intruder.
- Hardening by hand on each server; drift within weeks.
- Compilers and package development tools on production hosts.
- World-writable directories under the web root.
