## The problem

Storage problems are slow-motion outages. A disk fills over weeks and then everything fails at once; a volume is attached but not mounted at boot; a database sits on a volume with too few IOPS; a filesystem runs out of inodes with gigabytes free. The vocabulary (block device, partition, filesystem, mount point) is old and the tools are stable; an hour learning them prevents a class of 3 a.m. incidents.

## Adding a data volume (EBS example)

```bash
# 1. Attach the volume in the console/CLI (e.g. 100 GB gp3) as /dev/sdf; find it in the OS
lsblk -o NAME,SIZE,TYPE,FSTYPE,MOUNTPOINT,SERIAL
# nvme1n1  100G disk            vol0abc123...

# 2. Format (ONCE; this destroys data) with a label
sudo mkfs.ext4 -L appdata /dev/nvme1n1          # or: sudo mkfs.xfs -L appdata /dev/nvme1n1

# 3. Mount point, fstab by label, mount
sudo mkdir -p /var/lib/app
echo 'LABEL=appdata  /var/lib/app  ext4  defaults,noatime,nodev,nosuid,nofail,x-systemd.device-timeout=10  0 2' | sudo tee -a /etc/fstab
sudo systemctl daemon-reload && sudo mount -a
df -h /var/lib/app
sudo chown app:app /var/lib/app && sudo chmod 750 /var/lib/app

# 4. Grow later: resize the EBS volume in AWS (online), then
sudo growpart /dev/nvme0n1 1        # only if partitioned (root volumes)
sudo resize2fs /dev/nvme1n1         # ext4, online;   XFS: sudo xfs_growfs /var/lib/app
```

Always mount by `LABEL=` or `UUID=` (from `blkid`), never by device name; NVMe names can change between boots. Always `nofail` for anything that is not the root filesystem.

## Choosing filesystems and volume types

| Use | Filesystem | EBS type | Notes |
|---|---|---|---|
| Root / OS | ext4 (distro default) | gp3 | Small (20–50 GB); keep data off it |
| PostgreSQL / MySQL data | ext4 or XFS | gp3 with provisioned IOPS/throughput, or io2 for heavy loads | `noatime`; separate volume; size for WAL and growth; snapshots for backup |
| Logs | ext4 | gp3 | Separate volume or at least a quota so logs cannot fill root; rotation |
| Uploads / shared files | prefer S3; else EFS for multi-instance | — | Local disks do not scale across instances |
| Scratch / temp | tmpfs (RAM) or instance store | — | Ephemeral by nature |

**gp3** baseline is 3,000 IOPS and 125 MB/s regardless of size (configurable up to 16,000 IOPS and 1,000 MB/s for extra cost); **gp2** scales IOPS with size and bursts, which is why small gp2 database volumes mysteriously slow down after sustained load (burst balance exhausted). **io2** provides consistent high IOPS with higher cost. Instance store (local NVMe) is extremely fast and vanishes on stop; suitable for caches and scratch, not for data you cannot lose.

## Understanding "no space left on device"

Four different problems share one message:

1. **Blocks exhausted**: `df -h` shows 100%. Find the consumers: `du -xh --max-depth=2 / | sort -rh | head`; typical: logs, Docker images, old releases, core dumps, journal (`journalctl --disk-usage`), database bloat, temp files.
2. **Inodes exhausted**: `df -i` shows 100% with blocks free. Millions of tiny files (sessions on disk, cache files, mail queues). Find with `find / -xdev -printf '%h\n' | sort | uniq -c | sort -rn | head`. Fix the source; ext4 inode count is fixed at format time.
3. **Deleted-but-open files**: `df` full, `du` small. `lsof +L1` lists them; restart or signal the holding process (log rotation without reopening is the usual cause; use `copytruncate` or SIGHUP).
4. **Reserved blocks**: ext4 reserves 5% for root by default; non-root processes hit "full" at 95%. `tune2fs -m 1` reduces the reserve on data volumes.

Prevention: data, logs and Docker on their own volumes with alerts at 80% (CloudWatch agent `disk_used_percent`), log rotation and journald limits (chapter 9), image pruning, and a documented growth procedure.

## I/O performance

```bash
iostat -xz 1 5          # per device: r/s w/s, rkB/s wkB/s, await (ms latency), %util
# await > 10 ms on an SSD-backed volume under load = saturated or throttled; %util near 100 = busy
iotop -oPa              # which processes are doing I/O (install iotop)
pidstat -d 1            # per-process I/O rates
cat /sys/block/nvme1n1/queue/scheduler
```

Symptoms of storage trouble: high `await`, high `wa` CPU, database queries slow with low CPU, EBS `VolumeQueueLength` and `BurstBalance` (gp2) metrics in CloudWatch. Fixes in order: cut the I/O (indexes, caching, batching), increase IOPS/throughput on gp3, move to io2, add memory so the page cache absorbs reads.

## Snapshots and consistency

EBS snapshots are block-level, incremental and taken while the volume is in use; they are **crash-consistent** (like a power loss), not application-consistent. Databases recover from crash-consistent snapshots via their journal, but for guaranteed consistency: freeze writes (`fsfreeze -f`), snapshot, unfreeze; or use the database's own backup tooling; or use RDS, which handles this. Snapshot data volumes on a schedule (AWS Backup or Data Lifecycle Manager) with retention, and test restores (chapter 11).

## Encryption

Enable EBS encryption by default at the account level (KMS-backed, transparent, no performance penalty worth mentioning). Snapshots of encrypted volumes are encrypted; AMIs too. For on-premises or extra assurance, LUKS encrypts at the OS level with keys from a KMS or TPM; it complicates boot and recovery, so use cloud-native encryption where available.

## Shared and network filesystems

NFS (and EFS, AWS's managed NFS) lets several instances share a filesystem. Use it for legacy applications that need a shared directory; prefer S3 for new designs. EFS performance modes and throughput modes need matching to the workload; latency per operation is higher than local disk, which hurts applications doing many small file operations. Never put a database on NFS.

## Common mistakes

- Mounting by device name; volume not mounted after reboot or mounted in the wrong place.
- Missing `nofail`; boot hangs when a volume is absent.
- Everything on the root volume; one log flood takes down the server.
- gp2 for databases; burst exhaustion.
- No disk usage alerts.
- Formatting the wrong device (always check `lsblk` and the serial).
- Treating EBS snapshots as application-consistent database backups.
- Logs rotated by renaming while the process keeps the old file open.
