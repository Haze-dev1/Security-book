# TLS Certificates and Reverse Proxy Configuration

:::objectives
- Obtain and auto-renew TLS certificates on a server with Caddy or certbot, including wildcard and internal cases.
- Configure Nginx or Caddy as a hardened TLS terminator and reverse proxy in front of an application.
- Verify the deployment with external tools and monitor certificate expiry.
- Handle the operational edge cases: multiple domains, redirects, HTTP/2 and HTTP/3, client IP preservation, maintenance pages.
:::

:::prereq
Part II chapters 9, 10 and 12; chapter 5 of this part.

## The problem

Part II explained TLS and reverse proxies conceptually. On a server you have to make it real: a certificate that renews itself, a proxy that terminates TLS with a modern configuration, redirects HTTP to HTTPS, forwards to the application with the right headers, serves static files, and keeps working at 3 a.m. when the certificate would otherwise have expired. This chapter is the hands-on configuration for the two common choices.

## Option A: Caddy (automatic everything)

Caddy obtains certificates from Let's Encrypt (or ZeroSSL) via ACME, renews them, redirects HTTP to HTTPS, enables HTTP/2 and HTTP/3, and applies a modern TLS configuration, all by default. For a single server or small deployment it removes the most common operational failure (expired certificates) entirely.

```bash
# Install (Debian/Ubuntu, official repo)
sudo apt install -y debian-keyring debian-archive-keyring apt-transport-https curl
curl -1sLf 'https://dl.cloudsmith.io/public/caddy/stable/gpg.key' | sudo gpg --dearmor -o /usr/share/keyrings/caddy-stable-archive-keyring.gpg
curl -1sLf 'https://dl.cloudsmith.io/public/caddy/stable/debian.deb.txt' | sudo tee /etc/apt/sources.list.d/caddy-stable.list
sudo apt update && sudo apt install -y caddy
```

```caddy
@file: /etc/caddyfile  (/etc/caddy/Caddyfile)
{
    email ops@client.com                       # ACME account contact (expiry notices if renewal fails)
    # acme_dns route53                         # for wildcard/internal certs via DNS-01 (needs the DNS plugin build and IAM permissions)
}

api.client.com {
    encode zstd gzip
    header {
        Strict-Transport-Security "max-age=63072000; includeSubDomains"
        X-Content-Type-Options nosniff
        Referrer-Policy strict-origin-when-cross-origin
        -Server
    }
    request_body { max_size 10MB }
    log { output file /var/log/caddy/api.access.log { roll_size 100mb roll_keep 10 } format json }

    handle_path /static/* {
        root * /srv/app/current/static
        file_server
        header Cache-Control "public, max-age=31536000, immutable"
    }
    handle {
        reverse_proxy 127.0.0.1:8000 {
            header_up X-Request-ID {http.request.uuid}
            transport http { dial_timeout 5s read_timeout 30s }
            health_uri /health/ready
            health_interval 10s
        }
    }
}

www.client.com, client.com {
    redir https://app.client.com{uri} permanent
}
```

```bash
sudo caddy validate --config /etc/caddy/Caddyfile
sudo systemctl reload caddy
sudo journalctl -u caddy -f                   # watch certificate issuance on first start
```

Requirements: ports 80 and 443 reachable from the Internet (HTTP-01/TLS-ALPN-01) or DNS API credentials (DNS-01); the DNS record for the domain already pointing at this server before Caddy starts. Caddy stores certificates in `/var/lib/caddy/.local/share/caddy/`; back it up or let it reissue.

## Option B: Nginx + certbot (explicit control)

```bash
sudo apt install -y nginx certbot python3-certbot-nginx     # or python3-certbot-dns-route53 for DNS-01
# Initial certificate (nginx plugin edits the server block; or use --webroot and keep full control)
sudo certbot --nginx -d api.client.com --agree-tos -m ops@client.com --redirect --hsts --no-eff-email
# Wildcard via Route 53 (instance role needs route53:ChangeResourceRecordSets on the zone)
sudo certbot certonly --dns-route53 -d 'client.com' -d '*.client.com' --agree-tos -m ops@client.com
sudo certbot renew --dry-run                                   # proves renewal works
systemctl list-timers | grep certbot                           # the renewal timer runs twice daily
```

```nginx
@file: /etc/nginx/snippets/tls-modern.conf
ssl_protocols TLSv1.2 TLSv1.3;
ssl_ciphers ECDHE-ECDSA-AES128-GCM-SHA256:ECDHE-RSA-AES128-GCM-SHA256:ECDHE-ECDSA-AES256-GCM-SHA384:ECDHE-RSA-AES256-GCM-SHA384:ECDHE-ECDSA-CHACHA20-POLY1305:ECDHE-RSA-CHACHA20-POLY1305;
ssl_prefer_server_ciphers off;
ssl_session_timeout 1d;
ssl_session_cache shared:SSL:10m;
ssl_session_tickets off;
ssl_stapling on;
ssl_stapling_verify on;
resolver 10.20.0.2 valid=300s;       # VPC resolver, for OCSP stapling
resolver_timeout 5s;
```

```nginx
@file: /etc/nginx/sites-available/api.client.com
upstream app { server 127.0.0.1:8000; keepalive 32; }

server {
    listen 80; listen [::]:80;
    server_name api.client.com;
    location /.well-known/acme-challenge/ { root /var/www/acme; }       # if using --webroot
    location / { return 301 https://$host$request_uri; }
}

server {
    listen 443 ssl; listen [::]:443 ssl;
    http2 on;
    server_name api.client.com;
    ssl_certificate     /etc/letsencrypt/live/api.client.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/api.client.com/privkey.pem;
    include snippets/tls-modern.conf;

    server_tokens off;
    add_header Strict-Transport-Security "max-age=63072000; includeSubDomains" always;
    add_header X-Content-Type-Options nosniff always;
    add_header Referrer-Policy strict-origin-when-cross-origin always;

    client_max_body_size 10m;
    gzip on; gzip_types application/json text/css application/javascript image/svg+xml; gzip_min_length 1024;
    access_log /var/log/nginx/api.access.log json_combined;

    location = /health/ready { proxy_pass http://app; access_log off; }
    location /static/ { alias /srv/app/current/static/; expires 1y; add_header Cache-Control "public, immutable"; access_log off; }
    location / {
        proxy_pass http://app;
        proxy_http_version 1.1;
        proxy_set_header Connection "";
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_set_header X-Request-ID $request_id;
        proxy_connect_timeout 5s; proxy_read_timeout 30s; proxy_send_timeout 30s;
    }
    error_page 502 503 504 /maintenance.html;
    location = /maintenance.html { root /var/www/errors; internal; add_header Retry-After 30 always; }
}
```

```bash
sudo ln -s /etc/nginx/sites-available/api.client.com /etc/nginx/sites-enabled/
sudo nginx -t && sudo systemctl reload nginx
# certbot renewal hook to reload nginx after renewal
echo 'systemctl reload nginx' | sudo tee /etc/letsencrypt/renewal-hooks/deploy/reload-nginx.sh && sudo chmod +x /etc/letsencrypt/renewal-hooks/deploy/reload-nginx.sh
```

The `json_combined` log format is defined in `nginx.conf` (`log_format json_combined escape=json '{"time":"$time_iso8601","request_id":"$request_id","remote_addr":"$remote_addr","method":"$request_method","uri":"$request_uri","status":$status,"bytes":$body_bytes_sent,"rt":$request_time,"urt":"$upstream_response_time","ua":"$http_user_agent"}';`) so logs ship as structured records.

## Behind a cloud load balancer

If an ALB terminates TLS in front of these hosts, the host proxy serves plain HTTP on the application port to the ALB (or HTTPS with a self-signed or private certificate for re-encryption), does not redirect (the ALB does), passes through the ALB's `X-Forwarded-*` headers instead of overwriting them, and the certificate lives in ACM, not on the host. The host proxy remains useful for static files, buffering and local health checks; some teams drop it and let the ALB talk to the application directly.

## Multiple applications on one host

Name-based virtual hosts: one `server` block (Nginx) or site block (Caddy) per hostname, each with its own certificate (SNI selects it), each proxying to a different local port. Caddy handles the certificates for all of them automatically; certbot issues one certificate per hostname or a SAN certificate covering several (`-d a.client.com -d b.client.com`).

## Verification

```bash
curl -sIv https://api.client.com 2>&1 | grep -E 'HTTP/|SSL connection|subject|expire|strict-transport'
echo | openssl s_client -connect api.client.com:443 -servername api.client.com 2>/dev/null | openssl x509 -noout -dates -issuer
curl -sI http://api.client.com | head -1          # expect 301
curl -sI --http3 https://api.client.com | head -1 # Caddy: HTTP/3 200 (curl built with HTTP/3)
```

Then an external scanner (SSL Labs or `testssl.sh`) for an A grade, and an external expiry monitor alerting at 21/14/7 days (Part II chapter 10). On the host, `systemctl status certbot.timer` / `journalctl -u caddy | grep -i renew` confirms renewal activity.

## Operational edge cases

- **Maintenance page**: the `error_page 502 503 504` block above serves a static page with `Retry-After` when the app is down or deploying; Caddy equivalent via `handle_errors`.
- **Large uploads**: raise `client_max_body_size`/`max_size` deliberately per location, not globally.
- **WebSockets and SSE**: Part II chapter 12 settings; Caddy handles upgrades automatically.
- **Rate limiting**: `limit_req` zones (Nginx) or the `rate_limit` module (Caddy) per route for login and expensive endpoints.
- **Log rotation**: `logrotate` for Nginx (default config rotates daily, `postrotate` reloads), Caddy rolls its own.
- **Certificate for an internal-only host**: DNS-01 with a public domain (`internal.client.com`), or a private CA (Part II chapter 10); do not disable verification in clients.
- **Renewal failing**: common causes are port 80 closed after a security group change, DNS credentials rotated, or the domain's A record moved. The dry run and the monitor catch these before expiry.

## Common mistakes

- Certificates installed manually with no renewal automation.
- Renewal automation without a reload hook; new certificate on disk, old one served.
- Port 80 closed, breaking HTTP-01 renewal.
- `add_header` in a `location` block dropping the server-level security headers (Nginx inheritance).
- Missing `always` on headers, so error pages lack them.
- Overwriting `X-Forwarded-Proto` behind an ALB.
- Weak TLS snippets copied from old blog posts (TLS 1.0, RC4, no stapling).
- Access logs without request IDs, so proxy and application logs cannot be correlated.

## Exercises

1. Deploy Caddy on a test VM with a real domain you control; confirm automatic HTTPS, HTTP/3 and the security headers; read the issuance log.
2. Deploy Nginx + certbot with DNS-01 via Route 53 for a wildcard; add the reload hook; run the dry run; break renewal by revoking the IAM permission and observe the failure in the log.
