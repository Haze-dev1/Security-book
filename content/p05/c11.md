# Backups, Restoration and Disaster Recovery

:::objectives
- Design a backup strategy from recovery objectives (RPO, RTO) rather than from tooling.
- Back up databases, volumes, object storage and configuration correctly, with encryption, off-site copies and retention.
- Prove recoverability with regular, timed restore tests.
- Write a disaster recovery plan proportionate to the client's needs.
:::

:::prereq
Chapter 6; Part VIII chapter 9 covers database-specific mechanics in depth.
:::

## The problem

Everyone has backups until they need them. Then the dump was of the wrong database, the snapshot was never automated, the encryption key is gone, the restore takes nineteen hours, or the backups were on the same volume that failed. A backup is not a thing you have; it is a *restore you have rehearsed*. Everything in this chapter follows from that sentence.

## Start from objectives

- **[[rpo|RPO]]** (recovery point objective): how much data loss is acceptable, as time. "We can lose at most 15 minutes of orders." Determines backup frequency and whether you need continuous (WAL/PITR) protection.
- **[[rto|RTO]]** (recovery time objective): how long the system may be down. "Back within 4 hours." Determines automation, warm standbys, and how many people must be reachable.
- **Retention**: how far back you must be able to go (a corruption discovered after three weeks needs a three-week-old copy; regulations may require years).
- **Scope**: what must be recoverable: databases, uploaded files, configuration and secrets, infrastructure definitions, DNS, certificates, code and build artifacts, encryption keys, documentation.

Agree these with the client in writing. They drive cost: RPO of 5 minutes with RTO of 1 hour costs far more than nightly backups with a next-day restore.

## The 3-2-1 rule, updated

Three copies of the data, on two different media or systems, one off-site (different region or account), plus: **one offline or immutable** (ransomware deletes online backups it can reach) and **zero errors on restore test**. In AWS terms: the live database; automated snapshots in the same region; copies replicated to another region in a separate backup account with Object Lock or AWS Backup Vault Lock so even a compromised primary account cannot delete them.

## What to back up and how

| Asset | Method | Frequency | Notes |
|---|---|---|---|
| **RDS / Aurora** | Automated snapshots + PITR (transaction logs); AWS Backup for cross-region/account copies | Continuous (PITR), daily snapshots | Retention up to 35 days built in; longer via AWS Backup. Test restore to a new instance. |
| **Self-managed PostgreSQL** | `pg_basebackup` + WAL archiving (pgBackRest, WAL-G to S3) for PITR; `pg_dump` for logical portability | WAL continuous; base weekly; dump daily | Logical dumps are slow to restore at scale but survive major version changes and corruption. Part VIII chapter 9. |
| **EBS volumes** | Snapshots (Data Lifecycle Manager or AWS Backup) | Daily or hourly | Crash-consistent; freeze or use app-level backups for databases. |
| **S3 data** | Versioning + cross-region replication + lifecycle; Object Lock for immutability; S3 Batch Replication for existing objects | Continuous | Versioning protects against overwrite/delete; replication protects against region loss; neither protects against a bug that writes bad data everywhere, so keep point-in-time copies if that matters. |
| **Configuration and secrets** | Infrastructure as code in Git; Secrets Manager replication; export of parameters | On change | Can you rebuild the environment from the repo alone? |
| **Encryption keys** | KMS keys are durable; multi-region keys for DR; document which keys protect which backups | — | A backup encrypted with a deleted key is gone. Protect key policies; disable before delete; 30-day deletion window. |
| **Code and artifacts** | Git remotes (plus a mirror), container registry replication | Continuous | The registry is a backup target too. |
| **DNS, certificates** | Zone exports; certificates reissuable | On change | Registrar access is the real single point of failure. |
| **Runbooks and credentials to restore** | Documented, accessible outside the system that failed | On change | If the runbook lives on the server that died, it does not exist. |

Encrypt all backups (KMS), restrict access (a backup role only; humans via break-glass), and tag them for cost and retention.

## Restore testing

Untested backups are hope, not strategy. Schedule and automate:

- **Monthly** (at least): restore the latest database snapshot to a fresh instance, run integrity checks (row counts, checksums, application smoke tests), record the elapsed time against RTO, destroy the instance. Automate with a pipeline or Lambda so it actually happens.
- **Quarterly**: a full environment rebuild in a separate account or region from IaC plus backups: infrastructure, secrets, data, DNS cutover to a test name. Time it. This is the DR drill.
- **After any change** to backup configuration, encryption keys or infrastructure code.
- **Measure**: last successful restore test date, duration, data verified. Alert if a test is overdue or fails. Report to the client.

```bash
# Example: automated RDS restore test (shell, run by a scheduled job)
SNAP=$(aws rds describe-db-snapshots --db-instance-identifier prod-db --snapshot-type automated \
      --query 'reverse(sort_by(DBSnapshots,&SnapshotCreateTime))[0].DBSnapshotIdentifier' --output text)
aws rds restore-db-instance-from-db-snapshot --db-instance-identifier restore-test-$(date +%Y%m%d) \
   --db-snapshot-identifier "$SNAP" --db-instance-class db.t4g.medium --db-subnet-group-name private-db \
   --vpc-security-group-ids sg-restoretest --no-publicly-accessible --tags Key=purpose,Value=restore-test
aws rds wait db-instance-available --db-instance-identifier restore-test-$(date +%Y%m%d)
# run verification queries against the restored endpoint, record timings and counts, then:
aws rds delete-db-instance --db-instance-identifier restore-test-$(date +%Y%m%d) --skip-final-snapshot
```

## The DR plan document

One page the on-call engineer can follow at 4 a.m.:

1. **Scenarios covered**: AZ failure, region failure, data corruption or deletion (including malicious), account compromise, loss of a key person.
2. **Decision authority**: who declares a disaster and authorises failover (and the cost it incurs).
3. **Contacts**: client, provider support, DNS registrar, on-call rota.
4. **Procedures per scenario**: numbered steps with commands, expected durations, verification checks and rollback.
5. **Dependencies**: what must exist beforehand (backup account access, break-glass credentials in a sealed location, IaC pipeline that can target the DR region).
6. **Communication templates**: internal, client, end users.
7. **Drill log**: dates, outcomes, time to recover, action items.

## Ransomware and malicious deletion

Assume an attacker with your production credentials will try to destroy backups. Defences: backups in a separate account with no cross-account delete permission from production; Object Lock / Vault Lock (immutable for the retention period); MFA delete on critical buckets; retention long enough to recover from a slow-burn compromise (30–90 days); alerts on backup deletion attempts and on backup job failures; and the restore drill that confirms the immutable copies are actually restorable.

## Common mistakes

- Backups never restored; discovered unusable during the incident.
- Backups in the same account/region as production, deletable by the same credentials.
- Database backups as volume snapshots only, without consistency or PITR.
- Encryption key deleted or inaccessible; backups unreadable.
- RPO and RTO never agreed; expectations discovered during the outage.
- Runbook stored on the system that failed.
- Backup jobs failing silently for weeks (no alert on failure or on age of last success).
- Retention too short to cover late-discovered corruption.

## Exercises

1. Write down RPO, RTO and retention for a system you operate; compare with what the current backups actually provide. Fix the biggest gap.
2. Automate a monthly restore test of your database with verification queries and timing; run it now and record the result.
3. Draft the one-page DR plan and run a tabletop drill: walk through the region-loss scenario step by step with a colleague and note every missing prerequisite.
