## The problem

Every application runs on a physical machine somewhere. Between that machine and your code are layers of abstraction, each trading control for convenience: virtual machines hide the hardware, containers hide the operating system, serverless hides the server. Picking the wrong layer costs money and operational pain; not understanding the layer you picked makes performance problems inexplicable ("why does my t3.micro get slow every afternoon?").

The further down the stack you go, the more you control and the more you must operate. A Forward Deployed Engineer's default should be as high up the stack as the requirements allow, dropping down only for specific reasons (cost at scale, special hardware, a client mandate, a dependency that needs a full OS).

## Virtualisation in brief

A **hypervisor** (KVM, Xen, AWS Nitro, VMware ESXi) runs directly on hardware and presents each guest VM with virtual devices. Modern hardware virtualisation (Intel VT-x, AMD-V) runs guest code natively on the CPU with the hypervisor intervening only for privileged operations and I/O. AWS Nitro offloads networking and storage to dedicated cards, so EC2 instances get near-bare-metal performance.

Consequences you will observe:

- **vCPU ≠ core**: on most x86 instances a vCPU is one hyperthread; two vCPUs are one physical core's two threads, not two cores. Graviton (ARM) instances map one vCPU to one physical core. Compare benchmarks, not vCPU counts.
- **Steal time** (`st` in `top`): the hypervisor scheduled another VM on your core. Significant on oversubscribed hosts and on burstable instances out of credits.
- **Network and disk performance** are per-instance allowances that scale with size; small instances have "up to" bandwidth with burst credits, and EBS throughput is capped per volume and per instance.

## Burstable instances

`t3`/`t4g` instances earn CPU credits while below a baseline utilisation (20% for a t3.medium) and spend them to burst to 100%. Out of credits, the CPU is throttled to the baseline (or you pay for unlimited mode). This is the cause of "the server is fine all morning and crawls after lunch": sustained load drained the credits. Burstable instances are excellent for dev/staging and low-traffic services, wrong for sustained CPU work. Monitor `CPUCreditBalance`.

## Sizing

Start from measurement, not guesses:

1. **CPU**: profile the application under a load test (Part XI chapter 8). Web APIs are usually I/O-bound and need fewer cores than people assume; serialisation, compression and TLS are the CPU costs. Target 50–60% utilisation at peak for headroom.
2. **Memory**: per-worker RSS × workers plus runtime baseline plus page cache for databases (Part I chapter 7). Memory is the resource that kills; oversize it relative to CPU.
3. **Disk**: capacity (data plus logs plus headroom), IOPS and throughput. gp3 EBS gives 3,000 IOPS and 125 MB/s baseline regardless of size, configurable upward; databases often need more. Local NVMe (instance store) is fast but ephemeral.
4. **Network**: bandwidth allowances per instance; packets per second limits matter for chatty services; NAT gateway and cross-AZ transfer costs.

Instance families: **general purpose** (m, t) for web servers; **compute optimised** (c) for CPU-heavy work; **memory optimised** (r, x) for databases and caches; **storage optimised** (i, d) for local disk I/O; **accelerated** (g, p, inf) for GPUs and ML. **Graviton** (ARM, `g` suffix like m7g) is typically 20–40% cheaper for the same performance when your software has ARM builds (most interpreted-language stacks and container images do; check native dependencies).

:::fde
For most client web applications the answer is Fargate for the API and workers, Lambda for event glue and scheduled jobs, and managed services for everything stateful. Choose EC2 when a dependency genuinely needs a VM, when the client already operates VMs well and wants consistency, or when sustained load makes reserved EC2 materially cheaper and someone will own patching. Always compute the three-year cost including people time, not just the instance price.
:::

## Cost basics

On-demand is the list price. **Savings Plans** and **Reserved Instances** discount 30–70% for one- or three-year commitments; commit only to the baseline you are certain of. **Spot** instances are spare capacity at up to 90% off that can be reclaimed with two minutes' notice; good for stateless workers and CI, wrong for databases. Right-sizing (turning off idle instances, downsizing underused ones, Graviton) usually saves more than any purchasing option. Part VII chapter 4.

## Common mistakes

- Burstable instances for sustained workloads; mysterious afternoon slowness.
- Comparing vCPUs across families as if equal.
- Undersized memory; OOM kills "fixed" by restarts.
- Databases on gp2 volumes starved of IOPS.
- Running VMs for a workload that would be cheaper and simpler on Fargate, or Lambda for a steady high-throughput API that would be cheaper on containers.
- Reserving capacity before measuring baseline usage.
- Ignoring Graviton because of an untested assumption about compatibility.

## Exercises

1. Load test a small service on a burstable and a non-burstable instance of similar price for 30 minutes; graph latency and CPU credits.
2. Build a three-year cost comparison for a workload (2 vCPU / 4 GB, 24×7) on EC2 on-demand, EC2 with a one-year savings plan, Fargate, and Lambda at an assumed request rate. Include a line for operational hours.
3. Rebuild one of your container images for ARM64 and run it on a Graviton instance or Fargate ARM task; compare cost and performance.
