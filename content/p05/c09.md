# Logs and journald

:::objectives
- Know where every kind of log lives on a Linux server and how to read it quickly under pressure.
- Configure journald persistence and limits, log rotation, and shipping to a central store.
- Emit application logs that are structured, bounded and free of secrets.
- Correlate proxy, application and system logs during an incident.
:::

:::prereq
Part I chapter 4; chapter 5 of this part; Part XI chapter 1 covers log design across services.
:::

## The problem

When something breaks, logs are the primary evidence, and they are useless if you cannot find them, if they were rotated away, if the disk they filled took the server down, or if the intruder deleted them. Logging on a server is a small set of decisions: where logs go, how long they stay, how they leave the machine, and what they contain.

## Where logs live

| Source | Location | Read with |
|---|---|---|
| systemd services (stdout/stderr) and kernel | the journal (`/var/log/journal` if persistent, else `/run/log/journal`) | `journalctl` |
| Traditional syslog consumers | `/var/log/syslog` (Debian/Ubuntu), `/var/log/messages` (RHEL) via rsyslog | `tail`, `less`, `grep` |
| Authentication | journal (`_SYSTEMD_UNIT=ssh.service`, `sudo`) and `/var/log/auth.log` / `/var/log/secure` | `journalctl -u ssh`, `last`, `lastb` |
| Nginx / Caddy | `/var/log/nginx/*.log`, `/var/log/caddy/*.log` | `tail -f`, `jq` |
| PostgreSQL | `/var/log/postgresql/` or the journal | `tail`, `pgBadger` |
| Package manager | `/var/log/apt/history.log`, `/var/log/dpkg.log`, `/var/log/dnf.log` | what changed and when |
| cloud-init | `/var/log/cloud-init.log`, `/var/log/cloud-init-output.log` | first-boot problems |
| Kernel ring buffer | `dmesg` (also in the journal) | OOM kills, disk errors, firewall drops |
| Audit | `/var/log/audit/audit.log` | `ausearch`, `aureport` |

## journalctl fluency

```bash
journalctl -u app -f                              # follow one service
journalctl -u app -n 200 --no-pager               # last 200 lines
journalctl -u app --since "2026-03-14 09:00" --until "09:30"
journalctl -u app -p err                          # priority err and worse (emerg..debug)
journalctl -b                                     # this boot;  -b -1 previous boot
journalctl -k                                     # kernel messages (OOM: journalctl -k | grep -i 'killed process')
journalctl _PID=12345                             # by PID;  _UID=1001 by user
journalctl -o json-pretty -u app -n 1             # every field journald stores
journalctl -u app -o cat                          # message only (handy for JSON logs → pipe to jq)
journalctl --disk-usage; sudo journalctl --vacuum-size=1G
journalctl -g 'request_id=7f3a'                   # grep across everything
```

Make the journal **persistent** (survive reboots) and **bounded**:

```ini
@file: /etc/systemd/journald.conf.d/10-server.conf
[Journal]
Storage=persistent
Compress=yes
SystemMaxUse=2G
SystemKeepFree=1G
MaxRetentionSec=1month
RateLimitIntervalSec=30s
RateLimitBurst=20000          # a chatty app should not be silently dropped; raise and alert instead
ForwardToSyslog=no            # unless rsyslog is your shipper
```

```bash
sudo mkdir -p /var/log/journal && sudo systemd-tmpfiles --create --prefix /var/log/journal && sudo systemctl restart systemd-journald
```

## Rotation for file-based logs

`logrotate` runs daily (`/etc/logrotate.d/*`):

```
@file: /etc/logrotate.d/app
/var/log/app/*.log {
    daily
    rotate 14
    missingok
    notifempty
    compress
    delaycompress
    dateext
    create 0640 app app
    sharedscripts
    postrotate
        systemctl kill -s HUP app.service >/dev/null 2>&1 || true   # app reopens log files on SIGHUP
    endscript
}
```

The `postrotate` step matters: a process that keeps the old file open after rotation fills the disk invisibly (Part I chapter 3). Prefer logging to stdout under systemd (the journal handles rotation) or to a shipper; file logs are for software that insists.

## Shipping logs off the box

Local logs are vulnerable (disk full, instance terminated, attacker with root) and hard to search across a fleet. Ship them:

- **CloudWatch agent** (AWS): tails files and/or the journal (via the `collectd`/`journald` input in recent versions, or rsyslog → file → agent) to CloudWatch Logs groups with retention; also collects memory and disk metrics (chapter 10). Configuration from SSM Parameter Store for fleets.
- **Vector, Fluent Bit, Promtail/Alloy, Filebeat**: lightweight shippers to any backend (OpenSearch, Loki, Elastic, S3, Datadog). Vector and Fluent Bit parse JSON, add host metadata, redact fields and buffer to disk when the backend is down.
- **rsyslog over TLS** to a central syslog server: traditional, still fine.

```json
@file: /opt/aws/amazon-cloudwatch-agent/etc/amazon-cloudwatch-agent.json (excerpt)
{
  "logs": {
    "logs_collected": {
      "files": {
        "collect_list": [
          { "file_path": "/var/log/nginx/api.access.log", "log_group_name": "/client/prod/nginx/access", "log_stream_name": "{instance_id}", "retention_in_days": 30 },
          { "file_path": "/var/log/app/app.log", "log_group_name": "/client/prod/app", "log_stream_name": "{instance_id}", "retention_in_days": 90, "timestamp_format": "%Y-%m-%dT%H:%M:%S" }
        ]
      }
    }
  }
}
```

Set **retention** on every group (CloudWatch Logs defaults to never expire, which is both a cost and a privacy problem); longer retention belongs in S3 with lifecycle policies. For audit logs, the tamper-evidence rules of Part IV chapter 22 apply: a separate group or account, restricted access.

## What the application should log

- **To stdout/stderr**, one JSON object per line, with `timestamp` (UTC ISO 8601), `level`, `message`, `logger`, `request_id`, `user_id`/`tenant_id` where relevant, `route`, `status`, `duration_ms`, `error.type`, `error.stack` for errors. Part XI chapter 1 defines the schema; keep it consistent across services.
- **Bounded**: no request/response bodies by default; truncate long fields; sample noisy debug logs.
- **No secrets or PII**: redaction at the logger (Part IV chapters 22–23); never log `Authorization`, `Cookie`, passwords, tokens, card numbers.
- **Levels used honestly**: ERROR means someone should look; WARNING means degraded but handled; INFO for lifecycle and request summaries; DEBUG off in production.
- **Request ID** in every line and in the proxy's access log, so one ID joins proxy, app and worker records.

## Reading logs under pressure

A method for "the API is returning errors":

```bash
# 1. Proxy: which requests fail, since when, how many
sudo tail -n 5000 /var/log/nginx/api.access.log | jq -r 'select(.status >= 500) | [.time, .status, .uri, .request_id, .urt] | @tsv' | tail -20
sudo tail -n 20000 /var/log/nginx/api.access.log | jq -r 'select(.status >= 500) | .time[0:16]' | sort | uniq -c    # per-minute histogram
# 2. Proxy error log: upstream refused? timed out?
sudo tail -n 100 /var/log/nginx/api.error.log
# 3. Application: follow the request ID
journalctl -u app -o cat --since "-30min" | grep 7f3a9c2e | jq .
# 4. System: anything killed or failing?
journalctl -k --since "-30min" | grep -iE 'oom|killed|error'; systemctl --failed
# 5. Dependencies: database and cache logs
journalctl -u postgresql --since "-30min" -p warning
```

Correlation by **time** and by **request ID** is the whole skill. Clocks must be synchronised and in UTC, or the time correlation lies.

## Common mistakes

- Journal volatile (lost on reboot) and unbounded, or file logs filling the root volume.
- Logs only on the host; gone with the instance, or with the intruder.
- CloudWatch groups with infinite retention.
- Logging request bodies with PII and tokens.
- Different timestamp formats and time zones across services.
- Rotation without reopening; deleted-but-open files.
- DEBUG in production flooding the journal and hitting rate limits silently.
- No request ID in the access log; proxy and app logs cannot be joined.

## Exercises

1. Make the journal persistent and bounded; reboot; confirm the previous boot's logs are available with `journalctl -b -1`.
2. Configure the CloudWatch agent (or Vector) to ship Nginx and application logs with 30-day retention; find a request by ID in the central store.
3. Produce a per-minute error histogram from your access logs with `jq`; then find the first failing request's ID and trace it through the application log.
