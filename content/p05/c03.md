# SSH and Key-Based Access

:::objectives

- Know when to replace SSH with SSM Session Manager or certificate-based access.

## The problem

SSH is the administrative door to every Linux server. Password authentication on a public SSH port is attacked within minutes of a server coming online, continuously, by automated credential-guessing. Keys fix that, but introduce their own management problem: who has which key on which server, how keys are protected, and how access ends when people leave. Most organisations' SSH key sprawl is unknowable, which is why the modern direction is to remove the door entirely (SSM) or to issue short-lived certificates.

## How SSH works

1. **Transport**: the client connects (TCP 22), negotiates algorithms, and performs a key exchange to establish an encrypted channel.
2. **Server authentication**: the server presents its **host key**; the client checks it against `~/.ssh/known_hosts`. The first connection shows a fingerprint prompt (trust on first use); a *changed* host key later produces the loud "REMOTE HOST IDENTIFICATION HAS CHANGED" warning, which means either the server was rebuilt or you are being intercepted. Do not blindly delete the line; verify.
3. **User authentication**: public key (the server has your public key in `~/.ssh/authorized_keys`; it sends a challenge your private key signs), or password, or certificate, optionally plus a second factor.
4. **Session**: a shell, a command, or forwarded ports/sockets.

## Keys

```bash
ssh-keygen -t ed25519 -a 64 -C "ana@laptop-2026"    # Ed25519: small, fast, modern; -a adds KDF rounds protecting the passphrase
# → ~/.ssh/id_ed25519 (private, mode 600) and ~/.ssh/id_ed25519.pub (public)
ssh-add --apple-use-keychain ~/.ssh/id_ed25519       # macOS: load into the agent; Linux: ssh-add
ssh-copy-id -i ~/.ssh/id_ed25519.pub deploy@server   # append the public key to the server's authorized_keys (or do it via cloud-init/config management)
```

Rules: **one key per person per device**, with a passphrase, stored only on that device (ideally in a hardware token: YubiKey via FIDO2 `ssh-keygen -t ed25519-sk`, or the macOS Secure Enclave). Never share private keys; never copy them to servers; never commit them. The **public** key is not secret and can be published freely. Use the SSH agent to avoid typing passphrases, but do not forward the agent to untrusted hosts (`ForwardAgent yes` lets root on that host use your key; use `ProxyJump` instead). Rotate keys yearly or when a device is lost.

Client configuration keeps things sane:

```ssh-config
@file: ~/.ssh/config
Host *
    AddKeysToAgent yes
    IdentitiesOnly yes                 # only offer the configured key, avoiding "too many authentication failures"
    ServerAliveInterval 30
    HashKnownHosts yes

Host bastion
    HostName bastion.client.com
    User ana
    IdentityFile ~/.ssh/id_ed25519_client

Host prod-app-*
    User deploy
    ProxyJump bastion                  # transparent jump; your key never leaves the laptop
    IdentityFile ~/.ssh/id_ed25519_client
```

```bash
ssh prod-app-1                         # via bastion automatically
ssh -L 15432:prod-db.internal:5432 bastion     # local port forward: psql to localhost:15432 reaches the private DB
ssh -N -D 1080 bastion                 # SOCKS proxy for browsing internal dashboards
scp -J bastion file.tgz prod-app-1:/tmp/
```

## Hardening sshd

```sshd-config
@file: /etc/ssh/sshd_config.d/10-hardening.conf
Port 22                                 # changing the port reduces log noise, not risk; keep 22 unless policy says otherwise
PasswordAuthentication no               # keys only
KbdInteractiveAuthentication no
PermitRootLogin no                      # log in as a user, then sudo
PubkeyAuthentication yes
AuthenticationMethods publickey         # or "publickey,keyboard-interactive" with a PAM MFA module for a second factor
MaxAuthTries 3
LoginGraceTime 20
AllowGroups ssh-users                   # only members of this group may log in
X11Forwarding no
AllowAgentForwarding no
AllowTcpForwarding yes                  # needed for port forwarding; set no on application servers if unused
ClientAliveInterval 300
ClientAliveCountMax 2
LogLevel VERBOSE                        # logs key fingerprints used: you can tell *which* key logged in
# Modern algorithms only (Mozilla modern profile); drop legacy ciphers/MACs/KEX
KexAlgorithms sntrup761x25519-sha512@openssh.com,curve25519-sha256
Ciphers chacha20-poly1305@openssh.com,aes256-gcm@openssh.com,aes128-gcm@openssh.com
MACs hmac-sha2-512-etm@openssh.com,hmac-sha2-256-etm@openssh.com
```

```bash
sudo sshd -t && sudo systemctl reload ssh      # ALWAYS test the config before reloading; keep your current session open until a new login works
```

Plus: a firewall rule limiting port 22 to known ranges or the bastion (Part II chapter 15); `fail2ban` or `sshguard` to ban brute-forcers; unattended security updates for OpenSSH; no SSH at all on servers that do not need it (containers, Fargate).

## Managing a team's access

The simple approach (authorized_keys managed by configuration management or cloud-init, one `AllowGroups` group, keys listed in a repository) works for small teams and single-client deployments if you are disciplined: keys are added and removed by a reviewed change, never by hand on the server; every key has an owner and a comment; a quarterly audit lists keys per server against current staff; offboarding removes keys everywhere the same day.

It breaks down as servers and people multiply. Better options:

- **SSH certificates**: a certificate authority (your own `ssh-keygen` CA, HashiCorp Vault's SSH secrets engine, Teleport, Smallstep) signs short-lived user certificates (hours) after SSO authentication; servers trust the CA (`TrustedUserCAKeys`) instead of individual keys. No `authorized_keys` to manage; offboarding is automatic when SSO access ends; certificates carry principals and can be audited. Host certificates likewise eliminate known_hosts prompts.
- **SSM Session Manager** (Part II chapter 16): no SSH daemon exposed, IAM-based, logged. For AWS fleets this is the recommended default; keep sshd for emergencies behind the bastion or disable it entirely.
- **Identity-aware access tools** (Teleport, Boundary, Tailscale SSH): SSO, short-lived credentials, session recording.

## Auditing and logging

`journalctl -u ssh` shows logins with the key fingerprint at `LogLevel VERBOSE`, so "who logged in" is answerable even with shared accounts (do not have shared accounts). Ship auth logs off-box. Alert on logins from unexpected sources, root login attempts, and bursts of failures. Session recording (SSM, Teleport, or `script`/auditd on the host) is needed for regulated environments.

## Host keys and rebuilt servers

Immutable infrastructure rebuilds servers often, generating new host keys and triggering client warnings. Options: publish host keys via DNS SSHFP records, use host certificates signed by your CA, or pre-seed known host keys from a secure source. Do not train people to ignore the warning by making it routine.

## Common mistakes

- Password authentication left on; root login allowed.
- One shared key pair for the whole team, copied to every laptop and CI.
- Private keys on servers "for convenience" (jump host with keys to everything else).
- Agent forwarding to shared hosts.
- Editing `sshd_config` and restarting without `sshd -t`; locked out.
- SSH open to `0.0.0.0/0`.
- Keys of departed staff still in `authorized_keys` on servers nobody remembers.
- Treating a host key change warning as noise.
