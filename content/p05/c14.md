# Walkthrough: A Secure Linux Server for a Backend Application

:::objectives
- Build, from a blank VM, a hardened single-server deployment of a backend API with HTTPS, process supervision, logging, monitoring and backups.
- Understand every step well enough to adapt it to a client's constraints.
- Verify the result against a checklist and know its limits.
:::

:::prereq
Every previous chapter in this part. Costs: a small cloud VM (a few dollars per month on the smallest instance types; free tier may cover it), a domain you control. Delete resources when finished.
:::

## Scope and limits

This walkthrough produces the architecture many small client projects actually need: one VM running a FastAPI (or Node) application behind Caddy, with PostgreSQL either on the same VM (smallest budgets) or on RDS (recommended), automated certificates, systemd supervision, journald plus CloudWatch logs, basic monitoring and alarms, and nightly backups with a tested restore. It is secure and operable. It is **not** highly available: a single VM has downtime on reboots and failures. Part VII upgrades this to a load-balanced, multi-AZ deployment; Part IX chapter 17 discusses when the single-server design is the right call.

## Step 1: provision

In AWS (console or, better, Terraform from Part X): a VPC with a public subnet (for the instance) and private subnets (for RDS); a security group `sg-web` allowing 80/443 from `0.0.0.0/0` and `::/0`; a security group `sg-db` allowing 5432 from `sg-web`; an IAM role `app-instance` with `AmazonSSMManagedInstanceCore`, `CloudWatchAgentServerPolicy`, read access to one Secrets Manager secret and read/write to the uploads bucket prefix; a `t4g.small` Ubuntu 24.04 ARM instance with IMDSv2 required, 20 GB gp3 root, an Elastic IP; an RDS PostgreSQL 16 `db.t4g.micro` instance in the private subnets with `sg-db`, encryption, 7-day backups, deletion protection, and a master password generated into Secrets Manager. Point `api.client.com` at the Elastic IP.

Cost: roughly $12/month for the instance, $12–15 for RDS, a few dollars for storage, logs and the EIP; verify current prices.

## Step 2: first boot configuration

Connect with `aws ssm start-session --target i-…` (no SSH, no keys). Then:

```bash
sudo apt update && sudo apt full-upgrade -y
sudo apt install -y unattended-upgrades chrony fail2ban nftables jq htop sysstat \
    python3.12 python3.12-venv build-essential libpq-dev
sudo hostnamectl set-hostname api-1.prod.client.internal
sudo timedatectl set-timezone UTC && sudo systemctl enable --now chrony
sudo dpkg-reconfigure -plow unattended-upgrades    # enable; set Automatic-Reboot "true" at 03:30 in 50unattended-upgrades
```

Harden sshd anyway (in case it is ever enabled) with the chapter 3 drop-in, and **disable it** since SSM is the access path: `sudo systemctl disable --now ssh`. Install the CloudWatch agent (`amazon-cloudwatch-agent` from the AWS package) and the SSM agent is already present on Ubuntu AWS images.

## Step 3: users and layout

```bash
sudo useradd --system --home /srv/app --shell /usr/sbin/nologin --no-create-home app
sudo install -d -o root -g app -m 750 /srv/app /srv/app/releases /etc/app
sudo install -d -o app -g app -m 750 /srv/app/shared /srv/app/shared/uploads /var/lib/app
```

Deploy user: with SSM there is no human login; deployments arrive via a pipeline that copies an artifact from S3 (or pulls a container image) and switches a symlink, executed by `ssm send-command` or an SSM document, as the `root` or a dedicated `deploy` user with the sudoers rule from chapter 4.

## Step 4: application

```bash
# as root, deploying release 2026-03-14-1
R=/srv/app/releases/2026-03-14-1
sudo mkdir -p $R && aws s3 cp s3://client-prod-artifacts/app-2.4.0.tar.gz - | sudo tar -xzf - -C $R
sudo python3.12 -m venv $R/.venv && sudo $R/.venv/bin/pip install --require-hashes -r $R/requirements.txt
sudo chown -R root:app $R && sudo chmod -R o-rwx $R
sudo ln -sfn $R /srv/app/current
```

Environment file at `/etc/app/app.env` (640 root:app) contains non-secret config (`ENV=prod`, `DATABASE__HOST=…rds.amazonaws.com`, `AWS_REGION`, `SECRET_NAME=prod/app/db`); the application fetches the database credentials from Secrets Manager at start-up using the instance role (Part IV chapter 17) and connects with `sslmode=verify-full`.

Install the systemd unit from chapter 5 (with `MemoryMax`, sandboxing, `Type=notify`, `TimeoutStopSec=30`, `User=app`), run migrations as a one-shot (`ExecStartPre` or a separate `app-migrate.service` run by the deploy), then `systemctl enable --now app` and confirm `curl -s localhost:8000/health/ready`.

## Step 5: Caddy

Install Caddy (chapter 8) and the Caddyfile for `api.client.com` proxying to `127.0.0.1:8000`, with headers, body limit, JSON access log, and a `handle_errors` maintenance page. `systemctl reload caddy`; watch `journalctl -u caddy -f` for the certificate issuance; `curl -I https://api.client.com/health/ready`.

## Step 6: host firewall

Apply the nftables ruleset from chapter 7: input policy drop; allow established, loopback, rate-limited ICMP, 80 and 443 from anywhere; **no SSH rule** (SSM needs only outbound 443). Enable `nftables.service`. The security group already restricts inbound; the host firewall is defence in depth and local documentation.

## Step 7: logging and monitoring

Journald persistent and bounded (chapter 9). CloudWatch agent configuration shipping `/var/log/caddy/api.access.log`, the journal (via a small rsyslog or the agent's journald support) and collecting memory, disk and swap metrics; store the config in SSM Parameter Store and start the agent with it. Alarms (chapter 10): disk > 80%, memory available < 15%, CPU credits low, status check failed, `systemctl --failed` metric > 0, plus application alarms from Caddy's logs via a metric filter (5xx count). An SNS topic emails the on-call address and the client's nominated contact.

External checks: a Route 53 health check or a CloudWatch Synthetics canary hitting `https://api.client.com/health/ready` every minute from outside, alarming on failure; a certificate expiry check (the canary can assert days remaining, or a scheduled Lambda).

## Step 8: backups

RDS automated backups and PITR are on; add an AWS Backup plan copying daily snapshots to a backup vault in a second region (and, for a client with the budget, a separate account with Vault Lock). For uploads, enable S3 versioning and a lifecycle rule; replicate cross-region if the data warrants it. The instance itself is disposable: everything needed to rebuild it is the IaC plus the artifact plus the environment file (store a copy of `/etc/app/app.env` and the Caddyfile in the deployment repository, no secrets). Schedule the monthly restore test from chapter 11 and run it once now.

## Step 9: verify

```checklist
# Secure single-server deployment: acceptance checks
- `curl -I https://api.client.com/health/ready` returns 200 with HSTS and security headers; `http://` redirects to `https://`.
- SSL Labs (or testssl.sh) grade A; certificate auto-renewal visible in Caddy logs.
- `ss -ltnp` shows only Caddy on 80/443 (all interfaces) and the app on 127.0.0.1:8000; `nft list ruleset` matches intent.
- `systemctl is-enabled app caddy nftables chrony unattended-upgrades amazon-cloudwatch-agent` all enabled; `systemctl --failed` empty.
- `systemd-analyze security app.service` reports a good score; the service runs as `app`; `/srv/app/current` not writable by `app`.
- No SSH listening; SSM session works; CloudTrail shows the session.
- Database reachable only from the instance (test from another host fails with timeout); `sslmode=verify-full` in use; credentials fetched from Secrets Manager (none on disk).
- Logs visible in CloudWatch with a request ID joining Caddy and app entries; retention set.
- Alarms exist and have fired at least once in a test (fill disk with fallocate; stop the app).
- Backups: snapshot list non-empty; cross-region copy present; restore test performed and timed.
- Reboot test: `sudo reboot`; service returns without intervention; downtime measured.
- Runbook written: deploy, rollback (switch symlink, restart), rotate DB password, restore DB, renew cert manually, recover from full disk.
```

## Step 10: operate

Monthly maintenance (chapter 12), alarms routed to a human, the runbook kept with the code, and an honest statement to the client of what this design does and does not provide: single-instance availability (reboot downtime, no AZ redundancy), scaling by resizing, and the upgrade path to Part VII's architecture when the requirements justify it.

## Variations

- **PostgreSQL on the same VM** (smallest budgets): install PostgreSQL 16, listen on `127.0.0.1` only, `scram-sha-256` auth, a dedicated application role with least privilege, data on a separate EBS volume (chapter 6), nightly `pg_dump` to S3 plus WAL archiving with pgBackRest or WAL-G for PITR, restore tested. Accept that database and app share failure and resource domains.
- **Docker on the VM**: run the application as a container under systemd (`ExecStart=/usr/bin/docker run --rm --name app -p 127.0.0.1:8000:8000 …`) with the image pulled from ECR; mind the Docker/firewall interaction (chapter 7); Part VI covers images.
- **Client-provided VM, no AWS**: replace SSM with hardened SSH via a bastion or Tailscale, Secrets Manager with Vault or a 600-mode file plus documented rotation, CloudWatch with Prometheus/Grafana or a hosted logging service, RDS with local PostgreSQL and off-site backups to object storage. The principles do not change.

## Common mistakes in this build

- Forgetting to disable password SSH or to disable SSH at all when using SSM.
- App bound to `0.0.0.0:8000` with the security group accidentally open on 8000.
- Secrets in `app.env`.
- Caddy started before DNS points at the instance (certificate issuance fails until it does; Caddy retries).
- No alarm tested; the first real alarm reveals the email was wrong.
- Restore never tested.
- No runbook; the next person rebuilds from memory.

## Exercises

1. Build the entire walkthrough in a sandbox account with a test domain. Time each step. Delete everything afterwards and confirm the bill.
2. Run the acceptance checklist and fix every failing item. Then run the reboot test and measure downtime.
3. Write the runbook (deploy, rollback, rotate, restore, renew, disk-full) and hand it to a colleague to execute a rollback without your help.
