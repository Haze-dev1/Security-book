## The problem

A server that does not come up after a reboot is a worse incident than one that crashes, because the usual tools are gone. Knowing the boot sequence tells you where it stopped and what to look at (the serial console, the recovery volume, the cloud-init log). It also explains how your application becomes a service that starts automatically, in the right order, with the right environment, which is the subject of chapter 5.

A modern cloud VM reaches the login prompt in 20–60 seconds; your service's start-up time is added on top. Know this number for your systems; it bounds how fast autoscaling can respond and how long a reboot-based incident lasts.

## Anatomy of a running server

- **Kernel**: scheduler, memory, filesystems, networking, security modules (AppArmor/SELinux). Parameters via `sysctl` (`/etc/sysctl.d/`); loaded modules via `lsmod`. Version via `uname -r`; kernel updates require a reboot (or live patching).
- **systemd**: PID 1 and a family of tools: `systemctl` (units), `journalctl` (logs), `timedatectl`, `hostnamectl`, `networkctl`/`resolvectl` (where systemd-networkd/resolved are used), `systemd-analyze blame` (boot timing). Unit types: services, sockets, timers (cron replacement), mounts, targets. Chapter 5.
- **udev**: device management; creates `/dev` entries and applies rules (e.g., persistent names for NVMe volumes).
- **Networking**: configured by netplan (Ubuntu), NetworkManager, or systemd-networkd; on cloud instances DHCP from the VPC. Chapter 7.
- **Time**: chrony or systemd-timesyncd against the cloud time source. Essential (Part I chapter 3).
- **Logging**: journald collects everything; rsyslog may forward to files or remote collectors; the CloudWatch agent or a log shipper sends logs off-box. Chapter 9.
- **Scheduled jobs**: cron (`/etc/cron.d`, user crontabs) or systemd timers (preferred: logging, dependencies, randomised delays).
- **Users and access**: `/etc/passwd`, `/etc/group`, `sudoers`, `sshd`. Chapters 3 and 4.
- **Packages**: apt/dnf with the distribution's repositories plus any you added; unattended upgrades for security patches. Chapter 12.
- **Filesystems and mounts**: `/etc/fstab`, LVM, EBS volumes attached by device name. Chapter 6.

## Cloud-init and user data

User data is the standard way to turn a base image into a configured server at first boot:

```yaml
#cloud-config
package_update: true
package_upgrade: true
packages: [nginx, chrony, fail2ban, unattended-upgrades]
users:
  - name: deploy
    groups: [sudo]
    shell: /bin/bash
    sudo: "ALL=(ALL) NOPASSWD:ALL"
    ssh_authorized_keys:
      - ssh-ed25519 AAAA... deploy@laptop
write_files:
  - path: /etc/sysctl.d/90-app.conf
    content: |
      net.core.somaxconn = 4096
      net.ipv4.ip_local_port_range = 1024 65535
  - path: /etc/systemd/system/app.service
    content: |
      [Unit]
      Description=App
      After=network-online.target
      Wants=network-online.target
      [Service]
      User=app
      EnvironmentFile=/etc/app/app.env
      ExecStart=/srv/app/.venv/bin/gunicorn app.main:app -c /srv/app/gunicorn.conf.py
      Restart=always
      [Install]
      WantedBy=multi-user.target
runcmd:
  - sysctl --system
  - useradd --system --home /srv/app --shell /usr/sbin/nologin app
  - aws s3 cp s3://client-prod-artifacts/app-$(curl -s http://169.254.169.254/latest/meta-data/tags/instance/AppVersion).tar.gz /tmp/app.tgz
  - mkdir -p /srv/app && tar -xzf /tmp/app.tgz -C /srv/app && chown -R root:app /srv/app
  - systemctl daemon-reload && systemctl enable --now app
```

Rules: keep user data **idempotent** and **short**; bake slow, stable steps (package installs, runtime) into an AMI (Part VII chapter 7) and leave only instance-specific configuration to boot time; fetch secrets from Secrets Manager via the instance role, never embed them (user data is readable by anyone with `ec2:DescribeInstanceAttribute` and from the instance itself via IMDS); log to `/var/log/cloud-init-output.log` and check it when an instance misbehaves. For fleets, prefer immutable images plus minimal user data over long configuration scripts; configuration management tools (Ansible) fill the gap for VMs that must be maintained in place.

## When it will not boot

Without SSH, your tools are: the **serial console** (EC2 Serial Console or "Get system log" screenshot) showing kernel and systemd messages; **cloud-init logs** once you can reach the disk; and the **rescue procedure**: stop the instance, detach its root volume, attach it to a healthy instance as a secondary volume, mount it, fix the problem (bad `/etc/fstab` entry, broken sshd config, full disk, wrong permissions on `/etc/sudoers`), detach, reattach as root, start. Common causes: an `fstab` entry for a volume that no longer exists (boot hangs waiting; use `nofail` on non-root mounts), a kernel update that failed, disk full preventing services from starting, a typo in `sshd_config` (always `sshd -t` before restart), or a security group/NACL change that merely *looks* like a boot failure.

```bash
systemd-analyze blame | head                 # what took long at boot
systemctl --failed                           # units that failed
journalctl -b -p err                         # errors since this boot
journalctl -b -1 -e                          # end of the previous boot's log (why did it go down?)
sudo cat /var/log/cloud-init-output.log | tail -50
```

## Reboots in production

Kernel and some library updates require reboots. Plan them: behind a load balancer with at least two instances, drain one (deregister or set unhealthy), reboot, verify, re-register, repeat. Single-instance systems need a maintenance window and a communicated downtime. Test that services come back without manual steps (`systemctl is-enabled`); a service that someone started by hand and never enabled is a classic post-reboot outage.

## Common mistakes

- Services started manually and never enabled; outage after the first reboot.
- Long, non-idempotent user-data scripts that fail halfway.
- Secrets in user data.
- `fstab` entries without `nofail` for optional volumes.
- Editing `sshd_config` without `sshd -t`, locking yourself out on restart.
- No time sync in a custom image.
- Health check grace period shorter than boot plus application start-up, causing ASG replacement loops.
- Not knowing how long a boot takes until the day it matters.
