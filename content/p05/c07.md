# Network Configuration and Host Firewalls

:::objectives
- Inspect and configure a server's interfaces, addresses, routes and DNS settings, and understand how cloud networking supplies them.
- Lock down a host with nftables or ufw, default deny, with rules you can read and test.
- Reconcile host firewalls with Docker, cloud security groups and IPv6.
- Diagnose host-level connectivity problems in minutes.
:::

:::prereq
Part II chapters 3, 4, 5 and 15.
:::

## The problem

A server's network configuration is mostly supplied by the cloud (DHCP for addresses, VPC routing, security groups for filtering), which is why engineers rarely look at it until something breaks: a second interface that does not route, DNS pointing at the wrong resolver after a change, IPv6 silently enabled, Docker publishing a port through the firewall. Host-level knowledge is also what you need on client-owned VMs and on-premises servers where there is no VPC doing the work.

## Inspecting

```bash
ip -br addr                     # interfaces and addresses, brief
ip -br link                     # link state (UP/DOWN), MACs
ip route; ip -6 route           # routing tables; "default via" is the gateway
ip route get 8.8.8.8            # which interface/gateway a destination uses
resolvectl status               # DNS servers per interface (systemd-resolved); else cat /etc/resolv.conf
ss -ltnup                       # what is listening, on which address
ping -c 3 <gateway>; ping -c 3 1.1.1.1; dig +short example.com    # L3, Internet, DNS in order
networkctl status               # systemd-networkd summary (where used)
```

Cloud specifics: the primary interface gets its private IP from the VPC via DHCP, and DNS points at the VPC resolver (`.2` of the VPC CIDR) through `systemd-resolved`'s stub (`127.0.0.53`) on Ubuntu; the public IP is never visible on the interface (it is NAT at the Internet Gateway); the MTU is 9001 inside a VPC (jumbo frames) but 1500 toward the Internet, handled by path MTU discovery, which breaks if ICMP is blocked.

## Configuring

Ubuntu uses **netplan** (YAML in `/etc/netplan/`, rendering to systemd-networkd or NetworkManager); RHEL-family uses NetworkManager (`nmcli`). On cloud images the primary interface is DHCP and you should leave it alone. Configuration you might actually do:

```yaml
@file: /etc/netplan/60-secondary.yaml  (a second ENI with a static route for a private network)
network:
  version: 2
  ethernets:
    ens6:
      dhcp4: true
      dhcp4-overrides: { use-routes: false }     # do not install a second default route
      routes:
        - to: 192.168.50.0/24
          via: 10.20.65.1
```

```bash
sudo netplan try                 # applies with automatic rollback in 120 s if you lose connectivity; then `netplan apply`
```

Multiple interfaces need **policy routing** so replies leave via the interface they arrived on (asymmetric routing is dropped by reverse-path filtering and by cloud security groups). The `amazon-ec2-net-utils` package handles this automatically for secondary ENIs on Amazon Linux and Ubuntu AWS images; on other systems you configure `ip rule`/`ip route table` entries.

DNS: on servers, point at the VPC resolver or your corporate resolvers; set search domains for internal names; avoid hard-coding public resolvers inside a VPC (you lose private hosted zones). `resolvectl flush-caches` after record changes.

Hostnames: `hostnamectl set-hostname app-1.prod.client.internal`; keep `/etc/hosts` resolving the hostname to a local address so tools that resolve the local hostname do not hang.

## Kernel network parameters

```ini
@file: /etc/sysctl.d/90-network.conf
net.ipv4.ip_forward = 0                         # 1 only on routers/NAT instances/Docker hosts (Docker sets it)
net.ipv4.conf.all.rp_filter = 1                 # drop spoofed/asymmetric packets (set 2 = loose on multi-homed hosts)
net.ipv4.conf.all.accept_redirects = 0
net.ipv4.conf.all.send_redirects = 0
net.ipv4.conf.all.accept_source_route = 0
net.ipv4.conf.all.log_martians = 1
net.ipv4.tcp_syncookies = 1                     # SYN flood resistance
net.core.somaxconn = 4096                       # listen backlog ceiling (Part II chapter 5)
net.ipv4.ip_local_port_range = 1024 65535       # more ephemeral ports for busy clients/proxies
net.ipv4.tcp_tw_reuse = 1
net.ipv4.tcp_keepalive_time = 300               # detect dead peers sooner (default 7200)
net.ipv4.tcp_keepalive_intvl = 30
net.ipv4.tcp_keepalive_probes = 5
net.ipv6.conf.all.disable_ipv6 = 0              # keep IPv6 if the network provides it; disable deliberately (1) if not managed
```

Apply with `sudo sysctl --system`. Containers inherit the host's network namespace settings for some parameters and have their own for others; Kubernetes exposes safe sysctls per pod.

## Host firewall with nftables

Cloud security groups filter before packets reach the instance, but a host firewall adds defence in depth, protects against misconfigured groups, documents intent locally, and is the only control on non-cloud servers. `nftables` is the current Linux framework (`iptables` commands are now a compatibility layer over it).

```nft
@file: /etc/nftables.conf
#!/usr/sbin/nft -f
flush ruleset

define ADMIN_NETS = { 203.0.113.0/29, 10.20.0.0/16 }   # office + VPC (bastion lives there)

table inet filter {
  set ratelimit_ssh { type ipv4_addr; flags dynamic, timeout; timeout 10m; }

  chain input {
    type filter hook input priority filter; policy drop;

    ct state invalid drop
    ct state established,related accept
    iif "lo" accept

    # ICMP/ICMPv6 needed for PMTU, neighbour discovery, diagnostics (rate-limited)
    ip protocol icmp icmp type { echo-request, destination-unreachable, time-exceeded, parameter-problem } limit rate 10/second accept
    ip6 nexthdr icmpv6 icmpv6 type { echo-request, destination-unreachable, packet-too-big, time-exceeded, parameter-problem, nd-neighbor-solicit, nd-neighbor-advert, nd-router-advert } accept

    # SSH only from admin networks, with per-source rate limiting
    tcp dport 22 ip saddr $ADMIN_NETS ct state new add @ratelimit_ssh { ip saddr limit rate 6/minute } accept

    # Web (if this host terminates TLS itself; otherwise only the app port from the LB subnet)
    tcp dport { 80, 443 } accept
    # Application port from the load balancer subnets only
    tcp dport 8000 ip saddr { 10.20.0.0/20, 10.20.16.0/20, 10.20.32.0/20 } accept
    # Node exporter / monitoring from the monitoring host only
    tcp dport 9100 ip saddr 10.20.70.5 accept

    log prefix "nft input drop: " limit rate 5/minute
  }
  chain forward { type filter hook forward priority filter; policy drop; }
  chain output  { type filter hook output  priority filter; policy accept; }
}
```

```bash
sudo nft -c -f /etc/nftables.conf        # check syntax
sudo nft -f /etc/nftables.conf           # apply (keep your SSH session; test a new connection before closing it)
sudo systemctl enable --now nftables     # persist at boot
sudo nft list ruleset                    # view
sudo nft list set inet filter ratelimit_ssh
journalctl -k | grep 'nft input drop' | tail
```

`ufw` provides the same with a simpler front end (Part II chapter 15 showed it); use whichever the team will actually maintain. Both are stateful: allow inbound once and replies flow.

Outbound restriction (policy drop on output with explicit allows for DNS, NTP, package mirrors, your AWS endpoints, your dependencies) is a strong control for database and processing tiers; it requires knowing your dependencies and maintaining the list. Start with logging outbound connections (or VPC Flow Logs) to learn them.

## Docker and the host firewall

Docker programs iptables/nftables directly: published ports (`-p 8080:80`) are DNAT'd in the `nat` table and accepted in the `DOCKER` chain *before* your input rules. ufw does not see them; your nftables input chain is bypassed because the packets are *forwarded* to the container, not delivered to the host. Options: bind publications to localhost (`-p 127.0.0.1:8080:80`) and front with a proxy; add rules in the `DOCKER-USER` chain (iptables) which Docker guarantees to evaluate first; set `"iptables": false` in the daemon config and manage everything yourself (expert mode); or rely on cloud security groups as the authoritative filter and treat the host firewall as secondary on Docker hosts. Document whichever you choose; this surprise has exposed many databases.

## IPv6

If the VPC assigns IPv6 addresses, the host has a globally routable address with no NAT between it and the Internet; only security groups and the host firewall protect it. Either filter IPv6 identically (the `inet` family table above covers both) or disable IPv6 on hosts that should not have it. Services bound to `::` listen on IPv4 too (dual-stack) by default on Linux.

## Diagnosing host connectivity

Order: link up (`ip -br link`) → address present (`ip -br addr`) → route exists (`ip route get`) → gateway reachable (`ping`) → DNS (`resolvectl`, `dig`) → firewall (is the drop logged? `nft list ruleset`, `journalctl -k`) → service listening on the right address (`ss -ltnp`) → security group / NACL (cloud side) → remote end. For "works from the host, not from outside": bind address, host firewall, Docker forwarding, security group, in that order. Part II chapter 19 has the full toolkit.

## Common mistakes

- Two default routes after adding an ENI; traffic leaves the wrong interface and is dropped.
- Hard-coded public DNS inside a VPC; private zones stop resolving.
- IPv6 enabled with no filtering.
- Host firewall bypassed by Docker-published ports.
- Applying firewall rules without a connectivity test, locking out SSH.
- Blocking all ICMP, breaking path MTU discovery; large transfers hang.
- `rp_filter=1` on multi-homed hosts without policy routing, dropping legitimate replies.
- Forgetting to persist nftables at boot.

## Exercises

1. Apply the nftables ruleset on a test VM (adjusting networks) from a session you keep open; verify SSH from an allowed and a disallowed source, and find the drop in the kernel log.
2. Publish a container port with Docker and demonstrate it bypasses the input chain; fix with a `DOCKER-USER` rule or a localhost bind.
3. Attach a secondary ENI to a test instance, observe the routing table, and configure it so that only the intended traffic uses it.
