- Diagnose services that fail to start, restart in loops, or hang on shutdown.

## The problem

A process started from a shell dies with the shell. A production service must start at boot in the right order, run as the right user with the right environment, be restarted when it crashes, stop gracefully when asked, have its output captured, and be constrained so that a bug or a compromise cannot take the machine with it. That is process supervision, and on Linux the supervisor is [[systemd]].

## A production unit file

```ini
@file: /etc/systemd/system/app.service
[Unit]
Description=Client App API (gunicorn)
Documentation=https://wiki.client.com/runbooks/app
After=network-online.target postgresql.service
Wants=network-online.target
StartLimitIntervalSec=300
StartLimitBurst=5

[Service]
Type=notify                                   # gunicorn/uvicorn support sd_notify; use 'simple' or 'exec' otherwise
User=app
Group=app
WorkingDirectory=/srv/app/current
EnvironmentFile=/etc/app/app.env               # KEY=value lines, 640 root:app; no secrets if a secrets manager is used at runtime
Environment=PYTHONUNBUFFERED=1
ExecStartPre=/srv/app/current/.venv/bin/python -m app.preflight     # validate config, check migrations applied; fail fast
ExecStart=/srv/app/current/.venv/bin/gunicorn app.main:app -c /srv/app/current/gunicorn.conf.py
ExecReload=/bin/kill -HUP $MAINPID
KillSignal=SIGTERM
KillMode=mixed                                 # SIGTERM to main, then SIGKILL to the whole group after the timeout
TimeoutStopSec=30                              # must exceed the app's graceful drain timeout
Restart=always
RestartSec=2
LimitNOFILE=65536
# Resource limits (cgroups)
MemoryMax=1536M
MemoryHigh=1280M
CPUQuota=200%                                  # two cores
TasksMax=4096
# Sandboxing
NoNewPrivileges=yes
ProtectSystem=strict                           # whole filesystem read-only except...
ReadWritePaths=/srv/app/shared/uploads /var/lib/app
ProtectHome=yes
PrivateTmp=yes
PrivateDevices=yes
ProtectKernelTunables=yes
ProtectKernelModules=yes
ProtectControlGroups=yes
RestrictAddressFamilies=AF_INET AF_INET6 AF_UNIX
RestrictNamespaces=yes
LockPersonality=yes
MemoryDenyWriteExecute=yes                     # breaks some JITs (Node, JVM); remove for those runtimes
SystemCallFilter=@system-service
SystemCallErrorNumber=EPERM
CapabilityBoundingSet=                         # no capabilities at all (bind >1024? use AmbientCapabilities=CAP_NET_BIND_SERVICE)
UMask=0027

[Install]
WantedBy=multi-user.target
```

What each block buys you:

- **Ordering and dependencies**: `After=` orders start-up; `Wants=` pulls units in softly; `Requires=` hard-fails if the dependency fails (use sparingly: a database restart should not stop your app). `network-online.target` waits for actual connectivity; plain `network.target` does not.
- **Type**: `simple`/`exec` for ordinary foreground processes; `notify` when the app signals readiness (gunicorn, uvicorn, many Go/Rust servers), which makes `systemctl start` wait until the service is actually ready and lets systemd detect hangs; `forking` for legacy daemons; `oneshot` for scripts.
- **Restart policy**: `Restart=always` with `RestartSec` restarts crashes; `StartLimitBurst`/`IntervalSec` stops infinite crash loops (then alert on the failed unit). `on-failure` skips restarts on clean exits if that matters.
- **Shutdown**: `KillSignal`, `TimeoutStopSec` and `KillMode` implement graceful stop (Part I chapter 6). The timeout must exceed the application's drain time.
- **Limits**: file descriptors (web servers need many), memory (`MemoryMax` kills; `MemoryHigh` throttles first), CPU, task count.
- **Sandboxing**: read-only filesystem except declared paths, private `/tmp` and devices, no new privileges, restricted syscalls and address families, no capabilities. `systemd-analyze security app.service` scores the unit and lists what is still exposed.

```bash
sudo systemctl daemon-reload                  # after editing units
sudo systemctl enable --now app               # start now and at boot
systemctl status app                          # state, PID, recent logs, cgroup tree
sudo systemctl restart app; sudo systemctl reload app
systemctl show app -p MainPID,ActiveState,NRestarts,MemoryCurrent,ExecMainStartTimestamp
journalctl -u app -f                          # follow logs
journalctl -u app --since "30 min ago" -p warning
systemd-analyze security app.service          # hardening score; aim for "OK" or better
systemctl list-dependencies app               # what it waits for
```

## Environment and secrets

`EnvironmentFile` is the standard way to pass configuration (Part I chapter 8). For secrets, prefer fetching from a secrets manager at start-up using the instance role; if a file is unavoidable, 640 root:app, and consider `LoadCredential=`/`SetCredentialEncrypted=` (systemd's credentials mechanism, which exposes secrets to the service via `$CREDENTIALS_DIRECTORY` without putting them in the environment). Never put secrets in the unit file itself; it is world-readable.

## Timers instead of cron

```ini
@file: /etc/systemd/system/app-cleanup.service
[Unit]
Description=Nightly cleanup of expired uploads
[Service]
Type=oneshot
User=app
EnvironmentFile=/etc/app/app.env
ExecStart=/srv/app/current/.venv/bin/python -m app.jobs.cleanup
```

```ini
@file: /etc/systemd/system/app-cleanup.timer
[Unit]
Description=Run app-cleanup nightly
[Timer]
OnCalendar=*-*-* 03:15:00
RandomizedDelaySec=600                        # spread load across a fleet
Persistent=true                               # run at boot if the last schedule was missed
[Install]
WantedBy=timers.target
```

Timers give you logging in the journal, dependency ordering, resource limits and sandboxing identical to services, `systemctl list-timers` to see what runs when, and `Persistent` catch-up. Cron is fine for simple cases; timers are better for anything important.

## Socket activation and templates

**Socket activation** (`app.socket` listening, `app.service` started on first connection) enables zero-downtime restarts (systemd holds the socket; connections queue while the service restarts) and on-demand start. **Template units** (`worker@.service`, instantiated as `worker@1`, `worker@2`) run N copies with `%i` substitution. **Drop-ins** (`/etc/systemd/system/app.service.d/override.conf`, created with `systemctl edit app`) override parts of a vendor unit without copying it.

## Multiple services and ordering

A typical single-server deployment: `postgresql.service`, `redis-server.service`, `app.service` (After both), `app-worker.service` (After app), `nginx.service` (After app, so health checks pass quickly), `app-cleanup.timer`. Draw the graph; `systemd-analyze critical-chain app.service` shows it.

Other frequent findings: `status=203/EXEC` (ExecStart path wrong or not executable), `status=217/USER` (User does not exist), `status=226/NAMESPACE` (a `ReadWritePaths` directory missing), `Permission denied` on bind (needs `AmbientCapabilities=CAP_NET_BIND_SERVICE` for ports below 1024), `MemoryDenyWriteExecute` breaking Node/JVM, a service "active" but not ready (use `Type=notify` or a readiness check), and a stop that takes exactly `TimeoutStopSec` (the app ignores SIGTERM; Part I chapter 6).

## Common mistakes

- `Restart=always` with no `StartLimit*`, hiding a crash loop as "running".
- `After=network.target` when the app needs real connectivity.
- No `TimeoutStopSec` alignment with the app's drain; requests lost on every restart.
- Secrets in unit files or world-readable environment files.
- Running as root because the port is 80.
- No sandboxing; `systemd-analyze security` says UNSAFE and nobody looks.
- Cron jobs with no logging or failure alerting instead of timers.
- Forgetting `daemon-reload` after editing a unit, then debugging the old version.

## Exercises

1. Write a unit for a small web app with the full hardening block; iterate with `systemd-analyze security` until the score is good; verify the app still works (adjust for your runtime).
2. Replace a cron job with a timer and service pair with `Persistent=true`; reboot during the scheduled time and confirm catch-up.
3. Simulate a crash loop (ExecStart pointing at a failing script); observe StartLimit behaviour, `systemctl --failed`, and recover with `reset-failed`.
