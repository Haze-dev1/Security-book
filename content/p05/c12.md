# OS Patching and Routine Maintenance

:::objectives
- Establish a patching cadence for operating systems, runtimes and services that balances security against stability.
- Apply updates with zero or minimal downtime using load balancers, rolling restarts and immutable images.
- Run the recurring maintenance that keeps servers healthy: cleanup, rotation, certificate checks, capacity reviews.
- Track and report compliance so clients can see the system is maintained.
:::

:::prereq
Chapters 2, 4 and 5.
:::

## The problem

Unpatched systems are the most common root cause in breach reports after credentials and misconfiguration, because patching is nobody's favourite task: it risks breaking things, requires reboots, and produces no visible feature. Yet a server that is not maintained decays into a liability within months. The solution is to make maintenance routine, automated and boring, with a clear owner, and to design deployments so that patching does not require downtime.

## What needs patching

- **Kernel and OS packages**: security updates daily (automated), full updates on a schedule; kernel updates need a reboot (or kernel live patching: Canonical Livepatch, kpatch, which defer reboots for critical fixes).
- **Runtimes** (Python, Node, JVM, Go toolchain): follow their security releases; pinned in images (Part I chapter 9).
- **Application dependencies**: Part IV chapter 20.
- **Infrastructure software**: Nginx, Caddy, PostgreSQL, Redis, Docker, agents (CloudWatch, SSM, node_exporter).
- **Base container images**: rebuild on upstream updates.
- **Managed services**: RDS minor versions (enable auto minor upgrade in a maintenance window), EKS versions (quarterly cadence imposed by Kubernetes releases), Lambda runtimes (deprecation schedule).
- **Firmware/hypervisor**: the cloud provider's job (shared responsibility).

## Cadence

| Severity | Timeline | Mechanism |
|---|---|---|
| Critical, actively exploited (CISA KEV, vendor emergency) | 24–72 hours, including reboot | Emergency change; coordinate with client |
| High security | Within 7 days | Automated daily security updates; scheduled reboot |
| Other security | Within 30 days | Monthly maintenance window / image rebuild |
| Non-security updates | Monthly or quarterly | Image rebuild and roll |
| Major versions (OS LTS, PostgreSQL major, Kubernetes) | Planned, 1–2 per year | Project with testing in staging |

Choose a monthly maintenance window agreed with the client (e.g., second Tuesday 02:00–04:00 local, or whenever traffic is lowest), publish it, and use it for anything requiring a restart. Security-only updates apply automatically outside the window with reboots deferred to the window unless critical.

## Patching without downtime

**Behind a load balancer with N ≥ 2 instances**: for each instance, deregister (or let the health check fail deliberately), wait for connection draining, patch and reboot, verify (health check passes, smoke test), re-register, proceed to the next. Capacity during the roll is N−1; schedule off-peak or add a temporary instance. Automate: AWS Systems Manager Patch Manager with maintenance windows, or a script driving the target group API, or let the Auto Scaling Group do an **instance refresh** with a new AMI.

**Immutable infrastructure**: never patch in place. Build a new AMI (Packer: base image + hardening + agents + runtime), test it in staging, then roll it through the Auto Scaling Group (`start-instance-refresh` with a minimum healthy percentage). Old instances are terminated; drift is impossible; rollback is pointing the launch template at the previous AMI. This is the recommended model for fleets, and container platforms (Fargate, EKS managed node groups with Bottlerocket) give it to you for free.

**Single instance**: downtime is unavoidable for kernel reboots; use the maintenance window, a maintenance page from the proxy (chapter 8), and keep it short by pre-downloading updates. Consider whether the single instance is acceptable at all for this client (Part IX chapter 2).

**Databases**: RDS applies minor versions with a brief failover (Multi-AZ) in the maintenance window; self-managed PostgreSQL minor versions are a restart; major versions are a migration project with `pg_upgrade` or logical replication and a tested rollback.

## Automated security updates

Chapter 4 configured `unattended-upgrades`. Check it works:

```bash
sudo unattended-upgrade --dry-run --debug 2>&1 | tail -20
cat /var/log/unattended-upgrades/unattended-upgrades.log | tail
cat /var/run/reboot-required 2>/dev/null && cat /var/run/reboot-required.pkgs   # Debian/Ubuntu: pending reboot
sudo needs-restarting -r                                                        # RHEL: reboot needed?
sudo needs-restarting                                                           # services using updated libraries (restart them)
```

A reboot-required flag that persists for weeks is a finding. Publish it as a metric (a small timer writing to CloudWatch) and alert when it exceeds your SLA.

## Fleet patching with Systems Manager

AWS Systems Manager Patch Manager scans instances against a patch baseline (which severities, approval delays), reports compliance per instance, and installs patches during maintenance windows with reboot options; it works for Linux and Windows on EC2 and on-premises servers registered as managed instances. Combine with State Manager to enforce agent versions and configuration, and Inventory to know what is installed. Compliance reports become client-facing evidence. Part VII chapter 13.

## Routine maintenance beyond patching

```checklist
# Monthly server maintenance
- Apply pending updates; reboot if required; verify services and health checks after.
- Review disk usage and growth trend; prune old releases, images, logs; confirm log rotation works.
- Verify backups ran and the last restore test passed (chapter 11).
- Check certificate expiry dates and renewal logs (chapter 8).
- Review `systemctl --failed`, failed timers, and `journalctl -p err` for recurring errors.
- Review user accounts and SSH keys against current staff; remove leavers (chapters 3–4).
- Review security group and firewall rules for drift from infrastructure code.
- Check monitoring agents are running and reporting; alarms not in INSUFFICIENT_DATA.
- Review resource utilisation trends for capacity planning (chapter 10); right-size or plan scaling.
- Rebuild the base image with current packages; roll it through the fleet.
- Record what was done, by whom, and anomalies found; update runbooks.
```

Automate what can be automated (cleanup timers, agent health metrics, compliance scans) and keep the human review short and scheduled.

## Change management for maintenance

Even routine maintenance is a production change: announce the window, have a rollback (previous AMI, snapshot before patching single instances), verify afterwards (smoke tests, error rates for 30 minutes), and record it (Part XII chapter 8). Emergency patches follow an expedited path with the same verification and recording.

## Reporting

Clients and auditors want evidence: patch compliance percentage over time, mean time from vendor release to deployment for critical fixes, list of pending updates and why (exceptions with owners and dates), reboot-required age, and the maintenance log. A monthly one-page report with these numbers builds trust and catches decay.

## Common mistakes

- Automatic updates never verified; the service silently broke months ago.
- Reboots deferred indefinitely; a two-year-old kernel with a patched userland.
- Patching in place on a fleet until every server is different.
- No maintenance window agreed; every reboot is an argument.
- Major upgrades attempted without staging rehearsal or rollback.
- Agents (monitoring, SSM) never updated; eventually unsupported and silent.
- Nobody owns maintenance after handover (Part XIII chapter 12).
