# Resource Monitoring on a Server

:::objectives
- Read CPU, memory, disk, network and process metrics on a live server and tell saturation from noise.
- Use the standard tools (top/htop, vmstat, iostat, free, df, ss, sar) and the USE method to find the bottleneck.
- Export host metrics to a central system (CloudWatch agent, node_exporter) and set the alarms that matter.
- Avoid the misreadings that send engineers chasing the wrong resource.
:::

:::prereq
Part I chapters 3 and 7; chapter 6 of this part.

## The problem

"The server is slow" has four or five possible meanings, and the fix for each is different: more CPU, more memory, faster disk, a network limit, or a misbehaving process. Resource monitoring is how you decide in minutes rather than by trial. It also feeds capacity planning: knowing that a server runs at 70% CPU at peak tells you when to scale before users tell you.

## The USE method

For every resource, check three things: **Utilisation** (how busy), **Saturation** (how much work is queued), **Errors**. Saturation is the one people skip and the one that explains latency: a CPU at 80% utilisation with a run queue of 1 is fine; at 80% with a run queue of 12 it is saturated.

| Resource | Utilisation | Saturation | Errors |
|---|---|---|---|
| CPU | `top` %us/%sy; `vmstat` us/sy | run queue `r` in `vmstat` > cores; load average vs cores; `%steal` | `dmesg` MCE (rare) |
| Memory | `free` available; RSS per process | swapping (`si`/`so`), page reclaim, OOM kills (`dmesg`) | OOM kills |
| Disk | `iostat -x` %util | `await` latency, queue depth (`aqu-sz`); CloudWatch `VolumeQueueLength` | I/O errors in `dmesg`, SMART |
| Network | bandwidth vs instance allowance; `sar -n DEV` | drops, retransmits (`nstat`), `bw_in/out_allowance_exceeded` ENA metrics | interface errors (`ip -s link`) |
| File descriptors / sockets | count vs limit | accept queue overflow | EMFILE in app logs |

## The tools, in the order to use them

```bash
uptime                      # load averages: compare with core count (nproc)
top -bn1 | head -20         # or htop: who uses CPU/memory right now; press 1 (per core), M (sort by mem), P (by CPU)
vmstat 1 5                  # r (runnable), b (blocked), si/so (swap), us/sy/id/wa/st
free -h                     # available is the number that matters
iostat -xz 1 3              # per-disk r/s w/s, await, %util
df -h; df -i                # space and inodes
ss -s; ss -ltnp             # socket summary; listeners
ip -s link                  # interface errors/drops
sar -u 1 5; sar -r; sar -n DEV 1 5; sar -q      # sysstat history (enable the collector for retrospective views)
pidstat -u -r -d 1 5        # per-process CPU, memory, disk
ps -eo pid,ppid,user,%cpu,%mem,rss,nlwp,stat,etime,cmd --sort=-%mem | head
sudo nstat -az | grep -E 'TcpRetransSegs|TcpExtListenOverflows|TcpExtTCPTimeouts'
cat /proc/pressure/cpu /proc/pressure/memory /proc/pressure/io      # PSI: % of time tasks stalled on each resource (kernel ≥ 4.20)
```

Pressure Stall Information (PSI) deserves a mention: `/proc/pressure/*` reports the fraction of time *some* or *all* tasks were stalled waiting for CPU, memory or I/O. It is the cleanest single saturation signal and is exposed by node_exporter and the CloudWatch agent.

## Reading the numbers

**Load average** counts runnable plus (on Linux) uninterruptible-I/O-waiting tasks. Load 8 on 2 cores with CPU idle 60% means I/O wait, not CPU. Load 8 on 2 cores with idle 0% means CPU saturation. Load 1 on 2 cores is calm.

**CPU breakdown**: `us` (your code), `sy` (kernel: networking, I/O, context switches), `wa` (waiting on I/O), `st` (stolen by the hypervisor: burstable throttling or noisy neighbour), `si/hi` (interrupts: heavy network). High `sy` with moderate `us` often means too many small syscalls or too many connections; high `st` means move instance type.

**Memory**: `used` includes cache; `available` is what processes can get. Swap in/out non-zero means the box is memory-constrained *now*. A process whose RSS climbs steadily is leaking (Part I chapter 7). OOM kills appear in `dmesg` with the victim's name.

**Disk**: `await` is the latency per I/O in ms; on SSD/EBS, more than a few ms under load means saturation or throttling. `%util` near 100 on a device that can serve many parallel I/Os is less alarming than high `await`. Check EBS CloudWatch `BurstBalance` (gp2), `VolumeQueueLength`, and whether you are hitting the volume's or the instance's throughput cap.

**Network**: EC2 instances have bandwidth allowances; exceeding them shows as ENA `bw_out_allowance_exceeded`, `pps_allowance_exceeded`, `conntrack_allowance_exceeded` counters (visible via `ethtool -S`). Retransmits indicate loss; `ListenOverflows` indicate the app is not accepting fast enough.

## Exporting metrics

Host-level dashboards and alarms need metrics in a central system:

- **CloudWatch agent**: collects memory, disk, swap, process and custom metrics (EC2 default metrics have no memory or disk usage) to CloudWatch; configuration in SSM Parameter Store for fleets; alarms via CloudWatch (chapter: Part VII chapter 13).
- **node_exporter** (Prometheus): exposes hundreds of host metrics on `:9100` for a Prometheus server or Grafana Agent/Alloy to scrape; the standard outside AWS-native stacks (Part XI chapter 3).
- Collect per-service metrics too: Nginx `stub_status`/exporter, PostgreSQL exporter, application metrics.

Alarms that earn their keep on a host: disk used > 80% (per volume), memory available < 15%, swap in use, CPU > 85% for 15 minutes (or PSI cpu `some` > 20%), load average > 2× cores for 10 minutes, CPU credit balance low (burstable), status check failed (EC2), and `systemctl --failed` non-empty (a simple timer that publishes a metric). Everything else is a dashboard, not a page.

## Common misreadings

- "CPU is at 30%, so the server is not the problem": the server can be I/O- or memory-bound with idle CPUs.
- "Memory is 95% used": cache; look at `available`.
- "Load average is 4": meaningless without the core count and the CPU/wa breakdown.
- "The disk is 100% utilised": SSDs serve parallel I/O; `await` is the latency signal.
- "Network is fine, bandwidth is low": packets-per-second and connection-tracking limits bite before bandwidth.
- Looking at a 5-minute CloudWatch average and missing 30-second spikes; use 1-minute (or high-resolution) metrics and percentiles for latency.

## Common mistakes

- Monitoring CPU only; no memory or disk metrics (EC2 defaults do not include them).
- No alarms on disk space until it is full.
- Alarms on averages for latency.
- No historical data (`sar` not enabled; no central metrics) to compare "now" with "normal".
- Burstable instances without credit alarms.
- Treating `top` as the only tool.

## Exercises

1. On a test server, generate CPU load (`stress-ng --cpu 2`), memory pressure (`stress-ng --vm 1 --vm-bytes 80%`) and disk load (`fio` random reads) in turn; for each, record what `vmstat`, `iostat`, `free` and PSI show so you recognise the signatures.
2. Install the CloudWatch agent or node_exporter; build a dashboard with CPU, memory available, disk used, disk await, network and PSI; add the alarms listed above.
3. Enable `sysstat` and, a day later, use `sar` to find the busiest hour of each resource.
