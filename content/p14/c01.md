# Project 1: Secure Linux Server

:::objectives
- Provision an Ubuntu server, harden it, and run a backend application behind a TLS reverse proxy with automatic certificates, a firewall, monitoring and backups.
- Practise the Part V skills end to end on a real host and leave with a reusable hardening script and checklist.
:::

:::prereq
Part V (all chapters), [SSH and Key-Based Access](#/p05/c03), [TLS Certificates and Reverse Proxy Configuration](#/p05/c08). You need: a domain or subdomain you control, an SSH key pair, and either a cloud VM (a small EC2 or any VPS) or a local VM.
:::

:::cost Estimated cost
A small cloud VM (2 vCPU, 2 GB) costs roughly 10–20 USD per month; an EC2 `t4g.small` about 12 USD plus a few dollars for storage and a public IP. Destroy it when finished. The domain is whatever you already pay for.
:::

## Steps

### 1. Provision and first login

Create the VM with Ubuntu 24.04 LTS, your SSH public key, and a security group or provider firewall allowing 22, 80 and 443 (you will tighten 22 to your IP). Point `app.yourdomain.example` at its public IP (A record; AAAA if you have IPv6).

```bash
ssh -i ~/.ssh/project1 ubuntu@app.yourdomain.example
sudo apt-get update && sudo apt-get upgrade -y && sudo reboot
```

### 2. Users and SSH hardening

```bash
# Create an admin user and a service user; disable root and password SSH
sudo adduser --disabled-password --gecos "" admin
sudo usermod -aG sudo admin
sudo mkdir -p /home/admin/.ssh && sudo cp ~/.ssh/authorized_keys /home/admin/.ssh/ && sudo chown -R admin:admin /home/admin/.ssh && sudo chmod 700 /home/admin/.ssh && sudo chmod 600 /home/admin/.ssh/authorized_keys
sudo adduser --system --group --home /opt/app --shell /usr/sbin/nologin app

sudo tee /etc/ssh/sshd_config.d/10-hardening.conf > /dev/null <<'CONF'
PermitRootLogin no
PasswordAuthentication no
KbdInteractiveAuthentication no
PubkeyAuthentication yes
AllowUsers admin
MaxAuthTries 3
LoginGraceTime 20
X11Forwarding no
ClientAliveInterval 300
ClientAliveCountMax 2
CONF
sudo sshd -t && sudo systemctl reload ssh
```

Open a **second** terminal and confirm `ssh admin@app.yourdomain.example` works before closing the first. Then remove the default `ubuntu` user's key or the user itself.

### 3. Firewall

```bash
sudo apt-get install -y ufw
sudo ufw default deny incoming
sudo ufw default allow outgoing
sudo ufw allow from YOUR.IP.ADDR.0/24 to any port 22 proto tcp comment 'SSH from office/home'
sudo ufw allow 80/tcp comment 'ACME + redirect'
sudo ufw allow 443/tcp comment 'HTTPS'
sudo ufw enable && sudo ufw status verbose
```

If your IP changes often, keep 22 open to the world but add `fail2ban` (step 7) and consider a VPN or Tailscale instead.

### 4. Automatic patching and time

```bash
sudo apt-get install -y unattended-upgrades
sudo dpkg-reconfigure -plow unattended-upgrades    # answer Yes
sudo sed -i 's|^//\s*"${distro_id}:${distro_codename}-updates";|        "${distro_id}:${distro_codename}-updates";|' /etc/apt/apt.conf.d/50unattended-upgrades
echo 'Unattended-Upgrade::Automatic-Reboot "true";
Unattended-Upgrade::Automatic-Reboot-Time "04:30";' | sudo tee /etc/apt/apt.conf.d/52reboot > /dev/null
timedatectl   # confirm NTP active
```

### 5. PostgreSQL

```bash
sudo apt-get install -y postgresql
sudo -u postgres psql <<'SQL'
CREATE ROLE app LOGIN PASSWORD 'REPLACE_WITH_LONG_RANDOM';
CREATE DATABASE appdb OWNER app;
\c appdb
REVOKE ALL ON SCHEMA public FROM PUBLIC;
GRANT USAGE, CREATE ON SCHEMA public TO app;
SQL
sudo grep -E "^(listen_addresses|port)" /etc/postgresql/16/main/postgresql.conf   # listen_addresses = 'localhost'
```

### 6. The application as a hardened systemd service

Use any small HTTP service (the sample from Part III, or a minimal Python/Node app) that reads `DATABASE_URL` and listens on 8080. Install it under `/opt/app`, owned by root, readable by `app`.

```bash
sudo mkdir -p /etc/app
echo 'DATABASE_URL=postgresql://app:REPLACE_WITH_LONG_RANDOM@127.0.0.1:5432/appdb
PORT=8080
APP_ENV=production' | sudo tee /etc/app/env > /dev/null
sudo chown root:app /etc/app/env && sudo chmod 0640 /etc/app/env

sudo tee /etc/systemd/system/app.service > /dev/null <<'UNIT'
[Unit]
Description=Sample backend
After=network-online.target postgresql.service
Wants=network-online.target

[Service]
User=app
Group=app
WorkingDirectory=/opt/app
EnvironmentFile=/etc/app/env
ExecStart=/opt/app/venv/bin/python -m app        # adjust to your runtime
Restart=on-failure
RestartSec=3
# Hardening
NoNewPrivileges=true
ProtectSystem=strict
ProtectHome=true
PrivateTmp=true
PrivateDevices=true
ProtectKernelTunables=true
ProtectKernelModules=true
ProtectControlGroups=true
RestrictAddressFamilies=AF_INET AF_INET6 AF_UNIX
RestrictNamespaces=true
LockPersonality=true
MemoryDenyWriteExecute=true
SystemCallFilter=@system-service
SystemCallErrorNumber=EPERM
CapabilityBoundingSet=
AmbientCapabilities=
ReadWritePaths=/var/lib/app
StateDirectory=app
LimitNOFILE=65536

[Install]
WantedBy=multi-user.target
UNIT
sudo systemctl daemon-reload && sudo systemctl enable --now app
sudo systemctl status app --no-pager && curl -s localhost:8080/health
systemd-analyze security app      # aim for a low exposure score
```

### 7. Caddy with automatic TLS

```bash
sudo apt-get install -y debian-keyring debian-archive-keyring apt-transport-https curl
curl -1sLf 'https://dl.cloudsmith.io/public/caddy/stable/gpg.key' | sudo gpg --dearmor -o /usr/share/keyrings/caddy-stable-archive-keyring.gpg
curl -1sLf 'https://dl.cloudsmith.io/public/caddy/stable/debian.deb.txt' | sudo tee /etc/apt/sources.list.d/caddy-stable.list
sudo apt-get update && sudo apt-get install -y caddy

sudo tee /etc/caddy/Caddyfile > /dev/null <<'CADDY'
app.yourdomain.example {
	encode zstd gzip
	header {
		Strict-Transport-Security "max-age=31536000; includeSubDomains"
		X-Content-Type-Options nosniff
		X-Frame-Options DENY
		Referrer-Policy strict-origin-when-cross-origin
		Content-Security-Policy "default-src 'self'; frame-ancestors 'none'"
		-Server
	}
	log {
		output file /var/log/caddy/access.log
		format json
	}
	reverse_proxy 127.0.0.1:8080 {
		header_up X-Real-IP {remote_host}
	}
}
CADDY
sudo systemctl reload caddy
curl -sI https://app.yourdomain.example/health | head -5
```

Caddy obtains and renews the certificate automatically. Add `fail2ban` for SSH and (optionally) for Caddy's access log:

```bash
sudo apt-get install -y fail2ban
printf '[sshd]\nenabled = true\nmaxretry = 4\nbantime = 1h\n' | sudo tee /etc/fail2ban/jail.d/sshd.local > /dev/null
sudo systemctl restart fail2ban && sudo fail2ban-client status sshd
```

### 8. Monitoring and logs

```bash
sudo apt-get install -y prometheus-node-exporter
sudo sed -i 's|^ARGS=.*|ARGS="--web.listen-address=127.0.0.1:9100"|' /etc/default/prometheus-node-exporter
sudo systemctl restart prometheus-node-exporter
sudo mkdir -p /etc/systemd/journald.conf.d
printf '[Journal]\nSystemMaxUse=1G\nMaxRetentionSec=30day\n' | sudo tee /etc/systemd/journald.conf.d/retention.conf > /dev/null
sudo systemctl restart systemd-journald
journalctl -u app -u caddy --since "10 min ago" --no-pager | tail -20
```

For a single server, an external uptime probe (any free service) hitting `/health` every minute, plus email on failure, is the minimum alerting. If you have a Prometheus elsewhere, scrape node_exporter over an SSH tunnel or WireGuard rather than exposing 9100.

### 9. Backups

```bash
sudo apt-get install -y age awscli    # or rclone for other providers
sudo mkdir -p /var/backups/app && sudo chmod 700 /var/backups/app
sudo tee /usr/local/bin/backup-db.sh > /dev/null <<'SCRIPT'
#!/usr/bin/env bash
set -euo pipefail
STAMP=$(date -u +%Y%m%dT%H%M%SZ)
OUT=/var/backups/app/appdb-${STAMP}.sql.zst.age
sudo -u postgres pg_dump --format=custom appdb | zstd -q | age -r "$(cat /etc/app/backup.pub)" -o "${OUT}"
aws s3 cp "${OUT}" "s3://YOUR-BACKUP-BUCKET/project1/" --storage-class STANDARD_IA
find /var/backups/app -type f -mtime +7 -delete
logger -t backup "appdb backup ${STAMP} ok"
SCRIPT
sudo chmod 750 /usr/local/bin/backup-db.sh
# Generate an age key pair on your workstation; put the PUBLIC key in /etc/app/backup.pub; keep the private key offline.
printf '[Unit]\nDescription=Nightly DB backup\n[Timer]\nOnCalendar=*-*-* 02:15:00\nPersistent=true\n[Install]\nWantedBy=timers.target\n' | sudo tee /etc/systemd/system/backup-db.timer > /dev/null
printf '[Unit]\nDescription=Nightly DB backup\n[Service]\nType=oneshot\nExecStart=/usr/local/bin/backup-db.sh\n' | sudo tee /etc/systemd/system/backup-db.service > /dev/null
sudo systemctl daemon-reload && sudo systemctl enable --now backup-db.timer
sudo systemctl start backup-db.service && sudo journalctl -u backup-db --no-pager | tail -3
```

The instance needs an IAM role (or scoped credentials) that can only `PutObject` to that prefix. Then **restore once**: download a backup to a scratch machine, decrypt with the private key, `pg_restore` into a fresh database, and check row counts.

## Verification

```checklist
# Project 1 verification
- SSH as root or with a password is rejected; SSH as admin with key works; ufw shows only 22 (restricted), 80, 443
- https://app.yourdomain.example returns 200 with a valid certificate; http redirects to https; HSTS and security headers present (check with curl -I or an online header scanner)
- systemd-analyze security app reports a low exposure score; the app runs as user app and cannot write outside its state directory
- PostgreSQL listens only on localhost; the app role cannot create roles or access other databases
- Unattended upgrades configured; journald retention set; node_exporter bound to localhost
- fail2ban bans after repeated SSH failures (test from another IP or with a wrong key)
- A backup exists in the bucket and a restore has been performed successfully
- Reboot the server: everything comes back without manual steps
```

## Security checks

Run `sudo lynis audit system` for a broad hardening report and address the warnings relevant to a server (not laptop items). Run an external port scan (from another host: `nmap -Pn app.yourdomain.example`) and confirm only 80 and 443 answer (22 if from your allowed range). Check the TLS configuration with an online TLS tester for an A grade. Review `sudo last` and `sudo journalctl -u ssh` for login attempts.

## Troubleshooting

- **Locked out of SSH**: use the provider console (serial console) to fix `sshd_config` or ufw; this is why you test in a second terminal.
- **Caddy fails to get a certificate**: DNS not propagated, port 80 blocked, or rate limits; `journalctl -u caddy` shows the ACME error.
- **App fails under the hardened unit**: `systemd-analyze security` sandboxing can block legitimate needs (writing to a path, binding sockets); loosen one directive at a time and add `ReadWritePaths` rather than disabling `ProtectSystem`.
- **Backup upload denied**: the role lacks `s3:PutObject` on the prefix; check with `aws sts get-caller-identity` and the bucket policy.

## Cleanup

Delete the VM (or stop it if you will continue to Project 2), remove the DNS record, and empty or lifecycle the backup prefix. Rotate any credentials you used.
