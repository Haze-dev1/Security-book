# Project 5: Multi-Tenant Client SaaS

:::objectives
- Extend the backend into a multi-tenant SaaS with tenant onboarding, per-tenant SSO configuration, role-based access, row-level security, per-tenant rate limits, usage metering and a tenant admin API.
- Prove isolation with an automated cross-tenant test suite and a canary tenant tripwire, and document the isolation model as you would for a client's security team.
:::

## Steps

### 1. Tenant registry and context

Add `tenants (id, slug, name, tier, status, region, created_at)` and `tenant_auth_config (tenant_id, issuer, jwks_uri, client_id, audience, role_mapping jsonb, enforce_mfa bool)`. Implement `TenantContext` as an immutable object placed on the request by the first middleware. Every data access function takes a context parameter; there is no way to get a connection without one (a startup check scans for forbidden raw-connection usage, or a lint rule enforces it).

### 2. Per-tenant authentication

Validate tokens against the tenant's configured issuer and JWKS, caching JWKS per tenant with refresh on unknown `kid`. Map IdP groups to roles via the tenant's mapping. API keys are hashed (SHA-256 with a per-key random prefix for lookup), bound to a tenant and scopes, with last-used tracking and rotation endpoints. A token for tenant A presented on tenant B's host is rejected with 404 (do not reveal tenant existence).

### 3. Row-level security and repository discipline

Every tenant-scoped table gets `tenant_id` and the RLS policy; the application role has no `BYPASSRLS`; the repository sets `app.tenant_id` with `set_config(..., true)` inside each transaction; background jobs carry the tenant ID in their payload and re-establish context. A test asserts that a query without context returns zero rows (fail closed).

### 4. Onboarding workflow

`POST /control/tenants` (platform admin only, separate audience) runs an idempotent, resumable workflow: create registry row (status `provisioning`), create default roles and the first admin invitation, configure auth (or the default shared dev IdP), create storage prefix, seed metering, mark `active`. Each step records completion; rerunning resumes. Deprovisioning: `suspended` (read-only), then `deleted` after a grace period with a job that purges data across every store and writes a deletion certificate record.

### 5. Per-tenant limits and metering

Rate limits from tier config (free: 60/min; pro: 600/min; enterprise: custom), enforced in Redis per tenant and per user; concurrency cap per tenant for expensive endpoints. Emit `usage_events (tenant_id, metric, quantity, ts, idempotency_key)` for API calls, storage bytes and active seats; a daily job aggregates into `usage_daily`; `GET /admin/usage` returns the tenant's own usage.

### 6. Tenant admin API

Tenant admins (role from their IdP) manage members (invite, change role, remove), SSO configuration (with a test-login flow before enabling enforcement), API keys, and can export an audit log of their tenant's security events. Platform admins see all tenants through a separate, audited interface and cannot read tenant content without a break-glass flow that records reason and notifies the tenant.

### 7. Isolation verification

- **Cross-tenant suite**: fixtures create tenants A and B with data; for every route in the OpenAPI document, call as A with B's identifiers (path, query, body) and assert 404 and no B data in the body. Generate the test list from the OpenAPI spec so new routes are covered automatically; fail CI if a route lacks the test marker.
- **Canary tenant**: a tenant with documents containing unique fingerprints; a scheduled job searches every API response sample, log sample and export for the fingerprints and alerts on any hit outside the canary tenant.
- **Cache key audit**: a test wraps the Redis client and asserts every key begins with `t:{tenant}:`.
- **Access analysis**: a script lists database roles and confirms none has `BYPASSRLS` except the migration role, which the application cannot use.

### 8. Documentation for a security team

Write the one-page isolation statement (Part XIII chapter 8): mechanism per layer, enforcement, tests, residual risks, and the dedicated-database option for enterprise tiers (describe how the repository would route to a per-tenant connection string from the registry).

## Verification

```checklist
# Project 5 verification
- A token issued by tenant A's IdP is rejected on tenant B's host with 404
- Cross-tenant suite covers 100% of routes (CI fails on an unmarked route) and passes
- A direct query as the app role with no app.tenant_id returns zero rows from every tenant table
- Onboarding a tenant twice with the same request is idempotent; killing the workflow mid-way and rerunning completes it
- Tenant on the free tier receives 429 at 61 requests/min while a pro tenant continues
- Usage report for a tenant matches the number of calls made in a test
- Canary fingerprint planted in a shared log line triggers the tripwire alert
- Deleting a tenant purges rows in every table, cache keys and storage prefix; a verification query proves zero remaining rows
- Platform admin cannot read tenant documents without break-glass; break-glass use appears in the tenant's audit export
```

## Security checks

Attempt tenant confusion: send `X-Tenant: b` with a host of `a.portal.example`; confirm the host wins and the mismatch is logged. Attempt IDOR across tenants with sequential IDs (use UUIDs; test anyway). Attempt JWKS confusion: a token whose `iss` is tenant B's issuer presented to tenant A; confirm the validator uses A's configured issuer only, never the token's claim to choose keys. Review that SSO configuration changes require a successful test login and are audited.

## Troubleshooting

- **Everything returns empty after enabling RLS**: context not set in the same transaction, or connection pooling resets session variables; use transaction-scoped `set_config` and set it after `BEGIN`.
- **JWKS cache serves the wrong keys**: cache keyed by tenant, not globally; include the issuer in the key.
- **Onboarding workflow double-creates**: steps not idempotent; key each step on tenant ID and step name.
- **Rate limits leak across tenants**: Redis key missing the tenant prefix; the cache key audit test should have caught it.
