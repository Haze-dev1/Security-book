# Project 6: Production Incident Simulator

:::objectives
- Build a small environment in which realistic production failures can be injected on demand, then practise detecting, diagnosing and mitigating them with the tools and process from Part XI.
- Run a series of game days alone or with a team, write postmortems, and improve alerts and runbooks from what you find.
:::

:::prereq
Part XI (all); [Resilience Patterns](#/p09/c08); Project 3 (the Compose stack) or Project 4 (AWS).
:::

:::cost Estimated cost
Zero locally with Compose. On AWS, within Project 4's running costs; AWS Fault Injection Service experiments cost a small per-minute fee.
:::

## Steps

### 1. Baseline

Run the stack with the observability profile. Add Toxiproxy between `api` and `postgres`, and between `api` and `redis` (the app connects to the proxy's address). Start k6 with a steady scenario (Part XI chapter 8). Define SLOs: availability 99.9% (non-5xx), latency 95% under 500 ms. Create burn-rate alerts (Part XI chapter 4) and the symptom alerts from Part XI chapter 5 (no traffic, queue age, pool saturation, restart rate, certificate expiry) routed to a local Alertmanager webhook receiver that logs "PAGE" lines with timestamps. Write the baseline dashboard. Record normal values.

### 2. Scenario library

Each scenario is a script that injects a fault and a hidden note describing the expected signals and the intended mitigation; the responder does not read the note until the postmortem.

```bash
# scenarios/01-db-latency.sh : database slow (Toxiproxy latency toxic)
toxiproxy-cli toxic add -t latency -a latency=400 -a jitter=100 postgres
# expected: p95 latency alert within minutes; traces show DB spans dominating; mitigation: identify DB-side cause; here, remove the toxic

# scenarios/02-pool-exhaustion.sh : leak connections
docker compose exec api python -m app.debug.leak_connections --count 18   # debug endpoint enabled only in the simulator profile
# expected: pool saturation alert, then 5xx; mitigation: restart api (reversible) then find the leak

# scenarios/03-queue-stall.sh : stop the worker silently
docker compose stop worker
# expected: queue age alert (if you built it!); no API alert; mitigation: start worker; watch provider rate limits on drain

# scenarios/04-cert-expired.sh : swap the proxy certificate for an expired one
cp fixtures/expired.crt certs/server.crt && docker compose restart caddy
# expected: external probe fails; internal metrics quiet; mitigation: restore cert; prevention: expiry alert

# scenarios/05-disk-full.sh : fill the postgres volume
docker compose exec postgres sh -c 'fallocate -l 95% /var/lib/postgresql/data/fill || dd if=/dev/zero of=/var/lib/postgresql/data/fill bs=1M count=4000'
# expected: writes fail, reads continue; mitigation: remove the file; prevention: storage alert and predict_linear

# scenarios/06-bad-deploy.sh : deploy an image that returns 500 on one route after 60 s
docker compose up -d --no-deps api-bad
# expected: error ratio burn alert on one route; mitigation: roll back to the previous image

# scenarios/07-dependency-down.sh : the payments stub returns 503 for 90 s then recovers
curl -X POST localhost:9000/control/outage?seconds=90
# expected: if retries lack backoff, a retry storm keeps the API at 100% CPU after recovery; mitigation: shed load / breaker; prevention: resilience patterns

# scenarios/08-secret-rotated.sh : rotate the DB password without updating the app
docker compose exec postgres psql -U postgres -c "ALTER ROLE app_rw PASSWORD 'rotated'"
# expected: new connections fail as pool recycles; mitigation: update secret and restart; prevention: rotation runbook, pool health alert

# scenarios/09-memory-leak.sh : enable a leaky cache
curl -X POST localhost:8080/debug/leak?mode=cache
# expected: memory climb, OOM kill, restart loop over 10–20 min; mitigation: disable, restart; prevention: memory trend alert

# scenarios/10-dns-failure.sh : break resolution of redis
docker compose exec api sh -c 'echo "127.0.0.1 redis" >> /etc/hosts'   # or Toxiproxy reset_peer toxic on redis
# expected: rate limiting and idempotency fail open or closed depending on your design; discover which
```

Add your own from incidents you have seen. On AWS, implement a subset with Fault Injection Service (stop tasks, inject RDS failover, add network latency to subnets) and with deliberate misconfiguration in a sandbox.

### 3. Game day protocol

1. A facilitator picks a scenario the responder has not seen and runs it at an unannounced time within an agreed window.
2. The responder works only from alerts, dashboards, logs, traces and runbooks, declaring an incident (channel, timeline, roles even if solo), following the Part XI chapter 6 loop, and recording timestamps.
3. Time to detect (alert fired → acknowledged), time to diagnose (hypothesis confirmed) and time to mitigate (SLIs recovered) are measured.
4. The facilitator ends the scenario when mitigated or after a time box (45 minutes); hidden notes are revealed.
5. Postmortem within a day using the Part XI chapter 7 template: contributing factors (including gaps in alerts, dashboards, runbooks), action items with owners.
6. Action items are implemented before the next game day; the scenario is rerun later to confirm detection improved.

Run at least six scenarios over a few weeks. Track the metrics across runs; the trend is the learning.

### 4. Improve the system

Expected improvements from the first rounds: queue age and worker health alerts (scenario 3); certificate expiry probe (4); disk prediction alert (5); per-route error alerts and faster rollback (6); backoff, jitter and circuit breaker in the payments adapter (7); a rotation runbook that restarts tasks (8); memory trend alert (9); explicit fail-open/fail-closed decisions for Redis-dependent controls, documented (10). Each is a pull request with the alert, the runbook, and a test where possible.

### 5. Team variant

With three or more people: rotate facilitator, incident commander, hands-on responder and scribe; practise the communication cadence with a mock stakeholder who asks for updates; include a status page draft; add a scenario where two faults overlap and one where the first hypothesis is wrong by design (a red herring deploy that is unrelated).

## Verification

```checklist
# Project 6 verification
- Every scenario in the library has: injector script, hidden expected-signals note, cleanup script
- Baseline dashboard shows normal ranges; burn-rate and symptom alerts exist and have fired at least once in testing
- Game day records exist for at least six scenarios with detect/diagnose/mitigate times
- Postmortems written for each with action items; at least 80% of action items implemented
- Rerun of two early scenarios shows improved time to detect
- Scenario 7 run before and after resilience changes shows recovery time reduced from minutes to seconds
- Runbooks exist for every alert that fired and were followed literally during a rerun
```

## Security variant

Add security scenarios: a leaked API key being used from an unusual location (detect via audit logs and alert on anomaly); a brute-force login pattern (rate limiting and alerting); an SSRF probe against the import-from-URL feature (blocked and logged); CloudTrail disabled in the sandbox account (GuardDuty/Config alert). Practise the containment and notification steps from Part XV chapter 4 without executing real notifications.

## Troubleshooting

- **Alerts never fire**: check Prometheus targets are up, rule files loaded (`/rules` in the UI), `for` durations, and Alertmanager routing; fire a test alert with `amtool`.
- **Toxiproxy not in the path**: the app must connect to the proxy's listener address, not the service directly; verify with `toxiproxy-cli list`.
- **k6 itself is the bottleneck**: reduce VUs or run from a separate machine; watch generator CPU.
- **Scenario cleanup incomplete**: every scenario needs an idempotent cleanup script; run it before the next one.

## Cleanup

Remove toxics (`toxiproxy-cli toxic remove`), run all cleanup scripts, `docker compose down -v`. On AWS, stop FIS experiments and destroy per Project 4.
