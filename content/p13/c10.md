# Environment Configuration and Deployment Documentation

:::objectives
- Document each environment of a client deployment so that anyone authorised can understand, operate and rebuild it.
- Manage configuration across environments and clients safely: what is configuration, where it lives, how it changes, how it is validated.
- Produce deployment documentation that is accurate because it is generated or tested, not because someone remembered to update it.
:::

## The environment document

For every environment (per client, per stage) one document, in the repository, answers what exists and how it is reached:

```checklist
# Environment: <client> / <stage>
- Purpose and criticality; SLOs that apply; data classification present
- Cloud account ID, Region(s), organisation unit; who owns the account
- Access: SSO permission sets or roles, how to request, break-glass procedure, who approves
- Network: VPC IDs and CIDRs, subnets by tier, connectivity to client systems, egress path and allowlisted destinations, DNS zones and records, certificates and their expiry
- Compute: clusters/services, task definitions or deployments, scaling bounds, current version
- Data stores: database identifiers, engine versions, sizes, Multi-AZ, backup settings, encryption keys; caches; queues; buckets
- Secrets: names/paths of every secret (never values), owner, rotation schedule
- Configuration: where environment configuration lives and how it is applied; differences from the baseline environment and why
- Integrations: endpoints, credentials (by name), contacts; sandbox vs production mapping
- Observability: dashboards, log groups, alert routes, on-call schedule, status page
- Deployment: pipeline, how to deploy and roll back, last deployment record, change windows and approvals
- Backup and DR: what is backed up where, RTO/RPO, last restore test
- Cost: monthly estimate and actual, budget alarms, tags
- Known issues and accepted risks with links to the risk register
- Last verified date and verifier
```

Generate as much as possible from the source of truth: Terraform outputs produce IDs, endpoints and ARNs; a script renders them into the document; the pipeline updates the version and last deployment fields. Hand-written sections (purpose, access procedure, contacts) are reviewed on a schedule.

## Configuration: what it is and where it lives

Configuration is everything that differs between deployments of the same artefact: endpoints, feature flags, limits, tenant settings, credentials references, Region, scaling parameters. Rules that keep it manageable:

- **Code is the same everywhere; configuration differs.** The image digest deployed to staging and production is identical (Part X).
- **Layers**: defaults in the repository; per-environment values in versioned configuration files or IaC variables; per-client values in a per-client directory or repository with the same structure; secrets by reference only.
- **Secrets never in configuration files**; configuration points to the secret's name; the runtime fetches it.
- **Validation at startup**: the application declares required keys with types and constraints and fails fast with a clear message when one is missing or invalid; a deploy-time check compares the declared schema with the target environment before rolling out.
- **Typed, documented schema**: one reference document listing every key, type, default, meaning, allowed values, who may change it, and whether changing it requires a restart.
- **Change control**: configuration changes go through the same pipeline and review as code; a console edit is a drift to detect and revert.
- **Diffable**: you can diff staging against production and understand every difference; unexplained differences are bugs.

```yaml
# config/schema.yaml: the single reference for configuration keys
APP_ENV:
  type: enum [dev, staging, production]
  required: true
  description: Environment name; controls log level defaults and safety interlocks.
DATABASE_URL_SECRET:
  type: secret-ref
  required: true
  description: Secrets Manager name holding the connection string. Rotation owner: client DBA.
PAYMENTS_PROVIDER_BASE_URL:
  type: url
  default: https://api.payments.example
  description: Sandbox in non-production. Per-client override allowed.
FEATURE_FINANCE_THRESHOLD:
  type: integer
  default: 50000
  description: Minor units above which approvals route to finance. Changed by client admin via the admin UI (audited), not by env var.
LOG_LEVEL:
  type: enum [debug, info, warn, error]
  default: info
  description: debug forbidden in production (startup check).
```

```python
# Startup validation: fail fast and specifically
schema = load_schema("config/schema.yaml")
problems = validate_env(os.environ, schema)
if problems:
    for p in problems:
        log.error("config_invalid", key=p.key, reason=p.reason)
    sys.exit(78)      # EX_CONFIG
if os.environ["APP_ENV"] == "production" and os.environ.get("LOG_LEVEL") == "debug":
    log.error("config_invalid", key="LOG_LEVEL", reason="debug not permitted in production"); sys.exit(78)
```

## Per-client configuration

With many clients, per-client configuration becomes a product in itself. Keep a **client manifest** per client (identifier, account IDs, Region, tier, enabled features, integration endpoints, contacts, support hours, change windows, approvers) as structured data that the pipeline reads, the environment documents render from, and the support team consults. Validate manifests in CI (required fields, allowed values, no secrets). Changes to manifests are pull requests with client approval where contractually required.

## Deployment documentation

Two documents, both tested:

**The deployment runbook** (template in Part XV chapter 3): pre-checks, the exact pipeline action or commands, verification steps with expected results, rollback, communication, and the record to update. It is tested every time a deploy happens by someone following it literally; any deviation is a documentation bug fixed in the same change.

**The rebuild guide**: how to recreate the environment from nothing: prerequisites (account, access, DNS delegation), the order of IaC applies (foundations, then data, then compute), secrets to create and where their values come from (owners, not values), data restore, DNS cutover, verification. Tested by actually rebuilding in a sandbox at least annually and after major changes; it is also your DR plan's backbone.

## Diagrams that stay true

Maintain the architecture diagram as code (Mermaid, Structurizr DSL, or diagrams-as-code generators from Terraform) committed with the IaC; regenerate on change; include trust boundaries, Regions, accounts and the integrations. A diagram exported once to a slide deck is already wrong.

## Handing documentation to the client

The client's team and auditors will read these documents without you. Write them for that reader; store them in the client's repository or wiki in a format they can maintain; avoid references to your internal tools unless they have access; include the last-verified date so staleness is visible; and walk through them during handover (chapter 12) with the receiving team performing the steps.

:::fde Documentation is a security control
Access procedures, break-glass, secrets inventory and rotation schedules, integration contacts and the rebuild guide are the controls that work when people are gone. Auditors ask for them; incidents need them. Treat gaps in this documentation as findings with the same seriousness as a missing MFA.
:::

## Common mistakes

- Environment knowledge in one engineer's head and shell history.
- Configuration differences between staging and production that nobody can explain.
- Secrets in `.env` files committed "for staging only".
- A runbook that was never followed literally and does not work.
- A rebuild guide never rebuilt from.
- Diagrams in slides, two reorganisations old.
