# Integration Constraints and Integrating with Client Systems

:::objectives
- Integrate with the systems clients actually have (legacy APIs, databases, file drops, message buses, SaaS) robustly, with clear contracts and failure handling.
- Negotiate and document integration contracts, test environments and change management with system owners.
- Design integrations that survive the other side being slow, down, wrong or changed without notice.
:::

## Integration is where projects slip

The product works; the client's systems are the unknown. Integration work routinely takes longer than feature work because it depends on other people's systems, documentation, test environments and change calendars. Treat each integration as a mini-project: discovery, contract, spike, build, test with the owner, operate.

## Know what you are integrating with

Each integration gets a profile, gathered during discovery (chapter 2) and kept in the systems register:

```checklist
# Integration profile
- System name, purpose, owner (team and contact), vendor if any, version
- Interface type: REST/GraphQL/SOAP API, database access, file transfer (SFTP, S3), message bus (Kafka, MQ), events/webhooks, screen scraping (last resort)
- Documentation: location, accuracy, last updated; sample payloads
- Authentication: method (OAuth client credentials, API key, mTLS, basic, SAML for UI); how credentials are issued and rotated; IP allowlisting
- Environments: test/sandbox availability, data realism, access procedure, refresh schedule
- Network path: from where you run to where it is; firewalls, proxies, private connectivity; latency
- Limits: rate limits, payload sizes, concurrency, batch windows, maintenance windows
- Semantics: idempotency support, pagination, ordering guarantees, time zones, character encodings, identifiers (stable? reused?), soft deletes
- Reliability: historical uptime, known failure modes, who to call when it is down
- Change: how changes are announced, versioning policy, deprecation notice period
- Data: classification of what crosses the boundary; what you may store; retention
```

## Design the boundary

Put every external system behind an **adapter** in your code: one module that knows the other system's quirks, exposes a clean interface in your domain's terms, and is the only place that changes when they change. The adapter owns: authentication and token lifecycle; timeouts (always; shorter than your caller's); retries with backoff and jitter for idempotent operations only; a circuit breaker; request and response logging with secrets redacted and payload sampling; metrics (latency, errors, rate-limit hits) per operation; mapping of their errors to your error taxonomy; and translation of their data model (with validation) into yours.

```python
class AccountingClient:
    """Adapter for the client's accounting API. All quirks live here."""

    def __init__(self, http, creds, breaker, clock):
        ...

    def create_invoice(self, invoice: Invoice) -> InvoiceRef:
        # Their API lacks idempotency keys: we look up by our external reference first.
        existing = self._find_by_external_ref(invoice.id)
        if existing:
            return existing
        payload = self._to_their_shape(invoice)         # dates as DD/MM/YYYY, amounts as strings, their codes
        resp = self._call("POST", "/v2/invoices", json=payload, timeout=10)
        if resp.status_code == 200 and resp.json().get("Status") == "ERROR":   # errors come as 200
            raise AccountingError.from_body(resp.json())
        return InvoiceRef(resp.json()["InvoiceID"])
```

Prefer **asynchronous** integration (queue the work, process with retries, reconcile) over synchronous calls in the user's request path whenever the business allows: it decouples your availability from theirs and gives you a natural place for retries and dead-lettering. Where synchronous is required, design the degraded experience explicitly (Part IX chapter 9).

## Contracts

Write the integration contract down, agreed with the system owner: endpoints and operations used; request and response schemas with examples; authentication and credential ownership; error semantics; rate and volume expectations; availability expectations and maintenance windows; change notification period and versioning; test environment commitments; contacts and escalation. Keep it alongside your code (an OpenAPI or AsyncAPI document where possible) and version it. The contract is what you point to when their change breaks you, and what they point to when your volume breaks them.

## Testing integrations

- **Spike** early with real credentials against the sandbox (chapter 2).
- **Contract tests** that run against the sandbox on a schedule, not just in your unit suite, to detect their changes.
- **Recorded fixtures** (VCR-style) of real responses for fast unit tests of the adapter; refresh periodically.
- **Fault injection**: timeouts, 5xx, malformed responses, slow responses, rate limiting; prove the breaker, backoff and degradation behave.
- **End-to-end with the owner**: a joint test session where both sides watch logs; the fastest way to resolve "it works on our side".
- **Data validation** on everything received: types, ranges, required fields, identifiers that exist; reject and quarantine, never silently coerce.

## Operating integrations

Dashboards per integration (calls, errors, latency, rate-limit hits, breaker state, queue depth, reconciliation differences); alerts on error rate, on silence (expected file did not arrive; no events for an hour), and on certificate or credential expiry; runbooks for "their system is down" and "their data is wrong"; a reconciliation job comparing your state to theirs daily for anything financial; a change calendar subscription for their releases; and a named counterpart on their side with an escalation path.

:::fde Their system will change without telling you
Assume it. Tolerant parsing, schema validation with alerts rather than crashes, contract tests on a schedule, reconciliation and the systems register's contact list are the difference between "we noticed within an hour and called them" and "finance found out at month end". Budget for integration maintenance in the support agreement; it is recurring work.
:::

## Common mistakes

- Synchronous dependency on a fragile system in the user's critical path.
- No timeouts; retries on non-idempotent operations; no backoff.
- Trusting documentation over the sandbox, and the sandbox over production behaviour.
- Credentials for their systems handled loosely (chapter 7).
- Reading their database directly because the API was inconvenient.
- No reconciliation, so silent divergence accumulates.
- Integration logic scattered through the codebase instead of in an adapter.

## Exercises

2. Build an adapter with timeouts, backoff, breaker, metrics and idempotent create-by-lookup against a mock that injects faults; demonstrate each failure mode is handled.
