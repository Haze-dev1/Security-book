# Designing Tenant Isolation

:::objectives
- Choose and implement an isolation model for a client deployment: isolation between the client's tenants, between the client and other clients of your platform, and between environments.
- Apply isolation at every layer (identity, network, compute, data, storage, secrets, observability, billing) and verify it with tests and tripwires.
- Explain the isolation model to a client's security team in their terms and with evidence.
:::

:::prereq
[Multi-Tenancy and Tenant Isolation](#/p03/c15); [Case Study: Multi-Tenant SaaS Platform](#/p09/c16); [AWS Accounts, Organizations and IAM](#/p07/c02).
:::

## Three isolation questions

Every client deployment has to answer:

1. **Client-from-client**: if your organisation serves many clients from a shared platform, how is this client's data and compute separated from the others? Clients' security teams ask this first.
2. **Tenant-from-tenant within the client**: if the client's system serves their own customers, departments or business units, how are *those* separated?
3. **Environment-from-environment**: how are production, staging and development isolated so a mistake or compromise in one cannot reach another?

Answer each explicitly in the design document with the mechanism, the evidence and the residual risk.

Combine layers: a client-owned account (client-from-client) containing separate accounts per environment (environment isolation), with RLS or per-tenant databases inside (tenant-from-tenant). Strong isolation at the outer layers makes mistakes at inner layers survivable.

## Isolation by layer

**Identity**: separate IAM roles per workload and per environment; no role spans environments; human access per environment with separate approval; service principals per tenant where tenants hold credentials (per-tenant API keys scoped to their data). Identity provider configuration per tenant for SSO with claims verified against the tenant context.

**Network**: environments in separate VPCs or accounts; no peering from non-production to production; security groups per service referencing other security groups rather than CIDRs; private subnets for everything that is not an edge; VPC endpoints so service traffic never crosses the internet; for tenant-dedicated deployments, per-tenant VPCs or at least per-tenant security groups; egress controls per environment.

**Compute**: separate clusters or services per environment; per-workload task roles and Kubernetes service accounts with IRSA/Pod Identity; namespaces with network policies and resource quotas per tenant when tenants share a cluster; runtime hardening (Part VI chapter 13) so a container escape is contained.

**Data**: the tenancy model (Part IX chapter 16): RLS as the floor in shared databases, per-tenant databases for dedicated tiers, encryption keys per tenant where destruction-on-exit matters; per-environment databases always, never shared; tenant-prefixed keys in caches; tenant ID carried in every queue message with consumers re-establishing context.

**Storage**: per-tenant prefixes with IAM session policies scoped at request time; per-tenant buckets for dedicated tiers; separate buckets per environment; bucket policies denying cross-account access except the explicitly intended.

**Secrets**: per-environment secret stores or paths with IAM conditions; per-tenant secrets (their integration credentials) under tenant-scoped paths readable only by that tenant's execution context.

**Observability**: logs and metrics tagged with tenant and environment; tenant-scoped views for client staff; log storage per client where contracts demand; PII handling consistent across tenants.

**Billing**: tags for tenant and environment on every resource; cost allocation reports per client; separate accounts make this trivial.


Enterprise and regulated clients increasingly require the first or second. Design your product for both from the start: infrastructure as code parameterised by account, a deployment pipeline that fans out to many accounts (Part X), and an upgrade process that rolls through clients in waves.

## Verifying isolation

Isolation claims need evidence, continuously:

- **Cross-tenant test suite**: the full API as tenant A against tenant B's identifiers, in CI on every change (Part IX chapter 16).
- **Canary tenants** with fingerprinted data and alerts on appearance anywhere else.
- **IAM access analysis**: IAM Access Analyzer or equivalent to prove no role grants cross-account or cross-environment access except the intended; findings alert.
- **Network reachability analysis**: VPC Reachability Analyzer or periodic scans proving staging cannot reach production.
- **Configuration rules**: Config rules or policy-as-code asserting tags, encryption, no public access, per-environment boundaries.
- **Penetration tests** with explicit cross-tenant objectives, periodically.
- **Access reviews**: who can reach which environment and tenant data, quarterly.

Present this evidence to client security teams: the architecture diagram with boundaries, the controls per layer, the tests and their last results, the pen-test summary, the residual risks. A security team that sees mechanisms and evidence approves faster than one that hears assurances.

:::fde "Is our data separated from your other customers'?"
Answer with the specific mechanism at each layer, what enforces it (the database, IAM, the network), how it is tested, and what would have to fail for it to break. If the honest answer is "logically, by the application", say so, explain the compensating controls, and offer the dedicated tier if their risk appetite requires it. Never answer "yes, it's isolated" without the mechanism; the follow-up question will expose it.
:::

## Common mistakes

- Shared databases across environments "to save money".
- Peering non-production to production for convenience.
- Roles that span environments; one deploy role for everything.
- Logical isolation claimed as strong isolation.
- Isolation designed once and never tested.
- Tenant context derived from the URL or a header without verification against the authenticated principal.
