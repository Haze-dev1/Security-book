## The problem

Once data lives in more than one place (replicas, caches, services, regions), "what is the current value?" has no single answer at any instant. Systems choose how much disagreement to allow and for how long; applications must be written for the choice. Most consistency bugs come from engineers assuming a stronger model than their infrastructure provides: reading from a replica after a write, caching across a change, or coordinating two services as if they shared a transaction.

## Consistency models

From strongest to weakest, as application-visible guarantees:

- **Linearizable** (strong): every operation appears to take effect instantaneously at some point between its start and end; all clients see the same order. A single-leader database with reads from the leader behaves this way for committed data. Costly across distance (coordination round trips).
- **Sequential**: all clients see the same order of operations, but not necessarily in real time.
- **Causal**: operations that are causally related (a reply after the post it answers) are seen in order by everyone; unrelated operations may be seen in different orders.
- **Read-your-writes**: a client sees its own writes; others may lag. The minimum users expect.
- **Monotonic reads**: a client never sees time go backwards (no reading a newer value, then an older one from a lagging replica).
- **Eventual**: given no new writes, replicas converge. No guarantee about *when*, and reads may return any recent value meanwhile.

Real systems: a Multi-AZ RDS primary gives linearizable reads from the primary; asynchronous read replicas give eventual consistency with monotonic reads only if you keep reading from the same replica; DynamoDB offers eventually consistent reads by default and strongly consistent reads on request (base table only); S3 is strongly consistent for object operations; CDNs are eventually consistent up to their TTL; a cache in front of a database is eventually consistent up to its invalidation delay; microservices sharing data via events are eventually consistent by construction.

## CAP, precisely

The [[cap theorem]]: in the presence of a **network partition** (nodes cannot communicate), a distributed system must choose between **consistency** (every read sees the latest write, or errors) and **availability** (every request receives a non-error response). You cannot have both *during a partition*. Partitions happen (cross-AZ links fail, regions disconnect, a node is isolated), so the choice is real but applies only in those moments.

What CAP does not say: that you choose two of three at design time forever (partition tolerance is not optional in a networked system); that "AP" systems are always available (they may still fail for other reasons); that "CP" systems are always consistent (they refuse requests during partitions to stay consistent); or anything about latency and consistency during *normal* operation, which is most of the time.

**PACELC** fills the gap: if there is a Partition, trade Availability against Consistency; Else, trade Latency against Consistency. Synchronous replication across regions is consistent but slow (every write waits for the far side); asynchronous replication is fast but eventually consistent. Most systems that call themselves "AP" are really "EL": they chose low latency over consistency even when nothing is broken.

## Choosing per data class

| Data | Model needed | Implementation |
|---|---|---|
| Money movements, inventory decrements, uniqueness (usernames, bookings) | Linearizable within the system of record | Single-leader database; writes and the decisive reads on the primary; transactions and constraints (Part VIII chapter 5) |
| User profile edits, settings | Read-your-writes | Pin reads to the primary after a write (session flag, short window); or always read profile from primary |
| Feeds, timelines, notifications | Causal / eventual | Event-driven materialisation; ordering per source; UI tolerant of delay |
| Analytics, dashboards, reports | Eventual (minutes acceptable) | Replicas, warehouses, caches |
| Search indexes | Eventual (seconds) | Async indexing from events; show "indexing" states where it matters |
| Cross-service facts (order placed → inventory, billing) | Eventual with guarantees of delivery and idempotency | Outbox, sagas, reconciliation (chapter 6) |

Write the model into the design per data class; the application code then knows whether a stale read is a bug or expected.

## Delivering guarantees over asynchronous replication

- **Read-your-writes**: after a write, route the user's reads to the primary for N seconds (a `wrote_at` timestamp in the session) or compare the replica's replay position with the write's LSN before trusting it.
- **Monotonic reads**: stick a user to one replica (consistent hashing on user ID) or carry a version/LSN in the client and reject older values.
- **Causal ordering across services**: include a version or sequence per entity in events; consumers apply only newer versions (last-writer-wins by version, not by arrival time).
- **Bounded staleness**: measure replication lag; route to the primary when lag exceeds the bound; alert.
- **Compensation**: when eventual consistency produces a conflict (two regions accept the same username), detect and resolve with a defined rule (first by timestamp with a tie-breaker, or manual review), and design the domain so conflicts are rare (reserve usernames in one region; partition by tenant).

## Replication topologies

- **Single-leader** (primary/replica): all writes to one node; simple reasoning; replicas for reads and failover; the common choice (Part VIII chapter 8).
- **Multi-leader**: several nodes accept writes (multi-region active-active); conflicts must be resolved (last-writer-wins loses data; CRDTs or application rules); only for data designed for it (chapter 10).
- **Leaderless** (Dynamo-style quorums: write to W of N, read from R of N, W + R > N for overlap): tunable consistency; used inside Cassandra, DynamoDB, Riak; the application rarely sees it directly on managed services.

## Recognising consistency bugs

| Symptom | Likely cause |
|---|---|
| User saves, refreshes, sees old value, refreshes again, sees new | Replica read after write (no read-your-writes) |
| Item appears, disappears, reappears in a list | Reads alternating between replicas with different lag (no monotonic reads) |
| Reply shown before the post it answers | Causal violation in event delivery; order by version, not arrival |
| Two users both got the last ticket | Check-then-act across replicas or without locking; use the primary with atomic conditional writes |
| Search shows deleted items for a minute | Expected eventual consistency of the index; fix the UI expectation or speed indexing |
| Totals disagree between two services | Dual writes without outbox; missing idempotency; run reconciliation |

## Common mistakes

- Reading from replicas in the write path's follow-up.
- Treating "eventually consistent" as "consistent enough" for money.
- Last-writer-wins by wall clock across machines with skewed clocks.
- Multi-leader for data with uniqueness constraints.
- Citing CAP to justify weak consistency during normal operation (the actual trade was latency).
- No per-data-class consistency decision; every bug a surprise.
- Dual writes to two stores and hoping they agree.
