# Case Study: File Upload and Processing Service

:::objectives
- Design a service that accepts user uploads (images, documents, video), scans and processes them, and serves them safely.
- Apply direct-to-object-storage uploads, asynchronous pipelines, content validation and malware scanning.
- Understand the security model for user-supplied files: a hostile input problem disguised as a storage problem.
:::

:::prereq
[Storage: S3, EBS and EFS](#/p07/c10); [File Uploads and Object Storage](#/p03/c09); [Message Brokers](#/p09/c07).
:::

## Requirements

**Functional**: authenticated users upload files up to 5 GB (video) and 50 MB (documents, images); files belong to a workspace and have permissions; processing per type: image resize and format conversion, thumbnail generation, document text extraction and preview, video transcoding to streaming formats; virus and malware scanning; download and inline viewing with permission checks; resumable uploads; retention and deletion (including legal deletion within 30 days); audit of access.

**Non-functional**: 99.9%; upload throughput limited by the user's connection, not the service; processing SLA: images within 10 s, documents within 60 s, video within 2× its duration; 100,000 uploads per day, 2 TB per day inbound, 1 PB stored over three years; cost-aware storage tiering; files must never be served from a domain that shares cookies with the application.

## Key decisions

**Direct-to-storage uploads**: the API never proxies bytes. It authorises and issues a presigned URL (or multipart upload ID) bound to a specific key, maximum size and content type, valid for minutes. This keeps the API stateless and small, lets S3 absorb the bandwidth, and makes resumable multipart uploads straightforward. The trade-off: the API cannot inspect the content before it lands, hence the quarantine bucket.

**Quarantine and promotion**: raw uploads are untrusted and unreadable by anyone until the scanner promotes them. Promotion copies the object to the content bucket under a content-addressed key (SHA-256), which deduplicates identical files and makes the stored path independent of the user-supplied filename (which is stored only as metadata and sanitised on download via `Content-Disposition`).

**Processing isolation**: parsers for images, PDFs and video are historically the richest source of remote code execution bugs. Run them in minimal containers with no outbound network, read-only filesystems, memory and CPU limits, seccomp profiles, a hard timeout, and the least IAM privilege (read quarantine key, write content key). A compromised processor should be able to do nothing but corrupt its own output. Treat decompression bombs and pathological inputs (giant dimensions, deep PDF object nesting) as expected and fail them fast.

**Serving**: a separate domain (never the app's origin) so stored HTML or SVG cannot run with the app's cookies; `Content-Type` from your validated metadata, never from the user; `Content-Disposition: attachment` for anything that is not an image or PDF you have re-encoded; `X-Content-Type-Options: nosniff`; short-lived signed URLs issued only after the permission check in the API, so S3 and CloudFront never make authorisation decisions themselves.

**Video**: transcode to HLS/DASH renditions with a managed service (MediaConvert) unless volume justifies running ffmpeg yourself; store a poster frame and duration; serve segments through the CDN with signed cookies. Long jobs run on a separate queue and worker fleet so a batch of videos does not delay thumbnails.

**Storage tiering and retention**: intelligent tiering or lifecycle rules to infrequent access after 30 days and to archive classes for cold workspaces; versioning plus a deletion workflow that tombstones in the database immediately, deletes derived renditions, and hard-deletes originals and all versions after the legal window; a periodic job proving that files marked deleted no longer exist in any bucket.

**Metadata and status**: the database is the source of truth for existence and permissions; S3 is the byte store. A file in S3 without a database row is garbage to collect; a row without an object is a failed upload to expire.

## Bottlenecks and failure modes

- **Lost events**: S3 event notifications are at-least-once but a misconfiguration can drop them. Belt and braces: the client calls `complete` on the API, which enqueues the job too; a sweeper finds rows stuck in `uploading` for over an hour and checks S3 directly.
- **Poison files**: a file that crashes the processor every time will be retried forever. Max receive count with a dead-letter queue; the record is marked `failed` with a reason; alerts on DLQ depth.
- **Thundering transcodes**: one customer uploads 10,000 videos. Per-workspace concurrency limits and fair queueing so one tenant does not starve others; priority lanes for interactive uploads.
- **Scanner signature freshness**: ClamAV definitions must update; a scanner with stale definitions should fail health checks. Supplement with commercial scanning APIs for high-risk workspaces.
- **Large multipart uploads abandoned**: incomplete multipart parts cost money silently; lifecycle rule to abort incomplete multipart uploads after 1 day.
- **Signed URL leakage**: a shared link works for anyone until it expires. Keep expiry to minutes for private files, bind to the requester where possible, and offer explicit shareable links as a distinct, audited feature.

## Security considerations

Everything in [File Uploads and Object Storage](#/p03/c09) applies: validate type by content, not extension; limit size at the presigned URL (`content-length-range`) and again in the scanner; strip metadata (EXIF location) from images on re-encode; re-encode images rather than passing bytes through; never execute, include or render stored files server-side; separate serving domain; permission check on every download; audit log of uploads, downloads and shares; SSRF prevention in any "import from URL" feature (Part IV chapter 12); IAM policies that let the API only generate URLs for keys under the caller's workspace prefix; bucket policies denying public access and unencrypted puts; KMS encryption with per-environment keys and optional per-tenant keys for enterprise.

## Operations

SLIs: upload success rate, time-to-ready per type, scanner rejection rate, DLQ depth, processing cost per GB, storage by tier and tenant. Alarms on time-to-ready SLO breaches, on DLQ growth, on scanner definition age, on orphaned objects after reconciliation. Cost review monthly: storage growth, egress through the CDN, transcoding minutes.

## Exercises

1. Build the ticket → presigned PUT → S3 event → scan → promote path with a local S3-compatible store (MinIO) and ClamAV; test with the EICAR test file and a PNG renamed to .pdf.
2. Write the processor's container hardening (no network, read-only root, memory limit, seccomp, timeout) and prove a decompression bomb is rejected within budget.
3. Design the deletion workflow and the verification job that proves a deleted file is gone from every bucket and version.
