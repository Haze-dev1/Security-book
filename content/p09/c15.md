# Case Study: Real-Time Notification Platform

:::objectives
- Design a platform that delivers notifications to users across channels (in-app real time, push, email, SMS) with preferences, batching and delivery guarantees.
- Handle fan-out, connection management at scale, ordering, deduplication and the long tail of unreachable devices.
- Keep a system that touches every user's attention from becoming a spam engine or a privacy leak.
:::

:::prereq
[WebSockets, Server-Sent Events and gRPC](#/p02/c14); [Real-Time Applications](#/p03/c11); [Message Brokers](#/p09/c07).
:::

## Requirements

**Functional**: producers (other services) emit events ("comment on your document", "deploy finished", "invoice due"); the platform resolves recipients, applies user and tenant preferences (channels, quiet hours, digests), renders templates per channel and locale, and delivers: in-app via a persistent connection, mobile push (APNs/FCM), email, SMS, and webhooks to integrations; an inbox API with read/unread state; delivery status and analytics; rate limiting and digesting to prevent floods; unsubscribe and compliance (CAN-SPAM, GDPR consent for marketing).

**Non-functional**: 5 million users, 500,000 concurrently connected; 50 million notifications/day (~580/s average, 10,000/s peak during broadcast events); in-app delivery p95 < 1 s to connected users; push within 5 s; email within 1 minute; 99.9% availability for ingestion (producers must never block); at-least-once delivery with deduplication so users do not see duplicates; ordering within a user's inbox; a full month of inbox history retrievable.

## Key decisions

**The inbox is the source of truth; real time is an optimisation**: every notification is written to the inbox store first, then pushed to connected clients. A client that misses a push (network blip, node restart) reconciles on reconnect by fetching since its last seen ID. This turns the hardest problem (reliable delivery over flaky connections) into a simple one (durable write plus best-effort push plus catch-up read).

**Partition by user**: events for one user land on the same partition, so processing order per user is preserved and the inbox sort key reflects creation order. Broadcasts to a topic with a million subscribers are expanded into per-user records by the fan-out stage in batches, with the expansion itself checkpointed so a restart does not double-send.

**Connection gateway design**: stateless except for the in-memory connection table; each node registers the users it holds in the presence registry with heartbeats; delivery publishes to the specific node's channel. Nodes drain gracefully on deploy (stop accepting, tell clients to reconnect with jitter, close). Clients reconnect with exponential backoff and jitter; a mass reconnect after a node failure is the platform's own thundering herd, so the load balancer uses connection-aware routing and new nodes warm slowly.

**Preferences and digests**: resolved at fan-out time, cached with event-driven invalidation; quiet hours delay rather than drop; digest rules collapse many low-priority events into one email per hour or day via a scheduled aggregation job keyed by user and digest window; per-event-type and per-sender rate limits (max N pushes per user per hour) protect attention; critical categories (security alerts) bypass quiet hours and digests.

**Channels**: each channel is an independent queue and worker pool with its own retry and timeout policy, so an SMS provider outage does not delay in-app delivery; providers' feedback (bounces, invalid tokens, unsubscribes) flows back as events that update suppression lists; webhooks to customer integrations follow the webhook chapter (signatures, retries with backoff, dead-lettering after a day).

**Deduplication**: at ingest by producer idempotency key; at inbox by deterministic notification ID (hash of event ID and user ID) so a replayed partition is harmless; at the client by ID.

**Templates and localisation**: rendered per channel and locale from versioned templates; payload data validated against the event schema so a producer cannot inject HTML into an email template; previews and a test-send flow for template authors.

## Bottlenecks and failure modes

- **Broadcast fan-out**: a tenant-wide announcement to a million users generates a million inbox writes and pushes. Rate the expansion (for example 20,000 users/s), prioritise interactive events in a separate lane, and write inbox records in batches.
- **Reconnect storms**: a gateway deploy or network incident disconnects 100,000 clients who all reconnect at once. Jittered backoff on clients, connection rate limits at the load balancer, and never deploying all gateway nodes simultaneously.
- **Presence staleness**: a node dies without cleaning the registry; deliveries publish to nobody. Heartbeat TTLs (30 s) expire entries; delivery is best-effort anyway because the inbox catches up.
- **Hot users**: a user subscribed to everything gets 10,000 events per hour. Per-user rate limiting at fan-out collapses into a digest and protects their partition from dominating a consumer.
- **Provider throttling**: APNs and FCM throttle bursts; email providers enforce sending rates per domain; SMS costs real money per message. Token buckets per provider, cost caps per tenant per day, alerts on anomalies (a bug that sends 50 SMS to each user is a budget incident within minutes).
- **Clock skew and ordering**: ULIDs generated on different fan-out workers can interleave slightly out of order; acceptable for an inbox, and the per-partition order is preserved for causally related events from the same producer.
- **Inbox store hot partitions**: a single user's partition receiving a flood; DynamoDB adaptive capacity handles moderate skew; the rate limit handles the rest.

## Security and privacy considerations

Notifications carry snippets of private data to devices and third-party providers. Minimise payloads sent to push providers (send a title and an ID; fetch content on open) so content never transits APNs/FCM in clear text where policy demands; strip PII from logs; authenticate producers and validate that a producer may notify the recipients it names (a service for tenant A must not notify tenant B's users); webhook URLs owned by customers are SSRF targets (allowlist schemes, resolve and block private ranges, Part IV chapter 12); unsubscribe links signed and single-purpose; consent and suppression respected before any marketing send; the WebSocket handshake authenticates with a short-lived token, not a long-lived cookie reused cross-origin (Part II chapter 14); per-tenant and per-user data deletion covers inbox records, archives and provider-side data where possible.

## Operations

SLIs: ingest latency and success rate, end-to-end delivery latency per channel (p50/p95), connected clients, reconnect rate, delivery failure rate per provider, DLQ depths, cost per channel per day. Alarms on delivery latency SLO burn, on provider circuit breakers open, on reconnect storms, on daily SMS/email cost above budget. Dashboards per tenant for enterprise customers. Game days: kill a gateway node, pause a provider, replay a partition and verify no duplicates.

## Exercises

1. Build a minimal gateway (WebSocket server, presence in Redis, inbox in a local store) and demonstrate catch-up after a forced disconnect with no duplicates and no gaps.
2. Design the preference resolution function (tenant defaults, user overrides, quiet hours, digest, critical bypass) and write table-driven tests for it.
3. Simulate a provider outage with a stub that returns 429 and verify the circuit breaker, backoff and DLQ behaviour while in-app delivery is unaffected.
