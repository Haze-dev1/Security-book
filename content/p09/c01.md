# Requirements, Capacity Estimation and Latency Budgets

:::objectives
- Turn vague asks into functional and non-functional requirements with numbers you can design against.
- Estimate traffic, storage, bandwidth and growth to order-of-magnitude accuracy and use the estimate to size the architecture.
- Build a latency budget and allocate it across components.
- Record requirements so that later design decisions can be checked against them.
:::

:::prereq
Part II chapter 18; Part VII chapter 4.
:::

## The problem

"Make it fast and reliable and able to scale" is not a requirement; it is a mood. Every architecture choice in this part trades cost and complexity against specific numbers: how many users, how fast, how available, how much data loss is tolerable. Without the numbers, teams over-build (a multi-region platform for 200 users) or under-build (a single instance for a payroll run everyone depends on). Requirements work is where a Forward Deployed Engineer earns the right to make technical decisions.

## Functional and non-functional requirements

**Functional**: what the system does (create orders, send notifications, export reports). Captured as user stories or use cases with acceptance criteria (Part XII chapter 1).

**Non-functional** (quality attributes): how well it does it. The ones that drive architecture:

| Attribute | Question to ask the client | Expressed as |
|---|---|---|
| Availability | How long can it be down before it hurts, and when? | SLO: 99.9% monthly; maintenance windows |
| Latency | What feels slow to users? Which operations are time-critical? | p95/p99 targets per operation class |
| Throughput / scale | How many users, requests, records, now and in 3 years? Peaks? | Peak RPS, daily volumes, growth rate |
| Durability / RPO | How much data could you lose without disaster? | RPO in minutes |
| Recovery / RTO | How long may recovery take? | RTO in minutes/hours |
| Consistency | Can two users ever briefly see different values? Which operations must be exact? | Strong vs eventual per data class |
| Security / compliance | What data classes? Which regulations? Who may access what? | Classification; frameworks; authn/authz model |
| Residency | Where may data live and be processed? | Regions; processor list |
| Cost | What is the budget, monthly and total? | Ceilings; cost per tenant |
| Operability | Who runs it after handover, with what skills? | Managed-service bias; runbook needs |
| Integrations | What must it talk to, with what constraints? | Contracts; rate limits; auth |

Ask in the client's language and translate (Part XIII chapter 14). "It must not go down during the trade show" becomes an availability SLO for that period plus a change freeze. "We can't lose orders" becomes RPO ≈ 0 for the order path (synchronous replication, idempotent writes) and perhaps a looser RPO elsewhere.

## Capacity estimation

Order-of-magnitude arithmetic, done early, prevents both panic and complacency.

```widget:capacity
{"dau": 50000, "rpu": 40, "peak": 4, "bytes": 3000, "write": 15, "row": 600}
```

Method:

1. **Users and actions**: daily active users × actions per user per day = requests per day. 50,000 DAU × 40 = 2,000,000 requests/day.
2. **Average and peak rate**: ÷ 86,400 ≈ 23 rps average; peak factor 3–5× for business apps (more for events, launches, media): ~100 rps peak. Design and load test for 2–3× peak.
3. **Read/write mix**: typically 80–95% reads. Writes drive database sizing and replication; reads drive caching.
4. **Payload and bandwidth**: average response 3 KB × 100 rps × 8 bits ≈ 2.4 Mbps egress at peak; trivial for a load balancer, a cost line for data transfer (Part VII chapter 4).
5. **Storage**: writes per day × bytes per record × retention; plus indexes (×1.5–2), plus blobs separately. 300,000 writes/day × 600 B ≈ 180 MB/day ≈ 65 GB/year before indexes: a small RDS instance for years.
6. **Growth**: apply the client's expected growth (and a stretch case) to see when the next scaling rung arrives (Part VIII chapter 12).
7. **Connections and concurrency**: concurrent requests ≈ rps × average latency (Little's law): 100 rps × 0.2 s = 20 in flight; pool sizes and worker counts follow (Part VIII chapter 6).

The point is the *tier*: this example is "one modest application fleet and a small managed database", and anything more elaborate needs a justification other than scale.

## Latency budgets

A latency target is only actionable when allocated across components:

```widget:latency
{"target": 300, "rows": [["Client → edge (TLS reused)", 30], ["ALB + routing", 2], ["Auth middleware (cached session)", 3], ["Authorization + validation", 2], ["Primary query", 8], ["Secondary queries (batched)", 10], ["Cache lookups", 2], ["Serialise", 5], ["Edge → client", 30], ["Headroom for p99 variance", 100]]}
```

Rules: budget at p95 or p99, not average; sequential dependencies add, parallel ones take the max (but fan-out exposes the slowest); reserve 30–50% headroom for tail variance and growth; anything over budget by design (an external API at 400 ms) must move off the request path (async, cache, precompute) rather than consume the budget; and measure the real distribution after launch to recalibrate (Part XI chapter 8).

## Availability arithmetic

```widget:slo
{"value": 99.9, "req": 20000000}
```

99.9% monthly is ~43 minutes of downtime; 99.95% is ~22; 99.99% is ~4. Serial dependencies multiply: a system depending on three 99.9% services is at best 99.7%. Each extra nine roughly doubles cost and complexity (Multi-AZ → multi-Region → active-active; Part IX chapter 10). Ask what each nine is worth to the business before promising it, and write the SLO with its measurement method (Part XI chapter 4).

## Writing it down

A requirements document for a system of any size includes: scope and users; functional requirements with acceptance criteria; the non-functional table filled with numbers and their sources; capacity estimates with assumptions; data classification and compliance obligations; integrations and their contracts; constraints (budget, residency, team); explicit non-goals ("not designed for more than 1,000 tenants without re-architecture"); and open questions with owners. Two to five pages for most client systems. It is the reference every ADR cites and every readiness review checks against (Part I chapter 15).

## Common mistakes

- Designing for imagined scale (millions of users) when the client has hundreds.
- No peak factor; the launch-day spike takes the system down.
- Latency targets as averages; a terrible tail hidden by a good mean.
- Availability promised without arithmetic or measurement.
- RPO/RTO never discussed; discovered during the first incident.
- Residency and compliance omitted until procurement blocks the deployment.
- Requirements in someone's head; every design argument restarts from scratch.
- Confusing "the client said" with "the client needs"; failing to ask why.

## Exercises

1. Interview a stakeholder (or role-play one) about a planned system; fill the non-functional table with numbers and sources; note every answer you had to translate.
2. Run the capacity estimate for the system; identify the scaling tier and the first rung of the Part VIII ladder it would need in three years.
3. Build the latency budget for the main user action; identify the dominant component and propose how to move it off the request path if needed.
