# Case Study: Authentication Platform

:::objectives
- Design an identity platform serving several applications: registration, login, sessions and tokens, MFA, SSO federation, account recovery, administration.
- Reason about the availability, security and privacy constraints that make authentication different from ordinary services.
- Decide when to build versus buy (Cognito, Auth0, Keycloak) and what remains yours either way.
:::

:::prereq
Part IV chapters 3–8; chapters 1–10 of this part.
:::

## Requirements

**Functional**: email/password and passkey registration and login; TOTP and WebAuthn MFA; social login (Google, Microsoft) and enterprise SSO (OIDC/SAML per tenant); issue sessions for first-party web apps and OAuth 2.0 tokens for APIs and mobile; refresh and revocation; password reset and MFA recovery; admin console (users, roles, tenants, audit); SCIM provisioning for enterprise tenants; audit log of all authentication events.

**Non-functional**: availability 99.99% for token validation and login (every application depends on it); login p95 < 500 ms; token validation local (no network call) at p99 < 2 ms; 1 million users, 200,000 daily logins, peak 100 logins/s; strong security (this is the system whose compromise is total); privacy (minimal personal data, regional residency); auditability for compliance.

## Key decisions

**Build or buy**: managed IdPs (Cognito, Auth0/Okta CIC, Entra External ID) or self-hosted Keycloak/Ory provide the protocols, MFA, federation and much of the hardening; building from scratch is justified only with strong reasons (unusual requirements, cost at very large scale, residency constraints a vendor cannot meet). Even when buying, you own: user data model and tenancy, role mapping, session handling in your apps, recovery policy, audit integration, and the vendor's configuration. This case study assumes building the core to teach the trade-offs; in practice recommend buying unless the client has a reason not to.

**Tokens and sessions**: first-party web apps get a server-side session cookie from the auth service's domain via OIDC (the apps are relying parties); APIs receive short-lived (10 min) ES256 access tokens signed via KMS with `kid`, validated locally against cached JWKS (so token validation has no runtime dependency on the auth service, which is what makes 99.99% *for validation* achievable); refresh tokens are opaque, stored hashed, rotated on use with family revocation on reuse (Part IV chapter 5); revocation is immediate for sessions and refresh tokens and bounded by 10 minutes for access tokens (plus an optional short-TTL denylist check for high-risk apps).

**Credentials**: Argon2id with tuned parameters; breached-password check at set time; passkeys as the preferred factor; TOTP with replay protection; WebAuthn security keys for admins; recovery codes hashed; recovery flows deliberately slow and multi-channel (Part IV chapter 8).

**Tenancy and federation**: tenants configured with their own IdP (OIDC or SAML), domain-based routing on login, JIT provisioning or SCIM; users keyed by `(issuer, subject)`; role mapping from IdP groups; per-tenant policies (MFA required, session length, allowed factors). Tenant isolation via RLS and tenant-scoped admin roles (Part III chapter 15).

**Availability**: the auth service is stateless and multi-AZ; Redis and the database are HA; JWKS cached by clients for hours (so key rotation publishes the new key well before use); pilot light in a second Region with database replication and DNS failover for the login path; token validation already survives a full auth outage for the token lifetime. Degradation: if the email provider is down, logins proceed, resets queue; if an external IdP is down, that tenant's SSO fails with a clear message while others continue.

**Audit and privacy**: every authentication event (success, failure, MFA, recovery, admin action) to an append-only store with tamper-evidence, shipped off-box, retained per policy (Part IV chapter 22); minimal personal data (no unnecessary profile fields); IPs truncated after a short window; regional deployment per residency requirement.

## Bottlenecks and failure modes

- **Argon2 CPU**: 100 logins/s × 100 ms CPU = 10 CPU-seconds per second: 12+ vCPUs just for hashing at peak. Size for it; put hashing on a dedicated worker pool so a credential-stuffing burst cannot starve token endpoints; rate-limit per account and IP before hashing (reject early); use a dummy hash for unknown users to equalise timing.
- **Credential stuffing**: the dominant traffic during attacks. WAF rate rules, per-account and per-IP limits, progressive delays, device fingerprint reputation, breached-password checks, and MFA. Monitor failure rates as the attack signal.
- **Redis unavailable**: sessions and rate limits fail; fail closed (503) for session validation; HA Redis is therefore mandatory, not optional.
- **KMS latency and quotas**: signing via KMS adds ~5–10 ms and has request quotas; cache nothing about private keys (they never leave KMS) but batch and keep token issuance rate within quota; request quota increases; alternatively hold signing keys in memory loaded from KMS-wrapped storage for very high rates, accepting a weaker boundary.
- **Key rotation**: publish the new public key in JWKS, wait longer than the longest client cache, start signing with it, retire the old key after all tokens signed with it expire. A client that caches JWKS forever will break; document cache TTLs and `kid` handling for integrators.
- **Email deliverability**: reset links in spam; SPF/DKIM/DMARC configured; a provider with reputation management; status visible to support.

## Security considerations (the non-negotiables)

Everything in Part IV chapters 3–9 applies, plus: the auth service's own admin access via hardware-key MFA and SSO; separate deployment and network path for admin/SCIM; secrets (IdP client secrets, signing configuration) in Secrets Manager with per-tenant scoping; strict CSP and no third-party scripts on login pages; signed and pinned dependencies; regular penetration tests focused on the protocol flows; incident runbooks for "signing key compromised" (rotate immediately, revoke all sessions, force re-authentication) and "tenant IdP compromised" (disable federation for the tenant, notify).

## Operations

SLIs: login success rate and latency, token issuance latency, JWKS availability, MFA success rate, reset completion rate; alarms on failure-rate spikes (attack), on error budget burn, on KMS throttling, on Redis failover; dashboards per tenant for enterprise customers; audit queries for support; drills for key rotation and regional failover.

1. Write the token and session design (lifetimes, rotation, revocation, JWKS cache guidance) as the integration guide you would give relying-party developers.
2. Size the hashing capacity for 100 logins/s with Argon2id at 100 ms and design the pre-hash rate limiting; load test with a credential-stuffing simulation in a sandbox.
