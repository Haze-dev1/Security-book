## What a broker provides

Decoupling in time (producers and consumers need not be up simultaneously), buffering (absorb bursts), fan-out (many consumers of one event), durability (messages survive crashes), and delivery semantics (at-least-once, with deduplication or ordering as options). Each broker makes different choices; the choices determine what your consumers must handle.

## Kafka concepts, since you will meet them

A **topic** is split into **partitions**; each partition is an ordered, append-only log; messages with the same **key** go to the same partition (ordering per key); a **consumer group** divides partitions among its members (each partition to exactly one member), so parallelism is bounded by partition count; consumers track **offsets** and commit them; **retention** keeps messages for a time or size regardless of consumption, enabling replay and multiple independent consumer groups; **compacted topics** keep the latest value per key (a changelog). Producers batch and can be idempotent; **transactions** make produce-and-commit-offsets atomic for exactly-once stream processing. Operational concerns: partition count (hard to change without re-keying; over-provision moderately), consumer lag monitoring, rebalances (consumers joining/leaving pause processing), broker storage, under-replicated partitions, and version upgrades. Schema Registry (Avro/Protobuf/JSON Schema) enforces compatibility of message shapes.

Kafka is superb for streams: event sourcing, change data capture, analytics ingestion, feeding many downstream systems from one firehose. It is a poor job queue: no per-message acks (offsets are positional, so a slow message blocks its partition's progress or must be parked), no delayed delivery, no native dead-letter semantics, and a lot to operate.

## RabbitMQ in brief

AMQP broker: producers publish to **exchanges**; **bindings** route to **queues** by routing key or headers; consumers ack messages individually; unacked messages are redelivered; **dead-letter exchanges** capture rejected or expired messages; priorities, TTLs and delayed delivery (plugin); **quorum queues** replicate for HA; **streams** add Kafka-like replay. Excellent routing flexibility and per-message semantics; moderate operational load (Amazon MQ manages the broker but you size and configure it). Natural for on-premises or multi-cloud clients and for complex routing topologies.

## SQS and SNS/EventBridge in brief

Part III chapters 6–7 covered the patterns. Reminders: standard queues are at-least-once and unordered; FIFO queues order within a message group and deduplicate by ID for five minutes (and have throughput limits per group); visibility timeout must exceed processing time; long polling; batching for cost; DLQ with `maxReceiveCount`; redrive to source. SNS fans out to SQS queues, Lambda, HTTP endpoints with **message filtering** per subscriber; EventBridge adds content-based **rules**, schema discovery, archive and replay, scheduler, and integrations with SaaS and AWS service events (the right home for "something happened in AWS" automation). Both are serverless with no operations.

## Designing producers and consumers

Regardless of broker:

- **Envelope**: event ID, type, version, occurred-at, producer, trace context, and the payload (Part III chapter 7). The event ID is the dedup key.
- **Idempotent consumers** (Part III chapter 3): dedup by event ID with a bounded store; version checks for out-of-order.
- **Keys for ordering**: choose the entity whose order matters (order ID, tenant ID); never expect global order.
- **Bounded retries**: exponential backoff; dead-letter after N; alert on DLQ depth; a replay tool.
- **Backpressure**: consumers pull at their pace (SQS, Kafka); producers may need to slow when queues or lag grow; alert on age of oldest message or consumer lag.
- **Poison messages**: a message that always fails must not block the queue (SQS: DLQ; Kafka: park it in a retry/DLQ topic and commit past it).
- **Schema evolution**: additive changes; version field; consumers tolerant of unknown fields (Part III chapter 7).
- **Security**: encryption at rest and in transit; IAM/ACLs per producer and consumer; validate message content as untrusted input.
- **Observability**: trace propagation through message attributes; per-queue/topic metrics; end-to-end latency.

## Choosing for a client

- Work queue on AWS → **SQS** (standard; FIFO only if ordering per key is required and throughput fits).
- Fan-out of domain events to several AWS consumers → **SNS → SQS** or **EventBridge** (when routing rules, schema registry or SaaS sources matter).
- Replayable event stream, CDC, analytics feeds, many consumer teams, very high volume → **Kafka** (MSK Serverless or Confluent to limit operations), with a team that will own it.
- Complex routing, AMQP clients, on-premises → **RabbitMQ**.
- Lightweight in-app queue where Redis already exists and loss is tolerable → **Redis Streams** (Part VIII chapter 11).

Default to the simplest broker that meets the semantics; Kafka clusters for a three-service system are a common and expensive regret.

## Common mistakes

- Assuming ordering across partitions or standard queues.
- Kafka as a job queue; slow messages block partitions.
- Partition count chosen tiny; cannot scale consumers.
- Retries without backoff or limit; a poison message consumed forever.
- Visibility timeouts shorter than processing (duplicate processing) or far longer (slow recovery).
- No DLQ or nobody watching it.
- Breaking schema changes stranding old messages.
- No idempotency; duplicates become double emails and double charges.
- Choosing by hype; operating a cluster nobody owns.

1. Run Kafka (Redpanda) locally: create a topic with 3 partitions, produce keyed messages, run 1 then 3 then 5 consumers in a group and observe assignment; then make one message fail forever and design the parking strategy.
2. Implement the same work queue on SQS and RabbitMQ with DLQs; compare the code for acks, retries and poison handling.
3. Write the broker-selection ADR for a client system with order events consumed by billing, inventory and analytics, including the ordering key and dedup strategy.
