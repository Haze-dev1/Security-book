## Coordination is expensive

Agreeing on one value across machines that can fail and lose messages is the hard problem of distributed systems. [[consensus]] algorithms (Paxos, Raft) solve it correctly at the cost of round trips and operational care; they run inside etcd, ZooKeeper, Consul, Kubernetes, DynamoDB, Aurora's storage layer, Kafka's controller and every managed database's failover. You almost never implement consensus; you use systems that have it and design your application so that most operations need no cross-node agreement at all.

## Leader election

A singleton (a scheduler, a batch coordinator, a reconciler) must run exactly once across N instances, and keep running when the current runner dies. The practical mechanism is a **lease**: a record with an owner and an expiry that the leader renews; others try to acquire when it expires.

```sql
-- leases table: (name text primary key, owner text, expires_at timestamptz)
-- acquire or renew, atomically; returns the row only if we now hold it
INSERT INTO leases (name, owner, expires_at) VALUES ('scheduler', $1, now() + interval '30 seconds')
ON CONFLICT (name) DO UPDATE SET owner = EXCLUDED.owner, expires_at = EXCLUDED.expires_at
  WHERE leases.owner = EXCLUDED.owner OR leases.expires_at < now()
RETURNING owner;
```

The leader loop: acquire; while held, do leader work and renew every 10 s; if a renewal fails (someone else holds it), stop leader work immediately. Correctness caveats: the leader may be paused (GC, network) past expiry while believing it leads, so leader work must be idempotent or guarded with a **fencing token** (the lease's version number passed with every write and checked by the target). Kubernetes `Lease` objects, Redis `SET NX PX` with renewal, and DynamoDB conditional writes implement the same pattern; a database you already run is the simplest, most reliable choice.

For scheduled work specifically, consider not electing at all: an external scheduler (EventBridge → SQS/Lambda/ECS task) runs the job once; idempotency handles the rare double fire (Part III chapter 6).

## The dual-write problem

A service updates its database and then publishes an event (or calls another service). If it crashes between the two, the world is inconsistent: the order exists but billing never heard; or the event was sent for a transaction that rolled back. No amount of retry logic fixes this because the two writes are not atomic.

### The outbox pattern

Write the event into an `outbox` table in the **same transaction** as the business change. A relay (a polling worker, or change data capture reading the WAL via Debezium) publishes outbox rows to the broker and marks them sent. Publishing is at-least-once (the relay may crash after publishing but before marking), so consumers are idempotent (Part III chapter 3). Result: exactly-once *recording*, at-least-once *delivery*, no lost or phantom events.

```python
async with db.transaction():
    order_id = await orders.insert(db, ...)
    await db.execute("INSERT INTO outbox (id, aggregate, type, payload, created_at) VALUES ($1,'order','OrderPlaced',$2, now())", ulid(), json.dumps({"order_id": str(order_id), "version": 1}))
# relay (separate process):
# SELECT ... FROM outbox WHERE published_at IS NULL ORDER BY created_at LIMIT 100 FOR UPDATE SKIP LOCKED;
# publish each to SNS/SQS/Kafka with the outbox id as the dedup/message id; UPDATE outbox SET published_at = now()
```

### Sagas

A business process spanning services (reserve inventory → charge payment → create shipment) cannot be one transaction. A **saga** is a sequence of local transactions, each publishing an event that triggers the next, with **compensating actions** to undo earlier steps when a later one fails (release inventory if payment fails; refund if shipment cannot be created).

Two styles: **choreography** (each service reacts to events; simple for short chains, hard to follow as they grow) and **orchestration** (a coordinator, often a workflow engine, drives the steps and compensations; explicit, observable, easier to change). Design rules: every step idempotent; every compensation idempotent and able to run after partial failure; the saga's state persisted (orchestrator) or derivable from events (choreography); timeouts for steps that never respond; and **semantic locks** or status fields (`order.status = 'payment_pending'`) so other operations know a saga is in flight.

### Two-phase commit

2PC makes several resources commit atomically via a coordinator (prepare, then commit). It exists (XA transactions, some databases' distributed transactions) and is rarely appropriate for services: it blocks all participants while waiting, the coordinator is a single point of failure that can leave participants locked, it couples availability of every participant, and most message brokers and HTTP APIs do not participate. Use it only within a single database cluster that supports it natively, and even then prefer designs that avoid it.

## Workflow engines

For sagas with many steps, long waits (days), human approvals and retries, a durable workflow engine (AWS Step Functions, Temporal, Cadence, Camunda) persists state, handles retries and timeouts, and makes the process visible. Step Functions integrates with AWS services natively and is the pragmatic choice on AWS for order processing, document pipelines and provisioning flows; Temporal when you need code-first workflows across clouds. The trade is another system and a learning curve; for two-step processes, an outbox and idempotent consumers suffice.

## Reconciliation

Eventual consistency guarantees convergence only if nothing is lost; in practice bugs, dropped messages and partial failures leave inconsistencies. **Reconciliation jobs** compare systems periodically (orders marked paid versus payment provider records; reservations versus stock counts; events published versus consumed) and repair or alert. They are the safety net under every asynchronous design and a standard client requirement in finance-adjacent domains. Build them from day one; schedule them; alert on discrepancies; keep a log of repairs.

## Choosing

| Need | Use |
|---|---|
| One instance runs a periodic job | External scheduler + idempotency, or a database lease with fencing |
| Publish an event reliably after a database change | Outbox pattern |
| Multi-service business process with rollback | Saga (orchestrated via Step Functions/Temporal for anything non-trivial) |
| Atomic change across tables in one database | A normal transaction (keep related data together) |
| Atomic change across two databases | Redesign to avoid it; outbox + idempotent consumer; last resort 2PC within one cluster |
| Catch what slipped through | Reconciliation jobs |

## Common mistakes

- Publishing after commit without an outbox; lost events on crash.
- Leaders without fencing; two leaders after a pause.
- Sagas without compensations, or with compensations that are not idempotent.
- Choreographed sagas spanning eight services that nobody can trace.
- 2PC across HTTP services.
- No reconciliation; inconsistencies discovered by customers.
- Splitting tightly coupled data across services so that every operation needs a saga (Part I chapter 14).
