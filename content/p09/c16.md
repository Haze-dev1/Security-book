# Case Study: Multi-Tenant SaaS Platform

:::objectives
- Design a B2B SaaS platform serving hundreds of organisations from shared infrastructure with strong isolation, per-tenant configuration and enterprise features (SSO, audit, data residency).
- Choose a tenancy model deliberately and understand how it affects every layer: database, cache, queues, storage, observability and billing.
- Build the controls that prevent the single worst SaaS incident: one tenant seeing another tenant's data.
:::

:::prereq
[Multi-Tenancy and Tenant Isolation](#/p03/c15); [Authorization Models: RBAC, ABAC and Resource-Level Access](#/p04/c07); chapters 1–10 of this part.
:::

## Requirements

**Functional**: organisations (tenants) sign up self-serve or are provisioned by sales; each tenant has users, roles, projects and data; tenant admins manage members, SSO, API keys and billing; enterprise tiers require SSO/SAML, SCIM, audit log export, data residency (EU or US), custom retention, and optionally a dedicated database; public API with per-tenant keys and rate limits; integrations via webhooks; usage-based billing.

**Non-functional**: 2,000 tenants from 5-seat startups to a 20,000-seat enterprise; 99.95% availability with per-tenant status visibility; zero cross-tenant data exposure (a hard requirement verified by tests, not a goal); noisy-neighbour protection so one tenant's load cannot degrade others beyond defined limits; tenant onboarding in under a minute for the shared tier; ability to move a tenant between tiers (shared → dedicated) and Regions; per-tenant cost attribution.

This case study uses a **hybrid**: a shared PostgreSQL pool with `tenant_id` and row-level security for the self-serve tiers, plus database-per-tenant for enterprise tiers, behind the same application code. The application code is identical; only the connection routing differs. Both pools exist in each Region offered (EU, US) and a tenant lives in exactly one Region.

## Key decisions

**Tenant context is established once and enforced everywhere**: the first middleware resolves the tenant from the host or token, verifies that the authenticated principal belongs to it, and places an immutable context on the request. Database access goes through a repository layer that opens the connection for the right pool and sets `app.tenant_id` for RLS inside the transaction; cache, storage and queue clients take the context, not a raw ID, so forgetting the tenant is a compile-time or startup error rather than a data leak. Background jobs carry the tenant ID in the payload and re-establish the context before any I/O.

**Defence in depth against cross-tenant leaks**: RLS as the floor (even a buggy query cannot return another tenant's rows); application-level scoping as the first line; tests that run the entire API as tenant A against data seeded for tenant B and assert zero results and zero 200s on B's object IDs; a canary tenant whose data is fingerprinted and alerted on if it ever appears in another tenant's responses or exports; database roles for the app that cannot bypass RLS and cannot access other tenants' dedicated databases.

**Provisioning as a workflow**: creating a tenant is multi-step (registry row, database or RLS setup, migrations, default roles, billing customer, DNS for custom domains) and must be idempotent and resumable (Step Functions or a durable workflow library), with a "tenant status" that gates login until ready. Deprovisioning is the mirror image, with a grace period and export before destruction.

**Migrations across a fleet**: schema changes apply to the shared pool once and to every dedicated database; orchestrate with a migration runner that tracks per-database versions, runs in waves (canary tenants first), is backwards compatible across the deploy window (expand/contract, Part X chapter 8), and reports stragglers.

**Noisy-neighbour controls**: per-tenant rate limits at the edge and the API; per-tenant connection and query timeouts; statement timeouts; per-tenant job concurrency; cache budgets; per-tenant storage quotas; a "tier" that maps to limits, and an emergency knob to throttle a single misbehaving tenant without affecting others.

**Residency**: a tenant is pinned to a Region at creation; the global entry point routes by tenant to the Region (DNS per tenant subdomain or an edge lookup); no cross-Region replication of tenant data except where the tenant's tier includes DR into a permitted Region; control-plane metadata (tenant registry) may be global and contains no customer content.

**Feature flags and configuration per tenant**: flags evaluated with the tenant as the context, enabling gradual rollout by tenant, enterprise-only features and kill switches; configuration stored in the registry with validation and audit.

**Billing and metering**: usage events (seats, API calls, storage GB-hours, jobs) emitted with tenant ID into a metering pipeline; idempotent aggregation; invoices from a billing provider; the same events give per-tenant infrastructure cost attribution for pricing decisions.

## Bottlenecks and failure modes

- **One big tenant on the shared pool**: a 20,000-seat tenant dwarfs others; indexes leading with `tenant_id` become skewed; move such tenants to dedicated databases (tooling for live migration: dual-write or replicate, cut over with a short read-only window).
- **Connection explosion** with database-per-tenant: 200 dedicated databases × pool of 10 × 20 app instances is 40,000 connections. Use a proxy (RDS Proxy or PgBouncer) per database, lazy pools that close idle tenant connections, and route tenants to app instance subsets.
- **Migration stragglers**: a dedicated database fails a migration; the application must tolerate mixed versions during the window and the runner must surface the straggler loudly.
- **Cache key leaks**: a developer forgets the tenant prefix; prevented by a cache client that derives keys from the context and fuzz tests that look for unprefixed keys.
- **Registry as a single point of failure**: every request needs the tenant registry; cache it aggressively with a fallback to the last known good snapshot and a short TTL for changes.
- **Custom domains and certificates**: hundreds of customer domains need validation and renewal; use ACM with DNS validation and automate CNAME instructions; monitor expiring validations.

## Security considerations

Tenant isolation is the security property customers buy. Beyond the controls above: tenant-scoped admin roles (a tenant admin cannot see another tenant); support access to tenant data only through an audited, time-bound, consented "break glass" flow with tenant notification; per-tenant encryption keys for enterprise tiers so a tenant's departure can be enforced by key destruction; export and deletion APIs that are complete across every store; audit log export per tenant (SIEM integration); SSO enforcement options and session policy per tenant; API keys bound to tenant and scopes with rotation and last-used tracking; webhooks with per-tenant secrets; penetration tests specifically targeting cross-tenant access; threat model entries for "malicious tenant admin" and "compromised tenant user".

## Operations

SLIs per tenant and global: availability, latency, error rate, job latency, API quota consumption; per-tenant status pages for enterprise; alerts when a single tenant's error rate deviates (their integration broke) separately from global alerts (we broke); cost per tenant monthly; migration fleet health; provisioning success rate and duration. Runbooks: throttle a tenant, move a tenant to dedicated, suspend for non-payment (read-only mode), rotate a tenant's keys, respond to a suspected cross-tenant leak (containment, evidence, notification obligations).

1. Implement the tenant context middleware, RLS policies and a repository layer; write the cross-tenant test suite (tenant A against tenant B's IDs) and make it a CI gate.
2. Design the provisioning workflow as an idempotent state machine with compensation steps and failure handling for each stage.
