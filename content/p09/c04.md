# Caching Strategies

:::objectives
- Choose among cache-aside, read-through, write-through, write-behind and refresh-ahead for a given read/write profile.
- Design a cache hierarchy (browser, CDN, edge, application, database) and reason about coherence across layers.
- Decide what to cache, for how long, and how invalidation propagates, with staleness as an explicit requirement.
- Measure cache effectiveness and avoid the failure modes caches introduce.
:::

## Caching as a design decision

Part III chapter 8 covered the mechanics of an application cache; this chapter is about *strategy*: which pattern, at which layer, with what staleness contract. Every cache trades freshness and complexity for latency and load. The design question is never "should we cache?" but "which data, where, how stale may it be, and how do we know it is working?"

Cache-aside is the default; write-through where coherence matters more than write latency; precomputation for aggregates. Write-behind only for data whose loss is acceptable.

## The hierarchy

Requests can be answered at several layers, each closer to the user and cheaper, each with its own invalidation story:

1. **Browser cache**: `Cache-Control`, `ETag`; zero network cost. For assets and conditional API GETs.
2. **CDN / edge**: shared across users; for public, cacheable responses; keyed carefully (Part II chapter 17).
3. **Reverse proxy / API gateway cache**: for public API responses with `s-maxage`.
4. **Application cache (Redis)**: per-entity or per-query results scoped by tenant/user.
5. **In-process cache**: tiny, hot, harmless-if-stale data (config, flags).
6. **Database caches**: buffer pool, materialised views, query result caches.

Effective staleness is the sum along the path: a 60 s CDN TTL over a 300 s Redis TTL can serve data six minutes old. Design TTLs per layer with the end-to-end contract in mind, and make the shortest-TTL layer the one you can invalidate.

## What to cache

Good candidates: read-heavy, expensive to compute or fetch, tolerant of staleness, with a bounded key space: catalogue entities, configuration, computed aggregates, permission sets with short TTL, external API responses (rates, geocoding), rendered fragments. Poor candidates: data read once, data with strict freshness (balances at transaction time, inventory at checkout, authorization decisions beyond seconds), data whose key space is unbounded with low reuse (per-request computed results), very large objects (cache a pointer instead), and anything personal in a *shared* layer.

Decide and document per data class: **TTL**, **invalidation trigger**, **tolerated staleness**, **fallback when the cache is unavailable**.

## Coherence and invalidation across layers

Strategies from Part III chapter 8 and Part VIII chapter 11 apply per layer; across layers, propagate in order from origin outward: database commit → application cache delete (synchronous) → CDN purge or short TTL (asynchronous) → browser via ETag revalidation. Event-driven invalidation (outbox events consumed by cache maintainers and CDN purgers) scales to many consumers; versioned URLs (fingerprinted assets, versioned API resources) avoid invalidation entirely for immutable content; and for everything else, a TTL is the backstop that bounds how wrong you can be.

## Protecting the origin

Caches that fail together create thundering herds: a cache cluster restart, a deploy that changes key prefixes, synchronised TTL expiry, or a popular key expiring under load. Mitigations: jittered TTLs; single-flight/request coalescing per key; stale-while-revalidate; cache warming after deploys (replay hot keys); gradual key migration (dual-read old and new prefixes); origin rate limiting and load shedding so a cache failure degrades rather than destroys (chapter 9); and treating cache availability as part of the capacity plan (if the cache dies, can the origin serve the load for the minutes it takes to recover? If not, the cache is a hard dependency and must be highly available).

## Negative and partial caching

Cache "not found" briefly to stop repeated misses for missing items (and to blunt enumeration); cache partial results (a list of IDs, then entities) so the expensive part is reused while entities stay fresh; cache per-field (hash) when fields change at different rates.

## Measuring

Per key family: hit ratio, origin requests saved, latency with and without, memory consumed, eviction rate, staleness observed (sample and compare with the source). A cache is justified when it removes origin load or latency that matters; review quarterly and remove caches that do neither (every cache is also a correctness risk).

## Security

Shared layers must never hold personal responses; keys must include every dimension the data depends on (tenant, user, locale, role); encrypt sensitive values if the cache store is less protected than the database; respect data retention (cached PII is still PII, Part IV chapter 23); and never trust cache contents as authoritative for authorization decisions beyond a short TTL with invalidation on permission change.

## Common mistakes

- Caching first, measuring never.
- Personal data in a shared cache layer.
- TTLs chosen arbitrarily; staleness nobody agreed to.
- No invalidation path for an entity cache; stale forever until TTL.
- Cache as a hard dependency without HA; cache blip equals outage.
- Thundering herd after deploys or restarts.
- Caching mutable correctness-critical data (balances, inventory).
- Write-behind for data the business cannot lose.

2. Simulate a Redis restart under load and measure origin load and latency; add warming and coalescing; repeat.
