# Availability, Reliability and Scalability

:::objectives
- Define availability, reliability and scalability precisely and measure them.
- Identify single points of failure and the standard remedies at each layer.
- Understand redundancy, failover, degradation and the cost curve of each additional nine.
- Design a system to an availability target proportionate to the client's needs.
:::

:::prereq
Chapter 1; Part II chapter 13; Part VII chapters 1 and 11.
:::

## Definitions

- **Availability**: the fraction of time (or of requests) the system is usable. Measured as an SLI against an SLO (Part XI chapter 4): `successful requests / total requests` over a window, or uptime of a synthetic check.
- **Reliability**: the probability the system performs correctly for a period; includes correctness, not just being up. A system that answers quickly with wrong data is available and unreliable.
- **Scalability**: the ability to handle growth in load or data by adding resources, ideally proportionally and without redesign.
- **Resilience**: the ability to absorb failures and recover; the engineering that produces availability.
- **Durability**: the probability that stored data survives (Part VII chapter 10).

## Single points of failure

Draw the architecture and ask of each component: if this dies, what happens? Anything whose death takes the system down is a [[single point of failure|single point of failure]] (SPOF). Typical SPOFs and remedies:

| SPOF | Remedy | Cost |
|---|---|---|
| One application instance | Several instances across AZs behind a load balancer; autoscaling with min ≥ 2 | Instances ×2–3; stateless design required |
| One database instance | Multi-AZ standby with automatic failover; read replicas; backups and PITR | Roughly 2× database cost |
| One Availability Zone | Everything across ≥ 2 (ideally 3) AZs: subnets, ASG/ECS placement, RDS Multi-AZ, ElastiCache replicas, NAT per AZ | Cross-AZ transfer; NAT per AZ |
| One Region | Multi-Region DR (chapter 10) | Large; complexity |
| One NAT gateway | One per AZ | Hourly cost each |
| The load balancer | Managed ALB/NLB is multi-AZ by design | Included |
| DNS | Managed (Route 53 is 100% SLA); health-checked failover | Included |
| A cache node | Replication with automatic failover; application tolerates cache loss | Replica cost |
| A queue | Managed SQS is multi-AZ; self-managed brokers need clusters | Included / cluster cost |
| An external API | Timeouts, retries, circuit breakers, fallbacks, queues; contractual SLAs | Engineering |
| A certificate | Automated renewal and monitoring (Part II chapter 10) | Nearly free |
| A person | Runbooks, shared on-call, documentation, handover (Part XIII) | Discipline |
| A deploy pipeline | Not an availability SPOF, but a recovery one: can you deploy a fix when CI is down? Keep a documented manual path | Documentation |

Hidden SPOFs: a single secret rotation Lambda, a cron job on one instance, a shared service account, a single DNS registrar login, a certificate on an internal service nobody listed.

## Redundancy and failover

Redundancy means more than one of something; failover means the system switches to the redundant one when the primary fails. Three qualities matter: **detection** time (health checks every 10 s with 2 failures: ~20 s), **switch** time (ALB target removal: seconds; RDS Multi-AZ failover: 60–120 s; DNS failover: TTL-bound), and **state** (stateless components fail over trivially; databases need replication; sessions need a shared store). Active-active (all replicas serve) beats active-passive (standby idle) for utilisation and tested readiness, where the data model allows.

Test failover regularly: terminate an instance, force an RDS failover, kill a cache node, block an AZ's subnets in staging (Part XI chapter 9). An untested failover is a hypothesis with the same credibility as an untested backup.

## Graceful degradation

Full availability of every feature is not the only option. Design so that when a dependency fails, the system sheds the affected feature rather than everything: recommendations disappear but checkout works; search falls back to the database; reports queue for later; the cache is bypassed with higher latency. Requires: timeouts and circuit breakers (chapter 8), feature flags as kill switches (Part X chapter 7), a clear priority of features, and UI that handles absence. Partial availability is often what the SLO actually needs.

Most client systems belong at 99.5–99.9%. Promising 99.99% to a client with a two-person team is a promise you will break; the honest conversation is "here is what each level costs in infrastructure and in people, and here is what your business actually loses per hour of downtime."

## Scalability

Vertical (bigger machine) and horizontal (more machines) scaling (Part I chapter 14, Part VIII chapter 12). Horizontal scaling requires statelessness (chapter 3), load distribution (Part II chapter 13), and data tier strategies (Part VIII chapters 8, 11, 12). Scalability has dimensions: request throughput, data volume, number of tenants, geographic spread, team size; a system scalable in one is not automatically scalable in another. Measure the **scaling factor**: adding a second instance should roughly double capacity; if it adds 20%, a shared bottleneck (database, lock, cache node) is the real limit. Autoscaling (Part VII chapters 7–8) handles variation; capacity planning (Part XI chapter 8) handles growth.

## Shared fate and blast radius

Components that fail together share fate: everything in one AZ, every service on one database, every tenant in one deployment. Reducing [[blast radius]]: AZ isolation, bulkheads per tenant or workload (chapter 8), cell-based architectures (independent stacks each serving a subset of tenants, with a thin routing layer), separate accounts per environment (Part VII chapter 2), and staged rollouts (Part X chapter 7). The question for every design review: what is the largest thing one failure can take out?

## Reliability beyond uptime

Correctness under concurrency (Part VIII chapter 5), idempotency under retries (Part III chapter 3), data integrity (constraints, Part VIII chapter 3), and recoverability (backups, Part V chapter 11) are reliability. A system can meet its uptime SLO while silently corrupting data; include correctness SLIs (reconciliation checks, data validation jobs) in the definition of reliable.

## Common mistakes

- Multi-AZ application tier with a single-AZ database.
- Redundant instances all in one AZ or one subnet.
- "Highly available" claimed with no failover test ever run.
- SLOs promised without measurement or arithmetic.
- Over-building for availability the business does not need, consuming budget that should have bought observability and backups.
- Ignoring human SPOFs: one engineer who knows how it works.
- Treating availability as uptime while ignoring correctness.

## Exercises

1. Draw your system and mark every SPOF, including human and procedural ones; for each, write the remedy and its monthly cost.
2. Run a failover test in staging for each stateful component (database, cache, queue) and record detection and recovery times.
3. Write the availability proposal for a client: three tiers with architecture, cost and operational requirements, and your recommendation with the business reasoning.
