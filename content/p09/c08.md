## The problem

Every outbound call (database, cache, another service, a third-party API) can fail, hang or slow down. Without discipline, one slow dependency consumes all your threads or connections, your service slows, its callers retry, the dependency receives more load, and a small fault becomes a full outage: a **cascading failure**. The patterns here are the engineering of containment, and they are mostly configuration once you know what to set.

## Timeouts

A call without a timeout is a promise to wait forever. Every call gets: a **connect timeout** (short, 1–3 s: a dropped SYN should fail fast), a **read/response timeout** (per call, based on the dependency's p99 plus margin), and ideally a **total deadline** propagated across hops (the caller's remaining budget, so a downstream service does not keep working on a request the user has already given up on). Set them lower than the caller's own timeout so failures surface where they can be handled. Timeouts are errors (Part III chapter 12): log them, count them, and treat them as retryable only if the operation is idempotent.

```python
import httpx
client = httpx.AsyncClient(timeout=httpx.Timeout(connect=2.0, read=5.0, write=5.0, pool=1.0), limits=httpx.Limits(max_connections=50, max_keepalive_connections=20))
```

## Retries with backoff and jitter

Retries hide transient failures (a dropped packet, a restarting instance) and amplify sustained ones (a saturated dependency receives N× the load). Rules:

- Retry **only idempotent** operations or those protected by idempotency keys (Part III chapter 3).
- Retry **only retryable errors**: timeouts, connection errors, 429, 502/503/504; never 400/401/403/404/422.
- **Bound** attempts (2–3 for interactive paths; more for background jobs) and total time.
- **Exponential backoff with full jitter**: `sleep = random(0, min(cap, base × 2^attempt))`. Jitter prevents synchronised retry waves from many clients.
- Honour `Retry-After`.
- Make retries **visible**: a metric per dependency; a spike in retries is an early warning.
- Avoid **retry amplification** across layers: if the client, the gateway and the service each retry 3 times, the dependency sees 27 attempts. Retry at one layer (usually the outermost that can judge idempotency), or budget retries as a fraction of traffic (e.g., at most 10% extra load).

```python
import random, asyncio
async def with_retries(fn, attempts=3, base=0.2, cap=3.0, retry_on=(TimeoutError, ConnectionError, RetryableHTTP)):
    for i in range(attempts):
        try:
            return await fn()
        except retry_on as e:
            if i == attempts - 1: raise
            delay = random.uniform(0, min(cap, base * (2 ** i)))
            metrics.increment("retry", tags={"dep": fn.__name__})
            await asyncio.sleep(delay)
```

## Circuit breakers

When a dependency is failing, continuing to call it wastes resources (threads blocked on timeouts) and makes its recovery harder. A [[circuit breaker]] tracks failures per dependency; after a threshold (e.g., 50% failures over 20 calls) it **opens**: calls fail immediately without touching the dependency for a cooling period (30 s); then **half-open**: a few trial calls go through; success closes it, failure re-opens. Combine with a **fallback**: cached data, a default, a degraded response, or a queued deferral (chapter 9).

Breakers belong around every external dependency and non-critical internal one; they are the mechanism behind graceful degradation (chapter 2). Libraries: `pybreaker`/`aiobreaker`, Resilience4j (JVM), Polly (.NET), `opossum` (Node); service meshes and Envoy implement outlier detection and circuit breaking per upstream; API gateways can too.

## Bulkheads

Named after ship compartments: isolate resources so one failing dependency or one noisy tenant cannot exhaust everything. Separate connection pools and thread pools per dependency (a slow payment API cannot consume the connections needed for the database); per-tenant concurrency limits (semaphores) on expensive operations; separate worker pools or queues per job type (Part III chapter 6); separate instances or cells for critical versus bulk traffic. The cost is some idle capacity in each compartment; the benefit is that the blast radius of any single failure is one compartment.

```python
# Per-dependency bulkheads: bounded concurrency
payment_sem = asyncio.Semaphore(10)
async def charge(order):
    async with asyncio.timeout(5):
        async with payment_sem:               # at most 10 in-flight payment calls per instance
            return await breaker_payment.call(lambda: payments_client.charge(order))
```

## Idempotency as a resilience pattern

Retries, redeliveries and failovers all produce duplicates. Idempotent operations make all of them safe (Part III chapter 3). Every pattern above assumes it; without it, retries are dangerous and circuit breakers' fallbacks may double-apply effects.

## Distributed locks and leases

For **efficiency** (avoid two workers doing the same expensive work) a lock in Redis or a database lease is fine, provided the work is idempotent and the lock has a TTL and token-checked release (Part VIII chapter 11; chapter 6). For **correctness** (ensure at most one of something), rely on the database (unique constraints, conditional updates, row locks) or on fencing tokens, because distributed locks can be held by two parties after pauses and failovers. State explicitly which kind each lock is.

## Load shedding and admission control

When overloaded, serving everyone badly is worse than serving most well. Shed early: reject (503 with `Retry-After`) when queue depth or in-flight count exceeds capacity, prioritise critical endpoints and paying tenants, drop low-value work first (analytics events before orders), and apply backpressure to upstream producers. Adaptive concurrency limits (based on observed latency, as in Netflix's `concurrency-limits`) adjust automatically. Chapter 9 covers this with rate limiting.

## Metastable failures and the role of these patterns

A system can enter a state where load from retries and recovery work keeps it saturated even after the original trigger disappears (a **metastable failure**): caches empty, everything misses, database overloaded, timeouts, retries, more load. Breaking the loop requires shedding load, pausing retries, warming caches, or scaling. Prevent it by: bounded retries with jitter, circuit breakers that stop hammering, load shedding at the entry, cache warming on restart, and capacity headroom. Recognise it in incident reviews: "the trigger ended at 14:05 but we stayed down until 14:40 because retries kept the database pinned."

## Configuration, consistently

Resilience settings scattered across code drift. Centralise: a client factory per dependency that sets timeouts, retries, breaker and bulkhead from configuration; a service mesh or gateway enforcing timeouts, retries and outlier detection at the network layer for service-to-service calls; documented values per dependency (its p99, your timeout, retry policy, breaker thresholds, fallback). Review them when dependencies change.

## Testing resilience

Fault injection in staging: add latency and errors to a dependency (toxiproxy, AWS Fault Injection Service, mesh fault injection) and verify timeouts fire, breakers open, fallbacks serve, and the service stays within its SLO. Unit tests for retry classification (never retry 400). Game days that pull a dependency entirely (Part XI chapter 9).

## Common mistakes

- No timeouts; threads consumed by a dead dependency.
- Retrying everything, including non-idempotent POSTs and 4xx errors.
- Retries without jitter; synchronised storms.
- Retry at every layer; 27× amplification.
- Circuit breakers without fallbacks; or breakers on the database (where a tripped breaker *is* the outage; use timeouts, pools and shedding instead).
- One shared pool for every dependency; one slow API starves the database connections.
- Redis locks guarding money.
- Resilience "handled by the mesh" that nobody configured.
