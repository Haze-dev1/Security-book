# Case Study: URL Shortener

:::objectives
- Design a complete small system end to end: requirements, estimates, data model, ID generation, redirect path, analytics, abuse controls, operations.
- Practise the design method on a problem simple enough to see every trade-off clearly.
:::

:::prereq
Chapters 1–10 of this part; Part III chapters 2, 3 and 8.
:::

## Requirements

**Functional**: create a short link for a URL (optionally custom alias, expiry); redirect `GET /{code}` to the target; basic click analytics per link (count, timestamps, referrer, coarse geography); links owned by tenants/users with management UI and API.

**Non-functional**: redirects p99 < 50 ms at the edge, available at 99.95% (redirects are the product; management can be 99.9%); 10 million redirects/day peak 500 rps (bursty: viral links), 50,000 creations/day; links live up to 5 years; analytics may lag by minutes; abuse (phishing, malware) must be detectable and blockable; GDPR for click data (IPs are personal data).

**Estimates**: 50,000 creations/day ≈ 18M links/year; at ~500 bytes per link row ≈ 9 GB/year: tiny. Redirects 10M/day ≈ 115 rps average, 500 peak, with viral spikes to thousands for one code: read-heavy, hot-key prone. Click events 10M/day × 200 B ≈ 2 GB/day: the real volume, and it is append-only analytics data.

## Key decisions

**Code generation**: options are a counter encoded in base62 (short, sequential: enumerable, reveals volume), a random base62 string of 7+ characters (62⁷ ≈ 3.5 trillion: collisions negligible, check on insert and retry), or a hash of the URL (same URL → same code; privacy and custom-alias conflicts). Choose random 7-character codes with a unique constraint and retry on collision; custom aliases are validated (allowed characters, reserved words, length) and must be unique per domain. Codes are case-sensitive; document it.

**Redirect status**: 301 is cached permanently by browsers (fewer hits, but analytics lose repeat clicks and you cannot change the target); 302/307 re-request each time (accurate analytics, changeable targets, more load). Default 302; offer 301 for permanent links.

**Hot path**: CloudFront in front caches responses per code briefly, so a viral code is served from the edge; the service uses Redis cache-aside with a TTL and negative caching; the database is read only on misses. Analytics never block the redirect: publish-and-forget to a queue with a tiny timeout; if the queue is unavailable, drop the event and count the drop (redirect availability beats analytics completeness).

**Data model**: `links(code PK, target text, owner_id, tenant_id, created_at, expires_at, kind {temporary, permanent}, status {active, disabled, flagged}, custom bool)` with indexes on `(tenant_id, created_at)` and `(owner_id)`; `click_counts(code, day, count)` maintained by the consumer; raw clicks in S3 as Parquet partitioned by date.

**Analytics privacy**: store IP truncated (/24 for IPv4, /48 for IPv6) or hashed with a rotating salt; derive coarse geography at ingestion and discard the IP; retention 13 months; expose only aggregates to link owners. Document in the privacy notice.

**Abuse**: check targets against Google Safe Browsing (or equivalent) at creation and on a recurring schedule; rate-limit creation per user and per IP; require accounts for API creation; a reporting endpoint; flagged links show an interstitial warning instead of redirecting; take-down tooling for operators; audit log of moderation actions. Shorteners are abuse magnets; this is not optional.

**Expiry**: `expires_at` checked on redirect (cheap) and a daily job disables expired links and evicts cache keys; expired codes return 410.

## Bottlenecks and failure modes

- **Hot code**: one code receives 5,000 rps. Edge caching absorbs almost all; Redis handles the remainder; without CloudFront, a single Redis key could become hot (fine at this scale; replicate into process memory with a 1 s TTL if needed).
- **Redis down**: every redirect hits the database; at 500 rps PostgreSQL copes, so the cache is a soft dependency; short timeouts and fallthrough.
- **Database down**: redirects fail except edge-cached ones; management down. Multi-AZ RDS; consider a read replica and a last-known-good local cache for the hottest codes.
- **Queue down**: drop events, count drops, alert; redirects unaffected.
- **Enumeration**: attackers probe random codes to find private links; 7-character random space makes this impractical; negative caching and rate limiting blunt it; private links can additionally require a token.
- **Cache invalidation**: changing a target or disabling a link must evict Redis and (short) CloudFront TTL keeps edge staleness under a minute; for take-downs of malicious links, issue a CloudFront invalidation.

## Security

Open redirects are the product, so: validate target URLs (http/https only; no `javascript:`; resolve and block private IP ranges to avoid the shortener being used for SSRF against internal endpoints, Part IV chapter 12); interstitials for flagged links; authentication and per-tenant authorisation on management; audit logs; rate limits; secrets in a secrets manager; TLS everywhere; HSTS; CSP on management UI; the redirect domain separate from the management domain (cookies not sent to redirect domain).

## Operations

Metrics: redirect p99, cache hit ratio (edge and Redis), 404/410 rates, creation rate, flagged link count, queue age, drop count. Alarms: redirect 5xx rate, p99 > 50 ms at origin, Redis unavailable, queue age > 5 min, Safe Browsing API failures. Cost: dominated by CloudFront requests and Fargate tasks; tiny database; S3 storage for clicks. Runbooks: take down a link, rotate the salt, restore from PITR, scale for a viral event.

## What changes at 100× scale

Edge-serving of redirects from a KV store at the edge (CloudFront KeyValueStore or Cloudflare Workers KV), DynamoDB for the link table (key-based, global tables for multi-Region), Kinesis for clicks, pre-aggregation in stream processing. The design above already has the seams for each.
