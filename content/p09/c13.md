# Case Study: E-commerce Backend

:::objectives
- Design the backend for an online store: catalogue, cart, checkout, orders, payments, inventory and fulfilment.
- Handle the hard parts: inventory consistency under concurrent purchases, payment idempotency, flash-sale traffic and exactly-once-looking order creation.
- Apply the consistency, messaging and resilience patterns from this part to a domain where mistakes cost money.
:::

:::prereq
Chapters 1–10 of this part; [Transactions, ACID, Isolation Levels and Locks](#/p08/c05); [Message Brokers](#/p09/c07).
:::

## Requirements

**Functional**: browse and search a catalogue (500,000 SKUs); product pages with price, stock, images, reviews; cart (anonymous and logged-in, merged on login); checkout with address, shipping options, promotions and tax; payment via a provider (card, wallets); order lifecycle (placed, paid, packed, shipped, delivered, cancelled, refunded); inventory across warehouses; notifications; back office for merchandising and customer service.

**Non-functional**: 99.95% for browse and checkout (a 10-minute checkout outage at peak is lost revenue and public complaints); product page p95 < 300 ms; checkout p95 < 1.5 s excluding the payment provider; 2 million daily visitors, 50,000 daily orders, peak 20× average during sales (flash sales reach 5,000 requests/s on a few hot SKUs); never oversell beyond a defined tolerance; never charge twice; PCI scope minimised (card data never touches your servers); auditability of every price, stock and money change.

## Capacity sketch

| Quantity | Estimate | Implication |
|---|---|---|
| Page views | 2M visitors × 8 pages = 16M/day ≈ 185/s avg, ~2,000/s peak | Browse must be served mostly from caches and a CDN |
| Orders | 50,000/day ≈ 0.6/s avg, ~15/s peak, 200/s in a flash sale | Order writes are small; the contention is on hot SKUs, not volume |
| Catalogue | 500k SKUs × ~5 KB = 2.5 GB | Fits in a search index and a cache comfortably |
| Images | 500k × 6 × 300 KB ≈ 900 GB | S3 + CDN, resized variants generated once |
| Orders stored | 50k/day × 5 KB × 7 years ≈ 640 GB | Partition by month; archive cold months |

## Key decisions

**Inventory consistency**: the stock row is the serialisation point. Use a single atomic conditional update rather than read-then-write; use reservations with expiry so abandoned checkouts release stock; tolerate a small, configured oversell for marketplace-style catalogues where suppliers can backfill, but never for limited editions. For flash sales on a few SKUs, the row becomes a hotspot: pre-allocate a fixed number of "purchase tokens" into Redis at sale start and admit only token holders to checkout, turning a thundering herd at the database into a cheap Redis decrement and a polite "sold out" for everyone else.

**Money**: integers in minor units; every change to an order's financial state is an append-only ledger entry, not an update; payment state machine with explicit allowed transitions; reconciliation job comparing the provider's settlement report to the ledger daily; refunds through the same idempotent path.

**Idempotency**: client-generated keys on order creation; order-derived keys to the provider; event IDs for consumers; webhook deduplication by provider event ID. Store processed keys with TTLs matching retry windows (24 h for orders, forever for payments).

**Read path**: product pages assembled from a cached read model; stock shown as "in stock / low / out" rather than exact counts so the cache can be a little stale; price and stock fragments carry short TTLs and are invalidated by StockChanged and PriceChanged events; search index updated from events within seconds.

**Promotions and pricing**: rules evaluated server-side with a snapshot stored on the order (what price, which promotion, why) so disputes can be answered months later; coupon redemption counted atomically (same pattern as stock).

**Data ownership**: one PostgreSQL cluster with clear schema ownership per service at this scale (Part VIII chapter 12 argued against premature database-per-service); carts in Redis because they are high-churn and low-value; the search index and caches are derived and rebuildable.

## Bottlenecks and failure modes

- **Hot SKU at sale start**: thousands of transactions contend on one row; lock waits balloon; the whole database slows. Mitigation: Redis admission tokens, per-SKU queueing, or sharding stock into buckets that are summed lazily.
- **Payment provider slow or down**: checkout waits. Set timeouts (10 s), create the order as pending, and let the webhook complete it; show "we are confirming your payment" rather than failing; circuit-break and show a maintenance message if the provider is down for minutes; never retry a charge without the idempotency key.
- **Webhook ordering**: `succeeded` may arrive before `created`, or twice. Make handlers transition-aware and idempotent; fetch the current state from the provider when in doubt.
- **Cache stampede on a popular product**: use request coalescing and stale-while-revalidate (chapter 4).
- **Reservation leaks**: a crash between reservation and order insert leaves stock reserved. Reservations expire; a sweeper releases expired ones; the order insert and reservation can also live in the same transaction if both are in the same database.
- **Search index lag**: a new product appears in the catalogue before it is searchable; acceptable and documented, with a reindex job for drift.
- **Reporting queries** on the primary during peak: route to a replica or warehouse; forbid ad hoc queries on the primary.

## Security considerations

Price and quantity manipulation (recompute server-side; validate quantities and SKUs); coupon abuse (rate limit, single-use enforcement, bind to account); account takeover for stored payment methods (MFA, re-authentication before using a saved method or changing address); PCI scope kept to SAQ A/A-EP by using hosted fields; webhook signature verification and replay windows; IDOR on orders (`/orders/{id}` must check ownership, Part IV chapter 7); scraping and scalper bots (WAF bot control, proof-of-work or CAPTCHA at sale time); admin back office behind SSO with audit; PII minimisation and retention for addresses and emails; fraud screening hooks before capture.

## Operations

SLIs: checkout conversion funnel per step, order creation success rate, payment success rate by provider and method, p95 latencies, oversell count (should be zero), reservation leak count, webhook lag, search index lag. Alarms on payment failure spikes (provider incident or fraud wave), on oversells, on queue backlogs in fulfilment. Runbooks: provider outage, flash-sale preparation (pre-scale, token allocation, cache warm), stuck orders reconciliation. Load test the hot-SKU path before every big sale.
