# Case Study: Production Application for a Small Client

:::objectives
- Design and run a production deployment for a small organisation with a limited budget, no operations team and a real need for reliability and security.
- Practise the most common Forward Deployed Engineer judgement: delivering a boring, robust, well-documented system rather than an impressive one.
- Learn what "production-ready" means when the whole system costs less than a day of an engineer's time per month.
:::

:::prereq
Part V (Linux), Part VI chapters 1–6 (Docker), Part VII (AWS), chapters 1–10 of this part.
:::

## The brief

A regional professional-services firm (120 staff) needs a client portal: clients log in, view documents and invoices, upload files, exchange messages with their account manager, and e-sign agreements. Staff manage clients and content through an admin area. Integrations: the firm's accounting system (invoices via API) and email. Constraints: budget of roughly 300–500 USD per month for infrastructure; the firm has one IT generalist who manages laptops and Microsoft 365, no engineers; data includes financial and personal information, so the firm's clients expect confidentiality; availability during business hours matters, nights and weekends far less; the system must still be running and patched in three years with no one from your team around.

## Requirements, translated

| Stated need | Engineering requirement |
|---|---|
| "It must be secure" | HTTPS everywhere, SSO via the firm's Microsoft 365 for staff, MFA for clients, encrypted storage, audit log, dependency updates, backups tested |
| "It must not go down" | 99.5% during business hours is the realistic, affordable target; recovery within 2 hours; nightly maintenance window allowed |
| "Fast" | p95 < 500 ms for pages at 50 concurrent users; the load is tiny |
| "We cannot run servers" | Managed services wherever they cost less than the ops they save; everything scripted; a runbook the IT generalist can follow; a support agreement for the rest |
| "Keep costs down" | One Region, one environment per stage, serverless or small instances, right-sized database, budgets and alarms |
| "Our data stays with us" | The client's own AWS account, your access via a role they can revoke, documented data map, retention policy |

## Key decisions and the reasoning a client can follow

**Containers on Fargate, not EC2 and not Kubernetes**: no servers to patch, two tasks for resilience, rolling deploys with health checks. Kubernetes would add a control plane fee larger than the whole compute bill and an operational skill requirement the client does not have (Part VI chapter 14). A single EC2 instance would be cheaper but someone must patch it and it is a single point of failure; the Fargate premium buys away a class of operational work.

**Multi-AZ RDS even though it doubles the database cost**: the client cannot perform a manual failover or restore at 02:00; Multi-AZ gives automatic failover and zero-downtime patching. The 35 USD per month is the cheapest insurance in the design.

**No microservices, one repository, one container**: the application is small; a monolith with clear modules deploys in one step and is debuggable by one person. Background jobs (invoice sync, email digests) run as scheduled tasks from the same image with a different command.

**Identity**: staff via the firm's existing Microsoft Entra tenant (OIDC), so joiners and leavers are handled by the IT generalist in a system they already use; clients via a managed identity provider (Cognito or similar) with passkeys and TOTP so that password storage, MFA and recovery are not your code to maintain. Clear role model: staff roles from Entra groups; clients scoped to their own organisation's records with resource-level checks and RLS.

**Document handling** follows the file-upload case study in miniature: presigned uploads to a private bucket, type validation and malware scanning via a small Lambda, downloads via short-lived presigned URLs, separate CloudFront domain for files.

**Infrastructure as code from day one**: Terraform in the client's repository, state in their S3 with locking; a GitHub Actions pipeline deploying via an OIDC-assumed role; no long-lived AWS keys anywhere. Everything the client owns, in their account, with your access through a role they can revoke on the last day.

**Backups and recovery**: RDS PITR plus a nightly logical dump to the locked backup prefix; S3 versioning; a quarterly restore drill scripted as a single command that restores to a temporary environment and runs smoke tests; recovery procedure in the runbook with screenshots.

**Observability sized for one person**: a single dashboard (requests, errors, latency, DB CPU and connections, task count, queue of failed jobs), five alarms that page (site down, 5xx rate, DB failover, disk/storage thresholds, budget), structured logs with a 90-day retention, and a weekly automated email summary so someone looks at the system even when nothing is wrong.

**Patching and dependency updates**: Dependabot or Renovate opening pull requests; CI running tests and container scanning; a monthly "maintenance" calendar entry for the support engineer to merge and deploy; base image rebuilt monthly by a scheduled workflow even with no code changes.

## Handover deliverables

Architecture document with the diagram above and the trade-off table; runbook (deploy, roll back, restore, rotate secrets, grant support access, respond to the five alarms) written for the IT generalist; access and credentials inventory with owners; data map and retention policy; cost report and budget alarms; security summary (controls, last scan dates, open risks accepted by the client in writing); maintenance calendar; support agreement with response times. ## Exercises

1. Write the full Terraform for this architecture (VPC, ECS service, RDS Multi-AZ, S3, CloudFront, alarms, budget) and deploy it to a sandbox; record the actual monthly cost after a week.
2. Write the runbook for the five paging alarms so that a non-engineer can perform the first response and know when to escalate.
3. Run the restore drill: restore RDS to a point in time in a temporary environment, run smoke tests, destroy it, and document the elapsed time.
