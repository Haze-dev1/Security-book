# Stateless versus Stateful Services and Load Distribution

:::objectives
- Make services stateless so any instance can serve any request, and know where each kind of state must live instead.
- Handle the unavoidable stateful components (databases, caches, brokers, connection-heavy services) with the patterns that keep them available.
- Distribute load fairly across heterogeneous instances and long-lived connections.
- Recognise hidden state that breaks horizontal scaling and deployments.
:::

:::prereq
Part III chapter 1; Part II chapters 11, 13 and 14.
:::

## Why statelessness

A **stateless service** keeps nothing between requests that another instance would need. Consequences: any instance handles any request (load balancing is trivial); instances can be added, removed or replaced at will (autoscaling, rolling deploys, self-healing); a crashed instance loses nothing; and tests are simpler. Almost every architectural property in this part (availability, scalability, easy deployment) depends on it. State does not disappear; it moves to components designed to hold it.

## Where state goes

| State | Lives in | Why there |
|---|---|---|
| Session / login | Redis (shared, TTL) or signed token | Any instance can validate (Part IV chapters 4–5) |
| User data | Database | Durable, transactional |
| Files | Object storage | Durable, served directly |
| In-flight work | Queue | Survives instance loss; redistributable |
| Cache | Redis, or in-process if loss is harmless | Shared or disposable |
| Locks / coordination | Database row locks, Redis (advisory), or a coordination service | Visible to all instances |
| Rate limit counters | Redis | Atomic, shared |
| Configuration | Environment / parameter store; flags service | Same for all instances |
| WebSocket connections | A connection tier with a backplane | Unavoidably stateful; isolated (Part III chapter 11) |
| Scheduled job ownership | A leader lease (database or Redis) or a scheduler service | Exactly one runner |
| Metrics / logs | Shipped off-instance | Instance loss loses nothing |

## Hidden state that breaks scaling

The instance that "works fine until we added a second one":

- **Local disk**: uploads written to `/var/app/uploads`, PDFs generated to `/tmp` and served later, SQLite files. Second instance cannot see them. Move to S3 or a shared store.
- **In-memory sessions or caches used as truth**: logins "lost" when the load balancer sends the next request elsewhere; stale permission caches per instance. Shared store, or accept per-instance caches only for harmless data.
- **In-process schedulers** (`setInterval`, APScheduler) running on every instance: jobs run N times. Externalise scheduling or elect a leader.
- **Sticky sessions** as a design: uneven load, lost sessions on deploy (Part II chapter 13).
- **Instance-specific configuration** edited by hand; drift.
- **Sequence generation in memory** (counters, IDs): duplicates across instances. Use database sequences or UUIDs.
- **Long-lived connections pinned to instances** (WebSockets, HTTP/2 from a few heavy clients): load concentrates; deploys disconnect everyone.
- **Local queues** (`asyncio.create_task` fire-and-forget, in-memory job lists): lost on restart.

Detect by asking of every write: where does this go, and can the next request from the same user land on a different instance?

## Stateful components, handled

Some components must hold state; the patterns:

- **Databases**: replication and failover (Part VIII chapter 8); connections pooled and bounded (Part VIII chapter 6); the application treats the endpoint as potentially changing.
- **Caches**: replicated with failover; the application survives cache loss (Part III chapter 8).
- **Brokers**: managed (SQS) or clustered; consumers idempotent (Part III chapter 7).
- **Connection servers**: a dedicated tier scaled on connection count with a backplane; graceful drain on deploy (Part III chapter 11).
- **Leader-based singletons** (a scheduler, a reconciliation loop): leader election via a lease (`SELECT … FOR UPDATE SKIP LOCKED` on a leases row, Redis `SET NX PX` with renewal, or Kubernetes Lease objects); the leader renews; others wait; failover on lease expiry (chapter 6).
- **StatefulSets / stateful instances**: stable identities and storage where the software requires it (self-managed brokers, search clusters); prefer managed services.

## Load distribution

Beyond the basics (Part II chapter 13): **least outstanding requests** or least connections to handle heterogeneous request costs; **weighted** targets for mixed instance sizes or canaries; **consistent hashing** when requests for the same key should hit the same instance (cache locality, in-memory aggregation) while tolerating instance changes (only ~1/N keys move when an instance joins or leaves); **client-side load balancing** (gRPC, service meshes) when a client holds many backends' addresses; **connection-level rebalancing** for long-lived connections (periodic reconnect, `GOAWAY` frames in HTTP/2, max connection age in gRPC) so that a scale-out actually receives traffic.

Fairness across tenants or clients: per-tenant concurrency limits and queues (bulkheads, chapter 8) so a heavy tenant does not consume every instance's capacity; priority lanes for latency-sensitive traffic; load shedding when saturated (chapter 9).

## Deployments and state

Rolling deploys assume statelessness: a draining instance finishes in-flight requests and loses nothing else (Part I chapter 6). For services with long-lived connections or in-progress jobs: drain gradually, signal clients to reconnect, checkpoint jobs, and size `terminationGracePeriod`/`stopTimeout` accordingly (Part VI chapter 11; Part III chapter 6).

## Common mistakes

- Files on local disk; fine with one instance, broken with two.
- Sticky sessions instead of a session store.
- Schedulers in the API process.
- Per-instance caches holding permissions; revocation ignored on some instances.
- Autoscaling added to a service that quietly depended on being alone.
- Long-lived connections never rebalanced; new instances idle.
- Leader election "by hoping only one instance runs the cron".

## Exercises

1. Audit a service for hidden state: every write to disk, memory or process-local structures; classify each as harmless, needs a shared store, or needs a singleton with election.
2. Implement leader election with a database lease for a scheduler; run three instances; kill the leader and measure the takeover time.
3. Load test a gRPC or WebSocket service, scale out mid-test, and observe traffic distribution before and after adding connection rebalancing.
