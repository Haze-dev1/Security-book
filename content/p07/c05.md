## The problem

The VPC is the network your whole AWS system lives in, and it is almost impossible to change later without downtime: CIDRs are fixed at creation (secondary CIDRs can be added, with constraints), subnets cannot be resized, and everything references them. Getting it right the first time (address plan, tiering, routing, egress) is one of the few infrastructure decisions that deserves slow, careful work before anything else is built.

## How traffic flows

**Inbound to the ALB**: Internet → IGW (maps the ALB node's public IP to its private IP) → public subnet → ALB node (security group check) → ALB opens a new connection to a target IP in a private subnet → local route → target ENI (its security group check). The target never has a public IP and never sees the Internet directly.

**Outbound from an app task**: task in private subnet connects to `api.stripe.com` → route table: `0.0.0.0/0 → nat-<this AZ>` → NAT gateway rewrites source to its EIP → IGW → Internet. Replies traverse back through the NAT's connection table. If the destination is S3 and a gateway endpoint exists, the more specific prefix-list route wins and traffic never touches the NAT.

**App to database**: task → `10.20.128.10:5432` → local route → RDS ENI; the database's security group must allow 5432 from the task's security group; the data subnet's route table is irrelevant for this (local). Nothing in the data subnet can initiate outbound to the Internet because no route exists.

**Lambda in a VPC**: Lambda attaches ENIs (Hyperplane) in your private subnets; functions then follow the same routes (and need NAT or endpoints to reach AWS services; Lambda functions *outside* a VPC have Internet access by default but cannot reach your private resources).

## Route tables in detail

| Table | Associated subnets | Routes |
|---|---|---|
| `public` | public-a/b/c | `10.20.0.0/16 local`; `0.0.0.0/0 → igw-…`; `::/0 → igw-…` (if dual-stack) |
| `private-a` | app-a | `local`; `0.0.0.0/0 → nat-a`; `pl-s3 → vpce-s3`; `pl-dynamodb → vpce-ddb`; (`::/0 → eigw-…` for IPv6 egress-only) |
| `private-b`, `private-c` | app-b, app-c | same, pointing at their AZ's NAT |
| `isolated` | data-a/b/c | `local`; optionally `pl-s3 → vpce-s3` for direct backups |

Per-AZ private route tables are what let each AZ use its own NAT gateway; a single shared private table would send all egress through one NAT (cross-AZ charges and a single point of failure).

## IPv6

Dual-stack VPCs assign a /56 and each subnet a /64; instances get globally routable IPv6 addresses (no NAT needed). An **egress-only Internet Gateway** gives private subnets outbound IPv6 without inbound. Benefits: no NAT costs for IPv6 traffic, no IPv4 address charges, future-proofing. Costs: every security group and NACL needs IPv6 rules too; some AWS services and many third parties remain IPv4-only, so NAT stays for them. Enable dual-stack on new VPCs and ALBs; it is much harder to add later.

## Building it

Use a maintained module rather than hand-writing fifty resources: the `terraform-aws-modules/vpc/aws` module (or the CDK `Vpc` construct, or CloudFormation's quick-start) handles subnets, route tables, NAT per AZ, endpoints, flow logs and tags from a short definition:

```hcl
module "vpc" {
  source  = "terraform-aws-modules/vpc/aws"
  version = "5.13.0"

  name = "client-a-prod"
  cidr = "10.20.0.0/16"
  azs  = ["eu-west-1a", "eu-west-1b", "eu-west-1c"]

  public_subnets   = ["10.20.0.0/20", "10.20.16.0/20", "10.20.32.0/20"]
  private_subnets  = ["10.20.64.0/20", "10.20.80.0/20", "10.20.96.0/20"]
  database_subnets = ["10.20.128.0/24", "10.20.129.0/24", "10.20.130.0/24"]
  create_database_subnet_route_table = true     # isolated: no NAT route

  enable_nat_gateway     = true
  one_nat_gateway_per_az = true                 # prod; set single_nat_gateway = true for non-prod
  enable_dns_hostnames   = true
  enable_dns_support     = true
  enable_ipv6            = true
  public_subnet_assign_ipv6_address_on_creation = false

  enable_flow_log                      = true
  create_flow_log_cloudwatch_iam_role  = true
  create_flow_log_cloudwatch_log_group = true
  flow_log_max_aggregation_interval    = 60

  tags = { Environment = "prod", Project = "client-a", ManagedBy = "terraform" }
}

resource "aws_vpc_endpoint" "s3" {
  vpc_id            = module.vpc.vpc_id
  service_name      = "com.amazonaws.eu-west-1.s3"
  vpc_endpoint_type = "Gateway"
  route_table_ids   = concat(module.vpc.private_route_table_ids, module.vpc.database_route_table_ids)
}
```

Verification after apply: `aws ec2 describe-route-tables --filters Name=vpc-id,Values=<id>` shows the expected routes per subnet; launch a test instance in a private subnet and confirm it can `curl https://checkip.amazonaws.com` (returning the NAT EIP) and that nothing can reach it inbound; from a data subnet, confirm the same curl *fails* (no route); Reachability Analyzer from the ALB's ENI to a target.

## Flow logs

VPC Flow Logs record accepted and rejected flows per ENI (source, destination, ports, bytes, action) to CloudWatch Logs or S3. Enable them on every production VPC: they are the evidence for "what talked to what" during security investigations and the fastest way to find a security group blocking traffic (REJECT records). Cost is proportional to traffic; S3 destination with Athena is cheaper at volume; one-minute aggregation gives faster diagnosis.

## Peering, Transit Gateway and shared VPCs

Part II chapter 16 covered connectivity options. VPC-level notes: peering requires non-overlapping CIDRs and is non-transitive; Transit Gateway centralises; **VPC sharing** (via Resource Access Manager) lets multiple accounts place resources in subnets owned by a network account, useful in organisations with a central networking team. For most client deployments, one VPC per environment per account, connected only where a specific need exists.

## Common mistakes

- CIDR overlapping the client's office or other VPCs; discovered when a VPN is needed (Part II chapter 3).
- Subnets too small for ECS/EKS IP consumption.
- Databases in public subnets, or in private subnets with a NAT route they do not need.
- One shared private route table sending all egress through one AZ's NAT.
- NAT gateways in every AZ for staging; or no NAT and tasks that cannot pull images (ECR needs NAT or interface endpoints).
- Forgetting the S3 gateway endpoint; paying NAT data charges for backups and image layers.
- Flow logs off; investigations impossible.
- Hand-built VPCs with no IaC; undocumented, unreproducible.
- IPv6 enabled on the VPC but security groups left IPv4-only, or vice versa.
