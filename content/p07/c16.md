## Connecting to RDS

### From the application

Three decisions: **credential**, **transport**, **pool**.

```python
# app/db.py — IAM authentication + verified TLS + pool with keepalives (asyncpg/SQLAlchemy sketch)
import boto3, ssl
from sqlalchemy.ext.asyncio import create_async_engine

def rds_token():
    return boto3.client("rds").generate_db_auth_token(DBHostname=settings.database.host, Port=5432, DBUsername="app", Region=settings.aws_region)   # 15-minute token

ssl_ctx = ssl.create_default_context(cafile="/etc/ssl/certs/aws-rds-global-bundle.pem")   # RDS CA bundle baked into the image
ssl_ctx.verify_mode = ssl.CERT_REQUIRED; ssl_ctx.check_hostname = True

engine = create_async_engine(
    f"postgresql+asyncpg://app@{settings.database.host}:5432/app",
    connect_args={"password": rds_token, "ssl": ssl_ctx, "server_settings": {"application_name": "api"}},   # callable: fresh token per connection
    pool_size=settings.database.pool_max, max_overflow=0, pool_pre_ping=True, pool_recycle=600,
)
```

- **IAM authentication**: the task role has `rds-db:connect` for the `app` database user (created with `GRANT rds_iam TO app`); the SDK mints a signed token valid 15 minutes, used as the password on connect; no stored password, rotation irrelevant. Limits: a few hundred new connections per second per instance, which pooling makes irrelevant. Alternative: Secrets Manager-managed password with rotation and the app re-reading on auth failure (Part IV chapter 17).
- **TLS with verification**: `sslmode=verify-full` (or the equivalent SSL context) against the RDS CA bundle, plus `rds.force_ssl=1` on the server. Encryption without verification protects against sniffing but not impersonation.
- **Pooling**: pool size per task × tasks ≤ ~70% of `max_connections`; `pool_pre_ping` detects connections killed by failover; `pool_recycle` below any idle timeout on the path. With many tasks or Lambdas, add **RDS Proxy** (IAM auth, multiplexing, faster failover; the app connects to the proxy endpoint) (Part VIII chapter 6).
- **Failover behaviour**: on Multi-AZ failover the endpoint's DNS changes; set the client's DNS cache low, retry connection errors with backoff, and expect 30–120 s of errors unless you use the proxy.

Least privilege inside the database: the application user owns no schema changes (`app` has DML on `app` schema; `app_migrator` has DDL and is used only by the migration task); no superuser; `pgaudit` where required (Part VIII chapter 10).

### For humans

Never a public database. Options: `aws ssm start-session … AWS-StartPortForwardingSessionToRemoteHost` through an instance in the VPC (or a tiny always-off "ops" instance started on demand), ECS Exec into a task that has `psql`, a client VPN, or a bastion. Use a read-only database role for analysts; log every session (SSM does); IAM auth tokens for humans too so no shared passwords exist. For BI tools, a read replica in a private subnet reached through the tool's VPC connectivity, never the primary via a public endpoint.

## Static frontend on S3 + CloudFront

Chapter 9 set up the distribution (OAC, SPA rewrite, security headers, `/api/*` behaviour to the ALB). The deploy pipeline:

```bash
# Frontend deploy: upload fingerprinted assets first (long cache), then the shell, then invalidate the shell
npm ci && npm run build                                    # dist/ with hashed asset filenames
aws s3 sync dist/assets s3://client-a-prod-frontend/assets --cache-control "public, max-age=31536000, immutable" --delete
aws s3 cp dist/index.html s3://client-a-prod-frontend/index.html --cache-control "no-cache" --content-type "text/html"
aws s3 sync dist s3://client-a-prod-frontend --exclude "assets/*" --exclude "index.html" --cache-control "public, max-age=300"
aws cloudfront create-invalidation --distribution-id "$CF_ID" --paths "/index.html" "/"
```

Ordering matters: assets exist before the HTML that references them; `--delete` on assets only removes assets no longer referenced by *any* recent build (keep the previous build's assets for a day by syncing without `--delete` and pruning with a lifecycle rule, so users holding the old `index.html` do not get 404s on refresh). Bucket versioning gives trivial rollback of `index.html`. Environment-specific config (API base URL) comes from a small `config.json` fetched at runtime or from build-time variables per environment; the same build should not be hard-wired to one environment unless you rebuild per environment deliberately.

Rollback: re-upload the previous `index.html` (from versioning or the previous build artifact) and invalidate; because old assets were retained, the old shell works immediately.

## Rollback matrix

| Component | Mechanism | Time | Caveats |
|---|---|---|---|
| Backend (ECS) | `update-service` to the previous task definition revision (or re-run the deploy with the previous SHA) | 2–4 min | Requires expand-only migrations; verify `/version` |
| Worker | Same | 2–4 min | In-flight jobs finish on SIGTERM |
| Frontend | Re-upload previous `index.html` (bucket versioning) + invalidate | 1–2 min | Old assets must still exist |
| Database schema | Forward-fix migration, or a down migration if written and tested; restore from PITR only for data loss | Minutes to hours | Contract-phase changes are not rolled back casually (Part X chapter 8) |
| Infrastructure (Terraform) | Revert the commit; apply | Minutes | Some resources replace rather than update; read the plan |
| Configuration / secrets | Previous parameter/secret version; restart tasks | Minutes | Secrets Manager keeps versions (AWSPREVIOUS) |
| DNS / CDN config | Revert record or distribution config | Minutes + TTL / propagation | CloudFront changes take minutes to propagate |

Rehearse each in staging; the first time you roll back must not be in production. Write the commands in the runbook (Part XV chapter 3).

## Acceptance checks

```checklist
# Connectivity, frontend and pipeline: acceptance
- Application connects to RDS with IAM auth (or rotated secret), sslmode=verify-full, pooled; failover test shows recovery within the expected window.
- No public database endpoint; human access via SSM port forwarding or VPN; read-only role for analysts; sessions logged.
- Frontend bucket private (OAC); assets immutable with hashed names; index.html no-cache; invalidation on deploy; previous build's assets retained.
- Security headers served by CloudFront; SPA deep links work on refresh; API calls through /api/* behaviour (no CORS) or CORS exact allow-list.
- Pipeline: PR checks required; artifacts built once and promoted; staging deploy automatic; production behind required reviewers; OIDC roles per environment; no stored AWS keys.
- Deploy script verifies image signature, runs migrations once, waits for services-stable, checks /version, runs smoke tests, watches alarms.
- Rollback rehearsed for backend, worker and frontend in staging within the last month; commands in the runbook.
- Terraform plan reviewed in PRs; state remote with locking (Part X chapter 6).
```

## Common mistakes

- Database password in task environment variables; or IAM auth without TLS verification.
- Public RDS "for the BI tool".
- `aws s3 sync --delete` on the whole bucket, deleting assets referenced by cached HTML; users see broken pages until they hard-refresh.
- `index.html` cached for a year; deploys invisible for a day.
- Pipeline deploying to production from a developer's laptop keys.
- No approval gate; or an approval gate so slow that hotfixes bypass the pipeline.
- Rollback never rehearsed; discovered during an incident that the previous task definition referenced an image that lifecycle policy deleted.
- Migrations and application deploy coupled so that rolling back the app breaks against the new schema.
