# Deployment Walkthrough: Containers on ECS Fargate with ECR and an ALB

:::objectives
- Deploy a containerised API and worker on ECS Fargate behind an ALB with HTTPS, private networking, secrets injection, logging and autoscaling.
- Perform zero-downtime deployments with health gating and automatic rollback, and roll back deliberately.
- Verify the deployment against a checklist and understand its cost.
:::

:::prereq
Part VI chapters 1–7; chapters 5–13 of this part. Costs: ~$3–6/day at minimal sizes in a sandbox; destroy when done.
:::

## Target architecture

This is the recommended default for most client web services: the same outcomes as chapter 14 with no hosts to patch, faster rollouts and simpler operations.

## Step 1: foundations

As in chapter 14: VPC, security groups, endpoints (ECR api/dkr, S3 gateway, Logs, Secrets Manager, SSM for ECS Exec), Route 53, ACM, RDS, SQS with DLQ, secrets/parameters, the security baseline. Plus: an ECR repository (Part VI chapter 2) with immutable tags, scan on push and a lifecycle policy; an ECS cluster with Container Insights and capacity providers (FARGATE, FARGATE_SPOT).

## Step 2: the image

Part VI chapter 3's multi-stage Dockerfile: non-root, tini, exec-form CMD, health check, ARM64 build. CI builds `--platform linux/arm64`, tags with the Git SHA, scans (Trivy), signs (cosign), pushes to ECR, and generates an SBOM (Part IV chapter 20). One image serves API and worker with different commands.

## Step 3: IAM roles

## Step 4: task definitions and services

Chapter 8 showed the API service with `deployment_minimum_healthy_percent = 100`, `maximum_percent = 200`, circuit breaker with rollback, `health_check_grace_period_seconds`, private subnets without public IPs, and target tracking on ALB requests per target. The task definition (Part VI chapter 6): `cpu 512`/`memory 1024`, ARM64, `readonlyRootFilesystem`, `initProcessEnabled`, `secrets` from Secrets Manager/SSM, `awslogs` to `/client-a/prod/api`, health check command, `stopTimeout 30`, `ulimits nofile 65536`.

The worker: same image, `command: ["python", "-m", "app.worker"]`, no load balancer, `desired_count` managed by a step-scaling or target-tracking policy on a custom metric (`ApproximateNumberOfMessagesVisible / running tasks`, published by a small Lambda or computed with metric math), capacity provider strategy `FARGATE base 1` + `FARGATE_SPOT weight 3`, `stopTimeout 120` so in-flight jobs finish (visibility timeout longer still), and the worker handling SIGTERM by finishing the current message and exiting (Part III chapter 6).

Migrations: a third task definition (`command: ["alembic", "upgrade", "head"]`) run once per deploy by the pipeline via `ecs run-task` with `--wait` semantics (poll until stopped, check exit code), before the service update (Part X chapter 8).

## Step 5: observability

`awslogs` groups with retention; Container Insights for task CPU/memory; alarms from chapter 13 (target 5xx rate, p99, unhealthy hosts, running < desired, RDS, SQS age, DLQ depth); Synthetics canary on `/health/ready` and the login page; X-Ray via ADOT sidecar or OpenTelemetry SDK exporting to X-Ray if tracing is wanted; ECS Exec enabled with CloudTrail logging for shells.

```bash
# Deploy script essentials (CI, with OIDC-assumed deploy role)
IMAGE="$ECR_REPO:$GIT_SHA"
cosign verify --certificate-identity-regexp "$CI_IDENTITY" --certificate-oidc-issuer "$OIDC_ISSUER" "$IMAGE"
# migrations
TASK=$(aws ecs run-task --cluster prod --launch-type FARGATE --network-configuration "$NETCFG" \
       --task-definition "$(register_td migrate "$IMAGE")" --query 'tasks[0].taskArn' --output text)
aws ecs wait tasks-stopped --cluster prod --tasks "$TASK"
[ "$(aws ecs describe-tasks --cluster prod --tasks "$TASK" --query 'tasks[0].containers[0].exitCode' --output text)" = "0" ] || { echo "migration failed"; exit 1; }
# services
aws ecs update-service --cluster prod --service api    --task-definition "$(register_td api "$IMAGE")"
aws ecs update-service --cluster prod --service worker --task-definition "$(register_td worker "$IMAGE")"
aws ecs wait services-stable --cluster prod --services api worker
curl -fsS https://api.client.com/version | grep -q "$GIT_SHA" || { echo "version mismatch"; exit 1; }
```

Deploy time: 2–4 minutes for a three-task service. Blue/green with CodeDeploy (two target groups, test listener, traffic shifting, automatic rollback on alarms) is available when canary-style releases are required (Part X chapter 7).

## Acceptance checks

```checklist
# ECS Fargate deployment: acceptance
- HTTPS works; HTTP redirects; TLS policy modern; HSTS; ALB default action 404.
- Tasks in private subnets, no public IPs; sg-app allows 8000 from sg-alb only; sg-db allows 5432 from sg-app/sg-worker only.
- Image pulled by digest/immutable tag; signature verified in the pipeline; scan has no critical findings.
- Task definition: non-root user, read-only root FS, init process, secrets via `secrets` (none in `environment`), awslogs with retention, health check, stopTimeout aligned with drain.
- Execution role and task role separate and least privilege; ECS Exec enabled and logged.
- Deployment: 100/200 percent, circuit breaker with rollback; a deliberately broken image rolls back automatically; a good deploy produces zero 5xx under load test.
- Worker scales on queue depth; DLQ alarmed; SIGTERM handled (kill a task mid-job: job completes exactly once).
- Migrations run once per deploy as a separate task before service updates.
- RDS Multi-AZ, IAM auth or rotated secrets, backups + cross-Region copy, restore tested.
- Alarms tested; Synthetics canary green; dashboard shows golden signals.
- Cost review after one week vs. estimate (ALB, NAT or endpoints, 3+1 tasks, RDS, logs).
```

## Cost (illustrative, eu-west-1)

Three API tasks (0.5 vCPU/1 GB ARM) ≈ $45; worker base 1 on-demand + Spot ≈ $15–30; ALB ≈ $22; NAT per AZ ≈ $32 each (or endpoints ≈ $7/AZ each × 5–6 services, comparable, with better security); RDS `db.t4g.medium` Multi-AZ ≈ $120; Redis replicated small ≈ $25; logs/metrics/alarms ≈ $15; Secrets/SSM/Route 53 ≈ $5. Roughly $300–400/month for a small production SaaS with HA; halve it for staging (single NAT, single-AZ RDS, fewer tasks).

## Common mistakes

- Tasks with public IPs in public subnets because ECR could not be reached from private subnets (fix with NAT or endpoints).
- Execution role granted the application's permissions, or vice versa.
- `minimum_healthy_percent` below 100 on small services.
- Circuit breaker disabled; stuck deployments.
- Migrations in the container entrypoint; races across tasks.
- Health check grace period shorter than start-up; tasks killed in a loop.
- Worker `stopTimeout` shorter than job duration; duplicate processing.
- Logs without retention; Container Insights off; no version endpoint.
