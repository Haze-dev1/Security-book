# Security Services: KMS, Secrets Manager, Parameter Store, CloudTrail, Config, GuardDuty, WAF and Shield

:::objectives
- Deploy the AWS security baseline every client account should have, and know what each service detects or prevents.
- Configure CloudTrail, Config and GuardDuty for an organisation with centralised, immutable logging.
- Use KMS, Secrets Manager and Parameter Store together correctly.
- Attach WAF to the edge sensibly and understand what Shield does and does not cover.
:::

:::prereq
Part IV chapters 16, 17, 22; chapters 2 and 9 of this part.

## The baseline

A client account without these is an account where a breach would be invisible, unscoped and unrecoverable. Enable them first, before workloads, ideally through Control Tower or the organisation's landing zone, and verify them during discovery of client-owned accounts (Part XIII chapter 4).

```checklist
# AWS account security baseline
- Root: hardware MFA, no access keys, contact details current, alerts on root use.
- IAM Identity Center for humans with MFA; no IAM users with keys (chapter 3).
- CloudTrail: organisation trail, all Regions, management + relevant data events, to a log-archive account bucket with Object Lock and log file validation; CloudWatch Logs integration for alerting.
- AWS Config: recorder in all Regions, conformance pack (e.g. AWS Foundational Security Best Practices / CIS), aggregated to the security account.
- GuardDuty: enabled in all Regions with S3, EKS, RDS, Lambda and Runtime Monitoring protections as applicable; delegated administrator; findings to Security Hub and alerts.
- Security Hub: enabled with the Foundational Security Best Practices standard; findings reviewed weekly.
- IAM Access Analyzer: organisation-level analyzer for external access and unused access.
- EBS default encryption on; S3 account-level Block Public Access on; default KMS keys reviewed.
- Budgets and cost anomaly alerts (chapter 4).
- VPC Flow Logs on production VPCs (chapter 5).
- Inspector for EC2/ECR/Lambda vulnerability scanning where workloads exist.
- Backup vaults with Vault Lock for critical data (chapter 13).
- Security contact email registered; incident runbook naming who receives alerts.
```

## KMS

Chapter-length treatment in Part IV chapters 16–17; the AWS specifics: **AWS managed keys** (`aws/s3`, `aws/rds`) are free and automatic but shared across your account's use of that service with no policy control; **customer managed keys** (~$1/month each plus requests) give you the **key policy** (who may administer and use), **aliases**, **rotation** (automatic yearly for symmetric keys; old material retained for decryption), **grants** for services, **multi-Region keys** for DR, and CloudTrail logging of every use. Use customer managed keys for anything regulated or client-sensitive: database, S3 data buckets, Secrets Manager, backups. Key policy must allow the account root (so IAM policies can grant use) and should deny deletion without a scheduled window; never make a key policy that locks out everyone (AWS can help recover, slowly). Deleting a key is scheduled 7–30 days out and is irreversible: data encrypted under it is gone. Alarm on `ScheduleKeyDeletion` and `DisableKey`.

## Secrets Manager and Parameter Store

Covered in Part IV chapter 17. AWS-specific patterns: RDS **managed master passwords** rotate automatically; **rotation Lambdas** for custom secrets (templates exist); **resource policies** on secrets for cross-account access; **replication** of secrets to other Regions for DR; ECS/EKS/Lambda integrations to inject at start; Parameter Store **SecureString** with a customer managed key for config-level secrets at low cost, **hierarchies** (`/prod/app/db/host`) with `GetParametersByPath`, and **advanced parameters** for larger values and policies. Name secrets by environment and application; tag for cost and ownership; alert on `GetSecretValue` by unexpected principals.

## CloudTrail

Records every API call (management events) with identity, source IP, time, parameters and result. Configure an **organisation trail** in the management account (or delegated administrator) covering all Regions and all member accounts, delivering to a bucket in the **log-archive account** with **Object Lock** (compliance mode for the retention period) and **log file validation** (digest files proving integrity). Add **data events** selectively (S3 object-level for sensitive buckets, Lambda invocations, DynamoDB) because they are voluminous and billed. Integrate with CloudWatch Logs for metric filters and alarms on: root login, console login without MFA, IAM policy changes, security group changes, CloudTrail/Config/GuardDuty disabled, KMS key deletion scheduled, unauthorised API calls. **CloudTrail Lake** or Athena over the S3 bucket for investigations ("every action by this role in the last 30 days"). Retain 1 year hot, longer in S3 per policy (Part IV chapter 22).

## AWS Config

Records configuration history of resources and evaluates **rules** continuously: `s3-bucket-public-read-prohibited`, `restricted-ssh`, `rds-storage-encrypted`, `rds-instance-public-access-check`, `encrypted-volumes`, `iam-root-access-key-check`, `cloudtrail-enabled`, `required-tags`, and hundreds more; **conformance packs** bundle them (CIS, FSBP, PCI). Remediation actions (SSM Automation documents) can auto-fix some findings (close a public bucket, enable encryption). Aggregate to the security account for a single compliance view. Config is also your drift detector: "who changed this security group and when" is answered from its timeline when CloudTrail is too noisy. Cost: per configuration item recorded and per rule evaluation; noisy resources (frequent ECS task changes) can make it expensive; exclude high-churn resource types if needed.

## GuardDuty

Threat detection from CloudTrail, VPC Flow Logs, DNS logs, S3 data events, EKS audit logs, RDS login activity, Lambda network activity and runtime agents, without you shipping anything. Findings include: credential exfiltration (instance credentials used from outside AWS), crypto-mining, communication with known command-and-control, port scanning, unusual API patterns (new Region, disabled logging), S3 anomalous access, brute-force logins to RDS, malware in EBS (Malware Protection). Enable in every Region of every account with a delegated administrator; route findings (severity ≥ medium) to a channel a human reads and high severity to paging; integrate with Security Hub; suppress known-benign patterns with suppression rules rather than ignoring the feed. It is inexpensive relative to what it catches and is often the first signal of a compromised key.

## Security Hub, Inspector, Macie, Detective

**Security Hub** aggregates findings (GuardDuty, Inspector, Macie, Config, IAM Access Analyzer, partners) and scores against standards; use it as the single pane and weekly review. **Inspector** scans EC2 instances (via SSM agent), ECR images and Lambda functions for CVEs and network exposure, continuously. **Macie** discovers sensitive data (PII, credentials) in S3 buckets, useful for data-classification audits (Part IV chapter 23). **Detective** builds investigation graphs from GuardDuty findings. **Audit Manager** maps evidence to frameworks for compliance programmes.

## WAF and Shield

**AWS WAF** attaches to CloudFront, ALB, API Gateway, AppSync and Cognito. A web ACL contains rules: **managed rule groups** (AWS Core Rule Set for OWASP-style patterns, Known Bad Inputs, SQL injection, Linux/PHP/WordPress-specific, Amazon IP reputation, Anonymous IP, **Bot Control** with its own pricing), **rate-based rules** (e.g. 2,000 requests per 5 minutes per IP, with scope-down to login paths for tighter limits), geo-match, IP sets, and custom rules on headers, URIs, bodies and labels. Start every rule group in **count** mode, review sampled requests and CloudWatch metrics for a week, then switch to block; keep an allow rule for health checks and known partners; log to S3/CloudWatch/Kinesis for investigation; expect to tune false positives (a legitimate JSON body containing SQL keywords). Cost: per web ACL, per rule, per million requests; Bot Control and Fraud Control cost more. WAF is a shield against commodity attacks and floods, not a substitute for secure code (Part II chapter 15, Part IV).

**Shield Standard** is automatic and free: network/transport-layer DDoS protection for CloudFront, Route 53, ALB/NLB. **Shield Advanced** ($3,000/month per organisation plus data fees) adds enhanced detection, response team access, cost protection for scaling during attacks, and application-layer protections; justified for high-profile targets or contractual requirements, not for typical client systems. Architecturally, putting everything behind CloudFront and Route 53 gives you most practical DDoS resilience at no extra cost.

## Alerting on the baseline

Route to a monitored channel: GuardDuty findings (medium+), Security Hub critical/high new findings, Config non-compliance on critical rules (public S3, public RDS, open security groups), CloudTrail metric-filter alarms (root use, console login without MFA, IAM changes, logging disabled, KMS deletion), Access Analyzer external access findings, Inspector critical CVEs on Internet-facing resources, budget and anomaly alerts. Page a human for: root use, logging disabled, GuardDuty high severity, KMS key deletion scheduled. Everything else is a daily or weekly review.

## Common mistakes

- Trails per account with logs in the same account the attacker controls; or Object Lock missing.
- GuardDuty enabled in one Region; attackers use another.
- Config rules on with nobody reading findings; hundreds of non-compliant resources for years.
- Customer managed keys with policies that cannot be administered; or deleted keys with live data.
- WAF in count mode forever, or in block mode with no tuning and legitimate users blocked.
- Shield Advanced bought for a small system; or assuming Shield Standard protects an EC2 instance's public IP (put it behind CloudFront/ALB).
- Secrets in Parameter Store as plain `String`.
- Security findings routed to a mailbox nobody owns.

## Exercises

1. In a sandbox organisation, enable the baseline (organisation trail to a locked bucket, Config with FSBP, GuardDuty, Security Hub, Access Analyzer). Create a public bucket and an open security group; find the findings in Security Hub and the Config timeline.
2. Create CloudTrail metric filters and alarms for root login and IAM policy changes; trigger them deliberately.
3. Attach a WAF web ACL with the Core Rule Set in count mode to a test ALB; send a few hostile-looking requests; read the sampled requests; switch to block with a rate rule on the login path.
