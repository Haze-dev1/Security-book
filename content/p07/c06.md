# Security Groups, Network ACLs, Elastic IPs and VPC Endpoints

- Use gateway and interface endpoints to keep AWS service traffic private and cheap.

## The problem

The VPC's routing decides where packets *can* go; security groups and NACLs decide whether they are *allowed*. Most AWS exposure incidents are a security group rule with `0.0.0.0/0` on the wrong port, and most "it cannot connect" tickets are a missing security group reference. The mechanics are simple; the discipline is in the design.

## Security groups

A security group is a **stateful** virtual firewall attached to **elastic network interfaces** (instances, tasks, RDS, load balancers, Lambda ENIs, endpoints). Rules are allow-only; traffic not matched by any rule on any attached group is denied; return traffic for allowed connections is permitted automatically. Inbound rules specify protocol, port range and a source (CIDR, prefix list, or **another security group**); outbound rules likewise with a destination. Default: no inbound, all outbound.

### Design by role

```yaml
# Security groups for the reference architecture (Terraform-ish pseudocode)
sg-alb:
  ingress: [ {443 from 0.0.0.0/0 and ::/0}, {80 from 0.0.0.0/0 and ::/0} ]        # the only public surface
  egress:  [ {8000 to sg-app} ]                                                       # restrict egress too: ALB talks only to targets
sg-app:
  ingress: [ {8000 from sg-alb} ]                                                     # by group, never by CIDR
  egress:  [ {5432 to sg-db}, {6379 to sg-cache}, {443 to 0.0.0.0/0} ]                # DB, cache, HTTPS to the Internet/AWS APIs
sg-worker:
  ingress: []                                                                         # nothing inbound; workers poll
  egress:  [ {5432 to sg-db}, {6379 to sg-cache}, {443 to 0.0.0.0/0} ]
sg-db:
  ingress: [ {5432 from sg-app}, {5432 from sg-worker}, {5432 from sg-bastion} ]
  egress:  []                                                                         # databases initiate nothing
sg-cache:
  ingress: [ {6379 from sg-app}, {6379 from sg-worker} ]
  egress:  []
sg-vpce:
  ingress: [ {443 from sg-app}, {443 from sg-worker} ]                                # interface endpoints accept from app tier
sg-bastion (if any):
  ingress: [ {22 from <office CIDR>} ]   # better: no bastion; SSM
```

Principles: one group per role, attached to every member of that role; **references by group ID** so autoscaling, IP changes and new instances need no rule edits; inbound only for what the role serves; **egress restricted** on tiers that can be (databases initiate nothing; app tier reaches only its dependencies and 443); no SSH rules in favour of SSM; names and descriptions on every rule (`description = "ALB to API port"`), because rules without descriptions are never cleaned up.

Limits worth knowing: 60 inbound and 60 outbound rules per group by default (adjustable), 5 groups per ENI; referencing a group from another account is possible in peered VPCs; referencing groups across VPCs in the same Region works with peering and security-group referencing enabled on Transit Gateway.

```hcl
resource "aws_security_group_rule" "app_from_alb" {
  type                     = "ingress"
  security_group_id        = aws_security_group.app.id
  from_port                = 8000
  to_port                  = 8000
  protocol                 = "tcp"
  source_security_group_id = aws_security_group.alb.id
  description              = "ALB to API"
}
```

### Auditing

AWS Config managed rules: `restricted-ssh`, `restricted-common-ports`, `vpc-sg-open-only-to-authorized-ports`, `ec2-security-group-attached-to-eni` (find unused groups). Security Hub's foundational standard flags `0.0.0.0/0` on high-risk ports. **Network Access Analyzer** and **Reachability Analyzer** prove intended isolation. Run a script monthly listing every rule with a world source on a port other than 80/443 on a load balancer group.

## Network ACLs

Stateless, subnet-level, ordered allow/deny rules evaluated lowest number first; the default NACL allows everything. Because they are stateless, allowing inbound 443 requires allowing outbound ephemeral ports (1024–65535) for replies, and vice versa for outbound connections. Use them for: a hard deny of known-bad CIDRs; subnet-tier isolation that must hold even if a security group is misconfigured (data subnets accept 5432/6379 only from app subnet CIDRs); compliance requirements for subnet-level controls. Keep them few and documented; a forgotten NACL rule produces baffling one-directional timeouts (Part II chapter 15).

```text
Data-subnet NACL (example)
Inbound:  100 allow TCP 5432 from 10.20.64.0/18 (app tier) | 110 allow TCP 6379 from 10.20.64.0/18 | 120 allow TCP 1024-65535 from 10.20.0.0/16 (replies to any outbound the tier makes, e.g. to endpoints) | * deny all
Outbound: 100 allow TCP 1024-65535 to 10.20.64.0/18 (replies) | 110 allow TCP 443 to 10.20.0.0/16 (to interface endpoints for backups/monitoring) | * deny all
```

## Public addressing and Elastic IPs

Instances in public subnets may receive a dynamic public IPv4 at launch (changes on stop/start). An **Elastic IP** is a static public IPv4 you allocate and attach (to an instance ENI or a NAT gateway), remappable on failure. Since 2024, **every public IPv4 address costs ~$0.005/hour (~$3.60/month)**, attached or not, which changes the calculus: minimise public IPs (private subnets plus a load balancer), use IPv6 where possible, and release unused EIPs. The ALB's own public IPs are managed by AWS and change; NLBs can hold EIPs when partners need static addresses (Part II chapter 13). **Bring Your Own IP** exists for enterprises with owned ranges.

Elastic IPs are also the **egress identity** of your NAT gateways; record them in the runbook and in partner allow-list documentation, and manage them in IaC so a rebuild does not silently change them (Part II chapter 19 scenario).

## VPC endpoints

Without endpoints, traffic from private subnets to AWS services (S3, ECR, Secrets Manager, CloudWatch, SSM, STS, SQS…) goes through the NAT gateway to the public endpoints: data charges and a path through the Internet-facing side. Endpoints provide private paths:

- **Gateway endpoints** (S3, DynamoDB): a route-table entry via a prefix list; free; regional. Always create them.
- **Interface endpoints** (PrivateLink, most other services): an ENI with a private IP per subnet/AZ and private DNS so the service's normal hostname resolves to it; ~$0.01/hour per AZ per endpoint (~$7.30/month/AZ) plus $0.01/GB. Create them for high-volume or sensitive services (ECR api + dkr, CloudWatch Logs, Secrets Manager, SSM trio for Session Manager, STS, KMS); for low-volume services the NAT may be cheaper. Attach `sg-vpce` allowing 443 from the tiers that need them.
- **Endpoint policies** restrict which resources are reachable through the endpoint (e.g., only your buckets via the S3 endpoint, preventing exfiltration to an attacker's bucket). Combine with bucket policies using `aws:SourceVpce` to require that access comes via your endpoint.

```hcl
locals { interface_services = ["ecr.api", "ecr.dkr", "logs", "secretsmanager", "ssm", "ssmmessages", "ec2messages", "sts", "kms"] }
resource "aws_vpc_endpoint" "iface" {
  for_each            = toset(local.interface_services)
  vpc_id              = module.vpc.vpc_id
  service_name        = "com.amazonaws.eu-west-1.${each.value}"
  vpc_endpoint_type   = "Interface"
  subnet_ids          = module.vpc.private_subnets
  security_group_ids  = [aws_security_group.vpce.id]
  private_dns_enabled = true
}
```

Fully private deployments (no NAT at all) are possible for workloads that only talk to AWS services and each other: cheaper, with no Internet path from the application tier, at the cost of needing an endpoint for every AWS service used and a strategy for third-party APIs (none reachable, or a dedicated egress proxy).

## Putting the layers together

A request to the database must pass: the data subnet's NACL (inbound from app CIDR on 5432, outbound ephemeral to app CIDR), the database's security group (5432 from `sg-app`), and the route (local). A compromised app task trying to reach the Internet from a data-tier host cannot: no route. A compromised app task trying to upload data to an attacker's S3 bucket via the gateway endpoint is blocked by the endpoint policy restricting buckets. Each layer is independent; each is cheap.

## Common mistakes

- Security group rules by CIDR for internal tiers; breakage on IP change.
- The default security group used by everything; or one "allow all within VPC" rule.
- SSH or database ports open to the world "temporarily".
- Rules without descriptions; nobody dares delete them.
- NACLs edited without ephemeral-port rules; one-way timeouts.
- Public IPs on application instances; now also a monthly charge each.
- NAT data charges for S3 and ECR traffic that a free gateway endpoint or a cheap interface endpoint would carry.
- Interface endpoints for every service in every AZ of staging; the endpoint bill exceeds the NAT it replaced.
- No endpoint policy; exfiltration path via S3.
