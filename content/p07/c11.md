## Why managed

Running PostgreSQL yourself means owning installation, patching, replication, failover, backups, PITR, monitoring and storage management (Part V). RDS does all of that behind an endpoint for a premium of roughly 30–50% over the raw instance cost, which for every client system that is not a database company is the best money in the budget. The shared responsibility line moves: AWS runs the engine and host; you own schema, queries, users, parameter choices, sizing, and the decision to enable the protections below.

## RDS for PostgreSQL (and MySQL)

```hcl
resource "aws_db_subnet_group" "data" { name = "client-a-prod-data"; subnet_ids = module.vpc.database_subnets }

resource "aws_db_parameter_group" "pg16" {
  name   = "client-a-prod-pg16"
  family = "postgres16"
  parameter { name = "log_min_duration_statement", value = "500" }          # log slow queries (ms)
  parameter { name = "log_connections", value = "1" }
  parameter { name = "idle_in_transaction_session_timeout", value = "60000" }
  parameter { name = "statement_timeout", value = "30000" }
  parameter { name = "rds.force_ssl", value = "1" }                          # TLS required
  parameter { name = "shared_preload_libraries", value = "pg_stat_statements", apply_method = "pending-reboot" }
}

resource "aws_db_instance" "main" {
  identifier              = "client-a-prod"
  engine                  = "postgres"
  engine_version          = "16.4"
  instance_class          = "db.m7g.large"              # Graviton; size from load tests, not guesses
  allocated_storage       = 100
  max_allocated_storage   = 500                          # storage autoscaling: grows before it fills
  storage_type            = "gp3"
  storage_encrypted       = true
  kms_key_id              = aws_kms_key.data.arn
  db_subnet_group_name    = aws_db_subnet_group.data.name
  vpc_security_group_ids  = [aws_security_group.db.id]
  publicly_accessible     = false
  multi_az                = true                         # synchronous standby in another AZ; automatic failover
  db_name                 = "app"
  username                = "app_admin"
  manage_master_user_password = true                     # master password in Secrets Manager, rotated by RDS
  iam_database_authentication_enabled = true             # app connects with IAM tokens, no password
  parameter_group_name    = aws_db_parameter_group.pg16.name
  backup_retention_period = 14                           # days of automated backups + PITR
  backup_window           = "02:00-03:00"
  maintenance_window      = "sun:03:30-sun:04:30"
  auto_minor_version_upgrade = true
  copy_tags_to_snapshot   = true
  deletion_protection     = true
  skip_final_snapshot     = false
  final_snapshot_identifier = "client-a-prod-final"
  performance_insights_enabled = true
  performance_insights_retention_period = 7
  monitoring_interval     = 60
  monitoring_role_arn     = aws_iam_role.rds_monitoring.arn
  enabled_cloudwatch_logs_exports = ["postgresql", "upgrade"]
  apply_immediately       = false
}
```

What matters:

- **Multi-AZ** keeps a synchronous standby; failover in 1–2 minutes with the same endpoint (DNS flips; applications must reconnect and tolerate the blip). It does not serve reads; **read replicas** (asynchronous, own endpoints) do. Multi-AZ DB clusters (two readable standbys) exist for some engines.
- **Storage**: gp3 with autoscaling; provision IOPS/throughput for heavy loads; io2 for the most demanding. Storage can grow, never shrink.
- **Backups and PITR**: automated daily snapshots plus transaction logs give restore to any second within the retention window (max 35 days). Manual snapshots persist until deleted. Cross-Region/account copies via AWS Backup for DR (Part V chapter 11). Restores create a *new* instance; practise the procedure.
- **Security**: private subnets, security group from the app tier only, `publicly_accessible = false`, encryption at rest (cannot be enabled later without snapshot-restore), `rds.force_ssl`, IAM authentication or Secrets Manager-managed passwords with rotation, least-privilege database roles for the application (never the master user), CloudTrail for API actions, pgAudit extension where required.
- **Parameters**: slow query logging, timeouts, `pg_stat_statements` for query analysis (Part VIII chapter 4).
- **Monitoring**: Enhanced Monitoring (OS metrics), Performance Insights (wait events, top SQL), CloudWatch alarms on `CPUUtilization`, `FreeableMemory`, `FreeStorageSpace`, `DatabaseConnections`, `ReadLatency`/`WriteLatency`, `ReplicaLag`.
- **Maintenance**: minor versions in the window (brief failover on Multi-AZ); major versions are planned upgrades with a snapshot first and a tested rollback (Part VIII chapter 7 for application compatibility). Blue/Green Deployments for RDS create a synchronised staging copy to test upgrades and switch over with minimal downtime.
- **Connections**: each instance class has a `max_connections` ceiling; pool in the application and add **RDS Proxy** (connection multiplexing, IAM auth, faster failover) when many tasks or Lambdas connect (Part VIII chapter 6).

Cost (illustrative, us-east-1): `db.t4g.micro` single-AZ ≈ $12/month (dev); `db.m7g.large` Multi-AZ ≈ $300/month plus storage, backups beyond the free allowance, Performance Insights beyond 7 days. Reserved Instances cut 30–60% for steady production databases; buy after sizing settles.

## Aurora

Aurora (PostgreSQL- and MySQL-compatible) separates compute from a distributed, self-healing storage layer replicated six ways across three AZs. Consequences: storage grows automatically to 128 TiB; up to 15 low-lag read replicas sharing the storage (failover in ~30 s to a replica, with a reader endpoint load-balancing reads); **Aurora Serverless v2** scales compute in fractions of an ACU within seconds (excellent for spiky or low-average loads, and for dev/staging); **Global Database** replicates to other Regions with sub-second lag for DR and read locality; backtrack (MySQL) rewinds without restore; faster recovery; **Aurora I/O-Optimized** pricing for I/O-heavy workloads. The premium over RDS is roughly 20% on compute plus storage/I/O charges; it pays off when you need the replica scaling, the failover speed, the serverless elasticity, or global replication. For a small, steady client database, RDS PostgreSQL Multi-AZ is simpler and cheaper; Aurora is the upgrade path, not the default.

## DynamoDB

A fully managed key-value/document store with single-digit-millisecond latency at any scale, no servers, no connections, pay-per-request or provisioned capacity. The design discipline is inverted from relational: you model **access patterns first**, then design a **partition key** (and optional **sort key**) so that every query is a lookup or a range on a key. There are no joins and no ad-hoc queries without a scan.

```python
# Single-table design sketch: tenant-scoped orders and their items
# PK = "TENANT#t_7"             SK = "ORDER#2026-03-14T10:21:07Z#ord_01HZX"   → order header
# PK = "ORDER#ord_01HZX"        SK = "ITEM#1" / "ITEM#2"                        → line items
# GSI1: PK = "CUSTOMER#cus_42"  SK = "ORDER#2026-03-14..."                      → orders by customer
table.put_item(Item={"PK": "TENANT#t_7", "SK": f"ORDER#{created}#{order_id}", "status": "pending", "total": "49.90", "GSI1PK": "CUSTOMER#cus_42", "GSI1SK": f"ORDER#{created}", "ttl": expires_epoch})
table.query(KeyConditionExpression=Key("PK").eq("TENANT#t_7") & Key("SK").begins_with("ORDER#2026-03"))
```

Essentials: hot partitions come from low-cardinality keys (a tenant with 90% of traffic, a date as the whole key); **GSIs** add alternative access patterns (eventually consistent, own capacity); **LSIs** must be defined at creation; **TTL** expires items for free (sessions, idempotency keys, tokens); **Streams** feed Lambda for change events; **transactions** (`TransactWriteItems`) give atomic multi-item writes; **conditional writes** implement optimistic concurrency and create-once; **on-demand capacity** for unpredictable loads, **provisioned with autoscaling** for steady ones (cheaper at scale); item size limit 400 KB (large blobs go to S3 with a pointer); point-in-time recovery and on-demand backups; encryption with KMS; **DAX** for microsecond read caching; **Global Tables** for multi-Region active-active. Good fits: sessions, idempotency stores, rate-limit counters, event logs, high-scale key-value access, serverless architectures. Poor fits: ad-hoc reporting, complex relational queries, schemas that change access patterns often (Part VIII chapters 2 and 13).

## ElastiCache (Redis / Valkey)

Managed in-memory store (Redis OSS, Valkey fork, Memcached). Production configuration: **cluster mode disabled** with a primary and one or two replicas across AZs and **automatic failover** for sessions/caches up to a node's memory; **cluster mode enabled** (sharded) for larger datasets or throughput; encryption at rest and in transit; **AUTH token** or **RBAC users** (Redis 6+); private subnets with a security group from the app tier; `maxmemory-policy` chosen for the use (`allkeys-lru` for pure caches, `volatile-lru` when some keys must persist); snapshots if the data matters (usually not for caches); Multi-AZ. **ElastiCache Serverless** removes node sizing for variable loads at a per-GB-hour and per-request price. Treat Redis as losable from the application's perspective (Part III chapter 8) and as a hard dependency only for sessions where you have made it highly available. Cost: `cache.t4g.micro` ≈ $12/month; a replicated `cache.m7g.large` pair ≈ $200+/month.

## Common mistakes

- Single-AZ production databases to save money; AZ event equals outage plus possible data loss.
- `publicly_accessible = true` or a security group open to the VPC/world.
- Application connecting as the master user.
- No `max_allocated_storage`; disk fills; database stops.
- Backups at the default 7 days with no cross-Region copy; or `skip_final_snapshot = true` on production.
- Unencrypted at creation; cannot be fixed in place.
- Connection exhaustion from many Lambdas/tasks without a proxy.
- DynamoDB tables designed like relational tables; scans everywhere; hot partitions.
- Redis without AUTH/TLS, or as a single node holding sessions.
- Major version upgrades without a snapshot and a test.
