# Deployment Walkthrough: A Backend on EC2

:::objectives
- Deploy a backend API on EC2 the production way: golden AMI, Auto Scaling Group across AZs, ALB with HTTPS, private subnets, RDS, Secrets Manager, CloudWatch agent, SSM access.
- Understand the deploy and rollback mechanics of immutable VMs.
- Know what this design costs and when to choose it over containers.
:::

:::prereq
Part V (all); chapters 5–13 of this part. Costs: this walkthrough runs ~$3–5/day at minimal sizes in a sandbox; destroy when done.
:::

## Step 1: foundations (once)

VPC from chapter 5 (three AZs, public/private/data tiers, NAT per AZ for prod, S3 gateway endpoint, flow logs); security groups from chapter 6 (`sg-alb`, `sg-app`, `sg-db`, `sg-cache`, `sg-vpce`); interface endpoints for SSM, Logs, Secrets Manager, STS, KMS if you want private-only access paths; Route 53 zone and ACM certificate (chapter 9); RDS and ElastiCache (chapter 11); Secrets Manager entries and SSM parameters (`/prod/app/*`); S3 artifact and uploads buckets (chapter 10); the security baseline (chapter 12). All in Terraform, in a `platform` state separate from the application's.

## Step 2: the golden AMI

Packer (chapter 7) builds an Ubuntu 24.04 ARM image with: hardening (Part V chapter 4), chrony, unattended-upgrades, nftables, SSM and CloudWatch agents, Python 3.12 and system libraries, the `app` user and directory layout (Part V chapter 5), the systemd unit template, and the CloudWatch agent configuration pulled from SSM Parameter Store at boot. It does **not** contain the application code or any configuration: the same AMI serves staging and production. Built weekly by CI and on base-image advisories, scanned by Inspector, tagged with the commit and build time.

## Step 3: the application artifact

CI builds the application into a versioned tarball (`app-2.4.0.tar.gz` containing code and a pre-built virtualenv for the AMI's Python and architecture) and uploads it to the artifact bucket, plus a `manifest.json` with checksums. Containers would make this a registry push; with VMs the tarball is the artifact. Keep the last N versions for rollback.

## Step 4: launch template and user data

```bash
#!/usr/bin/env bash
# user-data: environment-specific, idempotent, short. Everything slow is in the AMI.
set -euo pipefail
exec > >(tee /var/log/user-data.log | logger -t user-data) 2>&1

REGION=$(curl -sS -H "X-aws-ec2-metadata-token: $(curl -sS -X PUT http://169.254.169.254/latest/api/token -H 'X-aws-ec2-metadata-token-ttl-seconds: 60')" http://169.254.169.254/latest/meta-data/placement/region)
ENV="${env}"                       # templated by Terraform
APP_VERSION="${app_version}"

# 1. Non-secret config from Parameter Store → environment file (640 root:app)
aws ssm get-parameters-by-path --region "$REGION" --path "/$ENV/app/config/" --query 'Parameters[].[Name,Value]' --output text \
  | awk -F'\t' '{ n=$1; sub(".*/", "", n); print toupper(n) "=" $2 }' > /etc/app/app.env
echo "ENV=$ENV" >> /etc/app/app.env; echo "APP_VERSION=$APP_VERSION" >> /etc/app/app.env
chown root:app /etc/app/app.env && chmod 640 /etc/app/app.env
# Secrets are fetched by the app at start via the instance role (SECRET_NAME in config); nothing secret touches disk.

# 2. Fetch and install the release
aws s3 cp "s3://client-a-artifacts/app-$APP_VERSION.tar.gz" /tmp/app.tgz --region "$REGION"
sha256sum -c <(aws s3 cp "s3://client-a-artifacts/app-$APP_VERSION.sha256" - --region "$REGION")
install -d -o root -g app -m 750 "/srv/app/releases/$APP_VERSION"
tar -xzf /tmp/app.tgz -C "/srv/app/releases/$APP_VERSION" && chown -R root:app "/srv/app/releases/$APP_VERSION"
ln -sfn "/srv/app/releases/$APP_VERSION" /srv/app/current

# 3. Start
systemctl daemon-reload
systemctl enable --now app
# ALB health checks will admit the instance when /health/ready returns 200
```

Database migrations do **not** run here (they would run once per instance); they run as a separate step in the pipeline before the fleet rolls (Part X chapter 8).

## Step 5: the ASG, ALB and scaling

Chapter 7's ASG (min 3, across private subnets, ELB health checks, grace period above boot-to-ready, instance refresh with 90% minimum healthy and auto-rollback) registered in chapter 9's target group (`/health/ready`, 10 s interval, deregistration 20 s). Target tracking on `ALBRequestCountPerTarget` (e.g. 400) with a CPU policy as a second signal. Lifecycle hook on termination giving 60 s for drain and log flush.

## Step 6: observability and operations

CloudWatch agent config (from Parameter Store) shipping the journal (`app`, `nginx` if present, auth, user-data) and system metrics; alarms from chapter 13; access via `aws ssm start-session`; patching via weekly AMI rebuild and instance refresh (Part V chapter 12). AWS Backup for RDS with cross-Region copy and restore testing.

```flow
    {"from":"asg","to":"alb","label":"register new / deregister old","title":"Traffic shifts","detail":"The ALB sends traffic only to healthy targets; in-flight requests on old instances complete during the deregistration delay. CI polls `describe-instance-refreshes` until Successful."},
    {"from":"ci","to":"ci","label":"smoke tests, watch alarms 15 min","title":"Verify","detail":"Hit /version through the ALB expecting 2.5.0 on every response; run smoke tests; hold for the alarm window. If 5xx rate or latency alarms fire, roll back."},
    {"from":"ci","to":"tf","label":"rollback: apply app_version=2.4.0","title":"Rollback (if needed)","detail":"Identical mechanism in reverse: a new launch template version with the previous artifact; instance refresh replaces the fleet. Because migrations were expand-only, 2.4.0 still works. The contract phase of the migration runs in a later release once 2.5.0 is stable.","dashed":true}
  ]

```

Deploy time is dominated by instance boot (1–3 minutes per batch); a three-instance fleet rolls in 5–10 minutes. Containers on ECS roll in 2–4 minutes with the same shape; that difference, plus no AMI pipeline and no OS to patch, is the main reason chapter 15's design is the usual recommendation. Choose EC2 when a dependency needs a VM, when the client's team operates VMs well, or when sustained load makes reserved EC2 materially cheaper.

## Acceptance checks

```checklist
# EC2 backend deployment: acceptance
- `curl -sI https://api.client.com/health/ready` → 200; `http://` → 301; ALB security policy TLS 1.2+/1.3; HSTS present.
- Instances have no public IPs; SG allows 8000 only from the ALB SG; SSH not open; SSM session works.
- IMDSv2 required (`aws ec2 describe-instances --query ... MetadataOptions.HttpTokens` = required).
- `/version` returns the deployed version on every instance; `app` enabled and hardened (`systemd-analyze security`).
- Terminate one instance: ASG replaces it within grace period + boot; no 5xx observed during replacement.
- Instance refresh with a new version completes with ≥90% healthy; rollback to the previous version succeeds.
- RDS reachable only from the app SG; TLS enforced; IAM auth or Secrets Manager; backups and cross-Region copy present; restore tested.
- Logs in CloudWatch with request IDs; alarms tested; Synthetics canary green.
- AMI less than 14 days old; Inspector shows no critical findings; patch compliance reported.
- Cost: estimate vs. first-week actual reviewed (ALB, NAT, 3 instances, RDS Multi-AZ, Redis, logs).
```

## Common mistakes

- Application code baked into the AMI, so every release needs an AMI build and staging/prod diverge.
- Migrations in user data, running N times.
- Grace period too short; refresh loops.
- Hand changes on instances that the next refresh erases.
- Secrets in user data or in the AMI.
- Single AZ, single instance, outside an ASG.
- No `/version` endpoint; nobody can confirm what rolled out.
- Forgetting deregistration delay and lifecycle hooks; dropped requests on every deploy.
