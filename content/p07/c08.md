## ECS on Fargate in depth

ECS is AWS's container orchestrator: a **cluster** (logical grouping; with Fargate, no instances to manage), **task definitions** (the pod-like blueprint: containers, images, CPU/memory, ports, environment, secrets, logging, roles, volumes), **tasks** (running instances of a task definition), and **services** (maintain N tasks, integrate with load balancers, roll out new task definitions, scale). Part VI chapter 6 showed a task definition's container section; the service is the deployment unit:

```hcl
resource "aws_ecs_cluster" "prod" {
  name = "client-a-prod"
  setting { name = "containerInsights", value = "enabled" }
}

resource "aws_ecs_task_definition" "api" {
  family                   = "client-a-prod-api"
  requires_compatibilities = ["FARGATE"]
  network_mode             = "awsvpc"
  cpu                      = 512                   # 0.5 vCPU
  memory                   = 1024                  # 1 GB; valid cpu/memory combinations are fixed
  runtime_platform { cpu_architecture = "ARM64", operating_system_family = "LINUX" }   # Graviton: cheaper
  execution_role_arn       = aws_iam_role.ecs_execution.arn   # pull image, fetch secrets, write logs
  task_role_arn            = aws_iam_role.api_task.arn        # what the app may do (S3, SQS, Secrets…)
  container_definitions    = jsonencode([ { name = "api", image = "${aws_ecr_repository.app.repository_url}:${var.image_tag}", ... } ])
}

resource "aws_ecs_service" "api" {
  name            = "api"
  cluster         = aws_ecs_cluster.prod.id
  task_definition = aws_ecs_task_definition.api.arn
  desired_count   = 3
  launch_type     = "FARGATE"            # or capacity_provider_strategy with FARGATE and FARGATE_SPOT
  platform_version = "LATEST"
  network_configuration {
    subnets          = module.vpc.private_subnets
    security_groups  = [aws_security_group.app.id]
    assign_public_ip = false
  }
  load_balancer {
    target_group_arn = aws_lb_target_group.api.arn
    container_name   = "api"
    container_port   = 8000
  }
  health_check_grace_period_seconds = 60
  deployment_controller { type = "ECS" }
  deployment_minimum_healthy_percent = 100
  deployment_maximum_percent         = 200          # start new tasks before stopping old: zero capacity loss
  deployment_circuit_breaker { enable = true, rollback = true }   # failed deployments roll back automatically
  enable_execute_command = true                     # ECS Exec for shells via SSM (audit it)
  propagate_tags = "SERVICE"
  lifecycle { ignore_changes = [desired_count] }    # autoscaling owns it
}

resource "aws_appautoscaling_target" "api" {
  service_namespace  = "ecs"
  resource_id        = "service/${aws_ecs_cluster.prod.name}/${aws_ecs_service.api.name}"
  scalable_dimension = "ecs:service:DesiredCount"
  min_capacity       = 3
  max_capacity       = 30
}
resource "aws_appautoscaling_policy" "api_rps" {
  name               = "alb-requests-per-target"
  service_namespace  = "ecs"
  resource_id        = aws_appautoscaling_target.api.resource_id
  scalable_dimension = aws_appautoscaling_target.api.scalable_dimension
  policy_type        = "TargetTrackingScaling"
  target_tracking_scaling_policy_configuration {
    predefined_metric_specification {
      predefined_metric_type = "ALBRequestCountPerTarget"
      resource_label         = "${aws_lb.main.arn_suffix}/${aws_lb_target_group.api.arn_suffix}"
    }
    target_value       = 400
    scale_in_cooldown  = 300
    scale_out_cooldown = 60
  }
}
```

Key behaviours: a **deployment** is a new task definition revision applied to the service; ECS starts new tasks (up to `maximum_percent`), waits for them to pass the ALB health check, then drains and stops old ones (respecting `stopTimeout` and deregistration delay); the **circuit breaker** rolls back if new tasks keep failing. Blue/green deployments via CodeDeploy are available for traffic shifting and canaries. **Fargate Spot** runs tasks on spare capacity at ~70% discount for interruption-tolerant workers. **Service Connect** or Cloud Map provide service discovery for task-to-task calls. **ECS Exec** gives SSM-backed shells into tasks. Scheduled tasks (EventBridge → ECS RunTask) handle cron-style jobs. Workers are services without a load balancer, scaled on SQS queue depth via a custom metric.

Costs (illustrative): a 0.5 vCPU / 1 GB Fargate task runs about $18–22/month on x86 and less on ARM in us-east-1; three always-on tasks plus an ALB is the baseline of a small production API.

## Lambda in depth

A function is code plus configuration (runtime, memory 128 MB–10 GB which also scales CPU, timeout up to 15 min, environment, role, VPC settings) invoked by events: API Gateway/ALB/Function URLs (HTTP), S3, SQS, EventBridge schedules and events, DynamoDB streams, Kinesis, SNS, and direct calls. Billing per request and per GB-second of duration; a generous permanent free tier.

Design notes: package as a zip (small, fast) or a container image (up to 10 GB, familiar tooling); keep functions single-purpose and short; initialise clients outside the handler (reused across warm invocations); make handlers idempotent (at-least-once invocation for async sources; Part III chapter 3); set reserved concurrency to cap blast radius and cost, provisioned concurrency to kill cold starts for latency-sensitive APIs; use SQS between producers and Lambda for buffering and retries with DLQs; attach to a VPC only when the function must reach private resources (then it needs NAT or endpoints for AWS APIs); Lambda runtimes are deprecated on a schedule (upgrade or lose support); watch for recursive invocation loops (budget alerts, built-in recursion detection for some patterns). Lambda Powertools (Python/TS/Java) gives structured logging, tracing and idempotency utilities. Step Functions orchestrates multi-step workflows across functions with retries and state.

When Lambda is the wrong tool: steady high-throughput APIs (containers are cheaper and have no cold starts), long jobs, workloads needing persistent connections or local state, and large monoliths lifted into a single giant function.

## EKS, briefly

Part VI covered Kubernetes and the honest cost. On AWS: control plane fee plus nodes (managed node groups, Karpenter) or Fargate profiles; add-ons to manage; IAM via IRSA/Pod Identity; VPC CNI consuming subnet IPs; ALB via the AWS Load Balancer Controller. Choose it for the reasons in Part VI chapter 14; otherwise ECS.

## App Runner and Elastic Beanstalk

**App Runner** takes a container image (or source repository) and gives you a scaled, HTTPS-fronted web service with minimal configuration, VPC connectivity to private resources via a connector, and pay-per-use with an idle discount. Excellent for simple web apps and APIs with small teams; limited control (no sidecars, no background workers in the same service, fewer networking options). **Elastic Beanstalk** is the older PaaS over EC2/ASG/ALB; still supported, less recommended for new work. **Lightsail** is the simplest VPS-style offering for very small projects.

## Choosing

:::fde
Decision sketch for a typical client web application: API and workers on **ECS Fargate** (ARM), scaled on ALB requests and queue depth; scheduled jobs as ECS scheduled tasks or **Lambda**; event glue (S3 uploads, webhooks fan-out) on **Lambda** with SQS; frontend on S3 + CloudFront; data on RDS/ElastiCache/S3. Pick **App Runner** when the app is a single web service and the client wants the least to operate; pick **EC2** when a dependency demands a VM or the client's team only knows VMs; pick **EKS** when the client already runs it well or genuinely needs a Kubernetes platform. Document the choice and its triggers as an ADR.
:::

## Common mistakes

- ECS services without `deployment_circuit_breaker`; failed deploys stall forever.
- `minimum_healthy_percent` 50 on a two-task service; half capacity on every deploy.
- Task role and execution role confused or merged with broad permissions.
- Fargate tasks in public subnets with public IPs (to reach ECR) instead of private subnets with NAT or endpoints.
- Lambda functions in a VPC without NAT/endpoints, timing out on AWS API calls.
- Lambda without reserved concurrency connecting to RDS; connection exhaustion (use RDS Proxy).
- Giant Lambda monoliths; or Lambda for a 24×7 high-RPS API.
- Ignoring ARM/Graviton on Fargate and Lambda (cheaper, often faster).
- EKS for one service.
