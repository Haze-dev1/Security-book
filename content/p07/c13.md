## CloudWatch metrics

Every AWS service publishes metrics to CloudWatch namespaces (`AWS/ApplicationELB`, `AWS/ECS`, `AWS/RDS`, `AWS/Lambda`, `AWS/SQS`…) at 1- or 5-minute resolution (enable detailed monitoring for 1-minute EC2 metrics). You add **custom metrics** via the CloudWatch agent (memory, disk, processes), the **Embedded Metric Format** (structured log lines that CloudWatch turns into metrics with no API calls: ideal for Lambda and containers), `PutMetricData` from SDKs, or OpenTelemetry exporters. Custom metrics are billed per metric per month; high-cardinality dimensions (one metric per user) get expensive fast. **Metric math** combines series (error rate = 5xx / requests); **anomaly detection** bands learn seasonality; **Metrics Insights** queries across dimensions with SQL-like syntax. **Container Insights** (ECS/EKS) and **Lambda Insights** add per-task/function resource metrics.

The metrics that matter per component (Part XI chapter 4's golden signals): ALB request count, 4xx/5xx (ELB and target), target response time percentiles, healthy host count; ECS service CPU/memory utilisation and running task count; RDS CPU, connections, free storage, read/write latency, replica lag; SQS visible messages and age of oldest message; Lambda errors, throttles, duration p99, concurrent executions; application-level request rate, error rate and latency per route via EMF.

## CloudWatch Logs

Log groups per application and environment (`/client-a/prod/api`), streams per task or instance; **retention set on every group** (defaults to never expire); encryption with KMS for sensitive logs; **subscription filters** to stream to OpenSearch, Kinesis or Lambda; **Logs Insights** for ad-hoc queries; **metric filters** turning log patterns into metrics (count of `"level":"error"`, or a specific exception); **data protection policies** to detect and mask PII (Part IV chapter 23). Structured JSON logs (Part XI chapter 1) make Insights queries trivial:

```sql
fields @timestamp, request_id, route, status, duration_ms
| filter status >= 500
| stats count() as errors, pct(duration_ms, 99) as p99 by route
| sort errors desc
```

Shipping: ECS `awslogs` driver or FireLens; Lambda automatic; EC2 via the CloudWatch agent (Part V chapter 9); EKS via Fluent Bit. Costs: ingestion is the dominant line ($0.50/GB in us-east-1 standard class; the Infrequent Access class is cheaper for logs you rarely query); storage per GB-month; Insights per GB scanned. Control volume with log levels and sampling, not by dropping errors.

## Alarms

An alarm watches one metric (or a metric math expression) against a threshold over N of M evaluation periods and transitions between OK, ALARM and INSUFFICIENT_DATA, sending notifications to SNS (email, Slack via Chatbot, PagerDuty/Opsgenie, Lambda) on state change. **Composite alarms** combine several (page only when error rate *and* traffic are both abnormal, or when any of a service's critical alarms fire, avoiding storms). Design rules (Part XI chapter 5): page on user-facing symptoms (5xx rate, p99 latency, queue age, health check failures), ticket on causes and capacity (CPU, disk, connections), use percentiles and rates rather than raw counts, require 2–3 consecutive periods to avoid flapping, treat missing data deliberately (`treat_missing_data = "breaching"` for health signals, `"notBreaching"` for sparse metrics), and give every alarm a runbook link in its description.

```hcl
resource "aws_cloudwatch_metric_alarm" "api_5xx_rate" {
  alarm_name          = "client-a-prod-api-5xx-rate"
  alarm_description   = "Target 5xx rate > 2% for 3 minutes. Runbook: https://wiki/runbooks/api-5xx"
  comparison_operator = "GreaterThanThreshold"
  evaluation_periods  = 3
  threshold           = 2
  treat_missing_data  = "notBreaching"
  metric_query { id = "e", expression = "IF(req > 50, 100 * err / req, 0)", label = "5xx %", return_data = true }   # ignore when traffic is tiny
  metric_query { id = "err", metric { namespace = "AWS/ApplicationELB", metric_name = "HTTPCode_Target_5XX_Count", period = 60, stat = "Sum", dimensions = { LoadBalancer = aws_lb.main.arn_suffix, TargetGroup = aws_lb_target_group.api.arn_suffix } } }
  metric_query { id = "req", metric { namespace = "AWS/ApplicationELB", metric_name = "RequestCount", period = 60, stat = "Sum", dimensions = { LoadBalancer = aws_lb.main.arn_suffix, TargetGroup = aws_lb_target_group.api.arn_suffix } } }
  alarm_actions = [aws_sns_topic.pager.arn]
  ok_actions    = [aws_sns_topic.pager.arn]
}
```

A starter alarm set for the reference architecture: target 5xx rate; ALB 5xx count (ALB-generated); p99 target response time; unhealthy host count ≥ 1; ECS running tasks < desired; RDS CPU > 80% for 15 min, free storage < 20%, connections > 80% of max, replica lag; SQS oldest message age; Lambda error rate and throttles; NAT `ErrorPortAllocation`; certificate `DaysToExpiry` < 21; Route 53 health check failed; budget and anomaly alerts; GuardDuty/CloudTrail security alarms (chapter 12). **Synthetics canaries** run scripted checks (load the login page, call an endpoint) from outside every minute and alarm on failure or latency: the external view that catches DNS, certificate and CDN failures your internal metrics miss.

## Dashboards

One dashboard per service with the golden signals at the top, saturation below, dependencies at the bottom; one overview per environment. Build them in IaC (dashboard JSON) so they exist for every environment. Keep them for diagnosis during incidents; alarms, not dashboards, detect problems (Part XI chapter 3).

## X-Ray and tracing

**X-Ray** collects traces: segments and subsegments per request across services (ALB → ECS → RDS/SQS → Lambda), showing where time goes and where errors originate, with a service map. Instrument with the X-Ray SDK or, preferably, **OpenTelemetry** via the AWS Distro for OpenTelemetry (ADOT), exporting to X-Ray (and optionally elsewhere); the trace header propagates through ALB (`X-Amzn-Trace-Id`), SQS message attributes and HTTP calls. Sample (1 request/second plus 5% by default) to control cost; always capture errors. **Application Signals** builds SLO dashboards and service-level views on top of these traces and metrics with minimal configuration. Part XI chapter 2 covers tracing design.

## Systems Manager

A fleet management toolbox for EC2 (and on-premises servers registered as managed nodes) via the SSM agent and an instance role:

- **Session Manager**: shell and port forwarding without SSH, logged (Part II chapter 16).
- **Run Command**: execute scripts across instances by tag (restart a service everywhere; collect diagnostics) with output in S3/CloudWatch.
- **Patch Manager**: baselines, maintenance windows, compliance reports (Part V chapter 12).
- **State Manager** and **Automation**: enforce configuration and run runbooks (AMI building, instance recovery, remediation of Config findings).
- **Parameter Store**: configuration and secrets (chapter 12).
- **Inventory** and **Fleet Manager**: what is installed where; a console view of nodes.
- **Incident Manager**: on-call schedules, escalation, response plans integrated with alarms (an alternative to PagerDuty for AWS-centric teams).
- **OpsCenter**: operational work items aggregating alarms and findings.

For Fargate-based systems SSM matters less (no hosts), apart from Parameter Store and ECS Exec (which uses Session Manager under the hood).

## AWS Backup

A central policy-based backup service across RDS, Aurora, DynamoDB, EBS, EFS, S3, FSx, EC2 and more. **Backup plans** define schedules, retention, lifecycle to cold storage, and **copy actions** to other Regions/accounts; **resource selections** by tag (`Backup = daily`) so new resources are covered automatically; **backup vaults** with KMS encryption and **Vault Lock** (immutability: even administrators cannot delete backups before retention ends); **restore testing** plans that automatically restore backups on a schedule and run validation (the automated version of Part V chapter 11's drill); cross-account management via the organisation. Audit Manager/Backup Audit Manager reports compliance with backup policies. Use it as the single backup system for client accounts, with a locked vault in the backup account, and treat its restore-testing reports as evidence.

```hcl
resource "aws_backup_plan" "prod" {
  name = "client-a-prod-daily"
  rule {
    rule_name         = "daily"
    target_vault_name = aws_backup_vault.prod.name
    schedule          = "cron(0 2 * * ? *)"
    start_window      = 60
    completion_window = 240
    lifecycle { cold_storage_after = 30, delete_after = 365 }
    copy_action { destination_vault_arn = aws_backup_vault.dr_other_region.arn, lifecycle { delete_after = 365 } }
  }
}
resource "aws_backup_selection" "by_tag" {
  name         = "tagged"
  plan_id      = aws_backup_plan.prod.id
  iam_role_arn = aws_iam_role.backup.arn
  selection_tag { type = "STRINGEQUALS", key = "Backup", value = "daily" }
}
```

## Operating rhythm

Daily: glance at the environment dashboard and alarm state; review new security findings. Weekly: Security Hub and Config review; cost graph; backup job status and restore-test results; alarm noise review (any alarm that fired without action gets tuned or deleted). Monthly: patch compliance; capacity trends; dashboard and runbook updates; a game day or restore drill (Part XI chapter 9).

## Common mistakes

- Log groups with infinite retention; CloudWatch bill exceeds compute.
- Alarms on raw counts (`5xx > 10`) that fire at 3 a.m. for a traffic blip and miss a 30% error rate at low traffic.
- No external synthetic check; internal metrics green while DNS is broken.
- Dashboards nobody opens as the "monitoring strategy"; no alarms route to a human.
- Missing-data handling left default; alarms stuck in INSUFFICIENT_DATA.
- Backups configured per resource by hand; new RDS instance never backed up; no cross-account copy; never restored.
- SSM agent missing from custom AMIs; no way to reach instances during an incident.
- Tracing never enabled; latency investigations by guesswork.
