## The problem

EC2 is the most flexible compute on AWS and therefore the one with the most ways to run badly: the wrong instance family, a hand-built image nobody can reproduce, a single instance with no replacement path, public IPs and open ports, long-lived keys on the box. Used well, EC2 with Auto Scaling Groups and golden AMIs gives you immutable, self-healing fleets; used casually, it gives you pets.

## Instances

An EC2 instance is a VM (Part V chapter 1) defined by: an **AMI** (root volume image plus metadata), an **instance type** (family, generation, size: `m7g.large` = general purpose, 7th generation, Graviton, large), a **subnet** and **security groups**, an **IAM instance profile** (the role the instance assumes), **user data** (first-boot script or cloud-config, Part V chapter 2), **storage** (EBS volumes; instance store on some types), **key pair** (avoid; use SSM), **metadata options** (require IMDSv2), **tags**, and optional placement (dedicated host/tenancy, placement groups).

```hcl
resource "aws_launch_template" "app" {
  name_prefix   = "client-a-prod-app-"
  image_id      = data.aws_ami.app_golden.id             # from Packer, filtered by tag and newest
  instance_type = "m7g.large"
  iam_instance_profile { name = aws_iam_instance_profile.app.name }
  vpc_security_group_ids = [aws_security_group.app.id]
  user_data = base64encode(templatefile("${path.module}/user-data.sh", { app_version = var.app_version, env = "prod" }))

  metadata_options {
    http_tokens                 = "required"              # IMDSv2 only (SSRF defence, Part IV ch.12)
    http_put_response_hop_limit = 1
    instance_metadata_tags      = "enabled"
  }
  block_device_mappings {
    device_name = "/dev/xvda"
    ebs { volume_size = 30, volume_type = "gp3", encrypted = true, delete_on_termination = true }
  }
  monitoring { enabled = true }                            # 1-minute CloudWatch metrics
  network_interfaces { associate_public_ip_address = false, security_groups = [aws_security_group.app.id] }
  tag_specifications { resource_type = "instance", tags = merge(local.tags, { Name = "client-a-prod-app" }) }
  update_default_version = true
}
```

Choosing a type: start general purpose (m7g / m7i), measure (Part V chapter 10), then move to compute-optimised (c) for CPU-bound, memory-optimised (r) for caches and databases, burstable (t) for dev/staging and light services. Prefer Graviton (`g`) for 20–40% better price-performance when your stack has ARM builds. Newer generations are cheaper per unit of performance than older ones; `m5` is rarely the right answer in 2026.

## AMIs

An AMI is the template an instance boots from. Three strategies:

1. **Vendor AMI + user data**: Ubuntu/Amazon Linux official image; everything installed at boot. Simple; slow boots (minutes of apt installs); fragile (repository outages break launches); drift between instances launched at different times.
2. **Golden AMI**: a pre-built image (Packer) with OS hardening, agents, runtime and sometimes the application; user data only sets environment-specific configuration. Fast, consistent boots; the image is scanned and versioned; rollback is "previous AMI". The right approach for fleets.
3. **Containers on EC2**: the AMI is just the ECS/EKS-optimised image; applications are images (Part VI). The AMI still needs updating on a schedule.

```hcl
@file: packer/app.pkr.hcl (excerpt)
source "amazon-ebs" "app" {
  region        = "eu-west-1"
  instance_type = "m7g.large"
  source_ami_filter {
    filters     = { name = "ubuntu/images/hvm-ssd-gp3/ubuntu-noble-24.04-arm64-server-*", virtualization-type = "hvm" }
    owners      = ["099720109477"]   # Canonical
    most_recent = true
  }
  ssh_username  = "ubuntu"
  ami_name      = "client-a-app-{{timestamp}}"
  encrypt_boot  = true
  tags          = { Project = "client-a", Role = "app", BuiltAt = "{{timestamp}}", GitSha = var.git_sha }
}
build {
  sources = ["source.amazon-ebs.app"]
  provisioner "ansible" { playbook_file = "ansible/harden-and-install.yml" }     # Part V chapters 4, 5, 9, 10
  provisioner "shell" { inline = ["sudo apt-get clean", "sudo rm -rf /var/lib/apt/lists/*", "sudo cloud-init clean"] }
}
```

Lifecycle: build weekly (and on security advisories) in CI; scan with Inspector; tag with the source commit; keep the last N; deregister old ones and delete their snapshots (they cost money); **never** modify an AMI's instances in place. Share across accounts with the organisation when the same base serves several environments. AWS **EC2 Image Builder** is the managed alternative to Packer.

## Auto Scaling Groups

An ASG maintains a desired number of instances from a launch template across subnets (AZs), replaces instances that fail health checks, scales on policies, and integrates with load balancers (registers instances in target groups). Even for a fixed-size fleet (desired = min = max = 2), an ASG gives you AZ spread and self-healing; a lone instance outside an ASG is a pet.

```hcl
resource "aws_autoscaling_group" "app" {
  name                = "client-a-prod-app"
  min_size            = 3
  max_size            = 12
  desired_capacity    = 3
  vpc_zone_identifier = module.vpc.private_subnets
  launch_template { id = aws_launch_template.app.id, version = "$Latest" }
  target_group_arns   = [aws_lb_target_group.api.arn]
  health_check_type         = "ELB"                       # use the ALB's health check, not just EC2 status
  health_check_grace_period = 120                         # boot + app start + first probe; too short → replacement loop
  default_cooldown          = 60
  termination_policies      = ["OldestLaunchTemplate", "OldestInstance"]
  instance_refresh {
    strategy = "Rolling"
    preferences { min_healthy_percentage = 90, instance_warmup = 120, auto_rollback = true }
    triggers = ["launch_template"]                         # new AMI → automatic rolling replacement
  }
  tag { key = "Name", value = "client-a-prod-app", propagate_at_launch = true }
  lifecycle { ignore_changes = [desired_capacity] }        # scaling policies own the desired count
}

resource "aws_autoscaling_policy" "cpu" {
  name                   = "target-cpu-55"
  autoscaling_group_name = aws_autoscaling_group.app.name
  policy_type            = "TargetTrackingScaling"
  target_tracking_configuration {
    predefined_metric_specification { predefined_metric_type = "ASGAverageCPUUtilization" }
    target_value = 55
  }
}
```

Scaling policies: **target tracking** (hold a metric at a value: CPU, ALB requests per target, a custom queue-depth metric) is the simplest and usually best; **step scaling** for custom thresholds; **scheduled** scaling for known patterns (office hours, batch windows); **predictive** scaling for cyclical loads. Scale-in protection and lifecycle hooks let instances finish work (drain connections, flush logs) before termination; the ALB's deregistration delay handles in-flight HTTP (Part II chapter 13). Warm pools pre-initialise instances for faster scale-out when boots are slow.

**Instance refresh** is how you deploy a new AMI or launch template version: a rolling replacement honouring minimum healthy percentage with automatic rollback on failure. Combined with golden AMIs this is immutable infrastructure for VMs (Part V chapter 12).

## Storage choices

Root volume: gp3, encrypted, sized small (OS plus logs headroom); application data on separate volumes or, better, in managed services. Instance store (local NVMe on `d`/`i` types and many others) is fast and free with the instance, lost on stop; use for caches and scratch. EBS volume types and snapshots: Part V chapter 6, chapter 10 of this part.

## Access and operations

No SSH key pairs; SSM Session Manager via the instance role (`AmazonSSMManagedInstanceCore`) with interface endpoints or NAT for the SSM API (Part II chapter 16). CloudWatch agent for memory and disk metrics and logs (Part V chapters 9–10). Patch Manager or AMI rotation for updates (Part V chapter 12). EC2 status checks (system and instance) with an alarm that recovers or replaces the instance.

## Purchasing

On-demand for variable and uncertain load; **Savings Plans** (compute or EC2 instance) for the measured baseline, 1 or 3 years; **Spot** for stateless workers and CI through ASG mixed-instances policies with capacity-optimised allocation and multiple instance types; **Reserved Instances** mostly superseded by Savings Plans for EC2 (still relevant for RDS). Right-size first (chapter 4).

## Common mistakes

- Single instances outside ASGs; no self-healing.
- `health_check_type = "EC2"` with a hung application that passes EC2 checks forever; use ELB checks.
- Grace period shorter than boot; endless replacement loop that looks like "instances keep dying".
- IMDSv1 allowed; SSRF steals role credentials.
- Public IPs on application instances.
- Hand-modified instances; "snowflake" fleets; AMIs built by hand from a running instance.
- Old AMIs and snapshots accumulating cost; or deleting the AMI the ASG still references.
- Choosing old generations or ignoring Graviton.
- Spot for stateful or latency-critical components.

## Exercises

1. Build a hardened golden AMI with Packer and Ansible; launch it via a launch template with IMDSv2 required and no public IP; connect with SSM.
2. Create an ASG of 2 behind an ALB with ELB health checks; stop the application on one instance and time the replacement; then set a too-short grace period and observe the loop.
3. Trigger an instance refresh with a new AMI version and watch the rolling replacement; roll back by pointing the launch template at the previous AMI.
