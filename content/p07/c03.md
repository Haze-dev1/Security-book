## The problem

The access key pair (`AKIA…`/secret) was the original way to call AWS APIs, and it remains the most common thing attackers find in repositories, laptops and CI logs. A leaked key is valid until someone notices and rotates it, which averages weeks. **Temporary credentials** expire on their own (15 minutes to 12 hours), are issued per session with an audit trail, and can be scoped further at issue time. Every AWS workflow in 2026 can run without a single long-lived key; this chapter shows how.

## STS and temporary credentials

The Security Token Service issues short-lived credential triplets (access key, secret, **session token**) through:

- **AssumeRole**: an authenticated principal assumes a role, receiving credentials with the role's permissions for a session (default 1 hour, up to 12 as configured on the role). Used for cross-account access, privilege separation, and by SSO and CI.
- **AssumeRoleWithWebIdentity**: exchange an OIDC token (from GitHub Actions, EKS, Cognito, Google) for role credentials. No AWS secret involved anywhere.
- **AssumeRoleWithSAML**: federation from enterprise IdPs.
- **GetSessionToken**: for IAM users to obtain MFA-protected session credentials (legacy).
- **Automatic**: EC2 instance profiles, ECS task roles and Lambda execution roles deliver rotating credentials to the workload via metadata endpoints; the SDKs fetch and refresh them transparently.

Every STS call appears in CloudTrail with the assumed role session name, so "who did this?" is answerable even through role chains, provided you set meaningful session names (`--role-session-name ana.lopez`).

## IAM Identity Center for humans

IAM Identity Center (formerly AWS SSO) is the way humans should access AWS: a single sign-on portal, backed by its own directory or your IdP (Entra ID, Okta, Google Workspace via SAML/SCIM), granting **permission sets** (role templates) on specific accounts to users and groups, with MFA enforced and sessions of configurable length.

Setup outline: enable Identity Center in the management account (or delegate administration to a security account); connect the IdP or create users; create permission sets (`ReadOnly`, `Developer`, `PowerUser`, `Administrator`, each a managed or custom policy plus optional boundary); assign groups to accounts with permission sets; enforce MFA (prefer phishing-resistant: passkeys/security keys) and a session duration (1–8 hours; shorter for admin sets). Offboarding happens at the IdP; provisioning via SCIM keeps groups in sync.

```bash
aws configure sso                       # one-time: start URL, Region, then pick account and role; creates a profile
# ~/.aws/config
# [sso-session company]
# sso_start_url = https://company.awsapps.com/start
# sso_region = eu-west-1
# sso_registration_scopes = sso:account:access
# [profile client-a-prod]
# sso_session = company
# sso_account_id = 123456789012
# sso_role_name = Developer
# region = eu-west-1
# output = json
aws sso login --sso-session company     # browser auth + MFA; caches a short-lived token
aws sts get-caller-identity --profile client-a-prod
export AWS_PROFILE=client-a-prod        # tools and SDKs pick it up
```

No access keys are created; the CLI holds a cached SSO token and fetches role credentials as needed, all expiring within hours.

## The credential provider chain

SDKs and the CLI look for credentials in order: explicit parameters in code (avoid), environment variables (`AWS_ACCESS_KEY_ID`/`AWS_SECRET_ACCESS_KEY`/`AWS_SESSION_TOKEN`, or `AWS_PROFILE`), the shared config/credentials files (`~/.aws/config`, `~/.aws/credentials`) including SSO and `role_arn` profiles, the container credential endpoint (ECS task roles), and finally the EC2 instance metadata (instance profile). Understanding the order explains the classic mistakes: a stale `AWS_ACCESS_KEY_ID` in a shell overriding your SSO profile; a developer's `~/.aws/credentials` baked into a Docker image; code that "worked locally" because the laptop had keys and fails on ECS because the task role lacks a permission.

Rules: code never contains or loads credentials explicitly; local development uses SSO profiles; containers and servers use their attached roles; CI uses OIDC. If something needs an environment variable, it is `AWS_PROFILE` or `AWS_REGION`, never a secret.

## Profiles for roles and accounts

```ini
@file: ~/.aws/config (excerpt)
[profile client-a-prod-admin]
sso_session = company
sso_account_id = 123456789012
sso_role_name = Administrator
region = eu-west-1

[profile client-b-deploy]             # assume a cross-account role from an SSO profile, with MFA and session name
source_profile = client-a-prod
role_arn = arn:aws:iam::999988887777:role/ConsultancyDeploy
external_id = 7f3a9c2e-client-b
role_session_name = ana.lopez
duration_seconds = 3600
```

```bash
aws s3 ls --profile client-b-deploy                           # chain: SSO → role in client B
aws sts assume-role --role-arn arn:aws:iam::999988887777:role/ConsultancyDeploy --role-session-name ana.lopez --external-id 7f3a9c2e-client-b --duration-seconds 3600
# returns temporary credentials to export for tools that do not understand profiles
```

Tools: `aws-vault` (stores credentials in the OS keychain, serves them via a local metadata-style server so secrets never sit in plaintext files), `granted`/`assume` (fast role switching), `aws-sso-util`. The CLI's built-in SSO support covers most needs now.

## CLI essentials

```bash
aws configure list                                   # which profile/credentials are active and where they came from
aws sts get-caller-identity                          # who am I? (first command in any debugging session)
aws ec2 describe-instances --query 'Reservations[].Instances[].{id:InstanceId,state:State.Name,ip:PrivateIpAddress,name:Tags[?Key==`Name`]|[0].Value}' --output table
aws logs tail /client/prod/api --follow --since 10m
aws ssm start-session --target i-0abc123
aws s3 sync ./dist s3://client-a-prod-frontend --delete
aws cloudformation describe-stack-events --stack-name prod --max-items 20
aws --cli-auto-prompt                                # interactive completion
```

Set `cli_pager=` in config to disable paging in scripts; use `--query` (JMESPath) and `--output` for parseable results; prefer the SDK for anything beyond one-liners.

## Credentials in CI

GitHub Actions, GitLab CI and others support OIDC federation: the job presents a signed identity token; `AssumeRoleWithWebIdentity` exchanges it for role credentials; the role's trust policy restricts which repository, branch and environment may assume it. Zero stored secrets, per-job credentials, full CloudTrail attribution. Part X chapter 2 has the configuration; Part IV chapter 18 the policy.

```json
// Trust policy: only main branch of one repository, via GitHub's OIDC provider
{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Principal": {"Federated": "arn:aws:iam::123456789012:oidc-provider/token.actions.githubusercontent.com"},
    "Action": "sts:AssumeRoleWithWebIdentity",
    "Condition": {
      "StringEquals": {"token.actions.githubusercontent.com:aud": "sts.amazonaws.com"},
      "StringLike": {"token.actions.githubusercontent.com:sub": "repo:client/app:ref:refs/heads/main"}
    }
  }]
}
```

## When long-lived keys are unavoidable

Some third-party tools and legacy systems demand an access key. Then: a dedicated IAM user per integration with a minimal policy and no console access; keys stored in the integration's secret store; rotation every 90 days with two active keys during the swap; CloudTrail alerts on use from unexpected sources; Access Analyzer unused-key findings; and a plan to remove it. Record each such key in the secrets inventory (Part IV chapter 17).

## Hygiene for laptops and shared machines

Never paste keys into terminals that log history or into chat; scan `~/.aws/credentials` and shell history for keys and delete them; prefer SSO so there is nothing to leak; set short session durations; lock screens; use `aws-vault` or the SSO cache rather than plaintext files; and when a laptop is lost, revoke the user's SSO sessions and rotate anything it held.

## Common mistakes

- IAM users with access keys for every engineer.
- Keys in `~/.aws/credentials` copied into Docker images or CI variables.
- `AWS_ACCESS_KEY_ID` left exported in a shell, silently overriding profiles.
- Role session names like `session1`, making CloudTrail useless.
- Sessions of 12 hours for administrator permission sets.
- Trust policies on CI roles without repository/branch conditions.
- Forgetting `aws sts get-caller-identity` and operating in the wrong account.
